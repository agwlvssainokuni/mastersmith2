# NFR Design の質問 — U3 u3-businessdata-screens

U3 は、業務データの一覧・詳細・作成・更新の画面を受け持つ単位です（ui。U1・U2・U4 に依存します）。成果物は、performance・security・logical-components・traceability の4つです。

## 前の段から持ち越した論点

**NFR 要件の「後の段に回すこと」**
- 記憶の作り・上限・消す時（U3-NFR4.22）
- 「1回だけ飛ばす」の旗（U3-NFR7.11）

**NFR 要件のレビューで、承認の場で扱いを決めなかったもの**
- R-02: 100×100 の描画の試し（→ Q1）

- R-04: 長さの数え方

**承認の場の決定**
- U3 R-01: 見本の DB の管理者の資格情報は、プロセスの環境変数で渡す（仕組みは Infrastructure Design）。
- nullable は U2 が足す。lookup は外す。

**同じ段の U1・U2・U4 のレビューの指摘のうち、U3 に当たるもの（先に避ける）**
- U4 R-01: menuOwner は Dropdown のトリガーだけ。
- U4 R-03: owner の末尾は数字か `r<n>` だけ。
- U2 R-04: 時間切れや断絶が 409 に隠れうる。
- U1 R-01: fieldErrors の無い 400。

## 読んで分かった事実

- ログイン状態（`LoginState`）に、利用者を見分ける値が無い。トークンの更新で利用者が替わっても、未ログインの状態を通らない。（→ Q2）
- 今の API の呼び出しは、送った後に応答が届かなかった場合も「通信の失敗」にする。書き込みでは「保存されたか分からない」に当たり、送り直すと二重に作るおそれがある。（→ Q3）
- 代表の流れ 180 のために E2E のアプリへ対象DB の接続先を渡すと、040 の前提（接続先が無い）が崩れる。（Infrastructure Design へ渡す）

## 決まっていること（質問にしない）

**依存と更新**
- 新しい依存は足さない。業務データの画面は `lazy` で登録する。
- ポーリング・自動の再送・独自の時間切れは置かない。
- 403 で、業務データの API を送り直さない。

**長さと本文の上限**
- 長さはコードポイントで数える（`countCodePoints` と Java の `codePointCount` は同じ数え方で、R-04 は解ける）。
- 本文は `JSON.stringify` を1回だけ行い、実際に送るバイト数で確かめる。

| 対象 | 上限 |
|---|---|
| 検索・主キーの値 | 1,000 字 |
| 書き込みの値 | 10,000 字 |
| 読み取り・削除の本文 | 64 KB |
| 作成・更新の本文 | 4 MiB |

**値と画面の範囲**
- 日時の入力は秒まで（秒より細かい値は送らない）。
- bit と空間の型は「（バイナリ）」で出す。
- page は 1〜1,000,000。

**部品・記録・検査**
- 行の操作の `data-testid` は、Dropdown を包む span に `tables-row-actions-r<n>` で置く。行のリンクは `tables-row-link-r<n>`。
- axe は 20 組のすべてで流す。規則と要素は外さず、記録は U4 の鍵の形にする。
- 主キー・行の値を、道・履歴・ブラウザの保存・DOM・`console`・`document.title`・例外の文・知らせに置かない。履歴の印は乱数で作る。
- 応答は `unknown` で受けて形を確かめる。`lookup`・知らない列挙の値・欠けた `formPart`／`nullable`／`required` は、形の崩れとして扱う。

## Q2. 記憶を消す時の知らせの受け方と、作業ロールの切り替え（U3-NFR4.22・R-03）

A. 次の3つを決める（推奨）。
- 骨組みの `app/login-state` に「ログインの範囲が変わった」の知らせを足す。ログイン⇄未ログインの切り替わりのたびに、記憶を全部消す（ログアウト・更新の失敗・新しいログインを覆う）。
- 作業ロールの roleId が変わったら、記憶を全部消す。詳細と更新の画面は、一覧へ移る。
- 既知の制約を記録する。別のタブで別の利用者がログインし、このタブのトークンの更新がその利用者に替わる場合は、記憶が消えない（サーバーが毎回判定するため、残るのは前の利用者の検索の条件だけ）。

B. A に加えて、利用者の替わりも見分ける。auth が、更新の応答の利用者が前と違うときに `LoginState` の新しい項目を進める（auth と骨組みの型を変える、範囲の外の変更）。

C. ログインの切り替わりだけで消し、作業ロールの切り替えでは消さない（定義は作業ロールを含む ID で読み直す）。

## Q3. 書き込みの結果が分からない・読めないときの表示

A. 次の3つに出し分ける（推奨）。
- 結果が分からないとき（応答が届かない・500・503 `BUSINESS_TARGET_DB_TIMEOUT`）
  - 「保存されたか分かりません」と出し、確かめる入口を出す。
  - 入口は、作成なら一覧で探す、更新なら開き直す、削除なら一覧を読み直す。
- 2xx で本文の形が崩れているとき
  - 保存できたとして「保存しました」と出し、一覧へ戻る。
  - D5 との差として記録する。
- 保存されていないとき（503 `UNAVAILABLE`・409・400・413）
  - 機能設計の 6.1 のとおりに出す。
- どの場合も、自動では送り直さない。

B. 分からない扱いは TIMEOUT だけにする。応答が届かない・500・2xx の崩れは、6.1 の通信の失敗のまま（送り直しで二重に作るおそれは残る）。

## Q4. axe の E2E 185 の組み立てと 200% の拡大（U3-NFR5.6・U3-NFR7.8）

- 100×100 の行は、時間の測りの件だけで使う。
