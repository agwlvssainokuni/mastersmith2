# Infrastructure Design の質問 — U3 u3-businessdata-screens

U3 は ui の単位です。画面は、WAR に同梱した `dist` のまま配ります。この段の中心は、代表の流れの E2E 180 を、本物の見本の PG の専用のスキーマで流すための仕組みです。

## 前の段から持ち越した論点

- NFR 要件の Q2: A。180 は本物の見本の PG の、流れ専用のスキーマで流す。170・185 は、見本の応答で差し替える。
- 承認の場の決定 U3 R-01。管理者の資格情報は、プロセスの環境変数で渡し、`SECRET_ENV_NAMES` に足す。
- 040 の前提「E2E の環境には対象DB の接続先が無い」との両立。
- U2 の Q5: A の一時のロール。U2 のレビュー R-01 は、これを成り立たせる道（届く道・資格情報・040）が未決だと指摘した。
- 専用のスキーマの作り方と消し方。
- E2E の時間。

## この PC の実行環境（読み取りで確かめた結果）

**見本の PG**
- PostgreSQL 18.6。PC にはポートを開けていない（`5432/tcp` だけ）。
- ロールは `target_admin` と `mastersmith_reader` だけ。PUBLIC は TEMPORARY を持っている。
- `pg_hba.conf` の設定:
  - コンテナの中のローカルのソケットと、コンテナの中のループバックは `trust`。パスワードなしで管理者に入れる。
  - 外からの接続は `scram-sha-256`。

**E2E の WAR**
- PC の上で `java -jar`（18081・一時の H2）として起動する。対象DB の環境変数は持たない。
- 全ファイルで1つの WAR を共有する（`workers: 1`）。
- Playwright 1.63 は、globalSetup より先に webServer を起動する。そのため、WAR が読む一時のロールの値は、Playwright を起動する前（Gradle の `e2eTest`）に作る必要がある。

**040 の警告**
- 040 の照合の警告は、設定が無ければ `TARGET_UNCONFIGURED`、DSL のスキーマ名が設定と違えば `SCHEMA_MISMATCH` の1件になる。適用は警告で止まらない。

## 決まっていること（質問にしない）

**範囲と一時のロール**
- 新しいコンテナ・移行は無い。戻しはイメージだけ。
- 180 は見本の PG を使う。170・185 は差し替えで流す。
- 一時のロールは、実行ごとに読み取り用と書き込み用の2つを作る（U2 の Q5: A）。
  - パスワードは乱数。
  - 権限は専用のスキーマの範囲だけ。DDL は与えない。
  - 前の実行の残りは、始めに消す。

**準備と片付け**
- 作る・消すのは Gradle の `e2eTest` が受け持つ（Playwright の前に作り、`finalizedBy` で消す）。
- 値は `Exec` の environment で渡し、WAR が引き継ぐ。`webServer.env` には置かない。
- 接続先は `127.0.0.1` にする（colima の IPv4 の学び）。
- SQL の値はコマンド行に入れず、psql の標準入力で渡す。ログには名前と件数だけを出す。
- `e2eTest` は始める前に見本の PG に届くかを確かめる。届かなければ、起動の手順を示して失敗する。起動・停止はしない（Mailpit と同じ扱い）。

**秘密の確かめ**
- `SECRET_ENV_NAMES` に一時のロールの値を足す。
- 報告の json と `test-results/` を検索する。
- 見本の行は架空の値だけにする。

**時間と CI**
- 時間は `caffeinate -dims` で包んで測る。U4 と同じ回にする。基準の 1.5 倍を超えたら諮る。
- B5・B6 は、統合の前に E2E の全件を流す。CI・verify は変えない。
- 全件の前提に、見本の PG の起動が加わる。

## Q1. E2E の WAR が見本の PG に届く道

A. 上乗せの compose ファイル（例 `docker/e2e/compose.targetdb-port.yaml`）で、`127.0.0.1:15432` だけを開ける（推奨）。
- E2E の前に、上乗せを付けて見本の PG を作り直す。ボリュームは残る。
- 上乗せを付けずに作り直せば、ポートは閉じる。`compose.yaml` の「開けない」は、既定のまま残る。
- 番号は `E2E_TARGETDB_PORT` で変えられる。

B. `compose.yaml` の見本の PG に、`127.0.0.1:15432` を常に開ける。管理者のパスワードで入れる口が、常に開く。

C. 転送だけをする小さなコンテナを `e2e` の profile で足す。新しいイメージの固定とライセンスの確かめが要る。

D. E2E の WAR をコンテナにして、compose の網に入れる。今の起動の形を大きく変える。

## Q2. 040 の前提との両立

A. WAR は1つのまま、040 の期待を `SCHEMA_MISMATCH` の警告に書き換える（推奨）。
- 対象DB の設定を渡し、スキーマは実行のスキーマにする。040 の DSL のスキーマは設定と違うため、警告は PG の中身によらず決まる。
- 書き換えは、既存の E2E の書き換えのため、本数に数えない。
- 未設定の経路は、サーバー側の結合テストと 135 の差し替えが受け持つ。
- 21 行の説明と README を直す。

B. WAR を2つにし、180 だけを対象DB の設定を持つ2つ目の WAR で流す。040 は変えない。起動が約 20〜30 秒増え、報告と秘密の確かめも2つに分かれる。

C. 040 も実行のスキーマ名で DSL を組み、本物の照合の結果を期待する。PG の中身で結果が変わりうる。

## Q3. 管理者の取り口（承認の場の決定 U3 R-01 との関係）

A. 管理者のパスワードを、プロセスに入れない（推奨）。
- DDL は `docker compose exec -T targetdb-postgres psql -U target_admin` で、コンテナの中のローカルのソケット（`trust`）から流す。README と U2 と同じ入り方で、新しい依存は要らない。
- プロセスの環境変数に入るのは、一時のロールの値だけ。それを `SECRET_ENV_NAMES` に足す。
- R-01 の目的は満たす。管理者の値をそもそも持たない点が、決定の文面との差になる。差として記録する。

B. R-01 の文面どおりにする。Gradle が `.env.targetdb` から管理者のパスワードを読み、プロセスの環境変数に入れ、15432 の TCP で DDL を流す（Gradle の JDBC なら、ドライバーが新しく要る）。

C. 開発者がシェルで、管理者のパスワードを export してから流す。

## Q4. 専用のスキーマとロールの名前と片付け

A. 名前に実行の印を入れ、終わりと始めの両方で消す（推奨）。
- 名前は次のとおり。
  - スキーマ: `e2e_biz_<UTC の時刻>_<16進 8 文字>`
  - ロール: `mastersmith_e2e_r_…`・`mastersmith_e2e_w_…`
- 終わりは、`finalizedBy` で、E2E が失敗しても次の順で消す。
  1. 接続を切る
  2. `DROP OWNED BY`
  3. `DROP ROLE`
  4. `DROP SCHEMA … CASCADE`
- 始めは、接頭辞に当たる前の残りを消す。`sales` と既存のロールには当たらない。
- 守りとして、ロールに `VALID UNTIL`（2 時間）を付ける。
- 消した件数をログに出す。

B. A と同じだが、`E2E_KEEP_TARGETDB=1` のときは、失敗の後も残して調べられるようにする（次の実行の始めに消える）。

C. ロールの名前は固定にし、実行ごとにパスワードだけを作り直す。

## Q5. 180 が使う行の用意

A. 準備のタスクが、代表の表を1つと架空の行を 21 件以上置く。180 は画面で、作成 → 詳細 → 更新 → 削除を流す（推奨）。
- 21 件は、ページ送りを通すための数。
- 表の定義の SQL は、リポジトリのファイル（ライセンスヘッダー付き）に置く。
- 180 の DSL は、同じ形を TS の側で組み、本物の応答と形を比べる。

B. 準備は空の表だけにし、行はすべて 180 が画面で作る（ページ送りまで通すと、時間が延びる）。

C. 準備は空の表だけにし、180 の始めに、書き込みの API で 21 件を作ってから画面を流す。

## Q6. PUBLIC の TEMPORARY が残っている見本の PG での扱い

今の見本の PG では、PUBLIC が TEMPORARY を持っています。U2 の REVOKE は配備のときの予定のため、このままでは 180 の一時の書き込みのロールが一時の表を作れます。

A. 準備のタスクで確かめ、残っていれば手順（REVOKE を exec で1回流す。U2 の README と同じ）を示して失敗する。見本の PG への REVOKE は、B6 の E2E の前に手で1回行う（推奨）。

B. 準備のタスクが、同じ REVOKE を毎回流す（何度流しても同じ結果になる。ただし、E2E が見本の DB 全体の権限を変える）。

C. E2E の一時のロールだけは許し、Mandated との差として記録する。
