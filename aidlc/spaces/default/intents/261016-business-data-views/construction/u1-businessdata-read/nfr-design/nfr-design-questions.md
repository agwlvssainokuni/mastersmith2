# NFR Design の質問 — U1 u1-businessdata-read

U1 は業務データの読み取りの単位です（service）。上流は、承認済みの NFR 要件と機能設計です。

## 前の段から持ち越した論点

**NFR 要件の「後の段に回すこと」**
- 長い文字の受け取る量を絞るやり方
- ヒープの見積もり
- 深い読み飛ばしと件数の重さ
- 時差の扱い
- `OTHER` の型の3種類の DB での振る舞い
- 型の誤りの SQLState の表
- 口（`TargetReadSession`）の置き場と例外の通り道

**NFR 要件の承認の場の決定**
- U1 R-01 は「通信の待ち（25 秒）以内に 503」に読み替え、実測する。
- U1 R-02 は、page の上限と、桁あふれしない計算を決める（→ Q4）。

**NFR 要件のレビューの Minor**
- R-03〜R-06（→ Q6）

## 決まっていること（質問にしない）

**接続と時間**
- 新しい依存は足さない。読み取りの接続（既定の候補にしない・読み取り専用・借りる待ち 3 秒）を使い、プールは 5 のまま。
- 時間の上限は、一覧が問い合わせごとに 5 秒、詳細が 5 秒。通信の待ちは 25 秒のまま。13 秒は約束しない。
- 内部DB の接続は、対象DB を借りる前に返し終える。対象DB は、1回の貸し出しにつき1本。
- 件数とページは同じ接続で読むが、トランザクションは張らない。2つが別の時点になりうることは、既知の制約とする。

**例外とログ**
- JDBC の例外は、JDBC を呼んだメソッドの中で受け、メッセージと原因を捨てる。各層の例外を TRACE に出す既存の仕組み（TraceAspect）に、メッセージを渡さないため。
- 口の部品は、次の2つに置く。
  - `targetdb.service`: 貸す・閉じる
  - `targetdb.domain`: 貸すときの値の型
- ログを出すのは、業務処理の層の1か所だけ。WARN で出し、キーは `reason`・`sqlState`・`vendorCode`・`exceptionClass`・`purpose` だけにする。

**長い値と並べ替え**
- 受け取る量は、選ぶ列を `SUBSTRING(列, 1, 上限＋1)` にして絞る。ドライバーは行を受け取りきってから渡すため、ストリームで読む形では絞れない。試しで裏付ける。
- 再試行と遮断器は置かない。
- 深い読み飛ばしは、主キーの索引に頼る。キーセットのページ送りは採らない（ページの番号の要件があるため）。
- 監視は、区画だけを足す。

## Q2. 時差つきの型を UTC にそろえるやり方の優先の順

MySQL・MariaDB の `timestamp` は、接続のタイムゾーンで読み書きされます。機能設計の承認の場では「接続の設定は変えない」と決めています。

A. 次の順で試す（推奨）。
1. まず接続の設定を変えない形で試す。PostgreSQL は JDBC の時差つきの型、MySQL・MariaDB は SQL の式（`UNIX_TIMESTAMP`・`FROM_UNIXTIME`）を使う。
2. 通らなければ、貸すたびに `SET time_zone='+00:00'` をかける形に切り替え、差を記録する。
3. どちらもだめなら、ADR-007 の「時差つきの型は読み取りだけ」を諮る。

B. 最初から、貸すたびに `SET time_zone='+00:00'` をかける（接続の状態を変え、スキーマの読み取りにも効く）。
C. ドライバーの設定で UTC に固定する（「接続の設定は変えない」と違う）。

## Q3. プールの借りる待ちの時間切れを、どの code にするか

## Q4. page の上限（R-02）

件数が読み飛ばす行の数以下なら行を読まないため、深い番号の重さは件数の問い合わせで止まります。上限が要るのは、桁あふれを防ぐためと、境界のテストのためです。

A. page は 1〜1,000,000 とし、超えたら 400 にする。読み飛ばす行の数は long で計算する。境界のテスト（1,000,000 は受け付け、1,000,001 は 400）を足す（推奨）
B. page は int の範囲とし、超える値は JSON の読み込みの誤りとして 400 にする

## Q5. 負荷の試験の悪い側の行の幅

100 カラムのすべてに長い値を入れると、表は 1〜3GB になります。この場合、対象DB の 512m の上限のもとでは、1 秒を満たせない見込みが高くなります。

A. 1行を約 2KB にする（推奨）。
- 型ごとの短い値を中心にし、TEXT の5本に 150〜300 字を入れる。1本だけ、10 行に数 MB の値を入れる。
- 試しの T6 で、この形の時間を3種類の DB で測る。
- 件数の1回が 300ms を超えたら、コード生成の前に ADR-007 の切り替え先（件数を「多数」と出す）を諮る。

B. 最悪の形（100 カラムすべてに長い値。1行は約 30KB）にする。満たせなければ、要件の変更を諮る。
C. 行の幅は B2 の台本で決め、試しでは時間を測らない。

- 件数を数え、読み飛ばす行の数が件数以上なら行を読まない。その後にページを読む。
- 長い値は `SUBSTRING` で上限＋1字に絞る。BINARY は選ばず、fetchSize は使わない。
