# NFR Design の質問 — U2 u2-businessdata-write

U2 は業務データの書き込みの単位です（service、U1 に依存）。上流は承認済みの NFR 要件・機能設計と、同じ段の U1 の NFR 設計です。

## 前の段から持ち越した論点

**NFR 要件の「後の段に回すこと」**
- 一意の事前の問い合わせと違反の後の確かめを、それぞれ1文にまとめる形
- 巻き戻しの後に同じ接続で確かめられるか（PG の 25P02）
- 件数の数え方
- SQLState の表
- 書き込みのアカウントの権限
- 時差の書き込み
- pattern の打ち切りの形
- 4 MiB の本文のヒープ
- 書き込みの型の名前と置き場（機能設計の R-08）
- 時間切れの監査の読み方（機能設計の R-05）

**NFR 要件の承認の場の決定**
- U2 R-01: 監査の値の切り詰めは businessdata の側で行い、AuditEvent は変えない。
- U2 R-02: 確定と巻き戻しの待ちを含めて、最悪の時間を算出し直す（→ Q4）。

**NFR 要件のレビューの Minor**
- R-03〜R-06（→ Q7）

**U1 の NFR 設計のレビューの指摘のうち U2 にも当たるもの**
- R-01・R-02・R-04 は、質問にせず、先に避ける形で設計に入れる。
  - 失敗した段を分ける部品に渡す。
  - 非検査の例外もメソッドの中で受ける。
  - 失敗した接続は捨てる。

## 見つかった穴（承認済みの機能設計に無いもの）

1. DB の型の精度を超える秒の端数が、誤りにならずに丸められる見込み。（→ Q6）
2. 日時の範囲の外・CHECK の違反・文字集合の不一致が BR6.1 の表に無く、500 になる。（→ Q6）
3. MySQL・MariaDB の REPEATABLE READ では、違反の後の確かめで、同時に確定した相手の行が見えないことがありうる。（→ Q2）

## 決まっていること（質問にしない）

**U1 にそろえる**
- 借りる失敗はすべて UNAVAILABLE にする。
- JDBC の例外は、呼んだメソッドの中で結果の型に変え、メッセージを捨てる。
- 時差のバインドの形は U1 と同じにする。
- 長さ 2 以上の bit と空間の型は入力にしない。
- ログを出すのは1か所だけにする。
- Performance Validation の対象DB の設定は U1 の F1 と同じにする。
- 再試行と遮断器は置かない。

**NFR 要件のまま**
- 文ごとの上限は 5 秒。書き込みのプールは 5、通信の待ちは 10 秒。
- 本文は 4 MiB／64KB。値は 10,000 字、主キーは 1,000 字。
- pattern は値ごとに 100 ms、合計 300 ms。
- 新しい依存は無い。

**監査の失敗の ERROR**
- 業務データの出来事では、監査の失敗の ERROR から `detail`・主キー・例外の cause を外し、例外のクラスの名前だけを残す。

**決まりのとおり**
- 書き込みの接続と資格情報は読み取りと分け、`.env` だけから受け取る。
- 書き込みのアカウントには DML だけを与える。
- テストはクラスごとのスキーマで行い、別の接続で読み直す。

**既存の境界テスト**
- `TargetDbBoundaryArchitectureTest` は、変えずに通る見込み（`TransactionTemplate` は当たらない）。

## Q2. 違反の後の確かめの形（穴 3）

A. 書き込みの文の直前にセーブポイントを置く（推奨）。
- 違反したらセーブポイントまで戻して確かめ、全体を巻き戻す。
- 書き込みのトランザクションは READ COMMITTED にし、同時に確定した行を確かめで見られるようにする。
- PG の 25P02 も起きない。
- BR6.2 の切り替え先を先に使う差になる（外から見える振る舞いは同じ）。
- W2 で通らなければ B にする。

B. BR6.2 の第一の形。巻き戻した後に、同じ接続で2つ目のトランザクションを続ける。分離のレベルは既定のままにする。

C. 分離のレベルは既定のままにし、A の形にする。カラムを示せないことは既知の制約にする。

## Q3. 書き込みの接続の通信の待ちと、時差の初期化を付ける場所

A. 書き込みのプールの設定で付ける（推奨）。
- 書き込みのプールは専用で、通信の待ちは 10 秒にする。
- MySQL・MariaDB の `SET time_zone`（と Q6 の `sql_mode`）は、接続を作るときに1回だけ流す（`connectionInitSql`）。
- 貸すたびに付けたり戻したりしないので、U1 の R-03・R-04 の形の誤りが起きない。
- U1 の「貸すたびに付ける」との差を記録する。

B. U1 と同じく、貸すたびに付けて戻す。
C. 通信の待ちはプールの設定で付け、時差の `SET` は貸すたびに流す。

## Q4. 最悪の時間の扱い（承認の場の U2 R-02）

確定・巻き戻し・戻しには文の上限が効かず、通信の待ち（10 秒）だけが効きます。机上の上限は次のとおりです。

| 道 | 机上の上限 |
|---|---|
| 成功の道 | 約 28〜31 秒 |
| 違反の道 | およそ 40 秒台 |

応答しない対象DB では、最初に止まった所で 10〜20 秒かかって失敗する見込みです。

A. 全体の上限は置かない（推奨）。
- 机上の上限の式と、W7 で止まる場所ごとに測った時間を並べて書く。
- 結合テストの合格の線は、実測に余裕を足して決める。
- 「およそ 18 秒」は、この値に読み替える。

B. 要求ごとの残りの時間（例: 25 秒）を持ち、各文の上限を「5 秒と残りの小さい方」にする。残りが足りなければ、確かめを飛ばす。作りが増える。

## Q5. 時間切れの監査の読み方（機能設計の R-05）

A. `AuditResult` に `UNKNOWN` を足し、時間切れの行の結果にする（推奨）。
- 列は `VARCHAR(16)` で CHECK も無いため、移行は要らない。
- アプリの本体は監査の行を読まないため、前の版へ戻しても動く。
- 既存のテストへの影響は、コード生成の計画で洗い出す。

B. 結果は FAILURE のままにし、`detail` に `"outcome":"UNKNOWN"` を足す。
C. 読み方の注記だけを、BR11.3 と README に書く。

## Q6. DB が黙って丸める値と、BR6.1 の表に無い拒否（穴 1・2）

A. 次の3つを行い、BR3.5・BR6.1 との差として記録する（推奨）。
1. 秒の端数が DB の型の精度を超えたら、`TOO_MANY_DIGITS` で拒む。
2. DB が拒んだ値（日時の範囲の外・CHECK の違反・文字集合の不一致など）は、409 `BUSINESS_SAVE_REJECTED` にする（カラムは示さない）。500 にはしない。
3. MySQL・MariaDB の書き込みの接続の `sql_mode` に、`STRICT_ALL_TABLES` を足す（セッションだけ）。

B. 1 と 2 だけを行い、厳しくない DB での切り詰めは既知の制約にする。
C. BR6.1 のまま（表に無い拒否は 500）とし、秒の端数の丸めは既知の制約にする。

## Q7. NFR 要件のレビューの Minor（R-03〜R-06）

A. 4つとも設計に取り込む（推奨）。
- R-03: 補助権限を持つ人が繰り返すと、監査の行が上限なく増えうる。これを既知の制約として書き、内部DB の大きさの基準の値を Observability Setup で記録する。
- R-04: 4 MiB は UTF-8 のまま送る前提で書く。エスケープが多いと、400 より先に 413 になる。境界のテストは、全カラムが4バイトの文字の最大の本文で行う。
- R-05: 締め切りを過ぎてから止まるまでの時間の上限を、W9 の合格の条件にする。
- R-06: 監査の移行の後方互換の結合テストと、既存のテストの洗い出しを、コード生成の計画の宿題に足す。

## Consolidated Summary Confirmation

**捨ての試し（Q1: A）**
- W1〜W12 を、優先の順に行う。
- リポジトリの外で行い、時間の上限は 3 時間。対象DB は1種類ずつ使い捨てで立てる。
- 結果の要点は、成果物の冒頭に写す。
- 試しで設計の前提が崩れたら、文書を書く前に諮る。

**performance-design**
- 書き込みの流れは、事前の問い合わせ（1文）→ セーブポイント → 書き込みの文 → 確定。
- 違反の道は、戻し → 確かめ（1文）→ 巻き戻し。
- p95 1 秒の予算は、W1・W7 の実測で配分する。
- pattern の式は、数を限って取っておく。
- k6 は既存の4つの場面に、大きな本文の専用の短い回（`bizCreateLarge`）を足す。

**security-design**
- 書き込みの SQL は、1つの部品だけで組み立てて実行する。セーブポイントと `SET` は定数の文にする。
- 非検査の例外も、メソッドの中で結果の型に変える。結果の型の `toString` は伏せる（U1 R-02 を先に避ける）。
- 監査の失敗の ERROR からは、`detail`・主キー・cause を外す。
- 書き込みのアカウントの権限は、W5 の結果で書く。PG の TEMP の権限は、基盤の設計へ引き継ぐ。

**scalability-design**
- 1要求で使う接続は、内部DB 1・書き込み 1・読み取り 0。
- 書き込みのプールは専用で 5 本。
- ヒープは W10 で書く。監査の行の増え方は既知の制約にする（R-03）。

**reliability-design**
- 失敗の分け方は、どの段で起きたかを部品に渡して行う（U1 R-01 を先に避ける）。
- 値の誤りと DB が拒んだ値は、409 `BUSINESS_SAVE_REJECTED` にする。秒の端数の精度を超えたら、`TOO_MANY_DIGITS` で拒む。MySQL・MariaDB の書き込みの接続は `STRICT_ALL_TABLES` にする（Q6: A）。
- 確定の失敗は「確定したか分からない」（TIMEOUT）とする。失敗した接続は捨てる（U1 R-04 を先に避ける）。
- 違反の後の確かめは、セーブポイントの形で、分離のレベルは READ COMMITTED（Q2: A）。
- 最悪の時間は全体の上限を置かず、机上の式と実測を並べる（Q4: A）。
- 通信の待ち（10 秒）と時差・`sql_mode` の初期化は、書き込みのプールの設定で付ける（Q3: A、U1 との差を記録）。

- 時間切れの監査の結果は `UNKNOWN`（Q5: A）。

**logical-components**
