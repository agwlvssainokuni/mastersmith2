# ユーザーストーリーの要否の評価 — business-data-views

## 判断

**Execute**（ユーザーストーリーを書く）

## 理由

- 利用者に見える機能を足す。業務データの一覧・検索・詳細・作成・更新・削除の画面と、テーブルを指すメニューからの入口がある（`aidlc/spaces/default/intents/261016-business-data-views/inception/requirements-analysis/requirements.md` の FR1〜FR11）。
- 立場の違う利用者が3人いる。業務データを見るだけの人、直す人、権限と DSL を用意する管理者で、同じ画面でも作業ロールの権限で見え方と行える操作が違う（ストーリーの質問 Q1: A）。
- 業務の決まりが多い。主権限（NONE・READ・FULL）によるカラムの出し分け、補助権限（CREATE・DELETE）、主キーの有無とビューによる操作の可否の表、表示の設定で隠すカラム、一意の事前の確かめ、拒否と接続の失敗の監査、404 と 403 の分け方がある（FR2・FR9・FR10・FR12・FR13）。
- 3種類の対象DB（MySQL・MariaDB・PostgreSQL）で同じ振る舞いを求め、対象DB への書き込みが初めて入る（NFR3・NFR4、コード知識ベースの所見 K-49）。
- 持ち越しの直しのうち、行の「操作」のトリガーの名前と axe の違反を無くすことは、読み上げを使う利用者に見える（FR14、ストーリーの質問 Q4: A）。

## 考えた要素

| 要素 | この Intent |
|---|---|
| 種類 | 既存のアプリへの機能の追加（ブラウンフィールド）と、前の Intent の持ち越しの直し |
| 利用者に見える範囲 | 業務データの一覧・検索・ページ送りと並べ替え・詳細・作成・更新・削除、値の表示、メニューからの入口、行の操作のトリガーの名前 |
| 複雑さの兆し | 3階層の主権限によるカラムの出し分け、補助権限、主キーとビューの表、表示の設定との重なり、3種類の対象DB、同時の作成・更新、監査と対象DB の確定の順 |
| ペルソナ | 見る人・直す人・管理者の3人 |

## ストーリーが最も効く所

- 主権限・補助権限・主キー・ビュー・表示の設定の組み合わせを、具体の値の組で受け入れ基準にし、QA が合否を書けるようにする。
- 作成・更新・削除の誤り（一意の重なり・参照先に無い値・行が無い・接続の失敗・時間切れ）を、利用者から見た結果と監査の残り方としてそろえる。
- 前の Intent の権限の解決の口（261004-role-menu の FR8.1）が業務データの API で要求ごとに使われることを、作業ロールの切り替えの直後の振る舞いで確かめる。

## ストーリーにしないもの

- 不安定なテスト2件の直し（FR15）と `dslMixed` の `memory.peak` の測り直し（FR16）は、利用者の操作の機能ではないため、ストーリーにせず `traceability.json` で Code Generation と Build and Test へ Deferred にする（ストーリーの質問 Q4: A）。
- 業務データの代表の E2E 1本（`team.md` の Testing Posture）は、受け入れ基準にせず Code Generation と Build and Test で扱う。

## 統合の後の形

- 参加者3人の意見と依頼者の決定（M1〜M8 はすべて A、まとめの確認の「リードが決めて取り込む点」）を `stories.md` に統合した。ストーリーは 17（群1 見る 5、群2 直す 5、群3 横断 6、群4 持ち越し 1）。
- 初稿から分けたもの: 一意の確かめ（US2.4 → US2.5）、API の認可と作業ロールの切り替え（US3.1 → US3.5）。team.md の必須のテストのうち初稿に無かった「SQL の組み立て」「接続の数」「3種類の DB の境界の値」を US3.6 にした。
- 要件と違う決定（`pattern` はサーバーだけ・2行以上に当たる更新と削除・時差つきの型・主キーとビューの拒否を 409 にしたことなど）は、要件を書き換えず `stories.md` の「要件との差」に書いた。
