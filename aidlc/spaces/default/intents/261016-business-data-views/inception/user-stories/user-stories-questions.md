# User Stories の計画と質問（Intent 261016-business-data-views）

## ストーリーの計画（案）

- **ペルソナの作り方**: 要件（`requirements.md`）の利用者を、作業ロールの権限の違いで分ける。前の Intent のペルソナ（管理者）を引き継ぎ、業務データを見る・直す人を足す（Q1）。
- **ストーリーの形**: 「As a [ペルソナ], I want [目的], so that [得られること]」。INVEST（独立・交渉できる・価値がある・見積もれる・小さい・確かめられる）を満たすように分ける。ID は `US{群}.{番号}`、受け入れ基準は Given/When/Then で `AC{群}.{番号}.{番号}`。
- **優先度**: MoSCoW（Must・Should・Could・Won't）。要件で合意した範囲は原則 Must とし、Should は Q5 で決める。MVP の境は Delivery Planning で決める。
- **分け方**: Q2 で決める。
- **合否の判定の仕方**: 状態コードと code、「含まれない」「変わらない」の確かめ方、3種類の対象DB、画面の共通の決まり（言語・アクセシビリティ）は、前の Intent と同じく「前提と読み方」に一度だけ書き、各受け入れ基準では繰り返さない。
- **要件の承認の場で受け入れた指摘**: R-09（更新の画面に出すカラム）と R-10（対象DB に接続できないときの監査）は、この段で決める（Q6・Q7）。
