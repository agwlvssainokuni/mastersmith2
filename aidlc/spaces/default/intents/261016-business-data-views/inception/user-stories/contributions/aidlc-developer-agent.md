### 1. 事実の食い違いの直し

- **D-1 検索の既定の値のキーの名前**（前提と読み方・AC1.2.6）: DSL の YAML のキーは `search.default`（`DslModelMapper` の `search.path("default")`）。`defaultValue` はモデルの欄の名前で、DSL を書く人が見る名前ではない。受け入れ基準では `search.default` と書く。
- **D-2 CHOICE には選択肢の無い場合がある**（AC1.2.3）: 既定の DSL の生成では、真偽値の型（`boolean`・MySQL の `tinyint(1)`）は `formPart: checkbox`・`search.operator: CHOICE`・`options` 無しになる（`TypeCategoryMapping` の BOOLEAN の行）。意味の検証も `checkbox`・`text` などに選択肢を持たせない（`matches` は `select`・`radio`・`lookup` 以外は `source == null` を求める）。つまり「CHOICE で固定の選択肢が無い」カラムは既定の DSL で普通に出る。AC1.2.3 は FIXED の場合だけなので、次を足す（追加の AC の A-3）。
- **D-3 監査の表に業務データの欄が無い**（AC3.4.1）: `audit_events` の欄は `event_type`・`result`・`failure_reason`（32 文字まで）・`actor_user_id`・`target_user_id`・`target_invitation_id`・`target_role_id`・`target_group_id`・`detail`（JSON、UTF-16 の 16,384 単位まで）。スキーマ・テーブル・主キーの値・作業ロールの名前の欄は無く、`detail` に入れる（欄を足すなら移行が要る）か、作業ロールは `target_role_id` に入れる形になる。複合の主キーや長い文字の主キーでは `detail` の上限に届きうるため、切り詰めの扱いを受け入れ基準に入れる（A-14）。どちらの形かは機能設計で決めてよいが、受け入れ基準は「欄」ではなく「読み出せること」で書くと実装に縛られない。
- **D-4 FR9 の拒否は 403 にできない**（AC3.2.1・AC3.4.2・AC3.4.4）: FR12.4 は「主キー・ビューの決まりによる拒否は監査に残す」「403 は残さない」。FR9 の拒否を 403 `ACCESS_DENIED` で返すと、この2つがぶつかる。FR9 の拒否は 403 と別の状態コードと code（例: 409 か 400 の、行の操作ができない旨の code。名前は機能設計）で返す、と AC3.2.1 に書く。
- **D-5 読み取りの拒否は監査に残らない**（AC3.2.1）: AC3.2.1 の「拒否は監査に残る」は、詳細の API の拒否も含めて読める。FR12.2 は読み取りを残さないため、「更新・削除（と、ビューへの作成）の拒否は監査に残り、詳細の拒否は残らない」と分けて書く。
- **D-6 DSL の主キーは対象DB の制約と一致する保証が無い**: `primaryKey` は DSL の YAML の値で、利用者が編集できる（生成のときは DB の主キーを写すが、ビューでは空にする。`DslTreeBuilder` 111 行）。DSL が主キーとするカラムに DB の一意の制約が無いと、`UPDATE`・`DELETE ... WHERE 主キー` が2行以上に当たりうる。更新・削除で当たった行が1でないときは巻き戻して拒否する受け入れ基準が要る（A-8）。ビューに DSL で主キーを書いた場合の詳細も同じ（2行以上が当たれば拒否）。
- **D-7 DSL と対象DB の食い違い**: DSL は適用の後に対象DB が変わりうる（照合の機能があるのはそのため）。DSL にあるカラム・テーブルが DB に無いと SQL の誤りになる。今の受け入れ基準に無いため足す（A-9）。
- **D-8 時差つきの型**: 生成の分類では `timestamptz`・`timetz`（PostgreSQL）と MySQL・MariaDB の `timestamp` が日時・時刻に入る（`TypeCategoryMapping` の DATETIME・TIME）。これらは接続のタイムゾーンで値が変わるため、AC1.5.3 の「DB の値のまま」が一意に決まらない（依頼者に尋ねる候補の Q-D6）。
- **D-9 生成の既定で詳細に出ない型**: 分類に無い型（`bytea`・`blob`・`json`・`uuid` など）は `formPart: text`・検索なし・一覧なし・`detail.visible: false` になる。PostgreSQL の `uuid` の主キーは珍しくなく、主キーの値を `uuid` の型へ渡すときは型の指定が要る。受け入れ基準に「主キーが分類に無い型（例: PostgreSQL の `uuid`）の行の詳細・更新・削除」を足す（A-10）。
- **D-10 既定の並びが複数のカラムにありうる**（AC1.3.4）: `list.defaultSort` はカラムごとの値で、JSON Schema も意味の検証も「1つだけ」を縛らない。2つ以上にあるときの順（例: `list.order` の順に並べる）を受け入れ基準に書く（リードが決めてよい。Q-D9 に推奨を書いた）。
- **D-11 DB の型の既定値・自動の採番を DSL は持たない**（AC2.1.4・AC2.1.5）: `DbType` は名前・長さ・精度・小数の桁・NULL の可否だけ。自動の採番の主キー（`serial`・`identity`・`AUTO_INCREMENT`）は DSL から分からない。作成の後に詳細へ移るには、DB が作った主キーの値を受け取る（PostgreSQL は `RETURNING`、MySQL・MariaDB は作られた鍵）必要がある。受け入れ基準に足す（A-6）。
- **D-12 外部キーの違反のカラムを1つに決められないことがある**（AC2.1.6）: `DslForeignKey` は制約の名前を持たない。DB の誤りの文から制約を読むと文に行の値が入る（ログに出せない）。外部キーが2つ以上あるテーブルで、どのカラムかを決める方法が要る（依頼者に尋ねる候補の Q-D5）。

### 3. 書き方の直し

- **AC2.2.5（主キーの値を変える）**: 「変わらない（拒否される）」の両方が書かれ、どちらを確かめるかが決まらない。案: 「主キーのカラムは、FULL でも更新の画面では読み取りで出す。更新の要求の本文に主キーのカラムを入れると入力の誤りとして拒否され、行は変わらない。作成では、FULL の主キーのカラムは入力できる」。
- **AC2.4.4 の後ろの文**（「両方が成功しうることを既知の制約として確かめに書く」）: 合否の無い文のため、受け入れ基準から外して「制約」（FR10.3）を参照する形にする。
- **AC1.2.9・AC1.3.6・AC3.1.6（NONE のカラムを要求に入れる）**: NONE のカラムと DSL に無いカラムで応答（状態コードと code）を同じにすることを明記する。別にすると、見られないカラムの名前が DSL にあるかを利用者が当てられる（依頼者に尋ねる候補の Q-D3）。
- **AC1.3.7（性能）**: 1ページ 100 件 × 100 カラムに加えて、全体の件数（`COUNT`）が要る。対象DB の行の数は決まっていないため、数え方の上限（数えきれないときの表示）を NFR 要件の段で決める、と注記する。

### 5. 依頼者に尋ねる候補（どちらも正当な選択）

- **Q-D1 更新で送るカラム**: (A) 利用者が変えたカラムだけを `UPDATE` に入れる（後勝ちで他人の変更を上書きする範囲が狭く、入力の形で丸められる値（秒の小数・NULL の真偽値・長い文字）を黙って書き換えない。推奨）／ (B) 入力できるカラムのすべてを入れる（作りは簡単だが、A-7 の値が変わる）。
- **Q-D2 空の入力の意味**: 文字の入力を空にして保存したとき、(A) NULL を入れる（NULL を許さないカラムは空の文字列）／ (B) 空の文字列を入れる／ (C) 画面で NULL にする操作を別に出す。FR11.5 は表示で NULL と空を分けるが、入力では分けていない。作成の FR6.4（空の FULL は DB の既定値に任せる）と更新で意味が変わらないかも合わせて決める。
- **Q-D3 NONE のカラムを要求に入れたときの応答**: (A) DSL に無いカラムと同じ 400 と code（見られないカラムの有無を当てられない。推奨）／ (B) 403 `ACCESS_DENIED`（権限の不足と分かるが、カラムの有無が分かる）。READ のカラムの値を作成・更新の本文に入れたとき（見えているカラム）は 400 か 403 かも合わせて決める。403 にすると監査に残らない（FR12.4）。
- **Q-D4 画面での `pattern` の検証**: DSL の `pattern` は Java の正規表現として確かめてある（`PatternChecker`）。JavaScript の正規表現とは書き方が違うもの（所有の量指定子 `*+`、`\p{...}` の一部など）があり、画面では時間の上限を置けない（時間のかかる正規表現で画面が止まる）。(A) 画面では `pattern` を当てず、サーバーの誤りを入力の近くに出す（推奨）／ (B) 画面でも当てる（書き方の違うものは画面で当てない）。AC2.4.1 の「画面で保存の前に誤りが出る」の範囲が変わる。
- **Q-D5 外部キーの違反のカラムの決め方**（FR6.2a・AC2.1.6）: (A) 保存の前に参照先に値があるかを問い合わせる（一意の確かめ FR10.2 と同じ形。カラムを確実に示せるが、同時の削除とは重なりうる）／ (B) DB の誤りから決める（外部キーが1つなら示し、2つ以上なら外部キーのカラムのすべてを示すか一般の保存の失敗にする）。参照先のテーブルを利用者が NONE でも、値の有無は分かってしまう点はどちらも同じ。
- **Q-D6 時差つきの型の表示**（FR11.3・AC1.5.3）: `timestamptz`・`timetz`・MySQL の `timestamp` を、(A) 接続のタイムゾーンを UTC に固定して読み、UTC の値として出す／ (B) 対象DB の接続の既定のまま出す／ (C) 今回はこの型を読み取りだけにする。
- **Q-D7 書き込みの接続が無いときの入口**（A-15）: (A) 作成・更新・削除の入口を出さない（操作の可否に書き込みの可否を含める）／ (B) 権限どおりに出し、押したときに誤りにする。
- **Q-D8 パスワードのフォーム部品**（`password`）: 一覧・詳細でそのカラムの値を (A) 伏せて出す（応答にも含めない）／ (B) 他のカラムと同じく出す。更新の画面で今の値を入れるかも合わせて決める。
- **Q-D9 一覧へ戻ったときの条件**: 詳細・作成・削除の後に一覧へ戻るとき、検索の条件・ページ・並びを (A) 道（URL）に持って保つ（戻る・共有でも同じ一覧になる。推奨。ただし検索の値が道に乗るため、トレースの属性の道の扱いと合わせて設計で決める）／ (B) 保たず既定に戻す。（既定の並びが複数のカラムにあるときの順 D-10 は、リードが「`list.order` の順」と決めてよい。）
