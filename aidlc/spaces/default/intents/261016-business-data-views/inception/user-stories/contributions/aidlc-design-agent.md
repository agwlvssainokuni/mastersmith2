## Contribution

観点は利用者の体験（UX）とペルソナの忠実さ。初稿の受け入れ基準はサーバー側の判定と権限の組み合わせをよく押さえているが、画面の状態（処理中・空・誤り・成功の後）、フォーカスと読み上げ、操作の後の行き先、広い表の扱いが薄い。以下は統合できる形の追加と直し。〔Must〕は要件の範囲の中の具体化、「依頼者に尋ねる候補」は判断が分かれるもの。

### 1. ペルソナの直し（personas.md）

- **P1 の目的の3つ目**: 「自分が見てはいけないカラムが出ないこと…を望む」は、見る人の願いではなく組織の決まりである。利用者の言葉に直す: 「見られないテーブル・カラムがあるとき、それが権限のせいか、データが無いせいかを画面の文で見分けたい（管理者に頼むか、探し直すかを決めるため）」。権限の決まりは US3.1 の so-that に残す。
- **P1・P2 の困りごとに足す**: 「テーブルに列が多く（最大 100 カラム）、横に長い表を読む」。広い表の扱い（下の 3.3）の根拠にする。
- **P2 の技術への慣れ**: 「DB の制約やエラーの文は読めない」は大事な特徴なので、受け入れ基準に結び付ける（下の 2.5。DB が拒んだ保存の失敗を、DB の文ではなく業務の言葉とカラムで伝える）。
- **P2 の目的に足す**: 「保存した後に、保存できたこととその結果を、その場で確かめたい」（成功の知らせと行き先。下の 2.1〜2.3）。
- **P3 の目的の2つ目**: 監査を見る画面・API は無い（コード知識ベースの component-inventory.md、audit の節）。「監査で追いたい」を「内部DB の監査の記録（今の手順では配備したアプリを止めた複写を読み取りで開く）で追いたい」と明記し、監査を見る画面はこの Intent の範囲の外と書く。読む人が画面を期待しないようにする。
- **P3 の目的の1つ目**: 管理者でも業務データは作業ロールで決まる（FR2.6）ため、確かめるには「確かめたいロールを自分に割り当てて作業ロールを切り替える」か「自分の権限を見る」画面で見る、という手段を書き添える。

### 2. 足すべき受け入れ基準・直すべき文（群1・群2）

#### 2.1 US1.2 検索

- **AC1.2.10（足す）** 〔Must〕 Given 一覧の2ページ目を見ている / When 検索の条件を変えて検索する / Then 1ページ目へ戻り、新しい全体の件数が出て、件数の変化が読み上げにも伝わる（`aria-live` の知らせ）。
- **AC1.2.11（足す）** 〔Must〕 Given 条件に合う行が 0 件 / When 検索する / Then 「条件に合う行がありません」と出て、条件を戻す操作（条件のクリア）が分かる。テーブルに行がそもそも無いときは「行がありません」と出し分ける（作成できる利用者には作成の入口を添える）。
- **AC1.2.12（足す）** 〔Must〕 Given 検索の項目 / When キーボードだけで操作する / Then 項目ごとに表示名の付いたラベルがあり、Enter か検索のボタンで検索でき、条件のクリアもキーボードで行える。
- **AC1.2.5 の直し**: 「どのカラムの誤りかが画面の言語で分かる」に「誤りはその検索の項目の近くに出て、読み上げにも伝わる（`aria-describedby`・`aria-invalid`）。直前の結果の一覧は消さずに残す」を足す。

#### 2.2 US1.3 ページ送りと並べ替え

- **AC1.3.8（足す）** 〔Must〕 Given 並べ替えたカラムの見出し / When 読み上げで見出しを読む / Then 並べ替えの向き（`aria-sort` の昇順・降順）が分かり、並べ替えの操作は見出しのボタンとしてキーボードで行える。並べ替えの操作が出ないカラムの見出しはボタンにしない。
- **AC1.3.9（足す）** 〔Must〕 Given 画面の言語が英語 / When ページ送りと件数の表示を見る / Then ページ送り・件数・1ページの件数の選択の文言が英語で出る（make-you-chic-ui の Table のページ送りの文言は日本語に固定のため、FR14.5 の依頼（5）か frontend の側で満たす。前の Intent の学び）。
- **AC1.3.10（足す）** 〔Must〕 Given 3ページ目を見ている間に、ほかの人の削除で全体が 2 ページに減った / When ページを読み直す / Then 空のページのままにせず、最後のページの行が出るか、空である旨と前のページへ戻る操作が出る（どちらにするかは画面の段で決める）。

#### 2.3 US1.4 詳細

- **AC1.4.6（足す）** 〔Must〕 Given 検索の条件・並べ替え・ページを変えた一覧から詳細へ移った / When 詳細から一覧へ戻る（戻るの操作、またはブラウザの戻る） / Then 移る前の条件・並べ替え・ページのまま一覧が出る。条件をどこに持つかは下の「依頼者に尋ねる候補 Q-D1」。
- **AC1.4.7（足す）** 〔Must〕 Given 詳細の画面 / When 開く / Then 画面の見出しにテーブルの表示名と、行を見分ける値（主キー、または DSL で決めた代表のカラム）が出て、一覧へ戻る入口がある。フォーカスは画面の見出しに移る。

#### 2.4 US2.1・US2.2・US2.3 操作の後の行き先と知らせ

- **AC2.1.1 の直し**: 「その行の詳細へ移り」に「『作成しました』の知らせが出て、読み上げにも伝わる」を足す。
- **AC2.2.2 の直し**: 保存の後の行き先が初稿に無い（FR7 にも無い）。「保存の後は、その行の詳細へ戻り『更新しました』の知らせが出る（読み上げにも伝わる）」を足す。詳細へ戻ることは FR6.5 の作成の形にそろえた案で、別の行き先にするなら画面の段で決める。
- **AC2.2.8（足す）** 〔Must〕 Given 更新の画面 / When 何も変えずに保存する、または「やめる」を選ぶ / Then やめるでは何も変わらず詳細へ戻る。何も変えない保存の扱い（更新として監査に残すか、保存を押せなくするか）は機能設計で決め、決めた側の動作を基準にする。
- **AC2.3.1 の直し**: 確かめの表示に、消す行を見分ける値（テーブルの表示名と主キーの値、または代表のカラム）と「元に戻せない」旨を出す。どの行を消すかが分からない確かめは誤操作を防がない。
- **AC2.3.2 の直し**: 「一覧へ戻り」に「戻る前の条件・並べ替え・ページを保ち（AC1.4.6）、『削除しました』の知らせが出る」を足す。
- **AC2.5.1（足す。US2.1・US2.2・US2.3 共通）** 〔Must〕 Given 作成・更新・削除の要求を送った / When 応答を待つ / Then 保存・削除のボタンは処理中の表示になり押せない（二度押しで同じ行を二度作らない）。5 秒を超えたら「時間がかかっています」が出る（既存の `shared/slow-notice` の形）。

#### 2.5 US2.4 誤りの伝え方

- **AC2.4.6 の直し**: 「誤りが複数のカラムにある」とき、保存の後にフォーカスを最初の誤りの入力（または誤りのまとめ）へ移すことを足す。入力した値は消さない。
- **AC2.4.7（足す）** 〔Must〕 Given DB が拒んだ保存の失敗（外部キー・NOT NULL など） / When 画面で受ける / Then DB の文や制約の名前は出さず、業務の言葉で出す。カラムが分かるときはそのカラムの入力に出す（FR6.2a の参照先に無い値と同じ形）。入力できないカラム（NONE・READ）の NOT NULL で拒まれたとき（A2）は、利用者には直せないため「このテーブルの作成には、入力できない項目の値が要ります。管理者に確かめてください」の旨を出す。入力した値は消さない。
- **AC2.4.8（足す）** 〔Must〕 Given 必須のカラム / When 作成・更新の画面を見る / Then 必須であることが入力の前に見て分かり（印と文言）、読み上げにも伝わる（`aria-required`）。長さの上限があるカラムは、上限を入力の前に伝える。

#### 2.6 US1.5・US2.1 値の形（入力側）

- **AC1.5.6（足す）** 〔Must〕 Given 広い値（長い文字・長い数） / When 一覧を見る / Then 一覧のセルでは省略して出しても、詳細では全体を読める（省略したときも読み上げでは全体が分かるか、詳細へ移れる）。
- `password` のフォーム部品のカラムの一覧・詳細での見せ方（値を伏せるか）と、入力で値を空にしたときの扱い（NULL にするか空の文字列にするか）は初稿に無い。下の「依頼者に尋ねる候補 Q-D2・Q-D3」。

### 3. 足すべき受け入れ基準（群3・群4）

#### 3.1 US3.2 できない理由を見せる

- **AC3.2.5（足す）** 〔Must〕 Given 主キーの無いテーブル・主キーのカラムが NONE のテーブル・ビューの一覧 / When 一覧を見る / Then 入口を出さないだけでなく、一覧の上に「このテーブルは行を1件に決められないため、詳細・更新・削除はできません」「このビューは読み取りだけです」の旨が出る。US3.2 の so-that（できないことが分かる）を、入口を隠す AC3.2.1〜AC3.2.3 だけでは満たせないため。理由の文に権限の名前（主キーの NONE など）をどこまで出すかは下の Q-D4。

#### 3.2 US3.3 403・404・接続の失敗の画面

- **AC3.3.6（足す）** 〔Must〕 Given 403・テーブルが見つからない・行が見つからない・DSL が適用されていない・対象DB に接続できない / When 画面で受ける / Then それぞれ別の文で出し（例: 権限が無い・テーブルが無い・行が無い（ほかの人が削除した可能性）・業務データを使える状態でない・対象DB とつながらない）、次の行き先（一覧へ戻る・メニューから選び直す・時間をおいてやり直す）がある。接続の失敗では「やり直す」の操作で読み直せる。
- **AC3.3.5 の直し**: 時間切れの文の「一覧で確かめる」は、更新・削除では「その行の詳細を開き直して確かめる」の方が早い。操作ごとに「確かめる」の入口（作成は一覧、更新・削除はその行の詳細）を出し、作成ではやり直す前に一覧で同じ行が無いかを確かめるよう促す（作り直すと二重の行になるため）。
- **AC3.3.7（足す）** 〔Must〕 Given 更新の画面を開いている間に作業ロールを切り替え、そのテーブルの FULL が無くなった / When 保存する / Then 403 の表示になり、権限が変わった旨が分かる。入力していた値の扱い（残すか捨てるか）は画面の段で決める。

#### 3.3 広い表とはみ出し（US1.1 か US1.3 に足す）

- **AC1.3.11（足す）** 〔Must〕 Given 1 テーブル 100 カラムの一覧、画面の幅が狭い（E2E の 375px を含む） / When 一覧を見る / Then 画面全体は横にスクロールせず、表の領域だけが横にスクロールする。表の領域はラベルの付いた領域（`role="region"`・`aria-label`）でキーボードからもスクロールでき、見出しの行は読み上げで列の名前として伝わる。行の「操作」のメニュー（make-you-chic-ui の `Dropdown`）は開いたときに画面の中に収まる（右端は `placement` を `bottom-end`。project.md の user-admin の学び）。

#### 3.4 US4.1

- **AC4.1.1 の直し**: 「名前に見えている文字が含まれる」に「名前は見えている文字（「操作」・`Actions`）で始まり、どの行の操作かも分かる（例: 「操作: 商品 A01」）」を足す。行を見分けられない名前（全行が同じ「操作」）は読み上げの利用者に役立たないため、WCAG 2.5.3 と行の見分けの両方を基準にする。業務データの一覧で行を見分ける値は主キーの値か代表のカラムで、これは画面に出す値でありログ・トレースには出さない（NFR4.2）。
- **AC4.1.6（足す）** 〔Must〕 Given 業務データの一覧・詳細・作成・更新の画面、ブランドカラーとテーマのすべての組 / When 実際のブラウザの axe（E2E）を流す / Then 違反が 0 件。誤りを出した状態・長い表示名・100 カラムの表・NULL の行・展開した検索の項目を含める（project.md の「誤りを出した状態と現実に近いデータで」の学び）。E2E の本数には数えない（Playwright のアクセシビリティの検査は流れの本数に数えない、project.md の学び）。

### 4. 依頼者に尋ねる候補

- **Q-D1 一覧の条件の持ち方（AC1.4.6）**: A. 検索の条件・並べ替え・ページを画面の道（URL のクエリ）に持つ（戻る・再読み込み・ブックマークで保てる。代わりに検索の値＝業務データの値が道に乗り、トレースの属性やアクセスのログに残りうるため、NFR4.2 の道の扱い（設計で決める未解決の点）と同じ手当てが要る）。B. 画面の中（メモリ・セッションの保存）だけに持つ（道に値が乗らない。代わりに再読み込みやブックマークでは消える）。どちらも正当。推奨は、NFR4.2 を素直に守れる B（再読み込みで消えることを既知とする）。
- **Q-D2 `password` のフォーム部品のカラムの見せ方**: 一覧・詳細でも値を伏せる（`••••`）か、DSL の一覧の書式に任せてそのまま出すか。更新の画面で今の値を入力に入れるか、空にして「変えるときだけ入れる」にするか。
- **Q-D3 入力を空にしたときの値**: NULL を許すカラムで文字の入力を空にして保存したとき、NULL にするか空の文字列にするか（作成は FR6.4 で DB の既定値に任せるが、更新は決まっていない）。NULL と空の文字列を表示で見分ける（FR11.5）なら、入力でも作り分けたいかが分かれる。
- **Q-D4 できない理由の文（AC3.2.5）**: 一覧の上に理由の文を出すか、入口を隠すだけ（FR9.3 のまま）にするか。出すなら、主キーのカラムが NONE のときに「権限の設定のため」と伝えてよいか（権限の形を利用者に推測させてよいか）。
- **Q-D5 更新の画面を離れるときの未保存の確かめ**: 入力を変えた後に「やめる」・メニュー・作業ロールの切り替えで離れるとき、確かめを出すか。前の Intent（user-management の S4）では出さない形を [assumption] にしたが、業務データの更新は 100 カラムまで入力がありうるため、改めて決めたい。

## Positions

- AGREE: ペルソナを作業ロールの権限の違いで3人に分けたこと。同じ人がロールの切り替えで P1 にも P2 にもなる注記は、権限の切り替えの基準（AC3.1.3）と合っている。
- AGREE: 横断の決まりを群3 に寄せ、群1・群2 には固有の点だけを書く形。画面の共通の決まり（確かめの表示・言語・文字として出す）を「前提と読み方」に一度だけ書いたことも同じ。
- AGREE: 削除の確かめの表示を既存と同じ形（背景で閉じない・はじめのフォーカスを「やめる」）にしたこと。
- OBJECT: US3.2 の so-that は「できないことが分かってほしい」だが、受け入れ基準は入口を隠すことと API の拒否だけで、利用者に理由が伝わる基準が無い。AC3.2.5 を足すか、so-that を「意図しない行を変えないため」だけに直すかを決める（Q-D4）。
- OBJECT: 作成・更新・削除の後の行き先と成功の知らせ、保存中に押せなくすることが基準に無い。時間切れの二重の作成（AC3.3.5）とあわせて、AC2.5.1・AC2.2.2 の直し・AC3.3.5 の直しを入れる。
- OBJECT: 詳細から一覧へ戻ったときに検索の条件・ページが消えると、P1 の目的（早く見つける）を損なう。AC1.4.6 を入れ、持ち方は Q-D1 で決める。
- OBJECT: P3 の「監査で追いたい」は、監査を見る画面が無いことを書かないと、画面があると読める。ペルソナと US3.4 に、監査は内部DB の記録で読むこと（画面は範囲の外）を明記する。
- OBJECT: 100 カラムの広い表と狭い幅でのはみ出し・行の操作のメニューの収まりの基準が無い（前の Intent で配備の後に見つかった不具合と同じ形）。AC1.3.11 を入れる。
