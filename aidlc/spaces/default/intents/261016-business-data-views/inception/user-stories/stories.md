## 前提と読み方（すべての受け入れ基準に共通）

### 分け方・優先度

- **分け方**: 操作ごとの群（群1 見る、群2 直す）と、横断の群（群3 カラムの出し分け・主キーとビュー・誤り・監査・API の認可・SQL と接続と境界の値）、持ち越しの群（群4）に分ける（SQ2 A）。横断の決まりは群3 のストーリーで確かめ、群1・群2 の受け入れ基準にはその操作に固有の点だけを書く（SQ3 A）。
- **優先度**: 要件で合意した範囲は Must。1ページの件数を選べること（既定 20 は Must）と、検索の項目を折りたたんで始める設定は Should（SQ5 A）。1つのストーリーに Should の部分が混ざるときは、ストーリーを Must とし、その受け入れ基準に **〔Should〕** と印を付ける。Should の操作を見送っても Must の決まりの確かめが抜けないよう、Should と Must は別の受け入れ基準に分ける（SL。AC1.3.2 と AC1.3.8）。
- **ストーリーにしないもの**: 不安定なテスト2件（FR15）と `memory.peak`（FR16）は `traceability.json` で Code Generation・Build and Test へ Deferred にする（SQ4 A）。業務データの代表の E2E 1本（見本の対象DB に届くかの事前の確かめ、流れが使う行を自分で作る、資格情報を `webServer.env` に置かず報告の json に資格情報・接続先が無いことを確かめる）は、TP のとおり Code Generation と Build and Test で扱い、受け入れ基準にはしない（Q）。

### 業務の決まりの読み方

- **対象**: 適用中の DSL（書式の版 2）のスキーマ・テーブル・カラム。テーブルの見せ方（一覧の列・並び・幅・検索の項目・詳細・表示名・書式・フォーム部品・検証）は DSL の設定に従う（KB K-51）。検索の既定の値の DSL のキーは `search.default`（要件の `search.defaultValue` はモデルの欄の名前。V）。
- **権限**: 要求ごとに、その利用者の今の作業ロールの実効の主権限（スキーマ → テーブル → カラム、既定 NONE）と補助権限 CREATE・DELETE（スキーマ → テーブル、既定 不可）を、前の Intent の解決の口で求める（FR2.1）。受け入れ基準の「T が READ」は「作業ロールでのテーブル T の実効の主権限が READ」と読む。作業ロールが無い利用者は、すべて NONE・不可として扱う。
- **カラムの出し分け**: 主権限が NONE のカラムは、一覧・検索・詳細・作成と更新の画面から除き、応答にも含めない（FR2.2）。READ 以上でも、一覧の応答は `list.visible`、詳細・作成・更新の画面と応答は `detail.visible` のカラムだけ（FR2.2a・SQ7 A）。行を指す主キーのカラムは、READ 以上なら `list.visible` で隠す設定でも一覧の応答に含め、画面には出さない。
- **入力できるカラム**: 作成・更新では、`detail.visible` のカラムのうち FULL のものだけを入力でき、READ のものは読み取りで出す。`detail.visible` で隠す FULL のカラムは入力せず値を変えない。更新の画面の値は詳細と同じ API で読む（SQ7 A）。主キーのカラムは、作成では FULL なら入力でき、更新では FULL でも読み取りで出す（FR7.3。V）。
- **書けないカラムを要求に入れたとき**: NONE・READ のカラム、DSL に無いカラム、`detail.visible` で隠すカラム、主キーのカラム（更新）を、作成・更新の本文に入れたときと、NONE のカラム・DSL に無いカラムを検索の条件・並べ替えに入れたときは、どれも同じ状態コード（400）と同じ `code` で拒否する。応答の形から、見られないカラムの名前が DSL にあるかを推測できない（SL。V・Q）。
- **主キーとビュー**: 操作の可否は要件 FR9.1 の表に従う。ビューは読み取りだけ（FR9.2）。表で「行わない」操作の拒否は、403 ではなく 409 と専用の `code` で返す（SL。V・Q）。作成・更新・削除の拒否は監査に残し、詳細の拒否は読み取りのため残さない（FR12.2）。画面は、行えない理由（行を1つに決められない・ビュー）を一覧の上に出す（SL。D）。
- **主キーで指した行が1行でないとき**: 更新・削除で当たった行が1行でなければ、巻き戻して「行を1つに決められない」の誤りとし、監査に残す。詳細で2行以上が当たったときも同じ誤りで拒否する（読み取りのため監査に残さない）（SM8 A。V・Q）。
- **判定の順**: 1つの要求が複数の拒否に当たるときは、次の順で最初に当たったものを返す。① 未認証（401）→ ② DSL が適用されていない・DSL に無いスキーマかテーブル（404）→ ③ テーブルの主権限が NONE（403 `ACCESS_DENIED`）→ ④ 主キーとビューの決まり（409）・補助権限や FULL の不足（403）→ ⑤ 入力の誤り（400）→ ⑥ 行が無い（404）→ ⑦ 行が1つに決まらない・一意の重なり・DB が拒んだ保存・接続の失敗・時間切れ。とくに③は⑥より先で、NONE のテーブルでは行があっても無くても同じ 403 になる（SL。Q）。④の中の前後と⑦の中の順は機能設計で決め、決めた順を表のパラメーターのテストで書く。
- **更新で保存するカラム**: 利用者が更新の画面で変えたカラムだけを保存する。変えていないカラムは送らず、DB の値のまま残る（SM1 A）。
- **同時の更新**: 後から保存した人の値で上書きする（FR7.2）。ただし保存するのは各人が変えたカラムだけなので、A と B が別のカラムを変えたときは両方の変更が残り、同じカラムを変えたときは後の人の値になる（SM1 A）。
- **空の入力**: 更新で入力を空にして保存すると、文字の型のカラムは空の文字列、それ以外の型（数・日付・真偽値など）は NULL になる（SM2 A）。作成で入力を空にした FULL のカラムは、要件 FR6.4 のとおり送らずに対象DB の既定値に任せる（リードの読み。「要件との差」の X9）。
- **`password` のフォーム部品のカラム**: 一覧・詳細では値を伏せて出し（例: `••••••`）、応答にも値そのものを含めない。更新の画面は空で始め、入れたときだけ変える（SM3 A。V）。
- **`pattern` の検証**: `pattern` はサーバーだけで当て、画面は保存のときにサーバーの誤りを該当の入力に出す。ほかの検証（必須・長さ・範囲・型）は画面とサーバーの両方で当て、サーバー側を正とする（SM4 A）。
- **一覧の状態の保ち方**: 検索の条件・ページ・並びは画面の中に持ち、詳細から戻る・作成・更新・削除の後に一覧へ戻る・ブラウザの戻る操作では保つ。再読み込みでは既定の状態に戻る。画面の道（URL）には検索の値を載せない（SM5 A）。
- **保存せずに離れる**: 作成・更新の画面で変更があるまま離れようとしたら、離れるか留まるかを確かめる表示を出す（SM6 A）。
- **時差つきの日時の型**: PostgreSQL の `timestamptz`・`timetz`、MySQL・MariaDB の `timestamp` は UTC に固定して出し（`+00:00` を付ける）、入力も UTC として読む。時差の無い日時の型は、タイムゾーンを足さずに DB の値のまま出す（SM7 A・FR11.3）。
- **NULL の並び**: 3種類の DB でそろえ、昇順では NULL を最後、降順では最初に置く（SL。Q）。
- **ページの範囲**: 最後のページを超えるページの番号は、空のページと全体の件数を返す（誤りにしない）。ページの番号の始まりより小さい番号と数でない値は入力の誤り。`RANGE` の下限が上限より大きいときは入力の誤り（400）（SL。Q）。
- **書き込みの接続の設定が無いとき**: 読み取り（一覧・詳細）は動き、作成・更新・削除の入口を出さない。API は専用の `code` で拒否し、アプリは起動を続ける（SL。V）。
- **外部キーの違反**: 違反したカラムは、DB の制約と対象DB のメタデータで決められるときにそのカラムを示し、決められないときはフォーム全体の誤り（参照先に無い値）として出す（SL。細部は機能設計）。
- **監査**: 作成・更新・削除の成功と失敗を残す。失敗として残すのは、主キーとビューの決まりの拒否（409）、一意の重なり、行が無い（404）、行が1つに決まらない、DB が拒んだ保存（外部キー・NOT NULL など）、対象DB に接続できない、時間切れ（確定したか分からない）。残さないのは、401・403・入力の誤り（400。書けないカラムの拒否を含む）、DSL に無いテーブル・DSL が適用されていないときの 404、一覧・詳細の読み取りとその拒否（FR12.2・FR12.4・SQ6 A・SL）。監査は P3 が内部DB の記録で読む。監査を見る画面はこの Intent の範囲の外（SL。D）。
- **既知の制約**（受け入れ基準では、決めた側の振る舞いを明示したテストにする）:
  - 主キーの無いテーブルと、主キーの設定の無いビューは並びの順を約束せず、ページの境で行が重なる・抜けることがある（FR4.3・SL）。
  - 部分一致の大文字と小文字の扱いは、対象DB の照合順序により DB ごとに違いうる（FR3.4）。
  - DB に一意の制約が無いカラムでは、同時の作成・更新で重なった値が入りうる（FR10.3）。
  - 対象DB の外部キーが `ON DELETE CASCADE` のとき、行の削除で、作業ロールで NONE の別のテーブルの行も消えうる（SL。Q）。

### 共通の受け入れ基準の読み方

- **認可**: 足す API はすべて、未認証は 401、要る権限だけを欠く利用者は 403（ほかのテーブルの権限は持つ）、要る権限を持つ利用者は成功を、サーバー側のテストで確かめる。API と権限の組はパラメーターを使うテストで表として書く。停止中の利用者は、権限があっても通らない（TP）。
- **API の分類**: 足す API はすべて「ログインだけ」に分類し、判定は作業ロールの権限で行う（KB K-61）。分類を足し忘れると既存の API の分類の網羅のテストが落ちる（AC3.5.1）。
- **拒否の応答**: 拒否は理由ごとに別の安定した `code` を持つ Problem Details で返る。「〜として拒否される」は「その理由の code で拒否される」と読む。code の名前は機能設計で決める。
- **「変わらない」の確かめ方**: 拒否の後に、対象の行をアプリとは別の接続で読み直して要求の前と同じであることを確かめる。応答の状態コードだけでは合格にしない。
- **書いた後の確かめ方**: 作成・更新・削除の成功も、アプリとは別の接続で対象DB を読み直して、行の値（作成・更新）か行が無いこと（削除）を確かめる（TP。Q）。
- **「含まれない」の確かめ方**: 応答の JSON に、そのカラムの名前と値のどちらも無いことを確かめる。画面に出ないことだけでは合格にしない（PM）。誤りの応答の `instance`・`detail`・カラムごとの誤りの項目にも、主キーの値と入力した値が入らない（Q）。
- **同時の重なりの確かめ方**: 「同じ時に」の受け入れ基準は、スレッドの数に頼らず待ち合わせで確実に重ねる。合否は、両方の要求が終わった後の対象DB の状態と、負けた側の応答が業務の理由の code の 4xx であること（500 にならないこと）で判定する（TP。Q）。
- **境界値の確かめ方**: 値を設計で決める上限（行の数・1ページの件数・`pattern` の時間・文字の長さなど）は、「上限ちょうどは受け付け、上限を1つ超えると拒否」の2点で確かめる（TP。Q）。
- **3種類の対象DB**: 対象DB に関わる受け入れ基準は、MySQL・MariaDB・PostgreSQL のすべてで同じ結果になることを確かめる（部分一致の大文字と小文字の扱いを除く。NFR3）。
- **漏えい**: 行の値（主キーの値を含む）は、アプリのログ・トレースの属性・エラー応答に出ない。TRACE を有効にした `*SecretLeakIT` と、外部へ送る設定を有効にした結合テストで確かめる。JDBC の例外のメッセージ（行の値を含みうる）は、応答・アプリのログ・監査のどれにも出ない（PM・NFR4.2。US3.6）。
- **画面の共通**: WCAG 2.1 AA に沿い、画面部品ごとにアクセシビリティ検査を1件入れる。操作の結果（成功・拒否）は読み上げにも伝わる（`aria-live` など）。取り消しにくい操作（削除）の確かめの表示は、背景のクリックで閉じず、はじめのフォーカスを「やめる」に置く。画面の文言は日本語と英語を用意し、受け入れ基準の中の文言は例とする（具体は画面の段で決める）。値と表示名は文字として出し、HTML として描かない（NFR5・NFR6・FR11.4）。誤りは DB の文や制約の名前ではなく業務の言葉で伝える（D）。
- **性能**: 応答時間の受け入れ基準の測り方は NFR 要件の段で決める。目標を緩めて「満たした」ことにはしない（A1・PM）。

## 群1 業務データを見る

### US1.1 メニューからテーブルの一覧を開く 〔Must〕

P1 業務データを見る人として、左のメニューでテーブルを指す項目を選び、そのテーブルの業務データの一覧を開きたい。それは、扱う業務データへ迷わずたどり着くためだ。

出典: FR1.1〜FR1.3、FR3.1、FR13.1、FR13.2、KB K-52、V・Q

- **AC1.1.1** Given 作業ロールでテーブル T が READ、T を指すメニューの項目がある / When その項目を選ぶ / Then T の業務データの一覧の画面が開き、サイドバーの今の項目（`aria-current`）が T の項目になる
- **AC1.1.2** Given 作業ロールでテーブル T が NONE / When サイドバーを見る / Then T を指す項目は出ない
- **AC1.1.3** Given 作業ロールでテーブル T が NONE / When T の一覧の画面の道を直接開く / Then 画面は 403 の表示になり、行は出ない（サーバーが 403 を返す。US3.3）
- **AC1.1.4** Given 適用中の DSL に無いテーブルの名前 / When その一覧の画面の道を直接開く / Then 画面は「テーブルが見つからない」の表示になる（サーバーが 404 を返す。US3.3）
- **AC1.1.5（直した）** Given T の一覧の画面を開いている / When 作業ロールを、T が NONE のロールへ切り替えた後に、一覧を読み直す（ページ送り・再読み込み・検索のいずれか） / Then サーバーが 403 を返し、画面は 403 の表示になる。切り替えの前に出ていた行は 403 の表示に置き換わって残らない（US3.5）（Q）
- **AC1.1.6** Given T の一覧から、詳細・作成・更新の画面へ移った / When サイドバーを見る / Then 今の項目（`aria-current`）は T の項目のまま。T を指す項目が2つ以上あるときは、選んだ項目が今の項目になる（V）
- **AC1.1.7** Given 一覧・詳細・更新の画面を開いている間に、DSL が適用し直されて T が DSL から消えた / When 次の操作（ページを送る・保存する） / Then 「テーブルが見つからない」の表示になり（404）、対象DB の行は変わらない（V）
- **AC1.1.8** Given 作業ロールで T が NONE、または T が READ で CREATE が不可 / When T の詳細・更新の画面の道（T が NONE のとき）、作成の画面の道（CREATE が不可のとき）を直接開く / Then 画面は 403 の表示になり、入力の部品は出ない（Q）
- **AC1.1.9** Given DSL で `list.visible` のカラムが `code`・`name`・`price`、`list.order` が `name`・`code`・`price` の順、`list.width` が決まっている / When 一覧を開く / Then 列は `name`・`code`・`price` の順に並び、幅は `list.width` に従う。`list.visible` でないカラムの列は出ない（FR3.1）

### US1.2 条件で行を絞り込む 〔Must〕

P1 業務データを見る人として、DSL で決めた検索の項目に条件を入れ、合う行だけを一覧で見たい。それは、多くの行の中から必要な行を早く見つけるためだ。

出典: FR3.2〜FR3.6、FR10.5、SL、D・V・Q

- **AC1.2.1** Given テーブル T のカラム `code` の検索が `EQUALS`、`name` が `CONTAINS` / When `code` に `A01`、`name` に `商品` を入れて検索する / Then `code` が `A01` に等しく、かつ `name` に `商品` を含む行だけが出る（AND）
- **AC1.2.2（直した）** Given カラム `price` の検索が `RANGE` / When 下限 `100`・上限を空にして、または下限を空・上限 `200` にして、または両方を入れて検索する / Then 下限 100 のとき `price` が 100 の行は出て 99 の行は出ない。上限 200 のとき 200 の行は出て 201 の行は出ない（両端を含む）。下限が上限より大きい（下限 200・上限 100）ときは入力の誤りとして拒否される（SL。Q）
- **AC1.2.3（直した）** Given カラム `status` の検索が `CHOICE` で、固定の選択肢がある / When 選択肢から2つを選んで検索する / Then `status` がそのどちらかの行だけが出る。選択肢を1つも選ばないときは `status` を条件にしない。固定の選択肢に無い値を要求に入れると入力の誤りとして拒否される（Q）
- **AC1.2.4（直した）** Given カラム `name` の検索が `CONTAINS` / When `10%`、`A_1`、エスケープに使われうる文字（`\`・`!`）を含む値で検索する / Then `%`・`_`・`\`・`!` は文字として扱われ、`10%` を含む行だけが出る。`A_1` で `AB1` の行は出ない。3種類の DB で同じ（V・Q）
- **AC1.2.5（直した）** Given カラム `price` の検索が `RANGE` で数の型 / When 下限に `abc` を入れて検索する / Then 入力の誤りとして拒否され、誤りはその検索の項目の近くに画面の言語で出て、読み上げにも伝わる（`aria-invalid`・`aria-describedby`）。直前の結果の一覧は消えずに残る（D）
- **AC1.2.6（直した）** Given カラムの検索の設定に既定の値（DSL のキー `search.default`）がある / When 一覧を開く / Then 検索の項目に既定の値が入った状態で、その条件の結果が出る（V）
- **AC1.2.7** 〔Should〕 Given 検索の設定が `collapsed` / When 一覧を開く / Then 検索の項目は折りたたんだ状態で始まり、開閉の状態（`aria-expanded`）が分かる
- **AC1.2.8** Given カラム `dept_code` の検索が `CHOICE` で、選択肢が他テーブル参照（`REFERENCE`）か参照ピッカー（`LOOKUP`） / When 検索の項目を見る / Then 選択肢は出ず、文字の入力の完全一致（`EQUALS`）として検索できる（FR3.6）
- **AC1.2.9（直した）** Given カラム `secret` が NONE で、DSL では `search.enabled` / When 一覧を開く、または `secret` を条件に入れた要求を送る / Then 検索の項目に出ず、要求は DSL に無いカラムの名前を入れたときと同じ状態コード（400）と `code` で拒否され、`secret` の値で絞り込めない（US3.1。SL）
- **AC1.2.10** Given 一覧の2ページ目を見ている / When 検索の条件を変えて検索する / Then 1ページ目へ戻り、新しい全体の件数が出て、件数の変化が読み上げにも伝わる（D）
- **AC1.2.11** Given 条件に合う行が 0 件 / When 検索する / Then 「条件に合う行がありません」の旨と、条件をクリアする操作が出る。テーブルに行がそもそも無いときは「行がありません」の旨を出し分け、作成できる利用者には作成の入口を添える（SL。D）
- **AC1.2.12** Given 検索の項目 / When キーボードだけで操作する / Then 項目ごとに表示名の付いたラベルがあり、Enter か検索のボタンで検索でき、条件のクリアもキーボードで行える（D）
- **AC1.2.13** Given 真偽値の型のカラム `active` の検索が `CHOICE` で、選択肢（`options`）が無い（既定の DSL の生成の形） / When 検索の項目を見て選ぶ / Then 「はい」「いいえ」（英語は `Yes`・`No`）の2つが選択肢として出て、選んだ値の行だけが出る。真偽値でない型で選択肢の無い `CHOICE` は、完全一致（`EQUALS`）として検索できる（SL。V）
- **AC1.2.14** Given `EQUALS`・`CHOICE` のカラムが数・日付の型 / When 型として読めない値（`abc`・`2026-02-30`）を要求に入れる / Then 入力の誤りとして拒否される（SL。V）

### US1.3 ページを送り、並べ替える 〔Must〕

P1 業務データを見る人として、一覧をページに分けて送り、見たいカラムで並べ替えたい。それは、多くの行を順に見通すためだ。

出典: FR4.1〜FR4.4、NFR1、NFR2、SL、D・V・Q

- **AC1.3.1（直した）** Given 条件に合う行が 45 件・40 件・0 件 / When 一覧を開く（1ページ 20 件） / Then 45 件では1ページ目に 20 件が出て、全体の件数 45 と 3 ページあることが分かる。40 件ではちょうど 2 ページ。0 件では全体の件数 0 と行の無い旨が出る（Q）
- **AC1.3.2（直した）** 〔Should〕 Given 一覧を開いている / When 1ページの件数を 50、100 に変える / Then 1ページに最大 50 件、100 件が出る（ほかの件数の拒否は AC1.3.8）（SL。Q）
- **AC1.3.3** Given カラム `name` が `list.sortable`、`price` は `sortable` でない / When `name` で降順に並べ替える / Then 行は `name` の降順に並ぶ。`price` には並べ替えの操作が出ず、要求に `price` の並べ替えを入れると入力の誤りとして拒否される
- **AC1.3.4（直した）** Given DSL の `list.defaultSort` が `code` の昇順 / When 一覧を開く / Then 行は `code` の昇順に並ぶ。`defaultSort` が2つ以上のカラムにあるときは `list.order` の順に並べ替えのキーにする。`defaultSort` が無く主キーがあるテーブルでは主キーの順に並ぶ。主キーの無いテーブルと主キーの設定の無いビューでは順を確かめず、全体の件数と、出た行が条件に合うことだけを確かめる（V・Q）
- **AC1.3.5（直した）** Given 主キーのあるテーブルで、並べ替えのカラム `category` が同じ値の行 45 件（うち `category` が NULL の行を含む） / When `category` で並べ替えて 20 件ずつ 3 ページ読む / Then 3 ページの主キーの和集合が 45 件ちょうどで、重なりが無い（主キーの順を足して順を安定させる）（Q）
- **AC1.3.6（直した）** Given NONE のカラム `secret` が DSL では `sortable` / When 要求に `secret` の並べ替えを入れる / Then DSL に無いカラムの名前を入れたときと同じ状態コード（400）と `code` で拒否される（US3.1。SL）
- **AC1.3.7（直した）** Given 規模の上限（1 テーブル 100 カラム）のテーブルで、1ページ 100 件 / When 一覧の API を繰り返し呼ぶ / Then 応答時間が目安（1 秒）を満たす。全体の件数の問い合わせ（FR4.2）も含めて測る。測り方と、対象DB の行の数・数えきれないときの扱いは NFR 要件の段で決める（A1。V）
- **AC1.3.8** Given 一覧の API / When 1ページの件数に `20`・`50`・`100` を入れる、または `0`・`19`・`21`・`101`・負の数・数でない値を入れる / Then 20・50・100 は受け付け、ほかはすべて入力の誤りとして拒否される（FR4.1。SL。Q）
- **AC1.3.9** Given 並べ替えのカラムに NULL の行がある / When 昇順・降順に並べ替える / Then 3種類の DB のどれでも、昇順では NULL の行が最後、降順では最初に並ぶ（SL。Q）
- **AC1.3.10** Given 条件に合う行が 45 件で1ページ 20 件 / When 4 ページ目、非常に大きな番号（例: `2147483647`）、始まりより小さい番号、数でない値を要求する / Then 4 ページ目と大きな番号は空のページと全体の件数 45 が返る。始まりより小さい番号と数でない値は入力の誤りとして拒否される（SL。V・Q）
- **AC1.3.11** Given 主キーの無いテーブル、または主キーの設定の無いビュー / When 並べ替えてページを送る / Then 全体の件数は正しく、どのページの行も条件に合う。ページの境で行が重なる・抜けることは既知の制約として許す。ビューに DSL の主キーの設定があるときは、主キーのあるテーブルと同じく主キーの順を足して安定させる（AC1.3.5 と同じ確かめ）（SL。V・Q）
- **AC1.3.12** Given 並べ替えたカラムの見出し / When 読み上げで見出しを読む / Then 並べ替えの向き（`aria-sort` の昇順・降順）が分かり、並べ替えの操作は見出しのボタンとしてキーボードで行える。並べ替えのできないカラムの見出しはボタンにしない（SL。D）
- **AC1.3.13** Given 画面の言語が英語 / When ページ送り・件数・1ページの件数の選択を見る / Then 文言が英語で出る（make-you-chic-ui の部品の文言が日本語に固定のときは、FR14.5 の依頼（5）か frontend の側で満たす）（D）
- **AC1.3.14** Given 3ページ目を見ている間に、ほかの人の削除で全体が 2 ページに減った / When ページを読み直す / Then サーバーは空のページと新しい全体の件数を返し、画面は空である旨と前のページへ戻る操作を出す（空のまま何も出ない画面にしない）（SL。D）
- **AC1.3.15** Given 1 テーブル 100 カラムの一覧、画面の幅が狭い（375px を含む） / When 一覧を見て、右端の行の「操作」のメニューを開く / Then 画面全体は横にスクロールせず、表の領域だけが横にスクロールする。表の領域はラベルの付いた領域としてキーボードからもスクロールでき、見出しの行は読み上げで列の名前として伝わる。行の「操作」のメニューは開いたときに画面の中に収まる（PM の user-admin の学び。SL。D）
- **AC1.3.16** Given 件数の多いテーブル（行の数は NFR 要件の段で決める） / When 一覧の1ページを読む / Then 1回の問い合わせで対象DB から読む行の数はページの件数を超えない（取り出しの上限が効くことを、読んだ行の数を数える形で確かめる。上限の値は NFR 要件の段で決める）（TP。Q）

### US1.4 行の詳細を見る 〔Must〕

P1 業務データを見る人として、一覧の行から詳細の画面へ移り、その行のカラムを見たい。それは、一覧に出ないカラムを含めて行の中身を確かめるためだ。

出典: FR5.1〜FR5.3、FR7.4、FR13.1、SM5、SL、D・V・Q

- **AC1.4.1** Given テーブル T が READ、主キーがあり、主キーのカラムがすべて READ 以上 / When 一覧の行の詳細への入口を選ぶ / Then その行の詳細の画面が開き、`detail.visible` のカラムのうち READ 以上のものが出る
- **AC1.4.2（直した）** Given 複合の主キー `(order_id, line_no)` の行と、主キーの値に `/`・`%`・`?`・`#`・空白・`'`・`"`・非 ASCII の文字（例: `A/1 #`・`商品`）を含む行、区切りに使われうる文字を含む別々の行（例: `("a,b","c")` と `("a","b,c")`） / When 詳細を開き、同じ行を更新・削除で指す / Then どれもその1行だけが指され、`("a,b","c")` と `("a","b,c")` は別の行として指せる（TP。Q）
- **AC1.4.3** Given 詳細を開こうとした行が、ほかの人に削除された / When 詳細を開く / Then 画面は「行が見つからない（ほかの人が削除した可能性）」の表示になる（サーバーが 404 を返す）
- **AC1.4.4（直した）** Given 主キーの無いテーブル、または主キーのカラムのどれかが NONE / When 一覧を見る・詳細の API を直接呼ぶ / Then 行に詳細への入口が出ず、詳細の API は 409 と行の操作ができない旨の `code` で拒否され、監査には残らない（読み取り）。主キーのカラムが NONE のとき、一覧の応答にその主キーの値は含まれない（US3.2。SL。V・Q）
- **AC1.4.5** Given カラム `memo` が READ で `detail.visible` が false / When 詳細を開く / Then `memo` は画面に出ず、詳細の応答にも含まれない（FR2.2a）
- **AC1.4.6** Given 検索の条件・並べ替え・ページを変えた一覧から詳細へ移った / When 詳細の「一覧へ戻る」か、ブラウザの戻る操作で一覧へ戻る / Then 移る前の条件・並べ替え・ページのまま一覧が出る。画面を再読み込みすると既定の状態に戻る。画面の道に検索の値は載らない（SM5 A。D）
- **AC1.4.7** Given 詳細の画面 / When 開く / Then 画面の見出しにテーブルの表示名と、行を見分ける値（主キーの値、または機能設計で決めた代表のカラム）が出て、一覧へ戻る入口がある。フォーカスは画面の見出しに移る（D）
- **AC1.4.8** Given 主キーが DSL の型の分類に無い型（PostgreSQL の `uuid` など、文字の型でない主キー）の行 / When 詳細・更新・削除で行を指す / Then 1行が正しく指され、型の誤りにならない（SL。V）

### US1.5 値を読みやすい形で見る 〔Must〕

P1 業務データを見る人として、表示名と日付・数・真偽値を、画面の言語に合った形で見たい。それは、DB の物理名や生の値を読まずに中身を理解するためだ。

出典: FR11.1〜FR11.5、NFR6、SM3、SM7、D・Q

- **AC1.5.1** Given テーブルとカラムに DSL の表示名（ja・en）がある / When 画面の言語を日本語・英語に切り替える / Then 見出しと項目名がその言語の表示名で出る
- **AC1.5.2（直した）** Given 一覧の書式が `DATE`・`DATETIME`・`TIME`・`NUMBER_GROUPED`・`BOOLEAN_YES_NO` のカラム / When 日本語と英語の画面で一覧を見る / Then それぞれ `2026-10-18`・`2026-10-18 09:30:00`・`09:30:00`・`1,234,567`・「はい／いいえ」（英語では `Yes`／`No`）で出る。日付・時刻の形は英語でも同じ。負の数と小数は `-1,234.5` のように出る。真偽値が NULL の行は NULL の出し方（AC1.5.5）で出る（Q）
- **AC1.5.3（直した）** Given 時差の無い日時の型のカラムの DB の値が `2026-10-18 09:30:00` / When アプリの JVM・ブラウザ・対象DB の接続のタイムゾーンを互いに違う値（UTC と Asia/Tokyo）にして一覧と詳細を見る / Then `2026-10-18 09:30:00` のまま出る（変換しない）（Q）
- **AC1.5.4（直した）** Given カラムの値が `<script>alert(1)</script>`・`<img src=x onerror=alert(1)>`・`javascript:x`・`'` を含む値、表示名が `"A&B"` / When 一覧と詳細を見る / Then 文字のまま出て、HTML として描かれず、スクリプトは動かず、`javascript:x` はリンクの先にならない（TP。Q）
- **AC1.5.5** Given 値が NULL の行と、空の文字列の行 / When 一覧と詳細を見る / Then 2つは見分けがつく形で出る（出し方は画面の段で決める）
- **AC1.5.6** Given 長い文字・桁の多い数の値 / When 一覧と詳細を見る / Then 一覧のセルでは省略して出してもよいが、詳細では値の全体を読める。省略したセルは、読み上げで全体が分かるか、詳細へ移れる（D）
- **AC1.5.7** Given PostgreSQL の `timestamptz`・`timetz`、MySQL・MariaDB の `timestamp` のカラム / When 対象DB の接続の既定のタイムゾーンを UTC でない値にして一覧と詳細を見る / Then 値は UTC に固定して `+00:00` を付けて出る（例: `2026-10-18 00:30:00+00:00`）。3種類の DB で同じ（SM7 A）
- **AC1.5.8** Given フォーム部品が `password` のカラム `pin` / When 一覧と詳細を見る / Then 値は伏せて出て（例: `••••••`）、一覧・詳細の応答にも値そのものは含まれない（SM3 A。V）

## 群2 業務データを直す

### US2.1 行を作成する 〔Must〕

P2 業務データを直す人として、テーブルに新しい行を作成したい。それは、DB を直接触る人に頼まずにマスタを登録するためだ。

出典: FR6.1〜FR6.5、FR10.1、FR10.5、FR12.1、SL、D・V・Q

- **AC2.1.1（直した）** Given テーブル T の CREATE が可で、`detail.visible` のカラム `code`・`name` が FULL / When 作成の画面で値を入れて保存する / Then 行が作成され（別の接続で読み直して値を確かめる）、その行の詳細へ移り、「作成しました」の知らせが出て読み上げにも伝わり、作成が監査に残る（US3.4）（D・Q）
- **AC2.1.2** Given T の CREATE が不可 / When 一覧を見る / Then 作成の入口が出ず、作成の API を直接呼ぶと 403 が返り、行は増えない（US3.5）
- **AC2.1.3（直した）** Given 作成の画面 / When 画面を見て値を入れる / Then FULL のカラムは DSL のフォーム部品（`text`・`textarea`・`checkbox`・`switch`・`radio`・`select`・`date`・`datetime`・`number`・`password`）で入力でき、READ のカラムは入力できない。`select`・`radio` の選択肢は DSL の固定の選択肢（`FIXED`）が出る。API に、`select`・`radio` の固定の選択肢に無い値、`checkbox`・`switch` に真偽値でない値、`date`・`datetime` に無い日（`2026-02-30`）を入れると入力の誤りとして拒否される（Q）
- **AC2.1.4** Given 主キーの無いテーブルで CREATE が可 / When 行を作成する / Then 作成され、詳細へ移れないため一覧へ戻る
- **AC2.1.5（直した）** Given 入力しない NOT NULL のカラムに既定値が無い / When 保存する / Then DB が拒む保存の失敗として返り、行は増えず、失敗が監査に残る。応答・アプリのログ・監査のどれにも JDBC の例外のメッセージは出ない（A2。Q）
- **AC2.1.6（直した）** Given カラム `dept_code` が他テーブル参照の選択肢（`REFERENCE`）で文字の入力として扱われ、外部キーがある / When 参照先に無い値を入れて保存する / Then 「参照先に無い値」の誤りとして返り、行は増えず、失敗が監査に残る。違反したカラムを DB の制約と対象DB のメタデータで決められるときは `dept_code` を示し、決められないときはフォーム全体の誤りとして出す。3種類の DB で同じ誤りになる（DB ごとに違う誤りの番号を読み替える）（FR6.2a。SL。Q）
- **AC2.1.7（直した）** Given 要求の本文に、NONE・READ のカラム、`detail.visible` で隠すカラム、DSL に無いカラムの値を足す / When 作成の API を呼ぶ / Then どれも同じ状態コード（400）と `code` で拒否され、行は増えない（一括代入の防止。US3.1。SL）
- **AC2.1.8** Given 主キーが DB の自動の採番（`serial`・`identity`・`AUTO_INCREMENT`）で、作成の画面で主キーを入れない / When 保存する / Then DB が作った主キーの値の行の詳細へ移る。3種類の DB で同じ（SL。V）
- **AC2.1.9** Given FULL のカラム `note` に DB の既定値 `-` があり、作成の画面で `note` を空のままにする / When 保存する / Then `note` は対象DB の既定値 `-` になる（FR6.4。空の入力の読みは「前提と読み方」）
- **AC2.1.10** Given 作成・更新・削除の要求を送った / When 応答を待つ / Then 保存・削除のボタンは処理中の表示になり押せない（二度押しで同じ行を二度作らない）。5 秒を超えたら「時間がかかっています」の旨が出る（既存の時間がかかる旨の表示と同じ形）（SL。D の AC2.5.1 を、US2.5 と番号が重なるためこの番号にした）

### US2.2 行を更新する 〔Must〕

P2 業務データを直す人として、行の詳細から更新の画面を開き、値を直して保存したい。それは、間違いのある値をその場で直すためだ。

出典: FR7.1〜FR7.4、FR10.1、FR12.1、SM1〜SM3、SM6、SQ7、D・V・Q

- **AC2.2.1** Given 詳細へ移れる行で、`detail.visible` のカラム `name` が FULL、`code` が READ / When 更新の画面を開く / Then `name` は入力でき、`code` は読み取りで出る。値は詳細と同じ API で読んだ今の値が入る
- **AC2.2.2（直した）** Given 更新の画面で `name` だけを直した / When 保存する / Then `name` が変わり、ほかのカラム（NONE・READ・`detail.visible` で隠すカラムを含む）は変わらず NULL で上書きもされない（別の接続で読み直して確かめる）。その行の詳細へ戻り、「更新しました」の知らせが出て読み上げにも伝わり、更新が監査に残る（SM1 A。D・Q）
- **AC2.2.3（直した）** Given 利用者 A と B が同じ行の更新の画面を開いている / When A が `name` を変えて保存した後に、B が `price` を変えて保存する。別の回で、A の後に B が同じ `name` を別の値で保存する / Then 前の回では `name` は A の値、`price` は B の値になる（各人が変えたカラムだけを保存する）。後の回では `name` は B の値になる（後から保存した人の値。FR7.2）（SM1 A。Q）
- **AC2.2.4** Given 更新の画面を開いた後に、ほかの人がその行を削除した / When 保存する / Then 行が無いとして 404 が返り、失敗が監査に残る
- **AC2.2.5（直した）** Given 主キーのカラムが FULL / When 更新の画面を見る、更新の要求の本文に主キーのカラムを入れる（値が今と同じでも違っても） / Then 画面では主キーは読み取りで出る。要求は書けないカラムと同じ状態コード（400）と `code` で拒否され、行は変わらない（SL。V・Q）
- **AC2.2.6** Given テーブル T のすべてのカラムが READ / When 詳細を見る / Then 更新の入口が出ず、更新の API を直接呼ぶと 403 が返る（US3.5）
- **AC2.2.7（直した）** Given `detail.visible` で隠す FULL のカラム `note` / When 更新の画面を見る、または要求に `note` の値を入れる / Then `note` は画面に出ず、要求は書けないカラムと同じ状態コード（400）と `code` で拒否され、`note` の値は変わらない（SQ7 A。SL）
- **AC2.2.8** Given 行のカラムに、画面の入力の形に乗らない値（日時の秒の小数 `09:30:00.123456`、NULL の真偽値、PostgreSQL の `char(n)` の後ろの空白、`DECIMAL(10,4)` の `1.5000`、表示の上限を超える長い文字）がある / When 更新の画面で別のカラム `name` だけを直して保存する / Then `name` 以外のカラムの値は、別の接続で読み直して1文字も変わっていない（SM1 A。V）
- **AC2.2.9** Given 更新の画面 / When 「やめる」を選ぶ、または何も変えずに保存する / Then 「やめる」では何も変わらず詳細へ戻る。何も変えない保存の扱い（保存を押せなくするか、変化の無い成功とするか、監査に残すか）は機能設計で決め、決めた側の動作を明示したテストにする（D）
- **AC2.2.10** Given NULL を許すカラムで、文字の型の `remark` と数の型の `qty` に値がある / When 更新の画面で両方の入力を空にして保存する / Then `remark` は空の文字列、`qty` は NULL になる（別の接続で読み直して確かめる）（SM2 A）
- **AC2.2.11** Given フォーム部品が `password` の FULL のカラム `pin` / When 更新の画面を開き、`pin` を空のまま別のカラムを直して保存する。別の回で `pin` に値を入れて保存する / Then 更新の画面の `pin` は空で始まり、空のままの保存では `pin` は変わらない。値を入れたときだけ `pin` がその値になる（SM3 A）
- **AC2.2.12** Given 作成・更新の画面で入力を変えた / When 保存せずに、「やめる」・メニュー・ブラウザの戻る操作・作業ロールの切り替えで離れようとする / Then 離れるか留まるかを確かめる表示が出て、「留まる」では入力が残る。変更が無いときは確かめずに離れる（SM6 A）
- **AC2.2.13** Given 更新の画面を開いている間に作業ロールを切り替え、そのテーブルの FULL が無くなった / When 保存する / Then 403 の表示になり、権限が変わった旨が分かる。行は変わらない。入力していた値の扱い（残すか捨てるか）は画面の段で決める（D）

### US2.3 行を削除する 〔Must〕

P2 業務データを直す人として、要らなくなった行を確かめてから削除したい。それは、誤って消すことを防ぎながらマスタを整理するためだ。

出典: FR8.1・FR8.2、FR12.1、FR12.4、SM5、SL、D・Q

- **AC2.3.1（直した）** Given 詳細へ移れる行で、テーブルの DELETE が可 / When 削除を選ぶ / Then 確かめの表示が出て、消す行を見分ける値（テーブルの表示名と主キーの値、または代表のカラム）と、元に戻せない旨が出る。「やめる」を選ぶと何も変わらない。背景のクリックで閉じず、はじめのフォーカスは「やめる」にある（D）
- **AC2.3.2（直した）** Given 確かめの表示で削除を選んだ / When 削除が終わる / Then 行が消え（別の接続で読み直して無いことを確かめる）、一覧へ戻り、戻る前の条件・並べ替え・ページを保ち、「削除しました」の知らせが出て読み上げにも伝わり、削除が監査に残る（SM5 A。D・Q）
- **AC2.3.3** Given DELETE が不可 / When 詳細を見る / Then 削除の入口が出ず、削除の API を直接呼ぶと 403 が返り、行は残る（US3.5）
- **AC2.3.4（直した）** Given ほかの表から外部キーで参照されている行 / When 削除する / Then DB が拒む保存の失敗として業務の言葉で返り、行は残り、失敗が監査に残る。応答・アプリのログ・監査に JDBC の例外のメッセージは出ない（Q）
- **AC2.3.5（直した）** Given 削除しようとした行が、ほかの人に先に削除された / When 削除する / Then 行が無いとして 404 が返り、失敗が監査に残る（FR12.4）
- **AC2.3.6** Given 削除する行を、作業ロールで NONE のテーブル U の行が `ON DELETE CASCADE` の外部キーで参照している / When 行を削除する / Then 削除は成功し、U の参照している行も DB によって消える（既知の制約の振る舞いを明示したテスト。監査に残るのは削除した行だけ）（SL。Q）

### US2.4 入力の誤りをその場で直す 〔Must〕

P2 業務データを直す人として、入力の誤りを、どのカラムの何が誤りかが分かる形で知りたい。それは、保存できない理由を自分で直してやり直すためだ。

出典: FR10.1、FR10.4、FR10.5、A2、SM4、D・V・Q

一意の確かめ（AC2.4.3・AC2.4.4）は US2.5 へ移した（ID は保った）。

- **AC2.4.1（直した）** Given DSL の検証（`required`・長さ・範囲）と DB の型（NOT NULL・文字の長さ・数の桁） / When 誤った値を入れる / Then 画面で保存の前に誤りが出る。画面の検証を通さずに API を直接呼んでも、サーバーが同じ誤りで拒否する（サーバー側を正とする）。`pattern` は画面では当てず、保存のときにサーバーの誤りが該当の入力に出る（SM4 A）
- **AC2.4.2（直した）** Given 文字の長さの上限が 20、`DECIMAL(5,2)` のカラム、範囲 1〜10 のカラム / When 長さ 20 と 21 の値（サロゲートペアの `𠮷` や絵文字 `😀` を含む値も）、`999.99` と `1000.00`・`1.234`・`1234.5`、`1` と `10`・`0` と `11` を入れる / Then 長さは DB と同じく文字（コードポイント）で数え、20 は受け付け 21 は誤り（画面とサーバーで判定が食い違わない）。`999.99` は受け付け、`1000.00`・`1.234`・`1234.5` は誤り（DB が黙って丸めない・切り詰めない）。範囲は両端を含む（V・Q）
- **AC2.4.5（直した）** Given `pattern` が時間のかかる正規表現（例: `(a+)+$`）/ When `aaaa…b` のような長い値を保存する / Then 時間の上限を超えたら検証の誤りとして返り、要求は上限の時間と余裕の中で終わる（上限と余裕の値は NFR 要件の段で決める）（Q）
- **AC2.4.6（直した）** Given 誤りが複数のカラムにある / When 保存する / Then 誤りはカラムごとに、画面の言語（日本語・英語）で、該当の入力の近くに出て、読み上げにも伝わる。フォーカスは最初の誤りの入力（または誤りのまとめ）へ移り、入力した値は消えない（D）
- **AC2.4.7** Given DB が拒んだ保存の失敗（外部キー・NOT NULL など） / When 画面で受ける / Then DB の文や制約の名前は出さず、業務の言葉で出す。カラムが分かるときはそのカラムの入力に出す。入力できないカラム（NONE・READ）の NOT NULL で拒まれたとき（A2）は、利用者には直せない旨（例: 「このテーブルの作成には、入力できない項目の値が要ります。管理者に確かめてください」）を出す。入力した値は消えない（SL。D）
- **AC2.4.8** Given 必須のカラムと長さの上限のあるカラム / When 作成・更新の画面を見る / Then 必須であることが入力の前に印と文言で分かり、読み上げにも伝わる（`aria-required`）。長さの上限も入力の前に分かる（SL。D）

### US2.5 同じ値の重なりを防ぐ 〔Must〕

P2 業務データを直す人として、一意であるべきカラムに同じ値を入れたときに、保存の前にそれと分かってほしい。それは、重なった値でマスタを壊さないためだ。

出典: FR10.2、FR10.3、FR12.4、SL、V・Q

- **AC2.4.3（直した。US2.4 から移した）** Given カラム `code` が DSL で `unique` / When ほかの行と同じ値で作成・更新する / Then 「同じ値がある」の誤りとして `code` を示して返り、行は変わらない。更新で自分の行の今の値のまま保存するときは誤りにならない。「同じ値」の判定は対象DB の照合順序に従い（大文字と小文字）、NULL どうしは重なりとしない（Q）
- **AC2.4.4（直した。US2.4 から移した）** Given DB に一意の制約がある `code` / When 2人が同じ時に同じ値で作成する（重なりは待ち合わせで作る） / Then 一方は成功し、もう一方は「同じ値がある」の誤りで返る（500 にならない）。DB に一意の制約が無いカラムで同時に重なった値が入りうることは、受け入れ基準ではなく既知の制約（FR10.3）として扱う（SL。V・Q）
- **AC2.5.1** Given DSL では `unique` でないが、DB に一意の制約があるカラム / When 同じ値で保存する / Then DB の制約の違反も「同じ値がある」の誤りとして返る（FR10.2）。応答・アプリのログ・監査に JDBC の例外のメッセージ（`Key (code)=(A01) already exists` のような行の値）は出ない（Q）
- **AC2.5.2** Given 一意の重なりで作成・更新が拒否された / When 監査を読む / Then 失敗と「同じ値がある」の理由の `code` が残る（FR12.4）

## 群3 横断の決まり

### US3.1 作業ロールの権限どおりにカラムが見え、直せる 〔Must〕

P2 業務データを直す人として、今の作業ロールの権限どおりに、見えるカラムと入力できるカラムが決まってほしい。それは、見てはいけない値が出ず、許されたカラムだけを直せるようにするためだ。

出典: FR2.2、FR2.2a、FR2.4、FR9.3、SL、TP、V・Q

API の認可と作業ロールの切り替え（AC3.1.2〜AC3.1.5）は US3.5 へ移した（ID は保った）。

- **AC3.1.1** Given テーブル T が READ、カラム `secret` が NONE、`name` が FULL / When 一覧・詳細・作成と更新の画面を見る / Then `secret` はどこにも出ず、一覧・詳細の応答にも含まれない。`name` は作成・更新で入力できる
- **AC3.1.6（直した）** Given 要求の本文や条件に、NONE のカラム・READ のカラム（作成・更新の値）・`detail.visible` で隠すカラム・DSL に無いカラムを入れる / When 業務データの API を呼ぶ / Then どれも同じ状態コード（400）と `code` で拒否され、対象DB の行は変わらない（一括代入・IDOR の防止。SL。V・Q）
- **AC3.1.7** Given 主権限と補助権限の任意の組と DSL の表示の設定の任意の組 / When 一覧・詳細・作成・更新の画面と応答に出すカラムを求める関数を性質ベースのテスト（jqwik・fast-check）で確かめる / Then NONE のカラムは出ない、FULL でないカラムは入力にならない、権限を上げても出るカラムは減らない。失敗時の乱数の種を記録する
- **AC3.1.8** Given 一覧で `list.visible` のカラムが `name`・`price`、主キー `id` は READ で `list.visible` が false、カラム `memo` は READ で `list.visible` が false / When 一覧の応答を見る / Then `name`・`price` と、行を指すための `id` が含まれ、`memo` は含まれない。`id` は画面の列には出ない（FR2.2a。Q）
- **AC3.1.9** Given 一覧・詳細の応答が返す操作の可否（作成・詳細・更新・削除）とカラムごとの入力の可否 / When 同じ利用者・同じ行で、その操作の API を呼んだ結果と比べる / Then 応答が「できる」と返した操作は API が受け付け、「できない」と返した操作は API が拒否する（画面はサーバーが返す可否で入口を出す。FR9.3。AC3.1.7・AC3.2.7 と同じ関数で求める）（V）
- **AC3.1.10** Given テーブル T がスキーマ S1 にあり、スキーマ S2 には無い（または S2 の T は NONE） / When 要求のスキーマ名を S2 に差し替えて T の一覧・詳細・作成・更新・削除を呼ぶ / Then 拒否され（DSL に無いなら 404、NONE なら 403）、S1 の T の行は変わらない（TP。Q）

### US3.2 主キーとビューで、行の操作が決まる 〔Must〕

P2 業務データを直す人として、行を1つに決められないテーブルやビューでは、詳細・更新・削除ができないことと、その理由が分かってほしい。それは、意図しない行を変えないためだ。

出典: FR9.1〜FR9.3、FR6.3、FR12.4、SM8、SL、PM、D・V・Q

- **AC3.2.1（直した）** Given 主キーの無いテーブル、CREATE・DELETE が可、カラムが FULL / When 一覧を見る・API を直接呼ぶ / Then 一覧・検索と作成はできるが、詳細・更新・削除の入口は出ず、API は 409 と行の操作ができない旨の `code` で拒否される。更新・削除の拒否は監査に残り、詳細の拒否は残らない（SL。V・Q）
- **AC3.2.2（直した）** Given 主キー `id` が NONE、ほかのカラムが FULL、CREATE・DELETE が可。あわせて、複合の主キー `(order_id, line_no)` のうち `line_no` だけが NONE のテーブル / When 一覧を見る・API を直接呼ぶ / Then どちらも、一覧・検索と作成はできるが、詳細・更新・削除は 409 で拒否される（更新・削除は監査に残る）（Q）
- **AC3.2.3（直した）** Given ビュー、作業ロールで FULL・CREATE・DELETE が可 / When 一覧を見る・API を直接呼ぶ / Then 一覧・検索はできるが、作成・更新・削除の入口は出ず、API は 409 で拒否され、拒否は監査に残る。詳細は、主キーの設定があり主キーのカラムがすべて READ 以上なら出る
- **AC3.2.4** Given 主キーがあり、主キーのカラムがすべて READ 以上 / When 権限の組（FULL のカラムの有無・CREATE・DELETE）を変える / Then 要件 FR9.1 の表のとおりに入口と API の可否が変わる（表のパラメーターのテストで書く）
- **AC3.2.5** Given 主キーの無いテーブル・主キーのカラムが NONE のテーブル・ビューの一覧 / When 一覧を見る / Then 入口を出さないだけでなく、一覧の上に理由が出る（例: 「このテーブルは行を1件に決められないため、詳細・更新・削除はできません」「このビューは読み取りだけです」）。理由の文は権限の設定の中身（どのカラムが NONE か）を出さない（SL。D）
- **AC3.2.6** Given DSL の主キー `code` が、対象DB では一意でない（同じ `code` の行が2つある） / When その `code` で更新・削除・詳細を行う / Then 更新・削除は当たる行が1行でないことを確かめて巻き戻し、「行を1つに決められない」の誤りで拒否され（監査に残る）、どの行も変わらない（別の接続で読み直す）。詳細も同じ誤りで拒否され、監査には残らない（SM8 A。V・Q）
- **AC3.2.7** Given 主キーの有無・ビューか・主キーのカラムの主権限・FULL のカラムの有無・CREATE・DELETE の任意の組 / When 許す操作の集合を求める関数を性質ベースのテスト（jqwik と、画面側の同じ関数があれば fast-check）で確かめる / Then 権限を足しても許す操作は減らない、主キーの無いテーブルと主キーのカラムが NONE のテーブルに詳細・更新・削除が出ない、ビューに作成・更新・削除が出ない。失敗時の乱数の種を記録する（TP。Q）

### US3.3 見られない・無いときに理由が分かる 〔Must〕

P1 業務データを見る人として、テーブルや行を開けないときに、権限が無いのか、テーブルや行が無いのか、つながらないのかが分かってほしい。それは、管理者に頼むべきか、探し直すべきか、時間をおいてやり直すべきかを判断するためだ。

出典: FR13.1〜FR13.4、FR1.3、NFR4.4、SQ6、SL、PM、D・V・Q

- **AC3.3.1** Given 適用中の DSL に無いテーブル / When 業務データの API を呼ぶ / Then 404 が返る
- **AC3.3.2** Given DSL にあるが作業ロールで NONE のテーブル / When 業務データの API を呼ぶ / Then 403（code `ACCESS_DENIED`）が返る
- **AC3.3.3** Given DSL が適用されていない / When 業務データの API を呼ぶ / Then 404 が返る
- **AC3.3.4（直した）** Given 対象DB に接続できない、または応答しない（既存の ServerSocket の方式） / When 一覧（全体の件数の問い合わせを含む）・詳細・作成・更新・削除を行う / Then どれも目的ごとの時間の上限の中で業務データの機能の誤りとして返り、画面はその旨を出す。応答とアプリのログに JDBC の例外のメッセージ・接続先・行の値が含まれない（Q）
- **AC3.3.5（直した）** Given 作成・更新・削除が時間切れになった / When 応答を受ける / Then 画面に「保存されたか分からない」旨と、確かめる入口が出る。更新・削除ではその行の詳細を開き直して確かめるよう、作成では作り直す前に一覧で同じ行が無いかを確かめるよう促す（SQ6 A。SL。D）
- **AC3.3.6** Given 作業ロールで NONE のテーブル T と、T に有る行の主キーの値・無い行の主キーの値 / When 詳細・更新・削除の API を呼ぶ / Then どちらも同じ 403 `ACCESS_DENIED` が返り、応答から行の有無を推測できない（判定の順。SL。Q）
- **AC3.3.7** Given 403・テーブルが見つからない・行が見つからない・DSL が適用されていない・対象DB とつながらない / When 画面で受ける / Then それぞれ別の文で出し（例: 権限が無い・テーブルが無い・行が無い（ほかの人が削除した可能性）・業務データを使える状態でない・対象DB とつながらない）、次の行き先（一覧へ戻る・メニューから選び直す・やり直す）がある。つながらないときは「やり直す」で読み直せる（SL。D）
- **AC3.3.8** Given DSL にあるカラム（またはテーブル）が対象DB に無い（DSL の適用の後に対象DB が変わった） / When 一覧・詳細・作成・更新・削除を行う / Then 業務データの機能の誤り（DSL と対象DB の食い違いの旨）として返り、500 にならず、応答とログに JDBC の例外のメッセージと行の値が含まれない（SL。V）
- **AC3.3.9** Given 書き込みの接続の設定（`.env`）が無い / When アプリを起動し、一覧・詳細を見て、作成・更新・削除の API を直接呼ぶ / Then アプリは起動を続け、一覧・詳細は動く。作成・更新・削除の入口は出ず、API は書き込みができない旨の専用の `code` で拒否される（SL。V）
- **AC3.3.10** Given 1つの要求が複数の拒否に当たる組（例: DSL に無いテーブルで未認証、NONE のテーブルで入力の誤り、主キーの無いテーブルで更新の本文に書けないカラム） / When API を呼ぶ / Then 「前提と読み方」の判定の順で最初に当たった応答が返る（表のパラメーターのテストで書く。④・⑦の中の順は機能設計で決めた順）（SL。Q）

### US3.4 業務データの操作を監査で追える 〔Must〕

P3 管理者として、誰がいつどのテーブルの行を作成・更新・削除したか、拒否・失敗したかを、内部DB の監査の記録で追いたい。それは、後から変更の経緯を確かめるためだ。

出典: FR12.1〜FR12.4、SQ6、SM8、SL、PM、D・V・Q

監査を見る画面はこの Intent の範囲の外。監査は内部DB の記録で読む（今の手順では、配備したアプリを止めた複写を読み取りで開く）。

- **AC3.4.1（直した）** Given 行の作成・更新・削除が成功した / When 監査の記録を読む / Then 操作した人・作業ロール・スキーマ・テーブル・操作の種類・結果・行の主キーの値（主キーの無いテーブルの作成では無し）が読み出せ、主キー以外の値と更新の前後の値は残らない。どの欄に置くか（欄を足すか、中身の JSON に入れるか）は機能設計で決める（V）
- **AC3.4.2（直した）** Given 業務の理由の拒否（主キーとビューの決まりの 409・一意の重なり・行が無い 404・行が1つに決まらない）と DB が拒んだ保存の失敗（外部キー・NOT NULL） / When 監査の記録を読む / Then 失敗と理由の `code` が残る（SM8 A。SL）
- **AC3.4.3** Given 対象DB に接続できない・時間切れで作成・更新・削除が失敗した / When 監査の記録を読む / Then 失敗と、「接続できない」「時間切れ（確定したか分からない）」を分けた理由の code が残る（SQ6 A）
- **AC3.4.4（直した）** Given 権限の不足（403）、入力の検証の誤り（400。書けないカラムの拒否を含む）、DSL に無いテーブル・DSL が適用されていないときの作成・更新・削除（404） / When 監査の記録を読む / Then どれも監査に残らない（SL。Q）
- **AC3.4.5（直した）** Given 一覧・詳細を読んだ、または詳細が拒否された（409・403・404） / When 監査の記録を読む / Then 監査に残らない（FR12.2。V・Q）
- **AC3.4.6** Given 監査の書き込みが失敗する（テストで失敗させる） / When 行を更新する / Then 更新は成功のままで、失敗がアプリのログに残り、そのログに主キーの値と行の値が含まれない
- **AC3.4.7** Given 主キーの値が長い（複合の主キー、長い文字） / When 作成・更新・削除が監査に残る / Then 監査の中身の上限を超える分は、切り詰めたと分かる形で残る（黙って切らない。上限と形は機能設計で決める）（SL。V）
- **AC3.4.8** Given DB が拒んだ保存の失敗・接続の失敗 / When 監査の記録を読む / Then 監査の行に JDBC の例外のメッセージ・行の値（主キー以外）・接続先は含まれない（PM。Q）

### US3.5 API が作業ロールの権限で守られる 〔Must〕

P2 業務データを直す人として、業務データの API が、今の作業ロールの権限どおりに受け付け・拒否してほしい。それは、作業ロールを切り替えたり権限が変わったりした直後でも、許された操作だけができるようにするためだ。

出典: FR2.1、FR2.3、FR2.5、FR2.6、TP、KB K-61、SL、V・Q

- **AC3.1.2（直した。US3.1 から移した）** Given API ごとに要る権限だけを欠く利用者（ほかのテーブルは FULL・CREATE・DELETE が可）: 一覧・詳細はそのテーブルだけ NONE、作成は CREATE だけ不可、更新は変えるカラムだけ READ（ほかのカラムは FULL）、削除は DELETE だけ不可 / When 業務データの API（一覧・詳細・作成・更新・削除）を呼ぶ / Then 403 が返る。未認証は 401、要る権限を持つ利用者は成功、停止中の利用者は権限があっても通らない。API と権限の組は表のパラメーターのテストで書く（TP。Q）
- **AC3.1.3（US3.1 から移した）** Given 作業ロール「営業（参照）」で T が READ、「商品マスタ担当」で T が FULL・CREATE 可 / When 作業ロールを切り替えた直後に作成の API を呼ぶ / Then 切り替えの後の次の要求で、403 と成功が入れ替わる（画面が持つ古い権限に頼らない）
- **AC3.1.4（直した。US3.1 から移した）** Given 管理者がロールの権限の設定を変えた、または利用者にロールの割り当てを付けた・外した / When その利用者の次の要求 / Then 新しい権限で判定され、403 と成功が入れ替わる（変更の前に出したアクセストークンのまま）（TP。Q）
- **AC3.1.5（US3.1 から移した）** Given 管理者の印を持つ利用者の作業ロールで T が NONE / When T の一覧の API を呼ぶ / Then 403 が返る（管理者でも業務データは作業ロールで決まる。FR2.6）
- **AC3.5.1** Given アプリのすべての API / When API の分類を確かめる既存のテストを流す / Then この Intent で足す業務データの API はすべて「ログインだけ」に分類されて載る。分類を足し忘れるとこのテストが落ちる（TP。KB K-61）
- **AC3.5.2** Given ロールが1つも無く作業ロールが無い利用者 / When 業務データの API を呼ぶ / Then どのテーブルも NONE として 403 が返る（DSL に無いテーブルは 404）

### US3.6 業務データの SQL と接続が入力や DB の違いで乱れない 〔Must〕

P2 業務データを直す人として、記号を含む値や大きな数を入れても、3種類のどの対象DB でも値が正しく扱われ、ほかの行や DB が乱されないでほしい。それは、マスタの値を壊さずに安心して直すためだ。

出典: NFR3、NFR4.1〜NFR4.3、TP（SQL の組み立て・3種類の対象DB の境界の値・行の数の上限・接続の数・漏えい）、PM、SL、V・Q

- **AC3.6.1** Given スキーマ名・テーブル名・並べ替えの列・検索の列・本文のカラム名に `'`・`"`・`;`・`--`・バッククォート・改行を含む要求 / When 業務データの API を呼ぶ / Then DSL に無い名前として拒否され（テーブル・スキーマは 404、カラムは書けないカラムと同じ 400）、対象DB の行は変わらない（TP。Q）
- **AC3.6.2** Given 検索の値・作成と更新の値・主キーの値に `'`・`"`・`;`・`--`・バッククォート・改行を含む / When API を呼ぶ / Then 値はその文字として扱われ（検索ならその文字を含む行だけが出る、作成ならその文字のまま保存される）、SQL として解釈されない。3種類の DB で確かめる（TP。Q）
- **AC3.6.3** Given DSL の名前に大文字と小文字・空白・予約語を含むテーブルとカラム（例: `Order Item`・`select`） / When 一覧・詳細・作成・更新・削除を行う / Then 3種類の DB で正しく引用されて同じ結果になる（Q）
- **AC3.6.4** Given 識別子の照合の部品 / When 任意の文字列（引用符・`;`・改行を含む）を与える性質ベースのテスト（jqwik）を流す / Then DSL に無い名前は必ず拒否され、通った名前は DSL の名前と一致する。失敗時の乱数の種を記録する（TP。Q）
- **AC3.6.5** Given 3種類の DB の境界の値（`BIGINT` の上限 `9223372036854775807` と下限、`DECIMAL(38,10)` の桁の多い値、NULL） / When 一覧・詳細で見る、作成・更新で入れて保存する / Then 値は1桁も変わらずに出て、保存した値を別の接続で読み直しても同じ（JavaScript の数の精度に頼らず文字で受け渡す）（TP・team.md の Code Style。V・Q）
- **AC3.6.6** Given 一覧・詳細・作成・更新・削除の要求1件 / When 対象DB の接続（読み取り・書き込み）と内部DB の接続の数を、既存の `NavigationConnectionUsageIT` と同じ形の結合テストで数える / Then 設計で決めた数と一致する（数は NFR 要件・NFR 設計の段で決める）（TP。V・Q）
- **AC3.6.7** Given 読み取りのアカウントと書き込みのアカウント / When 一覧・詳細と、作成・更新・削除を行う / Then 読み取りの API は読み取りのアカウントの接続だけを使い、書き込みの API は書き込みのアカウントの接続を使う。対象DB を待つあいだ内部DB の接続を持たない。見本の対象DB の書き込みのアカウントで表を作る・消す操作（DDL）を流すと DB が拒む（NFR4.3・team.md の Code Style。Q）
- **AC3.6.8** Given 外部へ送る設定を有効にした結合テストと、TRACE を有効にした `*SecretLeakIT` / When 一覧・詳細・作成・更新・削除を行う / Then トレースの属性（道・問い合わせの文など）とアプリのログに、主キーの値・検索の値・行の値・対象DB の接続情報が含まれない（NFR4.2・PM。Q）
- **AC3.6.9** Given 入力の誤り（400）・「同じ値がある」・行が無い（404）の誤りの応答 / When 応答を見る / Then カラムの名前と `code` だけが入り、入力した値・主キーの値は `detail`・`instance`・カラムごとの誤りの項目のどれにも含まれない（PM。Q）

### US4.1 読み上げで行の操作と画面の部品が分かる 〔Must〕

P1 業務データを見る人（読み上げを使う人）として、一覧の行の「操作」のメニューの名前に見えている文字が含まれ、画面のどこにもアクセシビリティの違反が無いようにしてほしい。それは、読み上げや音声の操作で、見えているものと同じ名前で操作するためだ。

出典: FR14.1〜FR14.6、NFR5、PM、team.md（Way of Working・Testing Posture の axe-core の決まり）、SL、D・V・Q

固定先の更新（AC4.1.2）は利用者の操作ではないため、Delivery Planning でこのストーリーの中の別の Bolt に分けてよい（V）。

- **AC4.1.2（直した）** Given make-you-chic-ui の固定先を `b0a1e79` に上げる / When 固定先を更新する / Then 承認を得た専用のコミットで行い、前後のコミットハッシュ・上流の `main` から辿れること・vendor の lockfile の差（増えた・変わったパッケージと `hasInstallScript` の増減）が記録に残る。`hasInstallScript` の付いた項目が増えたときは、取り込む前に依頼者に諮る（Q）
- **AC4.1.3（直した）** Given axe-core を 4.14 以降に上げ、`.github/dependabot.yml` の `ignore` を外した / When E2E の全件と画面の部品のテスト（vitest-axe）を流す / Then E2E の全件が通り、axe の違反が 0 件である（規則・要素を外さない）。件数を記録する。axe-core の版が lockfile で1つにそろっている（Q）
- **AC4.1.4** Given 表示の設定の画面（E2E 080）で出た違反 / When axe の違反の要素を確かめる / Then どの部品の違反かが記録に残る。make-you-chic-ui の部品の違反なら依頼（5）を出し、取り込んでから axe-core を上げる
- **AC4.1.5** Given 上流の対応が Build and Test までに間に合わない / When 依頼者に諮る / Then axe-core の引き上げだけを持ち越すかが依頼者の決定として記録され、持ち越すときは `ignore` の理由と外す時期が書き直される
- **AC4.1.6** Given 業務データの一覧・詳細・作成・更新の画面、ブランドカラーとテーマのすべての組 / When 実際のブラウザの axe（E2E）を流す / Then 違反が 0 件。誤りを出した状態・長い表示名・100 カラムの表・NULL の行・展開した検索の項目・開いた行の操作のメニューを含める（Playwright のアクセシビリティの検査のため、E2E の流れの本数には数えない）（PM の学び。SL。D・Q）

### 後の段で決める点（この段の受け入れ基準が「機能設計で決める」「画面の段で決める」などと書いたもの）

- **機能設計（Functional Design）**: 拒否の理由ごとの `code` の名前（409 の行の操作ができない、行を1つに決められない、書き込みができない、接続できない・時間切れなど）。判定の順の④（主キーとビューの決まりと補助権限・FULL の不足）と⑦の中の前後。書き込みの接続の設定が無いときの拒否の状態コードと、監査に残すか。監査の欄の置き方（欄を足すか中身の JSON か）と、中身の上限と切り詰めの形。外部キーの違反のカラムの決め方の細部。何も変えない更新の保存の扱い（AC2.2.9）。ページの番号の始まり（0 か 1）。行を見分ける代表のカラム（AC1.4.7・AC2.3.1・AC4.1.1）。秒未満の値を持つ日時の `DATETIME`・`TIME` の書式での出し方（Q の Q-G の後半。決まっていない）。主キーの値を道（URL）に置くかと、トレースの属性の道の伏せ方（要件の未解決の点）。
- **画面の段（Refined Mockups）**: NULL と空の文字列の出し分けの形（AC1.5.5）、一覧の省略の出し方（AC1.5.6）、作業ロールの切り替えで 403 になったときの入力の値の扱い（AC2.2.13）、理由と誤りの文言（AC3.2.5・AC3.3.7）、make-you-chic-ui に足りない点（表の並べ替え・ページ送りの英語の文言・行の操作・Topbar の利用者のメニュー）の一覧と依頼（5）（team.md の Way of Working。AC1.3.13・AC4.1.4）。
- **NFR 要件（NFR Requirements）**: 応答時間の測り方と全体の件数の数え方（AC1.3.7）、対象DB から読む行の数の上限（AC1.3.16）、`pattern` の時間の上限と余裕（AC2.4.5）、1要求の接続の数（AC3.6.6）、負荷の試験の対象DB の行の数。
- **コード生成の計画（Code Generation）**: 業務データの機能が解決の口を使い、対象DB に書き込むため、`RoleBoundaryArchitectureTest` と `TargetDbBoundaryArchitectureTest` に許す相手を足すか、足さない形にするか（緩めるときは計画に明記して依頼者の承認を得る。team.md の Code Style。V）。業務データの代表の E2E 1本（TP）。
- **Observability Setup**: 業務データの API で 403 が増えたときの警報 `ms-forbidden` のしきい値（NFR8）。
