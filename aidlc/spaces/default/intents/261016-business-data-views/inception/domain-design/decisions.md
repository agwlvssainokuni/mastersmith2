# 決定の記録（ADR）— business-data-views

出典の表記は `components.md` と同じ。日付はすべて 2026-10-18。状態はすべて Accepted（依頼者の答え DQ1〜DQ4 とストーリーの決定に基づく）。

## ADR-001: 業務データの機能を新しい `businessdata` に置き、行の SQL をその中の1つの部品に閉じる

- **Context** — 業務データの一覧・詳細・作成・更新・削除には、適用中の DSL（見せ方・主キー・ビュー・検証）、作業ロールの権限、対象DB の接続、監査を組み合わせる必要がある。今の `targetdb` は「読み取り専用・スキーマだけ」に固定され、境界テストが書き込み・`JdbcTemplate`・DSL への依存・web の層を止めている（K-49）。team.md は、業務データの機能を新しいパッケージに置き、既存の境界テストは緩めずに足す形を先に検討すること、SQL を組み立てて実行する部品を1つに閉じて ArchUnit で `prepareStatement`・`createStatement` を呼んでよい場所をその部品だけに絞ることを求める。
- **Decision** — 新しい機能 `businessdata` を作り、API（web）・業務処理（service）・出し分けの純粋な関数と型（domain）・行の SQL を組み立てて実行する唯一の部品 RowSqlExecutor と DB の種類ごとの方言（repository）を置く。対象DB の接続（読み取りと書き込み）は `targetdb` が持ち、`targetdb.service` の口で渡す（ADR-008）。`businessdata` は自分の境界テストを持ち、依存してよい相手（`targetdb.service`・`targetdb.domain`・`role.service`・`role.domain`・`dsl` の提供口・`common`）を書く。
- **Consequences**
  - 良い点: `targetdb` の境界テストを緩めずに済む。識別子の照合（DSL の名前と照らす）と SQL の組み立てが同じ機能の中にあり、照合を通らない名前が SQL の部品に届く口ができない。SpotBugs の `SQL_` の除外を RowSqlExecutor のクラス・メソッド・パターン名に絞れる。
  - 悪い点: `businessdata` は依存の多い機能になる（3つの既存の機能に依存する）。3種類の DB の方言がこの機能に集まる。
  - そのほか: RowSqlExecutor の中の方言の分け方と、問い合わせの時間の上限・読む行の数の上限は機能設計と NFR の段で決める。
- **Alternatives Rejected**
  - `targetdb` に行の読み書きを足す（DQ1 の B）: 「書き込みをしない」境界テストを緩めることになり、スキーマの読み取りだけを持つ部品の性質と、DSL を知らない決まりが崩れる。
  - 行の SQL と接続を持つ `rowstore` を別の機能にする（DQ1 の C）: SQL の部品が DSL を知らないため、照合を済ませた名前を外から受け取る口が要り、照合を通らない名前が届く経路ができる。部品と境界テストも1つ増える。

## ADR-002: 業務データの機能が `role` の解決の口に依存できるよう、`RoleBoundaryArchitectureTest` に依存してよい相手を足す

- **Context** — `role` の境界テストは、`role` に依存してよい外の機能を `audit`（`role.domain`）と `navigation`（`role.service`・`role.domain`）に限っている（DQ の確かめた事実）。業務データの API は、要求ごとに作業ロールの実効の主権限と補助権限を解決の口で求める必要がある（FR2.1）。team.md は、既存の境界テストを緩めるときにコード生成の計画に明記して承認を得ることを求める。
- **Decision** — `businessdata` を、`role.service`（解決の口）と `role.domain`（権限の値の型）に依存してよい相手として `RoleBoundaryArchitectureTest` に足す（`role.store`・`role.repository`・`role.web` には依存させない）。この変更はコード生成の計画に明記して依頼者の承認を得る（DQ2: A）。
- **Consequences**
  - 良い点: 解決の口を1か所のまま使え、権限の解決の決まり（継承・既定値）が二重にならない。
  - 悪い点: `role` の境界テストを緩める変更が入る（依頼者の承認が要る）。`role` に依存する機能が3つになる。
  - そのほか: 1要求で解決の口を何回呼ぶか（テーブルとカラムの数だけ呼ぶか、まとめて求める口を足すか）は NFR 設計で接続の数とあわせて決める。
- **Alternatives Rejected**
  - `navigation` に業務データ向けの権限の口を足して通す（DQ2 の B）: `navigation` が業務データのための中継になり、変わる理由が増える。`businessdata` が `navigation` に依存する不自然な向きになる。
  - 解決の口の型を `common` に移す（DQ2 の C）: 既存の `navigation` の依存も移す変更になり、この Intent の範囲が広がる。

## ADR-003: 業務データの操作の監査は、今の出来事の仕組み（AuditEventListener の fallbackExecution）で書く

- **Context** — 今の監査は、各機能が出来事を出し、`audit` の `AuditEventListener` が内部DB の確定の後（無ければ `fallbackExecution`）に書く（K-54）。業務データの作成・更新・削除は対象DB の操作で、内部DB のトランザクションが無い。要件は、監査を対象DB の確定の後に書き、監査の書き込みの失敗では操作を失敗させないとする（FR12.3）。
- **Decision** — `businessdata` が、対象DB の確定（失敗なら巻き戻し）の後に業務データの出来事（型は `businessdata.domain`）を出し、`AuditEventListener` が `fallbackExecution` で自分の短いトランザクションで書く。`AuditEventType` に業務データの作成・更新・削除の種類を足す（名前は機能設計。32 文字以内の既存の決まり）。
- **Consequences**
  - 良い点: 既存の監査の仕組みと失敗の扱い（操作は成功のまま、ログに残す）をそのまま使える。`businessdata` が `audit` に依存しない（出来事の向き）。
  - 悪い点: 対象DB の確定と監査の書き込みの間でアプリが止まると、監査が残らない（今の仕組みと同じ危険）。
  - そのほか: 監査の行に主キーの値・スキーマ・テーブルを置く欄（欄を足すか中身の JSON か）と切り詰めの形は機能設計で決める。既存の `AuditSecretLeakIT` の列の一覧が変わりうる（前の Intent の学び）。
- **Alternatives Rejected**
  - `businessdata` が `audit` の記録の口を直接呼ぶ（DQ3 の B）: `businessdata` が `audit` に依存する向きになり、既存の機能と書き方が分かれる。

## ADR-004: 画面は今の `features/tables` を引き継いで広げ、共通の小さな部品を `src/shared/` に置く

- **Context** — テーブルを指すメニューの項目の移り先は `features/tables` の「準備中」の置き場で、道・今の項目・E2E がこの形に依る（K-52）。team.md は、画面を `features/tables` を置き換える1つの機能とし、テーブルへの道を作る関数は1か所のまま、共通の部品は `src/shared/` に置くことを求める。機能どうしは直接 import しない（ESLint）。
- **Decision** — `features/tables` を引き継ぎ（フォルダの名前は変えない）、一覧・詳細・作成・更新の画面と検索の領域を置く。NULL の表示・横のスクロールの枠・1ページの件数の選択・離れるときの確かめ・「操作: …」の名前の関数は `src/shared/` に置き、既存の管理の一覧（`useradmin`・`groupadmin`・`roleadmin`）もその関数を使う（DQ4: A）。
- **Consequences**
  - 良い点: メニューからの道の組み立てと E2E の道がそのまま使える。行の操作の名前の形が全画面でそろう。
  - 悪い点: フォルダの名前（tables）が中身（業務データ）より狭い。
- **Alternatives Rejected**
  - 新しい `features/businessdata` を作り `features/tables` を消す（DQ4 の B）: 道の組み立ての関数と E2E の書き換えが増え、この Intent の変更が広がる。

## ADR-005: 出すカラム・入力できるカラム・許す操作は、サーバーの1つの純粋な関数で求め、画面はその結果で入口を出す

- **Context** — カラムの出し分けと操作の可否は、主権限・補助権限・主キーの有無と可視性・ビュー・表示の設定・書き込みの接続の有無の組み合わせで決まる（FR2・FR9、SQ7、SM8、AC3.3.9）。画面で同じ判定をもう一度書くと食い違いうる。判定はサーバー側で行い、画面の出し分けを代わりにしない（PM の Mandated）。
- **Decision** — `businessdata.domain` に、権限と DSL の設定から「出すカラム（一覧・詳細）」「入力できるカラム（作成・更新）」「許す操作（作成・詳細・更新・削除）」を求める1つの純粋な関数を置く。API はその結果を応答に操作の可否として含め、画面はそれで入口と入力を出す。同じ関数で API の受け付け・拒否も判定する（AC3.1.9）。性質ベースのテスト（jqwik）を当てる（AC3.1.7・AC3.2.7）。
- **Consequences**
  - 良い点: 画面とサーバーの判定が食い違わない。判定の組み合わせを1か所で網羅して確かめられる。
  - 悪い点: 画面は入口を出すためにサーバーの応答を待つ（操作の可否が応答に乗るため、追加の要求は要らない）。
  - そのほか: fast-check の性質ベースのテストは、画面側に同じ判定の関数を置かないため、画面の出し分けの関数（応答の可否を入口に写す関数）に当てるかを機能設計で決める。
- **Alternatives Rejected**
  - 画面とサーバーの両方で判定する: 食い違いの危険があり、画面の判定は安全の守りにならない。
  - 画面が権限の値を受け取って自分で判定する: 権限の設定の中身（どのカラムが NONE か）を画面に渡すことになる。

## ADR-006: 判定の順と、主キー・ビューの決まりの拒否を 409 にすること（ストーリーの決定の記録）

- **Context** — 1つの要求が複数の拒否に当たるときの応答をそろえ、NONE のテーブルで行の有無を推測させないこと、主キーとビューの決まりの拒否を監査に残すこと（403 は残さない）を両立させる必要がある（SL・FR12.4）。
- **Decision** — 判定の順を 401 → 404（DSL が無い・DSL に無いスキーマかテーブル）→ 403 `ACCESS_DENIED`（テーブルが NONE）→ 409（主キーとビューの決まり）・403（補助権限や FULL の不足）→ 400（入力の誤り・書けないカラム）→ 404（行が無い）→ 業務の失敗（行が1つに決まらない・一意の重なり・DB が拒んだ保存・接続の失敗・時間切れ）とする。④と⑦の中の順と code の名前は機能設計で決める。
- **Consequences**
  - 良い点: 応答が一意に決まり、表のパラメーターのテストで確かめられる。NONE のテーブルでは行があっても無くても同じ 403 になる。
  - 悪い点: 要件の FR9 は拒否の状態コードを決めておらず、409 はストーリーの段の決定である（stories.md の「要件との差」）。
- **Alternatives Rejected**
  - 主キー・ビューの決まりの拒否を 403 に専用の code を付けて返す: 「403 は監査に残さない」と食い違う。

## ADR-007: 実現できるかの判断（Feasibility の段が無いため、この段で扱う）

- **Context** — classic の範囲で Feasibility の段が無い。`project.md` の学びにより、実現できるかの判断はドメイン設計で扱い ADR に記録する。業務データの機能は、3種類の対象DB で同じ振る舞いを求め、対象DB への書き込みが初めて入る（NFR3・K-49）。
- **Decision** — 次の点を、確かめる段と、だめだったときの切り替え先とともに受け入れる。

| 論点 | 見立て | 確かめる段 | だめだったときの切り替え先 |
|---|---|---|---|
| NULL の並びを3種類の DB でそろえる | PostgreSQL は `NULLS LAST`/`NULLS FIRST`、MySQL・MariaDB は `IS NULL` の並べ替えのキーを先に足せばそろう | 機能設計・コード生成（結合テスト AC1.3.9） | 並べ替えのキーの式で DB ごとに組み立てる（方言の部品の中） |
| 部分一致の `%`・`_`・`\` のエスケープ | `LIKE ... ESCAPE` を明示すれば3種類で同じになる見込み（MySQL・MariaDB の既定のエスケープと `NO_BACKSLASH_ESCAPES` の違いに注意） | コード生成（結合テスト AC1.2.4） | エスケープの文字を DB ごとに変える |
| 一意と外部キーの違反の見分け | SQLState（`23505`・`23503`・MySQL の `1062`・`1452` など）で見分けられる。違反したカラムは制約の名前とメタデータで決められるときだけ示す | 機能設計・コード生成（AC2.1.6・AC2.5.1） | フォーム全体の誤りとして出す（ストーリーの決定のとおり） |
| 時差つきの型を UTC に固定 | セッションのタイムゾーンを UTC にするか、JDBC の型（`OffsetDateTime`）で受け渡す | NFR 設計で捨ての試し、コード生成（AC1.5.7） | 時差つきの型を読み取りだけにする（M7 の B） |
| 全体の件数の問い合わせの重さ | 規模の上限（100 テーブル・100 カラム）の行の数次第。`COUNT(*)` は大きな表で遅くなりうる | NFR 要件（行の数と目標を決める）・NFR 設計（試し） | 件数を出す問い合わせに時間の上限を置き、超えたら「多数」と出す（要件の変更として依頼者に諮る） |
| `pattern` の照合の時間の上限 | Java の正規表現は時間の上限を持たないため、照合を別のスレッドか、文字の読み出しで打ち切る形が要る | NFR 設計で捨ての試し（AC2.4.5） | 照合の前に値の長さの上限を当てる |
| 2行以上に当たる更新・削除の巻き戻し | 更新の件数を見てトランザクションを巻き戻せば3種類で同じ | コード生成（AC3.2.6） | — |
| 書き込みと読み取りの接続を分ける | 見本の対象DB に書き込みのアカウントを足し、`.env` に書き込みの接続の項目を足す | Infrastructure Design・コード生成（AC3.6.7） | — |

- **Consequences**
  - 良い点: 実現の危険を、確かめる段と切り替え先とともに先に見える形にした。
  - 悪い点: 切り替え先のいくつか（件数の「多数」、時差つきの型の読み取りだけ）は振る舞いの変更で、依頼者の決定が要る。
- **Alternatives Rejected**
  - 実現の判断を後の段に任せて記録しない: 前の Intent までの学び（Feasibility を吸収したときはドメイン設計で扱う）に反する。

## ADR-008: 対象DB の書き込みの接続を `targetdb` に足し、対象DB 用のトランザクションで書く

- **Context** — team.md の Code Style と `project.md` の Mandated により、対象DB へ書き込むときは書き込みの接続と資格情報を読み取りと分けて `.env` だけから受け取り、書き込みのアカウントには DSL の対象のスキーマの行の操作だけを与える。対象DB 用に別のトランザクションの管理者を置き、内部DB の接続を持ったまま対象DB を待たない。
- **Decision** — `targetdb` に書き込みの接続の設定と DataSource を足し、読み取りの DataSource と並べて `targetdb.service` の口で渡す。`businessdata` は、書き込みの DataSource の上の対象DB 用のトランザクションの管理者で作成・更新・削除を行う（内部DB のトランザクションの外で）。書き込みの接続の設定が無いときは起動を続け、口は「設定が無い」と答える。
- **Consequences**
  - 良い点: 読み取りの接続の性質（読み取り専用・スキーマの読み取りの時間の上限）を変えずに済む。書き込みのアカウントの権限を絞れる。
  - 悪い点: 対象DB の接続のプールが2つになり、接続の数の見積もり（NFR）が増える。`.env.example`・見本の対象DB の初期化の SQL・README の手順を直す必要がある。
  - そのほか: 書き込みのプールの大きさと時間の上限は NFR 要件・NFR 設計で決める。
- **Alternatives Rejected**
  - 読み取りと同じ接続でアカウントの権限を広げる（Practices Discovery の Q5 の B）: 依頼者が選ばなかった。読み取りの経路でも書き込みができる状態になる。
