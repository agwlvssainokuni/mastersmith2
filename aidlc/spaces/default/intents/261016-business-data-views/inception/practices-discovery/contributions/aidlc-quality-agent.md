### 2. 抜けている論点（足す提案）

- **Q1 `./gradlew verify` の時間と資源の測り直し**: 業務データの結合テストが3種類の対象DB で増えると、`verify` の時間・colima の VM のメモリ・テストの JVM のヒープ（`integrationTest` の `maxHeapSize = "1536m"`）・CI の `timeout-minutes: 60` に響きうる。今の基準の「3種類を毎回 verify で」は Intent 260923-dsl-schema-loader の実測が前提のため、業務データの結合テストを足した Bolt の後と Build and Test で、`verify` の時間（clean を付けて）とテストの JVM のヒープの最大を測って記録し、前の値から大きく伸びたら（目安は依頼者が決める）分け方を諮る、を決まりにすることを推す。推奨の答え: 測って記録し、CI の上限 60 分の 7 割（約 42 分）を超えたら諮る。
- **Q2 負荷の試験の見本のデータ**: Performance Validation が EXECUTE で、`docker/perf/compose.yaml` に3種類の対象DB があるが、一覧のページ送り・並べ替えの性能は行の数で大きく変わる。使い捨ての環境の対象DB に入れる行の数・作り方（台本で作る、決めた種で作る）と、k6 の場面の setup が前の場面の状態に頼らないこと（`project.md` の 2026-10-15 の学び）を、チームの進め方として先に決めておくことを推す。推奨の答え: 行は perf の台本（`perf/` の下）で決めた種から作り、行の数は NFR 要件の段で決める。
- **Q3 フロントエンドのカバレッジの下限の当て方**: `frontend/vitest.config.ts` の `thresholds` は全体の lines 80・branches 70 だけで、機能ごとの下限が無い。バックエンドはパッケージごとの下限があるため、新しい業務データの画面が低くても全体の合計に埋もれうる。今の基準を変えるかを問う。推奨の答え: 今の形のまま（全体の下限）とし、新しい機能のフォルダの値を Build and Test で記録する（下限を増やすと既存の機能が下回りうるため、決めるなら実測の後）。
- **Q4 対象DB の結合テストのデータの片付け**: 業務データの読み取りのテストでも表を作る（DDL）ため、今の基準の「テストのクラスごとに名前の重ならないスキーマを作り終わったら消す」が当たる。失敗で途中で止まったときにスキーマが残り、次の実行の行の数の確かめを崩さないよう、作る名前に実行ごとの一意の値を入れ、始める前に前の残りに頼らないことを確かめる。これは今の基準の読み方の確認で足りるため、質問にせず「決まっていること」として冒頭に書くことを推す。
