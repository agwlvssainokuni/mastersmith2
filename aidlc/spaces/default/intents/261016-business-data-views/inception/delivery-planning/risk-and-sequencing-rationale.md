# 順の理由と危険 — business-data-views

この文書は、Bolt（1つ以上の作る単位を設計から統合まで通して動くものにする1回の作り込み）の順を、なぜそう決めたかを書く。

## 使った考え方

- **危ないものから先に**（risk-first。Boehm の螺旋のモデルの考え方: 不確かさの大きいものを先に作り、後の作業が頼る前に判断を確かめる）を使った（DQ1: A）。
- **WSJF**（Weighted Shortest Job First: 価値と急ぎと危険の減り方の和を、作業の大きさで割った点数の高いものから作る型。Reinertsen・SAFe）は使わない（DQ2: A）。単位の依存がほぼ一本道で（U2 → U1、U3 → U1・U2・U4）、順の選択肢が少なく、点数を付けても順が変わらないため。前の Intent と同じ判断。
- **walking skeleton**（最初に全体を一通り動かす薄い作り込みを、単独で承認してから進める型。Cockburn）は使わない（team.md の Walking Skeleton。アプリの骨格は既にある）。

## 順と、それぞれの理由

| 順 | Bolt | 理由 |
|---|---|---|
| 1 | B1 U5 | CI を安定させる。不安定なテスト2件（RoleConcurrencyIT の #7・AdminForbiddenProvider.test.tsx）は、後のすべての Bolt の統合の後の CI で再び落ちうる。小さく、ほかの単位に依存しない |
| 2 | B2 U1 | いちばん不確かな ADR-007（3種類の対象DB の方言・行の SQL の部品）を最初に確かめる。U2・U3 が U1 の部品と API に依存する（DQ6 の A） |
| 3 | B3 U4 前半 | axe-core 4.14 で出る違反の範囲を、画面を作る前に確かめる。違反が make-you-chic-ui の部品なら依頼（5）を早く確定でき、上流の対応の時間を最も長くとれる。U3 が U4 の固定先と名前の関数に依存する（DQ6 の B） |
| 4 | B4 U2 | U1 の部品の上に書き込みを足す。書き込みの接続・トランザクション・監査の順（DQ6 の C）を、画面より先にサーバー側で確かめる |
| 5 | B5 U3 前半 | 読み取りの API（B2）と固定先（B3）がそろった後に、一覧・詳細の画面を作る（DQ6 の D） |
| 6 | B6 U3 後半 | 書き込みの API（B4）の後に、作成・更新・削除の画面と業務データの代表の E2E を作る |
| 7 | B7 U4 後半 | axe-core の引き上げの合格（E2E 全件・違反 0 件）は、B5・B6 の新しい画面を含めないと確かめられない（Units Generation のレビューの R-01）。依頼（5）の取り込みを最後に置き、上流の時間を最も長くとる |

## 単位の依存の順との違い

単位の依存（`unit-of-work-dependency.md`）の上では、U1・U4・U5 はどれも先に作れ、U2 は U1 の後、U3 は U1・U2・U4 の後である。この計画の順（U5 → U1 → U4 前半 → U2 → U3 前半 → U3 後半 → U4 後半）は依存を守っている。依存の順から外れているのは、U4 を前半と後半に分け、後半を U3 の後に置いたことだけで、理由は上の B7 の行（axe-core の引き上げは新しい画面を含めて確かめる必要がある）。U4 の後半は U3 に依存しないが、合格の条件が U3 の画面を含むため、後に置く。

## 危険の一覧

| 危険 | 起こりやすさ | 影響 | 減らし方 |
|---|---|---|---|
| 3種類の対象DB で方言（NULL の並び・エスケープ・時差つきの型・違反の見分け）が食い違う | 中 | 高 | B2 で最初に結合テストで確かめる。ADR-007 の切り替え先（DB ごとの式・フォーム全体の誤り・時差つきの型を読み取りだけ）を用意 |
| axe-core 4.14 で既存の画面の違反が多い（前の Intent では E2E が 100 件落ちた） | 高 | 中 | B3 で範囲を先に確かめる。部品の違反は依頼（5）。間に合わなければ引き上げだけを持ち越すかを諮る（FR14.6） |
| make-you-chic-ui の依頼（5）の対応が間に合わない | 中 | 中 | frontend の側の手当て（枠・Select）を先に作り、取り込めたら置き換える |
| 書き込みの接続・2つ目のトランザクションの管理者が既存の内部DB の注入と衝突する（Domain Design のレビュー R-01） | 中 | 高 | 機能設計・NFR 設計で作り方（既定の候補にしない）を決め、B4 の結合テストで確かめる |
| 全体の件数の問い合わせが大きな表で遅い | 中 | 中 | NFR 要件で行の数と目標を決め、NFR 設計の試しで確かめる（ADR-007） |
| `role` と `audit` の境界テストを変える承認が要る | 高（必ず要る） | 低 | B2・B4 のコード生成の計画に明記して承認を得る（ADR-002・C5） |
| 画面の量（S1〜S6、共通の部品、一覧の状態、E2E）が大きい | 中 | 中 | U3 を B5・B6 の2つに分ける |
| `verify` と CI の時間が増える（3種類の対象DB の結合テストが増える） | 中 | 中 | team.md のとおり Bolt の後と Build and Test で時間を記録し、約 42 分を超えたら諮る |
