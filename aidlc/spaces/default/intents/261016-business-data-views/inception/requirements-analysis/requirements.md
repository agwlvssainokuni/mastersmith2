# 要件（261016-business-data-views）

依頼: 「業務データの一覧・詳細の画面（J・K）を作る。これまでに作ったロールの主権限・補助権限を、業務データの出し分けと操作の可否（主キーの有無による操作の可否を含む）に当て、テーブルを指すメニューの項目から一覧・詳細へ移れるようにする。」と、前の Intent 261015-deps-ui-carryover からの持ち越し（make-you-chic-ui の固定先、axe-core 4.14、不安定なテスト2件、`dslMixed` の `memory.peak`） [desc]
範囲: classic（深さ Standard、Test Strategy Standard） [scope]

## Intent の分析

ここまでの Intent で、認証・利用者の管理・DSL の読み込みと適用・ロールの主権限と補助権限・N 階層のメニューを作った。ただし、マスタ管理の本体である業務データの画面はまだ無い。テーブルを指すメニューの項目の移り先は「準備中」の置き場で（所見 K-52）、対象DB の行を読む口も書く口も無い（K-49）。今回は参考資料の要件のドラフトの J（検索＋一覧）と K（詳細・編集）を、他テーブル参照の選択肢と参照ピッカーを除いて作る [desc] [Q1]。

- **目的1（業務データを見られるようにする）**: 利用者が、メニューから対象DB のテーブルを選び、行を検索・一覧・詳細で見られるようにする。見え方は適用中の DSL の設定（列・並び・検索の項目・表示名・書式）に従う（K-51）。
- **目的2（業務データを直せるようにする）**: 利用者が、行を作成・更新・削除できるようにする。入力は DSL のフォーム部品と検証に従う [Q1]。
- **目的3（ロールの権限を業務データに当てる）**: 前の Intent で作った実効の権限の解決の口（261004-role-menu の FR8.1、K-50）を使い、作業ロールの主権限（NONE・READ・FULL）と補助権限（CREATE・DELETE）で、カラムの出し分けと行の操作の可否を API ごとにサーバー側で決める。主キーの有無による操作の可否は、参考資料の 5.5 の表に従う [desc]。
- **目的4（持ち越しを閉じる）**: make-you-chic-ui の固定先を `b0a1e79` に上げ、一覧の行の「操作」のトリガーの名前を直し、見送っていた axe-core 4.14 以降を取り込む。あわせて、不安定なテスト2件を直し、`dslMixed` の `memory.peak` を測り直す（K-55〜K-60） [desc]。

管理者の印 `users.admin_flag` を縮める段（F2）は、この Intent に入れない。管理の可否をロールで表す形を先に決める必要があり（K-53）、業務データの機能とは独立に大きいため、後の Intent に回す [Q2]。

## 機能の要件

### FR1 メニューから業務データの一覧へ（部品 `frontend-feature-tables`・`frontend-registry`・`navigation`、所見 K-52）

- **FR1.1** テーブルを指すメニューの項目を選ぶと、そのテーブルの業務データの一覧の画面へ移る。今の「準備中」の置き場を、一覧の画面で置き換える [desc]。
- **FR1.2** 一覧の画面のテーブルは、移り先の道で指す。サイドバーの今の項目（`aria-current`）の表示は、今の置き場と同じ形で保つ。
- **FR1.3** 作業ロールでテーブルの主権限が NONE のテーブルは、今と同じくメニューに出さない。道を直接開いたときはサーバー側で拒否し、画面は 403 の表示にする（FR13） [memory:M3]。

### FR2 権限の当て方（部品 `role`・`navigation`・業務データの機能、所見 K-50）

- **FR2.1** 業務データの API はすべて、要求ごとに、その利用者の今の作業ロールの実効の主権限（スキーマ → テーブル → カラム、既定 NONE）と補助権限 CREATE・DELETE（スキーマ → テーブル、既定 不可）を、前の Intent の解決の口で求めて判定する。画面の出し分けを判定の代わりにしない [desc] [memory:M3]。
- **FR2.2** 主権限が NONE のカラムは、一覧の列・検索の項目・詳細・作成と更新の入力から除き、API の応答にも含めない。READ のカラムは見せるだけで、作成・更新の入力では変えられない。FULL のカラムは作成・更新で入力できる（参考資料の 5.4） [memory:M3]。
- **FR2.2a** 主権限が READ 以上でも、DSL の表示の設定で隠すカラムは応答に含めない。一覧の応答には `list.visible` のカラムだけ、詳細の応答には `detail.visible` のカラムだけを含める。ただし、詳細・更新・削除で行を指すために要る主キーのカラムは、READ 以上なら `list.visible` で隠す設定でも一覧の応答に含める（画面には出さない） [F4]。
- **FR2.3** 行の一覧・検索と詳細には、テーブルの主権限が READ 以上であることを要る。行の作成には補助権限 CREATE、削除には補助権限 DELETE を要る。更新には、変えるカラムが FULL であることを要る。
- **FR2.4** 要求の本文に、利用者が変えられないカラム（NONE・READ）の値や、DSL に無いカラムを入れても、反映せずに拒否する（一括代入の防止）。
- **FR2.5** 作業ロールを切り替えた直後・ロールの割り当てや権限の設定を変えた直後の次の要求で、新しい権限で判定する（画面が持つ古い権限に頼らない） [memory:M1]。
- **FR2.6** 管理者の印を持つ利用者でも、業務データへの入り方は作業ロールの権限で決まる（参考資料の 5.7）。

### FR3 一覧と検索（所見 K-51）

- **FR3.1** 一覧の列は、DSL の一覧の設定で見せるカラム（`list.visible`）を `list.order` の順に並べ、列の幅は `list.width` に従う。主権限 NONE のカラムは除く（FR2.2）。
- **FR3.2** 検索の項目は、DSL の検索の設定で `search.enabled` のカラムとし、演算子は `search.operator` の `EQUALS`（完全一致）・`CONTAINS`（部分一致）・`RANGE`（範囲。下限・上限のどちらか一方でもよい）・`CHOICE`（選択肢）のすべてを扱う。条件はすべて AND で組む [Q3]。
- **FR3.3** 検索の項目の既定の値（`search.defaultValue`）と、折りたたんで始めるか（`search.collapsed`）は DSL に従う [Q3]。
- **FR3.4** 部分一致の大文字と小文字の扱いは、対象DB の照合順序に任せる（3種類の DB でそろえない）。検索の値の中の `%`・`_` は文字として扱い、ワイルドカードにしない [Q3] [memory:M1]。
- **FR3.5** 範囲・選択肢の値は、カラムの型として読めない値を検証の誤り（FR10）として返す。
- **FR3.6** 検索の `CHOICE` が、他テーブル参照の選択肢（`REFERENCE`）か参照ピッカー（`LOOKUP`）を持つカラムに付いているときは、選択肢を出さず完全一致（`EQUALS`）に読み替える（選択肢の取得は後の Intent） [F3]。

### FR4 ページ送りと並べ替え

- **FR4.1** 一覧はページに分けて出す。1ページの件数は利用者が 20・50・100 から選べ、既定は 20 とする。それ以外の件数は受け付けない [Q4]。
- **FR4.2** 検索の条件に合う全体の件数を出す [Q4]。
- **FR4.3** 並べ替えは、DSL で `list.sortable` のカラムのうち1つを選び、昇順・降順を切り替えられる。既定は `list.defaultSort`、無ければ主キーの順（主キーの無いテーブルとビューは順を約束しない） [Q4]。並べ替えに主権限 NONE のカラムと、`sortable` でないカラムは選べない。
- **FR4.4** 同じ値の行の順を安定させるため、主キーのあるテーブルでは、並べ替えのカラムの後に主キーの順を足す。

### FR5 詳細

- **FR5.1** 一覧の行から、その行の詳細の画面へ移れる。詳細は、DSL の詳細の設定で見せるカラム（`detail.visible`）のうち、主権限が READ 以上のものを出す [desc]。
- **FR5.2** 詳細の行は主キーの値で指す。複合の主キーと、記号・空白・非 ASCII の文字を含む値も扱う。
- **FR5.3** 詳細へ移れるかは、主キーの有無による操作の可否（FR9）に従う。移れない行は、一覧に詳細への入口を出さない。

### FR6 作成

- **FR6.1** 補助権限 CREATE がある利用者は、行を作成できる。入力は FULL のカラムだけで、DSL のフォーム部品（`lookup` を除く 10 種: `text`・`textarea`・`checkbox`・`switch`・`radio`・`select`・`date`・`datetime`・`number`・`password`）に従う [Q1]。
- **FR6.2** `select`・`radio` の選択肢は、DSL の固定の選択肢（`FIXED`）だけを扱う。他テーブル参照の選択肢（`REFERENCE`）と参照ピッカー（`lookup`・`LOOKUP`）は後の Intent に回す。それらを持つカラムは、作成・更新では文字の入力（`text`）として扱う [Q1] [F3]。
- **FR6.2a** 文字の入力にしたカラムに外部キーの参照先に無い値を入れ、DB が外部キーの制約で拒んだときは、一般の保存の失敗ではなく「参照先に無い値」の誤りとして、そのカラムを示して返す（FR7・FR8 の保存でも同じ） [F3]。
- **FR6.3** 作成は、主キーの無いテーブルでも補助権限 CREATE に従って行える。主キーのカラムが NONE の行の作成も CREATE に従う（参考資料の 5.5）。ビューでは作成しない（FR9.2）。
- **FR6.4** 入力しないカラム（NONE・READ と、入力を空にした FULL）は、対象DB の既定値に任せる。既定値が無く NOT NULL のカラムで DB が拒んだときは、保存の失敗として返す [assumption]。
- **FR6.5** 作成に成功したら、その行の詳細へ移る（詳細へ移れない行は一覧へ戻る）。

### FR7 更新

- **FR7.1** 詳細へ移れる行で、FULL のカラムが1つ以上ある利用者は、その行を更新できる。更新の画面では、FULL のカラムを入力でき、READ のカラムを読み取りだけで出す（参考資料の 5.4） [desc]。
- **FR7.2** 更新は主キーの値で行を指して行う。同じ行を2人が同時に更新したときは、後から保存した人の値で上書きする（読んだときの値と照らさない） [Q6]。
- **FR7.3** 主キーのカラムの値は更新で変えない。
- **FR7.4** 更新しようとした行が無いとき（ほかの人が先に削除したなど）は 404 を返す（FR13）。

### FR8 削除

- **FR8.1** 詳細へ移れる行で、補助権限 DELETE がある利用者は、その行を削除できる。削除の前に確かめの表示を出す（既存の取り消しにくい操作と同じ形） [desc]。
- **FR8.2** 削除は主キーの値で行を指して行う。行が無いときは 404 を返す。対象DB の外部キーなどで拒まれたときは、保存の失敗として返す。

### FR9 主キーとビューによる操作の可否（参考資料の 5.5）

- **FR9.1** 操作の可否は次の表に従い、サーバー側で拒否する（画面で操作を隠すことを代わりにしない） [desc] [memory:M3]。

| テーブルの種類 | 一覧・検索 | 作成 | 詳細 | 更新 | 削除 |
|---|---|---|---|---|---|
| 主キーなし | 行う | CREATE に従う | 行わない | 行わない | 行わない |
| 主キーあり、すべての主キーのカラムが READ 以上 | 行う | CREATE に従う | 行う | FULL のカラムがあれば行う | DELETE に従う |
| 主キーあり、いずれかの主キーのカラムが NONE | 行う | CREATE に従う | 行わない | 行わない | 行わない |
| ビュー | 行う | 行わない | 主キーの設定があり、すべての主キーのカラムが READ 以上なら行う | 行わない | 行わない |

- **FR9.2** ビューは読み取りだけとし、権限にかかわらず作成・更新・削除をしない [Q7]。
- **FR9.3** 画面は、行える操作だけの入口（作成・更新・削除のボタン、詳細への入口）を出す。行えるかは、サーバーが返す操作の可否で決める。

### FR10 入力の検証（参考資料の 2.7）

- **FR10.1** 作成・更新の入力に、DSL の検証（`required`・長さ・範囲・`pattern`）と、DB の型から決まるもの（NOT NULL・文字の長さ・数の桁）を、画面とサーバーの両方で当てる。サーバー側を正とし、画面の検証をサーバー側の検証の代わりにしない [Q9]。
- **FR10.2** 一意（`unique`）は、保存の前に対象DB に問い合わせて、同じ値のほかの行が無いかを確かめる（DB に一意の制約が無いカラムも）。あわせて、保存のときの DB の一意の制約の違反も、同じ「同じ値がある」の誤りとして返す [Q9] [F1]。
- **FR10.3** DB に一意の制約が無いカラムで、2人がほぼ同時に同じ値で作成・更新すると、どちらも事前の確かめを通り、重なった値が入りうる。これは防げないものとして既知の制約にする（制約に書く） [F1]。
- **FR10.4** `pattern` の照合には時間の上限を置き、上限を超えたら検証の誤りとして返す（K-51）。
- **FR10.5** 検証の誤りのメッセージは日本語と英語の両方を用意し、画面の言語で出す。誤りはカラムごとに返し、画面は該当の入力に出す。

### FR11 値の表示（参考資料の 2.9、所見 K-51）

- **FR11.1** テーブル・カラムの表示名は、DSL の表示名（ja・en）を画面の言語で出す。
- **FR11.2** DSL の一覧の書式は、画面の言語に合わせた決まった形で出す: `DATE` は `2026-10-18`、`DATETIME` は `2026-10-18 09:30:00`、`TIME` は `09:30:00`、`NUMBER_GROUPED` は3桁区切り、`BOOLEAN_YES_NO` は「はい／いいえ」と `Yes`／`No` [Q8]。
- **FR11.3** 日時はタイムゾーンを足さず、DB の値のまま出す [Q8]。
- **FR11.4** 書式の無いカラムは、値をそのまま文字として出す。値の中の記号（`<`・`>`・`&`・`"`・`'`）も文字として出し、HTML として描かない [Q8] [memory:M1]。
- **FR11.5** 空の値（NULL）は、空の文字列と見分けがつく形で出す。

### FR12 業務データの操作の監査（所見 K-54）

- **FR12.1** 作成・更新・削除の成功と失敗を監査に残す。残す中身は、操作した人・作業ロール・スキーマ・テーブル・操作の種類・結果・行の主キーの値（主キーの無いテーブルの作成では無し）とし、失敗には理由（code）を足す [Q5] [F2]。
- **FR12.2** 更新の前後の値と、主キー以外のカラムの値は監査に残さない。一覧・詳細の読み取りは監査に残さない [Q5]。
- **FR12.3** 監査は対象DB の確定の後に、内部DB に書く。監査の書き込みに失敗しても、操作は成功のままとし、失敗をアプリのログに残す（今の決まりと同じ）。そのログには、主キーの値と行の値を含めない [Q5] [memory:M2] [memory:M3]。
- **FR12.4** FR12.1 の「失敗」は、業務の理由で拒否した作成・更新・削除とする: 主キー・ビューの決まり（FR9）による拒否、一意の重なり（FR10.2）、行が無い（FR7.4・FR8.2）、DB が拒んだ保存の失敗（外部キー・NOT NULL など、FR6.2a・FR6.4）。権限の不足（403）と入力の検証の誤り（400）は監査に残さない（今の管理の操作と同じ扱い） [F2]。

### FR13 応答と誤り

- **FR13.1** 適用中の DSL に無いテーブルと、主キーで指した行が無いときは 404、DSL にあるが作業ロールのテーブルの主権限が NONE のときは 403（code `ACCESS_DENIED`）を返す（今の置き場の API と同じ） [Q10]。
- **FR13.2** DSL が適用されていないときは、メニューにテーブルの項目が出ない今の扱いのまま、業務データの API は 404 を返す [F5]。
- **FR13.3** 対象DB に接続できない・時間内に答えないときは、業務データの機能の誤りとして返し、JDBC の例外のメッセージを応答とログに含めない [memory:M3]。
- **FR13.4** 誤りは Problem Details に安定した `code` を足した形で返す。業務データの code は機能の `XxxProblemTypes` に置く [memory:M2]。

### FR14 make-you-chic-ui と axe-core の持ち越し（部品 `make-you-chic-ui`・`frontend-e2e`・`build-and-verify`、所見 K-55・K-56・K-60）

- **FR14.1** make-you-chic-ui の固定先を `a9309c4` から `b0a1e79` に上げる。固定先の更新は承認を得た専用のコミットで行い、前後のコミットハッシュと、上流の `main` から辿れること、vendor の lockfile の差を記録する [desc] [memory:M3] [memory:M4]。
- **FR14.2** 一覧の行の「操作」のトリガーの名前を、見える文字を含む形に直す（利用者・グループ・ロールの管理の一覧と、今回の業務データの一覧） [desc]。
- **FR14.3** 見送っていた axe-core 4.14 以降を取り込み、`.github/dependabot.yml` の `ignore` を外す。上げる前に違反をすべて直し、検査の規則を外して違反を通さない [desc] [memory:M3]。
- **FR14.3a** 合格は、axe-core を上げた状態で E2E の全件が通り、E2E と画面の部品のテスト（vitest-axe）の axe の違反が 0 件であること（規則・要素を外さない）。件数を記録する [Q-R02] [memory:M1]。
- **FR14.4** 表示の設定の画面（E2E 080）で出た違反が、どの部品のものか（Topbar の利用者のメニューのトリガーなど）を axe の違反の要素で確かめて記録する [desc]。
- **FR14.5** make-you-chic-ui の部品の違反が `b0a1e79` で直らないときは、make-you-chic-ui への依頼（5）を出し、取り込んでから axe-core を上げる。業務データの画面に要る部品の足りない点（表の並べ替え・ページ送りの英語の文言・行の操作など）も、同じ依頼にまとめる [memory:M4]。
- **FR14.6** 上流の対応が Intent の最後（Build and Test）までに間に合わないときは、axe-core の引き上げ（FR14.3）だけを次の Intent へ持ち越すかを依頼者に諮る。持ち越すときは、`ignore` の理由と外す時期を書き直す [Q-R02]。

### FR15 不安定なテスト2件の直し（所見 K-57・K-58）

- **FR15.1** `RoleConcurrencyIT` の #7（監査の行の ID の順に頼る）と `AdminForbiddenProvider.test.tsx` の1件（効果の回数を効果が済む前に写しうる）を直す [desc]。

### FR16 `dslMixed` の `memory.peak` の測り直し（所見 K-59）

- **FR16.1** 物差しは `memory.peak`（線は上限の 90% 未満）のまま変えない [Q11]。
- **FR16.2** `dslMixed` の間の `memory.stat` の `anon` の最大も並べて測り、記録する [Q11]。
- **FR16.3** ページキャッシュを減らす手（H2 のファイルの読み書きの見直しなど）を試す。コンテナの上限（`MASTERSMITH_CONTAINER_MEMORY` の 2g）を上げて割合を下げる手は使わない。それでも線を超えたら、内訳とともに記録して依頼者に諮る [Q11] [Q-R01]。
- **FR16.4** 合格（Met）は、コンテナの上限 2g のまま、`dslMixed` の `memory.peak` が上限の 90% 未満であること。90% 以上は Not Met とする [Q-R01]。

## 非機能の要件

- **NFR1 応答時間**: 業務データの一覧（1ページ 100 件 × 100 カラムを含む）・詳細・作成・更新・削除の応答は、前の Intent と同じく 1 秒の目安とする。値と測り方は NFR 要件の段で決めて確かめる [assumption]。
- **NFR2 規模**: 対象DB 最大 100 テーブル・1 テーブル 100 カラム・利用者 50 名（参考資料の 7章）を扱える。対象DB から読む行の数に上限を置く [memory:M1]。
- **NFR3 対象DB**: MySQL・MariaDB・PostgreSQL の3種類で、一覧・検索・詳細・作成・更新・削除が同じ振る舞いになる（FR3.4 の大文字と小文字の扱いを除く）。結合テストは版を固定したイメージの3種類の DB で行う [memory:M3]。
- **NFR4 セキュリティ**:
  - NFR4.1 業務データの SQL に利用者の入力を文字列のまま組み込まない。識別子は適用中の DSL の名前と照らしてから引用し、値はバインド変数で渡す [memory:M3]。
  - NFR4.2 業務データの行の値（主キーの値を含む）を、アプリのログ・トレースの属性・エラー応答に含めない [memory:M3]。
  - NFR4.3 対象DB へ書き込む接続と資格情報は、読み取りと分けて環境変数（`.env`）だけから受け取る。書き込みのアカウントには、DSL の対象のスキーマの行の操作だけを与え、DDL の権限を与えない [memory:M3]。
  - NFR4.4 対象DB への問い合わせには、目的ごとの時間の上限を置く [memory:M2]。
- **NFR5 アクセシビリティ**: 画面は WCAG 2.1 AA を満たす。axe（E2E と画面の部品のテスト）で、ブランドカラーとテーマのすべての組について確かめる [memory:M1]。
- **NFR6 言語**: 画面の文言・表示名・誤りのメッセージは、日本語と英語の両方を用意し、既定を日本語とする [memory:M2]。
- **NFR7 テスト**: team.md の「業務データの画面」の必須のテストと、「役割・権限の機能」の必須のテストを当てる。E2E は業務データの代表の流れ1本まで [memory:M1]。
- **NFR8 運用**: 業務データの API で 403 が増えたときの警報 `ms-forbidden` のしきい値（20）は、Observability Setup で見直す（K-61） [assumption]。

## 制約

- 管理者の印 `users.admin_flag` は残す。縮める段（F2）は後の Intent で扱う [Q2]。
- 他テーブル参照の選択肢（`REFERENCE`）と参照ピッカー（`LOOKUP`）は後の Intent で扱う [Q1]。
- 同じ行を2人が同時に更新すると、後から保存した人の値で上書きされる（照らさない） [Q6]。
- DB に一意の制約が無いカラムでは、同時の作成・更新で重なった値が入りうる（FR10.3） [F1]。
- 部分一致の大文字と小文字の扱いは、対象DB の照合順序により DB ごとに違いうる [Q3]。
- `vendor/make-you-chic-ui` の中身は直接変えない。足りない部品は上流へ依頼する [memory:M3] [memory:M4]。
- 既存の ArchUnit の境界テスト（`TargetDbBoundaryArchitectureTest`・`RoleBoundaryArchitectureTest` など）を緩めるときは、コード生成の計画に明記して依頼者の承認を得る（K-49・K-50） [memory:M2]。
