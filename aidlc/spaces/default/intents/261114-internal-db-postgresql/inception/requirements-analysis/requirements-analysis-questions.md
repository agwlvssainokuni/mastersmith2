# Requirements Analysis の質問（Intent 261114-internal-db-postgresql）

## 決まっていること（質問にしない）

- 依頼の文: 内部DB（今は組み込みの H2）を PostgreSQL でも動かせるようにする。内部DB と対象DB（DSL の対象の業務DB）は別扱いのまま変えない。今回は PostgreSQL だけで、MySQL・MariaDB は後の Intent。
- Practices Discovery で決めたこと（`team.md`・`project.md`）:
  - 内部DB のテストは H2 が基本で、H2 の結合テストの全件は残す。PostgreSQL に固有の結合テストは別に作り、明示の指定を付けたときだけ流す（普段の `verify`・`verifyQuick`・CI では流さない）。PostgreSQL の結合テストは実際の PostgreSQL のコンテナで行い、H2 で代用しない。
  - 内部DB の PostgreSQL のイメージは、対象DB の PostgreSQL と同じ版とダイジェストを使う。
  - 手元の配備はこれまでどおり H2。PostgreSQL は compose の profile などで選べる形にし、配備の段で起動・スモークテスト・`pg_dump` などでの戻しの練習を確かめる。
  - E2E は H2 だけで流す。
  - 内部DB の接続情報はログ・監査ログ・エラー応答に含めず、環境変数（`.env`）だけから受け取る。
- 下調べとコードの調べで分かっていて、要件として既定の形で書くこと（違えば承認の場で直せます）:
  - PostgreSQL の上でも、H2 と同じ振る舞いを保つ: 待ちの上限（行の排他 3 秒、書き込みの待ち・一意の鍵の待ち約 2 秒）、違反の区分（名前の重なり・参照のある行の削除などが今と同じ応答になる）、失敗の後のトランザクションの扱い。
  - 対応していない種類の DB の接続先（MySQL・MariaDB など）を内部DB に指定したときは、起動を止めて、何が対応していないかを示す。

以下は、要件の中身として判断が分かれる点だけを尋ねます。

## Q1. [プロダクト] 既定の内部DB

今は内部DB は H2 だけで動きます。PostgreSQL を足した後、何も設定しないときの内部DB をどうするかです。

推奨: A。今の利用者と配備（手元の H2）を何も変えずに済み、PostgreSQL は使いたいときだけ選べるためです。Practices Discovery の「手元の配備は H2」とも合います。

A. 既定は H2 のまま。内部DB の接続先（環境変数 `MASTERSMITH_DB_URL` など）に PostgreSQL を指定したときだけ PostgreSQL で動く
B. 既定を PostgreSQL に変え、H2 は選べる形で残す
X. Other (please specify)

[Answer]: A

## Q2. [プロダクト] H2 から PostgreSQL へのデータの移し替え

推奨: A。今は配備先が手元のコンテナだけで、移す必要のある本番のデータがありません。移し替えは表の数が多く、監査の行の扱いなど決めることも多いため、必要になったときに別の Intent で行うのが確実です。

C. 道具は作らず、手で移す手順を文書に書く
X. Other (please specify)

[Answer]: A

## Q3. [プロダクト] アプリのインスタンスの数

## Q4. [運用] PostgreSQL の内部DB のコンテナの置き方（手元の compose）

B. 見本の対象DB と同じコンテナの中に、内部DB 用の別のデータベースと別の利用者を作る
X. Other (please specify)

[Answer]: A

## Q5. [運用] 対応を約束する PostgreSQL の版
