# 設計の判断の記録（ADR）— role-menu

出典の表記は `components.md` と同じ。各 ADR は Context・Decision・Consequences・Alternatives Rejected の形で書く（Inception の決まり）。実現可能性の評価の段が無いため、実現できるかの判断と、確かめる段・切り替え先を ADR-006 にまとめる（`project.md` の学び）。

## ADR-001: 役割・権限の機能を `role` と `group` の2つに分ける

- **Context**: ロール・主権限と補助権限の設定・割り当て・作業ロール・実効の権限の解決・YAML の受け渡しと、グループとメンバーを足す（FR1〜FR8）。既存の機能は層（web・service・domain・repository）で分け、機能の間の依存は ArchUnit の境界テストで固定している（TP）。
- **Decision**: 新しい機能を `role`（ロール・設定・解決・受け渡し・割り当て・作業ロール）と `group`（グループ・メンバー）の2つにする（DQ1: B）。依存は `role` → `group`。業務のメニューは別の新しい機能 `navigation` に置く（DQ3: A、ADR-004 の関連）。それぞれに `<機能>BoundaryArchitectureTest` を置く。
- **Consequences**:
  - 良い点: グループとメンバー（人の出入りで変わる）と、ロールの設定（業務の変更で変わる）を別々に直せる。`group` は役割を知らないため、グループの機能だけを単独で確かめられる。
  - 悪い点: 利用者のロールの和を求めるとき、`role` が `group` のメンバーを読む呼び出しが増える。グループの削除の確かめで依存が循環しうる（ADR-002 で解く）。境界テストが2つ増える。
- **Alternatives Rejected**: 1つの `role` にまとめる（DQ1: A。循環の心配が無いが、依頼者が分ける形を選んだ）。解決だけの `permission` を分ける3分割（DQ1: C。設定と解決の持ち主が分かれ、名前の照らし合わせの決まりが2か所になる）。

## ADR-002: グループの削除の確かめは、`group` が定義する「削除してよいかを問う口」を `role` が実装する

- **Context**: メンバーかロールの割り当てが残っているグループは削除できない（FR4.1a）。グループへのロールの割り当ては `role` が持つため、`group` が自分で確かめると `group` → `role` の依存ができ、`role` → `group` と循環する。
- **Decision**: `group` の service の層に「このグループを削除してよいか」を問うインターフェースを置き、`role` がそれを実装して自分の割り当ての有無を答える（DF1: A）。`group` は実装の中身を知らない。実装が無い（テストなど）ときは「削除してよい」と答える既定は置かず、必ず実装を要る形にする（割り当ての確かめの抜けを防ぐ）。
- **Consequences**:
  - 良い点: 依存の矢印は `role` → `group` の1本だけで、境界テストで固定できる。グループの API は `group` の持ち主のまま。
  - 悪い点: Spring の差し込みでインターフェースの実装を探すため、`group` の結合テストでは `role` の実装か、テスト用の実装が要る。削除の確かめと割り当ての追加が同時に重なる場合の守り方（行の排他など）は機能設計・NFR 設計で決める（要件の確かめの R-08、ストーリーの AC2.1.5）。
- **Alternatives Rejected**: グループの削除を `role` が受け持つ（DF1: B。グループの API がグループの持ち主の外に出る）。グループへの割り当てを `group` に置く（DF1: C。利用者のロールの和を求める部品が別に要り、循環を別の場所へ移すだけになる）。

## ADR-003: 実効の権限は要求ごとに内部DB から解決し、トークンに入れない

- **Context**: 割り当て・権限・作業ロールの変更は、その利用者の次の要求から効く（FR4.4・FR5.2）。アクセストークンに失効の仕組みは無い（PM の DECIDED）。固い制約「役割・権限による判定は API ごとにサーバー側で行う」（PM の Mandated）。今の管理者の印も要求ごとに DB から読む（K-32）。
- **Decision**: `role` の解決の口は、利用者と対象（スキーマ・テーブル・カラム）を受け、要求ごとに作業ロール・割り当て・設定を内部DB から読んで、直近の上位の明示の値を継承する規則で実効の主権限・補助権限を返す。全階層が設定なしなら NONE・不可、DSL に無い対象は NONE・不可。トークンにはロール・作業ロール・権限を入れない。業務のメニューの絞り込みは1回の要求の中で、作業ロールの設定をまとめて読んで行う（テーブルごとに問い合わせを重ねない）。
- **Consequences**:
  - 良い点: 割り当ての変更が次の要求からすぐ効き、トークンの有効期限を待たない。トークンの形を変えずに済む。
  - 悪い点: 要求ごとに読み出しが増える。業務のメニュー（最大 100 テーブル）・権限の設定の木の1階層（最大 100 カラム）の応答を 95 パーセンタイル 1 秒以内に収めることを NFR 要件・NFR 設計で確かめる（NFR2.2・NFR2.3）。キャッシュを置くかはそこで決め、置くなら変更の後の次の要求で古い値を使わない形にする。
- **Alternatives Rejected**: トークンに作業ロールと権限を入れる（失効が無いため外した権限が有効期限まで残り、FR4.4 と両立しない。PM の Mandated に反する）。セッションに覚える（今のアプリは状態を持たないトークンの形で、新しい仕組みが要る）。

## ADR-004: 権限の対象は、その都度 DSL と名前で照らし合わせる（写しを持たない）

- **Context**: 権限の対象と表示名は適用済みの DSL から出し（FR2.3、M1・F2 でスキーマの階層を足す）、DSL から消えた対象の設定は名前で持ち続けて解決では使わない（FR2.4）。DSL は `dsl` が持ち、適用は `dslmanage` が行う。
- **Decision**: `role` と `navigation` は `dsl` の提供口（`ActiveDslModelProvider`）を読む（片方向）。DSL の適用の出来事は受けず、権限の設定の画面・解決・業務のメニューのたびに、今の DSL と設定を名前で照らし合わせる（DQ4: A）。「今の DSL に無い」の印は、照らし合わせの結果として出す。
- **Consequences**:
  - 良い点: 写しと DSL の食い違いが起きず、DSL の適用の流れ（`dslmanage`）に手を入れない。`dsl` は役割を知らないまま。
  - 悪い点: 照らし合わせの分の処理が要求ごとに増える（今の規模では提供口の保持するモデルを読むだけで、ADR-003 の確かめに含める）。DSL から消えた対象の数を前もって出せない（画面で開いたときに分かる）。
- **Alternatives Rejected**: 適用の出来事で消えた数を数えておく（DQ4: B。出来事の受け手が増え、数と実際の食い違いを管理する必要が出る）。適用のたびに対象を写す（DQ4: C。写しの管理が要る）。

## ADR-005: DSL の書式の版 2 とメニューの深さの上限は `dsl` が持ち、起動時の読み直しでは深さだけを外す

- **Context**: 依頼者の決定で DSL にスキーマの階層を足し（M1: B）、形は複数・中身は対象DB の設定の1つ（F2: A）、書式の版 2 だけを受け付けて版 1 は読み替えない（F3: C）。メニューの深さに DSL の検証で上限を置く（FR9.4）。今のアプリは起動のたびに適用中の DSL を今の検証で読み直す（K-37 の関連）。
- **Decision**: `dsl` の型・JSON Schema・検証を版 2 に広げ、`dslmanage` の既定の DSL の生成を版 2 にする。メニューの深さの上限は、新しい投入と履歴からの復元では拒否し、起動時の読み直しでは深さだけを検証から外して深すぎる枝を出さず警告のログを出す（M3: A）。版 1 の適用中の DSL は、起動時に書式の版の誤りとして DSL が無い扱いになる（版 1 は深さの扱いでは救われない）。
- **Consequences**:
  - 良い点: DSL の形がスキーマを持ち、権限の3階層をそのまま当てられる。上限を後で下げても起動が止まらない。
  - 悪い点: 版を上げた環境では、既定の DSL を生成し直して投入し直すまで、権限の対象とメニューが空になる。前の版のアプリへ戻すと版 2 の DSL を読めず、DSL が無い状態で起動する（`team.md` の「広げてから縮める二段」との差。ストーリーの確かめの R-01 で受け入れ、配備の段へ引き継ぐ）。版 2 の DSL を前提に、DSL の既存のテスト（上限・タグ・重複キー・`$ref`）を書き換える。
- **Alternatives Rejected**: 版 1 も読み続ける・起動時に読み替える（F3: A・B。依頼者が版 2 だけを選んだ）。スキーマを「対象DB 全体の1つの節」と読み替え DSL を変えない（M1: A。依頼者が DSL に足す形を選んだ）。

## ADR-007: 権限の YAML の安全な読み込みは、`dsl` の service の層の口を使う

- **Context**: 権限の YAML は利用者が投入する信頼できない入力で、DSL と同じ守り（大きさ・入れ子・別名の上限、タグと任意の型の拒否、重複キーの誤り）を当てる（FR7.4、PM の Mandated）。今の安全な読み込み（`SafeYamlParser`・`LimitingParser`）は `dsl.parse` にあり、境界テスト（`DslBoundaryArchitectureTest` の `parseAndValidateStayInside`）が `dsl` の外からの直接の依存を禁じている（アーキテクチャの確かめの R-01）。
- **Decision**: `dsl` の service の層に「上限つきの安全な YAML の読み込み」の口を出し、上限の値は呼ぶ側が渡す。`role` はこの口だけを使い、`dsl.parse` には直接依存しない（DF2: A）。境界テストは変えない。上限の値は NFR 要件の段で決める（NFR2.4）。
- **Consequences**:
  - 良い点: 守りの実装が1か所のままで、DSL の読み込みの直しが権限の YAML にも効く。既存の境界テストを緩めない（`team.md` の承認の手続きが要らない）。
  - 悪い点: `dsl` の service の口が DSL 以外の用途にも使われる。口の形（受け取る上限、返す木と誤りの位置）は機能設計で決め、DSL の都合の項目（JSON Schema の検証など）を口に混ぜない。
- **Alternatives Rejected**: 共通の置き場へ移す（DF2: B。境界テストの変更と承認が要る）。`role` に同じ読み込みを作る（DF2: C。守りが2か所になり、上限の値が食い違うおそれがある）。

## ADR-008: API の分類は各 API の注釈で持ち、網羅のテストは全体の構造の検査に置く

- **Context**: すべての API が「公開・ログインだけ・管理者」のどれかに分類されていることを確かめる（NFR1.3、AC1.1.15）。今は `/api/**` の既定が「ログインだけ」（`AdminApiDefaultAccess`）で、権限の決まりの書き忘れとログインだけの意図を見分けられない。`access` は基盤の側で新しい機能を知らない（アーキテクチャの確かめの R-02）。
- **Decision**: `common/security` に分類の注釈（公開・ログインだけ・管理者）を定義し、各 API（コントローラーの口）に付ける。印の無い API があれば落ちるテストを、既存の `ArchitectureTest` と同じ置き場（全体の構造の検査）に置く（DF3: A）。あわせて、印と実際の安全の決まり（`/api/admin/**` は管理者だけ、など）が食い違わないことも確かめる（例: 管理者の印の API の道は `/api/admin/` の下）。`access` は新しい機能に依存せず、部品の依存からも外す。
- **Consequences**:
  - 良い点: 新しい API の書き忘れが構造の検査で落ちる。分類が API の隣にあり、読み手に意図が分かる。`access` の境界を崩さない。
  - 悪い点: 既存のすべての API に印を付ける作業が付く（この Intent の最初に手を入れる Bolt で行う）。印と安全の決まりが二重になり、両方の食い違いをテストで見る必要がある。
- **Alternatives Rejected**: テストの側に一覧を持つ（DF3: B。API を足すたびに別のファイルを直す必要があり、意図が API から離れる）。既定を「拒否」に変える（DF3: C。既存の決まりとテストの書き換えが多い）。

## ADR-006: 実現できるかの判断（確かめる段と切り替え先）

- **Context**: classic の範囲で実現可能性の評価の段が無い（`project.md` の学び）。この Intent で実現の見通しを確かめておく点が4つある。
- **Decision**: 次の4点を、記した段で確かめ、確かめられなかったときは記した切り替え先にする。

| 点 | 見通し | 確かめる段 | 確かめられなかったときの切り替え先 |
|---|---|---|---|
| 要求ごとの実効の権限の解決の重さ（ADR-003） | 業務のメニューは作業ロールの設定（最大 1 万行）をまとめて1回読めば足り、組み込みの H2 で 1 秒以内に収まる見込み | NFR 要件で目標と測り方、NFR 設計で試しのコード、Build and Test・Performance Validation で k6 | 作業ロールごとの設定の読み取りに、変更で捨てるキャッシュを置く（次の要求で古い値を使わない形） |
| 組み込みの H2（1つのアプリ）での同時の重なりの守り（ロール・グループの削除と割り当ての追加、作業ロールの切り替えと割り当ての外し） | 前の Intent の最後の管理者の保護と同じく、行の排他で守れる見込み | NFR 設計で試しのコード（`project.md` の学び） | 削除の側で、確かめと削除を1つの文（条件つきの削除）にする |
| DSL の版 2 への切り替え（ADR-005） | 書式の版の誤りとして DSL が無い扱いになることは、今の起動時の読み直しの仕組みで起きる | Functional Design・Code Generation、配備の段で生成し直しと戻しの手順 | — （依頼者が受け入れた影響。配備の段で手順を書く） |
| make-you-chic-ui への入れ子のサイドバーの依頼 | 上流への追加を先に依頼する（TP） | Functional Design で依頼の口を確定、Delivery Planning で間に合うかを見る | その時点で依頼者に諮り、frontend の側で自前で作る（自前でも満たす基準の切り分けは Delivery Planning） |

- **Consequences**: 4点の確かめの持ち主の段が決まり、確かめられなかったときの道がある。ただし、どれも今の時点では見通しで、確かめは後の段に残る。
- **Alternatives Rejected**: ここで試しのコードまで書いて確かめる（Domain Design の範囲を超え、設計の段で通す決まり（`project.md`）と合わない）。確かめを持ち主の段に割り振らない（前の Intent で見落としが出た）。
