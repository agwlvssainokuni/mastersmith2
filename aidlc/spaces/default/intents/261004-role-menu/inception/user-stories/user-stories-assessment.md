# ユーザーストーリーの要否の評価 — role-menu

## 判断

**Execute**（ユーザーストーリーを書く）

## 理由

- 利用者に見える機能を足す。管理者がロール・グループ・権限・割り当てを設定する管理の画面と、すべての利用者が使う作業ロールの切り替え・自分の権限の確かめ・N 階層のメニューがある（`aidlc/spaces/default/intents/261004-role-menu/inception/requirements-analysis/requirements.md` の FR1〜FR11）。
- 立場の違う利用者が2人いる。設定する管理者と、その結果（作業ロール・メニューの出し分け）を受ける一般の利用者で、同じ操作でも見え方が違う（ストーリーの質問 Q1: A）。
- 業務の決まりが多い。主権限・補助権限の継承の解決、割り当てのあるロール・グループの削除の拒否、作業ロールの選び直し、import の2段と適用時の再検証、DSL から消えた対象の扱い、メニューの出し分けの判定の基準がある（FR2〜FR10）。
- 画面の骨組み（サイドバー・登録の型・ルーティング）と make-you-chic-ui にまたがり、上流への部品の依頼が要る（制約 C3）。
- 統合の段で、DSL にスキーマの階層を足す変更（書式の版 2。版 1 は受け付けず読み替えない）が範囲に入った（ストーリーの質問 M1: B・F2: A・F3: C）。要件に無い変更のため、ストーリー US6.1 と `stories.md` の「要件との差」（D1・D2）に書いた。版を上げた環境では既定の DSL の生成と投入し直しが要り、前の版のアプリへ戻すと DSL が無い状態で起動するため、配備の段の論点にもなる。

## 考えた要素

| 要素 | この Intent |
|---|---|
| 種類 | 既存のアプリへの機能の追加（ブラウンフィールド） |
| 利用者に見える範囲 | 管理の画面（ロール・グループ・権限・割り当て・YAML）、作業ロールの切り替え、自分の権限、サイドバーのメニュー、準備中の画面、DSL の書式の版 2（スキーマの階層） |
| 複雑さの兆し | 3階層の継承、作業ロール、2段の import、同時の操作、権限による出し分け、N 階層の木、DSL の書式の版上げと前の版との非互換 |
| ペルソナ | 管理者・一般の利用者の2人 |

## ストーリーが最も効く所

- 継承の解決とメニューの出し分けを、具体の値の組み合わせで受け入れ基準にし、QA が合否を書けるようにする。
- 作業ロールの切り替え・割り当ての変更・ロールの削除が重なったときの、利用者から見た結果をそろえる。
- import の確かめと適用の間の流れと、拒否の場合を、管理者の手順として決める。
