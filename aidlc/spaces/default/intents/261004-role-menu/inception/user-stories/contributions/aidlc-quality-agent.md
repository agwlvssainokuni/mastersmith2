## Contribution

品質担当として、初稿 `aidlc/spaces/default/intents/261004-role-menu/inception/user-stories/stories.md` の受け入れ基準を、合否が一意に決まるか・境界値・失敗の場合・同時の重なり・`team.md` の役割・権限の必須のテストと N 階層のメニューのテストの決まりとの対応・要件の抜けの観点で確かめた。以下は、リードがそのまま取り込める形の「直す」「足す」の案である。新しい AC の ID は各ストーリーの続き番号で振った。

### A. 前提と読み方に足す（すべての受け入れ基準に共通）

- **同時の重なりの読み方**: 「同じ時に」の受け入れ基準は、スレッドの数に頼らず待ち合わせで確実に重ねて確かめる（TP）。合否は、両方の要求が終わった後の内部DB の状態（不変条件）と、負けた側の応答が業務の理由の code の 4xx であること（500 にならないこと）の2つで判定する。どちらが勝つかは問わない。
- **「変わらない」の読み方**: 拒否の後に、対象の行（ロール・権限の設定・割り当て・メンバー・作業ロール）を読み直して、要求の前と同じであることを確かめる。応答の状態コードだけでは合格にしない。
- **「次の要求から」の読み方（★変更の前に出したトークンの扱いの解決）**: 権限・割り当て・作業ロールはトークンに入れないため、変更の前に出したアクセストークンをそのまま使った次の要求で、サーバー側の結果が変わる。トークンの作り直しやログインのし直しを要しないことを、決めた側の動作として明示してテストする（FR4.4・FR8.2）。
- **ロールは管理の権限を与えない（C1）**: 管理の API の可否と最後の管理者の数え方は管理者の印だけで決まり、ロール・作業ロール・権限の設定では変わらない。最後の有効な管理者は印で数える（TP の★「最後の有効な管理者の役割での数え方」の解決）。
- **組み込みのロール（TP の★の解決、要確認）**: 要件にはあらかじめ用意するロールが無い。そのため組み込みのロールは置かず、すべてのロールは管理者が作り・消せるものとして読む（下の Positions で確認を求める）。
- **境界値の読み方**: 名前の長さ・YAML の大きさ・入れ子・別名・メニューの深さなど、値を設計で決める上限は、「上限ちょうどは受け付け、上限を1つ超えると拒否」の2点で確かめる。

### B. US1.1 ロールを整える

- **AC1.1.5 を直す**: Given 管理者の印を持たず、全スキーマを FULL・CREATE・DELETE 可にしたロールを作業ロールにしている利用者（要る権限＝管理者の印だけを欠く利用者） / When ロールの作成・名前の変更・削除の API を呼ぶ / Then 403 が返り、ロールは変わらない。未認証は 401、管理者は 200（作成は 201 など成功の状態コードは機能設計で決める）、停止中の管理者は通らない。API と期待の状態コードの組は表のパラメーターのテストで書く（TP）。
- **AC1.1.6 を直す**: 末尾に「両方の要求が終わった後、ロールが消えていれば割り当ては0件、割り当てが残っていればロールは残っている。負けた側は業務の理由の code で返り、500 にならない。重なりは待ち合わせで作る」を足す。
- **AC1.1.7（足す）**: Given 管理者がロールを作る・名前を変える / When 名前が空、空白だけ、長さの上限を1文字超える / Then 名前の誤りとして拒否され、ロールは変わらない。上限ちょうどは受け付ける（上限の値と大文字・小文字の扱いは機能設計で決め、決めた値の境界で確かめる。FR1.1）。
- **AC1.1.8（足す）**: Given 管理者がロールの作成・名前の変更の要求を送る / When 本文に許していない項目（ID・作成者・作成の時刻・組み込みの印など）を足す / Then それらは反映されず、作られたロールは名前だけが要求の値になる（一括代入の防止。TP）。
- **AC1.1.9（足す）**: Given 存在しないロールの ID / When 名前の変更・削除の API を呼ぶ / Then 存在しないロールとして拒否され、ほかのロールは変わらない（IDOR。TP）。

### C. US1.2 ロールの権限を設定する

- **AC1.2.1 を直す**: 「開いた所だけを読み込む」を合否が決まる形にする。「スキーマを開く要求の応答はそのスキーマのテーブルだけを含み、カラムを含まない。テーブルを開く要求の応答はそのテーブルのカラムだけを含む」（FR11.2）。
- **AC1.2.2 に足す**: Given スキーマ S を NONE、テーブル T を FULL、T のカラムは設定なし / Then T のカラムの実効は FULL（上位の NONE は下位の明示の値を止めない。FR2.2 の4つ目の例）。
- **AC1.2.4 を直す**: CREATE に加えて DELETE を同じ形で確かめ、「スキーマ S の CREATE を可・DELETE を設定なしにしたとき、T の実効の DELETE は不可（CREATE と DELETE は互いに影響しない）」と「スキーマ 不可・テーブル 可 のとき、テーブルの実効は可」を足す。
- **AC1.2.6 を直す**: 画面に加えて「権限の設定を保存する API も、DSL が無い旨で拒否され、設定は変わらない」を足す（画面の案内だけでは合否にしない）。
- **AC1.2.7 を分ける**: 「T が DSL から消えている間、T の設定は解決で使われず、権限の解決の口は T を NONE・不可と返し、T を指すメニューの項目は出ない。同じ名前の T が DSL に戻れば、残っていた設定がまた効く」を Must の **AC1.2.8** として独立させる（FR2.4・FR8.3。今の AC1.2.7 は「戻れば効く」だけが Must で、「消えている間は使わない」が受け入れ基準に無い）。AC1.2.7 は表示と削除の〔Should〕だけにする。
- **AC1.2.9（足す）**: Given 管理者が権限の設定を保存する / When 値に許していないもの（例: `ADMIN`）、カラムへの CREATE・DELETE、存在しないロールの ID を送る / Then 入力の誤りとして拒否され、設定は変わらない（FR2.1・FR3.1）。
- **AC1.2.10（足す）**: 管理者でない利用者（AC1.1.5 と同じ、管理者の印だけを欠く利用者）が、木を開く・保存する API を呼ぶと 403、未認証は 401、管理者は 200。停止中の管理者は通らない。
- **AC1.2.11（足す。性質ベースのテスト、NFR6.2）**: 任意の3階層の設定（設定なし・NONE・READ・FULL の組）について、カラムの実効の値は「カラム・テーブル・スキーマの順に見て最初の設定なしでない値、すべて設定なしなら NONE」に等しい。補助権限も同じで、すべて設定なしなら不可。作業ロールを変えない限り、利用者にロールを足しても外しても（作業ロール以外のロールであれば）実効の権限は変わらない（jqwik、失敗時の乱数の種を記録する）。
- **AC1.2.12（足す、判断が要る。Positions 参照）**: Given 管理者 A と B が同じロールの権限の設定の画面を開いている / When 2人が違う値を保存する / Then 〔決めた側の動作〕を明示したテストにする（後勝ち か、後の保存を「ほかの人が変えた」として拒否するか）。

### D. US2.1 グループで利用者をまとめる

- **AC2.1.2 を直す**: 名前の変更で既存の名前にするときも拒否、空・空白・長さの上限の境界を AC1.1.7 と同じ形で足す。
- **AC2.1.5 を直す**: AC1.1.6 と同じく、両方が終わった後の不変条件（グループが消えていればメンバーと割り当ては0件）と、負けた側が業務の code の 4xx であることを足す。
- **AC2.1.6 を直す**: AC1.1.5 と同じ形（管理者の印だけを欠く利用者で 403、未認証 401、管理者 200、停止中の管理者は通らない、表のパラメーターのテスト）。
- **AC2.1.7（足す）**: Given 利用者 A がグループ「経理部」経由でだけ「経理」を持ち、作業ロールが「経理」 / When 管理者が A を「経理部」から外す / Then A の次の要求（外す前に出したアクセストークンのまま）で、「経理」は A のロールから消え、作業ロールは残りのロールの最初か、無ければ無しになる（FR4.3・FR4.4・FR5.5。メンバーの変更による反映が初稿に無い）。
- **AC2.1.8（足す）**: Given A に「営業」が直接とグループ「営業部」経由の両方からある / When A を「営業部」から外す / Then A は直接の割り当てで「営業」を持ち続け、作業ロールは「営業」のまま（和と重なりの扱いの境界）。
- **AC2.1.9（足す）**: Given 存在しない利用者の ID・存在しないグループの ID / When メンバーを足す・外す / Then 拒否され、メンバーは変わらない（IDOR）。
- **AC2.1.10（足す）**: Given グループのメンバーの一覧の API / When 管理者が読む / Then 応答に、パスワードのハッシュ値・招待のトークンのハッシュ値・ロックの判定の内部の値が含まれない。TRACE のログを有効にして一覧を読み、メールアドレス・氏名がアプリのログに出ない（`XxxSecretLeakIT`、NFR1.6）。

### E. US2.2 利用者とグループにロールを割り当てる

- **AC2.2.3 を直す**: 「A の次の要求で」を「外す前に出した A のアクセストークンのままの次の要求で」に直し、確かめは権限の解決の口とメニューの API の両方の結果で行う。
- **AC2.2.5 を分ける**（「403 か入力の無視・拒否」は合否が一意でない）:
  - AC2.2.5a: 管理者の印だけを欠く利用者 B が、割り当て・外しの API を自分にも他人にも呼ぶと 403 で、割り当ては変わらない。未認証は 401、管理者は 200、停止中の管理者は通らない。
  - AC2.2.5b: B が `/api/me` など管理の API の外の要求の本文にロール・グループ・作業ロール・管理者の印の項目を足して送ると、その要求は既存の決まりどおりに扱われ（状態コードは今の動作）、B のロール・グループ・作業ロール・管理者の印は読み直して変わっていない。
- **AC2.2.7（足す）**: Given 存在しないロールの ID、存在しない利用者・グループの ID、別の利用者の割り当ての ID / When 割り当て・外しの API を呼ぶ / Then 拒否され、どの割り当ても変わらない（IDOR。TP）。
- **AC2.2.8（足す。決めた側の動作の明示、Positions 参照）**: Given 管理者 M の作業ロールでは業務データがすべて NONE / When M が全スキーマ FULL のロールを自分や他人に割り当てる / Then 受け付けられる（管理の操作の可否は印だけで決まり、操作する人の業務データの権限には縛られない。C1）。TP の「操作する人が持たない権限を与えられない」は、「管理者の印を持たない利用者は、ロール・権限・割り当てを一切変えられない」と読む。
- **AC2.2.9（足す。自分への操作と最後の管理者）**: Given 最後の有効な管理者 M がロールを持つ / When M が自分のロールをすべて外す / Then 受け付けられ、M の作業ロールは無くなるが、M の管理の API は 200 のまま。最後の管理者の保護（印を外す・利用を止める操作の拒否）は今までどおり印で数えて働く（C1）。
- **AC2.2.10（足す。ロールは管理の権限を与えない）**: Given 管理者の印を持たず、全スキーマ FULL のロールを作業ロールにする利用者 / When 今ある管理の API（利用者・招待・DSL など）を呼ぶ / Then すべて 403（ロールで管理の権限が増えない。C1）。

### F. US3.1 権限の設定を YAML で受け渡す

- **AC3.1.4 に足す**: 確かめと適用の間に、別の管理者が「営業」を削除した場合、ファイルにあるロールの名前で別のロールを作った場合、DSL を適用し直して対象の有無が変わった場合も、確かめた内容と違うとして拒否され、設定は変わらない（FR7.3a）。
- **AC3.1.7 を分ける**（上限は境界の2点で確かめる）:
  - AC3.1.7a: 大きさ・入れ子の深さ・別名の数のそれぞれで、上限ちょうどは受け付け、上限を1つ超えると拒否される。別名の展開の爆発で処理が止まらない（時間の上限内に拒否が返る）。
  - AC3.1.7b: 任意の型を作るタグ（`!!` など）を含むと拒否され、型が作られない。重複キーは誤りになり、後の値で黙って上書きされない。外部の参照を取りに行かない。
  - AC3.1.7c: どの拒否も Problem Details で返り、YAML の部品の例外のメッセージを含まず、設定は変わらない。
- **AC3.1.9（足す。形の誤り）**: Given YAML の形は正しいが中身が誤り（許していない権限の値、カラムへの CREATE・DELETE、ロールの名前の空・上限超え、同じロールの名前がファイルの中で2回、知らない項目） / When 読み込む / Then 誤りの位置（ロールの名前・対象）が分かる形で拒否され、設定は変わらない。
- **AC3.1.10（足す。往復）**: Given ある環境で export した YAML / When 同じ環境で変更せずに読み込む / Then 確かめの一覧に変わる点が無い（書き出しと読み込みの往復で設定が変わらない）。変わる点の無い一覧を適用したときの動作は機能設計で決め、決めた側の動作を明示したテストにする。
- **AC3.1.11（足す。認可）**: export・確かめ・適用の API は、管理者の印だけを欠く利用者で 403、未認証 401、管理者 200、停止中の管理者は通らない。
- **AC3.1.8 を直す**: 「適用の途中で失敗した」を「テストで、適用の途中の書き込みを失敗させる（例: 何件目かの対象の保存で失敗を起こす）」と、起こし方まで書く。合否は、ロール・設定の全件が読み込む前と同じで、適用の監査の行が成功として残らないこと（NFR3.2）。

### K. 横断（どのストーリーにも無い要件。置き場はリードが決める。US1.1 か新しい横断の受け入れ基準に置く案）

- **ACX.1（NFR1.3、TP の必須）**: アプリのすべての API が「公開・ログインだけ・管理者」のどれかに明示して分類されていることを確かめるテストがあり、分類の無い API を足すと落ちる。今回足す API（ロール・グループ・権限・割り当て・import・作業ロール・自分の権限・メニュー・準備中の画面の権限の確かめ）はすべて分類に載る。
- **ACX.2（NFR5.1）**: 今回足す監査の種類の名前は、すべて 32 文字以内（列挙を全件読んで確かめる単体テスト）。
