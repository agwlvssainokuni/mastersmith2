## Contribution

デザイナーの立場で、初稿（`aidlc/spaces/default/intents/261004-role-menu/inception/user-stories/stories.md`・`personas.md`）を、利用者の体験とペルソナへの忠実さで確かめた。全体として、群の切り方・Given/When/Then・失敗の場合の網羅はよい。足りないのは主に次の4点で、それぞれを受け入れ基準の案にした。

1. **作業ロールの見え方**: 今の作業ロールが常に見えること、切り替えた結果が読み上げで伝わること、作業ロールが本人の操作なしに変わったとき（AC2.2.3・AC2.2.4）に本人が気づけること。
2. **N 階層のメニューの道案内**: 今の項目の祖先が開いていること、深い階層と長い名前でも読めること、業務と管理の2つのまとまりが見出しで分かること、古いメニューから移ったときの扱い。
3. **誤操作の防止と拒否の案内**: 削除の確かめ、拒否されたときに次の一手が分かる文言（どこに割り当てが残っているか）、直接とグループ経由のロールの出どころの区別。
4. **権限の設定の画面の読みやすさ**: 明示と継承を色だけで分けないこと、継承の元が分かること、保存していない変更の扱い。

新しい AC の ID は、既存の連番の後ろに足した。文言の具体は画面の段（Refined Mockups）で決めるため、案の中の文言は例として書く。画面の置き場（上部・ユーザーメニューなど）は FR5.6 のとおり画面の段で決める前提で、受け入れ基準は置き場によらない形にした。

### 「前提と読み方」に足す行（共通の画面の受け入れ基準）

`stories.md` の「共通の受け入れ基準の読み方」に、次の1行を足す。各 AC に繰り返さないため（前の Intent の学びと同じ書き方）。

- **画面の共通**: 足す画面と部品は WCAG 2.1 AA に沿う。状態（明示・継承・今の DSL に無い・開閉・今の項目・作業ロール）は色だけで表さず、文字かアイコンと読み上げの名前を伴う。操作の結果（成功・拒否）は読み上げにも伝わる（`aria-live` など）。取り消しにくい操作（削除・import の適用）の確かめの表示は、背景のクリックで閉じず、はじめのフォーカスを「やめる」に置く（前の Intent の Modal の決まり）。画面の文言は日本語と英語を用意し、ロール・グループの名前と DSL の表示名は利用者が入れた値のまま出す（訳さない）（NFR4.1・NFR4.3）。

### ペルソナ（`personas.md`）への提案

- P1 の目的「権限を変えた後に、利用者のメニューが期待どおりに変わったかを確かめたい」は、今のストーリーのどれも満たしていない（FR6.2 で管理者は他人の実効の権限を見られない）。AC1.2.10 を足すか、この目的を「ロールの実効の権限で、どのテーブルがメニューに出るかを確かめたい」に書き直す（Positions の OBJECT 1）。
- P1 の困りごと「2〜3人の管理者が同じロールを同時に直すと、ほかの人の変更に気づけない」に当たる受け入れ基準が、権限の設定（US1.2）に無い（import の AC3.1.4 だけ）。Positions の OBJECT 3 を参照。
- P2 に、作業ロールを1日に何度か切り替える使い方（例: 午前は「営業」、午後は「経理」）を1行足すと、切り替えの部品を毎回の画面に置く理由（FR5.6）がペルソナから読める。

## Positions

- AGREE: 群を利用者の目的で切り、各ストーリーに失敗の場合と同時の重なりを入れた形は、画面の段で受け入れ基準を画面ごとに振り分けやすい。
- AGREE: AC5.1.2 の「判定はテーブルの階層の値だけ」と、子が出ないまとまりを出さない形は、利用者が開いても何も無いまとまりに迷わないため体験としても正しい。
- AGREE: AC5.1.7 で許していない icon を既定のアイコンにする形は、DSL の誤りで画面が崩れず、利用者に余計な誤りを見せないためよい。
- AGREE: AC4.1.6（管理者でも業務データは作業ロールで決まる）は、管理者が自分の画面で利用者の見え方を再現できる手段にもなり、明記してよい。
- OBJECT: 1. 判断が要る。P1 の目的「権限を変えた後に、利用者のメニューが期待どおりに変わったかを確かめたい」に応える受け入れ基準が無い。案は AC1.2.10（権限の設定の画面に、テーブルごとに業務のメニューに出るかを表示する。データは増えず FR11.3 の実効の値の見せ方の延長）。足さないなら、ペルソナの目的を書き直してストーリーとそろえる。
- OBJECT: 2. 判断が要る。管理者の操作で作業ロールが本人の知らないうちに変わる・無くなる（AC2.2.3・AC2.2.4）とき、本人への案内が要件に無い。案は AC4.1.11（Should）。要件 FR5.5 の範囲で表示を足すだけだが、「前回の作業ロール」を覚えて比べる作りが要るため、要件の追加とみなすかを依頼者に決めてもらう。
- OBJECT: 3. 判断が要る。P1 の困りごと（同じロールを同時に直すと、ほかの人の変更に気づけない）に対し、権限の設定の保存に後勝ちの上書きを防ぐ受け入れ基準が無い（import には AC3.1.4 がある）。案は「Given 管理者 A が画面を開いた後に B が同じ対象を保存した / When A が保存する / Then 他の人が変えたことが分かり、A の保存は拒否されるか、最新を読み直して確かめられる」。要件 NFR3 に無いため、足すなら要件の出どころを記録する。足さないなら、ペルソナの困りごとから外すか、後の Intent の論点として記録する。
- OBJECT: AC1.2.2 の「区別して見える」は、色だけで分ける作りでも満たせてしまう。色だけでなく文字で区別し、継承の元の階層が分かる形に直す（WCAG 1.4.1。上の「AC1.2.2 を直す」）。
- OBJECT: AC5.1.4 は NONE のテーブルだけを書いており、DSL に無いテーブルの道で表示が違うと、道を変えてテーブルの有無を探れる。同じ表示にそろえる（上の「AC5.1.4 を直す」）。
- OBJECT: AC5.1.1 は「キーボードだけでたどれる」だけで、操作の形（開閉のボタンか、ARIA の tree と矢印のキーか）が決まっていない。make-you-chic-ui に依頼する入れ子のサイドバーの口と、テストの合否が形で変わるため、今の `DslMenuTree` と同じ開閉のボタンの形を受け入れ基準に書く（上の「AC5.1.1 を直す」）。
- OBJECT: 拒否の受け入れ基準（AC1.1.3・AC2.1.3）は「拒否され、変わらない」だけで、管理者が次に何をすればよいかが分からない。割り当て・メンバーの残りの数を示す AC1.1.8・AC2.1.7 を足す（P1 の困りごと「誤って消すと利用者の仕事が止まる」と合わせ、確かめの表示 AC1.1.7 も足す）。
