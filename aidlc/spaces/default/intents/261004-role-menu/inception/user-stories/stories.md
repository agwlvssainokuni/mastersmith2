## 前提と読み方（すべての受け入れ基準に共通）

### 分け方・優先度

- **分け方と細かさ**: 利用者の目的で群を作り、目的ごとに大きめにまとめる（SQ2 A・SQ5 B）。操作をまたぐ要件（管理の API の認可・監査・同時性・漏えい・API の分類の網羅）は、関わる各ストーリーの受け入れ基準に入れる（SQ3 A）。アプリ全体で1つのテストで確かめるもの（API の分類の網羅・監査の種類の名前の長さ）は、最初に新しい API を足す US1.1 に置き、この Intent で足すすべての API・監査の種類を対象とする。
- **優先度**: 1つのストーリーに Should の部分が混ざるときは、ストーリーを Must とし、その受け入れ基準に **〔Should〕** と印を付ける。すべてが Should のストーリーは Should とする（SF1 B）。

### 業務の決まりの読み方

- **権限の対象**: 適用済みの DSL（書式の版 2）のスキーマ・テーブル・カラム。スキーマの階層は DSL に足す（US6.1。SM1 B）。この Intent では、DSL のスキーマは対象DB の設定のスキーマ1つだけを中身とする（SF2 A）。設定は名前で持ち、DSL から消えた対象の設定は解決で使わない（FR2.3・FR2.4）。
- **主権限の値**: 各階層の値は「設定なし・NONE・READ・FULL」。実効の値は、その階層が「設定なし」でなければその値、「設定なし」なら直近の上位の実効の値、スキーマまで「設定なし」なら NONE（FR2.2）。
- **補助権限の値**: CREATE と DELETE のそれぞれに、スキーマ・テーブルの階層で「設定なし・可・不可」。継承は主権限と同じで、スキーマまで「設定なし」なら「不可」。CREATE と DELETE は互いに影響しない（FR3.2）。
- **利用者のロール**: 直接の割り当てと、属するグループへの割り当ての和。同じロールが両方から来ても1つとして扱う（FR4.3・A2）。
- **作業ロール**: 利用者のロールから1つ。実効の権限は作業ロールだけで決まり、ほかのロールの権限は合算しない。ロールが無い利用者は作業ロールが無く、実効の権限はすべて NONE・不可（FR5.1・FR5.5）。覚えている作業ロールが自分のロールでなくなったときは、機能設計で決めた順序の最初のロールに置き換わる。この置き換えは利用者の操作ではないため、作業ロールの切り替えとしては監査に残さない（V）。
- **「次の要求から」**: 権限・割り当て・作業ロールはトークンに入れず、要求ごとに内部DB から求める。変更は、その利用者の次の要求でサーバー側の結果に効く。変更の前に出したアクセストークンをそのまま使った次の要求で結果が変わり、トークンの作り直しやログインのし直しは要らない。これを決めた側の動作として明示してテストする（FR4.4・FR8.2。TP の★「変更の前に出したトークンの扱い」の答え）（Q）。
- **管理の操作**: ロール・グループ・権限・割り当て・import・export は管理者だけが行える。受け入れ基準の「管理者」は管理者の印を持つ利用者を指す（C1・FR1.3）。
- **ロールは管理の権限を与えない**: 管理の API の可否と最後の有効な管理者の数え方は、管理者の印だけで決まる。ロール・作業ロール・権限の設定では変わらない（C1。TP の★「最後の有効な管理者の役割での数え方」の答え）（Q）。
- **権限の昇格の防止の読み方**: TP の「操作する人が持たない権限を、自分や他人に与えられない」は、「管理者の印を持たない利用者は、ロール・グループ・割り当て・権限を一切変えられない」と読む。管理者は、自分の作業ロールに無い権限を持つロールも、自分や他人に割り当てられる（SM5 A）。
- **組み込みのロール**: 置かない。すべてのロールは管理者が作り・消せる。TP の★「組み込みの役割の有無と、その削除・権限の取り上げの保護」のテストは「当たらない」と記録する（SM6 A）。
- **変えるものが無い操作**: 管理の操作（同じロールを重ねて割り当てる、割り当てられていないロールを外す、すでにメンバーの利用者を足す、メンバーでない利用者を外す、今と同じ名前への名前の変更、今と同じ値での権限の保存、変わる点の無い import の適用 など）は、業務の誤りとして拒否し、監査に残す。作業ロールの切り替えで今と同じロールを選んだときは、何も変えない成功とし、監査には残さない（SM4 C）。
- **同じロールの権限の同時の保存**: 2人の管理者が同じロールの権限の設定を同時に保存したときは、後の保存で上書きし、監査に両方の前後の値を残す（後勝ち。SM2 A）。
- **テーブルと子の両方を持つメニューの項目**: テーブルが見える（実効の主権限が READ 以上）か、子が1つでも見えれば出す。テーブルが READ 以上なら、選ぶとテーブルの画面へ移れるまとまりとして出す。テーブルが NONE で子だけが見えるときは、選んでもテーブルの画面へは移らないまとまりとして出す（SL。V の F-2）。
- **作業ロールの変化の案内**: 管理者の操作で本人の作業ロールが変わった・無くなったときに、本人へ知らせる案内は出さない。作業ロールの表示が変わるだけとする（SM8 B）。

### 共通の受け入れ基準の読み方

- **認可**: 管理の API を足す・変えるストーリーでは、未認証は 401、管理者でない利用者は 403、管理者は成功（200 など。作成の 201 などの成功の状態コードは機能設計で決める）をサーバー側で確かめる。403 を確かめる利用者は、権限が何も無い利用者ではなく、ロールを持ち作業ロールもある（例: 全スキーマを FULL・CREATE と DELETE を可にしたロールを作業ロールにする）、管理者の印だけを欠く利用者とする。停止中の利用者は、管理者の印やロールがあっても、この Intent で足す API をどれも呼べない。API と期待の状態コードの組は、パラメーターを使うテストで表として書く（NFR1.2・TP）（V・Q）。
- **API の分類**: 足す API はすべて「公開・ログインだけ・管理者」のどれかに明示して分類する。ロール・グループ・権限・割り当て・import・export は「管理者」、作業ロールの切り替え・自分の権限・業務のメニュー・準備中の画面の表示名と権限の確かめは「ログインだけ」（NFR1.3）（V）。
- **拒否の応答**: 業務の理由の拒否は、理由ごとに別の安定した `code` を持つ Problem Details（4xx）で返る。受け入れ基準の「〜として拒否される」は「その理由の code で拒否される」と読む。code の名前は機能設計で決める。
- **「変わらない」の確かめ方**: 拒否の後に、対象の行（ロール・権限の設定・割り当て・メンバー・作業ロール）を読み直して、要求の前と同じであることを確かめる。応答の状態コードだけでは合格にしない（Q）。
- **同時の重なりの確かめ方**: 「同じ時に」の受け入れ基準は、スレッドの数に頼らず待ち合わせで確実に重ねて確かめる。合否は、両方の要求が終わった後の内部DB の状態（受け入れ基準に書いた不変条件）と、負けた側の応答が業務の理由の code の 4xx であること（500 にならないこと）の2つで判定し、どちらが勝つかは問わない（TP）（Q）。
- **境界値の確かめ方**: 値を設計で決める上限（名前の長さ・YAML の大きさ・入れ子・別名・メニューの深さなど）は、「上限ちょうどは受け付け、上限を1つ超えると拒否」の2点で確かめる（TP）（Q）。
- **監査**: 「監査に残る」は、操作した人・対象・変えた中身・結果を含む行が残ることを指す（FR12.1）。業務の理由で拒否した操作のうち、変えるものが無い管理の操作は拒否して監査に残す（SM4 C）。それ以外の拒否を残すかは機能設計で決める（FR12.2）。
- **漏えい**: 応答と監査の行に、パスワード・トークン・ハッシュ値（パスワード・招待のトークン）・ロックの判定の内部の値を含めない。個人に関する値（メールアドレス・氏名・検索の文字）を扱う API は、TRACE のログを有効にしてもアプリのログに値が出ないことを、既存の `*SecretLeakIT` と同じ形で確かめる（FR4.5・FR12.3・NFR1.6）。
- **画面の共通**: 足す画面と部品は WCAG 2.1 AA に沿い、画面部品ごとにアクセシビリティ検査を1件入れる。状態（明示・継承・今の DSL に無い・開閉・今の項目・作業ロール・業務のメニューに出るか）は色だけで表さず、文字かアイコンと読み上げの名前を伴う。操作の結果（成功・拒否）は読み上げにも伝わる（`aria-live` など）。取り消しにくい操作（削除・import の適用）の確かめの表示は、背景のクリックで閉じず、はじめのフォーカスを「やめる」に置く。画面の文言は日本語と英語を用意し、ロール・グループの名前と DSL の表示名は利用者が入れた値のまま出す（訳さない）。文言の具体と置き場は画面の段（Refined Mockups）で決め、受け入れ基準の中の文言は例とする（NFR4.1・NFR4.3）（D）。
- **性能**: 応答時間の受け入れ基準は、規模を NFR2.1 の上限にして、測り方を NFR 要件の段で決める。負荷の環境が無く測れない段では `Unverified` とし、持ち主の段を明記して引き継ぐ。目標を緩めて「満たした」ことにはしない（PM）（Q）。

## 群1 ロールと権限を整える

### US1.1 ロールを整える 〔Must〕

P1 管理者として、部署や仕事に合わせたロールを作り、名前を直し、要らなくなったロールを消したい。それは、業務データの見せ方を人ではなくロールで管理するためだ。

出典: FR1.1〜FR1.3、FR5.5、FR11.1、FR12.1〜FR12.3、NFR1.2〜NFR1.4、NFR3.1、NFR4.1、NFR5.1、NFR5.2、SM4、SM6

- **AC1.1.1** Given 管理者がロールの管理の画面を開いている / When 「営業」という名前でロールを作る / Then ロールの一覧に「営業」が出て、作成が監査に残る
- **AC1.1.2** Given 「営業」がすでにある / When もう一度「営業」を作る、または別のロールの名前を「営業」に変える / Then 名前の重なりとして拒否され、ロールの一覧は変わらない
- **AC1.1.3** Given ロール「営業」が利用者かグループに1つでも割り当てられている / When 「営業」を削除する / Then 割り当てが残っているとして拒否され、「営業」と割り当てはそのまま残る
- **AC1.1.4** Given ロール「営業」に割り当てが無い / When 「営業」を削除する / Then 「営業」とその権限の設定が消え、削除が監査に残る
- **AC1.1.5（直した）** Given 管理者の印だけを欠く利用者（全スキーマを FULL・CREATE と DELETE を可にしたロールを作業ロールにしている）がログインしている / When ロールの作成・名前の変更・削除の API を呼ぶ / Then 403 が返り、ロールは変わらない。未認証は 401、管理者は成功、停止中の管理者は通らない。API と期待の状態コードの組は表のパラメーターのテストで書く（Q）
- **AC1.1.6（直した）** Given 管理者 A がロール「営業」を削除しようとしている / When 同じ時に管理者 B が「営業」を利用者に割り当てる（重なりは待ち合わせで作る） / Then 両方の要求が終わった後、「営業」が消えていれば「営業」の割り当ては 0 件、割り当てが残っていれば「営業」は残っている。負けた側は業務の理由の code の 4xx で返り、500 にならない（Q）
- **AC1.1.7** Given ロール「営業」に割り当てが無い / When 管理者が「営業」の削除を選ぶ / Then 「営業」の名前と、その権限の設定も消えることを示す確かめの表示が出て、「やめる」を選ぶと何も変わらない（D）
- **AC1.1.8** Given ロール「営業」が利用者 2 人とグループ 1 つに割り当てられている / When 管理者が「営業」を削除しようとして拒否される / Then 拒否の文言で、割り当てが残っているため消せないことと、残りの数（利用者 2・グループ 1）が分かり、割り当ての画面へ移る手がかりがある。利用者の氏名・メールアドレスは拒否の応答に出ない（D）
- **AC1.1.9** Given 管理者がロールを作る・名前を変える / When 名前が空、空白だけ、長さの上限を1文字超える / Then 名前の誤りとして拒否され、ロールは変わらない。長さが上限ちょうどの名前は受け付ける（上限の値と大文字・小文字の扱いは機能設計で決め、決めた値の境界で確かめる。FR1.1）（Q）
- **AC1.1.10** Given 管理者がロールの作成・名前の変更の要求を送る / When 本文に許していない項目（ロールの ID・作成者・作成の時刻・組み込みの印など）を足す / Then 足した項目は反映されず、ロールの ID と作成者は変わらず、名前だけが要求の値になる（一括代入の防止。TP）（V・Q）
- **AC1.1.11** Given 「営業」が無い / When 管理者 A と B が同じ時に「営業」を作る（重なりは待ち合わせで作る） / Then 「営業」は1つだけ作られ、もう一方は名前の重なりとして 4xx で拒否される（500 にならない）（V）
- **AC1.1.12** Given 存在しないロールの ID / When 名前の変更・削除の API を呼ぶ / Then 存在しないロールとして拒否され、ほかのロールは変わらない（IDOR の防止。TP）（Q）
- **AC1.1.13** Given 利用者 A が覚えている作業ロールが「営業」で、A から「営業」の割り当てはすでに外れている / When 管理者が割り当ての無くなった「営業」を削除する / Then 削除は受け付けられ（覚えている作業ロールは削除を止めない）、A の次の要求の作業ロールは割り当ての中の最初のロール、割り当てが無ければ作業ロール無しになる（FR5.5）（V）
- **AC1.1.14** Given ロール「営業」がある / When 名前を今と同じ「営業」に変える / Then 変えるものが無いとして拒否され、監査に残る（SM4 C）
- **AC1.1.15** Given アプリのすべての API / When API の分類を確かめるテストを流す / Then すべての API が「公開・ログインだけ・管理者」のどれかに明示して分類されており、この Intent で足す API（ロール・グループ・権限・割り当て・import・export・作業ロール・自分の権限・業務のメニュー・準備中の画面）もすべて載る。分類の無い API を足すとこのテストが落ちる（NFR1.3・TP。分類の持ち方と仕組みの置き場は設計で決める）（V・Q）
- **AC1.1.16** Given この Intent で足す監査の種類の一覧 / When 一覧を全件読む単体テストを流す / Then すべての名前が 32 文字以内である。監査の対象の操作（ロール・権限・割り当て・グループ・メンバー・import・作業ロールの切り替え）ごとに、監査の行の操作した人・対象・変えた中身・結果が埋まり、パスワード・トークン・ハッシュ値を含まない（NFR5.1・FR12.1・FR12.3）（Q）
- **AC1.1.17** Given この Intent で足す管理の API / When API を呼ぶ / Then 今の管理の API と同じ指標（要求の数・誤りの数・時間）が出る（指標の名前とタグは結合テストで確かめる。NFR5.2）（Q）

### US1.2 ロールの権限を設定する 〔Must〕

P1 管理者として、ロールごとに、スキーマ→テーブル→カラムの順に主権限を、スキーマ→テーブルの順に補助権限を、大きく決めてから細かく上書きしたい。それは、1 万カラムの規模でも少ない設定で業務データの見せ方を決めるためだ。

出典: FR2.1〜FR2.4、FR3.1〜FR3.3、FR8.3、FR10.1、FR11.2・FR11.3、FR12.1、FR12.3、NFR1.2、NFR2.2、NFR4.1、NFR6.2、SM2、SM4、SM7

- **AC1.2.1（直した）** Given 適用済みの DSL（書式の版 2）がある / When 管理者がロール「営業」の権限の設定の画面を開く / Then DSL のスキーマ（この Intent では対象DB の設定のスキーマ1つ）が表示名つきで最上位に並び、スキーマを開くとテーブル、テーブルを開くとカラムが出る。スキーマを開く要求の応答はそのスキーマのテーブルだけを含み、カラムを含まない。テーブルを開く要求の応答はそのテーブルのカラムだけを含む（FR11.2）（Q）
- **AC1.2.2（直した）** Given ロール「営業」で スキーマ S を FULL、テーブル T を READ、カラム C を NONE に設定した / When 画面を見る / Then S の実効は FULL、T の実効は READ、T の別のカラムの実効は READ、C の実効は NONE と見える。明示の値と実効の値は、色だけでなく文字（例: 「継承: READ（テーブル T から）」）でも区別して見え、継承の値には継承の元の階層が分かる（D）
- **AC1.2.3** Given ロール「経理」で全階層が設定なし / When 画面を見る / Then すべてのカラムの実効の主権限は NONE、すべてのテーブルの実効の CREATE・DELETE は不可と見える
- **AC1.2.4（直した）** Given スキーマ S の CREATE を可・DELETE を設定なし、テーブル T の CREATE と DELETE を設定なし、テーブル U の CREATE を不可に設定した / When 画面を見る / Then T の実効の CREATE は可・DELETE は不可（CREATE と DELETE は互いに影響しない）、U の実効の CREATE は不可と見える。スキーマ S の CREATE を不可・テーブル V の CREATE を可にすると、V の実効の CREATE は可と見える。カラムには補助権限の欄が無い（Q）
- **AC1.2.5** Given 管理者が設定を変えて保存した / When 保存が終わる / Then 変えた対象と前後の値が監査に残り、その権限を作業ロールに選んでいる利用者の次の要求（保存の前に出したアクセストークンのまま）から効く
- **AC1.2.6（直した）** Given 適用済みの DSL が無い / When 権限の設定の画面を開く、または権限の設定を保存する API を呼ぶ / Then 画面には対象が無い旨の案内が出て設定はできず、保存の API は DSL が無い旨で拒否され、設定は変わらない（Q）
- **AC1.2.7（直した）** 〔Should〕 Given テーブル T に設定がある状態で、T の無い DSL を適用し直した / When 権限の設定の画面を開く / Then T の設定は「今の DSL に無い」と文字で分かるように出て、管理者が消せる。消すまでは設定が残る（Q）
- **AC1.2.8** Given ロール「営業」でテーブル T に READ の設定がある状態で、T の無い DSL を適用し直した / When 「営業」を作業ロールにする利用者の、T の実効の権限を解決の口で求める・業務のメニューを読む / Then T の設定は解決で使われず、口は T を NONE・不可と返し、T を指すメニューの項目は出ない。同じ名前の T がある DSL を適用し直すと、残っていた READ がまた効く（FR2.4・FR8.3）（Q）
- **AC1.2.9** Given 任意の3階層の主権限の設定（設定なし・NONE・READ・FULL の組）と、任意の2階層の補助権限の設定 / When 継承の解決の関数を性質ベースのテスト（jqwik）で確かめる / Then カラムの実効の主権限は「カラム・テーブル・スキーマの順に見て最初に設定なしでない値、すべて設定なしなら NONE」に等しく、テーブルの実効の補助権限は同じ順で、すべて設定なしなら不可に等しい。失敗時の乱数の種を記録する（NFR6.2）（Q）
- **AC1.2.10** Given 管理者が権限の設定を保存する / When 値に許していないもの（例: `ADMIN`）、カラムへの CREATE・DELETE、存在しないロールの ID を送る / Then 入力の誤りとして拒否され、設定は変わらない（FR2.1・FR3.1）（Q）
- **AC1.2.11** Given 管理者の印だけを欠く利用者 / When 木を開く・保存する API を呼ぶ / Then 403 が返る。未認証は 401、管理者は成功、停止中の管理者は通らない（Q）
- **AC1.2.12** Given 管理者 A と B がロール「営業」の同じテーブル T の主権限の設定の画面を開いている / When 2人が同じ時に T を違う値（A は READ、B は FULL）で保存する（重なりは待ち合わせで作る） / Then どちらの保存も成功し、T の値は後に確定した方の値になる。監査には2行とも、それぞれの前後の値つきで残る。500 にならない（後勝ち。SM2 A）（V・Q）
- **AC1.2.13** Given 管理者が権限の設定の画面でテーブル T を開いた後に、T の無い DSL が適用された / When T のカラムを開く、または T の値を保存する / Then 500 にならず、「今の DSL に無い」旨で拒否されるか、名前で持つ設定として保存される（どちらにするかは機能設計で決め、決めた側の動作を明示したテストにする）（V）
- **AC1.2.14** Given 管理者がロール「営業」の権限の設定の画面を開いている / When キーボードだけで木を開閉し、カラム C の主権限を選ぶ / Then 開閉の状態（`aria-expanded`）が分かり、値を選ぶ部品の読み上げの名前に対象（例: 「カラム C の主権限」）が含まれる（D）
- **AC1.2.15** Given 管理者が設定を変えて、まだ保存していない / When 別のロールや別の画面へ移ろうとする / Then 保存していない変更があることが分かり、移るか留まるかを選べる。移ると保存していない変更は保存されない（保存の単位（階層ごとか、まとめてか）は画面の段で決める）（D）
- **AC1.2.16** 〔Should〕 Given ロール「営業」でテーブル T の実効の主権限が NONE、テーブル U が READ / When 権限の設定の画面を見る / Then テーブルごとに業務のメニューに出るかが示され、T は「出ない」、U は「出る」と色だけでなく文字で分かる。表示は実効の主権限から求め、新しいデータを持たない（FR10.1 の判定と同じ。SM7 A）（D）
- **AC1.2.17** Given ロール「営業」のテーブル T が READ / When T を READ のまま保存する（変わる点の無い保存） / Then 変えるものが無いとして拒否され、監査に残る（SM4 C）
- **AC1.2.18** Given NFR2.1 の上限の規模（1 ロールで最大 1 万カラム） / When 木の1階層を開く API と保存する API を繰り返し呼ぶ / Then 応答時間の 95 パーセンタイルが 1 秒以内である（測り方は NFR 要件の段で決める。NFR2.2）（Q）

## 群2 グループと割り当て

### US2.1 グループで利用者をまとめる 〔Must〕

P1 管理者として、利用者をグループにまとめたい。それは、人が増えたり異動したりしても、グループのメンバーを変えるだけでロールを渡せるようにするためだ。

出典: FR4.1、FR4.1a、FR4.3〜FR4.5、FR5.5、FR11.1、FR12.1、NFR1.2、NFR1.4、NFR1.6、NFR3.1、NFR4.1、SM4

- **AC2.1.1** Given 管理者がグループの管理の画面を開いている / When 「営業部」というグループを作り、利用者 A と B をメンバーに足す / Then 「営業部」のメンバーに A と B が出て、作成とメンバーの足しが監査に残る
- **AC2.1.2（直した）** Given 「営業部」がすでにある / When 同じ名前のグループを作る、または別のグループの名前を「営業部」に変える / Then 名前の重なりとして拒否される。名前が空・空白だけ・長さの上限を1文字超えるときも拒否され、上限ちょうどは受け付ける（AC1.1.9 と同じ形）（Q）
- **AC2.1.3** Given 「営業部」にメンバーか、ロールの割り当てが1つでも残っている / When 「営業部」を削除する / Then 拒否され、グループ・メンバー・割り当ては変わらない
- **AC2.1.4** Given 「営業部」にメンバーも割り当ても無い / When 「営業部」を削除する / Then 削除され、監査に残る
- **AC2.1.5（直した）** Given 管理者 A が「営業部」を削除しようとしている / When 同じ時に管理者 B が「営業部」にメンバーかロールの割り当てを足す（重なりは待ち合わせで作る） / Then 両方の要求が終わった後、「営業部」が消えていればそのメンバーと割り当ては 0 件、メンバーか割り当てが残っていれば「営業部」は残っている。負けた側は業務の理由の code の 4xx で返り、500 にならない（守り方は機能設計で決める。要件の確かめの R-08）（Q）
- **AC2.1.6（直した）** Given 管理者の印だけを欠く利用者がログインしている / When グループの作成・名前の変更・削除・メンバーの変更の API を呼ぶ / Then 403 が返り、グループは変わらない。未認証は 401、管理者は成功、停止中の管理者は通らない。表のパラメーターのテストで書く（Q）
- **AC2.1.7** Given グループ「営業部」にメンバー 3 人がいる / When 管理者が「営業部」を削除しようとして拒否される / Then 拒否の文言で、メンバーか割り当てが残っているため消せないことと、残りの数が分かる（AC1.1.8 とそろえる）（D）
- **AC2.1.8** Given 利用者が 50 人いる / When 管理者がグループにメンバーを足す / Then 氏名かメールアドレスの一部で候補を絞って選べ、すでにメンバーの利用者は候補にそれと分かるように出る（D）
- **AC2.1.9** Given 利用者 A がグループ「経理部」経由でだけ「経理」を持ち、作業ロールが「経理」 / When 管理者が A を「経理部」から外す / Then A の次の要求（外す前に出したアクセストークンのまま）で、「経理」は A のロールから消え、作業ロールは残りのロールの最初、残りが無ければ作業ロール無しになる（FR4.3・FR4.4・FR5.5）（Q）
- **AC2.1.10** Given 利用者 A に「営業」が直接とグループ「営業部」経由の両方から割り当てられ、作業ロールが「営業」 / When 管理者が A を「営業部」から外す / Then A は直接の割り当てで「営業」を持ち続け、作業ロールは「営業」のまま（Q）
- **AC2.1.11** Given 管理者がグループのメンバーを足す・外す / When 存在しない利用者の ID・存在しないグループの ID を指定する、または招待中で登録が終わっていない人を指定しようとする / Then 拒否され、メンバーは変わらない。招待中の人は利用者の行が無いため、メンバーの候補にも出ない。利用停止の利用者は足せる（IDOR の防止。要件との差 D7）（V・Q）
- **AC2.1.12** Given グループのメンバーの一覧の API / When 管理者が一覧を読み、メンバーを足し・外す / Then 応答に、パスワードのハッシュ値・招待のトークンのハッシュ値・ロックの判定の内部の値が含まれない。TRACE のログを有効にしても、メンバーのメールアドレス・氏名と候補の絞り込みの文字がアプリのログに出ない（`*SecretLeakIT` と同じ形。NFR1.6）（V・Q）
- **AC2.1.13** Given 利用者 A が「営業部」のメンバーで、B はメンバーでない / When 管理者が A を「営業部」に重ねて足す、B を「営業部」から外す、「営業部」の名前を今と同じ名前に変える / Then それぞれ変えるものが無いとして拒否され、監査に残る（SM4 C）

### US2.2 利用者とグループにロールを割り当てる 〔Must〕

P1 管理者として、利用者やグループにロールを割り当て・外したい。それは、利用者が仕事に合ったロールを作業ロールに選べるようにするためだ。

出典: FR4.2〜FR4.5、FR5.5、FR11.1、FR12.1、NFR1.2、NFR1.4、NFR1.6、NFR3.1、NFR4.1、C1、SM4、SM5

- **AC2.2.1** Given ロール「営業」と「経理」がある / When 管理者が利用者 A に「営業」を、グループ「経理部」（A が属する）に「経理」を割り当てる / Then A のロールは「営業」と「経理」の2つになり、割り当てが監査に残る
- **AC2.2.2** Given A に「営業」が直接とグループ経由の両方から割り当てられている / When A のロールを見る / Then 「営業」は1つとして扱われる
- **AC2.2.3（直した）** Given A のロールが「営業」だけで、作業ロールが「営業」 / When 管理者が A から「営業」を外す / Then 外す前に出した A のアクセストークンのままの次の要求で、A の作業ロールは無くなり、権限の解決の口と業務のメニューの API の結果はどちらも実効の権限がすべて NONE・不可の結果になる（Q）
- **AC2.2.4** Given A のロールが「営業」と「経理」で、作業ロールが「営業」 / When 管理者が A から「営業」を外す / Then A の次の要求で、作業ロールは割り当ての中の最初のロール（「経理」）になる
- **AC2.2.5（直した）** Given 管理者の印だけを欠く利用者 B がログインしている / When 割り当て・外しの API を、自分に対しても他人に対しても呼ぶ / Then 403 が返り、どの割り当ても変わらない。未認証は 401、管理者は成功、停止中の管理者は通らない（初稿の「403 か入力の無視・拒否」を入口ごとに分け、管理の API の入口をこの基準、管理の API の外の入口を AC2.2.11 にした）（Q）
- **AC2.2.6（直した）** Given 管理者が利用者の割り当ての画面を開く / When 応答を見る、TRACE のログを有効にして読む / Then 応答に、パスワードのハッシュ値・招待のトークンのハッシュ値・ロックの判定の内部の値が含まれず、利用者のメールアドレス・氏名がアプリのログに出ない（NFR1.6）
- **AC2.2.7** Given 利用者 A に「営業」が直接と、グループ「営業部」経由の両方から割り当てられている / When 管理者が A の割り当ての画面を見る / Then 「営業」は1つとして出て、その出どころ（直接・グループ「営業部」経由）が両方分かる（D）
- **AC2.2.8** Given AC2.2.7 の状態 / When 管理者が A から直接の「営業」を外す / Then 外した後の表示で、A のロールに「営業」がグループ経由で残ることが分かる（D）
- **AC2.2.9** 〔Should〕 Given 利用者 A の作業ロールが「営業」で、「営業」の割り当ては直接の1つだけ / When 管理者が A から「営業」を外そうとする / Then 確かめの表示で、A の作業ロールが変わる（または無くなる）ことが分かる（管理者への表示で、A 本人への案内ではない。SM8 B とは別）（D）
- **AC2.2.10** Given 管理者が割り当てを足す・外す / When 存在しないロールの ID・存在しない利用者やグループの ID、または別の利用者に付いた割り当ての ID に差し替えて送る / Then 拒否され、どの割り当ても変わらない（IDOR の防止。TP）（V・Q）
- **AC2.2.11** Given 管理者の印だけを欠く利用者 B がログインしている / When 管理の API の外の要求（`PUT /api/me/preferences` など）の本文に、ロール・グループ・作業ロール・管理者の印の項目を足して送る / Then 要求は今の決まりどおりに扱われ（状態コードは今の動作）、読み直した B のロール・グループ・作業ロール・管理者の印は変わっていない（一括代入の防止。SL）（V・Q）
- **AC2.2.12** Given 管理者 M の作業ロールでは業務データがすべて NONE / When M が全スキーマを FULL にしたロールを、自分にも他人にも割り当てる / Then どちらも受け付けられる（管理の操作の可否は管理者の印だけで決まり、操作する人の業務データの権限には縛られない。SM5 A）（Q）
- **AC2.2.13** Given 最後の有効な管理者 M がロールを持つ / When M が自分のロールをすべて外す / Then 受け付けられ、M の作業ロールは無くなるが、M の管理の API は成功のまま。最後の有効な管理者の保護（印を外す・利用を止める操作の拒否）は今までどおり印で数えて働く（C1）（V・Q）
- **AC2.2.14** Given 管理者の印を持たず、全スキーマを FULL にしたロールを作業ロールにする利用者 / When 今ある管理の API（利用者・招待・DSL など）を呼ぶ / Then すべて 403 が返る（ロールで管理の権限は増えない。C1）（Q）
- **AC2.2.15** Given 利用者 A に「営業」が直接割り当てられ、「経理」は割り当てられていない / When 管理者が A に「営業」を重ねて直接割り当てる、A から「経理」を外す / Then それぞれ変えるものが無いとして拒否され、監査に残る（SM4 C）
- **AC2.2.16** Given 招待中で登録が終わっていない人と、利用停止の利用者がいる / When 管理者が割り当ての対象を選ぶ / Then 招待中の人は利用者の行が無いため候補に出ず、割り当てられない。利用停止の利用者には割り当てられ、その応答に AC2.2.6 の値は含まれない（要件との差 D7）（V）

## 群3 権限の設定の受け渡し

### US3.1 権限の設定を YAML で受け渡す 〔Must〕

P1 管理者として、ロールとその権限の設定を YAML で書き出し、別の環境で読み込みたい。それは、検証用の環境で整えた権限を、本番の環境で一つずつ設定し直さずに済ませるためだ。

出典: FR7.1〜FR7.5、FR12.1、FR12.3、FR12.4、NFR1.2、NFR1.5、NFR2.4、NFR3.2、NFR4.1、SM4

- **AC3.1.1** Given ロール「営業」「経理」に権限の設定がある / When 管理者が export する / Then 2つのロールとその主権限・補助権限の設定（スキーマ・テーブル・カラムの名前で持つ）だけを含む YAML が得られる（グループ・メンバー・割り当ては含まない）。DSL が無くても今ある設定を書き出せる
- **AC3.1.2** Given 「営業」がある環境で、「営業」と「総務」を含む YAML を読み込む / When 確かめの一覧を見る / Then 「総務」は作る、「営業」は設定が変わる対象と前後の値が一覧に出て、この時点では設定は変わっていない
- **AC3.1.3（直した）** Given 確かめの一覧を見た / When 適用する / Then 「総務」が作られ、「営業」の設定がファイルの内容に置き換わり（ファイルの「営業」に無い対象の設定は、適用の後に「設定なし」になる。足し合わせではない）、ファイルに無いロール「経理」は残る。適用が監査に残る（V）
- **AC3.1.4（直した）** Given 確かめの一覧を見ている間に、別の管理者が「営業」の設定を変えた、「営業」を削除した、ファイルにあるロールの名前で別のロールを作った、または DSL を適用し直した / When 適用する / Then どの場合も確かめた内容と違うとして拒否され、設定は別の管理者の操作の後の状態のまま残る（FR7.3a）（V・Q）
- **AC3.1.5** Given 適用済みの DSL が無い / When YAML を読み込む / Then DSL が無いとして拒否され、ロールと設定は変わらない
- **AC3.1.6** Given 適用済みの DSL にテーブル X が無く、YAML に X の設定がある / When 確かめの一覧を見る / Then X は「今の DSL に無い」と分かるように出て、適用すると名前で持つ設定として残る
- **AC3.1.7（直した）** Given 大きさ・入れ子の深さ・別名の数のそれぞれが上限ちょうどの YAML と、上限を1つ超える YAML / When 読み込む / Then 上限ちょうどは受け付けられ、上限を1つ超えると拒否される。別名の展開の爆発で処理が止まらず、時間の上限内に拒否が返る（上限の値は設計で決める）（初稿の基準を、境界・タグと重複キー・応答の形に分け、残りを AC3.1.13 にした）（V・Q）
- **AC3.1.8（直した）** Given テストで、適用の途中の書き込みを失敗させる（例: 何件目かの対象の保存で失敗を起こす） / When 適用する / Then ロールと設定の全件が読み込む前と同じで、適用の監査の行が成功として残らない（NFR3.2）（Q）
- **AC3.1.9** Given 2 つのロールで数千の対象が変わる YAML を読み込んだ / When 確かめの一覧を見る / Then まずロールごとの要約（作る・変わる対象の数・「今の DSL に無い」の数）が出て、ロールごとに開いて変わる対象と前後の値を見られる。「今の DSL に無い」は色だけでなく文字で分かる（D）
- **AC3.1.10** Given 確かめの一覧を見ている / When 適用を選ぶ / Then 置き換わるロールの数と、ファイルに無いロールは残ることを示す確かめの表示が出る。適用の後は、作った・置き換えたロールの数が結果として分かる（D）
- **AC3.1.11** Given AC3.1.4 で適用が拒否された / When 拒否の表示を見る / Then 確かめた後に設定が変わったため確かめからやり直すことが分かり、同じファイルで確かめをやり直す手がかりがある（D）
- **AC3.1.12** Given YAML の形は正しいが中身が誤り（許していない権限の値、カラムへの CREATE・DELETE、ロールの名前が空・長さの上限を超える、同じロールの名前がファイルの中で2回、知らない項目） / When 読み込む / Then 確かめの段で拒否され、誤りの位置（ロールの名前・対象、または行）と種類が分かり、設定は変わらない（D・V・Q）
- **AC3.1.13** Given 任意の型を作るタグ（`!!` など）、重複キー、外部の参照を含む YAML / When 読み込む / Then タグを含むと拒否され型は作られず、重複キーは誤りになり後の値で黙って上書きされず、外部の参照は取りに行かない。AC3.1.7・AC3.1.12・この基準のどの拒否も Problem Details で返り、YAML の部品の例外のメッセージを含まず、設定は変わらない（FR7.4・TP）（Q）
- **AC3.1.14** Given ある環境で export した YAML / When 同じ環境で変更せずに読み込み、確かめの一覧を見て適用する / Then 確かめの一覧に変わる点が無く（書き出しと読み込みの往復で設定が変わらない）、適用は変えるものが無いとして拒否され、監査に残る（SM4 C）（Q）
- **AC3.1.15** Given ロール「営業」に今の DSL に無いテーブル X の設定が残っている / When export する / Then X の設定も名前のまま書き出される（FR7.3b の「今ある設定を書き出す」の読み）（V）
- **AC3.1.16** Given 管理者の印だけを欠く利用者 / When export・確かめ・適用の API を呼ぶ / Then 403 が返る。未認証は 401、管理者は成功、停止中の管理者は通らない（Q）
- **AC3.1.17** Given NFR 要件の段で決めた YAML の大きさの上限ちょうどの YAML / When 確かめと適用を行う / Then 応答時間が NFR 要件の段で決めた目標以内である（目標の値と測り方は NFR 要件の段で決める。NFR2.4）（Q）

## 群4 作業ロールと自分の権限

### US4.1 作業ロールを切り替える 〔Must〕

P2 一般の利用者として、自分のロールの中から今の仕事に合ったロールを選び、いつでも切り替えたい。それは、そのロールで見てよい業務データだけを扱うためだ。

出典: FR5.1〜FR5.6、FR8.1〜FR8.3、FR12.1、NFR1.2〜NFR1.4、NFR2.2、NFR3.1、NFR4.1、NFR5.2、NFR6.2、SM4、SM8

- **AC4.1.1** Given 利用者のロールが「営業」と「経理」で、作業ロールが「営業」 / When どの画面からでも作業ロールを「経理」に切り替える / Then 次の要求から実効の権限とメニューが「経理」の設定で決まり、切り替えが監査に残る
- **AC4.1.2** Given 作業ロールを「経理」にしてログアウトした / When 次にログインする / Then 作業ロールは「経理」で始まる
- **AC4.1.3** Given 自分に割り当てられていないロール「総務」がある / When 要求の本文を変えて「総務」に切り替えようとする / Then 拒否され、作業ロールは変わらない
- **AC4.1.4（直した）** Given ロールが1つも無い利用者 / When 画面を開く / Then 作業ロールが無いことと、ロールの割り当ては管理者に頼むことが分かる案内が出る。業務データの実効の権限はすべて NONE・不可で、ログイン・自分の設定（管理者なら管理画面）は今までどおり使える（D）
- **AC4.1.5（直した）** Given 利用者が作業ロールを切り替えようとしている / When 同じ時に管理者がそのロールを外す（重なりは待ち合わせで作る） / Then 両方の要求が終わった後、利用者の作業ロールは割り当ての中のロールか、無しである。次の要求の実効の権限は、その作業ロール（無しなら NONE・不可）で決まる。負けた側は 4xx で返り、500 にならない（Q）
- **AC4.1.6** Given 管理者の印を持つ利用者で、作業ロールが「経理」 / When 業務データの実効の権限を求める / Then 管理者であっても「経理」の設定で決まる（管理画面の操作の可否は印で決まり、作業ロールで変わらない）
- **AC4.1.7** Given 利用者のロールが「営業」と「経理」で、作業ロールが「営業」 / When どの画面を開いても / Then 今の作業ロールの名前が見え、読み上げでも「作業ロール: 営業」のように分かる（D）
- **AC4.1.8** Given AC4.1.7 の状態 / When キーボードだけで作業ロールを「経理」に切り替える / Then 切り替えた結果が読み上げに伝わり（例: 「作業ロールを経理に切り替えました」）、フォーカスは切り替えの部品に残り、メニューは「経理」の権限で出し直される（D）
- **AC4.1.9** Given ロールが「営業」の1つだけの利用者 / When 画面を見る / Then 作業ロール「営業」は見えるが、切り替える先が無いことが分かる（選べない項目を並べない）（D）
- **AC4.1.10** Given 作業ロール「営業」で、テーブル T（「営業」で READ）の準備中の画面を開いている / When 作業ロールを、T が NONE の「経理」に切り替える / Then 今の画面は権限が無い旨の表示になり（AC5.1.4 と同じ）、T の表示名は出ない（D）
- **AC4.1.11** Given 存在しないロールの ID / When その ID で作業ロールを切り替える / Then 拒否され、作業ロールは変わらない（IDOR の防止）（Q）
- **AC4.1.12** Given 利用者 A と B がいる / When A が作業ロールの切り替えの要求の本文に、B を指す値を足して送る / Then B の作業ロールは変わらない（切り替えの API は利用者を指す値を受け取らず、主体は要求の文脈から読む）（Q）
- **AC4.1.13** Given 作業ロールが「営業」 / When 作業ロールを「営業」に切り替える / Then 何も変えない成功として返り、作業ロールは「営業」のままで、監査には残らない（SM4 C）
- **AC4.1.14** Given 利用者 A の覚えている作業ロールが「営業」で、A がログインしていない間に管理者が A から「営業」を外し、続けて割り当ての無くなった「営業」を削除した / When A が次にログインする / Then 削除は受け付けられており、A の作業ロールは割り当ての中の最初のロール、割り当てが無ければ無しで始まり、500 にならない（FR5.4・FR5.5）（Q）
- **AC4.1.15** Given 覚えている作業ロールが、割り当ての変更で自分のロールでなくなった / When 次の要求が来る / Then 作業ロールは FR5.5 のとおり置き換わるが、作業ロールの切り替えとしては監査に残らない（利用者の操作ではないため）（V）
- **AC4.1.16** Given ロールが3つ以上ある利用者の覚えている作業ロールが外れた / When 次の要求が来る / Then 作業ロールは機能設計で決めた順序の最初のロールになる（2つの組では順序の誤りを見分けられないため、3つ以上の組で確かめる）（Q）
- **AC4.1.17** Given ロールが「営業」と「経理」の利用者が作業ロールを「経理」に切り替えた / When ログインし直す・トークンを更新する / Then ログインと更新の応答（または作業ロールを返す API）に、作業ロール「経理」と、切り替えられるロールの一覧が入る（応答の形は設計で決める）（V）
- **AC4.1.18** Given 利用者の作業ロールでテーブル T が READ / When アプリの中の解決の口に、その利用者と、今の DSL に無いテーブル・カラムの名前を渡す / Then NONE・不可が返る。同じ口は、作業ロールの切り替え・割り当ての外し・権限の保存の直後の呼び出しで新しい結果を返し、トークンや画面から送られた値を使わない（FR8.1〜FR8.3）（V）
- **AC4.1.19** Given 作業ロールの切り替えの API / When 未認証で呼ぶ、停止中の利用者が呼ぶ / Then 未認証は 401、停止中の利用者は通らない（API の分類は「ログインだけ」）（V・Q）
- **AC4.1.20** Given NFR2.1 の上限の規模 / When 作業ロールの切り替えの API を繰り返し呼ぶ / Then 応答時間の 95 パーセンタイルが 1 秒以内で、今の管理の API と同じ指標（要求の数・誤りの数・時間）が出る（NFR2.2・NFR5.2）（Q）
- **AC4.1.21** Given 任意の作業ロールと、作業ロール以外のロールの任意の足し外し / When 実効の権限を求める関数を性質ベースのテスト（jqwik）で確かめる / Then 作業ロールを変えない限り、作業ロール以外のロールを足しても外しても実効の権限は変わらない。失敗時の乱数の種を記録する（TP の例「役割を足しても権限は減らない」を、合算しない作業ロールの形に読み替えた。SL）（Q）

### US4.2 自分の実効の権限を確かめる 〔Should〕

P2 一般の利用者として、今の作業ロールで、どのテーブル・カラムを見られる・直せるのかを確かめたい。それは、メニューや項目が見えないときに、権限のせいかどうかを自分で分かるようにするためだ。

出典: FR6.1・FR6.2、FR10.1、NFR1.2〜NFR1.4、NFR4.1

- **AC4.2.1** Given 作業ロールが「営業」 / When 自分の権限の画面を開く / Then DSL のスキーマ・テーブル・カラムごとの実効の主権限と、スキーマ・テーブルごとの実効の CREATE・DELETE が表示名つきで見える
- **AC4.2.2** Given 作業ロールを「経理」に切り替えた / When 自分の権限の画面を開き直す / Then 「経理」の実効の権限が見える
- **AC4.2.3（直した）** Given 利用者 A がログインしている / When 自分の権限の API に、利用者 B を指す値（パラメーター・本文）を足して送る / Then 足した値は使われず、応答は A 自身の作業ロールの権限だけで、B の権限は含まれない（API は利用者を指す値を受け取らず、主体は要求の文脈から読む）（初稿の「受け付けられず」を1つの結果にした）（V・Q）
- **AC4.2.4** Given 作業ロールが無い / When 自分の権限の画面を開く / Then すべて NONE・不可で、作業ロールが無い旨が分かる
- **AC4.2.5** Given 自分の権限の API / When 未認証で呼ぶ、停止中の利用者が呼ぶ / Then 未認証は 401、停止中の利用者は通らない（API の分類は「ログインだけ」）（Q）
- **AC4.2.6** Given 作業ロールが「営業」 / When 自分の権限の画面を見る / Then テーブルごとに、業務のメニューに出るか（実効の主権限が NONE でないか）が分かり、READ・FULL・NONE は色だけでなく文字で分かる（D）
- **AC4.2.7** Given 業務のメニューの項目が1つも出ていない利用者 / When ホームの画面を見る / Then 表示できる業務のメニューが無いことと、自分の権限の画面へ移る手がかりが出る（D）

## 群5 メニューをたどる

### US5.1 業務のメニューをたどって画面へ移る 〔Must〕

P2 一般の利用者として、左のメニューで業務のまとまりを開き、扱うテーブルの画面へ移りたい。それは、平らな一覧から探さずに、業務の流れに沿ってたどるためだ。

出典: FR8.1、FR8.3、FR9.1〜FR9.3、FR9.5、FR9.6、FR10.1〜FR10.5、NFR1.1〜NFR1.3、NFR2.2、NFR4.1〜NFR4.3、NFR6.2

- **AC5.1.1（直した）** Given 適用済みの DSL の `menus` に「販売」＞「受注」＞「受注明細（テーブル）」の木がある / When 利用者がサイドバーで「販売」「受注」を開く / Then 「受注明細」が出て、開閉の状態（`aria-expanded`）が分かり、キーボードだけでたどれる。開閉は入れ子のリストと開閉のボタン（Enter・Space）で行い（ARIA の `tree` の役割と矢印のキーの移動は使わない。今の `DslMenuTree` と同じ形）、開閉のボタンの読み上げの名前にまとまりの表示名が含まれる。make-you-chic-ui の部品に頼る振る舞いも、このリポジトリの画面のテストで確かめる（TP）（D・Q）
- **AC5.1.2（直した）** Given 作業ロールで「受注明細」のテーブルの実効の主権限が NONE / When メニューを見る / Then 「受注明細」は出ず、子がすべて出ないまとまり「受注」も出ない（カラムに明示の READ があっても、判定はテーブルの階層の値だけ）。テーブルと子の両方を持つ項目は、テーブルが READ 以上ならテーブルの画面へ移れるまとまりとして出し、テーブルが NONE で子が1つでも見えれば、選んでもテーブルの画面へ移らないまとまりとして出し、テーブルが NONE で子がすべて見えなければ出さない（SL）（V）
- **AC5.1.3** Given 「受注明細」の実効が READ / When 「受注明細」を選ぶ / Then 「この画面は準備中です」と「受注明細」の表示名を出す画面へ移り、メニューでは今の項目（`aria-current`）が分かる
- **AC5.1.4（直した）** Given 作業ロールで NONE のテーブルの準備中の画面の道、または今の DSL に無いテーブルの道を、直接開く / When 画面を開く / Then どちらも同じ「権限が無い」表示になり、表示名などテーブルの中身は出ず、テーブルの有無を見分けられない（サーバー側で解決の口を使って確かめる。FR8.3・FR10.4）（D・V・Q）
- **AC5.1.5（直した）** Given 作業ロールを切り替えた / When 次にメニューを読む / Then 新しい作業ロールの権限で絞った業務のメニューが出る。業務のメニューを返す API は、権限の無い項目と管理のメニューを応答に含めない。API の分類は「ログインだけ」で、未認証は 401、停止中の利用者は通らない（FR10.5）（Q）
- **AC5.1.6** Given 適用済みの DSL が無い、または `menus` が空 / When メニューを見る / Then 業務のメニューは出ない（管理者には管理のメニューが出る）
- **AC5.1.7（直した）** Given DSL のメニューの label に `<script>` などのタグや `<`・`>`・`&`・`"`・`'` を含め、icon に許していない名前がある / When メニューを見る / Then label は文字として出て（HTML として描かない）、icon は許した名前の一覧に無いため既定のアイコンになる（Q）
- **AC5.1.8** Given 利用者が「受注明細」の準備中の画面の道を直接開く、または再読み込みする / When サイドバーを見る / Then 「受注明細」の祖先（「販売」「受注」）が開いた状態で出て、「受注明細」が今の項目（`aria-current`）として分かる（D）
- **AC5.1.9** Given 利用者が「販売」を開いた状態で別の画面へ移る / When 移った先でサイドバーを見る / Then 開閉の状態は保たれている（移るたびに閉じない）（D）
- **AC5.1.10** Given 深さが上限ちょうどのメニューと、40 文字の表示名の項目がある / When サイドバーを見る / Then 各段の入れ子が字下げなどで見分けられ、長い表示名は省略されても全体を読み上げと表示（折り返しか、省略の上での全文の表示）で確かめられ、サイドバーの外へはみ出さない。画面全体に横のスクロールが出ない（D）
- **AC5.1.11** Given 利用者がメニューを読んだ後に、管理者がテーブル T を利用者の作業ロールで NONE にした / When 利用者が古いメニューの T を選ぶ / Then 権限が無い旨の表示になり（AC5.1.4 と同じ）、メニューは読み直されて T が出なくなる（D）
- **AC5.1.12** Given 表示の言語を英語にした / When サイドバーを見る / Then ナビゲーションの領域の読み上げの名前と、開閉のボタンの名前も英語になる（今の `Sidebar` の `aria-label` は日本語に固定のため、make-you-chic-ui への依頼の口に入れる。KB K-36）（D）
- **AC5.1.13** Given DSL の `menus` の table の名前に `/`・`..`・`?`・`#`・`%`・空白・`javascript:`・`https://` を含む / When 項目を選ぶ / Then 名前はエンコードされ、移る先はアプリの中の準備中の画面の決めた形の道から外れない（別の画面・外部の URL・`javascript:` の道を作らない。FR9.6・TP）（V・Q）
- **AC5.1.14** Given 業務のメニューを権限で絞る関数に、DSL の `tables` に無いテーブルを指す項目を渡す / When 絞る / Then その項目は絞った木に出ない（解決の口が NONE を返すため。FR8.3）（Q）
- **AC5.1.15** Given 任意のメニューの木と任意の権限の組 / When 業務のメニューを権限で絞る関数を性質ベースのテストで確かめる / Then 絞った木には実効 NONE のテーブルだけを指す項目が無く、子の無いまとまりが無く、残った項目の親子と並びは元の木と同じ。画面側は fast-check、サーバー側で絞る関数は jqwik で同じ性質を当て、失敗時の乱数の種を記録する（NFR6.2）（V・Q）
- **AC5.1.16** Given 上限の深さまで展開し、長い名前の項目を含むサイドバー / When 実際のブラウザで axe を流す / Then ブランドカラーとテーマのすべての組で違反が無く、開いたメニューが画面の中に収まる（NFR4.2・TP・PM）（Q）
- **AC5.1.17** Given 作業ロールが無い利用者 / When 業務のメニューの API を呼ぶ / Then 誤りではなく空の木が返る（V）
- **AC5.1.18** Given NFR2.1 の上限の規模 / When 業務のメニューを返す API を繰り返し呼ぶ / Then 応答時間の 95 パーセンタイルが 1 秒以内である（NFR2.2）（Q）

### US5.2 メニューの深さの上限を守る 〔Must〕

P1 管理者として、深すぎるメニューの DSL を投入したときに、DSL の検証で教えてほしい。それは、利用者のサイドバーが読めないほど深くなるのを防ぐためだ。

出典: FR9.4、SM3

- **AC5.2.1** Given メニューの深さが上限ちょうどの DSL / When 投入する / Then 受け付けられる
- **AC5.2.2** Given メニューの深さが上限を1段超える DSL / When 投入する / Then 検証の誤りとして拒否され、誤りの位置が分かる（上限の値は設計で決める。目安 5 段）
- **AC5.2.3** Given 書式の版 2 で、上限を超える深さのメニューを持つ DSL が適用中として保存されている（例: 後の版で上限を下げた場合） / When アプリを起動する / Then 起動は止まらず、起動時の読み直しではメニューの深さだけを検証から外して DSL を適用中として読み、深すぎる枝は画面に出さず、警告のログ（DSL の本文と接続情報を含まない）を出す。権限の対象とメニューの上限までの枝は使える（SM3 A。この Intent の版上げのときに適用中の版 1 の DSL は、書式の版の誤りで外れるため、この基準ではなく AC6.1.6 のとおり DSL が無い扱いになる）（V）
- **AC5.2.4** Given DSL の履歴に、上限を超える深さのメニューを持つ版 2 の DSL がある / When その版を復元する / Then 検証の誤り（業務の誤りの 4xx）として拒否され、今の適用中の DSL は変わらず、500 にならない（SM3 A）（V・Q）
- **AC5.2.5** Given AC5.2.3 の状態 / When 適用中の DSL をダウンロードする / Then 500 にならない（本文を返すか業務の誤りで拒否するかは機能設計で決め、決めた側の動作を明示したテストにする）（V）

### US5.3 管理のメニューを今までどおり使う 〔Must〕

P1 管理者として、業務のメニューと並べて、管理のメニュー（管理・DSL・招待・利用者・ロール・グループなど）を今までどおり使いたい。それは、業務の権限とは別に、管理の仕事をすぐ始めるためだ。

出典: FR9.1、FR10.3、FR10.5、NFR4.1、C1

- **AC5.3.1** Given 管理者がログインしている / When サイドバーを見る / Then 業務のメニューと並んで管理のメニューが出て、管理のメニューにはロール・グループの画面の入口もある
- **AC5.3.2** Given 管理者でない利用者がログインしている / When サイドバーを見る / Then 管理のメニューは出ない（管理の API は 403 のまま）
- **AC5.3.3** Given 管理者の作業ロールで、業務のどのテーブルも NONE / When サイドバーを見る / Then 業務のメニューは出ないが、管理のメニューは出る
- **AC5.3.4** Given 管理者で、作業ロールで業務のメニューの項目がある / When サイドバーを見る / Then 業務のメニューと管理のメニューが見出し（例: 「業務」「管理」）で分かれ、見出しは読み上げでもまとまりの名前として分かる（2つの並べ方は画面の段で決める）（D）
- **AC5.3.5** Given 管理者でない利用者 / When サイドバーを見る / Then 管理の見出しは出ない（空の見出しを残さない）。業務のメニューの項目も無いときは、業務の見出しも出ない（D）
- **AC5.3.6** Given 管理者が作業ロールを切り替えた、または自分からロールをすべて外した / When サイドバーを見て、管理の API を呼ぶ / Then 管理のメニューは出たままで、管理の API も成功のまま（作業ロールで管理の可否は変わらない。C1）（V）
- **AC5.3.7** Given 管理者の印を外された利用者（前の Intent の操作） / When 次の要求でサイドバーを読む / Then 管理のメニューは出ず、業務のメニューは作業ロールの権限で出る（印とロールは独立している）（Q）

## 群6 DSL のスキーマ

### US6.1 DSL にスキーマの階層を持たせる 〔Must〕

P1 管理者として、DSL にスキーマの階層（スキーマ名・表示名と、その下のテーブル）を書きたい。それは、権限をスキーマ→テーブル→カラムの順に大きく決められるよう、権限の対象のスキーマを DSL から得るためだ。

出典: SM1 B・SF2 A・SF3 C（要件に無い DSL の変更。要件との差 D1・D2）、FR2.1、FR2.3、FR3.1、FR3.3、C2、C6、V の F-1・F-3

この Intent の範囲: DSL に書式の版 2 を足し、スキーマの階層を持たせる。書式（JSON Schema）は複数のスキーマを並べられる形にするが、中身は対象DB の設定のスキーマ1つとする（SF2 A）。DSL は版 2 だけを受け付け、版 1 は読み替えない（SF3 C）。

- **AC6.1.1** Given 書式の版 2 の DSL に、スキーマ（スキーマ名・表示名と、その下のテーブル）がある / When 投入し、プレビューを経て適用する / Then 権限の設定の画面と自分の権限の画面に、そのスキーマが表示名つきで最上位に出て、その下にテーブルとカラムが出る
- **AC6.1.2** Given 書式の版 1 の DSL（スキーマの無い今の形） / When 投入する / Then 書式の版の誤りとして検証で拒否され（Problem Details の 4xx）、版 2 で書く必要があることが分かる。プレビューと適用中の DSL は変わらない
- **AC6.1.3** Given 対象DB の設定のスキーマ名が S / When 既定の DSL を生成する / Then 書式の版 2 で、スキーマ S（名前は設定のスキーマ名）の下に対象DB のテーブルが並ぶ DSL が得られ、そのまま投入すると検証を通る。生成した DSL・プレビューの応答に、対象DB の接続先・ポート・ユーザー名・パスワード・JDBC の URL は含まれない（PM の Forbidden。要件との差 D1）
- **AC6.1.4** Given 書式の版 2 の DSL に、対象DB の設定のスキーマと名前の違うスキーマ、または2つ目のスキーマがある / When 投入する / Then 書式（JSON Schema）の検証は複数のスキーマを受け付ける形で通り、この Intent でその DSL を受け付けるか意味の誤りとして拒否するかは機能設計で決め、決めた側の動作を明示したテストにする。受け付ける場合も、照合（対象DB との違い）と既定の DSL の生成は設定のスキーマだけを扱う（SF2 A）
- **AC6.1.5** Given 同じスキーマ名が2回ある、または同じスキーマの中に同じテーブル名が2回ある書式の版 2 の DSL / When 投入する / Then 検証の誤り（重複キーまたは意味の誤り）として拒否され、後の値で黙って上書きされない
- **AC6.1.6** Given 書式の版 1 の DSL が適用済みの環境 / When 書式の版 2 に対応したアプリへ上げて起動する / Then 起動は止まらず、適用中の DSL は無い扱いになる（ログには DSL の本文と接続情報を含めない）。権限の設定の画面は対象が無い旨の案内（AC1.2.6）、業務のメニューは出ず（AC5.1.6）、import は拒否され（AC3.1.5）、権限の解決の口はすべて NONE・不可を返す。管理者が既定の DSL を生成し（版 2）、プレビューを経て適用し直すと、権限の対象と業務のメニューが使えるようになる（SF3 C。版 1 は書式の版の検証で外れるため、AC5.2.3 の「深さだけを外す」では救われない）
- **AC6.1.7** Given DSL の履歴に書式の版 1 の DSL がある / When その版を復元する / Then 書式の版の誤り（業務の誤りの 4xx）として拒否され、適用中の DSL は変わらず、500 にならない。版 1 の履歴のダウンロードも 500 にならない（本文を返すか業務の誤りで拒否するかは機能設計で決め、決めた側の動作を明示したテストにする）（V の F-3）
- **AC6.1.8** Given 書式の版 2 の DSL を適用した環境 / When 前の版のアプリへ戻して起動する / Then 前の版のアプリは版 2 を読めず、起動は止まらずに DSL が無い状態で起動する。戻した後に DSL を使うには、前の版で既定の DSL を生成し直して投入し直す。この手順と確かめは配備の段（deployment-pipeline の戻しの手順と練習）で扱う（要件との差 D2）
- **AC6.1.9** Given 書式の版 2 の DSL / When DSL の管理の画面で投入・プレビュー・違いの表・適用・破棄・ダウンロード・履歴を使う / Then 今までどおり使え、違いの表（照合）は設定のスキーマのテーブルとカラムで比べ、ダウンロードは版 2 の本文になる
- **AC6.1.10** Given 書式の版 2 の DSL / When 大きさ・入れ子の深さ・別名の数の上限、タグ、重複キー、JSON Schema の外部の `$ref` を確かめる既存のテストを版 2 の形に書き換えて流す / Then すべて今までどおり通り、拒否は Problem Details で返り、YAML・JSON Schema の部品の例外のメッセージを含まない（TP の DSL の必須のテスト）
