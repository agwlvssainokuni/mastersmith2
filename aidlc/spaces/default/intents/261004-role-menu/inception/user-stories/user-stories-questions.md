# User Stories — ストーリーの計画と質問

## 計画の案

- **ストーリーを書くか**: 書く。管理者と一般の利用者の2つの立場があり、ロール・グループ・作業ロール・継承の解決・import の2段・メニューの出し分けと、利用者に見える振る舞いと業務の決まりが多いため（`user-stories-assessment.md` に記録する）。
- **ストーリーの書き方**: 「〔利用者〕として、〔したいこと〕をしたい。それは〔得られる価値〕のためだ」の形で書き、INVEST（独立・交渉可能・価値がある・見積もれる・小さい・テストできる）を満たすようにする。受け入れ基準は Given/When/Then で、1ストーリーに3〜6件とし、失敗の場合を必ず含める。
- **ID**: ストーリーは `US{群}.{番号}`、受け入れ基準は `AC{群}.{番号}.{連番}`。
- **優先度**: MoSCoW（Must / Should / Could / Won't）を付ける。どこまでを最初に届けるかの線引きは、後の Delivery Planning で決める。
- **出典**: 各ストーリーに、元になった要件（`requirements.md` の FR・NFR）を示す。
- **要件の確かめで持ち越した点**: R-08（グループの削除とメンバー・割り当ての追加の同時の重なり）は、承認の場で機能設計で扱うことにした。ストーリーには、重なりで割り当てのあるグループが消えないことだけを受け入れ基準に入れ、守り方は機能設計に回す。

以下の点を決めてください。

要件の利用者は、管理者（ロール・グループ・権限・割り当てを設定する人）、管理画面の利用者（作業ロールを切り替え、自分の権限を確かめ、メニューから移る人。管理者も含む）、運用者・監査者（監査ログを見る人。見る画面は無い）の3つの立場です。

A. 管理者と、一般の利用者（業務データを扱う人）の2人。運用者・監査者は監査の受け入れ基準の中で扱う
B. 管理者・一般の利用者・運用者（監査者）の3人
C. A に加えて、「ロールが1つも無い利用者」を別のペルソナとして立てる（権限なしの振る舞いを確かめるため）

## M1. 権限の「スキーマの階層」をどう持つか

要件は主権限をスキーマ→テーブル→カラムの3階層で持つとしていますが、開発担当の確かめで、今の DSL にはスキーマの階層が無いと分かりました（DSL はテーブルの平らな一覧で、対象DB のスキーマは設定の1つだけ）。

A. スキーマの階層を「対象DB 全体（すべてのテーブル）」を表す1つの節と読み替える。継承の3階層の規則はそのまま使い、画面と YAML にも1つの節として出す。要件は書き換えず、差をストーリーに書く
B. DSL にスキーマを足す（DSL の書式の版を上げる。範囲が広がる）
C. 設定のスキーマ名を表示に使う（設定の値を画面に出すため、接続情報を画面に出さない決まりとの関係の確かめが要る）
