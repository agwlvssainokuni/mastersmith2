# Practices Discovery の質問（再実行）

`aidlc/spaces/default/memory/team.md` の5つの節は、確認済みの基準として引き継ぎます。下書き（`team-practices.md`）と3人の担当の意見（`contributions/`）では、基準と今のコード・設定の食い違いは見つかりませんでした。ここでは、証拠だけでは決まらない進め方の点だけを尋ねます。

今回の Intent の機能の中身は、要件定義・設計の段で扱います。たとえば、役割の持ち方と `admin_flag` との関係、権限の粒度、権限を DB とトークンのどちらで持つか、メニューの出どころ（DSL の `menus` か `registration.ts` か）、メニューの深さの上限の値、監査の種類の名前などです（`evidence.md` の5節）。

質問は Standard の目安（5〜8）より多い 12 問です。今回は認可の芯（管理者の真偽値1つから役割・権限へ）と画面の骨組み（平らなサイドバーから N 階層へ）の両方に触れるうえ、担当の確かめで既存の決まりの抜け（Q11・Q12）が見つかったためです。

## Q1. 役割・権限の機能で「必ず書くテスト」の一覧を足すか

`team.md` には、認証・認可・監査・メール・DSL について「必ず書くテスト」の一覧がありますが、役割・権限の一覧はありません。リード・品質担当・セキュリティ担当が次の案を出しました。★の値や動作は要件定義で決めてからテストを書きます。

- 権限ごとの API の認可: 足す・変える API のすべてで、未認証 401・その権限を持たない 403・持つ 200 をサーバー側で確かめる。403 を確かめる利用者は、権限が何も無い利用者ではなく「要る権限だけを欠く利用者」にする。停止中の利用者は権限があっても通らない。
- API の分類の網羅: すべての API が「公開・ログインだけ・権限が要る」のどれかに分類されていることを確かめるテストを置き、分類に無い API があれば落ちる（今は `/api/**` の既定が「ログインだけ」で、権限の決まりを書き忘れるとログイン中の誰でも呼べる）。
- 割り当ての変更の反映: 役割・権限を付けた直後・外した直後の次の要求で、403／200 がサーバー側で切り替わる。★変更の前に出したトークンの扱い
- 権限の昇格・一括代入・IDOR の防止: 自分が持たない権限を自分や他人に与えられない。要求の本文の値を変えて自分の役割・権限を変えられない。★組み込みの役割の保護
- 自分自身への操作と最後の管理者の読み替え: ★自分の役割を外す操作、★最後の有効な管理者を役割でどう数えるか。同時の重なりは待ち合わせで確実に作る。
- 監査: 割り当ての変更ごとに、操作した人・対象・変えた中身・結果が残る。★役割そのものの作成・変更・削除、拒否した操作を残すか
- 画面の出し分け: メニュー・画面を隠すことをサーバー側の検査の代わりにしない。権限の無い画面へ直接移ったときの 403 の表示。
- 性質ベースのテスト: 役割から権限を求める関数・権限でメニューを絞る関数に jqwik・fast-check を当てる。

A. 上の項目をすべて一覧に足す（API の分類の網羅を含む）
B. API の分類の網羅を除いて足す（網羅は設計の段で決める）
C. 一覧は足さず、この Intent の要件・設計で個別に決める
X. Other (please specify)

[Answer]: A
