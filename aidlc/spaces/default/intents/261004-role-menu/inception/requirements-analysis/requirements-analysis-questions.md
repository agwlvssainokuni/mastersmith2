# 要件定義の質問（Intent 261004-role-menu）

依頼文: 「F: ロールベースの権限の管理、I: メニュー・ナビゲーション（N階層）」

依頼文の F・I は、依頼者が以前に用意した要件のドラフト（参考資料。Git の管理の外）の Intent の分け方の記号です。ドラフトには、F について権限の考え方（ロール・グループ・作業ロールの切り替え・主権限 NONE/READ/FULL と補助権限 CREATE/DELETE・スキーマ→テーブル→カラムの継承・内部DB への保存・YAML の export/import）があります。I については「メニューは N 階層（可変）、テーブル単位の項目と複数テーブルをまとめた業務メニューを設定できる」とあります。

## 決まっていること（質問にしない）

- 役割・権限による判定は、API ごとにサーバー側で行い、メニュー・画面の出し分けを代わりにしない（`project.md` の Mandated、Practices Discovery の Q10）。
- 役割・権限の機能の必須のテスト（権限ごとの 401/403/200、API の分類の網羅、割り当ての変更の反映、昇格・一括代入・IDOR の防止、監査、画面の出し分け、性質ベースのテスト）と、N 階層のメニューの画面のテストの決まり（`team.md` の Testing Posture）。
- make-you-chic-ui に無い入れ子のサイドバーは、上流への追加を先に依頼する（`team.md` の Way of Working）。
- DB の変更は前進のみで、前の版が動く後方互換を保つ。`users.admin_flag` は消さない（`team.md` の Deployment）。
- E2E は最大2本（F と I に1本ずつ）（`team.md` の Testing Posture）。
- 今のコードの事実: 権限は `users.admin_flag` の真偽値1つで、要求ごとに DB から読みトークンには入れない（K-32）。メニューの N 階層の定義は DSL の `menus`（label・icon・table・items）にすでにあるが、画面には使われていない（K-37）。業務データの一覧・詳細の画面（ドラフトの J・K）はまだ無い。
