## 1. Intent の分析

- **目的**: 対象DB の業務データ（スキーマ・テーブル・カラム）に対する利用者ごとの権限を、ロールで設定・管理できるようにする（F）。あわせて、画面の左のメニューを、DSL に書いた N 階層の業務メニューと管理のメニューから作り、利用者の作業ロールの権限で出し分ける（I）（DESC、DR、RQ5、RQ7）。
- **背景**:
  - 今の権限は、利用者の管理者の印（`users.admin_flag` の真偽値）1つだけで、役割・権限の仕組みは無い（KB K-32〜K-35）。
  - サイドバーは画面の機能ごとの登録から作る平らな一覧で、入れ子は無い。make-you-chic-ui の `Sidebar` にも入れ子・今の項目の表示の口が無い（K-36）。
  - N 階層のメニューの定義は DSL の `menus` にすでにあるが、画面には使われていない（K-37）。
  - 業務データの一覧・詳細の画面（DR の J・K）はまだ無い。そのため今回の権限は、設定と解決と、後の Intent が使う口までを作り、業務データへの適用は J・K に任せる（RQ5）。
- **利用者**:
  - 管理者（管理者の印を持つ利用者）: ロール・グループ・権限の設定と、利用者・グループへのロールの割り当てを行う。権限の設定を YAML で書き出し・読み込む（RQ2、RQ3）
  - 管理画面の利用者（すべてのログイン済みの利用者）: 自分に割り当てられたロールから作業ロールを選び、自分の実効の権限を確かめ、メニューから画面へ移る（RQ3、RQ7）
  - 運用者・監査者: ロール・権限・割り当て・import・作業ロールの切り替えが監査ログに残る（RQ10）
- **成功基準**:
  - 管理者が、ロールを作り、スキーマ→テーブル→カラムの単位で主権限（NONE/READ/FULL）と、スキーマ→テーブルの単位で補助権限（CREATE/DELETE）を設定し、利用者・グループに割り当てられる
  - 利用者が作業ロールを切り替えると、次の要求から、実効の権限とメニューの出し分けが選んだロールのものに変わる
  - 実効の権限は、継承の規則どおりに、後の Intent が呼べる口で求められる
  - 業務データのメニューが DSL の N 階層の木で出て、作業ロールで主権限が NONE のテーブルの項目は出ない
  - 管理画面の操作の可否は、これまでどおり管理者の印で決まり、ロールの変更で変わらない
- **種類・規模**: 既存のアプリへの機能の追加（ブラウンフィールド）。新しい機能のパッケージ（ロール・権限）と管理の画面を足し、画面の骨組み（サイドバー・登録の型・ルーティング）と DSL（メニューの深さの上限）に手が入る。make-you-chic-ui への入れ子のサイドバーの追加を上流に依頼する（TP）。

## 2. 機能要件

Given/When/Then は受け入れの判定の例で、網羅はユーザーストーリーの段で行う。

### FR1 ロール

出典: DR（5.1）、RQ2、RQ3、RQ11

- **FR1.1** 管理者は、ロールを作成・名前の変更・削除できる。ロールの名前は空でなく、同じ名前のロールは作れない（大文字と小文字の扱い・長さの上限は機能設計で決める）。
  - Given 管理者がログインしている / When 「営業」という名前のロールを作る / Then ロールの一覧に「営業」が出る
  - Given 「営業」がすでにある / When もう一度「営業」を作る / Then 名前の重なりとして拒否され、ロールは増えない
- **FR1.2** 割り当て（利用者・グループのどちらか）が1つでも残っているロールは削除できない。拒否は業務の誤り（4xx）として返し、ロールと割り当ては変わらない（RQ11）。
  - Given ロール「営業」が利用者 A に割り当てられている / When 「営業」を削除する / Then 拒否され、「営業」と A への割り当てはそのまま残る
- **FR1.3** ロールの作成・変更・削除と、FR2〜FR5 の設定・割り当て・import は管理者だけが行え、管理者の印の判定（今の `/api/admin/**` の認可）で守る。管理者でない利用者は 403 を受ける（RQ2、PM（Mandated））。

### FR2 主権限（NONE / READ / FULL）

出典: DR（5.2）、RQ4、RF1

- **FR2.1** 管理者は、ロールごとに、スキーマ・テーブル・カラムの3つの階層のそれぞれに主権限を設定できる。値は「設定なし・NONE・READ・FULL」の4つ。
- **FR2.2** 実効の主権限は次の規則で求める。ある階層の値が「設定なし」でなければその値、「設定なし」なら直近の上位の階層の実効の値を継承する。スキーマの階層まで「設定なし」なら NONE。
  - Given スキーマ FULL・テーブル 設定なし・カラム 設定なし / Then カラムの実効の値は FULL
  - Given スキーマ FULL・テーブル READ・カラム 設定なし / Then カラムの実効の値は READ
  - Given スキーマ FULL・テーブル READ・カラム NONE / Then カラムの実効の値は NONE
  - Given スキーマ NONE・テーブル FULL・カラム 設定なし / Then カラムの実効の値は FULL
  - Given 全階層が設定なし / Then カラムの実効の値は NONE
- **FR2.3** 権限を当てる対象（スキーマ・テーブル・カラムの一覧）と表示名は、適用済みの DSL のモデルから出す。適用済みの DSL が無いときは、権限の設定の画面に対象が無い旨の案内を出し、設定はできない（RQ4）。
- **FR2.4** 設定は対象の名前（スキーマ名・テーブル名・カラム名）で持つ。DSL を適用し直して対象が DSL から消えても、設定は消さずに持ち続け、実効の値の解決では使わない。権限の設定の画面では「今の DSL に無い」と分かるように出し、管理者が消せる。同じ名前の対象が DSL に戻れば、その設定はまた効く（RF1）。

### FR3 補助権限（CREATE / DELETE）

出典: DR（5.3）

- **FR3.1** 管理者は、ロールごとに、スキーマ・テーブルの2つの階層のそれぞれに、補助権限 CREATE と DELETE を設定できる。値は「設定なし・可・不可」の3つ。カラムの階層は持たない。
- **FR3.2** 実効の補助権限は、FR2.2 と同じ継承の規則で求め、スキーマの階層まで「設定なし」なら「不可」とする。
  - Given スキーマ 可・テーブル 設定なし / Then テーブルの実効の CREATE は可
  - Given スキーマ 設定なし・テーブル 設定なし / Then テーブルの実効の CREATE は不可
- **FR3.3** 対象の出どころと、DSL から消えた対象の扱いは、FR2.3・FR2.4 と同じ。

### FR4 グループと割り当て

出典: DR（5.1）、RQ3

- **FR4.1** 管理者は、グループを作成・名前の変更・削除でき、グループのメンバー（利用者）を足し・外せる。グループの名前の規則は FR1.1 と同じ考え方で機能設計で決める。
- **FR4.1a** メンバーかロールの割り当てが1つでも残っているグループは削除できない。拒否は業務の誤り（4xx）として返し、グループ・メンバー・割り当ては変わらない（ロールの削除 FR1.2 とそろえる。利用者の作業ロールと実効の権限も変わらない）（RC: R-01）。
  - Given グループ「営業部」に利用者 A がいる / When 「営業部」を削除する / Then 拒否され、「営業部」と A のメンバーはそのまま残る
  - Given グループ「営業部」にメンバーが無く、ロール「営業」が割り当てられている / When 「営業部」を削除する / Then 拒否され、割り当ては残る
  - Given グループ「営業部」にメンバーも割り当ても無い / When 「営業部」を削除する / Then 削除される
- **FR4.2** 管理者は、ロールを利用者とグループのそれぞれに割り当て・外せる。1人の利用者・1つのグループに複数のロールを割り当てられる。
- **FR4.3** 利用者に割り当てられたロールは、利用者へ直接割り当てたロールと、利用者が属するグループに割り当てたロールを合わせたものとする（同じロールが両方から来ても1つとして扱う）。
- **FR4.4** 割り当て・外しの直後の、その利用者の次の要求から、作業ロールに選べるロールと実効の権限がサーバー側で変わる。割り当てと権限はトークンに入れず、要求ごとに内部DB から求める（TP、PM（Mandated）、KB K-32）。
  - Given 利用者 B がロール「営業」だけを持ち、作業ロールが「営業」 / When 管理者が B から「営業」を外す / Then B の次の要求で、B の実効の権限はすべて NONE・不可になり、作業ロールは無い
- **FR4.5** 割り当てのある利用者（利用停止の利用者・招待中の利用者を含む）を表す画面・API の応答に、パスワードのハッシュ値・招待のトークンのハッシュ値・ロックの判定の内部の値を含めない（PM（Forbidden））。

### FR5 作業ロール

出典: DR（5.1）、RQ3、RQ6

- **FR5.1** 利用者は、自分に割り当てられたロール（FR4.3）の中から1つを作業ロールとして選べ、いつでも切り替えられる。実効の権限は、作業ロールの設定だけで求める（複数のロールの権限は合算しない）。
- **FR5.2** 切り替えた直後の次の要求から、実効の権限とメニューの出し分けが新しい作業ロールのものになる。
  - Given 利用者がロール「営業」と「経理」を持ち、作業ロールが「営業」 / When 「経理」に切り替える / Then 次の要求の実効の権限とメニューは「経理」の設定で決まる
- **FR5.3** 自分に割り当てられていないロールへの切り替えは拒否し、作業ロールは変わらない（要求の本文の値を変えた要求を含む）。
- **FR5.4** 作業ロールは利用者ごとに内部DB に覚え、次のログインでも同じロールで始める（RQ6）。
- **FR5.5** 覚えている作業ロールが、割り当ての変更・ロールの削除などで自分のロールでなくなったときは、割り当ての中の最初のロールを作業ロールとする（「最初」の順序は機能設計で決める）。ロールが1つも無い利用者には作業ロールが無く、業務データの実効の権限はすべて NONE・不可とする。ログイン・自分の設定、管理者なら管理画面は今までどおり使える（RQ6）。
- **FR5.6** 画面の上部など、どの画面からも作業ロールを確かめて切り替えられる（置き場は画面の段で決める）。

### FR6 自分の実効の権限の確かめ

出典: RQ3

- **FR6.1** 利用者は、今の作業ロールでの自分の実効の主権限（スキーマ・テーブル・カラムごとの NONE/READ/FULL）と実効の補助権限（スキーマ・テーブルごとの CREATE/DELETE の可・不可）を画面と API で確かめられる。対象は適用済みの DSL のもので、表示名を出す。
- **FR6.2** 他の利用者の実効の権限は、この画面・API では見られない（自分の分だけ。管理者が他人の権限を確かめる方法は持たない）。

### FR7 権限の設定の YAML の export / import

出典: DR（5.6）、RQ3、RF2、RF3、PM（Mandated）

- **FR7.1** 管理者は、ロールとその権限の設定（主権限・補助権限）を YAML のファイルとして書き出せる。グループ・グループのメンバー・割り当ては含めない（RF2）。
- **FR7.2** 管理者は、FR7.1 の形の YAML を読み込める。ファイルにあるロールだけを置き換え（同じ名前のロールは権限の設定を置き換え、無いロールは作る）、ファイルに無いロールは残す（RF3）。
- **FR7.3** 読み込みは2段にする。まず YAML を検証して、変わる点の一覧（作るロール、設定が変わるロールと変わる対象）を見せ、管理者が確かめてから適用する。確かめの前に設定は変えない（RF3）。
- **FR7.3a** 適用のときに、確かめに使った YAML を検証し直して変わる点の一覧を作り直す。確かめた一覧と違えば（確かめの後に別の管理者がロールや設定を変えた、DSL を適用し直した など）、適用を拒否して設定を変えず、確かめからやり直してもらう（RC: R-03）。確かめた内容の結びつけ方（一覧の値の比べ方など）は設計で決める。
  - Given 管理者 A が import の確かめを見ている間に、管理者 B が同じロールの設定を変えた / When A が適用する / Then 拒否され、設定は B が変えた状態のまま残る
- **FR7.3b** 適用済みの DSL が無いときは、import（確かめ・適用とも）を拒否し、設定は変えない（FR2.3 とそろえる）（RC: R-02）。export は DSL の有無によらず、今ある設定を書き出せる。
  - Given 適用済みの DSL が無い / When 権限の設定の YAML を読み込む / Then DSL が無い旨で拒否され、ロールと設定は増えも変わりもしない
- **FR7.4** 読み込む YAML は利用者が投入する信頼できない入力として扱い、DSL と同じ守りを当てる。大きさ・入れ子の深さ・別名の数の上限を置き、タグと任意の型の生成を拒否し、重複キーを誤りにし、外部の参照を取りに行かない。拒否は Problem Details の形で返し、YAML の部品の例外のメッセージを含めない（PM（Mandated・Forbidden）、TP）。上限の値は設計で決める。
- **FR7.5** 適用済みの DSL があり、YAML の中の対象の名前がその DSL に無いときは、FR2.4 と同じく名前で持つ設定として読み込み、変わる点の一覧で「今の DSL に無い」と分かるように出す（RF1 と RF3 の組み合わせ。§5 の前提 A3。DSL そのものが無いときは FR7.3b のとおり拒否する）。

### FR8 権限の解決の口（後の Intent 向け）

出典: RQ5、DR（9.1）

- **FR8.1** アプリの中に、利用者と対象（スキーマ・テーブル・カラム）を受け取り、その利用者の今の作業ロールでの実効の主権限・補助権限を返す口を作る。業務データの一覧・詳細の画面（J・K）と、メニューの出し分け（FR10）が使う。
- **FR8.2** 口は要求ごとに内部DB の割り当て・作業ロール・設定から求め、トークンや画面から送られた値を使わない（PM（Mandated））。
- **FR8.3** 口は、DSL に無い対象を問われたときは NONE・不可を返す。

### FR9 メニュー（N 階層）

出典: DR（2.3）、RQ7、RQ8、RQ9、KB K-36・K-37

- **FR9.1** サイドバーのメニューは、業務データのメニューと管理のメニューの2つから作る。業務データのメニューは適用済みの DSL の `menus` の木から作り、管理のメニューは今の画面の機能ごとの登録から作る。両方をサイドバーに並べる（並べ方は画面の段で決める）（RQ7）。
- **FR9.2** 業務データのメニューは N 階層の木で、まとまり（子を持つ項目）とテーブルを指す項目を持つ。まとまりは開閉でき、今の画面に当たる項目が分かる（TP の N 階層のメニューのテストの決まり）。
- **FR9.3** テーブルを指す項目を選ぶと、そのテーブルの画面の置き場へ移る。テーブルの一覧の画面ができる J までは、置き場は「この画面は準備中です」とテーブルの表示名を出すだけの画面とする（RQ8）。
- **FR9.4** DSL の `menus` に深さの上限を置き、上限を超えるメニューを持つ DSL は DSL の検証で拒否する。上限の値は設計で決める（目安 5 段）（RQ9）。
  - Given メニューの深さが上限ちょうどの DSL / When 投入する / Then 受け付ける
  - Given メニューの深さが上限を1段超える DSL / When 投入する / Then 検証の誤りとして拒否される
- **FR9.5** 適用済みの DSL が無いとき、または DSL の `menus` が空のときは、業務データのメニューを出さない（管理のメニューは管理者に出す）。
- **FR9.6** メニューの label・icon・table は DSL から来る値として扱い、画面に出すときはエスケープし、icon は許した名前（make-you-chic-ui のアイコン）だけを使い、許していない名前は既定のアイコンにする。テーブルの画面の置き場への道はエンコードする（TP）。icon の扱いの細部は設計で決める。

### FR10 メニューの出し分け

出典: RQ5、RQ2、PM（Mandated）

- **FR10.1** 業務データのメニューで、テーブルを指す項目は、作業ロールでのそのテーブルの実効の主権限が NONE なら出さない（READ・FULL なら出す）。判定はテーブルの階層の実効の主権限だけで行い、カラムの値は見ない（テーブルが NONE でカラムに明示の READ・FULL があっても出さない）（RC: R-05）。作業ロールが無い利用者には、テーブルを指す項目を出さない。
  - Given 作業ロールでスキーマ NONE・テーブル 設定なし・あるカラムに READ / Then そのテーブルの項目は出ない
- **FR10.2** 子がすべて出ないまとまりは出さない（子の無いまとまりを残さない）。
- **FR10.3** 管理のメニューは、これまでどおり管理者の印で出し分ける（RQ2）。
- **FR10.4** メニューを出さないことは、サーバー側の権限の判定の代わりにしない。テーブルの画面の置き場へ直接移ったときも、FR8 の口で権限を確かめ、NONE なら権限が無い旨を出す（PM（Mandated））。
- **FR10.5** 業務データのメニューの木は、サーバー側で作業ロールの権限を当てて絞った形で画面に渡す（権限の無い項目を応答に含めない）。メニューを返す API は業務データの木だけを返し、管理のメニューは含めない。管理のメニューは、今までどおり画面の側の登録から作り、管理者の印で出す（RC: R-04）。API の形は設計で決める。

### FR11 管理の画面

出典: RQ2、RQ3、RQ12

- **FR11.1** 管理者は、管理画面から、ロールの一覧・作成・名前の変更・削除、グループの一覧・作成・名前の変更・削除とメンバーの変更、利用者・グループへのロールの割り当て、ロールの権限の設定、YAML の export/import を行える。
- **FR11.2** ロールの権限の設定の画面は、スキーマ→テーブル→カラムの木で、開いた所だけを読み込む（1 つのロールで最大 1 万カラムの規模でも、開いた範囲だけを返す）（RQ12）。
- **FR11.3** 権限の設定の画面では、各階層の明示の値（設定なしを含む）と、継承の結果の実効の値を区別して見られる。

### FR12 監査

出典: RQ10、PM（Mandated）、TP

- **FR12.1** 次の操作を監査ログに残す。各行に、操作した人・対象（ロール・グループ・利用者）・変えた中身・結果を含める。
  - ロールの作成・名前の変更・削除、ロールの権限の設定の変更（主権限・補助権限）
  - 利用者・グループへのロールの割り当て・外し、グループの作成・名前の変更・削除、メンバーの足し・外し
  - 権限の設定の import の適用
  - 作業ロールの切り替え（操作した人と対象は同じ利用者）
- **FR12.2** 業務の理由で拒否した操作（割り当てのあるロールの削除、名前の重なり、割り当てられていないロールへの切り替え など）を監査に残すかは、今の利用者の管理の操作と同じ考え方で機能設計で決める。
- **FR12.3** 監査の行に、パスワード・トークン・ハッシュ値を含めない。権限の設定の変更が多い（例: import で数千の対象）ときの「変えた中身」の残し方（要約か全件か）は設計で決める。
- **FR12.4** export を監査に残すかは機能設計で決める（RQ10 では選ばれていない）。

## 3. 非機能要件

### NFR1 セキュリティ

出典: PM（Mandated・Forbidden）、TP

- **NFR1.1** 役割・権限による判定は、API ごとにサーバー側で行い、メニュー・画面の出し分けを代わりにしない。
- **NFR1.2** 足す・変える API のすべてについて、未認証 401・その権限を持たない 403・持つ 200 をサーバー側のテストで確かめる。403 は要る権限だけを欠く利用者で確かめる。停止中の利用者は権限があっても通らない（TP）。
- **NFR1.3** すべての API が「公開・ログインだけ・権限が要る（管理者）」のどれかに分類されていることを確かめるテストを置き、分類に無い API があれば落ちる（TP）。
- **NFR1.4** 昇格・一括代入・IDOR を防ぐ。自分の作業ロールを、割り当てられていないロールに変えられない。管理者でない利用者が、要求の本文の値を変えて自分のロール・グループ・権限を変えられない（TP）。
- **NFR1.5** 権限の設定の YAML の守りは FR7.4 のとおり。
- **NFR1.6** 個人に関する値（メールアドレス・氏名・検索の文字）は、既存の決まりどおり TRACE のログに出ない型で受け渡し、`XxxSecretLeakIT` で確かめる（PM の Code Style の学び）。

### NFR2 性能

出典: RQ12、DR（7 章）

- **NFR2.1** 規模の前提は、対象DB 最大 100 テーブル・1 テーブル最大 100 カラム、利用者最大 50 名程度、ロールとグループは各 100 程度まで [assumption]。
- **NFR2.2** 権限の設定の画面で木の1階層を開く・保存する API、メニューを返す API、作業ロールの切り替えの API の応答時間は、95 パーセンタイルで 1 秒以内を目標とし、NFR 要件の段で測り方と確かめ方を決める（RQ12）。
- **NFR2.3** 実効の権限は要求ごとに内部DB から求めるため、要求ごとの読み出しが重くならないことを NFR 要件・NFR 設計で確かめる（品質担当の論点）。
- **NFR2.4** 権限の設定の YAML の import の確かめと適用（数千の対象をまとめて確定しうる）の応答時間の目標は、NFR 要件の段で、YAML の大きさの上限とあわせて決める（RC: R-06）。

### NFR3 信頼性・同時性

- **NFR3.1** 割り当て・外し・ロールの削除・作業ロールの切り替えが同時に重なっても、割り当ての無いロールが作業ロールとして残らない・割り当てのあるロールが消えない。重なりは待ち合わせで確実に作ってテストする（TP）。
- **NFR3.2** import の適用は、1つのファイルの分をまとめて確定し、途中で失敗したら設定は変わらない。

### NFR4 アクセシビリティ・画面

出典: TP

- **NFR4.1** 足す画面は WCAG 2.1 AA に沿い、画面部品ごとにアクセシビリティ検査を入れる（前の Intent と同じ）。
- **NFR4.2** N 階層のメニューは、開閉の状態（`aria-expanded`）と今の項目（`aria-current`）を持ち、キーボードだけでたどれる。実際のブラウザの axe を、展開した深い階層・長い名前で、ブランドカラーとテーマのすべての組について行う（TP）。
- **NFR4.3** 画面の文言は日本語と英語を用意する。

### NFR5 監査・観測

- **NFR5.1** 監査は FR12 のとおり。監査の種類の名前の長さは今の列（32 文字）に収める（KB K-38）。
- **NFR5.2** 新しい管理の API と作業ロールの切り替えに、今の管理の API と同じ指標（要求の数・誤りの数・時間）を出す。

### NFR6 テスト・品質

出典: TP

- **NFR6.1** 役割・権限の必須のテスト（TP の「役割・権限の機能では、次のテストを必ず書く」）と、N 階層のメニューの画面のテストの決まりを満たす。
- **NFR6.2** 継承の解決（FR2.2・FR3.2）と、メニューを権限で絞る関数（FR10.1・FR10.2）に性質ベースのテスト（jqwik・fast-check）を当てる。
- **NFR6.3** E2E は最大2本（F: 管理者がロールを作って割り当て、利用者の作業ロールの切り替えでメニューが変わる流れ。I: N 階層のメニューをたどって準備中の画面へ移る流れ）。役割を変える操作は、その流れで自分で作った利用者とロールだけを対象にし、初期管理者は変えない（TP）。
- **NFR6.4** カバレッジの下限（行 80%・分岐 70%、パッケージごと）を満たす。手を入れる見込みの `access.service`（全体の合計で判定している一覧に入っている）は、手を入れる Bolt で下限を満たして一覧から外す（TP、KB K-38）。

## 4. 制約

- **C1** 管理者の印（`users.admin_flag`）は残し、管理画面の操作の可否は印で決める。ロールは業務データの権限だけに使う（RQ2、DR 5.7）。既存の最後の管理者の保護・利用者の管理の決まりは変えない。
- **C2** DB の変更は前進のみで、1つ前の版のアプリが動く後方互換を保つ。今回は表を足すだけで、既存の列を消さない（TP の Deployment）。
- **C3** `vendor/make-you-chic-ui` はこのリポジトリから直接変えない。入れ子のサイドバーなど足りない部品は、設計の段で一覧にして上流への追加を先に依頼し、取り込みは固定先の更新の専用のコミットで行う（PM（Forbidden）、TP）。
- **C4** 新しい機能は自分のパッケージに `<機能>BoundaryArchitectureTest` を置き、`access` の本体に手を入れる Bolt では `access` の境界テストも足す（TP）。
- **C5** 画面の機能どうしの直接の import を ESLint で止め、今の違反1件（`features/registration/useRegistration.ts`）を、この Intent で最初に手を入れる Bolt で直す（TP）。
- **C6** 対象DB には接続しない（権限の対象は適用済みの DSL から出す、RQ4）。対象DB の接続情報を画面・API・YAML から受け取らない（PM（Forbidden））。

## 5. 前提

- **A1** 業務データの一覧・詳細の画面（J・K）は後の Intent で作り、主権限・補助権限の業務データへの適用（一覧・検索・詳細・編集の出し分け、主キーの有無による操作の可否、DR 5.4・5.5）はそこで行う。今回は FR8 の口を J・K が使える形で用意する（RQ5）。
- **A2** 利用者に割り当てられたロールは、直接の割り当てとグループ経由の割り当ての和とする（FR4.3）。DR は「ロールは利用者とグループに複数割当可能」としか書いておらず、和として読んだ。
- **A3** import の YAML に今の DSL に無い対象の名前があるときは、拒否せずに名前で持つ設定として読み込む（FR7.5）。RF1（DSL から消えた設定を持ち続ける）と同じ扱いにそろえた。
- **A4** 作業ロールの切り替えは、割り当てがあるすべての利用者（管理者を含む）が行える。管理者でも、業務データの権限は作業ロールで決まる（DR 5.7）。
- **A5** 権限の対象は DSL から出すため、DR の「対象DB のメタデータを直接見る」（9.1）とは違う。DSL を適用していない環境では権限を設定できない（RQ4、FR2.3）。
- **A6** 規模の前提（NFR2.1）のうち、ロールとグループの数の上限は DR に無く、仮に置いた。NFR 要件の段で確かめる。

## 6. 範囲の外

- 業務データの一覧・詳細・編集の画面と、そこへの権限の適用（J・K）。テーブルの画面の置き場は準備中の表示だけ（FR9.3）。
- 管理画面の操作のロールによる許可（管理者の印のロールへの置き換え）（RQ2）。
- グループ・グループのメンバー・割り当ての YAML の export/import（RF2）。
- 管理者が他の利用者の実効の権限を確かめる画面（FR6.2）。
- 権限の設定の行単位の条件（行の値による絞り込み）。DR にも無い。
- 対象DB のメタデータを直接読むこと（RQ4）。

- サイドバーでの業務メニューと管理のメニューの並べ方、作業ロールの切り替えの置き場、準備中の画面の見た目（画面の段）。
