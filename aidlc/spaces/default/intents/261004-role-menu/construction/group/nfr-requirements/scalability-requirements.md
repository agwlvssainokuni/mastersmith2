## 要件

| ID | 要件 | 測り方・確かめ方 | 持ち主の段 |
|---|---|---|---|
| NFR2.1 | 規模の前提は、グループ 100 程度・利用者 50 名程度を目安として確定する（前提 A6 の確かめ、Q2: A）。試験の悪い側は目安の 10〜20 倍の、グループ 1,000・利用者 1,000 名・メンバー 1,000 人のグループとする | NFR2.5 の k6 の場面のデータ。Performance Validation の結果に規模を記録する | Performance Validation |
| NFR2.7 | 書き込みの操作は、操作のトランザクションに1本、確定の後の監査の記録に2本目の接続を使う（既存の監査の形）。違反の後の失敗の出来事は、1つ目のトランザクションを終えてから2つ目の `TransactionTemplate` を実行するため、同時に持つ接続は2本を超えない（`reliability-requirements.md` の NFR3.4）。接続プールの上限（既定 30）に対する見積もりは「同時の書き込みの数 × 2 本 ≦ 上限」で、これを次の2つで数として確かめる（承認の場の直し R-02）。<br>・**結合テストで決定的に**: `GroupConnectionUsageIT`。7つの口のそれぞれ（書き込みは成功・業務の拒否・違反の読み替え（BR5.7）・`GROUP_BUSY` の経路を含む）を1回ずつ呼び、1要求で同時に持つ接続の最大を数える（テストだけで接続を貸す部品を包み、借りている本数の最大を記録する。確定の後の監査の記録の途中は、既存の `audit/testsupport` の待ち合わせで止めて数える）。期待: 書き込みは最大 2、一覧・詳細は最大 1。3 以上が出たら見積もりの誤りとして直す。<br>・**負荷の試験で上限に届かせて**: 場面 `groupPoolLimit`。使い捨てのアプリの接続プールの上限を 10 に下げ（接続の待ちの上限は 5000 ms のまま）、VU ごとに自分のグループでメンバーの追加と外しを繰り返しごとに交互に送る（1回の繰り返しに要求1つ、どれも書き込みで 204）。トークンは `setup()` で取る。<br>・**4 VU を 2 分**（4 × 2 = 8 本 < 10 本で、尽きないはず）。期待: 接続の待ちの時間切れの累計（`hikaricp.connections.timeout`）が 0、500 が 0 件。<br>・**20 VU を 2 分**（20 × 2 = 40 本 > 10 本で、尽きうる）。期待: 借りるまでの待ちの最大（`hikaricp.connections.acquire` の max）が 0 ミリ秒より大きい（待ちが起きる）。待ちが 5000 ms に届いて時間切れと 500 が出たら、それも見積もりどおりとして件数を記録する。<br>・4 VU で待ちの時間切れか 500 が1件でも出たら、見積もりの誤り（1要求で3本以上使う経路がある）として扱い、`GroupConnectionUsageIT` で経路を確かめてから直す。20 VU で待ちが1度も起きなかったら、負荷が上限に届いていないとして VU を増やして流し直す。<br>この場面は p95 と checks の閾値を置かず、状態コードの件数を数え分けて記録する | `GroupConnectionUsageIT` は `./gradlew verify` で毎回。負荷の試験は `/actuator/metrics` の `hikaricp.connections.timeout`（累計）・`hikaricp.connections.acquire`（最大）・`hikaricp.connections.pending` を試験の前と後に読む。公開は使い捨てのアプリにだけ `MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE=health,metrics` で行い、配備したアプリの公開の範囲は変えない（`project.md` の学び） | 結合テストと台本は Code Generation（B3）、負荷の試験は Performance Validation |
| NFR2.8 | グループの数と1つのグループのメンバーの数に、アプリで上限を置かない（作成・追加を数で拒否しない）。詳細はメンバーを全件返す（BR7.4）。メンバー 1,000 人の詳細でも NFR2.5 の目標を満たすことで、規模の余裕を確かめる。上限やページ送りが要るときは、後の Intent で契約 C6 を変えて扱う | NFR2.5 の `groupDetail` | Performance Validation |

## 補足

- 内部DB は組み込みの H2 で、アプリは1つのインスタンスだけで動く（既存の前提）。横に広げる設計はこの単位では扱わない。
- 一覧は 1 ページ 20 件（既存の `Paging`）で、グループの数が増えても1回の応答の大きさは変わらない。

## 承認の場の決定と直し

依頼者は承認の場で Request Changes を選び、直す範囲を「Major 11 件だけを直す」と決めた。この成果物で直したのは次の1件（レビューの記録は `aidlc/spaces/default/intents/261004-role-menu/.aidlc-reviews/nfr-requirements/units/group/4e9510ac79c4db11/` の 1 回目）。

- **R-02（Major）NFR2.7 の合格の条件**: 見積もりの式（同時の書き込みの数 × 2 本 ≦ 上限）を書き、1要求で同時に持つ接続の最大を決定的に確かめる結合テスト `GroupConnectionUsageIT`（書き込み 2・読み取り 1、3 以上は見積もりの誤り）を足した。負荷の試験は場面 `groupPoolLimit` に名前を変え、上限 10・接続の待ち 5000 ms で、尽きないはずの 4 VU（時間切れの累計 0・500 が 0）と尽きうる 20 VU（借りるまでの待ちの最大が 0 より大きい）の期待を数で置き、外れたときに見積もりの誤りとして扱う条件を書いた。U4 role の NFR 要件で先に採った形にそろえた。
