| ID | 要件 | 測り方・確かめ方 | 持ち主の段 |
|---|---|---|---|
| NFR3.1 | グループの削除と、同じグループへのメンバーの追加（と B5 からはロールの割り当ての追加）が同時に重なっても、終わった後に「消えたグループにメンバー・割り当てが残る」「メンバー・割り当てが残るのにグループが消える」のどちらも起きない。負けた側は業務の code の 4xx（`GROUP_NOT_FOUND`・`GROUP_IN_USE`・`GROUP_BUSY`）で、500 にならない（BR5.1・BR5.3・BR5.4） | 結合テスト `GroupConcurrencyIT`。待ち合わせの口 `GroupBarrier`（テストは `@Primary`）で、削除を排他の直後に止めてメンバーの追加を送る（逆の順も）。スレッドの数に頼らない。合否は両方が終わった後の内部DB の状態と負けた側の状態コードと code。割り当ての側は B5 で U4 が同じ形で確かめる | Code Generation（B3・B5） |

## 障害と戻し

- グループの操作は内部DB だけを使い、外部への呼び出しは無い。外の部品の障害に引きずられない。
- 戻しは直前の版のイメージで行う（配備の段の手順）。足した表と列は前の版から見えないだけで、グループのデータは残る。戻した後は前の版にグループの機能が無いため、グループ経由のロールは効かない（ロールの機能も前の版に無い）。
