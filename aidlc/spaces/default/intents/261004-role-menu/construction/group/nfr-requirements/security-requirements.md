## 脅威の見方（STRIDE）

| 脅威 | この単位での例 | 守り |
|---|---|---|
| なりすまし（S） | 未ログイン・停止中の管理者がグループを変える | 既存のアクセストークンの認証と停止の判定（NFR1.1・NFR1.2） |
| 改ざん（T） | 本文に ID・時刻を足してほかの値を変える | 決めた項目だけを受ける（NFR1.4） |
| 否認（R） | 誰が名前を変えたか・メンバーを外したかが分からない | 成功と業務の拒否の監査（NFR5.1） |
| 情報の漏えい（I） | メンバーのメールアドレス・氏名が TRACE・監査・例外の文に出る | 伏せ字の型・detail の型・例外の文を出さない（NFR1.6・NFR1.7・NFR1.8） |
| 処理の妨害（D） | 同じグループへの操作の重なりで待ちが積み上がる | 待ちの上限 3 秒と GROUP_BUSY（NFR3.3、reliability） |
| 権限の昇格（E） | ロールや作業ロールでグループの管理を行う、管理者でない人が自分をグループに足す | 管理者の印だけで判定（NFR1.1）、ロールでは管理の権限が増えない |

## 要件

| ID | 要件 | 測り方・確かめ方 | 持ち主の段 |
|---|---|---|---|
| NFR1.1 | グループの管理の API（7つの口）の可否は、API ごとにサーバー側で管理者の印と停止で判定する。ロール・作業ロール・画面の出し分けを判定に使わない（BR2.1） | 結合テスト `GroupAdminAuthorizationApiIT`（下の NFR1.2 の表）。全スキーマを FULL にしたロールを作業ロールにする、管理者の印を持たない利用者でも 403（B5 で足す。role への引き継ぎ） | Code Generation（B3・B5） |
| NFR1.2 | 7つの口のそれぞれで、未認証 401・管理者の印だけを欠く利用者 403・管理者は成功（一覧と詳細 200、作成 201、ほか 204）・停止中の管理者 403 を、パラメーターを使う表のテストで確かめる。403 の後に対象の行が変わっていないことを読み直して確かめる | 同上。表は 7 口 × 4 主体 = 28 行 | Code Generation（B3） |
| NFR1.3 | 7つの口はすべて `ApiAccess(ADMIN)` の印を持ち、道は `/api/admin/groups` の下。U1 の構造の検査と実行時の検査を通る | U1 の全体の検査（既存のテストがそのまま落ちる・通るで判定） | Code Generation（B3） |
| NFR1.4 | 一括代入と IDOR を防ぐ。作成・名前の変更は `name` だけ、メンバーの追加は `userId` だけを受け、ほかの項目を足しても反映しない。存在しない・0 以下のグループの ID と利用者の ID は 400 にせず `GROUP_NOT_FOUND`・`USER_NOT_FOUND`（404、変える操作は監査に FAILURE）にし、行の排他やダミーの行に触れない（機能設計のレビューの R-06 の手当て）。招待中の人（利用者の行が無い）は足せない | 結合テスト `GroupAdminMassAssignmentIT`（ID・作成の時刻を足しても名前だけが変わる）、`GroupAdminIdorApiIT`（0・負・存在しない ID・招待中の人。拒否の後に読み直して変わらない） | Code Generation（B3） |
| NFR1.6 | メンバーのメールアドレス・氏名は、repository から web までのすべての層で伏せ字の型のまま渡し、TRACE を有効にしてもアプリのログに出ない。`user.service` に足すまとめて読む口も伏せ字の型を返す | 結合テスト `GroupSecretLeakIT`（TRACE を有効にして一覧・詳細・メンバーの足し外しを行い、ログにメールアドレス・氏名が0件） | Code Generation（B3） |
| NFR1.7 | 監査の行と `detail` に、パスワード・トークン・ハッシュ値・メールアドレス・氏名を入れない。`detail` は決めた型（Name・Rename・Membership・InUse）からだけ作る。グループの名前は管理者が入れる業務の名前で、個人に関する値として扱わない（まとめの確認で受け入れ）。応答にパスワードのハッシュ値・招待のトークンのハッシュ値・ロックの判定の内部の値を含めない | 既存の `AuditSecretLeakIT` の列の一覧に `target_role_id`・`target_group_id`・`detail` を足し、グループの操作の後の行に秘密と個人に関する値が無いことを確かめる。単体テストで `detail` の JSON が決めたキーだけを持つこと。結合テストで一覧・詳細・作成の応答に該当の項目が無いこと | Code Generation（B3） |
| NFR1.8 | 一意・主キー・外部キーの違反、排他・鍵の待ちの上限切れの例外の文（行の値が入りうる）を、応答・ログ・監査に出さない。受けた所で区分に変え、ログにはクラスの名前だけを出す（BR9.3） | 結合テスト `GroupUniqueViolationSecretLeakIT`（同じ名前の作成の重なりと、同じメンバーの追加の重なりで、応答とログに名前と ID の値の文が出ない。既存の `UserUniqueViolationSecretLeakIT` と同じ形） | Code Generation（B3） |
| NFR1.9 | 静的解析の関門を今のまま通す（SpotBugs ＋ FindSecBugs の priority 1 と `SQL_`・`PREDICTABLE_RANDOM`・`SMTP_HEADER_INJECTION`）。問い合わせは名前の付いた引数だけで組み、文字列の連結で SQL を作らない | `./gradlew verify` の SpotBugs | Code Generation（B3） |
| NFR1.10 | 要求の入口で管理者の印を確かめた後、書き込みまでの間に別の管理者に印を外されても、その1件の要求は通る窓を受け入れる。グループの操作は管理者の印・停止を変えず、次の要求からは入口で拒否されるため（機能設計のレビューの R-05 の手当て。まとめの確認で受け入れ） | テストは置かない（受け入れた振る舞い）。次の要求で 403 になることは NFR1.2 の停止・印の無い主体の行で確かめる | — |
| NFR1.11 | グループの名前は信頼できない入力として、前後の空白を取り除いて 1〜64 コードポイント、制御文字を拒否する。画面へは文字として出す（HTML として描かないのは U6） | 結合テストと jqwik の性質ベースのテスト（NFR6.5） | Code Generation（B3） |
