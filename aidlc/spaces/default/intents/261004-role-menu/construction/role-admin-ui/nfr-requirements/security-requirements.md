## 前提

- 画面は表示と要求の組み立てだけを持ち、判定の正はいつもサーバー（`project.md` の Mandated「役割・権限による判定は、API ごとにサーバー側で行い、メニュー・画面の出し分けを代わりにしない」）。
- 守るものは、管理の操作の正しさ（サーバーが守る）、画面に出る個人に関する値（氏名・メールアドレス）、利用者が持ち込む権限の YAML、ブラウザに保存されるファイルの名前、E2E の報告。
- 画面は個人データを新しく保存しない。

## 3. 脅威と扱い（STRIDE の見方、画面の側）

| 脅威 | 例 | 扱い |
|---|---|---|
| なりすまし | 管理者でない利用者が道を直接入れる | 骨組みの `ADMIN_FORBIDDEN` と、サーバーの 403（NFR1.1） |
| 改ざん | 画面の本文に項目を足す・道の ID を差し替える | 画面は決めた項目だけを送り（NFR1.4）、判定はサーバー（U3・U4） |
| 否認 | 管理の操作をしていないと言う | 監査はサーバー（U3・U4）。画面は持たない |
| 情報の漏えい | 氏名・メールアドレス・YAML の中身がコンソール・保存・URL・E2E の報告に残る | NFR1.6・NFR1.11 |
| サービスの妨げ | 大きな YAML を送る・大きな確かめの応答で画面が固まる | 送る前の大きさの確かめ（NFR1.5）、サーバーの上限（U4）、描画を 100 件ずつにする（performance の NFR2.7・NFR2.8） |
| 権限の昇格 | 画面の押せない形を外して操作する | 判定はサーバー（NFR1.1）。ロールは管理の権限を与えない（U4） |
| クロスサイトスクリプティング | 名前・表示名に HTML を入れる | 文字として描く（NFR1.7・NFR1.12） |
| 保存の名前の悪用 | `Content-Disposition` に道の区切りを入れる | NFR1.10 |

## 4. コンプライアンスと品質の視点

- 個人に関する値: 画面は応答の氏名・メールアドレスを表示するだけで、保存・送信（外部）しない。テストの見本のメールアドレスは `example.com` だけで、実在しそうな氏名を置かない（`team.md`）。
- 公開のリポジトリ: E2E の報告と見本に秘密を置かない（NFR1.11）。
- ライセンス: 新しい依存を足さない（tech-stack の NFR6.5）。
- 監査は U3・U4 が持ち、画面は監査に代わる記録を持たない。

## 5. 受け入れた制約

- 画面の確かめ（大きさ・名前の規則・押せない形）は案内であり、画面を経ない要求はサーバーだけが守る。
- ブラウザの拡張機能や開発者の道具で、表示中の氏名・メールアドレスを読むことは防げない（表示する以上の守りは持たない）。

## 6. 上流との差

- 契約 C7 は確かめ・適用を multipart としていたが、画面は `application/yaml` の本文と指紋のヘッダー `X-Role-Transfer-Fingerprint` で送る（role の機能設計の Q8 A、この単位の機能設計の 1.2）。
- 書き出しのヘッダー `X-Role-Transfer-Exceeds-Import-Limit` を画面が読むため、共有の `ApiDownload` にヘッダーを足す（tech-stack の NFR6.6、この段の Q2 A）。

## 7. コード生成（B8）への引き継ぎ

- NFR1.1 の画面と API の組の表のテストを、画面ごとのテストか1つの表のテストのどちらに置くかを計画で決める。
- NFR1.10 のファイル名の関数と NFR1.5 の定数のテストを `roletransfer` に置く。
- NFR1.11 の報告の確かめを、流れの E2E と検査の E2E の両方に入れる。
