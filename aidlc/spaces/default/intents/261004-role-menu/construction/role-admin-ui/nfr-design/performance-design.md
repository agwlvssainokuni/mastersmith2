## 1. API の時間（NFR2.2・NFR2.4）

- API の時間は U3・U4 の目標（管理の API の p95 1 秒、import の確かめ 15 秒・適用 30 秒）をそのまま当て、U6 では測り直さない。U6 は要求の形を変えず（L2）、`api/*Api.test.ts` で形を確かめる。
- 確かめと適用は、サーバーの入口で同時に1つずつしか通らない（role の `RoleTransferSlot`）。画面の二重の送信の防ぎ（2節）と合わせ、1つの画面から重ねて送ることは無い。ほかの管理者と重なったときの `ROLE_BUSY` は `security-design.md` の 4節の文言。

## 2. 待ちと二重の送信（NFR2.10）

- L5（`useSlowNotice`）: 送信の開始で 5 秒の時計を始め、応答・失敗・画面を離れたときに止める。5 秒で「時間がかかっています」を出す。S7 の確かめと適用では、上限ちょうどのファイルで確かめは最大 15 秒・適用は最大 30 秒かかりうることを文に含める。
- 送信中は押したボタンを処理中（`Button` の `loading`）にし、フックが送信の最中を参照で持って、その間の呼び出しを捨てる。要求に独自の時間切れを置かない。
- 確かめ: 画面のテストで偽の時計を使い、4.9 秒で出ず 5 秒で出て応答で消えること、送信中の2回目の押下で API が呼ばれないこと（S3・S4・S5・S6・S7）。実時刻と `sleep` に頼らず、描画の後の値は `waitFor` で待つ。

## 3. 読み込みの扱い（NFR2.11・NFR2.12・NFR2.7・NFR2.8）

- **古い答えを捨てる**（L4）: 各フックが読み込みの世代を参照で持ち、読み込みを始めるたびに進める。答えを受けたとき世代が違えば捨てる。画面を離れたら世代を進める。要求は取り消さない（ApiClient に取り消しの口が無く、送った書き換えはサーバーで確定しうるため）。決まった間隔の自動の読み直しはしない。
- **カラムの表**（NFR2.12）: 1テーブルの全カラムを分割せずに描く（目安 100、悪い側 1,000）。各行の Select はネイティブの `select`（make-you-chic-ui の `Select`）で、開いた一覧はブラウザが描く。写し（L7）は対象の鍵で引く表で持ち、1件の変更で表全体を作り直さない（行の部品を `memo` にし、写しの値で比べる）。
- **確かめの大きな応答**（NFR2.7・NFR2.8、Q1 A）: 応答は JSON として1回読み、型の項目だけを写した値を画面の状態に持つ。描くのはロールの要約の表と、開いたロールの 100 件だけ（`changePaging` の範囲）。確かめた本文の文字列（最大 10 MiB）も同じ状態に持つ。適用の成功・ファイルの選び直し・画面を離れたときに、本文・指紋・結果を捨てる。
- 確かめ: 画面のテストで答えの順を入れ替えた2つの読み込み、画面を外した後の答え、偽の時計を進めても API が呼ばれないこと。`changePaging.test.ts` に fast-check（範囲が重ならず全件を覆う）。

## 4. 画面の時間の測り（NFR2.5〜NFR2.9、読み直しの R-03・R-07）

（承認の場の直し R-01・R-02 で、app-frame-ui の NFR 設計の Q1 A の形にそろえた。9節）

### 4.1 置き場と見本

- 測りのテストは U6 の検査のファイル（140 の案、L13）の中に1件置く。表示の設定の 20 組の繰り返しの外で、既定の1組（テーマ light・文字の大きさ md・ブランドカラー blue・既定の幅）だけで動く。E2E の本数に数えない。
- API は差し替えの口（`e2e/support/adminApiRoute.ts`）で遅れなく返す。見本の本文は、テストの準備で前もって `JSON.stringify` した文字列にし、口はその文字列を `route.fulfill` の `body` にそのまま渡す。今の口は `json` を受けて `reply` の中で直列化するため、直列化済みの本文（`body: string`）を受ける形を足す（互換の変更。既存の 120・130 は変えない。`logical-components.md` 3節の L13）。測りの中に直列化の時間を入れない。
- 見本: 100 カラムと 1,000 カラムのテーブル、25 ロール × 1万の変わる点の確かめの応答（関数で作り、画面の型で縛る）。

### 4.2 時計と聞き手

- 時計は画面の中の `performance.now()` の1つだけを使う。テストの側の時計と組にしない。聞き手と見張りは、測りのテストの中で `page.evaluate` を使って入れる。アプリのコードには入れない。
- 測り始めは、項目ごとに次のどちらかを画面の中の時計で取る。
  - **操作から測る項目**: 目当ての要素を押す直前に聞き手を入れ、`click`（Select は `change`）の捕捉の段で、`event.target.closest(目当ての選択子)` が当たったときだけ時刻を記録する。`pointerdown` からは取らない（Playwright の down と up の往復が入るため）。`once` と「最初の1回だけ」の記録にはせず、目当てでない押下は記録しない。
  - **応答から測る項目**: 要件が「応答を受けてから」と書く項目は、その要求の資源の時刻（`PerformanceObserver` の `resource`、`initiatorType` が `fetch` で道が当たる項目の `responseEnd`）を使う。同じ画面の時計で、ファイルの読み込み・要求の送信・差し替えの口の処理を含まない。コード生成の最初に、差し替えた応答でも項目が得られることを確かめ、得られなければ操作から測る形にして、その旨を記録する。
- 測り終わりは、`MutationObserver` で終わりの条件が満たされたのを見つけ、その後の次の `requestAnimationFrame` の時刻とする。条件は項目ごとの関数として測りのテストの中に書く（複数の要素が揃うこと・文の中身を含む）。
- テストの側は記録が揃うのを `expect.poll` で待ち、差を読む。

```ts
// 説明用の断片（操作から測る項目の聞き手の形だけ）
await page.evaluate((target) => {
  const w = window as unknown as { __u6Mark: { start?: number; end?: number } }
  w.__u6Mark = {}
  document.addEventListener('click', (event) => {
    if ((event.target as Element).closest(target)) w.__u6Mark.start = performance.now()
  }, { capture: true })
}, startSelector)
```

### 4.4 判定と記録（NFR2.9）

- 各項目を 5 回測る（NFR2.12 は1回）。1回ごとに画面を読み込み直し、聞き手と見張りを入れ直す。
- 判定は 5 回の中央値（小さい順の3番目）で行う。中央値が目標以内なら Met（最大だけが超えたときも Met とし、最大を記録する）。中央値が目標を超えたら Not Met。5 回のうち測れない回があれば、その項目は Unverified とし、理由を記録する。
- 添付には、項目ごとの 5 回の値・中央値・最大・1回目と、使った時計（画面の中の `performance.now()`）と測り始めの種類（`click`・`change`・`responseEnd`）を書く。名前と時間だけを書き、氏名・メールアドレスを書かない。
- **目標を超えたとき**（R-03）: 値は Build and Test が `Not Met` と値で記録し、承認の場で依頼者が扱いを決める。目標を緩めて満たしたことにはしない。統合は止めない（NFR2.9 のとおり記録だけ）。

## 5. 初回の JavaScript（NFR2.13、読み直しの R-04）

- 新しい3つの画面と `UserRolesDialog` は遅延読み込み（L1 の `lazy`）にする。
- `check-bundle-size.mjs` は入口から静的に読み込むファイルだけを数えるため、NFR2.13 の確かめは「入口の大きさが B8 の前と比べて増えていない（新しい画面が入口に入っていない）」こととする。台本は変えない。
- 遅延読み込みの3つの機能の塊の gzip の大きさは、Build and Test で `dist/.vite/manifest.json` から読んで記録だけする。

## 6. E2E の流れの前提（NFR6.3）

- F の流れのファイル（150 の案）は、始めに自分で版 2 の DSL（流れ用の見本。スキーマ・テーブル・メニューの名前に接頭辞 `E2EF_`）を管理の API で投入して適用する。前のテストの状態に頼らず、後始末はしない。番号は 040 より後で、U7 の I の流れの見本とも名前が重ならない（読み直しの R-08）。
- 流れの時間は測らない（成否は流れの通過だけ）。

## 7. 受け入れた制約

- 画面の時間は手元の1台・1つのブラウザで測り、記録だけにする。
- S7 の大きな応答の受け取りと読み込みの時間・メモリは画面では減らせない（応答の大きさは U4 の持ち物）。確かめた本文（最大 10 MiB）も画面に持つ（Q1 A）。

## 8. 上流との差

- Q1 A により、3節で確かめた本文の文字列を画面の状態に持つ形にした。
- NFR2.6・NFR2.7 の測り始めを、要求の資源の時刻 `responseEnd`（画面の中の時計）に固定し、JSON の読み込みと描画を含むと決めた（NFR 要件の読み直しの R-07。承認の場の直しで `route.fulfill` の直前から変えた、9節）。
- NFR 要件の NFR2.9 は「1回目と2〜5回目を分けて記録」とするが、判定を 5 回の中央値にした（app-frame-ui の承認の場の決定にそろえる、9節）。1回目・最大も記録する。
- NFR2.13 の確かめを「入口が増えていないこと」と読み、遅延読み込みの塊は記録だけにした（読み直しの R-04）。

## 9. 承認の場の決定と直し

- **決定**: 依頼者は NFR 設計の承認の場で Request Changes を選び、決定の文は「推奨の案のとおり直す」（直す範囲は各単位の読み直しの Major と、単位の間でそろえる3点）。この単位で直したのは R-01・R-02 で、ほかの指摘（R-03〜R-06）は直していない。
- **R-01（Major）**: 測り始めを `route.fulfill` の直前としていたが、今の `adminApiRoute.ts` は見本の関数の後に `reply` の中で直列化してから `route.fulfill` を呼ぶため、その時刻を取る手段が無く、数十 MB の直列化が測りの外に出るか中に入るかが定まらなかった。4節を次のように直した: 見本の本文は前もって直列化した文字列にし、口はそれを `body` にそのまま渡す（`adminApiRoute.ts` に直列化済みの本文を受ける形を足し、`logical-components.md` 3節の L13 の変更の対象に入れた）。測り始めは `route.fulfill` に置かず、操作から測る項目は `click`・`change` の捕捉の段（`closest` で目当てに当たったときだけ。`pointerdown` は使わない）、応答から測る項目（NFR2.6・NFR2.7）は要求の `responseEnd` にした。
- **R-02 とそろえる点2**: 時計を画面の中の `performance.now()` の1つに固定し、テストの側の `Date.now()` を外した（app-frame-ui の NFR 設計の Q1 A の形）。判定は 5 回の中央値で、最大と1回目も記録する。測り終わりの条件は項目ごとの関数で書く（app-frame-ui の読み直しの R-03 の注意を踏まえた）。
- `traceability.json` は NFR2.6 の target の言い方を合わせて直した。
