# Functional Design の質問 — U2 dsl-v2

単位 U2 dsl-v2（library。画面 `features/dsl` の小さな変更を含む）の機能設計の前に、決まっていない点を確かめます。読んだもの: 単位 `aidlc/spaces/default/intents/261004-role-menu/inception/units-generation/unit-of-work.md`・`unit-of-work-story-map.md`、要件 `requirements.md`、ストーリー `stories.md`（US5.2・US6.1、US3.1 の安全な読み込みの土台）、部品 `components.md`、ADR `decisions.md`（ADR-004・ADR-005・ADR-006・ADR-007）、契約 `contract-summary.md`（C3）、画面 `mockups.md`（S10）、Bolt の計画 `bolt-plan.md`（B1）、各段の質問の答えと承認の場の記録（監査ログ）、コード（`backend/src/main/java/cherry/mastersmith/dsl/**`・`dslmanage/**`・`backend/src/main/resources/dsl/dsl-schema-v1.json`・`db/migration/V5__u4_dsl_management.sql`・`frontend/src/features/dsl/**`、関係するテスト）。

## 決まっていること

上流・承認の場・`team.md`・`project.md`・コードで決まっていて、質問にしない点です。

### 範囲と進め方

- この単位は最初の Bolt（B1）で作る。終わりの条件は `bolt-plan.md` の B1 のとおり（版 2 の投入・プレビュー・適用・ダウンロード、版 1 は書式の版の誤り、既定の DSL の生成、メニューの深さの上限、版 1 の環境の起動、安全な YAML の読み込みの口、既存の DSL のテストの版 2 への書き換え、`./gradlew verify`）。
- 画面（`features/dsl`）の部分は、この段で `frontend-components.md` を作って設計する（Units Generation の承認の場の直し R-04）。
- DSL は書式の版 2 だけを受け付け、版 1 は読み替えない。形は複数のスキーマを受け付け、中身は対象DB の設定のスキーマ1つ（ストーリーの段の M1: B・F2: A・F3: C、ADR-005）。
- メニューの深さの上限は、新しい投入と履歴からの復元では拒否し、起動時の読み直しでは深さだけを検証から外し、深すぎる枝を出さずに警告のログ（DSL の本文と接続情報を含まない）を出す（M3: A、ADR-005、AC5.2.1〜AC5.2.4）。
- 既存の提供口 `ActiveDslModelProvider.current()` と `ActiveDsl`（`Present`・`Absent`）の形は変えない。版 1 の適用中の DSL は起動時に `Absent` になる（契約 C3、AC6.1.6）。
- `DslModel` は `formatVersion` 2 で、`schemas`（スキーマ名・表示名と、その下のテーブル）と `menus` を持ち、メニューの項目はテーブルをスキーマ名とテーブル名の組で指す。テーブル名はスキーマの中でだけ一意（契約 C3、`components.md` の DslDefinition）。
- 上限つきの安全な YAML の読み込みの口（`SafeYamlReader`）を `dsl.service` に置き、上限は呼ぶ側が渡す。既存の `SafeYamlParser`・`LimitingParser` を包み、守りの実装は1か所のまま。結果は区分（TOO_LARGE・TOO_DEEP・TOO_MANY_ALIASES・TAG_NOT_ALLOWED・DUPLICATE_KEY・SYNTAX）と位置だけで、例外の文を出さない。DSL の JSON Schema の検証は口に含めない。`DslBoundaryArchitectureTest` の `parseAndValidateStayInside` は変えない（ADR-007、契約 C3 と承認の場の直し R-04）。
- 照合（対象DB との違い）と既定の DSL の生成は、設定のスキーマだけを扱う（AC6.1.4・AC6.1.9）。

### 既存のコードで確かめたこと

- **版の誤りの応答**: 今の `DefaultDslReader` は 大きさ → 読み込み → 書式の版 → 構文 → 意味 の順に確かめ、版の誤りは種類 `UNSUPPORTED_VERSION` の誤りになる。投入と履歴の復元（`DslLifecycle.restore`）は、どちらも既存の `DSL_INVALID`（422、誤りの一覧つき）で拒否し、プレビューと適用中は変わらない。そのため、版 1 の拒否（AC6.1.2・AC6.1.7 の復元）に新しい code は足さない。文言（`DslErrorMessages` の `VERSION_UNSUPPORTED`・`VERSION_MISSING`）を画面の段の文（「書式の版 1 は使えません。書式の版 2（スキーマの階層あり）で書いてください。既定の DSL を生成し直すと版 2 で得られます。」、`mockups.md` の 10節）に合わせて直す。
- **起動時の読み直し**: `dslmanage.service.DslStartupLoader` が適用中の版を `DslReader.read` で読み、通らなければ ERROR を1件（識別の先頭12文字と誤りの種類だけ）出して「無い」で起動を続ける。版 1 の環境はこの仕組みで `Absent` になる（ADR-006 の見通しどおり）。深さだけを外す読み方は、この読み直しにだけ足す。
- **内部DB の表**: `dsl_previews`・`dsl_applied_revisions` は本文（`yaml_bytes`）と識別だけを持ち、版の列は無い。この単位で Flyway の移行は要らない（`team.md` の「前進のみ・前の版が動く」に触れない）。
- **対象DB の設定のスキーマ名**: `TargetDbProperties.schema` は種類によらず必須（MySQL・MariaDB ではデータベース名と同じ値を入れる）。使える設定（`TargetDbSettings.Usable`）なら必ずスキーマ名があり、`TargetSchema.schemaName` で読める。既定の DSL の生成でスキーマ名が無い場合は起きない。PostgreSQL の `database`（接続の項目）は DSL に書かない。
- **スキーマ名を書かないことを確かめている既存のテスト**: `DslTreeBuilderTest`・`TargetSchemaDslGeneratorTest`・`AbstractDefaultDslGeneratorIT`・`DslTargetDbIT` は「生成した DSL にスキーマ名が無い」ことを確かめている（前の Intent の BR5.3）。ストーリーの要件との差 D1 のとおり、スキーマ名は DSL に書くため、これらは「スキーマ名は書き、接続先・ポート・ユーザー名・パスワード・JDBC の URL は書かない」形に書き換える。
- **版 1 の DSL を持つテストと道具**: バックエンドのテスト（`dsl/valid-sample.yaml`・`dslmanage/generate/dept_mst.yaml` と 9 つのテストのクラス）、画面のテスト（`features/dsl` の 5 ファイル、`shared/api-client/apiClient.download.test.ts`）、E2E（`frontend/e2e/040-dsl-admin.e2e.ts`）、負荷の試験の道具（`perf/make-pattern-dsl.mjs`・`perf/ui/dsl-ui-lang.mjs`）が版 1 の DSL を作る・持つ。すべて版 2 に書き換える（AC6.1.10。既存の E2E の書き換えは `team.md` の本数に数えない）。
- **カバレッジ**: `dsl` と `dslmanage` の下のパッケージは `packagesJudgedByTotal`（`backend/build.gradle.kts`、7 パッケージ）に入っておらず、すでにパッケージごとの下限（行 80%・分岐 70%）の対象である。この単位で一覧に手を入れる作業は無い。手を入れたパッケージが下限を割らないことを B1 の `verify` で確かめる。
- **境界テスト**: `DslBoundaryArchitectureTest`・`DslManageBoundaryArchitectureTest`・`DslManageGenerateBoundaryArchitectureTest` がある。新しく足す境界テストは無く、既存のものを緩めない。`dsl` は `targetdb`・`dslmanage` に依存できないため、対象DB の設定と照らす確かめは `dslmanage` の側に置く。
- **API の分類の注釈**: 注釈の定義と既存のすべての API への印は U1（B2、この単位の後）が行う（Units Generation の承認の場の直し R-03）。この単位は新しい API を足さないため、注釈を付ける作業は無い。既存の DSL の API の道（`/api/admin/dsl/**`）も変えない。
- **画面の部品**: S10 の変更は、すでに使っている make-you-chic-ui の `Alert`（`warning`・`danger` の種類がある）・`Button`・`Card`・`Tabs`・`Tooltip`・`Modal` と、素の表（`mycui-table` の見た目）で足りる。make-you-chic-ui への新しい依頼は無い（`vendor/make-you-chic-ui` のソースで確かめた）。
- **TraceAspect**: `dsl.service` は追跡の対象の層で、引数と戻り値が TRACE のログに文字列で出る。`SafeYamlReader` の引数（本文のバイト列は `[B@…` の形で中身は出ない）と上限の値は出てよいが、戻り値の木をそのまま文字列にすると、利用者が投入した YAML の中身（権限の YAML のロールの名前など）がまるごと出る。結果の型は文字列にするとき区分と大きさだけを出す形にする（下の「設計で決める細部」）。

### 設計で決める細部（質問にしない。まとめの確認で確かめる）

- **起動時に深すぎる枝を落とす決まり**: 深さが上限を超える項目は、その下の子ごと落とす。落とした結果、テーブルも子も持たなくなったまとまりは、上へさかのぼって落とす（今の `DslMenuItem` の「テーブルか子の少なくとも一方を持つ」決まりを保つ）。警告のログは1件で、落とした項目の数と上限の値、識別の先頭12文字だけを出す。
- **深さの誤りの出し方**: 意味の誤り（`SEMANTIC`）として、上限を超えた最初の段の項目ごとに1件出す（その下の子孫は重ねて出さない）。位置は既存の形（行・列・JSON Pointer の道）で、文言に上限の値を埋める（AC5.2.2、`mockups.md` の 10節）。
- **安全な読み込みの口の上限の項目**: 契約 C3 の `maxBytes`・`maxDepth`・`maxAliases` に、別名を展開した後の節の数の上限（今の `MAX_EXPANDED_NODES` に当たる）を足す。別名の展開の爆発で止まらないこと（AC3.1.7）を、呼ぶ側の上限で守るため。今の `RECURSIVE_ALIAS`・展開後の節の数の超過は区分 `TOO_MANY_ALIASES` に、文字の誤り（UTF-8 で読めない）は `SYNTAX` に写す。DSL の読み込みは今の `DslFormat` の値で同じ部品を使う。
- **JSON Schema の公開**: 版 2 の書式を `dsl/dsl-schema-v2.json` として足し、同じ形の道で公開する。アプリが受け付けない版 1 の書式のファイルは置かない。
- **既定の DSL の生成のスキーマの表示名**: 対象DB にスキーマの説明が無いため、表示名の ja・en ともスキーマ名にする（テーブルの説明が無いときの今の扱いと同じ）。メニューは今と同じく平ら（深さ 1）。

## Q1 版 2 の YAML の形と、テーブルを指す書き方

背景: 契約 C3 で「版 2 の JSON Schema の具体の形（schemas の書き方）」が未決のまま残っています。投入する人が書く形と、公開する JSON Schema が決まります（AC6.1.1・AC6.1.5、契約 C3）。メニューの項目がテーブルをスキーマ名とテーブル名の組で指すことは決まっていますが、外部キーの参照先（`referencedTable`）と選択肢の出どころ（`options.table`）の書き方は決まっていません。

A の形の例:

```yaml
version: 2
menus:
  - label: {ja: 受注明細, en: Order items}
    table: {schema: sales, name: order_items}
schemas:
  sales:
    label: {ja: 販売, en: Sales}
    tables:
      order_items: { ... 今のテーブルと同じ ... }
```

A. `schemas` をスキーマ名をキーにした対応表にし、各スキーマに `label`（ja・en）と `tables`（今と同じ、テーブル名をキーにした対応表）を置く。メニューの `table` は `{schema, name}`。外部キーの `referencedTable` と選択肢の `options.table` は、同じスキーマの中のテーブル名（今の文字列）のままとする（推奨: 今の `tables` と同じ書き方で、スキーマ名・テーブル名の重なりは既存の重複キーの誤りで落ちる（AC6.1.5）。中身は1つのスキーマだけのため、参照をスキーマの中で閉じても困らず、複数のスキーマの間の参照が要る時は、項目を足す形で後から広げられる）
B. A と同じだが、外部キーの参照先と選択肢の出どころも `{schema, name}` で書く（後の複数のスキーマの間の参照に先に備える。生成する DSL と書く量が増える）
C. `schemas` を並び（各項目に `name` を持つ）にする。スキーマ名の重なりは意味の検証で落とす（JSON Schema では重なりを落とせない）

## Q2 設定のスキーマと名前の違うスキーマ・2つ目のスキーマを受け付けるか

背景: ストーリーの AC6.1.4 が機能設計に回した点です。`dsl` は対象DB の設定を知らない（境界テスト）ため、名前の確かめを置く場所も決まります。権限の対象とメニューは DSL のスキーマ名を鍵に使います（契約 C3・C5・C9）。

A. 意味の検証でスキーマは1つだけを受け付け、2つ以上は意味の誤りとして拒否する。名前は問わない。名前が対象DB の設定のスキーマと違うときは、照合で「DSL のスキーマが対象DB の設定のスキーマと違うため照合できない」という警告を1件出し、テーブル・カラムは比べない（推奨: 検証が `dsl` の中で閉じ、対象DB の設定が無い・接続できないときも同じ結果になる。2つ以上を後で受け付けるのは、決まりを緩めるだけで済む）
B. スキーマは1つだけで、名前が対象DB の設定のスキーマと違えば、投入・復元・生成のときに `dslmanage` の側で拒否する（対象DB の設定が無い・使えないときは確かめずに受け付ける。起動時の読み直しでは確かめない）
C. 2つ以上も受け付ける。照合と既定の生成は設定と同じ名前のスキーマだけを扱い、ほかのスキーマは「照合の対象外」の警告にする。権限の設定とメニューはすべてのスキーマを使う
