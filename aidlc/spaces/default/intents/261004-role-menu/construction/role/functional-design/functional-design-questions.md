## 決まっていること

### 業務の決まり（要件・ストーリー・ADR）

- ロール・権限の設定・割り当て・import・export は管理者（管理者の印を持つ利用者）だけが行える。ロールは管理の権限を与えず、管理の API の可否と最後の有効な管理者の数え方は管理者の印だけで決まる（FR1.3、要件 C1、stories.md の「ロールは管理の権限を与えない」）。
- 組み込みのロールは置かない。`team.md` の★「組み込みの役割の有無と、その削除・権限の取り上げの保護」は「当たらない」（SM6 A）。
- 権限の昇格の防止は「管理者の印を持たない利用者は、ロール・グループ・割り当て・権限を一切変えられない」と読む。管理者は、自分の作業ロールに無い権限を持つロールも、自分や他人に割り当てられる（SM5 A、AC2.2.12）。
- `team.md` の★「自分の役割を外す操作の扱い」「最後の有効な管理者の役割での数え方」: 自分のロールをすべて外す操作は受け付け、作業ロールは無くなるが管理の API は成功のまま。最後の有効な管理者の保護は今までどおり管理者の印で数える（AC2.2.13、要件 C1）。役割では数えない。
- `team.md` の★「変更の前に出したトークンの扱い」: 権限・割り当て・作業ロールはトークンに入れず、要求ごとに内部DB から求める（ADR-003）。変更の前に出したアクセストークンのままの次の要求で結果が変わることを、決めた側の動作として明示してテストする（stories.md の「次の要求から」、AC1.2.5・AC2.2.3）。
- 主権限は「設定なし・NONE・READ・FULL」をスキーマ・テーブル・カラムに、補助権限 CREATE・DELETE は「設定なし・可・不可」をスキーマ・テーブルに持つ（カラムは主権限だけ）。実効の値は直近の上位の明示の値を継承し、スキーマまで設定なしなら NONE・不可。CREATE と DELETE は互いに影響しない（FR2.1〜FR3.3）。
- 設定は対象の名前（スキーマ名・テーブル名・カラム名）で持ち、その都度適用中の DSL と名前で照らし合わせる（写しを持たない、ADR-004）。DSL に無い対象の設定は持ち続けるが解決では使わず、画面では「今の DSL に無い」と出して消せる。同じ名前が DSL に戻ればまた効く（FR2.4、AC1.2.7・AC1.2.8）。
- 利用者のロールは、直接の割り当てとグループ経由の割り当ての和（同じロールは1つ）。実効の権限は作業ロールだけで決まり、合算しない（FR4.3・FR5.1）。
- 作業ロールは利用者ごとに内部DB に覚え、次のログインでも同じロールで始める（FR5.4）。覚えている作業ロールが自分のロールでなくなったときは、決めた順の最初のロールに読み替える。読み替えは読み取りの要求で保存を書き換えず、監査にも残さず、本人への案内も出さない（契約 C5、AC4.1.15、SM8 B）。「最初」の順序は Q1。
- 作業ロールの切り替えで今と同じロールを選んだときは何も変えない成功（204）で、監査に残さない。自分に無いロールと存在しないロールへの切り替えは同じ `ROLE_NOT_ASSIGNED`（409）。切り替えの API は利用者を指す値を受け取らず、主体は要求の文脈から読む（契約 C8、AC4.1.3・AC4.1.11〜AC4.1.13）。
- 変えるものが無い管理の操作（同じ名前への変更・同じ値での保存・重ねての割り当て・割り当てていないものの外し・変わる点の無い import の適用）は `ROLE_NO_CHANGE`（409）で拒否し、監査に残す（SM4 C）。
- 同じロールの権限の同時の保存は後勝ちで、監査に両方の前後の値を残す（SM2 A、AC1.2.12）。
- 画面を開いた後に DSL から消えた対象への保存は `PERMISSION_TARGET_NOT_IN_DSL`（409）で拒否し、消す操作（`POST .../permissions/clear`）は受け付ける（契約 C7。AC1.2.13 の「どちらにするか」は契約の段で拒否に決まっている）。
- 割り当てに足せるのは登録の終わった利用者（`users` の行がある人）だけ。招待中の人は候補に出ず、利用停止の利用者には割り当てられる（要件との差 D7、AC2.2.16）。
- import は2段（確かめ → 適用）。確かめは指紋を返してサーバーは保存せず、適用で同じ YAML と指紋を送り、検証し直して作り直した一覧の指紋が違えば `ROLE_TRANSFER_STALE`（409）で拒否する（契約 C7、CQ1: A、FR7.3a）。ファイルにあるロールだけを置き換え（ファイルの中の対象だけの状態にする。足し合わせではない）、無いロールは作り、ファイルに無いロールは残す。グループ・メンバー・割り当ては含めない（FR7.1・FR7.2、AC3.1.3）。適用は1つのトランザクションで、途中で失敗したら変わらない（NFR3.2）。適用済みの DSL が無いときは確かめ・適用とも `DSL_NOT_APPLIED`（409）、export は DSL の有無によらず書ける（FR7.3b）。
- 権限の YAML は信頼できない入力として、`dsl.service` の `SafeYamlReader`（上限は role が渡す `SafeYamlLimits(maxBytes, maxDepth, maxAliases, maxExpandedNodes)`、結果は `Parsed(木, 位置を引く口)` か `Rejected(区分, 行・列・道)`）だけで読む。`dsl.parse` には依存しない（ADR-007、`aidlc/spaces/default/intents/261004-role-menu/construction/dsl-v2/functional-design/functional-spec.md` の 3.8）。拒否は `ROLE_TRANSFER_INVALID`（400）の `errors` に位置と種類を載せ、部品の例外の文を含めない（FR7.4、`project.md` の Forbidden）。
- 権限の対象は版 2 の DSL のスキーマ→テーブル→カラム。この Intent ではスキーマは対象DB の設定の1つ（SF2 A、dsl-v2 の BR1.3）。DSL の名前は対応表のキーで、大文字と小文字を区別する。

### API（契約 C7・C8・C5）

- 道と状態コードは契約 C7（`/api/admin/roles` の下、`/api/admin/groups/{groupId}/roles`、`/api/admin/users/{userId}/roles`、`/api/admin/role-transfer/{export,check,apply}`）と C8（`/api/me/work-role`、`/api/me/permissions/...`）のとおり。管理の API は U1 の注釈 `ApiAccess` に `ADMIN`、自分の API は `AUTHENTICATED` を付ける（`aidlc/spaces/default/intents/261004-role-menu/construction/cross-cutting/functional-design/rules.md` の BR1）。`/api/admin/**` は既存の `AdminPaths` と管理者の印の決まりで、`/api/me/**` は `/api/**` の既定のログイン必須で守られるため、`SecurityRuleContributor` は足さない（group と同じ）。停止中の利用者は既存のアクセストークンの認証で通らない。
- 拒否の code と状態コードは契約の表のとおり（`ROLE_NOT_FOUND` 404・`ROLE_NAME_DUPLICATE` 409・`ROLE_IN_USE` 409・`ROLE_NO_CHANGE` 409・`ROLE_NOT_ASSIGNED` 409・`PERMISSION_TARGET_NOT_IN_DSL` 409・`DSL_NOT_APPLIED` 409・`ROLE_TRANSFER_INVALID` 400・`ROLE_TRANSFER_STALE` 409）。`GROUP_NOT_FOUND`・`GROUP_BUSY` は group の定義、`USER_NOT_FOUND` は `user.domain.UserProblemTypes`（group が B3 で移す）、`PAYLOAD_TOO_LARGE`・`VALIDATION_FAILED`・`AUTHENTICATION_REQUIRED`・`ACCESS_DENIED` は既存の共通の定義を使い回す（`team.md` の Code Style）。コードで確かめた既存の code に `ROLE_`・`DSL_NOT_APPLIED`・`PERMISSION_` で始まるものは無く、重ならない。
- 解決の口は契約 C5 の `EffectivePermissionResolver`（`effectiveWorkRole`・`snapshotFor`・`resolve`）。有効な作業ロールを決めるのはこの口だけで、C8 の GET・U5 の業務のメニュー・後の Intent はすべてこの結果を使う。写しは1回の要求の中だけで使い、要求をまたいで持ち越さない（キャッシュは置かない。重さは NFR 要件・NFR 設計で確かめる、ADR-006）。
- 一括代入の防止: ロールの作成・名前の変更の本文は `name` だけ、割り当ての本文は `userId` か `groupId` のどちらか一方だけ、作業ロールの切り替えは `roleId` だけを受け、ほかの項目を足しても反映しない（AC1.1.10・AC2.2.11・AC4.1.12）。

### group・dsl-v2・cross-cutting から引き継ぐこと（`construction/group/functional-design/functional-spec.md` の 8・9節）

- **名前の規則**（group の Q1: A、BR1.1〜BR1.5 にそろえる）: 前後の空白（全角を含む）を取り除いてから判定・保存し、長さは 1〜64（コードポイント）。制御文字は拒否。重なりは大文字と小文字を区別せず、全角と半角は別の文字。今と同じ名前への変更は `ROLE_NO_CHANGE`。大文字・小文字だけの変更は受け付ける。
- **監査の線引き**（group の Q5: A、BR8.2・BR8.3）: 業務の理由の拒否はすべて操作ごとの種類で結果 FAILURE と理由を付けて残す。入力の誤り（400）・排他の待ちの上限切れ（BUSY）・読み取りは残さない。
- **detail**（group の Q6: A、BR8.5〜BR8.7）: キーを決めた型から作る JSON の文字列で、16,384 文字まで。超えそうなときは role が要約（数と先頭の何件か）に切り替え、途中で切らない。パスワード・トークン・ハッシュ値・メールアドレス・氏名を入れない（入れるのは ID・ロールとグループの名前・権限の値・数だけ）。U3 が足す `target_role_id`・`target_group_id`・`detail` の列と、ロール・グループ向けのファクトリーを使う。
- **グループの行の排他**（group の Q2: A、BR5.3）: グループへのロールの割り当て・外しは、自分のトランザクションの中で `GroupMembershipQuery.lockForAssignment(groupId)` を呼んでから書く。`Busy` なら巻き戻して `GROUP_BUSY`（409、監査なし）、グループが無ければ `GROUP_NOT_FOUND`（404）。割り当ての表からグループへの外部キー（削除の制限）も置く（BR5.4）。
- **問う口の実装**（group の Q3: A・Q4: A）: `GroupDeletionGuard` の `canDelete(groupId)` と `assignedRoleCounts(groupIds)`（渡した ID のすべてにキーを返し、無ければ 0。数はグループへの直接の割り当ての数）を実装する。B3 で `role` のパッケージに置かれる仮の実装（0 件・Allowed）を B5 で本物に置き換え、仮の実装が残っていないことを B5 の終わりの条件に入れる。グループの削除と割り当ての追加の同時の重なり（AC2.1.5 のロールの側）を B5 で待ち合わせのテストにする。
- **DSL の読み取り**（dsl-v2）: `ActiveDslModelProvider.current()` が `Absent`（適用中が無い・版 1 で読めない）なら DSL が無い扱い（AC6.1.6）。`Present` のモデルはスキーマ→テーブル→カラムの木。

### 漏えいと TRACE のログ（`team.md`・`project.md`）

- 割り当ての一覧（C7 の `RoleAssignments`）と利用者のロールの読み取りに出る氏名・メールアドレスは個人に関する値で、`TraceAspect` が web・service・domain・repository の引数と戻り値を TRACE に出すため、すべての経路で伏せ字の型で受け渡す（既存の `UserSummary`・`RedactedText`）。応答にパスワードのハッシュ値・招待のトークンのハッシュ値・ロックの判定の内部の値を含めない。TRACE を有効にした `RoleSecretLeakIT`（仮の名前）で確かめる（AC2.2.6、NFR1.6）。
- 一意の制約・主キー・外部キーの違反や排他の上限切れの例外の連なりには行の値が入りうるため、`TraceAspect` の対象の層の外へ出さず、受けた所でクラスの名前だけをログに出す（`project.md` の学び）。権限の YAML の木の中身もログに出さない（`SafeYamlResult` の文字列は区分・位置・節の数だけ）。

### 作りの決まり（`team.md` の Code Style）

- パッケージは `cherry.mastersmith.role` の下に `web`・`service`・`domain`・`repository`（YAML の書式の読み書きは用途名の下位パッケージ、例 `role/transfer` に置いてよい）。トランザクションの境界は service の層だけ。DTO は `record` の `XxxRequest`・`XxxResponse`。コンストラクター注入のみ。
- 業務処理の層は想定内の失敗を結果の型（sealed interface の record）で返し、web の層が `switch` で尽くして `BusinessException` に変える。code の定数は `role.domain.RoleProblemTypes`、一覧は `role.service.RoleProblemTypeCatalog`。
- `role` のテストに `RoleBoundaryArchitectureTest` を置き、`role` が依存してよい機能（`group` の service と domain、`user` の service と domain、`dsl` の service と domain、`common`）と、`role` に依存してよい機能（`navigation`・`audit`）を書く。既存の境界テスト（`DslBoundaryArchitectureTest` の `parseAndValidateStayInside` など）は緩めない。
- 同時の重なりの待ち合わせは既存の `UserAdminBarrier`（本番は何もしない実装、テストは `@Primary`）と同じ形の口を `role` に置き、テストの手伝いは `src/test/java/cherry/mastersmith/role/testsupport` に置く。
- 継承の解決は純粋な関数にし、jqwik の性質ベースのテストを当てる（AC1.2.9・AC4.1.21、NFR6.2）。

### カバレッジとほかの機能への手入れ（`team.md` の Testing Posture）

- B4〜B6 で本体（`src/main`）に手が入る見込みのパッケージは、`role.*`（新しい）、`audit.domain`（`AuditEventType`・`AuditFailureReason` に種類と理由を足す）、`audit.service`（`AuditEventListener` に role の出来事の受け取りを足す）。どれも `packagesJudgedByTotal`（`backend/build.gradle.kts`。`access.service`・`audit.repository`・`common.error.domain`・`common.error.service`・`common.health`・`common.i18n.domain`・`common.web`）に入っていない。
- 本文の大きさの道ごとの上限は、既存の `common.web.RequestBodyLimitRoute`（record）の部品を `role.web` の設定で足すだけで、`common.web` の本体には手を入れない（`dslmanage.web.DslWebConfig` と同じ形）。413 は既存の `GlobalExceptionHandler`（`common.error.web`。一覧に入っていない）が受ける。`access`・`auth` の本体には手を入れない（作業ロールは専用の API で渡し、ログインと更新の応答は変えない。CQ3: B）。

### Flyway と戻し（`team.md` の Deployment）

- B3 の移行（V10 から。グループ・メンバー・監査の列）の後に、role の表（ロール・権限の設定・割り当て・作業ロール）を足す移行を B4・B5 で足す。表を足すだけで既存の列は消さず、`users.admin_flag` は残す（要件 C2、`team.md` の「広げてから縮める二段」）。前の版のアプリは新しい表を知らないまま起動する（`ddl-auto: validate` は余分な表を許す）。この Intent は行を移す移行を持たない（管理者の印を役割へ移さない）ため、「戻したときの権限のずれ」の確かめは、戻した版で管理の権限が管理者の印のまま変わらないことの確かめになる（配備の段へ引き継ぐ）。

## この段で決める設計の要点（質問にしない案。まとめの確認で確かめる）

- **一覧のページ送りと並び**: ロールの一覧は group と同じく既存の `common.paging.Paging`（`page` だけを受け、1ページ 20 件）に合わせ、並びはロールの ID の順にする（Q1 の推奨とそろう）。契約 C7 の `RolePage` の形は変えない。一覧の `userCount`・`groupCount` は直接の割り当ての数（グループ経由の利用者は数えない）。`ROLE_IN_USE` の `assignedUsers`・`assignedGroups` も同じ数え方にする（AC1.1.8 の「利用者 2・グループ 1」）。作業ロールの選択肢（C8 の `roles`）と S5・S9 の読み取りは全件を返す（ロールは 100 程度まで、NFR2.1）。
- **拒否の判定の順**: 名前の変更は 入力（名前の規則）→ ロールの有無 → 変えるものが無い → 名前の重なり（group と同じ）。削除は ロールの有無 → 割り当ての数（利用者・グループのどちらかが 0 でなければ `ROLE_IN_USE`）。割り当ては 入力（`userId` と `groupId` のちょうど一方）→ ロールの有無 → 相手の有無（`USER_NOT_FOUND`・`GROUP_NOT_FOUND`）→ すでに割り当て済み。外しは ロールの有無 → 割り当てていない（存在しない利用者・グループも `ROLE_NO_CHANGE`。契約 C7 の外しの応答に 404 の相手は無い。group のメンバーの外しと同じ読み）。権限の保存は 入力（値・カラムへの CREATE と DELETE・名前の長さ）→ ロールの有無 → DSL の有無 → 今の DSL に無い対象への値の設定 → 変えるものが無い。
- **権限の保存（PUT）の意味**: `entries` に載せた対象だけを、その値（null は「設定なし」）に置き換え、載せていない対象は変えない（差分の保存）。`scope` の外の対象を `entries` に入れたら入力の誤り。すべての値が「設定なし」になった対象は行を消す（行があるのは、どれかの値が設定されている対象だけ）。今の DSL に無い対象は、「設定なし」へ戻す（消す）entry だけを受け付ける。2人の保存の後勝ちは、対象ごとに後の保存の値が残る形になる（違う対象を変えた2つの保存は両方残る）。
- **木の API**: 1段目はスキーマ、スキーマを開くとテーブル、テーブルを開くとカラムを返し、開いた階層の分だけを読む（FR11.2）。今の DSL の対象と、設定だけがある対象（今の DSL に無い、`inCurrentDsl: false`）を名前で合わせて返す。今の DSL に無いテーブルの下のカラムも、設定があれば返す（消せるように）。並びは DSL の順、今の DSL に無いものはその後に名前のコードポイントの順。`inheritedFrom` は `EXPLICIT`・`TABLE`・`SCHEMA`・`DEFAULT`。`inMenu` はテーブルの実効の主権限が NONE でないか（AC1.2.16、新しいデータを持たない）。
- **名前の照らし合わせ**: 設定の対象の名前は DSL のキーと同じく大文字と小文字を区別して完全一致で照らす（前後の空白も取り除かない）。対象の名前の長さは 1〜128（コードポイント。主な DB の識別子の上限 128 に合わせる）で、超える名前・制御文字を含む名前への設定は入力の誤り。列は UTF-16 のサロゲートペアを見込んで 256 文字で取る（group のレビューの R-03 の手当て）。
- **ロールの名前の列**: 名前の重なりを判定する鍵（大文字と小文字をそろえた値）は Java で1か所で作って通常の列に保存し、一意の制約を置く（DB の生成列の小文字化と Java の小文字化が食い違う問題を避ける。group のレビューの R-04 の手当て。group の承認の場の決着が違えば、それにそろえる）。名前の列は 128 文字、鍵の列は小文字化の膨らみを見込んで 256 文字で取る。
- **違反の読み替えと失敗の監査**（group のレビューの R-01・R-02 の手当て）: 名前の重なりは書く前にトランザクションの中で鍵を読んで判定し、同時の作成が重なって一意の制約の違反になったときは、そのトランザクションを巻き戻した後に、書き込みの無い新しいトランザクションで失敗の出来事（`ROLE_NAME_DUPLICATE`）だけを出す（巻き戻しの印が付いたトランザクションで確定させない）。一意の鍵の待ちの上限切れは `ROLE_BUSY`（Q3）に読み替える。割り当ての主キーの違反は `ROLE_NO_CHANGE` に同じ形で読み替える。同じ名前の同時の作成・同じ割り当ての同時の追加が違反になるか待ちの上限切れになるかは、NFR 設計の捨ての試しのコードで確かめる（`project.md` の学び）。
- **ロールの削除で消すもの**: 削除は、割り当てが 0 のときに、そのロールの権限の設定と、そのロールを指す作業ロールの保存を同じトランザクションで消してから行を消す（覚えている作業ロールは削除を止めない、AC1.1.13・AC4.1.14）。
- **作業ロールの保存は割り当ての変更で書き換えない**: 割り当てを外しても、そのロールを指す作業ロールの保存は残し、読みで「最初のロール」に読み替える（契約 C5 の「保存は書き換えない」）。そのため、同じロールが後でまた割り当てられると、覚えていた作業ロールに戻る（利用者が切り替えたのではないため監査に残らない）。グループのメンバーの外し（U3）は role を知らないため、どの経路でも同じ振る舞いにそろう。
- **YAML の書き出しの並びと読み込みの照らし方**: 書き出しは、ロールを Q1 の順、スキーマ・テーブル・カラムを名前のコードポイントの順に並べ、設定のある対象だけを書く（往復で変わる点が出ない、AC3.1.14）。今の DSL に無い対象の設定も書く（AC3.1.15）。読み込みはロールを名前の鍵（大文字と小文字をそろえた値）で今のロールと照らし、当たれば置き換え（名前は変えない）、当たらなければ作る。ファイルの中で鍵が重なるロールは中身の誤り。YAML の値の誤り・カラムへの CREATE と DELETE・名前の規則の違反・知らない項目は、確かめの段で位置（ロールの名前・対象・行）と種類つきの `ROLE_TRANSFER_INVALID` にする（AC3.1.12）。
- **指紋**: 作り直した変わる点の一覧を、ロールの鍵の順 → 対象（スキーマ・テーブル・カラムの名前のコードポイントの順）に並べ、各行にロールの名前・作る／置き換え・置き換えるロールの ID・対象・前後の値・今の DSL にあるかを入れ、適用中の DSL の識別（`dslHash`。無ければ空）を足して SHA-256 の 16 進数にする。ロールの削除と同じ名前での作り直し・DSL の適用し直し・別の管理者の保存のどれでも指紋が変わる（AC3.1.4）。
- **import の適用の排他**: 適用は、置き換えるロールの行をロールの ID の昇順に排他してから一覧を作り直して指紋を比べ、書き換える（Q3 の答えが A のとき）。新しく作るロールは名前の鍵の一意の制約で守る。
- **監査の種類と理由**: 種類は契約 C10 の `ROLE_CREATED`・`ROLE_RENAMED`・`ROLE_DELETED`・`ROLE_PERMISSION_CHANGED`・`ROLE_ASSIGNED`・`ROLE_UNASSIGNED`・`ROLE_TRANSFER_APPLIED`・`WORK_ROLE_SWITCHED`（いずれも 32 文字以内）。失敗の理由（`AuditFailureReason`）に `ROLE_NOT_FOUND`・`ROLE_NAME_DUPLICATE`・`ROLE_IN_USE`・`ROLE_NOT_ASSIGNED`・`PERMISSION_TARGET_NOT_IN_DSL`・`DSL_NOT_APPLIED`・`ROLE_TRANSFER_STALE` を足し、`USER_NOT_FOUND`・`NO_CHANGE` は既存、`GROUP_NOT_FOUND` は group が足す値を使う。業務の拒否は失敗として残す（`ROLE_NOT_ASSIGNED` の切り替え、`ROLE_TRANSFER_STALE`・`DSL_NOT_APPLIED`・`ROLE_NO_CHANGE` の適用を含む）。import の確かめ（`check`）は設定を変えないため、成功も拒否も残さない。作業ロールの切り替えの行は、操作した人と対象の利用者を同じ ID にし、`target_role_id` に切り替えた先、detail に前の有効な作業ロールの ID と名前を入れる。
- **権限の保存の detail**: 1回の保存で変わった対象ごとの前後の値（主権限・CREATE・DELETE）を入れる。1つの表の分（最大 100 カラム）で名前が長いと 16,384 文字を超えうるため、超えるときは変わった対象の数と先頭の何件かの要約にする。
- **作業ロールの切り替えの表と口**: 作業ロールの保存は利用者ごとに1行（利用者の ID が主キー、ロールの ID と更新の時刻）。切り替えは保存の行を書く（無ければ作る）。
