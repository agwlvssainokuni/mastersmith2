## 決まっていること

### group の NFR 設計の試しの結果で足りるもの（T1〜T7 を使い回し、role では試し直さない）

- 版は Spring Boot 4.1.1・Hibernate 7.4.5.Final・HikariCP 7.0.2・H2 2.4.240・Java 25 で、group の試しと同じ。表の形（名前の鍵の一意の制約、組の主キー、外部キー）も role の設計と同じ種類のため、次はそのまま使う。
  - T1〜T3: 一意の鍵・主キーの待ちはヒントが効かず、H2 の既定の約 2,000 ms で切れる。重なった側は違反（23505）にも待ちの上限切れ（HYT00・50200）にもなる。
  - T4: 行の排他（`PESSIMISTIC_WRITE`、ヒント 3,000 ms）は約 3,015 ms で切れる。外部キーの確かめは親の行の排他を待たない。
  - T5: 違反を受けた1つ目のトランザクションで `setRollbackOnly()` を付けずに戻ると `UnexpectedRollbackException` になる。
  - T6: 違反の文・行の排他の上限切れの連なりの奥に行の値（名前・ID）が入る。`org.hibernate.orm.jdbc.error` が値つきの WARN を出す（本番は OFF）。
  - T7: 区分は `RowLockFailures.isLockFailure` → SQLState 23505・23503 と制約の名前 → 想定外の順で行う。
- 一意の鍵・主キーの待ちの上限は、group の承認の場の決着（約 2 秒を NFR3.3 の上限として読み替えるか、トランザクションの中で設定して戻すか。group の読み直しの R-03）にそろえる。role だけ別の値にはしない。

### 設計の形（承認済みの要件と group の NFR 設計にそろえる）

- 違反・上限切れを起こしうる書き込みと排他は、`TraceAspect` の対象の層（web・service・domain・repository）の外の `role/store` の部品にまとめる（group の Q3 A と同じ）。
  - 例外の文は外へ出さず、ログはクラスの名前だけにする。
  - 想定外の例外は包み直す。包み直した例外には、値を含まない SQLState と制約の名前を持たせる（group の読み直しの R-06 の手当てを先に入れる）。
  - 書き込みの問い合わせ（`@Modifying`）も、この部品の中に置く（`project.md` の学び）。
- 違反・上限切れを区分した時点で、`role/store` の中で巻き戻しの印を付ける。呼び出し側の付け忘れが構造的に起きない形にする（group の読み直しの R-05 の手当て。T5 の 500 を防ぐ）。
- 外部キーの違反（23503）は、操作ごとに読み替える。ロールの削除なら `ROLE_IN_USE`、割り当ての追加なら相手の `USER_NOT_FOUND`・`GROUP_NOT_FOUND`（group の読み直しの R-04 と同じ形）。
- 個人に関する値（割り当ての一覧の氏名・メールアドレス）と、YAML の本文・木・一覧・`errors` は、`toString` で伏せる型で受け渡す（NFR1.6・NFR1.9）。
- 違反の後の失敗の監査は、2つの `TransactionTemplate` を順に実行する（NFR3.4）。

### 機能設計・NFR 要件の読み直しで残った点のうち、この段で書き込むもの（質問にしない）

- **R-11**（`resolve` を1要求で複数回呼んだときの一貫性）: `EffectivePermissionResolver` の Javadoc に書く。「1要求で複数の対象を判定する呼ぶ側は `snapshotFor` を使う。理由は問い合わせの数と、1回の要求の中で同じ作業ロールで答える一貫性」。`resolve` が一貫するのは1回の呼び出しの中だけであることも書く。
- **R-05**（YAML の上限の根拠）: 形が使う集まりの深さは最大 8（根・roles・ロール・schemas・スキーマ・tables・テーブル・columns）で、上限 10 は余裕 2。展開後の節は、1万カラムを明示したロール 25 個（約 25 万の対象）で約 52 万（キーと値の対）と見積もり、上限 1,000,000 に収まる。上限ちょうどのファイルは、テストで生成する部品（ロールの数・カラムの数・名前の長さを引数に取り、バイト数をちょうどに合わせる）で作る。
- **R-06**（問い合わせの上限 10 秒と適用 30 秒）: 適用は1つのトランザクションのまま、書き込みを決まった件数ごとのまとめた書き込み（バッチ）に分け、1文が 10 秒を超えないようにする。件数は Q4 の試しで決める。
- **R-07**（import の適用どうしと、適用中の割り当ての重なり）: NFR3.1 に (h) として足し、持ち主は B6 にする。(h) の期待は次の2つ。
  - 同じロールを置き換える適用どうし: 後の側は `ROLE_BUSY` か `ROLE_TRANSFER_STALE` になり、設定は先の側の状態になる。
  - 適用中の同じロールへの割り当て: `ROLE_BUSY` になり、割り当ては変わらない。
- **R-03**（k6 の op のタグ）: B4 の台本の前に `k6 inspect --include-system-env-vars` と短い試し走りを B4 の条件に入れる。タグが付かないときに分ける場面の名前は先に決める（`roleAdminOpsCreate`・`roleAdminOpsDelete`・`roleAdminOpsRename` など、1つの操作に1つの場面）。
- **R-04・R-08・R-09**: traceability の枝番の行の target の足し、403 の差の期間、p95 の警報が無いことは、この段の `traceability.json` と各設計の「要件との差」・「受け入れた制約」に書く。

## この段で決める要点（質問にしない案。まとめの確認で確かめる）

- **排他の順番**: ロールを変える操作はロールの行を排他し（複数はロールの ID の昇順）、グループへの割り当てと外しは続けて group の `lockForAssignment` でグループの行を排他する（ロール → グループ）。グループの削除はグループの行だけを排他して、role の問う口（`canDelete`・`assignedRoleCounts`）を読み取りで呼ぶ。そのため、待ちの輪はできない。import の適用は、置き換えるロールの行を ID の昇順に排他する。
- **作業ロールの切り替え**: 排他を取らず、読みのたびの読み替えで守る（承認済み）。保存の行の書き込みは利用者の ID の主キーの1行で、同じ利用者の切り替えどうしは主キーの待ちで並ぶ。待ちの上限切れは `ROLE_BUSY` にする（WARN の種類は `WORK_ROLE_SELECTION_KEY`）。
- **監査を残さない切り替えの接続**: 保存がすでに選んだロールを指すときは読み取りだけのトランザクションで終え、接続は1本（NFR2.11）。

## Q1 接続プールの上限の場面（rolePoolLimit）の合否の形（role の NFR 要件の読み直しの R-10）

背景:
- 承認済みの NFR2.7 は、上限 10・20 VU の1回で「上限に届いた証拠（pending 1 以上・acquire の最大 10 ms 以上）」を求めつつ、「時間切れ 0・500 が 0 件」を合格にしています。読み直しの R-10 は、書き込みの2本使いの既知の制約（10 本すべてが1本目を持ったまま2本目を待つ）のため、見積もりが正しくてもこの形は不合格になりうると指摘しました。
- group は NFR 設計の Q1 A で、本数は結合テスト、合否は上限ちょうど（5 VU × 2 = 10）の回、上限を超える回は記録だけにしました。その読み直しの R-01 は、次の2点を指摘しています。
  - 合否を `pending` の瞬間値で決めると短い待ちを見落とす（`project.md` の学びは、時間切れの累計と借りるまでの待ちの最大で判断する）。

- 1要求の本数は、すでに NFR2.11 の `RoleConnectionUsageIT` で決定的に確かめます。

A. group の Q1 A の形にそろえ、group の読み直しの R-01 を直した形にする（推奨: 見積もりの誤りは決定的なテストで見つけ、負荷の回は「見積もりどおりなら待たない」を数で判定できる。健全性の確かめで線が崩れない。group の R-01・R-08 の直しを先に入れ、group と同じ判定にそろう）。
  - 本数の合否は `RoleConnectionUsageIT`（書き込み 2・読み取りと監査を残さない切り替え 1、3 以上で見積もりの誤り）で決める。

## Q2 写し（snapshotFor）と resolve の一致の守り方と、一致のテストの期待値（navigation の R-01・R-08 の role に当たる部分）

背景:
- role の承認済みの NFR2.3 は、`resolve` が写しを使わず、作業ロールの決定の4回と祖先の行の1回（合計5回以内）で答える形で、契約 C5 との差です。U5 への引き継ぎは「たくさんの対象は `snapshotFor` を1回（必須）」でした。
- navigation の Q1 A は、メニューでは写しを、テーブルの置き場では `resolve` を1回使います。
- navigation の読み直しの R-08 は、2つの指摘をしました。
  - (1) role の「必須」と置き場の `resolve` の食い違いが記録されていない。
  - (2) 2つの口の一致を確かめる `EffectivePermissionConsistencyIT` が role の B5 に無い。
- R-01 は、一致のテストの期待値をメニューの応答から作ると、「メニューに出ないが READ のテーブルの置き場は 200」（navigation の NFR1.1）と食い違うと指摘しました。
- navigation の残りは navigation の NFR 設計で決めます。ここで問うのは、role の側の口と一致のテストです。

A. 2つの口はそのまま（承認済みの NFR2.3）とし、一致を role のテストで守る（推奨: 承認済みの形と時間の予算を変えずに、2本の実装の食い違いを、メニューに頼らない独立の期待で決定的に見つけられる。navigation の R-01 の期待値の誤りも role の側で起きない）。
  - 引き継ぎの文言: 「`resolve` は1回の要求で対象が1つのとき（テーブルの置き場など）に使ってよい。2つ以上の対象は `snapshotFor` を1回」に改め、navigation の置き場の `resolve` 1回がこの決まりに合うことを、契約 C5 との差の記録に書き足す。
  - B5 に結合テスト `EffectivePermissionConsistencyIT` を足す。期待は、テストの用意（DSL と明示の設定と割り当て）だけから、テストの中に書いた期待の表（各スキーマ・テーブル・カラムの期待の主権限・CREATE・DELETE）として持ち、メニューの応答からは作らない。
  - すべての対象で、`resolve` と写しの値がどちらも期待の表に等しいことを確かめる。
  - 組は次の8つ。
    - (a) 下位の明示が上位を上書きする向き（スキーマ NONE・テーブル READ、スキーマ FULL・テーブル NONE）
    - (b) カラムだけに明示の値
    - (c) 全階層が設定なし
    - (d) 作業ロールが無い
    - (e) DSL が無い
    - (f) DSL に無い対象の名前
    - (g) 直接とグループ経由の割り当てにまたがるロール
    - (h) 保存が割り当ての外を指す読み替え中
B. `resolve` の中で `snapshotFor` の写しを使う形に戻す（契約 C5 と機能設計 2.9 のまま）。一致は作りから保たれ、一致のテストは要らない。その代わり、`resolve` 1回ごとに作業ロールの設定の全件（悪い側で1万行）を読み、置き場の問い合わせの重さが写しと同じ予算（300 ミリ秒）になる。承認済みの NFR2.3 との差になる。
C. A と同じ口と文言にするが、一致のテストは navigation の `NavigationMenuAccessConsistencyIT` に任せ、role には置かない（テーブルの階層しか確かめず、カラム・補助権限・読み替え中の食い違いは見つからない）。

## Q3 同時の重なりのテストを時間に頼らずに作る形（group の NFR 設計の読み直しの R-02 の role に当たる部分）

背景:
- role にも、違反の側と待ちの上限切れの側の結合テストがあります（`RoleConflictAuditIT`・`RoleBusyApiIT`・`RoleConcurrencyIT` の (b)・(g)）。
- group の設計は、「先の側を 2 秒より短く止めて確定させれば違反、長く止めれば上限切れ」と、壁時計の 2 秒の境で作りました。読み直しの R-02 は、負荷の高い CI で後の側の待ちが 2 秒を超えると違反ではなく BUSY になり、テストが落ちると指摘しました（`team.md` の「実時刻に頼らない」「不安定なテスト」）。
- T1 のとおり、待った後の違反と待たない違反は、同じ例外（23505）で同じ区分を通ります。

A. 待ちの有無で分け、どちらも時間の境に頼らない形にする（推奨: どちらのテストも結果が1つに決まり、時間の境に合否を預けない。同じ区分の部品を通るため、待った後の違反の経路は区分の単体テスト（例外の連なりを作って渡す）で確かめれば足りる）。
  - 違反の確かめ: 先の側を確定させてから後の側を書く、待たない違反にする。待ち合わせの口で「先の側の確定」を合図に後の側を進める。
  - 上限切れの確かめ: 先の側を待ち合わせの口で止めたまま放さず、後の側が H2 の上限で切れて `ROLE_BUSY` を返すのを待つ。テストの待ちの上限は長め（20 秒）にする。後の側の結果が出た後に先の側を放す。合否は、後の側の 409 と状態が変わらないことで決め、経過の時間では決めない。
B. 後の側が待ちに入ったことを観測して（H2 の `INFORMATION_SCHEMA.SESSIONS` の待ちの相手の列など）、先の側を放す形にし、待った後の違反も結合テストで起こす（実際の重なりに近いが、H2 の観測の口を Q4 の試しで確かめる必要があり、テストの部品が増える）。
C. group と同じ時間の境の形にし、境の余裕を広げる（先の側の停止を 200 ms と 5 秒に分ける）。作りは簡単だが、負荷の高い CI では揺れが残る。

## Q4 role で足りない部分の捨ての試しの範囲と時間の上限

背景: `project.md` の学びにより、DB や部品の振る舞いに頼る前提は、この段でリポジトリの外の捨ての試しのコードで先に確かめます。group の試し（T1〜T7）で足りない、role だけの前提は次の4つです（承認済みの NFR3.7）。
- (2) YAML のキー（`true`・`null`・`123`・`yes`）が、読み込みの木で文字列のキーになるか（機能設計の R-06）。
- (3) 10 MiB の YAML の確かめ 15 秒・適用 30 秒に届くか。あわせて、1文が問い合わせの上限 10 秒を超えないバッチの件数（読み直しの R-06）。
- (4) 悪い側での `snapshotFor` 1回 300 ミリ秒と、`resolve` の5回の時間。
- (1)（違反か待ちの上限切れか）は T1〜T3 で足ります。

`SafeYamlReader` は dsl-v2 の B1 で作るためまだ無いので、試しは今の `dsl.parse` と同じ SnakeYAML の版と設定（`LoaderOptions` と、木を作る Jackson の変換）を写して行います。

A. 次の範囲で試す（推奨: 試しの時間が上限内に収まり、Q4 の答えで分かったことを、この段の設計（バッチの件数・引用符・時間の見通し）にそのまま写せる。重い試し（10 MiB）は1回で済ませる）。
