## 補足

- 内部DB は組み込みの H2 で、アプリは1つ（単一インスタンス。前の Intent の決定のまま）。横に増やす要件は無い。
- 試験のデータの用意（ロール 1,000・1万カラム明示・メンバー 1,000 人のグループ）は、API ではなく使い捨ての環境の内部DB に SQL で直接入れてよい。直接入れた利用者はロックの状態の行が無いため、同時のログインの前に1人ずつログインさせて行を作る（`project.md` の学び）。

## 承認の場の決定と直し

承認の場で依頼者が Request Changes を選び、直す範囲を「Major 11 件だけを直す」とした。この成果物では、レビュー `aidlc/spaces/default/intents/261004-role-menu/.aidlc-reviews/nfr-requirements/units/role/4e9510ac79c4db11/1.json` の次の指摘を直した。

- **R-02（Major）**: NFR2.7 の k6 の `rolePoolLimit` は、見積もりの誤りを見分けにくかった。4 VU の回は上限に届かず、20 VU の回は「待ちの最大が 0 より大きい」がいつも成り立ち、不合格の条件も無かった。直した点は次の3つ。
  - 「1要求で同時に持つ接続は2本まで」を、新しい NFR2.11 の結合テスト `RoleConnectionUsageIT` で経路ごとに決定的に確かめる。
  - `rolePoolLimit` は補助の確かめにし、20 VU の1回にまとめた。上限に届いた証拠（pending の最大 1 以上、acquire の最大 10 ミリ秒以上）と、合格の条件（時間切れ 0、500 が 0 件、`checks` の率 1）を数で書いた。
  - 時間切れか 500 が1件でも出たら、見積もりの誤りとして扱う。
