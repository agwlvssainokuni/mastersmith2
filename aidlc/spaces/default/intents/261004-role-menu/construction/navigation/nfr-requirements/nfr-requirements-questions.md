### 性能（要件・role からの引き継ぎ）

- メニューを返す API の応答時間は 95 パーセンタイルで 1 秒以内（NFR2.2、AC5.1.18）。目標は緩めない。置き場の問い合わせにも同じ 1 秒を置く（同じ「メニューから画面へ移る」流れの API のため）。
- メニューの API は、1回の要求で `snapshotFor(userId)` を1回だけ呼ぶ。`resolve` を項目ごとに呼ばない（機能設計 BR1.4、role の NFR2.3 と引き継ぎ。role のレビューの R-01 で、`resolve` を対象ごとに呼ぶと1回あたり作業ロールの決定の4回と祖先の行の1回の問い合わせが繰り返されると指摘された）。`snapshotFor` の予算は悪い側で 300 ミリ秒（role の NFR2.3）。
- 呼び出しの回数を確かめるテストでは、数えるのは navigation が呼ぶ回数（`current()` 1回・`snapshotFor` 1回）だけで、解決の口の内側の `current()` や問い合わせの数は role の `EffectivePermissionQueryCountIT` が持つ（機能設計の再レビューの R-04）。
- 写しの形は契約 C5 から変わっている（`workRoleId` の代わりに `workRole`、`dslHash` を足した。role の機能設計の再レビューの R-09）。navigation は `main(schema, table, null)` と `dslHash` だけを使う。
- 画面は、画面の道が変わるたびに業務のメニューと作業ロールを裏で読み直す（app-frame-ui の Q2 A）。メニューの API は、利用者の画面の移動の数だけ呼ばれる。
- k6 の場面は、1回の繰り返しに要求1つにし、判定は単調な時計の `iteration_duration` の p95 で行い、`http_req_duration{name:…}` は並べて記録する（`project.md` の学び、group のレビューの R-01）。操作ごとの `op` のタグには頼らず、操作ごとに場面を分ける（role のレビューの R-03）。VU ごとのアクセストークンは `setup()` で取り、場面の長さはトークンの有効期限 5 分より短い 3 分にする。台本全体を `caffeinate -i` で包み、使い捨ての環境で流す。

### 規模・接続

- 2本の API は読み取りだけで、監査の2本目の接続を使わない。1要求で同時に持つ接続は1本まで（解決の口の読み取りの間だけ）。navigation の業務処理は自分でトランザクションを開かない。この「1本まで」は、k6 ではなく結合テストで決定的に確かめる。待ち合わせの口で解決の口の読み取りの途中で止め、プールの統計（使用中の数）が1であることを数える（role のレビューの R-02 の形）。
- 1要求で1本だけを使う読み取りは、上限に届いても待ちで遅くなるだけで、2本使いのような詰まりにはならない。そのため、上限を下げた k6 の場面（`rolePoolLimit` の形）は U5 では置かない。
- 内部DB は組み込みの H2 でアプリは1つ（単一インスタンス）。横に増やす要件は無い。

### セキュリティ（devsecops・コンプライアンスの視点）

- STRIDE の見方で並べると次のとおり。
  - なりすまし・IDOR: 主体は要求の文脈から読み、利用者を指す値を受け取らない（BR1.1）。
  - 権限の昇格: 絞り込みと置き場の判定はサーバー側だけで行い、画面の出し分けを代わりにしない（BR2.1・BR5.2）。
  - 情報の漏えい: 権限の無いテーブルは応答に含めない。NONE・DSL に無い組・DSL が無いときは同じ 403 で、表示名を返さない（BR5.2）。
  - 改ざん（信頼できない入力）: `label` はそのまま返し、画面が文字として描く。`icon` は一覧と照らす。名前は問い合わせの引数で受け、文字を問わない（BR3.2・BR4.2・BR5.1）。
  - サービスの妨害: 引数の長さの上限は置かない（機能設計の直し R-01）。極端に長い URL は Tomcat の要求の頭の大きさの上限（既定）で、Spring に届く前に拒否される。
  - 否認: 対象が無い（読み取りだけで、監査に残す操作が無い）。
- 問い合わせの引数（スキーマ名・テーブル名）の出る経路はコードで確かめた（機能設計の再レビューの R-06）。
  - トレースの属性と指標のタグ: `common/observability/UrlQueryStrippingObservationFilter.java` が URL の問い合わせの部分を取り除く。`http.server.requests` の `uri` は道の型だけ。
  - アクセスログ: Tomcat のアクセスログは設定していない（`application.yaml` に無い）。
  - 誤りの応答: `ProblemDetail` の `instance` は問い合わせの部分を含まない道。
  - 403 の WARN: 既存の `GlobalExceptionHandler` の行は code・状態・例外の型だけ。
  - TRACE のログ: `TraceAspect` が web・service・domain の引数を TRACE のときだけ文字列で出すため、スキーマ名・テーブル名が出る。どちらも DSL の業務の名前で、個人に関する値でも秘密でもないため伏せない（機能設計 SP 9・BR7.4）。

- 個人データの保存・新しい監査は無い。コンプライアンスの新しい論点は無い。
- 静的解析の関門は今のまま（SpotBugs ＋ FindSecBugs の priority 1 と、`SQL_`・`PREDICTABLE_RANDOM`・`SMTP_HEADER_INJECTION`）。navigation は SQL を持たない。

### 信頼性

- 読み取りの間に DSL が適用し直されても読み直さず、権限の無い項目は出ない（機能設計 BR1.5）。重なりは待ち合わせで作って確かめる（スレッドの数に頼らない）。

## Q1 テーブルの置き場の問い合わせで使う解決の口（NFR2.3、機能設計 BR5.2 との関係）

背景: 承認済みの機能設計 BR5.2 は、置き場の問い合わせでも `snapshotFor` を1回呼ぶ形です。その後、role の NFR 要件で口の重さが決まりました。
- `snapshotFor` は、作業ロールの決定（4回以内）の後に、作業ロールの設定の行を全件読みます（悪い側は1万行、予算 300 ミリ秒）。
- `resolve(userId, target)` は、作業ロールの決定の後に、その対象の祖先の行（スキーマ・テーブルの最大2行）だけを1回で読みます。

置き場の問い合わせが見るのは1つのテーブルだけで、画面の移動のたびに呼ばれえます。

A. 置き場の問い合わせは `resolve(userId, {schema, table, null})` を1回だけ呼ぶ。機能設計 BR5.2 の「`snapshotFor` を1回」との差を、成果物の「上流との差」に書く。DSL が無い・組が無いときも必ず `resolve` を呼ぶことは変えない。口の内側で早く返る経路がありうるため、拒否の理由ごとの応答の時間が揃うことは保証せず、受け入れた制約にする。テーブルの有無はメニューと DSL の管理で業務の名前として扱われ、応答の本文は同じため（推奨: 1万行を読まずに済み、1回の問い合わせの重さが対象の数によらない。メニューの API は今のとおり `snapshotFor` を1回）
B. 機能設計のとおり `snapshotFor` を1回呼ぶ。悪い側では置き場の問い合わせのたびに1万行を読むが、予算 300 ミリ秒の中で 1 秒の目標は満たせる見込み。口の内側の経路はメニューの API と同じになる
