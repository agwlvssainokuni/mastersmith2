## 要件

| ID | 要件 | 測り方・確かめ方 | 持ち主の段 |
|---|---|---|---|
| NFR2.1 | 規模の前提と試験の悪い側を次のとおりにする（Q2 A）。<br>・目安: menus は既定の DSL の 100 項目（深さ 1）、対象DB 100 テーブル × 100 カラム、利用者 50 名。<br>・悪い側: menus 1,000 項目で深さ 5 段まで使い、100 テーブルを平均 10 回ずつ別々のまとまりから指す。作業ロールは role の悪い側と同じ（1万カラムすべてに明示の値。テーブルの半分を NONE にして絞り込みが働くようにする）。利用者は 100 のグループに属し、各グループにロールがある。<br>・要求の数の見積もり: 画面は画面の移動のたびにメニューの API を1回呼ぶ（app-frame-ui の Q2 A）。利用者 50 名が 5 秒に1回ずつ移っても毎秒 10 要求で、NFR2.2 の 10 VU の閉じた繰り返し（応答 1 秒なら毎秒 10 要求以上）がこれを覆う。<br>・menus の項目の数にアプリの上限は置かない（DSL の大きさの上限 10 MiB と深さ 5 段のほかに増やさない） | k6 の場面のデータ（`performance-requirements.md` の NFR2.2）。悪い側の DSL は生成の手順（既存の `perf/make-large-dsl.mjs` に倣う）で作り、DSL の管理の API で適用する。ロール・グループ・割り当ては使い捨ての環境の内部DB に SQL で直接入れてよい（直接入れた利用者は、同時のログインの前に1人ずつログインさせてロックの状態の行を作る。`project.md` の学び）。Performance Validation の結果に、使った規模（項目の数・深さ・明示の行の数・グループの数）を記録する | データの用意は Code Generation（B7）、流すのは Performance Validation |
| NFR2.6 | 2本の API は、1要求で同時に持つ内部DB の接続を1本までにする。navigation は自分でトランザクションを開かず、接続は解決の口の読み取りの間だけ使う。監査の2本目の接続は使わない（読み取りだけで監査が無い。BR6.2・BR7.3）。<br>1本だけを使う読み取りは、プールの上限に届いても待ちで遅くなるだけで、2本使いのような詰まりにはならない。そのため、上限を下げた k6 の場面（role の `rolePoolLimit` の形）は置かない | 結合テスト `NavigationConnectionUsageIT`。解決の口の読み取りの途中で止める待ち合わせの口（テストだけの差し替え）で要求を止め、その間の HikariCP の使用中の接続の数が 1 であることを、2本の API それぞれ（メニュー、置き場の 200 と 403）で確かめる。判定はプールの統計の値で決定的に行い、スレッドの数や時間に頼らない（role のレビューの R-02） | Code Generation（B7） |

## 補足

- 内部DB は組み込みの H2 で、アプリは1つ（単一インスタンス。前の Intent の決定のまま）。横に増やす要件は無い。
- 写しは要求をまたいで持たない（BR1.4）ため、利用者の数と要求の数に比例してメモリが増えることは無い。1回の要求の写しの大きさは role の悪い側（1万行）で決まる。
