# Unit of Work — auth-audit-foundation

本書は、Domain Design の部品（`aidlc/spaces/default/intents/260922-auth-audit-base/inception/domain-design/components.md`）と要件（`aidlc/spaces/default/intents/260922-auth-audit-base/inception/requirements-analysis/requirements.md` の FR1〜FR10）を、Construction で1つずつ作り上げる開発の単位（Unit）にまとめたものである。分け方は `units-generation-questions.md` の確定回答（Q1〜Q5）と承認済みの分割計画に基づく。

- 切り口: 機能ごとに、バックエンドと画面をまとめた縦の単位（Q1）
- 粒度: 粗め。4単位（Q2）
- 骨格と共通の仕組み: 独立した骨格の単位（Q3）
- 依存関係の形: 一列（Q4）。依存関係は `unit-of-work-dependency.md` に記す
- 単位どうしの約束事（API・出来事）: 各単位の Contract Design で決める（Q5）

どの単位から作るか（順番）は本書では決めない（Delivery Planning で決める）。

## 単位の一覧

| Unit ID | Directory | 名前 | 種別（kind） | 含む部品 | 対応する要件 | 規模 |
|---|---|---|---|---|---|---|
| U1 | u1-app-skeleton | アプリの骨格 | （なし） | 共通の仕組み（アプリの骨格・観測性・共通のエラー応答）、AppFrame | FR1.1、FR1.2、FR2.3、FR10.1〜FR10.4 | L |
| U2 | u2-authentication | 認証 | （なし） | UserAccount、Authentication、AuthUi、ApiClient | FR2.1、FR2.4、FR3.1〜FR3.4、FR4.1〜FR4.5、FR5.1〜FR5.3、FR6.1、FR6.2、FR7.1〜FR7.5 | XL |
| U3 | u3-access-control | 管理画面のアクセス制御 | （なし） | AccessControl、AdminArea | FR2.2、FR8.1、FR8.2 | S |
| U4 | u4-audit-log | 監査ログ | service | AuditLog | FR9.1〜FR9.5 | M |

種別について: U1〜U3 はバックエンドと画面の両方を持つため、種別を付けない（設計の成果物をすべて作る。画面部品の設計とバックエンドの設計の両方が要るため）。U4 は画面を持たないバックエンドだけの単位のため `service` とする。

配備について: 4単位とも、フロントエンドのビルド結果を同梱した実行可能 WAR 1つに入る（チームの進め方）。単位は開発の単位であり、配備の単位ではない。

## U1 アプリの骨格（u1-app-skeleton）

**説明**: アプリが起動し、内部DBにつながり、ヘルスチェックに応答し、決めた形式でログを出し、画面の骨組みが表示されるところまでを作る。以降の単位が乗る土台である。

**受け持つこと**:
- バックエンドの起動とヘルスチェック（FR1.1）
- 内部DB（H2）への接続設定。既定は組み込み・ファイル保存で、application.yml の接続設定だけで切り替えられる（FR1.2）
- 1行1件の JSON のログ、トレースIDのログへの付与、W3C Trace Context によるトレースの引き継ぎ、OTEL による外部エクスポート（既定は無効）（FR10.1〜FR10.4）
- 共通のエラー応答（Problem Details と `code`、`@RestControllerAdvice` の1か所での変換）
- 画面の骨組み（AppFrame）: ルーティング、make-you-chic-ui の AppShell（サイドバー・トップバー・コンテンツ）、ログイン画面を置くための AppShell の外のレイアウトとログイン画面の枠、日本語・英語の文言とブラウザの言語設定による切り替え（FR2.3）
- ビルド: フロントエンドのビルド結果を実行可能 WAR に同梱する。開発時は開発サーバーのプロキシを通して API を呼ぶ
- 1コマンドの検査（フォーマット・リンタ・ライセンスヘッダー・ビルド・全テスト・カバレッジ下限・秘密情報の検出・静的解析・依存関係の脆弱性検査）、pre-commit フック、CI（GitHub Actions）

**配備の形**: 共有（実行可能 WAR 1つの土台）

**実装上の注意と制約**:
- チームの進め方の「アプリの骨格がまだ無いときに最初の単位に含める一式」をすべて含める（DB を使うテスト1件以上、ヘルスチェックの起動確認テスト、Vite の `resolve.dedupe` による React の二重読み込み対策を含む）。
- 画面の骨組みには、後の単位が中身を足すための差し込み口を用意する。後の単位は U1 のファイルを書き換えず、差し込み口に登録して中身を足す。差し込み口は次の4つである。
  - 画面（ルート）の登録: 単位が自分の画面とその URL を登録する。
  - サイドバーの項目の登録: 表示の条件（例: 管理者だけ）を添えて項目を登録する。
  - ユーザーメニューの項目の登録: 例として、ログアウトを登録する。
  - ログイン状態の提供元の登録: ログインしているか、管理者かを返す手段を登録する。ログイン画面への振り分けと項目の表示条件に使う。登録が無い間は「未ログイン」として扱う。
- 差し込み口の具体的な形は、U1 の Contract Design で決める。
- Domain Design の部品の依存では、AppFrame が AuthUi と AdminArea に依存している。単位ではこの依存を差し込み口への登録で逆向きにし、U2・U3 が U1 に依存する形にする（ApiClient と AuthUi の関係と同じ考え方。Domain Design の ADR-007）。ログイン状態による画面の振り分けとユーザーメニューのログアウトは U2 が、サイドバーの「管理」は U3 が登録する。
- 観測性とアプリの骨格は部品ではない共通の仕組みである（Domain Design の ADR-005）。

## U2 認証（u2-authentication）

**説明**: メールアドレスとパスワードでログインし、トークンを受け取り、更新し、ログアウトできるようにする。アカウントロックと初期管理者の自動作成も含む。

**受け持つこと**:
- 利用者（User）の保持、パスワードの照合、初期管理者の自動作成（UserAccount。FR3.1〜FR3.4）
- ログイン、アクセストークンの発行と検証、リフレッシュトークンの発行・作り直し・無効化、ログアウト、失敗時の応答の統一（Authentication。FR4.1〜FR4.5、FR5.1、FR5.2、FR6.1、FR6.2）
- 連続失敗によるアカウントロックと自動解除、しきい値と解除時間の設定（Authentication の LoginAttemptState。FR7.1〜FR7.5）
- ログイン成功・ログイン失敗・ログアウトの出来事の通知（受け取る側は U4）
- ログイン画面、失敗時の同じ表示、アクセストークンのメモリ上での保持と更新、再読み込み時のログイン状態の復元、ログアウト（AuthUi。FR2.1、FR2.4、FR5.3、FR6.1）
- API 呼び出しの共通部分: アクセストークンの付与、401 時の更新と1回の再試行、エラー応答の変換（ApiClient）
- 画面の骨組みへの登録（U1 の差し込み口を使い、U1 のファイルは書き換えない）: ログイン画面、ログイン状態の提供元（ログイン状態による画面の振り分けに使われる）、ユーザーメニューのログアウト

**配備の形**: 組み込み（実行可能 WAR の一部）

**実装上の注意と制約**:
- パスワード・トークン・署名鍵をログ・エラー応答に含めない。初期管理者のパスワードや署名鍵をソースや設定ファイルに直接書かない（project.md の Forbidden）。
- チームの進め方で必須とされた認証のテスト（ロックのしきい値の境界、ユーザーの存在を推測できないこと、トークンの有効期限の境界・改ざん・`alg: none`、ログアウト後の扱い、初期管理者の重複作成なし など）を含める。
- 出来事には、監査ログが記録する項目（入力されたメールアドレス・失敗の理由・接続元IP・User-Agent・トレースID）を載せる。出来事の形は U2 の Contract Design で決める（Q5）。
- 規模が最も大きい（XL）。Construction で分けて作る場合は Delivery Planning で扱う。

## U3 管理画面のアクセス制御（u3-access-control）

**説明**: 管理者だけが使える API と画面を、サーバー側の判定で守る。

**受け持つこと**:
- 管理者のみの API の判定（未認証は 401、管理者フラグの無い利用者は 403）と、管理者専用の確認用 API（AccessControl。FR8.1、FR8.2）
- 権限不足によるアクセス拒否の出来事の通知（受け取る側は U4）
- 管理者向け領域（プレースホルダ）の表示と、拒否された場合に表示しないこと（AdminArea）
- 画面の骨組みへの登録（U1 の差し込み口を使い、U1 のファイルは書き換えない）: 管理者向け領域の画面、「管理者だけ」の条件を付けたサイドバーの「管理」（FR2.2）

**配備の形**: 組み込み（実行可能 WAR の一部）

**実装上の注意と制約**:
- 画面で管理メニューを隠すことを、サーバー側の判定の代わりにしない（FR8.2）。401／403／200 をサーバー側のテストで確かめる。
- 後続の Intent F でロール・権限の判定をこの部品に足せる形にする（Domain Design の ADR-003）。

## U4 監査ログ（u4-audit-log）

**説明**: 認証とアクセス制御の出来事を受け取り、監査イベントとして内部DBに記録する。

**受け持つこと**:
- ログイン成功・ログイン失敗・ログアウト・アクセス拒否の出来事の受け取りと、監査イベント（AuditEvent）の記録（FR9.1、FR9.2）
- 削除・変更の機能を持たない（FR9.3）
- 書き込みに失敗しても元の操作を続け、失敗と記録しようとした内容（秘密情報を除く）をアプリのログにエラーとして出す（FR9.4）
- 監査ログをアプリのログ出力で代用しない（FR9.5）

**配備の形**: 組み込み（実行可能 WAR の一部）

**実装上の注意と制約**:
- U2・U3 が知らせる出来事を受け取る。出来事を知らせる側は監査ログを知らない（Domain Design の ADR-004）。
- 存在しないメールアドレスでのログイン失敗も記録する。パスワード・トークンを記録しない。
