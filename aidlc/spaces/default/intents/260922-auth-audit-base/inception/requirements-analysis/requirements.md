## 1. Intent の分析

- **目的**: MasterSmith（マスタ管理アプリ）の他の全機能が依拠する、認証・認可と監査ログの土台を最初に確立する（IS）。
- **利用者**: MasterSmith を導入・運用する組織の内部管理者・利用者（IS）。
- **成功基準**（IS）:
  - ログイン・トークン発行／検証・管理者権限ゲートが動作する
  - 正常に動いているときは、対象イベントが漏れなく監査ログに記録される（RQ17）
  - 後続Intent（D以降）がこの基盤の上に問題なく構築できる
- **種類・規模**: 新規開発（グリーンフィールド）。本Intentが MasterSmith 最初のアプリ骨格を兼ねる（S1）。バックエンド・フロントエンド・内部DBにまたがる複数部品の開発で、複雑さは標準。

## 2. 機能要件

受け入れ基準は Given/When/Then で書く。★は設定で変更できる値で、表記は既定値。

### FR1 アプリ骨格と内部DB

出典: S1、RQ1、RQ14、RQ16、TP

- **FR1.1** アプリが起動し、ヘルスチェックに応答する。
  - Given アプリを起動した / When ヘルスチェックを要求する / Then 正常を示す応答が返る
- **FR1.2** 内部DB（ユーザー・監査ログなど、アプリ自身が使うDB）は H2 とする。接続先は application.yml の接続設定だけで切り替えられ、既定はアプリに組み込んでファイルに保存する形とする。
  - Given 既定の設定でアプリを起動し、データを書き込んだ / When アプリを再起動する / Then 書き込んだデータが残っている
  - Given application.yml で接続先を別の H2 に変えた / When アプリを起動する / Then 変更後の接続先を使う

### FR2 画面

出典: S2、CV、PM（DECIDED: AppShell 構成）、RQ12、RQ18

- **FR2.1** ログイン画面は、アプリシェル（AppShell）の外に独立したレイアウトとして置き、メールアドレス・パスワードの入力欄とログインボタンを持つ。
  - Given ログインしていない / When アプリの画面を開く / Then ログイン画面が表示される
- **FR2.2** ログイン後の画面は、make-you-chic-ui の AppShell（サイドバー＋トップバー＋コンテンツ）の中に置く。サイドバーには「ホーム」を表示し、管理者にだけ「管理」を追加で表示する。「管理」を選ぶと管理者のみ入れる領域（プレースホルダ）を表示する。トップバー右のユーザーメニューからログアウトできる。
  - Given 管理者でない利用者がログインした / When ログイン後の画面を表示する / Then サイドバーに「管理」が表示されない
  - Given 管理者がログインした / When 「管理」を選ぶ / Then 管理者のみ入れる領域が表示される
- **FR2.3** 画面の文言は日本語・英語に対応し、ブラウザの言語設定で切り替える。
  - Given ブラウザの言語設定が英語 / When ログイン画面を表示する / Then 英語の文言で表示される
  - Given ブラウザの言語設定が日本語でも英語でもない / When ログイン画面を表示する / Then 既定の言語で表示される（既定の言語は未確定。7章の OQ6）
- **FR2.4** ログインに失敗したときの表示は、パスワード誤り・存在しないメールアドレス・ロック中のいずれでも同じにする。画面イメージの画面2（ロック表示）は、通常のログイン失敗の表示に読み替える。
  - Given ロック中のアカウント、存在しないメールアドレス、パスワード誤りのそれぞれ / When ログインを試す / Then 画面の表示（文言）が同じである

### FR3 初期管理者の自動作成

出典: S3、RQ7、PM（Forbidden）

- **FR3.1** 初回起動時に、設定（設定ファイル／環境変数）で指定したメールアドレスとパスワードで、管理者フラグを持つユーザーを作成する。
  - Given 内部DBに該当するユーザーがなく、初期管理者の設定が正しい / When アプリを起動する / Then 管理者フラグを持つユーザーが作成され、そのメールアドレスとパスワードでログインできる
- **FR3.2** 2回目以降の起動では、初期管理者を重複して作成しない。
  - Given 初期管理者が作成済み / When アプリを再起動する / Then ユーザーは増えない
- **FR3.3** 初期管理者の設定が無い場合、またはパスワードが規則（12文字以上。NFR2）を満たさない場合は、初期管理者を作らずに起動を続け、警告をログに出す。
  - Given 初期管理者の設定が無い、またはパスワードが11文字以下 / When アプリを起動する / Then アプリは起動し、初期管理者は作成されず、警告がログに出る
- **FR3.4** 初期管理者のパスワードをログに出さない。
  - Given 初期管理者を作成する（またはしない）起動 / When ログを確認する / Then パスワードの値が含まれていない

### FR4 ログインとトークンの発行・検証

出典: S4、RQ2、RQ4、RQ6、RQ15、RQ18

- **FR4.1** メールアドレスとパスワードでログインする。成功すると、アクセストークンを応答で返し、リフレッシュトークンを HttpOnly・Secure・SameSite の Cookie で渡す。
  - Given 登録済みで、ロックされていないアカウント / When 正しいメールアドレスとパスワードでログインする / Then アクセストークンが返り、リフレッシュトークンの Cookie が設定される
- **FR4.2** アクセストークンの有効期限は ★5分とする。
- **FR4.3** リフレッシュトークンの有効期限は ★24時間とする。
- **FR4.4** 認証が必要な API は、有効なアクセストークンが無い要求（トークンなし・期限切れ・署名の改ざん・署名方式の指定を悪用したものを含む）を拒否する（401）。
  - Given 有効期限を過ぎたアクセストークン / When 認証が必要な API を呼ぶ / Then 401 が返る
  - Given 署名を改ざんした、または署名方式を「なし」にしたアクセストークン / When 認証が必要な API を呼ぶ / Then 401 が返る
- **FR4.5** ログイン失敗時の応答は、パスワード誤り・存在しないメールアドレス・ロック中のいずれでも同じにし、応答から登録の有無やロックの状態を推測できないようにする。
  - Given 存在しないメールアドレス、パスワード誤り、ロック中のそれぞれ / When ログインを試す / Then 応答の状態コードと内容が同じである

### FR5 トークンの更新

出典: S5、RQ5、RQ6

- **FR5.1** リフレッシュトークンを使ってトークンを更新すると、新しいアクセストークンと新しいリフレッシュトークンを渡し、使ったリフレッシュトークンは無効にする。
  - Given 有効なリフレッシュトークン / When トークンを更新する / Then 新しいアクセストークンと新しいリフレッシュトークンが渡される
- **FR5.2** 無効にしたリフレッシュトークン、有効期限を過ぎたリフレッシュトークンによる更新は拒否する（401）。
  - Given 1回使って無効になったリフレッシュトークン / When もう一度トークンを更新する / Then 401 が返る
- **FR5.3** 画面の再読み込みや新しいタブでも、有効なリフレッシュトークンがあればログイン状態が続く。
  - Given ログイン中 / When 画面を再読み込みする / Then ログインし直さずにログイン後の画面が表示される

### FR6 ログアウト

出典: S6、PM（DECIDED: ログアウトの意味）

- **FR6.1** ログアウトすると、画面側はアクセストークンを破棄し、サーバー側はリフレッシュトークンを無効にして Cookie を消す。
  - Given ログイン中 / When ログアウトする / Then ログイン画面に戻り、そのリフレッシュトークンによる更新は 401 になる
- **FR6.2** ログアウト後も、発行済みのアクセストークンは有効期限まで使える（決定済みの仕様）。
  - Given ログアウトした直後で、有効期限内のアクセストークン / When 認証が必要な API を呼ぶ / Then 受け付けられる

### FR7 アカウントロック

出典: S7、RQ3、RQ18

- **FR7.1** 連続して ★5回ログインに失敗したアカウントをロックする。
  - Given 失敗回数が4回 / When 5回目の失敗をする / Then アカウントがロックされる
  - Given 失敗回数が3回 / When 4回目の失敗をする / Then ロックされない
- **FR7.2** ロック中は、正しいパスワードでもログインを拒否する。表示と応答は通常のログイン失敗と同じにする（FR2.4、FR4.5）。
- **FR7.3** ロックは ★30分経過で自動的に解除する。
  - Given ロックされてから30分経過した / When 正しいパスワードでログインする / Then ログインできる
- **FR7.4** ログインに成功すると、失敗回数を0に戻す。
  - Given 失敗回数が4回 / When 正しいパスワードでログインし、その後1回失敗する / Then ロックされない
- **FR7.5** ロックのしきい値（回数）と解除までの時間は application.yml で設定できる。

### FR8 管理画面のアクセス制御

出典: S8、IS（Intent B の定義）、TP

- **FR8.1** 管理者のみが使える API・画面は、サーバー側で権限を確かめる。未認証は 401、管理者フラグの無い利用者は 403 とし、管理者は利用できる。
  - Given 管理者フラグの無い利用者 / When 管理者のみの API を呼ぶ / Then 403 が返る
  - Given 管理者 / When 管理者のみの API を呼ぶ / Then 利用できる
- **FR8.2** 画面で管理メニューを隠すことは、サーバー側の権限確認の代わりにしない。

### FR9 監査ログ

出典: S9、RQ8、RQ9、RQ10、RQ17、PM（Forbidden）

- **FR9.1** 次のイベントを内部DBに記録する: ログイン成功、ログイン失敗、ログアウト、権限不足による管理画面へのアクセス拒否。
  - Given 監査ログが正常に書き込める / When 対象イベントのそれぞれが起きる / Then それぞれ1件ずつ記録される
  - Given 存在しないメールアドレス / When ログインに失敗する / Then 失敗のイベントが記録される
- **FR9.2** 記録する項目は、日時・イベントの種類・結果（成功／失敗）・入力されたユーザーID（メールアドレス）・失敗の理由（パスワード誤り・存在しないユーザー・ロック中・権限不足など）・接続元のIPアドレス・ブラウザの情報（User-Agent）・トレースIDとする。
- **FR9.3** 本Intentでは監査ログを削除する仕組みを作らない（無期限に保存する）。
- **FR9.4** 監査ログの書き込みに失敗した場合は、元の操作を続け、書き込みに失敗したことと記録しようとした内容（秘密情報を除く）をアプリのログにエラーとして出す。
  - Given 監査ログの書き込みができない状態 / When ログインする / Then ログインは成功し、アプリのログにエラーが出る
- **FR9.5** 監査ログとアプリのログは別の仕組みとし、監査記録をアプリのログ出力で代用しない（TP）。

### FR10 構造化ログ・分散トレース・外部エクスポート

出典: S10、RQ13、TP

- **FR10.1** アプリのログは、1行1件の JSON で標準出力に出す（開発時も同じ）。
  - Given アプリが動いている / When ログが出る / Then 1行が1件の JSON として読める
- **FR10.2** ログにトレースIDを含める。
- **FR10.3** 分散トレースを行う。
- **FR10.4** トレースやログの外部エクスポート（OTEL）の機能を持ち、既定は無効、設定で有効にできる。
  - Given 既定の設定 / When アプリを起動する / Then 外部へのエクスポートは行われない

## 3. 非機能要件

| ID | 分類 | 要件 | 出典 |
|---|---|---|---|
| NFR1 | 性能 | 利用者 最大50名、同時にログインする利用者 最大10名を想定する。ログインとトークン更新の API は、この負荷で 95% の要求が1秒以内に応答する | RQ11 |
| NFR2 | セキュリティ | パスワードは12文字以上とする（文字種の組み合わせは問わない） | RQ7 |
| NFR3 | セキュリティ | パスワード（平文・ハッシュ値とも）・アクセストークン・リフレッシュトークン・署名鍵を、ログ・監査ログ・トレースの属性・外部へのエクスポート・エラー応答に含めない。秘密情報をソースコードや設定ファイルに直接書かない | PM（Forbidden） |
| NFR4 | セキュリティ | ログインの応答と表示から、メールアドレスの登録の有無やロックの状態を推測できない | RQ18、TP |
| NFR5 | セキュリティ | 画面側では、アクセストークンをメモリ上にだけ持ち、リフレッシュトークンはスクリプトから読めない Cookie（HttpOnly・Secure・SameSite）に置く。トークンをブラウザの保存領域（localStorage・sessionStorage）に置かない | RQ6、RQ15 |
| NFR6 | 設定 | ロックのしきい値・ロック解除までの時間・アクセストークンとリフレッシュトークンの有効期限・内部DBの接続先・外部エクスポートの有効化は、application.yml（または環境変数）で設定できる | RQ3、RQ4、RQ14、S10 |
| NFR7 | 多言語 | 画面の文言は日本語・英語に対応する | RQ12 |
| NFR8 | アクセシビリティ | 画面の部品ごとにアクセシビリティ検査（axe）を通す | TP |
| NFR9 | 保守性 | テストの行カバレッジ 80% 以上、分岐カバレッジ 70% 以上（バックエンド・フロントエンドとも） | TP |
| NFR10 | 観測性 | アプリのログは JSON、トレースIDを含み、外部エクスポートは既定で無効 | RQ13、S10 |

## 4. 制約

| 分類 | 制約 | 出典 |
|---|---|---|
| 構成 | リポジトリのルートに `backend/`（Java）と `frontend/`（React + TypeScript）を分ける。バックエンドのビルドは Gradle（Kotlin DSL）、ルートパッケージは `cherry.mastersmith` | TP |
| 構成 | ビルドの成果物は、フロントエンドのビルド結果を同梱した実行可能 WAR。画面は配信元と同じサーバーの API を呼び、CORS の設定は置かない。開発時はフロントエンドの開発サーバーのプロキシを通す | TP |
| 画面 | デザインシステム make-you-chic-ui（`vendor/make-you-chic-ui`、Gitサブモジュール）を使う。サブモジュールの中身を直接変更しない | PM（Tech Stack・Forbidden） |
| 技術 | アプリのログは SLF4J/logback、外部エクスポートは Actuator 経由の OTEL（Intent の依頼内容） | IS |
| 内部DB | H2。内部DBのテストは本番と同じ H2 を組み込みで使う | RQ1、RQ16 |
| 配備 | 当面は開発者のPC上のコンテナでの起動・確認のみ | TP |
| 進め方 | 本Intentが最初のアプリ骨格を兼ねるため、最初の Bolt に検査・カバレッジ・CI・共通エラー応答などの一式を含める | TP |
