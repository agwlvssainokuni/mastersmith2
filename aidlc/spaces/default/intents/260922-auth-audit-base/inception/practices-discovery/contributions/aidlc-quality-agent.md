### 2. Testing Posture への指摘と提案

#### 2.1 Methodology / Ordering（面談 P8）

- 証拠（Q-E7）が示すのは test-after であり、初稿の既定値と一致する。ただし本Intentは認証・アカウントロック・
  監査ログというセキュリティ上重要なロジックを含むため、面談では次の3案を**それぞれの Ordering の文とともに**示すことを勧める。
  品質担当の推奨は案B。
  - 案A `test-after`: 「テスト可能な層（ドメイン・サービス・API・画面部品）ごとに実装を書き、同じ Bolt の中でその層のテストを書いて実行し、すべて通ってから次の層へ進む。」
  - 案B `custom`: 「パスワード照合・ログイン失敗の回数とロック判定・トークンの発行と検証・管理者権限の判定・監査イベントの記録は、先に失敗するテストを書いてから実装する。それ以外の層は実装を書いた後、同じ Bolt の中でその層のテストを書いて実行し、すべて通ってから次の層へ進む。」
  - 案C `tdd`: 「すべての層で、先に失敗するテストを書き、それを通す最小限の実装を書き、整理する、の順で進める。」
- 案Bを推奨する理由: 失敗系（拒否・ロック・不正トークン）は、実装後にテストを書くと実装に合わせた確認になりやすく、
  「通るべきでないものが通る」欠陥を見落としやすい。一方、画面や構成まわりまで先にテストを書くのは1名体制には負担が大きい。
- 統合時の注意: `team-practices.md` の `- **Ordering**:` の行には現在【要確認・初稿の値】という印が入っている。
  この行は Code Generation が読み取る構造化された項目なので、最終版では印を外し、確定した順序を1文だけ書くこと。

#### 2.2 カバレッジの下限（面談 P9）

- 初稿の指摘どおり、スコープ `auth-audit-foundation` は org.md のスコープ別下限の一覧にないため、
  明示しなければ新規テストの下限がかからない。org.md は「Build and Test は定めた下限を検証し、通すために下げてはならない」
  としているので、**下限は本ステージで数値として確定しておかないと後で検証の根拠がなくなる**。
- 提案（面談で数値を確定）:
  - バックエンド・フロントエンドとも **行カバレッジ 80% 以上**（初稿と同じ）。
  - 加えて **分岐カバレッジ**の下限を持つ（例: 全体 70% 以上）。認証・認可・ロック判定は条件分岐が本体であり、
    行カバレッジだけでは「ロックされていない側の分岐しか通っていない」状態を見逃すため。
  - セキュリティ上重要なパッケージ（認証・トークン・権限判定・監査記録）には、より高い下限（例: 行・分岐とも 90% 以上）を別に設ける案もある。
- 書き方の注意: 下限を「スコープ `auth-audit-foundation` では」と書くと、後続Intent（別スコープ）で下限が外れる。
  `team.md` に入る内容なので、**スコープに依存しない本チームの下限**として書くこと（org.md の下限に追加する形で、矛盾はしない）。
- 除外対象を先に決める: 計測から外すもの（アプリの起動クラス、設定値だけのクラス、自動生成コード、`vendor/make-you-chic-ui`）を
  ここで決めておく。後から除外を増やすと、実質的に下限を下げることになる。
- 道具の候補: バックエンドは JaCoCo（ビルドの検証タスクで下限を下回ったら失敗させる）。
  フロントエンドは Vitest のカバレッジ機能（`@vitest/coverage-v8`、`thresholds` 設定）。
  make-you-chic-ui にはカバレッジの設定がない（Q-E7）ため、フロントエンドでは新規に導入する。

#### 2.3 テストの層と道具（面談 P10・P11、技術選定は後続ステージ）

- テスト量はワークフローの Test Strategy `Standard`（部品ごとに5〜8件、単体＋結合）に従い、下限はこれに追加される（初稿どおり）。
- バックエンド（Spring Boot 想定、候補）:
  - 単体: JUnit 5 ＋ AssertJ ＋ Mockito。
  - Web 層の結合: Spring の Web 層テスト＋ `spring-security-test`（未認証 401、権限不足 403、管理者 200 を HTTP で確かめる）。
  - DB を使う結合: **本番と同じ種類の DB をコンテナで起動する（Testcontainers）** を既定の原則とすることを勧める（面談 P11）。
    別の組み込み DB で代用すると、SQL の方言やスキーマ移行の差で本番だけ失敗することがあるため。
    この場合、ローカルと CI にコンテナ実行環境が必要になるので、前提条件として文書化する（Construction の規則「文書化した前提以外の手作業なしにテストを実行できること」）。
- フロントエンド: make-you-chic-ui と同じ Vitest ＋ Testing Library（jsdom）＋ user-event ＋ vitest-axe（初稿どおり）。
  画面ごとにアクセシビリティ検査を1件入れる（Q-E3 の慣行）。API 呼び出しの差し替え方法（例: MSW）は技術選定で決める。
- 性質ベースのテスト: `fast-check`（フロントエンド）／jqwik（Java）を、純粋関数（ロック判定の回数計算、トークンの有効期限判定、入力の検証など）に一部適用する案を、依頼者の既存の慣行（Q-E4）に合わせて提示する。
- 端から端まで（E2E）のテスト: Test Strategy `Standard` の範囲外。入れる場合は「ログイン → 管理画面の可否 → ログアウト」の1〜2本に絞る（例: Playwright）。入れるかどうかを面談で確認する。
- 性能検証（Operation）: 負荷試験の道具（例: k6、Gatling）は performance-validation ステージで決める。本ステージでは「性能の目標値は NFR 要件で数値化し、Operation で目標と実測を突き合わせる」ことだけを記録すればよい。

#### 2.4 テストしやすさのための設計上の前提（設計ステージへの申し送り）

- 時刻の差し替え: トークンの有効期限、ロックの解除（時間で解除する場合）を境界値で確かめるため、
  現在時刻は注入可能な時計（Java の `Clock` 等）から取得する。テスト中の `sleep` や実時刻への依存は避ける。
- テストの独立性: テストごとに自分のデータを用意し、DB はテストごとに巻き戻す／初期化する。実行順に依存しない。
- 再現性: 性質ベースのテストは失敗時の乱数の種を記録して再現できるようにする。不安定なテスト（flaky）は放置せず、原因を直すまで統合を止める。

#### 2.5 必ず書くテストの範囲（面談 P10）— 初稿への追加

初稿の一覧（認証・認可・監査）に賛成し、次を追加する。いずれも `scope-document.md` の S3〜S10 から導いた
テストの観点であり、新しい要件ではない。★印は**要件がまだ決まっておらず、テストが書けないもの**で、
本ステージで決めずに要件定義（requirements-analysis）へ申し送る。

- アカウントロック（S7）: 失敗回数のしきい値の境界（しきい値−1回ではロックされない／しきい値ちょうどでロックされる）、
  ロック中は正しいパスワードでも拒否される、ログイン成功で失敗回数が初期化されるか。
  ★しきい値、失敗回数を数える期間、ロックの解除方法（時間経過／管理者操作）。
- ログイン（S4）: 存在しないユーザーとパスワード誤りで、画面・API の応答が区別できない（ユーザーIDの存在が推測できない）こと。
- トークン（S4〜S6）: 有効期限の境界（期限直前は有効／直後は無効）、署名の改ざん、署名方式の指定を悪用した改ざん（`alg: none` 等）、
  ログアウト後のリフレッシュトークンの拒否。ログアウト後もアクセストークンが有効期限まで使えることは DECIDED 済みの仕様なので、
  「意図した動作」としてテストで明示する。★アクセストークン・リフレッシュトークンの有効期限の値、リフレッシュトークンを使うたびに作り直すか。
- 初期管理者の自動作成（S3）: 2回目以降の起動で重複作成しない、設定が無い／不正なときの動作、指定したパスワードがログに出ない。
  ★設定が無いときに起動を止めるか続けるか。
- 認可（S8）: 未認証（401）、管理者フラグなし（403）、管理者（200）をサーバー側で確かめる。
  画面で管理メニューを隠すことはセキュリティの代わりにならないため、画面のテストとは別にサーバー側のテストを必須とする。
- 監査ログ（S9）: 対象イベントごとに1件ずつ、必須項目（日時・ユーザー・イベント種別・結果など）が記録されること。
  存在しないユーザーIDでのログイン失敗も記録されること。★監査ログの書き込みに失敗したとき、操作自体を失敗させるか続けるか。
- 秘密情報の漏えい（S9・S10、候補F1と対応）: ログ出力と監査ログを取り込み、パスワード・トークンの値が含まれないことを確かめるテスト。
- 構造化ログ・分散トレース（S10）: ログが決めた形式で出る、トレースIDがログに含まれる、外部エクスポートが既定で無効であること。
- 画面（S2）: ログイン画面のアクセシビリティ検査、ロック時のメッセージ表示、ログアウトでトークンが破棄されること。

### 3. CI の品質ゲートへの指摘（面談 P3・P9・P14）

- **矛盾の指摘**: 初稿は「統合前に CI で実行する」（Testing Posture）と「プルリクエストは使わず、ローカルで統合してプッシュし、
  統合先へのプッシュで CI を実行する」（Way of Working）を同時に提案している。後者では CI は統合**後**に走るため、
  失敗しても統合は止まらず、「統合前の CI 実行」は満たせない。面談で次のどちらかを選ぶ必要がある。
  - 案1: 1名体制でもプルリクエストを使い、CI が通らないと統合できない設定（ブランチ保護）にする。CI が本当の関門になる。
  - 案2: プルリクエストは使わない。代わりに、CI と**同じ検査を1コマンドでローカル実行**し、通ったことを確認してから統合する（これを統合前の関門とする）。
    CI は統合後の再確認として走らせ、失敗したら次の Bolt に進む前に直す。
- CI で実行する検査の順序（提案）: フォーマット検査 → lint → ビルド（型検査を含む）→ 単体テスト → 結合テスト（DB コンテナ使用）
  → カバレッジ下限の検証。いずれか1つでも失敗したら全体を失敗とする。セキュリティ検査（依存関係・秘密情報の走査など）の位置は security 担当の提案に合わせる。
- テストを飛ばして通すことの禁止: `@Disabled` や `it.skip` などでテストを無効化したまま統合しない。一時的に無効化する場合は理由と戻す期限をコード中に書く。
- `vendor/make-you-chic-ui` のテストは本リポジトリの CI の対象外とする（同リポジトリ側で管理する。候補F3と整合）。ただしフロントエンドのビルドが同梱版で通ることは CI で確かめる。

### 4. 最初の Bolt（端から端まで通る薄い土台）への追加提案（面談 P6）

- 初稿の完了条件に加え、**カバレッジの計測と下限の検証を最初の Bolt から有効にする**。後から入れると、既存コードのために下限を
  下げたくなる圧力がかかるため。
- DB を使う結合テスト（コンテナで起動）を最低1件、ヘルスチェックへの起動確認テストを1件含める。これで「DB のテスト方法」が最初の Bolt で実証される。

### 5. discovered-rules.md の候補への意見（面談 P21）

- 候補M1・M2・F1・F2 は品質の観点から妥当。人間が明言した場合のみ採用する、という初稿の扱いに賛成。
- 面談で確認する候補として次を追加することを提案する（いずれも依頼者が明言した場合のみ採用）。
  - 候補M4: ALWAYS 不具合を修正するときは、その不具合を再現するテストを同じコミットに含める（Q-E6 の慣行と一致）
  - 候補F4: NEVER テストを無効化（`@Disabled`、`it.skip` 等）した状態で統合先へ統合しない
- カバレッジ下限を下げてはならないことは org.md に既にあるため、重複する規則は作らない。

### 6. 面談で追加で聞くべきこと（品質担当から）

- P10 補足: E2E テストを入れるか（入れるなら本数の上限）。
- P11 補足: DB を使うテストは本番と同じ種類の DB をコンテナで起動する、を原則にしてよいか。
