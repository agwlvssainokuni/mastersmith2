## Way of Working

- 私たちは依頼者1名とAIの2者で開発する。レビューと承認は依頼者が行う。
- **【要確認・最重要】統合ブランチ**: 現在の作業はすべて `develop` に直接コミットされ、
  `origin/develop` へプッシュされている。`main` はリモート（`origin/main`）に初回コミットだけがあり、
  ローカルには `main` ブランチが存在しない。org.md の既定（`main` へのトランクベース開発）とは
  実態が異なるため、次のいずれかを選ぶ必要がある。
  - 案A（実態に合わせる・主担当の推奨）: `develop` を日々の統合先とする。Construction の Bolt
    ごとの作業ブランチ（worktree）は `develop` から作成し、`develop` へ戻す。`main` はリリース
    （デプロイ対象の確定版）を取り込む先として扱い、`develop` → `main` の取り込みはリリース時に
    依頼者の承認のもとで行う。
  - 案B（org.md の既定に合わせる）: `main` を唯一のトランクとし、Bolt ブランチは `main` から作成して
    `main` へ戻す。現在の `develop` の履歴を `main` へ取り込み、以後 `develop` は使わない。
- **【要確認】Bolt ブランチの寿命**: Bolt ブランチは短命（1〜2日程度で統合先へ戻す）とする。
  長期間生きる機能ブランチは作らない。
- **【要確認】統合方法**: Bolt ブランチは統合先へ **squash マージ** し、1 Bolt = 統合先の1コミットとする
  （org.md の既定）。代替案は、Bolt ブランチの個々のコミットを残すマージコミット方式。
  これまでの「こまめにコミットし、履歴を細かく残す」進め方を統合先の履歴にも残したい場合は
  マージコミット方式が合う。squash の場合でも、細かい履歴は Bolt ブランチと監査ログに残る。
- **【要確認】統合コミットのメッセージ**: squash / マージのコミットメッセージは日本語で、
  Bolt の内容が分かる件名にする（project.md の Change Control に従い、実行前に依頼者の承認を得る）。
- **【要確認】プルリクエストの要否**: 1名体制のため、GitHub のプルリクエストは使わず、
  ローカルで統合して `origin` へプッシュする。CI を導入した後は、統合先へのプッシュで CI を実行する。
- **【要確認】プッシュのタイミング**: コミットと同じく、プッシュも実行前に依頼者の承認を得る。

## Walking Skeleton

- **【要確認】最初に端から端まで通る薄い土台を作るか**: スコープ `auth-audit-foundation` は
  `skeleton: on` を宣言しており、主担当は「作る」を推奨する。最初の Bolt は単独で実行し、
  依頼者が明示的に承認してから残りの Bolt に進む。
- **【要確認】土台に含める範囲（提案）**: 本Intentはアプリ骨格を兼ねる（scope-document.md S1）ため、
  次を1本に通すことを土台の完了条件とする。
  - バックエンドのアプリが起動し、内部DBに接続でき、ヘルスチェック用のエンドポイントが応答する
  - 構造化ログが1行以上、決めた形式で出力される
  - make-you-chic-ui を組み込んだフロントエンドがビルドでき、バックエンドとつながった画面
    （ログイン画面の枠）が表示される
  - バックエンド・フロントエンドの両方でビルドとテスト（最低1件ずつ）が1コマンドで通る
  - （CI を導入する場合）同じビルドとテストが CI 上でも通る
- **【要確認】2本目以降の Bolt の進め方**: 最初の Bolt の完了後に「残りの Bolt をどう進めるか」を
  改めて選ぶ（自動で続ける／Bolt ごとに承認する）。主担当は、認証・監査という影響範囲の大きい
  基盤であること、これまで各段階で細かく承認してきた進め方から、**Bolt ごとに承認する**を推奨する。
  この選択は最初の Bolt 完了時に行い、ここでは希望のみを記録する。

## Testing Posture

- **Methodology**: test-after
- **Ordering**: 【要確認・初稿の値】テスト可能な層（ドメイン・サービス・API・画面部品など）ごとに実装を書き、その直後に同じ Bolt の中でその層のテストを書いて実行し、全テストが通ってから次の層へ進む。
- 【要確認】上記は org.md の既定（test-after）をそのまま初稿に置いたもの。代替案として、
  認証・認可・アカウントロック・トークン検証などセキュリティ上重要なロジックだけは先にテストを書く
  （TDD）混在方式がある。その場合は Methodology を `custom` とし、Ordering をその順序に書き換える。
- 私たちはテストを各 Bolt の成果物の一部として扱い、テストのない機能は完成とみなさない。
- **【要確認】カバレッジの下限**: 本スコープ `auth-audit-foundation` はプロジェクト用に作成した
  スコープで、org.md の「スコープ別の下限」一覧（mvp / feature など）に含まれない。そのため、
  明示しない限り新規テストのカバレッジ下限がかからない。主担当は、バックエンド・フロントエンド
  それぞれで **行カバレッジ 80% 以上** を下限とし、統合前に CI で実行することを提案する。
- テスト量と種類はワークフローの Test Strategy（現在 `Standard`）に従い、上記の下限はそれに追加される。
- **【要確認】必ず書くテスト（提案）**:
  - 認証: ログイン成功、パスワード誤り、存在しないユーザー、アカウントロック、
    期限切れ・改ざんされたトークン、リフレッシュトークンの無効化後の利用
  - 認可: 管理者フラグのないユーザーが管理画面へアクセスした場合の拒否
  - 監査: 対象イベント（ログイン成功・失敗、ログアウト、権限不足によるアクセス拒否）が
    漏れなく内部DBに記録されること
- **【要確認】テストの道具（候補）**: バックエンドの道具は技術選定（後続ステージ）で確定する。
  フロントエンドは make-you-chic-ui と同じ Vitest + Testing Library（jsdom）+ vitest-axe
  （アクセシビリティ検査）を候補とする。
- 【要確認】DBを使うテストで本番と同じ種類のDBを使うか（コンテナで起動する等）は、
  内部DBの選定とあわせて決める。

## Deployment

- **【要確認・現状】** CI も配備先も、まだ何もない。Operation フェーズのステージ
  （デプロイパイプライン、環境構築、デプロイ実行、監視設定、性能検証）はすべて実行予定のため、
  配備先の方針をここで決めておく必要がある。
- **【要確認】配備先の環境（候補）**:
  - 案1: 当面はローカル（開発者のPC上のコンテナ）での起動・確認のみとし、クラウドへの配備は後続Intentで決める
  - 案2: 検証環境（staging）を1つ用意し、統合先への統合ごとに自動で配備する（org.md の既定）。
    本番環境は、依頼者の手動承認があるときだけ配備する
  - 案3: その他（依頼者が指定）
- **【要確認】本番配備の承認者**: org.md の既定は「技術リーダー＋プロダクトオーナーの承認」だが、
  1名体制のため依頼者1名がその両方を兼ねる。
- **【要確認】CI の置き場所（候補）**: リモートが GitHub のため、GitHub Actions を候補とする。
  統合先ブランチへのプッシュで、lint・フォーマット検査・ビルド・テスト・カバレッジ検査を実行し、
  失敗したら統合を止める。
- 私たちは、配備のたびに起動確認（ヘルスチェック）と最低限の動作確認（スモークテスト）を行い、
  それが通るまで配備完了とはみなさない。
- 私たちは、すべての配備に戻し方（直前の成果物での再配備など）を用意する。DBスキーマの変更は
  前進のみ・後方互換を保つ形で行う。
- **【要確認】成果物の版の付け方（候補）**: コミットのハッシュを成果物に付け、リリース時には
  `main`（または統合先）にタグを付ける。
- 構造化ログの外部エクスポートは既定で無効、設定で有効化する（scope-document.md S10）ため、
  配備設定でその切り替えを環境ごとに持つ。

## Code Style

- 私たちは、言語ごとの慣習的な命名（Java はクラスが PascalCase・メソッドと変数が camelCase、
  TypeScript は camelCase、React コンポーネントは PascalCase）に従う。
- 私たちは、フォーマッタとリンタの設定をリポジトリに置き、CI で検査して、違反があれば統合を止める。
  主担当の提案は、リンタの設定で既に扱っている項目については追加の指摘をしないこと（org.md の既定）。
- **【要確認】フロントエンド（提案）**: 依頼者自身の make-you-chic-ui と同じ設定を採用する。
  - Prettier: セミコロンなし、シングルクォート、末尾カンマあり（all）、1行100文字、インデント2スペース
  - oxlint（correctness を error、react / jsx-a11y / typescript 系のルール）＋ ESLint（react-hooks の推奨ルールのみ）
  - Stylelint（stylelint-config-standard）
  - テストファイルは対象ファイルと同じ場所に `*.test.tsx` として置く
- **【要確認】バックエンド（Java）（候補）**: フォーマッタとリンタを決める。候補は
  Spotless ＋ google-java-format / palantir-java-format / IntelliJ の既定スタイル、および
  Checkstyle などの静的検査。インデント幅、1行の文字数もあわせて決める。
- **【要確認】ライセンスヘッダーのコメント記法**: project.md のとおり Apache License 2.0 ヘッダーを
  入れる。make-you-chic-ui ではヘッダーを `/* ... */`（`/** ... */` ではない）で書く方式に統一しているため、
  Java・TypeScript・CSS でも同じく `/* ... */` を使うことを提案する。
- **【要確認】パッケージ名・ディレクトリ構成**: Java のルートパッケージ名と、バックエンド・
  フロントエンドのリポジトリ内の配置（例: バックエンドとフロントエンドを別ディレクトリに分ける）を決める。
- **【要確認】コード中のコメントの言語**: コードコメントや Javadoc を日本語で書くか英語で書くかを決める。
- 文字コードは UTF-8、改行コードは LF とする（【要確認】）。
