# Domain Design — Questions

要件定義書（`aidlc/spaces/default/intents/260922-auth-audit-base/inception/requirements-analysis/requirements.md` の FR1〜FR10）を実現する「部品（コンポーネント）」の分け方を決めます。ここでいう部品は、私たちが書くコードのまとまり（業務の決まりとデータを持つ単位）で、DB やログの送り先などは部品ではなく、部品が使う外部のものとして扱います。どの単位でデプロイするか（1つのアプリにまとめるか等）は次の Units Generation で決めます。

アーキテクトとしての初期案は次の部品です。

- **利用者アカウント**: 利用者（メールアドレス・パスワードのハッシュ・管理者フラグ）と、初期管理者の自動作成
- **認証**: ログイン、トークンの発行・検証・更新、ログアウト、アカウントロック
- **監査ログ**: 監査イベントの記録
- **画面（フロントエンド）**: ログイン画面、アプリシェル、管理者向け領域、トークンの保持と API 呼び出し

以下で、分け方が複数考えられる点を確認します。

### Q1. ログインの失敗回数とロックの状態（ロック解除の時刻）は、どの部品が持ちますか？

- A. 利用者アカウントが、利用者の情報の一部として持つ（利用者1人に1組）
- B. 認証が、利用者とは別のデータ（ログイン試行の状態）として持つ。利用者アカウントはロックを知らない
- X. Other (please specify)

[Answer]: B. 認証が、利用者とは別のデータ（ログイン試行の状態）として持つ。利用者アカウントはロックを知らない

### Q2. 管理者だけが使える API・画面を守る仕組み（管理画面のアクセス制御）は、どこに置きますか？

後続の Intent F で、ロール（役割）ごとの権限設定を追加する予定です。

- A. 認証の一部とする（本Intentでは「管理者フラグがあるか」の判定だけなので小さい）
- B. 「アクセス制御」という別の部品にする（Intent F のロール・権限の判定を後から同じ部品に足せる）
- X. Other (please specify)

[Answer]: B. 「アクセス制御」という別の部品にする（Intent F のロール・権限の判定を後から同じ部品に足せる）

### Q3. 認証やアクセス制御が監査ログを記録するとき、どのようにつなぎますか？

監査ログの書き込みに失敗しても元の操作は続けます（決定済み）。後続Intent向けの共通化は後で行います（決定済み）。

- A. 認証・アクセス制御が、監査ログの部品を直接呼び出して記録する（書き込み失敗は監査ログの部品の中で受け止め、呼び出し元には影響させない）
- B. 認証・アクセス制御は「ログインに成功した」などの出来事をアプリ内に知らせるだけにし、監査ログの部品がそれを受け取って記録する（呼び出し元は監査ログの部品を知らない）
- X. Other (please specify)

[Answer]: B. 認証・アクセス制御は「ログインに成功した」などの出来事をアプリ内に知らせるだけにし、監査ログの部品がそれを受け取って記録する（呼び出し元は監査ログの部品を知らない）

### Q4. 構造化ログ・分散トレース・外部エクスポート（FR10）は、どう扱いますか？

これらは業務の決まりを持たず、アプリ全体にかかる設定・仕組みです。

- A. 部品にはせず、アプリ全体の共通の仕組み（設定）として扱う。各部品はそれを使う側
- B. 「観測性」という部品にする
- X. Other (please specify)

[Answer]: A. 部品にはせず、アプリ全体の共通の仕組み（設定）として扱う。各部品はそれを使う側

### Q5. 初期管理者の自動作成（FR3）は、どの部品が持ちますか？

- A. 利用者アカウントが持つ（利用者を作る処理の1つとして）
- B. 起動時の初期化を受け持つ別の部品にする
- X. Other (please specify)

[Answer]: A. 利用者アカウントが持つ（利用者を作る処理の1つとして）

### Q6. 画面（フロントエンド）は、どのように分けますか？

チームの進め方では、フロントエンドは機能ごとに分けることにしています。

- A. 次の単位に分ける: ①アプリの骨組み（ルーティング、アプリシェル、表示言語の切り替え）、②認証の画面側（ログイン画面、トークンの保持と更新、ログアウト、ログイン状態の管理）、③管理者向け領域（プレースホルダ）、④API 呼び出しの共通部分（アクセストークンの付与、401 時の更新と再試行、エラー応答の変換）
- B. 画面（フロントエンド）全体を1つの部品として扱い、中の分け方は後の設計で決める
- X. Other (please specify)

[Answer]: A. 次の単位に分ける: ①アプリの骨組み（ルーティング、アプリシェル、表示言語の切り替え）、②認証の画面側（ログイン画面、トークンの保持と更新、ログアウト、ログイン状態の管理）、③管理者向け領域（プレースホルダ）、④API 呼び出しの共通部分（アクセストークンの付与、401 時の更新と再試行、エラー応答の変換）

### Q7. （実現可能性）内部DBを「アプリに組み込んだ H2（ファイルに保存）」にすると、アプリを同時に複数台動かして負荷を分けることはできません。この前提でよいですか？

想定規模（利用者 最大50名、同時ログイン 最大10名）では1台で足りる見込みです。接続先は設定で切り替えられるため、将来 H2 を別サーバーとして動かす形に変えることはできます。

- A. 当面は1台で動かす前提でよい
- B. 最初から複数台で動かせるようにしたい（内部DBの形を見直す）
- X. Other (please specify)

[Answer]: A. 当面は1台で動かす前提でよい
