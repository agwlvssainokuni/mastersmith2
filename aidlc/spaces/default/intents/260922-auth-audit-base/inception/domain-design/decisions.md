# Architecture Decision Records — Domain Design

本書は、部品の分け方（`components.md`）で下した設計判断の記録である。判断の元は `domain-design-questions.md` の確定回答（DQ1〜DQ7）と、要件定義書 `aidlc/spaces/default/intents/260922-auth-audit-base/inception/requirements-analysis/requirements.md` である。

## ADR-001: 利用者アカウントと認証を別の部品に分ける

- **Context** — 本Intentでは利用者の管理は「初期管理者の自動作成」だけで小さい。一方、後続Intentでは利用者の登録・招待（G）、プリファレンス（H）、ロールの割り当て（F）が利用者のデータに加わり、認証の仕組み（トークン・ロック）とは別の理由で変わっていく。
- **Decision** — 利用者のデータ（User）と初期管理者の作成を UserAccount に、ログイン・トークン・ログアウト・ロックを Authentication に置く。Authentication は UserAccount からパスワードの照合結果だけを受け取り、パスワードのハッシュ値は UserAccount の外に出さない。
- **Consequences** — 後続Intentで利用者の管理を広げても、認証の仕組みを触らずに済む。パスワードのハッシュ値を扱う場所が1か所に閉じる。一方、ログインのたびに部品をまたぐ呼び出しが1回増える（同じアプリ内の呼び出しで、性能への影響は小さい）。
- **Alternatives Rejected** — 利用者アカウントと認証を1つの部品にする案: 当面は小さいが、後続Intentで利用者の管理と認証の仕組みが同じ部品の中で絡み合い、変更の影響範囲が広がるため採らない。

## ADR-002: ログインの失敗回数とロック状態は、認証が別のデータとして持つ

- **Context** — アカウントロック（FR7）には利用者ごとの連続失敗回数とロック解除の時刻が要る。これを利用者のデータに載せるか、認証の側に置くかを決める必要があった（DQ1）。
- **Decision** — Authentication が LoginAttemptState（利用者ID・連続失敗回数・ロック解除の時刻）として持つ。UserAccount はロックを知らない。
- **Consequences** — ロックの規則（しきい値・解除までの時間、FR7.5）を変えても UserAccount に影響しない。ログインのたびに書き換わる値が利用者のデータから切り離され、利用者のデータの更新と競合しにくい。一方、利用者を削除する機能を後で加える場合は、LoginAttemptState の後始末を Authentication 側で行う必要がある（本Intentでは利用者の削除は範囲外）。
- **Alternatives Rejected** — 利用者のデータの一部として持つ案: 利用者1人に1組で単純だが、認証の規則が UserAccount に入り込み、ADR-001 の分け方の意味が薄れるため採らない。

## ADR-003: 管理画面のアクセス制御を「アクセス制御」という別の部品にする

- **Context** — 本Intentの判定は「管理者フラグがあるか」だけで小さい。ただし後続の Intent F でロール・権限ごとの判定が加わる予定である（DQ2）。
- **Decision** — AccessControl を別の部品とし、管理者のみの API の判定（未認証は 401、管理者フラグの無い利用者は 403）と、アクセス拒否の出来事の通知を置く。利用者と管理者フラグは Authentication が検証したアクセストークンから得る。
- **Consequences** — Intent F の判定をこの部品に足せば済み、Authentication を触らずに済む。判定はサーバー側で行い、画面でメニューを隠すことに頼らない（FR8.2）。一方、本Intentでは中身の小さい部品が1つ増える。
- **Alternatives Rejected** — 認証の一部にする案: 当面は小さいが、Intent F で認証の部品に権限の判定が加わり、変更の理由が混ざるため採らない。

## ADR-004: 監査ログは、出来事を受け取って記録する形でつなぐ

- **Context** — 認証とアクセス制御の出来事を監査ログに記録する（FR9.1）。監査ログの書き込みに失敗しても元の操作は続ける（FR9.4）。後続Intent向けの監査の共通化は後で行う（決定済み）。部品どうしのつなぎ方を決める必要があった（DQ3）。
- **Decision** — Authentication と AccessControl は「ログインに成功した」などの出来事をアプリ内に知らせるだけにし、AuditLog がそれを受け取って記録する。出来事を知らせる側は AuditLog を知らない。書き込みの失敗は AuditLog の中で受け止め、アプリのログにエラーとして出す。
- **Consequences** — 監査ログの失敗が元の操作に影響しない形が、つなぎ方そのもので保証される。後続Intentで記録する出来事が増えても、出来事を知らせる側に監査の処理を書き足さずに済む。一方、出来事の受け取りを元の操作と同じ流れで行うか別の流れで行うか、また出来事に載せる項目（接続元IP・User-Agent・トレースIDなど）は、後の設計（Functional Design・NFR Design）で決める必要がある。同じ流れで行う場合は、書き込み失敗の例外を元の操作に伝えない作りが必要になる。
- **Alternatives Rejected** — 認証・アクセス制御が監査ログの部品を直接呼ぶ案: 流れが追いやすいが、呼ぶ側が監査ログの部品に依存し、監査の対象が増えるたびに呼ぶ側を変える必要があるため採らない。

## ADR-005: 構造化ログ・分散トレース・外部エクスポートは部品にせず、共通の仕組みとして扱う

- **Context** — FR10 のログ・トレース・エクスポートは業務の決まりもデータも持たず、アプリ全体にかかる設定と仕組みである（DQ4）。FR1 のアプリの起動・ヘルスチェック・内部DBの接続設定も同じ性質を持つ。
- **Decision** — 観測性（FR10）とアプリの骨格（FR1）、共通のエラー応答（Problem Details と `code`）は部品にせず、アプリ全体の共通の仕組みとして扱う。各部品はそれを使う側とする。
- **Consequences** — 部品の一覧が業務の関心事だけになり、境界が分かりやすい。一方、トレースIDを監査ログに載せる（FR9.2）ために、AuditLog が共通の仕組みから現在のトレースIDを得る方法を後の設計で決める必要がある。
- **Alternatives Rejected** — 「観測性」という部品にする案: データも業務の決まりも持たない部品になり、依存関係の図で全部品から依存される形になって、部品の分け方として意味を持たないため採らない。

## ADR-006: 初期管理者の自動作成は、利用者アカウントが持つ

- **Context** — 初回起動時に設定で指定した管理者を作る（FR3）。これを利用者を作る処理の1つとするか、起動時の初期化を受け持つ別の部品にするかを決める必要があった（DQ5）。
- **Decision** — UserAccount が持つ。起動時に UserAccount の処理として実行し、既にいれば作らない。設定が無い・パスワードが規則を満たさない場合は警告を出して起動を続ける。
- **Consequences** — 利用者を作る処理とパスワードの規則（12文字以上）が1か所にまとまり、後続Intent（G: 登録・招待）で同じ処理を使える。一方、起動時の処理が UserAccount に入るため、起動の順序（内部DBの準備の後に実行すること）を後の設計で押さえる必要がある。
- **Alternatives Rejected** — 起動時の初期化を受け持つ別の部品にする案: 起動時の処理が1か所にまとまるが、本Intentでは初期化の対象が初期管理者だけであり、利用者を作る処理が2か所に分かれるため採らない。

## ADR-007: 画面（フロントエンド）を4つの部品に分け、API 呼び出しの共通部分は認証の画面側に依存させない

- **Context** — チームの進め方では、フロントエンドは機能ごとに分ける（DQ6）。API 呼び出しの共通部分はトークンを付け、401 時にトークンを更新する必要があるが、トークンを持つのは認証の画面側であり、認証の画面側はログイン・更新・ログアウトの API 呼び出しに共通部分を使う。そのまま依存させると互いに依存する形になる。
- **Decision** — 画面を AppFrame（骨組み・アプリシェル・表示言語）、AuthUi（ログイン画面・トークンの保持と更新・ログアウト・ログイン状態）、AdminArea（管理者向け領域）、ApiClient（トークンの付与・401 時の更新と1回の再試行・エラー応答の変換）に分ける。ApiClient はトークンの取得と更新の手段を AuthUi から登録してもらう形とし、AuthUi に直接依存しない。
- **Consequences** — 部品どうしの依存に循環が無い（AppFrame → AuthUi・AdminArea → ApiClient）。トークンの扱いが AuthUi に閉じる。一方、ApiClient を使う前に AuthUi がトークンの手段を登録しておく必要があり、登録の時期（アプリの起動時）を後の設計で決める。
- **Alternatives Rejected** — 画面全体を1つの部品として扱う案: 当面は単純だが、後続Intentで管理機能が加わったときにトークンの扱いと機能の画面が混ざるため採らない。ApiClient が AuthUi に直接依存する案: 両者が互いに依存する循環になるため採らない。

## ADR-008: 内部DBを組み込みの H2 とし、当面はアプリを1台で動かす

- **Context** — 内部DBは H2 で、既定はアプリに組み込んでファイルに保存する形とする（FR1.2）。この形ではアプリを同時に複数台動かして負荷を分けることができない。想定規模は利用者 最大50名、同時ログイン 最大10名である（DQ7）。
- **Decision** — 当面はアプリを1台で動かす前提とする。UserAccount・Authentication・AuditLog のデータはすべて同じ内部DBに置く。
- **Consequences** — 構成が単純で、開発者のPC上のコンテナでもそのまま動く。リフレッシュトークンやロック状態を複数台で共有する仕組みが要らない。一方、複数台で動かす必要が出たときは、H2 を別サーバーとして動かす形へ接続設定で切り替え、同時更新の扱い（ロック状態の失敗回数など）を見直す必要がある。
- **Alternatives Rejected** — 最初から複数台で動かせるようにする案: 想定規模では1台で足り、内部DBの形の見直しと共有の仕組みの分だけ手間が増えるため採らない。
