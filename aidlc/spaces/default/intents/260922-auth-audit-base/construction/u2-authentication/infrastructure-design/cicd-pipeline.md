# CI/CD Pipeline — U2 認証（u2-authentication）

U2 は U1 の検査・ビルド・配備の流れ（U1 の `infrastructure-design/cicd-pipeline.md`: `./gradlew verify`、pre-commit、GitHub Actions、手元のコンテナへの配備）をそのまま使い、流れの形は変えない。本書は、U2 がその流れに足すテストと設定だけを書く。入力は U2 の NFR Design（`security-design.md` 8章のテスト、`reliability-design.md` 5章の品質、`performance-design.md`、`observability-design.md`、`scalability-design.md`、`logical-components.md`）、Domain Design の `components.md`、U2 の `functional-spec.md` である。`contract-summary.md` は、本ワークフローで Contract Design を行わないため無い。

## 1. `./gradlew verify` に足すもの

| 段（U1 の順） | U2 が足すもの |
|---|---|
| 5 単体テスト | ロックの判定と有効期限の判定の性質ベースのテスト（jqwik）、トークンの発行と検証（期限の境界・改ざん・`alg: none`・別の方式）、パスワードの長さの境界、秘密情報を持つ型の伏せ字、ログイン画面の部品（Vitest・vitest-axe・日英の文言） |
| 6 結合テスト | ログイン・更新・ログアウトの流れ（組み込みの H2）、3つの失敗の経路の応答・SQL の回数・照合の回数、同時の失敗（行の排他）、同時の更新（条件付きの無効化）、Cookie の属性と Path、Origin の確認、初期管理者の作成（重複しない・設定が無い／不正）、鍵が無い・短いときの起動の失敗、TRACE を有効にしても秘密情報がログに出ないこと、監査の受け取りの失敗で応答が変わらないこと |
| 8 安全の検査 | 追加なし（U1 の検査が U2 のコードも対象にする） |

チームの進め方の必須の認証のテスト（ロックのしきい値の境界、ユーザーの存在を推測できないこと、トークンの有効期限の境界・改ざん・`alg: none`、ログアウト後のリフレッシュトークンの拒否、ログアウト後もアクセストークンが期限まで使えること、初期管理者の重複作成なし・設定が無い／不正なとき・パスワードがログに出ないこと、秘密情報がログに出ないこと、ログイン画面のアクセシビリティ）を、上の単体テストと結合テストで漏れなく入れる。

- 時刻に依存するテストは注入できる時計を使い、実時間を待たない。
- テストの署名鍵と初期管理者の値は、テストの中で作った仮の値を使い、リポジトリの設定ファイルに書かない。Gitleaks がテストの仮の値を誤って検出する場合は、その値の形を Gitleaks の除外の設定に理由つきで書く（除外を広げすぎない）。

## 2. CI（GitHub Actions）

- 追加の設定は無い。CI は署名鍵などの秘密情報を使わない（U1 の設計のとおり、GitHub の秘密情報の保管は使わない）。
- 同時の処理のテスト（行の排他・条件付きの無効化）は、CI のランナーでも安定して通るように、スレッドの開始をそろえる仕組み（同時に始める合図）で書き、時間の待ちに頼らない。不安定なテストは原因を直すまで統合しない（チームの進め方）。

## 3. 配備と戻し方

| 手順 | U2 に固有の点 |
|---|---|
| 初めての配備 | `.env` に署名鍵と初期管理者の設定を入れてから `docker compose up`。起動のログで「初期管理者を作成した」の INFO を確かめる |
| 配備の確認 | U1 の確認（ヘルスチェック、ログイン画面の表示）に加えて、初期管理者でログインでき、ログアウトできること（スモークテスト） |
| 鍵の交換 | `.env` の署名鍵を替えてコンテナを作り直す。発行済みのアクセストークンは 401 になり、画面は更新で取り直す（ログインし直しは要らない） |
| 戻し方 | U1 のとおり直前の版の WAR で作り直す。U2 の表のスキーマの変更も前進のみ・後方互換で、1つ前の版のアプリが今のスキーマで動く |

## 4. 段と関門の対応

U1 の `cicd-pipeline.md` 6章のとおり。U2 のテストは、統合の前の `./gradlew verify` と CI の関門に含まれる。
