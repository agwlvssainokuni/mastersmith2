# Scalability Design — U2 認証（u2-authentication）

U2 の拡張性の要件（`scalability-requirements.md` の NFR1.6〜NFR1.10）を満たす設計。前提は Domain Design の ADR-008（当面はアプリを1台で動かす）。技術は U2 の `tech-stack-decisions.md`、処理の流れは U2 の `functional-spec.md`、性能は `performance-design.md`（`performance-requirements.md`）、同時の処理の正しさは `reliability-design.md`（`reliability-requirements.md`）、秘密情報とログは `security-requirements.md`・`observability-requirements.md` に従う。`contract-summary.md` は、本ワークフローで Contract Design を行わないため無い。

## 1. データの量と索引

| 表 | 行の数の見積もり | 索引 | 要件 |
|---|---|---|---|
| 利用者 | 最大 50 行 | メールアドレス（一意） | NFR1.6 |
| ロックの状態 | 利用者1人に1行（最大 50 行）＋ダミーの記録（数行） | 利用者ID（主キー） | NFR1.9 |
| リフレッシュトークン | 1人1日 約 100 行、全体で1日 約 5,000 行。削除により常に数万行以内 | トークンのハッシュ（一意）、有効期限、利用者ID | NFR1.7、NFR1.8 |

- ロックの状態の行は、利用者を作るときに同じトランザクションで作る。ログインのときに行が無ければ（将来、別の経路で利用者が作られた場合）、行を作ってから排他つきで読む。
- ダミーの記録の行は、スキーマの変更（Flyway）で固定の数（8 行）を入れる。利用者と結びつかない ID の範囲を使う。

## 2. 使い終わったリフレッシュトークンの削除（NFR1.7）

- Spring の定期実行で1日1回（既定は毎日 3 時 30 分、設定で変更可）動かす。
- 削除するのは、無効（使用済み・ログアウト）または期限切れで、期限から 7 日（設定で変更可）たった行。
- 1回の削除は件数の上限（1,000 行）ごとに分けて繰り返し、1つのトランザクションを長くしない。要求の処理と並んで動いても、ログインや更新を待たせない。
- 削除した件数を INFO でログに出す。失敗したら ERROR を出し、次の日に再び行う（要求の処理には影響しない）。

## 3. 1台で動かす形と、複数台にするときの余地（NFR1.6、NFR1.10）

- 1台で、同時ログイン 10 名を処理する（負荷の試験は `performance-design.md`）。
- サーバーに画面のセッションを持たない。認証の状態は、アクセストークン（利用者の側）と内部DB（リフレッシュトークン・ロックの状態）にだけある。
- 同じ利用者の試みを1つずつ行う処理は、内部DBの行の排他で行い、アプリのメモリに頼らない。リフレッシュトークンの無効化も、内部DBの条件付きの更新で行う。そのため、別サーバーの H2 に切り替えて複数台にしても、そのまま共有できる。
- 複数台にしたとき、削除の定期実行は各台で動くが、削除は何度行っても同じ結果になるため、害はない（重なりを避けたくなったら、そのときに1台だけで動かす仕組みを入れる）。
- 署名鍵は環境変数で渡すため、複数台では同じ鍵を渡す（Infrastructure Design で扱う）。
