# NFR Design — Questions（U2 認証 / u2-authentication）

U2 の NFR 要件（`nfr-requirements/` の各文書）を満たす設計の方針のうち、これまでの段階で決まっていない点を確認します。

決定済みの事項（再確認はしません）: 技術は U1 と U2 の `tech-stack-decisions.md` のとおり（bcrypt の cost 既定 12、JWT は HS256 で OAuth2 Resource Server の仕組みを使う、リフレッシュトークンは SHA-256 のハッシュで保存、CSRF は SameSite=Strict と Origin の確認、Spring Data JPA で行の排他と条件付きの更新）。U1 の NFR Design の決定（U1 が Spring Security のフィルターの連鎖を用意し、U2 は差し込み口で決まりを足す。ログは同期で標準出力へ。外部エクスポートの有効時はトレース・ログ・指標を送る）。ロックの悪用への追加の対策はしない（NFR4.4）。監査ログは元の操作の確定後に別のトランザクションで、同じスレッドで記録する（U4 の決まり 1.3）。

### Q1. ログインのパスワードの照合（bcrypt、1回 約 0.1〜0.5 秒）を、ロックの状態の行の排他の中で行いますか、外で行いますか？

U2 の決まり 3.8 は、同じ利用者の試みを1つずつ行う（行の排他）ことを求め、決まり 2.7 は、失敗の3つの経路で「利用者の検索1回・ロックの状態の読み取り1回・書き込み1回・照合1回」をそろえることを求めています。照合を排他の中で行うと、そのあいだ内部DBの接続（最大 10 本）と行の排他を持ち続けます。

- A. 照合を排他の外で先に行う。順番は「利用者の検索 → 照合（利用者がいなければダミーのハッシュで照合）→ 1回のトランザクションでロックの状態を排他つきで読み、判定して書き込む」。接続と排他を持つのは数ミリ秒で、同時のログインが接続を使い切らない。ロック中の場合も照合は行うが、結果は使わず失敗とする（決まり 2.5・3.3 の「ダミーの照合」を「結果を使わない照合」として満たす。回数と時間はそろう）
- B. 照合を排他の中で行う（決まりの文の順番どおり）。「利用者の検索 → 1回のトランザクションでロックの状態を排他つきで読む → ロック中ならダミーの照合、そうでなければ本物の照合 → 書き込み」。同じ利用者の試みは照合の時間ぶん順番待ちになり、同時のログインが 10 件あると、その間 DB の接続を使い切り、ほかの要求（認証つきの API の利用者の読み取り）が待つ
- X. Other (please specify)

## Consolidated Summary Confirmation

- パスワードの照合の位置（Q1）: 照合は行の排他の外で先に行う。順番は「利用者の検索 → 照合（利用者がいなければダミーのハッシュで照合）→ 1回の短いトランザクションでロックの状態を排他つきで読み、判定して書き込む」。DB の接続と排他を持つのは数ミリ秒
- ロック中の扱い: ロック中でも照合は行うが、結果は使わずに失敗とする。決まり 2.5・3.3 の「ダミーの照合」は「結果を使わない照合」として満たし、失敗の3つの経路で DB の読み書きと照合の回数をそろえる（決まり 2.7）
