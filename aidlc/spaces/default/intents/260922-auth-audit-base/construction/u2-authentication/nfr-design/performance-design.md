# Performance Design — U2 認証（u2-authentication）

U2 の性能の要件（`performance-requirements.md` の NFR1.1〜NFR1.5）を満たす設計。技術は U2 の `tech-stack-decisions.md` と U1 の選定、処理の流れは U2 の `functional-spec.md`（WF2〜WF5）に従う。規模は `scalability-requirements.md`、同時の処理の正しさは `reliability-requirements.md`、秘密情報とログは `security-requirements.md`・`observability-requirements.md` の要件とあわせて各設計書で扱う。設計の方針の確定回答は `nfr-design-questions.md`（Q1）にある。`contract-summary.md` は、本ワークフローで Contract Design を行わないため無い。U1 の共通の処理の予算（20 ミリ秒）は U1 の `nfr-design/performance-design.md` に従う。

## 1. ログインの API の予算（NFR1.1、NFR1.3）

同時 10 件の状態で 95% が1秒以内。確定回答 Q1 により、パスワードの照合は行の排他の外で先に行う。

| 手順 | 予算の目安 | DB の接続 | 備考 |
|---|---|---|---|
| U1 の共通の処理 | 20 ms | なし | U1 の設計 |
| 利用者の検索（メールアドレスの一意の索引） | 5 ms | 借りてすぐ返す | 読み取りだけ。トランザクションの外 |
| パスワードの照合（bcrypt、cost 12） | 100〜500 ms | 持たない | 利用者がいなければダミーのハッシュで照合 |
| ロックの状態の読み取り（排他つき）・判定・書き込み（1回のトランザクション） | 10 ms | 数ミリ秒だけ持つ | 排他を持つのはこの間だけ |
| トークンの発行（アクセストークンの署名、リフレッシュトークンの乱数・ハッシュ・保存） | 10 ms | 上と同じトランザクション | HMAC と SHA-256 は1ミリ秒未満 |
| 出来事の通知と監査の記録（確定の後、同じスレッド） | 10 ms | U4 の別のトランザクション | U4 の決まり 1.3 |
| 合計 | 約 150〜560 ms | — | 残りは同時の要求による CPU の取り合いの余裕 |

- **照合の時間をそろえる**: 利用者がいない・ロック中・誤り・成功のどの経路でも、照合は1回だけ行う。ダミーのハッシュは起動時に、設定した cost で1つ作っておく（cost が本物と同じになり、時間がそろう）。
- **cost の確かめ**: 起動時に照合1回の時間を測り、INFO でログに出す。100〜500 ミリ秒を外れたら WARN を出し、cost の見直しを促す（NFR2.1）。
- **CPU**: 照合は要求を処理するスレッドで行う。同時 10 件の照合が1秒以内に収まるかは、コンテナに割り当てる CPU の数による（仮定: 当面の開発者の PC で 4 コア程度。本番の配備先は未定）。Performance Validation で測り、足りなければ cost を下げる（NFR2.1 の範囲内で）か、配備先で割り当てる CPU を決める（Infrastructure Design）。
- **確認済みでないこと**: 上の予算の目安（検索 5 ms など）は見積もりであり、Performance Validation で実測して見直す。

## 2. トークンの更新の API の予算（NFR1.2）

| 手順 | 予算の目安 |
|---|---|
| U1 の共通の処理と Origin の確認 | 20 ms |
| リフレッシュトークンのハッシュ（SHA-256）で行を探す（一意の索引） | 5 ms |
| 条件付きの無効化（更新の問い合わせ1回）と新しい行の保存 | 10 ms |
| 利用者の読み取りとアクセストークンの発行 | 5 ms |
| 合計 | 約 40 ms（パスワードの照合が無いため、予算に大きな余裕がある） |

## 3. 認証が必要な API の要求ごとの処理（NFR1.4）

| 手順 | 予算の目安 | 設計 |
|---|---|---|
| アクセストークンの取り出しと署名の検証（HS256） | 1 ms | 検証の仕組みは起動時に1つ作って使い回す |
| 有効期限の確認 | 0 ms | 注入できる時計で比べる |
| 利用者の読み取り（主キー） | 5 ms | 決まり 4.5 により毎回 DB から読む。キャッシュは持たない（管理者フラグの変更をすぐ反映するため） |
| 合計 | 95% で 50 ms 以内 | — |

## 4. 利用者ごとの待ち合わせ（NFR1.5）

- ロックの状態の排他は利用者ごとの行に対して取るため、別の利用者のログインは待たない。
- 排他を持つのは1回の短いトランザクションの間だけで、照合の時間を含まない（確定回答 Q1）。同じ利用者の同時の試みも、待つのは数ミリ秒。
- 存在しないメールアドレスの試みは、ダミーの記録の行を使う（決まり 2.7）。ダミーの記録は複数行を用意し、ほかの試みが排他を持っている行を飛ばして選ぶ（排他の取得で待たない指定）。存在しないメールアドレスの試みどうしも待ち合わせない（決まり 2.7 の「待ち合わせが起きない形」）。

## 5. 画面

- アクセストークンはメモリに持つため、読み書きの費用はない。
- 401 を受けたときの更新は、同じタブの中で1回にまとめる（決まり 8.5）。同時に 401 を受けた要求は、1つの更新の結果を待ってから送り直す。
- ログイン画面の部品は、U1 の設計のとおり開いたときに読み込む（U1 の `nfr-design/performance-design.md` 4章）。
