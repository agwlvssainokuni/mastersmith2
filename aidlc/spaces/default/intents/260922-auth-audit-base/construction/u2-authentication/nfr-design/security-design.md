# Security Design — U2 認証（u2-authentication）

U2 の安全の要件（`security-requirements.md` の NFR2.1〜NFR2.3、NFR3.1〜NFR3.6、NFR4.1〜NFR4.4、NFR5.1〜NFR5.6）を満たす設計。技術は U2 の `tech-stack-decisions.md`、処理の流れは U2 の `functional-spec.md`（WF1〜WF9）、決まりは U2 の `rules.md` に従う。性能・拡張性・信頼性・観測性の要件（`performance-requirements.md`・`scalability-requirements.md`・`reliability-requirements.md`・`observability-requirements.md`）に関わる部分は各設計書を参照する。設計の方針の確定回答は `nfr-design-questions.md`（Q1）にある。`contract-summary.md` は、本ワークフローで Contract Design を行わないため無い。そのため、U2 の API のパスと Cookie の名前・Path は本書で決める（3章）。

U2 は、U1 が用意する土台（U1 の `nfr-design/security-design.md`: Spring Security のフィルターの連鎖、セキュリティ関係のヘッダー、アクセスの決まりの差し込み口、秘密情報の出し方の決まり、共通のエラー応答の組み立て）の上に作り、U1 の設定を書き換えない。

## 1. 部品の分け方と秘密情報の閉じ込め（ADR-001）

| 部品 | 受け持つ秘密情報 | 外に出すもの |
|---|---|---|
| UserAccount（`user` パッケージ） | パスワードのハッシュ、初期管理者の設定のパスワード | 照合の結果（一致・不一致）だけ。ハッシュは外に出さない |
| Authentication（`auth` パッケージ） | 署名鍵、アクセストークン、リフレッシュトークン（平文は応答の直前だけ、保存はハッシュ） | 検証済みの利用者（AuthenticatedUser: 利用者ID・メールアドレス・管理者か） |

照合（ダミーの照合と 72 バイトの確認を含む）は UserAccount の照合の処理にまとめる。Authentication はその結果だけを使う。

## 2. パスワード（NFR2.1〜NFR2.3、NFR3.1）

- **ハッシュ**: Spring Security の bcrypt（cost は設定、既定 12）。保存するのは bcrypt の形式の文字列だけ。
- **72 バイト**: 照合の処理に渡す前に、UTF-8 のバイト数を確かめる。72 バイトを超えたら照合の仕組みには渡さず、ダミーのハッシュで照合して「不一致」とする（決まり 2.8。例外にしない）。初期管理者の設定では、作らずに WARN（決まり 1.3）。
- **ダミーの照合**: 起動時に、設定した cost でダミーのハッシュを1つ作る。利用者がいないとき・72 バイトを超えたときに使う。
- **ロック中**: 確定回答 Q1 により、照合はロックの状態を読む前に行う。ロック中の場合も照合は行うが結果は使わず失敗とする。決まり 2.5・3.3 の「ダミーの照合」は、照合を1回行って時間をそろえ、結果を判断に使わないことで満たす。
- **出さない**: 入力のパスワード・ハッシュを、ログ・監査ログ・トレースの属性・エラー応答・出来事に入れない（5章）。

## 3. API・Cookie・CSRF（NFR5.2〜NFR5.5）

| API | メソッドとパス | 認証 | Origin の確認 |
|---|---|---|---|
| ログイン | `POST /api/auth/login` | 求めない | しない（Cookie を使わないため） |
| トークンの更新 | `POST /api/auth/session/refresh` | リフレッシュトークンの Cookie | する |
| ログアウト | `POST /api/auth/session/logout` | リフレッシュトークンの Cookie | する |

**Cookie**:

| 項目 | 値 |
|---|---|
| 名前 | `mastersmith_refresh` |
| 値 | 256 ビットの暗号学的な乱数（SecureRandom）を URL で使える Base64 にしたもの。内部DBには SHA-256 のハッシュだけを保存する（NFR5.2） |
| 属性 | `HttpOnly`、`Secure`、`SameSite=Strict`、`Path=/api/auth/session`、`Max-Age`＝リフレッシュトークンの有効期限 |
| 削除 | 同じ名前・同じ `Path` で `Max-Age=0`（NFR5.3） |

`Path=/api/auth/session` により、Cookie は更新とログアウトの API にだけ送られ、ログインの API やほかの API には送られない（NFR5.3）。

**Origin の確認（NFR5.4）**: 更新とログアウトの API の前に、要求の `Origin` ヘッダーが自分の配信元と一致することを確かめる。自分の配信元は、U1 のエラー応答のベースURLと同じ決め方（設定の固定値、無ければ要求のスキーム・Host・ポート。転送元のヘッダーは信頼の設定があるときだけ）で決める。一致しない、または `Origin` が無いときは 403 で拒否する。code は `ORIGIN_NOT_ALLOWED` とし、日英の説明つきの問題の種類を U2 が定義する（決まり 9.1 の3つに加える。承認済みの `rules.md` との違いは 8章）。開発時は、画面の開発サーバーのプロキシが元の Host を保つ設定のため、`Origin`（`http://localhost:5173` など）と自分の配信元が一致する（U1 の `functional-spec.md` 5章）。

**localhost（NFR5.5）**: `Secure` の Cookie はブラウザが `http://localhost` にも送るため、開発・CI・E2E は `http://localhost` で行う。HTTPS は配備先が決まったときに扱う。

## 4. アクセストークン（NFR3.2〜NFR3.4）

- **発行**: HS256 で署名した JWT。載せる項目は利用者ID（`sub`）・発行時刻（`iat`）・有効期限（`exp`）だけ（決まり 4.1）。管理者フラグは載せない（要求ごとに DB から読む。決まり 4.5）。
- **検証**: Spring Security の OAuth2 Resource Server で検証する。検証の仕組みは HS256 だけを受け付けるように作り、`alg: none`・別の方式・署名の不一致は拒否する。
- **有効期限の境界**: 検証の時刻のずれの許容（既定 60 秒）は 0 にし、注入できる時計を使う。発行から5分ちょうどで無効（決まり 4.2）。
- **取り出し**: `Authorization: Bearer` のヘッダーだけから取り出す。URL の問い合わせの部分やフォームからは取り出さない。
- **署名鍵（NFR3.3）**: 環境変数で Base64 の文字列として受け取り、復元した長さが 32 バイト（256 ビット）未満、または無いときは起動を止める。鍵は設定ファイルに書かない。見本の `.env.example` には名前だけを置き、値は空にする。
- **鍵の交換（NFR3.4）**: 設定を変えて再起動する。発行済みのアクセストークンは 401 になり、画面はトークンの更新で取り直す。
- **U1 の連鎖への足し方**: U2 は、U1 のアクセスの決まりの差し込み口（U1 の `nfr-design/security-design.md` 3章）に、ログインと `/api/auth/session/**` を認証なしとする決まりと、トークンの検証（OAuth2 Resource Server）を足す部品を置く。検証の結果から利用者を DB で読み、AuthenticatedUser を作る変換を置く。利用者がいなければ 401。
- **401 の応答**: トークンが無い・無効のときの 401 / `AUTHENTICATION_REQUIRED` は、U1 の共通の組み立ての仕組みで ErrorResponse の形にする（U1 の決まり 5.1）。理由（TOKEN_MISSING などの区分）は DEBUG でアプリのログにだけ出す。

## 5. 秘密情報を出さない仕組み（NFR3.1、NFR3.5、NFR3.6）

| 出力先 | 仕組み |
|---|---|
| アプリのログ | パスワード・トークン・鍵をメッセージにもキーと値にも入れない。ロックのログは利用者IDだけ（メールアドレスも出さない）。初期管理者の作成のログはメールアドレスまで |
| メソッドの呼び出しの追跡（TRACE） | 秘密情報を持つ型（ログインの要求、ログインと更新の応答、初期管理者の設定、リフレッシュトークンの値を持つ型）は、文字列化でその項目を伏せ字（`***`）にする。`record` の既定の文字列化を上書きする |
| 出来事（U4 へ） | 出来事の項目は決まり 7.1 のもの（日時・種類・メールアドレス・利用者ID・理由・接続元IP・User-Agent・トレースID）だけで、秘密情報の項目を持たない（決まり 7.2） |
| エラー応答 | 失敗の理由も含めず、同じ応答にする（6章） |
| トレースの属性・指標 | U1 の設計のとおり（URL の問い合わせの部分を除く、例外のメッセージを載せない、タグに利用者の情報を使わない）。U2 はトークンを URL に載せない |
| 画面（NFR5.1） | アクセストークンはメモリ（画面の部品の外にある変数）にだけ持ち、localStorage・sessionStorage・Cookie に置かない。画面を閉じれば消える |

テスト: TRACE を有効にしてログイン・更新・起動（初期管理者の作成）を行い、パスワード・トークン・鍵の値がログに出ないこと。U1 が用意するログの捕まえ方の補助を使う。

## 6. 登録の有無・ロックの状態の推測を防ぐ（NFR4.1〜NFR4.3）

確定回答 Q1 による、どの失敗の経路でも同じ手順:

1. 利用者の検索（1回）
2. 照合（1回。利用者がいない・72 バイト超えはダミーのハッシュ、ロック中は結果を使わない）
3. 1回のトランザクションで、ロックの状態の排他つきの読み取り（1回）と書き込み（1回）。存在しないメールアドレスはダミーの記録の行、ロック中は値を変えない書き込み、誤りは失敗回数の更新

- 応答は理由によらず 401 / `AUTHENTICATION_FAILED` で、本文も同じ（NFR4.1）。
- 回数がそろっていることを、テストで SQL の回数と照合の回数を数えて確かめる（NFR4.2。応答時間は比べない）。
- 画面の失敗の文言は1種類（NFR4.3）。

## 7. 脅威の分析（STRIDE、U2 の範囲）

| 脅威 | 例 | 対策 | 残る危険 |
|---|---|---|---|
| なりすまし | パスワードの総当たり | ロック（5回で30分）、bcrypt | ロックの悪用（NFR4.4 で受け入れる） |
| なりすまし | アクセストークンの偽造 | HS256 の署名、鍵は 256 ビット以上の乱数、方式の固定 | 鍵が漏れた場合は交換して再起動 |
| なりすまし | 盗んだリフレッシュトークンの再利用 | 1回使えば無効、HttpOnly、SameSite=Strict、Path の限定 | 再利用を検知しても他のトークンは無効にしない（NFR5.6 で受け入れる） |
| 改ざん | 署名方式のすり替え（`alg: none`） | 検証は HS256 だけ | なし |
| 否認 | ログイン・ログアウトを否定する | 出来事を U4 が監査ログに記録（トレースID・接続元IP つき） | 監査ログの書き込みの失敗（U4 がアプリのログに ERROR） |
| 情報漏えい | 応答・DB の手順の違いから登録の有無を推測 | 6章 | 応答時間のわずかな揺れ（照合の回数はそろえる） |
| 情報漏えい | ログ・トレースへの秘密情報の出力 | 5章 | 後の変更での伏せ忘れ（テストで防ぐ） |
| 情報漏えい | ブラウザの保存領域からのトークンの盗難 | アクセストークンはメモリだけ、リフレッシュトークンは HttpOnly | 画面へのスクリプトの注入（U1 の CSP で防ぐ） |
| サービス妨害 | 重いハッシュの計算を大量に起こさせる | 受け入れる（NFR4.4）。U1 の本文の大きさの上限 | 入口での回数制限は配備先で必要なら入れる |
| 権限昇格 | 管理者フラグの偽装 | フラグはトークンに載せず、要求ごとに DB から読む | なし |
| CSRF | 別のサイトから更新・ログアウトを起こさせる | SameSite=Strict、Origin の確認、POST だけ | なし |

## 8. 承認済みの Functional Design との違い（Code Generation で揃える）

本書と `reliability-design.md` は、承認済みの U2 の Functional Design と次の2点で異なる。どちらも確定回答（Q1）と要件（NFR5.4）から来る設計上の変更で、振る舞いの外から見える結果（応答・読み書きの回数・判定の結果）は変えない。Functional Design の文書そのものはこの段階では書き換えず、Code Generation の計画の確認（Plan Approval）の時点で、下の対応を計画に明記して依頼者の承認を得る。Functional Design のやり直し（`/aidlc --stage functional-design`）を選ぶ場合は、その中で同じ内容を反映する。

| 違い | Functional Design の記述 | 本設計 | 変わらないこと |
|---|---|---|---|
| ログインの手順の順番 | `functional-spec.md` WF2: 手順4でロックの状態を排他つきで読み、ロック中ならダミーの照合、手順5で本物の照合 | 手順を「利用者の検索 → 照合 → 1回のトランザクションでロックの状態を排他つきで読み、判定し、書き込む」とする（確定回答 Q1）。ロック中は照合の結果を使わない | 決まり 3.8（読み取りから更新までを同じ利用者について1つずつ）は、判定を排他の後の最新の値で行うことで満たす。照合は判定の材料（一致したか）を先に用意するだけで、状態の読み取り・判定・書き込みは1つのトランザクションの中にある。決まり 2.7 の回数（検索1・照合1・排他つきの読み取り1・書き込み1）も同じ |
| 問題の種類 | `rules.md` BR9.1: U2 の問題の種類は `AUTHENTICATION_FAILED`・`AUTHENTICATION_REQUIRED`・`REFRESH_FAILED` の3つ | NFR5.4 の 403 のために `ORIGIN_NOT_ALLOWED`（403）を加え、4つとする | U1 の決まり 5.14（使う code すべてに日英の説明を定義）と、U1 の起動時の重複の検査はそのまま当てる |

## 9. 確かめるテスト

| 対象 | テスト |
|---|---|
| パスワード | 保存が bcrypt の形式。11文字・12文字・72 バイト・73 バイトの境界（初期管理者とログイン） |
| トークン | 期限の直前は有効・ちょうどで無効、署名の改ざん、`alg: none`、別の方式、鍵が無い・短いと起動しない |
| リフレッシュトークン | 保存がハッシュ、使用済み・期限切れ・存在しないで 401、同時の2回の更新で1つだけ成功、ログアウト後の拒否 |
| Cookie | 発行と削除で名前と Path が同じ、属性がそろう |
| Origin | 一致は受け付け、不一致・無しは 403 / `ORIGIN_NOT_ALLOWED` |
| 推測の防止 | 3つの失敗の経路で応答・SQL の回数・照合の回数が同じ |
| 秘密情報 | TRACE を有効にしてもログに出ない、出来事・エラー応答に無い |
| 画面 | アクセストークンが localStorage・sessionStorage に無い、ログアウトで破棄される |
