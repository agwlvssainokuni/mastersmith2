# Reliability Design — U2 認証（u2-authentication）

U2 の信頼性と品質の要件（`reliability-requirements.md` の NFR9.1〜NFR9.5、NFR10.1、NFR6.1〜NFR6.3、NFR7.1、NFR8.1）を満たす設計。技術は U2 の `tech-stack-decisions.md`、処理の流れは U2 の `functional-spec.md`、決まりは U2 の `rules.md` に従う。性能・拡張性・安全・観測性の要件（`performance-requirements.md`・`scalability-requirements.md`・`security-requirements.md`・`observability-requirements.md`）は各設計書で扱う。設計の方針の確定回答は `nfr-design-questions.md`（Q1）にある。`contract-summary.md` は、本ワークフローで Contract Design を行わないため無い。

## 1. 同時の試みでも取りこぼさない（NFR9.1）

確定回答 Q1 による、ログインの手順:

```text
user    = users.findByEmail(email)                 -- トランザクションの外
matched = userAccount.verify(user, password)       -- 照合。排他を持たない
tx {
  state = attempts.lockForUpdate(user or dummy)    -- 行の排他つきの読み取り
  decide(state, matched, clock.now())              -- ロック中・解除・加算・リセット
  attempts.save(state)                             -- 書き込み1回
  if success: issue tokens
}
```

- この順番は、承認済みの `functional-spec.md` WF2（排他つきの読み取りの後に照合）と異なる。違いと、決まり 3.8・2.7 を満たし続ける理由は `security-design.md` 8章にまとめ、Code Generation の計画の確認で揃える。
- 失敗回数の加算とロックの判定は、排他を取った後の値で行う。同じ利用者の失敗が同時に来ても、1つずつ加算され、しきい値ちょうどでロックされる。
- 照合と判定の間に、別の試みがロックさせた場合: 判定は排他の後の最新の値で行うため、照合が一致していてもロック中として拒否する（決まり 3.3）。
- 排他の待ち時間の上限は 3 秒とする。超えたら 500 とする（利用者1人の試みがそれほど重なることは、想定の規模では起きない）。
- テスト: 同じ利用者で同時に 5 回の失敗を起こし、ロックされ、失敗回数が 5 になることを確かめる（しきい値の境界も）。

## 2. リフレッシュトークンの同時の更新（NFR9.2）

- 無効化は「その行が無効でないこと」を条件とする更新の問い合わせ1回で行い、更新した行の数が 1 のときだけ成功とする。0 なら、同時の更新に負けたか既に無効なので、401 / `REFRESH_FAILED` と Cookie の削除（決まり 5.5・5.6）。
- 無効化と新しい行の保存は同じトランザクションで行う。途中で失敗したら両方とも取り消され、古いトークンは有効のまま残る（利用者は再度更新できる）。
- テスト: 同じトークンで同時に2回の更新を行い、1つだけ成功することを確かめる。

## 3. 監査の記録の失敗を持ち込まない（NFR10.1）

- U2 は出来事（LOGIN_SUCCEEDED・LOGIN_FAILED・LOGGED_OUT）をアプリの中に知らせるだけで、受け取り側（U4）を知らない（決まり 7.3、ADR-004）。
- 出来事は、U2 のトランザクションの中で知らせる。U4 は、U2 の更新が確定した後に、同じスレッド・別のトランザクションで記録する（U4 の決まり 1.3）。U4 の失敗は U4 の中で受け止める。
- ログインの失敗も、失敗回数の更新を伴うため、確定の後に記録される。U2 の応答は、U4 の結果によらず同じ。
- テスト: 受け取り側で例外を起こす出来事の受け取りを置き、ログイン・更新・ログアウトの応答が変わらないことを確かめる。

## 4. 起動と設定（NFR6.1〜NFR6.3）

| 場合 | 振る舞い |
|---|---|
| 署名鍵が無い・32 バイト未満 | 起動を止める。理由（鍵の名前と必要な長さ）をログに出す。鍵の値は出さない |
| 初期管理者の設定が無い・不正 | 作らずに WARN（理由と直し方）。起動は続ける |
| 初期管理者が既にいる | 何もしない。何度再起動しても重複しない（メールアドレスの一意の制約でも守る） |
| そのほかの設定が無い | 既定値で動く（ロックのしきい値 5 回、ロックの時間 30 分、アクセストークン 5 分、リフレッシュトークン 24 時間、cost 12、削除までの日数 7 日） |
| 設定の値が範囲外（0 以下など） | 起動を止め、どの設定が正しくないかを示す（設定の検証） |

- 初期管理者の作成は、スキーマの変更の後、要求の受け付けの前に、起動時の処理として行う（ADR-006）。
- 設定は1つの設定のまとまり（`mastersmith.auth.*`）で受け取り、起動時に検証する。

## 5. 時刻と品質（NFR9.3〜NFR9.5、NFR7.1、NFR8.1）

| 要件 | 設計 |
|---|---|
| NFR9.4 時刻 | 有効期限とロックの解除は、注入できる時計（`Clock`）から現在時刻を得る。トークンの検証の時刻のずれの許容は 0 |
| NFR9.5 性質ベースのテスト | ロックの判定（失敗回数・しきい値・解除時刻から結果を決める関数）と、有効期限の判定を、DB を使わない純粋な関数にし、jqwik で確かめる |
| NFR9.3 必須のテスト | チームの進め方の認証のテストの一覧を、`security-design.md` 8章と本書のテストで漏れなく入れる |
| NFR7.1 多言語 | ログイン画面の文言を日英で用意し、鍵がそろっていることを U1 のテストの仕組みで確かめる |
| NFR8.1 アクセシビリティ | ログイン画面の部品ごとに vitest-axe の検査を1件 |

## 6. 故障の場合

| 故障 | 振る舞い |
|---|---|
| 内部DBが使えない | ログイン・更新・認証つきの API は 500（U1 の設計の時間の上限で失敗する）。画面はログイン画面の一般的なエラーを表示する |
| 更新の API が失敗（通信エラーなど） | 画面はログイン状態を消してログイン画面へ（決まり 8.5） |
| ログアウトの API が失敗 | 画面は結果によらずトークンを破棄してログイン画面へ（決まり 8.6）。サーバー側のリフレッシュトークンは期限まで残る |
| 削除の定期実行が失敗 | ERROR を出し、翌日に再び行う |
