# Security Requirements — U2 認証（u2-authentication）

U2（ログイン・トークン・ログアウト・ロック・初期管理者）の安全の要件。判断の元は `nfr-requirements-questions.md` の確定回答（Q1〜Q5）、U2 の Functional Design の決まり、要件定義書の NFR2〜NFR5 である。要件の ID は、要件定義書の NFR の ID に枝番を付けたものである。

## 1. パスワード（NFR2・NFR3）

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR2.1 | パスワードは bcrypt でハッシュにして保存する。計算の重さ（cost）は設定で変えられ、既定は 12 とする。1回の照合が、開発者の PC 上のコンテナで 100〜500 ミリ秒に収まる値を選ぶ | 照合の時間を測る。保存された値が bcrypt の形式であることをテストで確かめる | Q1、NFR1、U2 の決まり 1.5 |
| NFR2.2 | パスワードは 12 文字以上、かつ UTF-8 で 72 バイト以内とする。初期管理者の設定がこれを外れたら、作らずに理由と直し方を警告する（U2 の決まり 1.3。72 バイトの条件を Functional Design に書き足した） | テスト（11文字、12文字、72 バイト、73 バイト） | NFR2、Q5 |
| NFR2.3 | ログインで入力されたパスワードが 72 バイトを超える場合は、例外にせず、パスワード誤りと同じ失敗（401 / AUTHENTICATION_FAILED）とする。このときもダミーの照合を行い、応答時間をそろえる | テスト | Q5、U2 の決まり 2.4・2.5・2.8 |
| NFR3.1 | パスワード（平文・ハッシュ値とも）を、ログ・監査ログ・トレースの属性・エラー応答・出来事に含めない | テストで出力に含まれないことを確かめる | NFR3 |

## 2. アクセストークン（NFR3・NFR5）

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR3.2 | アクセストークンは HS256 で署名する。検証は HS256 だけを受け付け、`alg: none` や別の方式のトークンは拒否する | テスト（改ざん、`alg: none`、別の方式） | Q2、FR4.4、U2 の決まり 4.3 |
| NFR3.3 | 署名鍵は 256 ビット以上の乱数とし、環境変数で渡す。ソースコード・設定ファイルに書かない。鍵が無い、または 256 ビット未満のときは、起動を止める（トークンを安全に発行できないため） | 起動のテスト。Gitleaks で鍵の直書きを検出する | Q2、NFR3、project.md Forbidden |
| NFR3.4 | 署名鍵を替えるときは、設定を変えて再起動する。発行済みのアクセストークンは検証に失敗して 401 になり、画面はトークンの更新で取り直す（リフレッシュトークンは鍵に依存しないため、ログインし直しは要らない） | 鍵を替えた再起動の確認 | Q2 |
| NFR3.5 | アクセストークン・リフレッシュトークン・署名鍵を、ログ・監査ログ・トレースの属性・エラー応答・出来事に含めない | テストで出力に含まれないことを確かめる | NFR3 |
| NFR5.1 | 画面側では、アクセストークンをメモリ上にだけ持ち、localStorage・sessionStorage に置かない | 画面のテスト | NFR5、U2 の決まり 8.3 |

## 3. リフレッシュトークンと CSRF（NFR5）

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR5.2 | リフレッシュトークンは 256 ビット以上の暗号学的な乱数とし、内部DBには SHA-256 のハッシュだけを保存する | テスト | U2 の決まり 5.1 |
| NFR5.3 | リフレッシュトークンの Cookie は HttpOnly・Secure・SameSite=Strict とし、送り先（path）をトークンの更新とログアウトの API に限る。Cookie を消す指示（ログアウト・更新の失敗）は、発行時と同じ名前・同じ Path で、Max-Age=0 とする | 応答のヘッダーのテスト（発行と削除の Path が同じこと） | U2 の決まり 5.2・5.5・6.1、レビュー指摘 R-04 |
| NFR5.4 | トークンの更新とログアウトの API は POST とする（パスは Contract Design で決める）。この2つの API は、要求の Origin ヘッダーが自分の配信元と一致するときだけ受け付ける。一致しない、または Origin ヘッダーが無いときは 403 で拒否する。自分の配信元は、エラー応答のベースURLと同じ決め方（設定の固定値、無ければ要求の Host）で決める | テスト（一致・不一致・無し） | Q4、U1 の決まり 5.10、レビュー指摘 R-02 |
| NFR5.5 | 開発・CI・E2E は `http://localhost` で行う（Secure の Cookie が localhost では送られるため）。HTTPS は配備先が決まったときに扱う | E2E の設定 | U1 Q7 |

## 4. 登録の有無・ロックの状態の推測（NFR4）

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR4.1 | ログインの失敗は、理由（存在しないメールアドレス・パスワード誤り・ロック中・72 バイト超え）によらず、状態コード・code・本文を同じにする | テスト | FR4.5、U2 の決まり 2.4 |
| NFR4.2 | 失敗の経路ごとに、パスワードの照合（ダミーを含む）の回数と、内部DBの読み書きの種類と回数をそろえる | テストで照合と SQL の回数を確かめる（応答時間そのものは比べない） | U2 の決まり 2.5・2.7 |
| NFR4.3 | 画面のログイン失敗の表示は、理由によらず1種類の文言とする | 画面のテスト | FR2.4 |

## 5. 受け入れる危険

| ID | 内容 | 判断 | 出典 |
|---|---|---|---|
| NFR4.4 | 他人のメールアドレスで5回失敗させて、その利用者をロックさせる妨害（ロックの悪用）と、大量のログイン試行への追加の対策（接続元ごとの回数制限など）は行わない。利用者 50 名の社内向けであり、ロックは 30 分で自動的に解ける | 受け入れる。監査ログ（ログイン失敗の記録）で事後に確かめる | Q3（OQ3） |
| NFR5.6 | 盗まれたリフレッシュトークンの再利用を検知しても、その利用者の他のトークンは無効にしない | 受け入れる（Functional Design の Q6） | U2 の決まり 5.5 |

## 6. 脅威の考慮（U2 の範囲）

脅威の分析（STRIDE）の詳細は NFR Design で行う（OQ4）。

| 脅威 | 例 | 対応する要件 |
|---|---|---|
| なりすまし | パスワードの総当たり、トークンの偽造 | ロック（FR7）、NFR2.1、NFR3.2、NFR3.3 |
| 改ざん | トークンの署名方式のすり替え | NFR3.2 |
| 否認 | ログイン・ログアウトの記録が無い | 出来事の通知と監査ログ（U2 の決まり 7.1、U4） |
| 情報漏えい | 応答や時間からの登録の有無の推測、ログへの秘密情報の出力 | NFR4.1〜NFR4.3、NFR3.1、NFR3.5 |
| サービス妨害 | ロックの悪用、重いハッシュの計算を大量に起こさせる | NFR4.4（受け入れる） |
| 権限昇格 | 管理者フラグの偽装 | 管理者フラグはトークンに載せず DB から読む（U2 の決まり 4.1・4.5） |
| CSRF | 別のサイトからトークンの更新・ログアウトを起こさせる | NFR5.3、NFR5.4 |
