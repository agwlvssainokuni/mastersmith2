# Performance Requirements — U4 監査ログ（u4-audit-log）

U4 の性能の要件。監査イベントの記録は要求と同じスレッドで行うため、その時間はログイン・ログアウト・アクセス拒否の応答時間に含まれる。測定の環境は、当面の配備先である開発者の PC 上のコンテナとする。

| ID | 要件 | 測り方 | 出典 |
|---|---|---|---|
| NFR1.1 | 監査イベント1件の書き込み（別のトランザクションの開始から確定まで）は、同時に 10 件の要求が来る状態で、95% が 50 ミリ秒以内とする | 書き込みの時間を測る（負荷の試験の中で） | Q2、NFR1 |
| NFR1.2 | 監査イベントの書き込みは、ログインとトークンの更新の API の目標（95% が1秒以内。U2 の NFR1.1・1.2）の内側に収まる。あわせて、アクセス拒否の経路（フィルターの段階でトランザクションの外から、応答の前に同じスレッドで記録する）では、U3 の NFR1.3（拒否の記録で 401／403 の応答を 100 ミリ秒以上遅らせない）の内側に収まる。この経路が時間の余裕の最も少ない経路であり、負荷の試験で必ず測る | U2 の負荷の試験と、管理者でない利用者の 403 を同時 10 件で繰り返す試験で、監査ログを有効にした状態で測る | NFR1、U3 の NFR1.3、レビュー指摘 R-01 |
| NFR1.3 | 監査イベントの書き込みは、1件につき内部DBへの追記1回だけとし、ほかの表の読み取りを伴わない | 発行する SQL の回数を確かめる | U4 の決まり 1.1 |

NFR1.1 の値は設計上の目標であり、測定の結果に応じて NFR Design で見直す。特に、組み込みの H2 は書き込みを1つずつ進めるため、元の操作の確定と監査イベントの書き込み（別のトランザクション）が同時の要求どうしで待ち合う危険がある。NFR Design の負荷の試験では、この待ち合いによる遅れを名指しで測る（レビュー指摘 R-02）。
