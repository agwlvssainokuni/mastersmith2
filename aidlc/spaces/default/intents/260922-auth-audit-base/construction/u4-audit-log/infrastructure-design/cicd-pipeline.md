# CI/CD Pipeline — U4 監査ログ（u4-audit-log）

U4 は U1 の検査・ビルド・配備の流れ（U1 の `infrastructure-design/cicd-pipeline.md`: `./gradlew verify`、pre-commit、GitHub Actions、手元のコンテナへの配備）をそのまま使い、流れの形は変えない。本書は、U4 がその流れに足すテストと配備の確認だけを書く。入力は U4 の NFR Design（`reliability-design.md` 4章の必須のテスト、`security-design.md`、`performance-design.md`、`observability-design.md`、`scalability-design.md`、`logical-components.md`）、Domain Design の `components.md`、U4 の `functional-spec.md` である。`contract-summary.md` は、本ワークフローで Contract Design を行わないため無い。

## 1. `./gradlew verify` に足すもの

| 段（U1 の順） | U4 が足すもの |
|---|---|
| 5 単体テスト | 切り詰め（メールアドレス 254・User-Agent 512・要求のパス 512、コードポイント単位、サロゲートペアを分断しない）の性質ベースのテスト（jqwik）、監査イベントの組み立て、構造の検査（ArchUnit: 監査の保存の部品に更新・削除の操作が無い、更新の問い合わせが無い） |
| 6 結合テスト | 対象の出来事ごと（LOGIN_SUCCEEDED・LOGIN_FAILED・LOGGED_OUT・ACCESS_DENIED）の必須の項目、存在しないメールアドレスでのログインの失敗の記録、要求のパス（ACCESS_DENIED だけ、問い合わせなし）、2つの受け取りの経路（確定の後・その場）、元の操作の取り消しで記録しないこと、書き込みの失敗（DB の例外・接続を借りる失敗）で元の操作の応答が変わらず ERROR が1回出ること、記録とログに秘密情報が無いこと、トレースIDがアプリのログと一致すること、1件の記録の SQL が挿入1回だけであること、監査イベントが内部DBに記録されアプリのログで代用されていないこと、書き込みが 200 ミリ秒を超えたときに遅れの WARN が1回出ること（注入できる時計で時間を進めて確かめる） |
| 8 安全の検査 | 追加なし（U1 の検査が U4 のコードも対象にする） |

チームの進め方の必須の監査ログのテスト（対象のイベントごとの必須の項目、存在しないユーザーIDでのログイン失敗も記録、書き込みに失敗しても操作が失敗しない）を、上の結合テストで入れる。

- 書き込みの失敗は、テスト用に失敗させる保存の部品に差し替えて起こす（本物の DB を壊さない）。
- 時刻は注入できる時計を使い、実時間に頼らない。

## 2. CI（GitHub Actions）

追加の設定は無い。U4 のテストは組み込みの H2 で動き、秘密情報を使わない。

## 3. 配備と戻し方

| 手順 | U4 に固有の点 |
|---|---|
| 配備の確認（スモークテスト） | U1〜U3 の確認に加えて、初期管理者のログインとログアウトで監査イベントが2件（LOGIN_SUCCEEDED・LOGGED_OUT）記録されること。確認は、アプリを止めてボリュームを複写し、複写したファイルを読み取りで開いて行う |
| 版を替える前 | U1 の手順でボリュームを複写する（監査ログを守る） |
| 戻し方 | U1 のとおり直前の版の WAR で作り直す。監査イベントの表のスキーマの変更は前進のみ・後方互換で、1つ前の版のアプリが今のスキーマ（要求のパスの項目を含む）で動く |
| してはいけない操作 | ボリュームを消す操作（`docker compose down -v` など）を、バックアップの前に行わない（README の注意） |

## 4. 段と関門の対応

U1 の `cicd-pipeline.md` 6章のとおり。U4 のテストは、統合の前の `./gradlew verify` と CI の関門に含まれる。
