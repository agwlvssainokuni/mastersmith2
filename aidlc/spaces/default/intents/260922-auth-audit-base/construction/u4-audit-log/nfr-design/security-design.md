# Security Design — U4 監査ログ（u4-audit-log）

U4 の安全の要件（`security-requirements.md` の NFR3.1〜NFR3.7）を満たす設計。処理の流れは U4 の `functional-spec.md`（WF1〜WF3）、決まりは U4 の `rules.md`（BR1〜BR4）、技術は U4 の `tech-stack-decisions.md` に従う。性能・拡張性・信頼性・観測性の要件（`performance-requirements.md`・`scalability-requirements.md`・`reliability-requirements.md`・`observability-requirements.md`）は各設計書で扱う。設計の方針の確認は `nfr-design-questions.md` にある。`contract-summary.md` は、本ワークフローで Contract Design を行わないため無い。出来事の形は、U2・U3 の設計（U2 の `nfr-design/observability-design.md` 2章、U3 の `nfr-design/security-design.md` 4章）に従う。

## 1. 秘密情報を持ち込まない（NFR3.1）

- 監査イベントの項目は、発生の日時・種類・結果・入力されたメールアドレス・失敗の理由・接続元IP・User-Agent・トレースIDだけとし（U4 の `entities.md` の AuditEvent の項目）、パスワード・トークン・ハッシュ値・Authorization ヘッダーの項目を持たない。受け取る出来事の型にも、これらの項目は無い（U2 の決まり 7.2、U3 の決まり 3.4）。
- 書き込みの失敗のときに ERROR で出す内容は、記録しようとした監査イベントの項目だけで、同じく秘密情報を含まない。例外は型の名前とスタックトレースを出し、例外の中の SQL の値の並びは出さない（JDBC の例外のメッセージには挿入しようとした値が入ることがあるため、メッセージは U4 が決めた固定の文にする）。
- テスト: ログインと 403 の記録と、書き込みの失敗のときの ERROR のログに、パスワード・トークンの値が含まれないこと。

## 2. 変更・削除させない（NFR3.2、NFR3.3、NFR3.6）

| 層 | 設計 |
|---|---|
| DB アクセスの部品 | 監査イベントの保存の部品は、追記（保存）と読み取りだけを持つ。Spring Data の既定の部品（保存・削除をまとめて持つもの）は継承せず、最小の部品から必要な操作だけを宣言する |
| 業務処理 | 更新・削除の処理を持たない |
| API | 監査ログを見る API・変える API を本Intentでは作らない（NFR3.5） |
| 構造の検査 | ArchUnit で、監査の保存の部品に `delete`・`update` で始まる操作が無いこと、監査イベントの表を変える SQL（更新の問い合わせ）が無いことを確かめる |
| エンティティ | 監査イベントの項目は作ったときに決め、あとから変える手段（設定の操作）を持たない。JPA の設定で、この表の行を更新しない指定にする |
| ファイル | 内部DBのファイルは、コンテナの実行者だけが読み書きできるボリュームに置く（U1 の `nfr-design/security-design.md` 4章、Infrastructure Design で決める） |

受け入れる危険（NFR3.6）: OS の権限を持つ者によるファイルの直接の書き換えは検知できない。ハッシュの連鎖などは行わない（U4 の NFR Requirements の Q1）。

## 3. 攻撃者が決められる値（NFR3.4、NFR3.5）

- 入力されたメールアドレスは 254 文字、User-Agent は 512 文字（コードポイント単位）で切り詰める。切る位置がサロゲートペアの途中なら、その文字の手前で切る（BR2.1）。
- 値は加工せずに保存する（BR2.2）。改行・制御文字もそのまま入る。
- アプリのログに出すときは、U1 の仕組みで JSON の値として出るため、改行で記録を偽装できない（U1 の NFR3.11）。
- 監査ログを見る画面・API を後続Intentで作るときは、管理者のみ（U3 の `/api/admin` の下）とし、表示の際に値を無害化する。この要件を後続Intentへ引き継ぐ（NFR3.5）。
- SQL への値の渡し方は、JPA の値の結び付け（パラメーター）だけとし、文字列の連結で SQL を作らない。

## 4. 記録の欠落（NFR3.7）

元の操作の確定の後、監査イベントを書く前にアプリが止まった場合、その1件は失われる。受け入れる危険とする（U4 の決まり 3.1）。止まる前の最後の要求の記録が欠ける可能性は、アプリの停止の手順（U1 の穏やかな停止: 処理中の要求を終えてから止める）で小さくする。

## 5. 脅威の分析（STRIDE、U4 の範囲）

| 脅威 | 例 | 対策 | 残る危険 |
|---|---|---|---|
| 改ざん | アプリの機能で監査イベントを書き換える・消す | 2章（変更・削除の処理を持たない、構造の検査） | ファイルの直接の書き換え（NFR3.6 で受け入れる） |
| 改ざん | 改行や制御文字で偽の記録を作る | 監査ログは DB の行で1件1行。アプリのログは JSON の値 | なし |
| 否認 | ログイン・拒否を否定する | 出来事ごとの記録、トレースIDでアプリのログと結び付く | 書き込みの失敗・停止による欠落（ERROR のログに内容が残る。停止時は失われる） |
| 情報漏えい | 監査ログからの秘密情報の漏えい | 1章 | 監査ログにはメールアドレスと接続元IP が残る（見る機能は後続Intentで管理者のみ） |
| サービス妨害 | 大量の失敗で記録を増やす | 受け入れる（社内向けの規模、U2 の NFR4.4） | ボリュームの消費（`scalability-design.md` の見積もりで監視） |
| SQL の注入 | 入力されたメールアドレス・User-Agent に SQL を入れる | 値の結び付けだけで SQL を作る | なし |
