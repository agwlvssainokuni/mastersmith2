U1 の NFR 要件（`nfr-requirements/` の各文書）を満たす設計の方針のうち、これまでの段階で決まっていない点を確認します。

決定済みの事項（再確認はしません）: 技術は `tech-stack-decisions.md` のとおり（Java 25、Spring Boot 4 系、Spring MVC、Spring Data JPA、H2、Flyway、HikariCP、logstash-logback-encoder、Micrometer Tracing＋OpenTelemetry、Actuator、React・Vite・make-you-chic-ui）。アプリは当面1台で動かす（ADR-008）。当面の配備先は開発者の PC 上のコンテナで、HTTPS は配備先が決まるまで扱わない。U2 は Spring Security の OAuth2 Resource Server で JWT を検証し、U3 は Spring Security のアクセス制御の設定でパスごとの利用条件を決める。

### Q1. セキュリティ関係のヘッダー（CSP など、NFR3.10）は、どの仕組みで付けますか？

U2・U3 は Spring Security を使う予定ですが、U1 の段階ではまだ認証がありません。ヘッダーをどこで付けるかで、U2・U3 が U1 の設定を書き換える必要があるかが変わります。

- A. U1 で Spring Security を組み込み、すべての要求を許可するフィルターの連鎖を1つ用意する。ヘッダーは Spring Security のヘッダーの設定で付ける。U2・U3 は、この連鎖に認証とアクセスの決まりを足す（U1 の設定のヘッダーの部分は変えない）
- B. U1 では Spring Security を入れず、自前のサーブレットのフィルターでヘッダーを付ける。U2 で Spring Security を入れるときに、ヘッダーの付け方をどちらに寄せるかを決め直す
- X. Other (please specify)

[Answer]: A. U1 で Spring Security を組み込み、すべての要求を許可するフィルターの連鎖を1つ用意する。ヘッダーは Spring Security のヘッダーの設定で付ける。U2・U3 は、この連鎖に認証とアクセスの決まりを足す（U1 の設定のヘッダーの部分は変えない）

### Q2. アプリのログの書き出し方は、どれにしますか？（NFR1.6「ログの出力で要求を待たせない」）

ログは標準出力に出し、コンテナの実行環境が受け取ります（NFR1.10）。書き出しを同期にするか非同期にするかで、「ログを失わないこと」と「要求を待たせないこと」のどちらを優先するかが決まります。監査の記録はログではなく内部DBに残すため（チームの進め方）、アプリのログの取りこぼしは監査の欠落にはなりません。

- A. 同期で標準出力へ書く。ログは失わない。標準出力の受け手が詰まったときは、要求も待つ
- B. 非同期で書く。待ち行列が残り少なくなったら INFO 以下を捨て、WARN・ERROR は待ってでも残す。通常は要求を待たせず、エラーの記録は失わない
- C. 非同期で書き、待ち行列があふれたらレベルによらず捨てる。要求を決して待たせないが、負荷が高いときは ERROR も失うことがある
- X. Other (please specify)

[Answer]: A. 同期で標準出力へ書く。ログは失わない。標準出力の受け手が詰まったときは、要求も待つ

### Q3. 外部エクスポートを有効にしたとき、指標（要求の件数・5xx の件数など）も送りますか？

U1 の要件の間に食い違いがあります。NFR3.4 は「外部エクスポートで送るのはトレースとログだけ」、NFR10.9 は「エラーの割合の指標は、外部エクスポートを有効にしたときに送る」としています。U2〜U4 の要件は「本Intentでは指標を外部に公開しない」で一致しています。

- A. 本Intentでは指標を外部へ送らない。エラーの割合は、受け取る側で、ログ（ERROR の件数）とトレース（状態コード 5xx の要求）から数える。NFR10.9 の括弧書きは「送らない」として設計する
- B. 外部エクスポートを有効にしたときは、指標も OTLP で送る。NFR3.4 の「トレースとログだけ」を「トレース・ログ・指標」として設計する（秘密情報を載せない決まりは同じ）
- X. Other (please specify)

[Answer]: B. 外部エクスポートを有効にしたときは、指標も OTLP で送る。NFR3.4 の「トレースとログだけ」を「トレース・ログ・指標」として設計する（秘密情報を載せない決まりは同じ）

### Q4. 外部エクスポートを有効にしたとき、トレースを送る割合（サンプリング率）の既定値はどうしますか？

トレースIDは、サンプリングの設定に関係なくすべての要求に割り当てます（NFR10.6）。サンプリング率が効くのは、外部へ送るトレースの割合だけです。Spring Boot の既定は 10% です。どちらを選んでも、設定で変えられます。

- A. 既定 100%（すべて送る）。想定の規模（同時ログイン 最大10名）では量の問題が無く、調べたい要求のトレースが必ず届く
- B. 既定 10%（Spring Boot の既定のまま）。送る量を抑える
- X. Other (please specify)

[Answer]: A. 既定 100%（すべて送る）。想定の規模（同時ログイン 最大10名）では量の問題が無く、調べたい要求のトレースが必ず届く

### Q5. 外部エクスポートで送る指標は、どの範囲にしますか？（Q3 の回答「指標も送る」の確認）

Q3 で指標も OTLP で送ると決まりました。送る範囲によって、受け取る側の量と、設計で確かめる「秘密情報を載せない」の対象が変わります。なお、U2〜U4 が「運用で見る指標の候補」とした値（ログインの失敗の割合、アクセス拒否の件数、監査ログの書き込みの失敗の件数）は、本Intentでは監査ログやアプリのログから数えるもので、指標としては作りません。また、指標を取り出すための Actuator の窓口（`/actuator/metrics` など）は、NFR3.5 のとおり公開しません。

- A. Spring Boot が既定で集める指標をすべて送る（HTTP の要求の件数・時間・状態コード、JVM、コネクションプール、ログのレベルごとの件数など）
- B. エラーの割合に要るものだけに絞る（HTTP の要求の件数と状態コード、ログのレベルごとの件数）
- X. Other (please specify)

[Answer]: A. Spring Boot が既定で集める指標をすべて送る（HTTP の要求の件数・時間・状態コード、JVM、コネクションプール、ログのレベルごとの件数など）
