# Performance Design — U1 アプリの骨格（u1-app-skeleton）

U1 の性能の要件（`performance-requirements.md` の NFR1.1〜NFR1.6）を満たす設計。技術は `tech-stack-decisions.md`、処理の流れは `functional-spec.md`（WF1〜WF8）に従う。設計の方針の確定回答は `nfr-design-questions.md`（Q1〜Q5）にある。`contract-summary.md` は、本ワークフローで Contract Design を行わないため無い。

## 1. 性能の予算

アプリ全体の目標は、ログインとトークンの更新の API の 95% が1秒以内（NFR1、U2 が受け持つ）。U1 は、すべての要求に共通する処理の時間を小さく抑え、その予算を圧迫しないことを受け持つ。

| 区間 | 予算（95%） | 内訳と根拠 | 要件 |
|---|---|---|---|
| すべての要求に共通する処理 | 20 ミリ秒以内 | トレースの開始と終了、Spring Security のフィルターの連鎖（U1 の段階はすべて許可）、要求の本文の大きさの確認、ヘッダーの付与、ログの出力（1要求あたり数行） | NFR1.3 |
| ヘルスチェック（内部DBにつながるとき） | 500 ミリ秒以内 | 共通の処理＋内部DBへの確認の問い合わせ1回（組み込みの H2 では数ミリ秒） | NFR1.1 |
| ヘルスチェック（内部DBが応答しないとき） | 制限時間（既定2秒）＋わずか | 制限時間で確認を打ち切り DOWN を返す（2章） | NFR1.2 |
| 起動から要求の受け付けまで | 30 秒以内 | 3章 | NFR1.4 |
| 画面の初回表示の JavaScript | 圧縮後 500KB 以内（目安） | 4章 | NFR1.5 |

共通の処理が予算を超えた場合に疑う順番: ログの出力行数（1要求の行数が増えていないか）、トレースの記録（外部エクスポートの有効時の送信の待ち行列）、フィルターの追加（U2・U3 が足したもの）。測り方は `performance-requirements.md` の NFR1.3 のとおり、何もしない API との差を Performance Validation で測る。

## 2. ヘルスチェックの時間の上限（NFR1.1、NFR1.2）

Actuator の既定の DB の確認は、問い合わせの制限時間を細かく決められない。そこで、内部DBの確認を U1 が用意する確認の仕組み（ヘルスの指標の1つ）に置き換え、次の形にする。

- 確認は専用の小さな実行の枠（スレッド1本）で行い、呼び出し側は制限時間（設定 `mastersmith.health.db-timeout`、既定2秒）だけ待つ。時間内に終わらなければ DOWN（503）を返し、確認を中断させる。
- 前の確認がまだ終わっていないときは、新しい確認を始めずに DOWN を返す。内部DBが応答しない間にヘルスチェックの要求が続いても、スレッドや接続を使い果たさない（隔壁の考え方）。
- 確認の中身は、コネクションプールから接続を1本借りて確認の問い合わせ（`SELECT 1`）を1回行うこと。接続を借りる待ち時間も制限時間に含まれる。
- 応答は状態（UP／DOWN）だけ（BR1.3、`security-design.md` 3章）。

```text
check(timeout):
  if running  -> return DOWN
  future = executor.submit(() -> pool.borrow().query("SELECT 1"))
  try   future.get(timeout) -> UP
  catch timeout/error        -> future.cancel(); DOWN
```

## 3. 起動時間（NFR1.4）

起動を遅くする処理を持ち込まないことで 30 秒以内に収める。

- スキーマの変更（Flyway）は起動時に当てるが、U1 の段階の変更は少なく、組み込みの H2 では数秒以内に終わる。
- Hibernate にはスキーマを作らせず、検証だけ行う（`tech-stack-decisions.md`）。
- 起動時に外部へ接続しない。外部エクスポートは既定で無効であり、有効でも送信は非同期で、送り先に届かなくても起動を止めない（`reliability-design.md` 2章）。
- 測り方: コンテナの起動の開始から、ヘルスチェックが UP を返すまでの時間を Build and Test で測る。30 秒を超えたら、起動の記録（Spring Boot の起動の段階ごとの時間）で原因を調べる。

## 4. 画面の読み込み（NFR1.5）

- **分割の方針**: 各機能の登録用ファイル（`import.meta.glob` で読み込む）は、画面の起動に必要なため最初に読み込む。登録用ファイルが指す画面の部品は、開いたときに読み込む（遅延読み込み）。後の単位が画面を増やしても、初回の読み込みの量はほとんど増えない。
- **デザインシステム**: make-you-chic-ui は、使う部品だけがビルドに入る形で取り込む（Vite の不要なコードの除去を妨げない）。React の二重読み込みは `resolve.dedupe` で防ぐ（チームの進め方）。
- **文言**: 日本語・英語の文言は U1 の段階では小さいため、最初の読み込みに含める。
- **確かめ方**: ビルドの後に、最初の読み込みに入る JavaScript（入口のファイルと、そこから静的に読み込まれるファイル）の圧縮後の合計を測るスクリプトを、1コマンドの検査に入れる。500KB は目安のため、超えたときは警告を出し（統合は止めない）、Performance Validation で見直す。

## 5. 配信とキャッシュ

| 対象 | キャッシュの指定 | 理由 |
|---|---|---|
| ビルドした画面のファイルのうち、名前にハッシュが付くもの（`/assets/` の下） | `public, max-age=31536000, immutable` | 中身が変われば名前が変わるため、長く保存してよい |
| 画面の入口（`index.html` と、画面の URL への応答） | `no-cache` | 新しい版を配備したらすぐ反映する |
| API の応答（`/api/` の下）と Actuator の応答 | `no-store` | NFR3.10。利用者ごとの応答を保存させない |

- 応答の圧縮（gzip）を、組み込みの Tomcat で有効にする（HTML・JavaScript・CSS・JSON）。
- Spring Security は既定ですべての応答に保存させない指定を付けるため、U1 ではその既定を外し、上の表の指定を U1 が付ける（`security-design.md` 2章）。

## 6. サーバー側の資源

| 資源 | 設定 | 理由 | 要件 |
|---|---|---|---|
| 内部DBの接続（HikariCP） | 最大 10 本、接続を借りる待ち時間の上限 5 秒 | 想定の規模を1台で処理する。待ちが長引いたときは失敗させ、要求を無期限に待たせない | NFR1.7 |
| 要求の処理の中の DB 接続 | 画面の描画まで接続を持ち越す設定（open-in-view）は無効 | 接続を持つ時間を短くする | `tech-stack-decisions.md` |
| 問い合わせの時間の上限 | 既定 10 秒（JPA の問い合わせの時間の上限の設定） | 別サーバーの H2 に切り替えたときに、応答しない問い合わせで接続を使い続けない | — |
| 要求を処理するスレッド（Tomcat） | Spring Boot の既定（最大 200） | 同時ログイン 最大10名に十分 | NFR1.7 |
| キャッシュ | 持たない | 想定の規模では DB への問い合わせで足り、キャッシュの一貫性の問題を持ち込まない | — |

## 7. ログの出力と性能（NFR1.6）

確定回答 Q2 により、ログは同期で標準出力へ書く。NFR1.6 の確かめ方（「非同期の出力、または標準出力への書き込み」）の後者に当たる。標準出力はコンテナの実行環境が受け取り、アプリはファイルへ書かないため、通常は書き込みで要求が止まらない。

- 受け入れた危険: 標準出力の受け手（コンテナの実行環境のログの仕組み）が詰まったときは、要求も待つ。ログを失わないことを優先した（Q2）。
- 出力の費用を抑える: ログの1件ごとに呼び出し元の場所（クラス名・行番号）を求めない（スタックをたどる費用がかかるため）。既定のレベルは INFO で、要求1件あたりの行数を少なく保つ。
- メソッドの呼び出しの追跡（TraceAspect）は TRACE のときだけ文字列を組み立てるため、既定（INFO）では追跡の文字列を作らない（`observability-design.md` 4章）。
