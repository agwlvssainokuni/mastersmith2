# Reliability Design — U1 アプリの骨格（u1-app-skeleton）

U1 の信頼性と品質の要件（`reliability-requirements.md` の NFR6.1、NFR9.1〜NFR9.5、NFR10.10、NFR10.11、NFR1.11、NFR7.1、NFR8.1）を満たす設計。技術は `tech-stack-decisions.md`、処理の流れは `functional-spec.md`（WF1〜WF8）に従う。性能・拡張性・観測性・安全の要件（`performance-requirements.md`・`scalability-requirements.md`・`observability-requirements.md`・`security-requirements.md`）に関わる部分は各設計書を参照する。`contract-summary.md` は、本ワークフローで Contract Design を行わないため無い。

本番の稼働率の目標（SLO）と警報の条件は、配備先が決まったときに Operation の段階で定める（`reliability-requirements.md`）。本書は、配備先によらず土台に求める振る舞いを設計する。

## 1. 故障の場合と振る舞い

| 故障 | 振る舞い | 影響の範囲 | 戻り方 | 要件 |
|---|---|---|---|---|
| 起動時に内部DBにつながらない、またはスキーマの変更に失敗する | 起動を止める（途中の状態で動かない） | アプリ全体（起動しない） | 原因を直して再起動する。スキーマの変更は前進のみ | NFR9.1 |
| 起動後に内部DBにつながらない・応答しない | ヘルスチェックは制限時間内に DOWN（503）。DB を使う API は、接続を借りる待ち（5 秒）または問い合わせの時間の上限（10 秒）で失敗し 500。DB を使わない要求（画面の配信・説明ページ）は応答を続ける | DB を使う要求だけ | 内部DBが戻れば、次の要求から自動で戻る（接続はプールが作り直す） | NFR10.10、NFR1.2 |
| 外部エクスポートの送り先に届かない | 要求の処理は止めない。送信は要求と切り離して行い、待ち行列があふれた分は捨てる。警告をログに出す | 外部へ送る記録の一部だけ | 送り先が戻れば、次の送信から自動で戻る | NFR10.11 |
| 標準出力の受け手が詰まる | ログは同期で書くため、要求も待つ（確定回答 Q2 で受け入れた危険） | 要求全体の遅れ | 受け手が戻れば解消 | NFR1.6 |
| 想定外の例外 | 500 / `INTERNAL_ERROR` を返し、ERROR でスタックトレース付きのログを1回出す | その要求だけ | — | BR5.5、BR5.6 |
| 後の単位の問題の種類の code・slug の重複（バックエンド） | アプリの起動を失敗させ、重複した code・slug を示す | アプリ全体（起動しない） | 定義を直して再起動する | BR5.16 |
| 画面の登録の重複（URL・項目の id・featureId、ログイン状態の提供元やログイン画面の2つ以上の登録） | 画面の起動（ブラウザでの初期化）を止め、重複した登録を示す。バックエンドは動き続ける | 画面だけ（API とヘルスチェックは応答する） | 登録用ファイルを直して画面を作り直す | BR7.2 |

## 2. 回復の仕組み（パターンの選択）

| パターン | 採否 | 理由と設定 |
|---|---|---|
| 時間の上限 | 採る | ヘルスの確認（既定2秒、`performance-design.md` 2章）、接続を借りる待ち（5 秒）、問い合わせ（10 秒）、外部エクスポートの送信（送信1回あたり 10 秒） |
| 隔壁 | 採る（ヘルスチェックだけ） | ヘルスの確認を専用のスレッド1本で行い、前の確認が終わるまで次を始めない。内部DBが応答しない間も、要求を処理するスレッドを使い果たさない |
| 捨てて守る（外部エクスポート） | 採る | 送信の待ち行列（トレース・ログ）は上限付きで、あふれたら古いものから捨てる。要求の処理を待たせない |
| 再試行 | DB には採らない。外部エクスポートは送信の仕組みの再試行に任せる | DB への書き込みの再試行は重複の原因になる。内部DBは組み込みのため、一時的な通信の失敗が起きにくい |
| 遮断器（サーキットブレーカー） | 採らない | 外部の依存は内部DBと任意の OTLP の受け手だけで、どちらも上の時間の上限と「捨てて守る」で足りる。仕組みを増やさない |
| 代わりの応答（劣化の運転） | 部分的に採る | 内部DBが止まっても、画面の配信と説明ページは応答を続ける（1章） |

優先度の区分: ログイン・ヘルスチェック・画面の配信を「常に動くべきもの」、外部エクスポートを「劣化してよいもの」とする。

## 3. 起動と停止

- **起動の順番**: 設定の読み込み → 問題の種類の定義の収集と重複の検査 → 内部DBの接続とスキーマの変更（失敗したら止める） → 要求の受け付け（`functional-spec.md` WF1）。初期管理者の作成（U2）はスキーマの変更の後に行う（ADR-006 の帰結）。
- **停止（NFR1.11）**: 止める合図を受けたら、新しい要求を受け付けず、処理中の要求を終えてから止める。待ち時間の上限は 30 秒（Spring Boot の穏やかな停止の設定）。コンテナの停止の猶予もこれより長くする（Infrastructure Design で決める）。外部エクスポートの待ち行列は、停止のときに送れる分だけ送る。

## 4. データの保護（NFR6.1、NFR9.1、NFR9.2）

- 内部DBは既定で組み込み・ファイル保存（`./data/`、コンテナでは `/app/data` をボリュームにする）とし、再起動してもデータが残る。
- スキーマの変更は Flyway の SQL のファイルで、前進のみ・1つ前の版のアプリが動く後方互換を保つ。適用済みの変更のファイルは書き換えない（Flyway の検証で書き換えを検出して起動を止める）。
- バックアップは、アプリを止めた状態で `./data/` の下のファイルを複写する。戻すときは、アプリを止めてファイルを置き換える。手順を README に書く。
- 配備の確認（NFR9.3）: 配備のたびにヘルスチェックの UP と、ログイン画面の表示を確かめるまで配備の完了としない。戻すときは直前の版の成果物で配備し直す（スキーマは前進のみのため、1つ前の版のアプリが今のスキーマで動く）。手順は Deployment Pipeline で作る。

## 5. 品質を保つ仕組み（NFR7.1、NFR8.1、NFR9.4、NFR9.5）

| 要件 | 設計 |
|---|---|
| NFR7.1 多言語 | 文言は i18next の日本語・英語の文言のファイルで持つ。両方の言語で鍵の集まりが同じであることをテストで確かめる。ブラウザの希望言語が ja・en のどれにも当たらなければ日本語（BR6.1） |
| NFR8.1 アクセシビリティ | U1 の画面の部品（アプリシェル、ログイン用レイアウト、ホーム、ページが見つかりません）ごとに vitest-axe の検査を1件入れる |
| NFR9.4 カバレッジ | JaCoCo（行 80%・分岐 70%）と `@vitest/coverage-v8` の `thresholds`（同じ値）で、下回ったらビルドを失敗させる。計測から外すのは、起動クラス、設定値だけのクラス、自動生成コード、`vendor/` の下に限る |
| NFR9.5 1コマンドの検査 | リポジトリのルートに、フォーマット・リンタ・ライセンスヘッダー・ビルド・全テスト・カバレッジ下限・秘密情報の検出・静的解析・依存関係の脆弱性検査をこの順に実行し、1つでも失敗したら全体を失敗にする入口を1つ置く。CI（GitHub Actions）も同じ入口を呼ぶ |

時刻に依存する処理（ヘルスの制限時間を含む）は、注入できる時計と実行の枠を使い、テストで実時間の待ちに頼らない（チームの進め方）。
