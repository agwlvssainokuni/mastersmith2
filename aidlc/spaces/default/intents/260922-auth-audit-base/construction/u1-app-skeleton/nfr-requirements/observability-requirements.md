# Observability Requirements — U1 アプリの骨格（u1-app-skeleton）

U1 の観測性の要件。ログ・トレース・外部エクスポートの仕組みは U1 が用意し、U2〜U4 はそれを使う。

## ログ

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR10.1 | アプリのログは、標準出力へ1行1件の JSON で出す（開発時も同じ）。出力は logstash-logback-encoder で行う | テストで、1行が1件の JSON として読めることを確かめる | FR10.1、Q3 |
| NFR10.2 | ログの項目の名前を固定する: `timestamp`（ISO 8601、タイムゾーン付き）、`level`、`logger`、`thread`、`message`、`traceId`、`spanId`、`exception`（あれば）、呼び出し側が渡したキーと値 | テストで項目の名前を確かめる | U1 の決まり 3.2 |
| NFR10.3 | 要求の処理中のログには、その要求の `traceId` と `spanId` を必ず入れる | テストで、1要求の間のすべてのログに同じトレースIDが入ることを確かめる | FR10.2 |
| NFR10.4 | ログのレベルの既定は INFO とし、設定で機能ごとに変えられる。想定内のエラー（4xx）は WARN 以下、想定外（5xx）は ERROR | 設定の確認とテスト | U1 の決まり 5.5 |

## トレース

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR10.5 | 受け取った要求に正しい `traceparent` があれば引き継ぎ、無い・正しくなければ新しいトレースを始める | テスト（FR10.3 の受け入れ基準） | FR10.3 |
| NFR10.6 | すべての要求にトレースIDを割り当てる。サンプリングの設定によって、ログ・エラー応答・監査ログのトレースIDの有無が変わらないようにする | テストで、サンプリングの設定を変えてもトレースIDが入ることを確かめる | U1 functional-spec.md 6.1 |

## 外部エクスポート

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR10.7 | 外部エクスポート（OTLP）は既定で無効とし、設定で有効にして送り先を指定できる | 既定の設定で外部へ何も送らないことをテストで確かめる | FR10.4、NFR6 |

## ヘルスと指標

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR10.8 | ヘルスチェック（`/actuator/health`）でアプリと内部DBの状態を返す。これを、稼働しているかの指標（健全性の指標）とする | テスト | FR1.1 |
| NFR10.9 | エラーの割合の指標として、アプリのログの ERROR の件数と、応答の状態コード 5xx の件数を使う。本Intentでは指標を外部に公開しない（外部エクスポートを有効にしたときに送る） | 配備先が決まったときに確かめる | operation フェーズの決まり（健全性の指標とエラーの割合の指標） |

## 目標と警報

本番の目標（SLO）と警報の条件は、配備先が決まったときに Operation の段階で定める。その際は、目標を割る前に警報が出るようにしきい値を決める。当面（開発者の PC 上のコンテナ）は、ヘルスチェックとアプリのログで状態を確かめる。
