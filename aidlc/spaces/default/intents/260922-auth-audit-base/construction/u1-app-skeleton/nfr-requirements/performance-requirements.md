# Performance Requirements — U1 アプリの骨格（u1-app-skeleton）

U1 の性能の要件。アプリ全体の目標は NFR1（利用者 最大50名・同時ログイン 最大10名で、ログインとトークンの更新の API の 95% が1秒以内）で、その達成は U2 が受け持つ。U1 は、すべての要求に共通する処理（トレース・ログ・エラー応答）がその目標を圧迫しないことと、U1 自身の処理の応答を受け持つ。測定の環境は、当面の配備先である開発者の PC 上のコンテナとする。

| ID | 要件 | 測り方 | 出典 |
|---|---|---|---|
| NFR1.1 | ヘルスチェックは、内部DBにつながるとき、95% が 500 ミリ秒以内に応答する | 同時10件の要求を繰り返し、応答時間の 95 パーセンタイルを測る | NFR1（同じ負荷の想定）、FR1.1 |
| NFR1.2 | ヘルスチェックの内部DBの確認は、制限時間（既定2秒、設定で変更可）を超えたら打ち切り、DOWN を返す。制限時間を超えて応答を待たせない | 内部DBの応答を止めた状態で、応答が制限時間＋1秒以内に返ることを確かめる | U1 の決まり 1.2 |
| NFR1.3 | すべての要求に共通する処理（トレースの開始、ログの出力、エラー応答への変換）が加える時間は、1要求あたり 95% で 20 ミリ秒以内とする | 何もしない API とそれを通さない場合の差を測る（Performance の検証で行う） | NFR1 の予算を圧迫しないため |
| NFR1.4 | アプリは、開発者の PC 上のコンテナで、起動から要求を受け付けられるまで 30 秒以内とする | 起動の開始からヘルスチェックが UP を返すまでを測る | 開発と E2E の回しやすさ |
| NFR1.5 | 画面の初回の表示に読み込む JavaScript の合計は、圧縮後 500KB 以内を目安とする | ビルドの出力の大きさを確かめる | 利用者の画面の表示を遅くしないため |
| NFR1.6 | ログの出力は、要求の処理を待たせない（出力先への書き込みで要求の応答が止まらない） | 設定の確認（非同期の出力、または標準出力への書き込み） | NFR1 |

NFR1.3〜NFR1.5 の値は設計上の目標であり、測定の結果に応じて NFR Design で見直す。
