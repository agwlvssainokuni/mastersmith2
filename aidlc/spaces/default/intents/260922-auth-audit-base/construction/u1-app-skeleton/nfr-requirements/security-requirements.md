# Security Requirements — U1 アプリの骨格（u1-app-skeleton）

U1 が受け持つ土台（起動・内部DB・ログ・トレース・共通のエラー応答・説明ページ・画面の配信）の安全の要件。認証・認可そのもの（トークン・パスワード・アクセス制御）は U2・U3 の要件で扱う。要件の ID は、要件定義書の NFR の ID に枝番を付けたものである。

## 1. 秘密情報の扱い（NFR3）

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR3.1 | パスワード・トークン・署名鍵・内部DBのパスワードを、ログ・トレースの属性・外部エクスポート・エラー応答に含めない | テストで、秘密情報の値が出力に含まれないことを確かめる | NFR3、U1 の決まり 2.3・3.4・4.3・5.4 |
| NFR3.2 | 秘密情報（内部DBのパスワード、署名鍵、初期管理者のパスワード）は環境変数などで渡し、ソースコード・設定ファイルに直接書かない。見本は値を空にした `.env.example` とする | Gitleaks（pre-commit と CI）で検出し、High 以上で統合を止める | NFR3、project.md Forbidden・Mandated |
| NFR3.3 | エラー応答に、内部の例外メッセージ・スタックトレースを載せない | テストで確かめる | U1 の決まり 5.4 |
| NFR3.4 | 外部エクスポートを有効にしても、送るのはトレースとログだけとし、秘密情報を載せない | 設定の確認とテスト | NFR3、U1 の決まり 4.3 |

## 2. 公開する範囲

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR3.5 | Actuator は health だけを公開し、ほかの機能（env・configprops・heapdump など）は外部に公開しない。health の応答は状態（UP／DOWN）だけとし、内訳を載せない | テストで、health 以外の Actuator に届かないこと、health に内訳が無いことを確かめる | U1 の決まり 1.3、U3 の決まり 1.5 |
| NFR3.6 | H2 の Web コンソールは有効にしない（開発時も含む） | 設定の確認とテスト（コンソールのパスに届かない） | 内部DBを外部から操作させないため |
| NFR3.7 | 内部DBは、既定の組み込み・ファイル保存では外部からの接続を受け付けない。別サーバーの H2 に切り替える場合も、接続はアプリからに限る | 設定の確認 | FR1.2 |

## 3. 要求と応答

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR3.8 | エラー応答の `type` のベースURLは、設定の固定値か、要求そのものの Host から組み立てる。転送元のヘッダーは信頼する設定を有効にしたときだけ使う（既定は無効） | テストで、転送元のヘッダーが既定で無視されることを確かめる | U1 の決まり 5.10 |
| NFR3.9 | 問題の種類の説明ページ（HTML）は、埋め込むすべての値をエスケープし、要求から受け取った値を埋め込まない | テストで確かめる | U1 の決まり 5.15 |
| NFR3.10 | 画面とすべての応答に、セキュリティ関係のヘッダーを付ける: `Content-Security-Policy`（`default-src 'self'`、スクリプトは同じ配信元のものだけ、`frame-ancestors 'none'`）、`X-Content-Type-Options: nosniff`、`Referrer-Policy: same-origin`。キャッシュは、API の応答には `no-store` を付ける | テストで、応答のヘッダーを確かめる | 同じ配信元で画面を配る構成、NFR5（画面側のトークンの保護） |
| NFR3.11 | ログに出す値は、キーと値として JSON の値に入れ、改行などで記録を偽装できないようにする | テストで、改行を含む値が1行の JSON に収まることを確かめる | U1 の決まり 3.1・3.5、U4 の決まり 2.2 |
| NFR3.12 | 要求の本文の大きさに上限を設け（既定 1MB）、超えた要求は 413 で拒否する | テストで確かめる | 大きすぎる要求で資源を使い果たさせないため |

## 4. 依存関係と検査

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR3.13 | 依存関係は lockfile（npm）とバージョンカタログ（Gradle）で版を固定し、CI ではそのとおりに入れる | CI の設定 | project.md Mandated |
| NFR3.14 | 依存関係の脆弱性検査（Dependabot、OSV-Scanner。`vendor/make-you-chic-ui` の lockfile を含む）と静的解析（SpotBugs＋FindSecBugs）を統合前と CI で実行し、重大度 High 以上で統合を止める | 1コマンドの検査と CI | TP |

## 5. 脅威の考慮（U1 の範囲）

脅威の分析（STRIDE）の詳細は NFR Design で行う（要件定義の未解決の論点 OQ4）。U1 の範囲で考慮する主な脅威と、対応する要件は次のとおり。

| 脅威 | 例 | 対応する要件 |
|---|---|---|
| なりすまし（Spoofing） | 転送元のヘッダーの偽装で、エラー応答の URL や接続元IP を偽る | NFR3.8（U2・U3 の接続元IP も同じ方針） |
| 改ざん（Tampering） | ログへの改行の注入で、偽の記録を作る | NFR3.11 |
| 否認（Repudiation） | 操作の追跡ができない | トレースIDをログ・エラー応答・監査ログに載せる（U1 の決まり 3.3・5.3、U4 の決まり 2.4） |
| 情報漏えい（Information disclosure） | Actuator・H2 コンソール・エラー応答・ログからの内部情報や秘密情報の漏えい | NFR3.1〜NFR3.7 |
| サービス妨害（Denial of service） | 大きすぎる要求 | NFR3.12 |
| 権限昇格（Elevation of privilege） | 画面での表示の制御だけに頼る | サーバー側の判定は U3 が受け持つ（U3 の決まり 2.6） |
| クロスサイトスクリプティング | 画面や説明ページへのスクリプトの注入 | NFR3.9、NFR3.10、画面では HTML を直接埋め込まない（TP の `react/no-danger`） |
