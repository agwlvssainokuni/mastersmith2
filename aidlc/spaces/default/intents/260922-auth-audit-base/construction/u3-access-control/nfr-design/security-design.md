# Security Design — U3 管理画面のアクセス制御（u3-access-control）

U3 の安全の要件（`security-requirements.md` の NFR3.1〜NFR3.8）を満たす設計。判定の決まりは U3 の `rules.md`（BR1〜BR6）、処理の流れは U3 の `functional-spec.md`（WF1〜WF4）、技術は U3 の `tech-stack-decisions.md` に従う。性能・拡張性・信頼性・観測性の要件（`performance-requirements.md`・`scalability-requirements.md`・`reliability-requirements.md`・`observability-requirements.md`）に関わる部分は各設計書を参照する。設計の方針の確定回答は `nfr-design-questions.md`（Q1）にある。`contract-summary.md` は、本ワークフローで Contract Design を行わないため無い。そのため、確認用 API のパスと U2 との受け渡しの形は本書で決める。

U3 は、U1 のフィルターの連鎖と差し込み口（U1 の `nfr-design/security-design.md` 3章）と、U2 のトークンの検証（U2 の `nfr-design/security-design.md` 4章）の上に作り、U1・U2 の設定を書き換えない。

## 1. アクセスの決まりの並び（NFR3.1〜NFR3.3、NFR3.8）

U1 の連鎖の中での決まりの並び（先に当たった決まりが使われる）:

| 順 | 置く単位 | パス | 利用条件 |
|---|---|---|---|
| 1 | U1 | `/actuator/health`、`/api/problems/**` | 公開 |
| 2 | U2 | `/api/auth/login`、`/api/auth/session/**` | 公開 |
| 3 | U3 | `/api/admin`、`/api/admin/**` | 管理者のみ |
| 4 | U1（U3 が「ログイン必須」に切り替える） | 1〜3 に当たらない `/api/**` | ログイン必須 |
| 5 | U1 | `/api/**` 以外 | 画面の配信（公開） |

- U1 の差し込み口の「API の既定の扱い」を U3 が「ログイン必須」に切り替える部品を置く（U1 の設計のとおり、この部品は1つだけ）。公開する API は 1・2 の一覧だけになる（NFR3.2）。公開の一覧を変えるときは、レビューで理由を確かめる。
- U3 の決まりの文（BR1.4）の順「管理者のみ → 公開 → ログイン必須」と、上の表の順（公開の 1・2 が管理者のみの 3 より先）は、パスが重ならないため結果が同じになる。
- パスの照合: 大文字・小文字を区別する。`/api/admin` と `/api/admin/**` の2つを書き、末尾のスラッシュの有無で判定を変えない（NFR3.3）。`/API/admin/...` は 4 に当たり、ログインしていれば存在しない API として 404、していなければ 401。
- `/api/**` の外で応答するのは、画面の配信と `/actuator/health` だけ（NFR3.8）。Actuator のほかの窓口は U1 の設計で用意しない。

## 2. 正規化されていないパスの拒否（NFR3.3、確定回答 Q1）

- Spring Security の要求の検査（エンコードされた区切り、`;`、`..`、`//` などを含むパスの拒否）は、既定のまま外さずに使う。判定の前に拒否される。
- 確定回答 Q1 により、拒否の処理を置き換え、U1 の共通の組み立ての仕組みで ErrorResponse の形の 400 を返す。code は `REQUEST_REJECTED`（日英の説明つきの問題の種類を U3 が定義する）。traceId も載せる。
- この拒否はセキュリティ関係のヘッダーを書く処理より手前で起きるため、拒否の処理の中で、U1 と同じヘッダー（CSP・`X-Content-Type-Options`・`X-Frame-Options`・`Referrer-Policy`・`Cache-Control: no-store`）を付ける。ヘッダーの値は U1 の設定を読み、U3 で書き直さない。
- 拒否したパスはログにそのまま出さない（細工された文字列を記録に入れない）。WARN で `REQUEST_REJECTED` とトレースIDだけを出す。
- **トレースIDが付く理由**: 要求の観測（トレースの開始）は、Spring Boot が登録するサーブレットのフィルターで、順番はほぼ最優先（最優先＋1）である。Spring Security のフィルターの連鎖は、それより後（順番 -100）に登録される。要求の検査は Spring Security のフィルターの連鎖の入口で行われるため、拒否の時点で既にトレースが始まっており、拒否の応答にも traceId が載る。U1 の設計でもトレースの開始を最初に通る部品としている（U1 の `nfr-design/logical-components.md` 2章）。Code Generation で、拒否の 400 の応答とその WARN のログに同じトレースIDが入ることをテストで確かめる（使う版でフィルターの順番が変わっていないことの確認を兼ねる）。

## 3. 判定と応答（NFR3.1、NFR3.4〜NFR3.6）

- 管理者かどうかは、U2 が要求ごとに内部DBから読んだ AuthenticatedUser の値で判断する。画面から送られた値・トークンの中身は使わない（NFR3.5）。U3 は DB への問い合わせを追加しない（`performance-design.md`）。
- 管理者のみの判定は、API が存在するかどうかを調べる前（フィルターの段階）に行う。管理者でない利用者には、存在しない管理 API も 403 になる（NFR3.4）。
- 確認用 API は `GET /api/admin/check` とし、判定を通れば 204（内容なし）を返す（BR4.1）。
- **401 の処理（認証の入口の処理）**: U3 が1つ用意し、U1 の差し込み口で連鎖に置く。応答は U1 の共通の組み立ての仕組みで 401 / `AUTHENTICATION_REQUIRED`。管理者のみのパスで、理由が `TOKEN_EXPIRED` でなければ出来事を知らせる（BR3.2・3.3）。
- **401 の理由の受け渡し（U2 との約束）**: 理由は、認証の失敗の例外の種類で渡す。受け渡しの形を次のとおり決める。
  - U2 は、Spring Security の認証の失敗の例外を継承した「トークンの認証の失敗」の例外（名前は Code Generation で決める）を1つ用意し、理由の区分を持たせる。トークンの検証の失敗（形式の誤り → `TOKEN_MALFORMED`、署名・方式の不一致 → `TOKEN_INVALID`、有効期限切れ → `TOKEN_EXPIRED`）と、利用者が DB にいない（`USER_NOT_FOUND`）は、すべてこの例外にして投げる。U2 はこの区分を DEBUG でログに出す（U2 の `nfr-design/observability-design.md` 1章）。
  - トークンが無い要求は、U2 の検証を通らず、Spring Security が「認証が足りない」の例外で U3 の 401 の処理を呼ぶ。U3 はこれを `TOKEN_MISSING` とみなす。
  - U3 の 401 の処理は、受け取った例外が上の例外なら持っている区分を、そうでなければ `TOKEN_MISSING` を理由とする。理由が `TOKEN_EXPIRED` のときだけ出来事を知らせない（BR3.2）。
  - U2 の設計はこの例外の形を書いていないため、U2 の Code Generation の計画にこの約束を書き、両方の単位のテスト（区分ごとに出来事の有無を確かめる）で守る。
- **403 の処理（アクセス拒否の処理）**: 応答は U1 の共通の組み立ての仕組みで 403 / `ACCESS_DENIED`。理由 NOT_ADMIN の出来事を知らせる（BR3.1）。
- 応答に内部の情報（例外のメッセージ、判定の詳細、パス）を載せない（NFR3.6）。

## 4. 出来事の秘密情報と接続元IP（NFR3.7）

- アクセス拒否の出来事の項目は、監査ログの記録項目（日時・種類・メールアドレス（分かれば）・理由・接続元IP・User-Agent・要求のパス・トレースID）にそろえ、アクセストークンの値・Authorization ヘッダー・パスワードを持たない。
- 要求のパスは、判定を通った正規化済みのパスだけを載せる（2章で拒否したパスは出来事にならない）。問い合わせの部分（`?` 以降）は載せない。
- 接続元IP は、U1 の方針と同じく、転送元のヘッダーを既定で信頼しない（U2 の出来事と同じ取り方）。

## 5. 承認済みの Functional Design との違い（Code Generation で揃える）

| 違い | Functional Design の記述 | 本設計 |
|---|---|---|
| 問題の種類 | `rules.md` BR6.1: U3 の問題の種類は `ACCESS_DENIED` だけ | 確定回答 Q1 により `REQUEST_REJECTED`（400）を加え、2つとする |
| 拒否の応答 | `functional-spec.md` WF1 の手順1は「判定の前に拒否する」だけで、応答の形を決めていない | 共通の形の 400 とヘッダー（2章） |

Functional Design の文書そのものはこの段階では書き換えず、Code Generation の計画の確認（Plan Approval）で計画に明記して依頼者の承認を得る。U1 の決まり 5.14（使う code すべてに日英の説明）と起動時の重複の検査はそのまま当てる。

## 6. 脅威の分析（STRIDE、U3 の範囲）

| 脅威 | 例 | 対策 | 残る危険 |
|---|---|---|---|
| 権限昇格 | 画面を介さずに管理 API を呼ぶ | サーバー側の判定（1章・3章） | なし |
| 権限昇格 | パスの細工で判定を回り込む（`..;`、エンコードされた区切り、大文字、末尾のスラッシュ） | 要求の検査で判定の前に拒否、大文字・小文字の区別、2つのパスの型、既定でログイン必須 | 新しい API を `/api/admin` の外に置く誤り（レビューで防ぐ） |
| 権限昇格 | 管理者フラグの偽装 | 要求ごとに DB の値で判断 | なし |
| 情報漏えい | 管理 API の有無の推測 | 非管理者には存在しなくても 403 | 管理者には 404 が見える（管理者自身のため問題ない） |
| 情報漏えい | エラー応答・ログからの内部情報 | 共通の形、パスをログに出さない | なし |
| 否認 | 管理画面への不正なアクセスが追えない | 403 と期限切れ以外の 401 を出来事として U4 が記録 | 期限切れの 401 は記録しない（BR3.2 の判断） |
| サービス妨害 | 拒否の記録を大量に起こさせる | 受け入れる（1件の記録は軽く、社内向けの規模） | 入口の回数制限は配備先で必要なら入れる |

## 7. 確かめるテスト

| 対象 | テスト |
|---|---|
| 判定 | 未ログイン 401、非管理者 403、管理者 204（`/api/admin/check`）。画面を介さない呼び出し |
| パス | 非管理者の `/api/admin` と `/api/admin/` は 403。`/api/admin/..;/`・エンコードされた区切りは 400 / `REQUEST_REJECTED`（共通の形とヘッダーつき）。`/API/admin/check` はログイン中 404・未ログイン 401 |
| 存在の秘匿 | 非管理者の `/api/admin/nothing` は 403、管理者は 404 |
| 既定で拒否 | 公開の一覧に無い `/api/` の下がログインなしで 401 |
| DB の値 | 管理者フラグを外した直後の要求が 403 |
| 出来事 | 403 と期限切れ以外の 401 で知らせる、期限切れと管理者のみ以外の 401 では知らせない、秘密情報が無い |
| 公開する範囲 | health 以外の Actuator に届かない |
