# CI/CD Pipeline — U3 管理画面のアクセス制御（u3-access-control）

U3 は U1 の検査・ビルド・配備の流れ（U1 の `infrastructure-design/cicd-pipeline.md`: `./gradlew verify`、pre-commit、GitHub Actions、手元のコンテナへの配備）をそのまま使い、流れの形は変えない。本書は、U3 がその流れに足すテストと配備の確認だけを書く。入力は U3 の NFR Design（`security-design.md` 7章のテスト、`reliability-design.md` 3章の品質、`performance-design.md`、`observability-design.md`、`scalability-design.md`、`logical-components.md`）、Domain Design の `components.md`、U3 の `functional-spec.md` である。`contract-summary.md` は、本ワークフローで Contract Design を行わないため無い。

## 1. `./gradlew verify` に足すもの

| 段（U1 の順） | U3 が足すもの |
|---|---|
| 5 単体テスト | 管理者向け領域の画面の部品（確認中・表示・見つからない・エラーの4つの状態、Vitest、vitest-axe による各部品のアクセシビリティ検査、日英の文言の鍵の一致） |
| 6 結合テスト | サーバー側の認可（未ログイン 401、管理者でない 403、管理者 204）、画面を介さない呼び出し、パスの境界（`/api/admin` と `/api/admin/`、細工されたパスの 400 / `REQUEST_REJECTED` とヘッダー、`/API/admin/check` の扱い）、存在しない管理 API（非管理者 403・管理者 404）、公開の一覧に無い `/api/` の下が未ログインで 401、管理者フラグを外した直後の 403、DB への問い合わせが増えないこと（SQL の回数）、出来事の有無（403 と期限切れ以外の 401 で知らせる、期限切れと管理者のみ以外の 401 では知らせない）と秘密情報が無いこと、出来事の受け取りの失敗で応答が変わらないこと、health 以外の Actuator に届かないこと、401 の理由の受け渡し（U2 の例外の区分ごと） |
| 8 安全の検査 | 追加なし（U1 の検査が U3 のコードも対象にする） |

チームの進め方の必須の認可のテスト（未認証 401、管理者フラグなし 403、管理者 200 をサーバー側で確かめる。画面で管理メニューを隠すことはサーバー側の検査の代わりにしない）を、上の結合テストで入れる。確認用 API は内容なしの成功（204）で、「200 系の成功」として確かめる。

## 2. CI（GitHub Actions）

追加の設定は無い。U3 のテストは秘密情報を使わず、仮の署名鍵で U2 のトークンを作って行う（鍵はテストの中で作る）。

## 3. 配備の確認

| 手順 | U3 に固有の点 |
|---|---|
| 配備の確認（スモークテスト） | U1・U2 の確認（ヘルスチェック、ログイン画面の表示、初期管理者でのログインとログアウト）に加えて、初期管理者で「管理」から管理者向け領域が開けること |
| 戻し方 | U1 のとおり直前の版の WAR で作り直す。U3 は表を持たないため、スキーマの影響は無い |

管理者でない利用者の確認（「ページが見つかりません」になること）は、本Intentでは管理者でない利用者を作る機能が無いため、配備の確認ではなく結合テストと E2E で行う。

## 4. 段と関門の対応

U1 の `cicd-pipeline.md` 6章のとおり。U3 のテストは、統合の前の `./gradlew verify` と CI の関門に含まれる。
