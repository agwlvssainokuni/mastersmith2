# Security Requirements — U3 管理画面のアクセス制御（u3-access-control）

U3（管理者のみの API の保護と、アクセス拒否の出来事）の安全の要件。判定の決まりそのものは Functional Design の U3 の決まり（BR1〜BR3）が正本で、本書はそれを満たすことの確かめ方と、U1・U2 の要件との関係を定める。

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR3.1 | /api/admin そのものと /api/admin/ の下は管理者のみとし、未ログインは 401、管理者でなければ 403、管理者は受け付ける。判定はサーバー側で行い、画面の表示に頼らない | サーバー側のテスト（401／403／200）。画面を介さずに API を呼ぶテストを含む | FR8.1、FR8.2、U3 の決まり 1.1・2.1〜2.3・2.6、TP |
| NFR3.2 | /api/ の下は既定でログインを求め、公開するのは明示した一覧（問題の種類の説明ページ、ログイン、トークンの更新、ログアウト）だけとする | 一覧にない API がログインなしで 401 になることをテストで確かめる。公開の一覧の変更はレビューで確かめる | U3 の決まり 1.2・1.3 |
| NFR3.3 | 正規化されていないパス（エンコードされた区切り、`;`、`..`、`//`）は判定の前に拒否し、大文字・小文字を区別し、末尾のスラッシュで判定を変えない。フレームワークの既定の防御（要求のパスの検査）を外さない | テストで次の応答を確かめる: 管理者でない利用者の `/api/admin`・`/api/admin/` は 403。`/api/admin/..;/` やエンコードされた区切りを含むパスは、判定の前に 400。`/API/admin/...`（大文字）は管理者のみとして扱わず、ログイン必須の既定で判定する（ログインしていれば 404、していなければ 401） | U3 の決まり 1.6 |
| NFR3.4 | 管理者でない利用者には、/api/admin/ の下の存在しない API も 403 を返し、API の有無を明かさない | テスト | U3 の決まり 2.5 |
| NFR3.5 | 管理者かどうかは要求ごとに内部DBから読んだ値で判断し、画面から送られた値やトークンの中身を信用しない | テスト（管理者フラグを外した直後の要求が 403 になる） | U3 の決まり 2.4、U2 の決まり 4.5 |
| NFR3.6 | 401／403 の応答は、U1 の共通の組み立ての仕組みで、ほかのエラー応答と同じ形（type・code・traceId）で返し、内部の情報を載せない | テスト | U3 の決まり 3.6、U1 の決まり 5.1・5.4 |
| NFR3.7 | アクセス拒否の出来事に、アクセストークンの値・パスワードなどの秘密情報を載せない。接続元IP は、U1 の決まり 5.10 と同じく転送元のヘッダーを既定で信頼しない | テスト | NFR3、U3 の決まり 3.4 |
| NFR3.8 | /api/ の外で応答するのは、画面の配信と /actuator/health だけとする | テスト（health 以外の Actuator に届かない） | U3 の決まり 1.5、U1 の NFR3.5 |

## U2 の要件で扱うもの

トークンの検証、パスワード、Cookie と CSRF 対策は U2 の要件（NFR2・NFR4・NFR5 の詳細）で扱う。

## 脅威の考慮（U3 の範囲）

| 脅威 | 例 | 対応する要件 |
|---|---|---|
| 権限昇格 | 画面を介さない管理 API の呼び出し、パスの細工による判定の回り込み、管理者フラグの偽装 | NFR3.1、NFR3.3、NFR3.5 |
| 情報漏えい | 管理 API の有無の推測、エラー応答からの内部情報 | NFR3.4、NFR3.6 |
| 否認 | 管理画面へのアクセス拒否が追えない | アクセス拒否の出来事（U3 の決まり 3.1・3.2）と監査ログ（U4） |
