# Functional Design の質問 — u6-registration-ui

単位 U6（`aidlc/spaces/default/intents/260925-user-management/inception/units-generation/unit-of-work.md`、種類 ui）の機能設計のための質問です。U6 は主に受け持つストーリーを持たず、US3.2 の画面の受け入れ基準と共通の決まり CR1・CR6 の画面の部分を受け持ちます（`unit-of-work-story-map.md`）。契約は C6（受ける側）・C9（受ける側）（`aidlc/spaces/default/intents/260925-user-management/inception/contract-design/contract-summary.md`）。画面は S2（`inception/refined-mockups/mockups.md`・`interaction-spec.md` の 5節・`design-system-mapping.md`・`accessibility-checklist.md`）。依存する単位の機能設計 `construction/u3-invitation/functional-design/`・`construction/u4-display-foundation/functional-design/`（W8・W9・3.4節）と、U2 の氏名とパスワードの決まり（`construction/u2-user-preferences/functional-design/rules.md` の BR1・BR4.1）、既存のコード `frontend/src/app/routing/decideRoute.ts`・`frontend/src/app/layout/`・`frontend/src/shared/api-client/apiClient.ts`（`AUTH_API_PATHS`）・`frontend/src/shared/api-client/apiError.ts`・`frontend/src/features/auth/`（ログインの画面・`authSession.ts` の `logout`）・`backend/src/main/java/cherry/mastersmith/common/error/web/GlobalExceptionHandler.java` を確かめました。make-you-chic-ui（`vendor/make-you-chic-ui`）は変更しません。

ui の単位のため、成果物は `functional-spec.md`（画面の流れと状態の移り変わりの正本）・`frontend-components.md`・`traceability.json` です（`entities.md`・`rules.md` は作りません）。

## 設計の要点（案）

上流の決定とコードの確認から導ける、この単位の機能設計の見通しです。質問の答えで決まる点は（Qn）と書きます。

1. **置き場と登録**: 機能 `frontend/src/features/registration/`（featureId `registration`）を新しく置き、機能の登録で画面 `/register` を `layout: 'STANDALONE'`・`access: 'PUBLIC'`（role なし）として足す。画面の部品は遅延読み込みにする（既存の `features/auth/registration.ts` と同じ形）。サイドバーとユーザーメニューの項目は足さない。
2. **画面の枠**: 既存の `StandaloneLayout` の中に make-you-chic-ui の Card を置き、アプリ名と見出し（h1「登録を完了する」）を持つ。既存の `LoginLayout` は見出しが「ログイン」に固定のため使わず、U4 の `LoginLayout` も変えない。幅は中央の 480px 前後、768px 未満は1列に積む（`interaction-spec.md` の 5節）。
3. **トークンの取り出し**: 招待のリンク `https://<ベース URL>/register#token=<トークン>`（契約 C6）の `location.hash` から `token` の値を取り出す。値が無い・空のときは API を呼ばずに「リンクが使えない」の表示にする。トークンの形（長さ・文字）は画面では確かめない（形の誤りもサーバーが同じ 404 にする、U3 の BR3）。取り出した後のアドレス欄の扱いは（Q2）。
4. **API の呼び方**: `features/registration/` の API の関数から既存の ApiClient（`apiRequest`）で `POST /api/registration/verify`・`POST /api/registration/complete` を JSON の本文で呼ぶ。トークンは本文にだけ入れ、URL のパス・問い合わせに入れない（契約 C6）。U4 のレビューの R-01 の直しにより、この2つのパスは ApiClient の「トークンを付けず、401 での更新と送り直しもしない公開の API のパス」に入る前提とする。`Accept-Language` は U4 の ApiClient が画面の言語で付ける（W12）。
5. **状態の移り変わり**: `verifying`（リンクの確かめ中）→ `ready`（入力できる）・`unavailable`（リンクが使えない）・`loadFailed`（読み込めない）。`ready` → `submitting`（送信中）→ `completed`（ログインの画面へ移る）・`ready`（入力の誤りを項目に出す）・`unavailable`（完了の時点で使えない）・`submitFailed`（送れない、入力は残す）。ログインしたままリンクを開いたときの状態は（Q1）。`functional-spec.md` に状態の図と文字の代わりの説明を置く。
6. **確かめの結果の振り分け**: 200 は `ready`。404 `REGISTRATION_LINK_INVALID` は理由によらず `unavailable`（フォームを出さない、AC3.2.2・NFR3）。それ以外の状態コードと通信の失敗は `loadFailed` とし、`role="alert"` で「読み込めませんでした。しばらくしてから、もう一度お試しください」と「もう一度読み込む」ボタン（同じトークンで確かめをやり直す）を出す。通信の失敗を「リンクが使えない」と見せない（使えるリンクを捨てさせないため）。後の段で公開の API の回数の制限が入ったとき（NFR 要件の持ち主）の拒否もこの扱いに入る。
7. **開いた時点の表示の設定（W8）**: 確かめ中と「使えない」の表示は、その時点の画面の言語（ブラウザに保存された言語、無ければブラウザの言語設定）で出す（招待の言語はまだ分からないため）。確かめが通ったら、招待の言語を `setLanguage` で当てる。テーマと文字の大きさはブラウザに保存された値のまま表示し（FR4.3、AC3.2.1）、フォームの初期値は、氏名がメールアドレス・言語が招待の言語・テーマが system・文字の大きさが md とする（FR4.2）。表示とフォームの初期値の食い違いは、選んだ時点で画面に当てる形で扱う（refined-mockups の Q3 A、承認済み）。
8. **選んだ時点の反映**: テーマを選んだら `setPreview(theme)`、文字の大きさを選んだら `setPreview(undefined, fontSize)` とし、選んだ軸だけを画面に当てる（まだ選んでいない軸はブラウザの値の表示のまま）。「言語」を選んだら `setLanguage` で画面の言語を切り替える（文言・`<html lang>`・以降の要求の言語がそろう、CR1.2・CR1.3）。選んだ後もフォーカスは選んだラジオのまま（`accessibility-checklist.md` の 2節）。テーマ system を選んで見せている間も OS の切り替えに追従する（U4 の D4）。
9. **画面の側の入力の確かめ**: 送信のときに、サーバーと同じ決まりを画面でも確かめ、項目の下に文字で出す（CR6.1）。氏名は前後の White_Space を除いた後に 1〜254 コードポイントで、内側に Cc・Cf の文字が無いこと（空白だけは空として「氏名を入力してください」、U2 の BR1.1〜BR1.4）。パスワードは 12 コードポイント以上（入力の前に「12 文字以上」と案内、CR6.2）、UTF-8 で 72 バイトを超えたら「長すぎます（半角で 72 文字、全角でおよそ 24 文字まで）」（refined-mockups の Q6 B）、2回の入力が文字の並びとして完全に一致すること。誤りがあれば送らず、最初の誤りの項目にフォーカスを移し、入れた値（パスワードを含む）は消さない。判定はサーバーが正で、画面の確かめはその代わりにしない（`team.md`）。サーバーの 400 の扱いは（Q3）。
10. **確かめの関数の置き場**: パスワードの規則（コードポイントの数と UTF-8 のバイト数、2回の一致）と氏名の決まりは、React に触れない純粋な関数として `frontend/src/shared/validation/`（新しい）に置き、U7（パスワードの変更・プリファレンスの氏名）も同じ関数を使う。性質ベースのテスト（fast-check、失敗時の種を記録）の対象にする（`team.md`）。U6 と U7 は同じ B5 で作るため、置き場と形をこの単位で決め、U7 の機能設計はこれを使う。
11. **送信**: 送信の間は「登録を完了する」を押せなくし、文言を「登録しています」にして `aria-busy` を付ける（CR6.3、二重の送信を防ぐ）。送る値は、トークン・入力した氏名（前後の空白の除去はサーバーが行う）・パスワード・確かめのパスワード・選んだ言語・テーマ・文字の大きさ（契約 C6 の CompleteRequest）。
12. **完了の後（W8・W9）**: 204 を受けたら、(1) 選んだ3つを `saveBrowserDisplaySettings` で保存し（見せ方は捨てられる、AC3.2.18）、(2) 確かめで受けた招待のメールアドレスを `handOffToLogin` で渡し（URL に載せない、AC3.2.17）、(3) `/login` へ履歴を置き換えて移る（戻るで使い終えたリンクの画面に戻らないため）。自動ではログインしない（FR4.7、AC3.2.5）。完了の知らせ（Alert）はログインの画面が出す（U4 の W9）。
13. **完了の時点の失敗**: 404 `REGISTRATION_LINK_INVALID`（期限が切れた・同時に完了された・同じメールアドレスの利用者がいる など）は `unavailable` に移り、フォームと入れた値（パスワードを含む）を捨てる（`mockups.md` の S2 の状態の表、AC3.2.11）。通信の失敗と 5xx は `submitFailed` として、フォームの上に `role="alert"` で「登録できませんでした。しばらくしてから、もう一度お試しください」を出し、入れた値を残して送り直せるようにする（CR6.4）。
14. **離れるとき**: 完了せずに画面を離れる（部品が外れる）ときは `clearPreview` を呼び、言語とテーマ・文字の大きさの見せ方をやめる（W8 の 5）。完了のときは `saveBrowserDisplaySettings` が見せ方を捨てているため、続く `clearPreview` は何も変えない。
15. **項目の作り**: ログインに使うメールアドレスは、見える label 付きの読み取り専用の入力（`readOnly`、`type="email"`、`autocomplete="username"`）で示す（AC3.2.16）。`disabled` にしない（パスワードの管理の道具が組で保存できるように、フォーカスで読めるように）。パスワードの2つの項目は `autocomplete="new-password"`（CR6.9）。言語・テーマ・文字の大きさは `fieldset`・`legend` ごとの RadioGroup で、言語の選択肢は U4 の `LANGUAGE_NAMES` と `lang` 属性（CR6.6）、テーマ・文字の大きさの文言は U4 の骨組みの文言の鍵 `display.theme.*`・`display.fontSize.*` を使う。項目の下の案内「選ぶとこの画面の言語が切り替わります」「テーマと文字の大きさは選ぶと画面に反映されます」を置く（`mockups.md` の S2）。
16. **文言**: 新しい文言は機能の登録の `messages` に ja・en の両方で置き、鍵は `registration.` で始める（NFR8、`design-system-mapping.md` の 4節）。サーバーの Problem Details の `detail` は画面に出さず、画面は `code` と状態コードで分けて自分の文言を出す（既存の画面と同じ扱い、`frontend/src/features/dsl/failureMessage.ts`）。
17. **秘密と個人情報**: トークンはブラウザの保存（localStorage）に置かず、画面のログ（`console`）・画面の文言・エラーの表示に出さない。パスワードの値は送信の後に持ち続けない。メールアドレスの受け渡しは U4 の画面の中のメモリだけ（U4 の D13）。`project.md` の Forbidden（招待のトークンをログ・エラー応答に含めない）を画面の側でも守る。
18. **テスト**: 画面部品のテスト（Vitest・Testing Library・user-event、画面部品ごとに vitest-axe を1件、説明文は英語、対象と同じ場所の `*.test.tsx`）で、AC3.2.1・AC3.2.2（画面の表示）・AC3.2.4（画面の確かめの境界: 11・12 コードポイント、72・73 バイト、絵文字 11・12 文字、空、不一致）・AC3.2.5（ログインの画面へ移り、自動でログインしない）・AC3.2.9（氏名の 254・255 コードポイント、空白だけ）・AC3.2.10（誤りの後に同じ画面から送り直せる）・AC3.2.16・AC3.2.17（受け渡しを呼ぶ、URL にメールアドレスが載らない）・AC3.2.18（保存する値）と CR1.2・CR1.3・CR6.1〜CR6.4・CR6.6・CR6.9 を確かめる。API は `fetch` の差し替えで作り、U4 の口は本物（`renderWithProviders`）で動かす。サーバー側の受け入れ基準（AC3.2.3・AC3.2.6〜AC3.2.8・AC3.2.11〜AC3.2.15）は U3 が確かめる。フロントエンドのカバレッジの下限（行 80%・分岐 70%）を守る。
19. **E2E-1（招待から登録の完了まで）**: `frontend/e2e/` に Playwright で1本足し、`./gradlew e2eTest` で動かす（`verify` と CI の外、`team.md`）。流れはストーリーの E2E-1 のとおりで、管理者のログインと招待を自分で行い、実行ごとに重ならないメールアドレスを使う。招待メールのリンクを取り出す方法は infrastructure-design の持ち主のまま（ストーリーの E2E の「後の段で決めること」）で、この段では流れと確かめる点だけを書く。
20. **既存への影響**: 新しい機能の追加だけで、既存の画面・骨組みは変えない（U4 の口と受け渡しを使う側）。ApiClient の公開のパスの追加は U4 の R-01 の直しで行う（この単位では前提として書き、U4 の変更の一部として確かめる）。

## Q1. ログインしたまま招待のリンクを開いたとき、登録の完了の画面をどう扱いますか？

理由: 画面 `/register` は PUBLIC のため、今の振り分け（`frontend/src/app/routing/decideRoute.ts`）ではログインしたままでも表示されます。U4 のレビューの R-01 の直しで登録の完了の要求にトークンは付かなくなりますが、ログインしたままでは表示の設定の土台が「ログインの後」のままのため、完了の後のログインの画面はログイン中の利用者の表示の設定で表示され、選んだ3つ（AC3.2.18）では表示されません（U4 の `functional-spec.md` の 5節「User のまま `saveBrowserDisplaySettings` を呼んだときはブラウザの保存の値だけを書き換える」）。また、ログインの画面でログインすると前の利用者のセッションは置き換わります。上流ではこの場合の振る舞いが決まっていません。管理者が自分で出した招待のリンクを同じブラウザで開いて確かめる場面が考えられます。

A. リンクを確かめる前に、ログイン中であることと「登録を続けるには、ログアウトしてください」の案内を出し、「ログアウトして続ける」と「ホームへ戻る」のボタンを置く。「ログアウトして続ける」を押したら、既存のログアウト（リフレッシュトークンのサーバー側の無効化を含む）を行ってからリンクを確かめる（AuthUi の `logout` を登録の完了の機能から呼ぶ新しい依存が1本増える）
B. 尋ねずに、画面を開いた時点でログアウトしてからリンクを確かめる（手数は増えないが、同じブラウザで確かめた管理者のセッションが黙って終わる）
C. ログインしたまま画面を出し、登録を完了できるようにする（何もしない。完了の後のログインの画面はログイン中の利用者の表示の設定で表示され、この場合は AC3.2.18 の見た目にならない）
X. Other (please specify)

[Answer]: A

## Q2. トークンを取り出した後、アドレス欄の `#token=...` をどう扱いますか？

理由: フラグメントはサーバーにも Referer にも送られません（契約 C6 の Q1: A でこの形にした理由）が、画面を開いている間はアドレス欄と閲覧の履歴にトークンが残ります（肩越しの覗き見・画面の共有・履歴の同期）。トークンは1回だけ有効で、完了するまで（最長で有効期限まで）使えます。消すと、入力の途中で読み込み直したときに続けられなくなります。上流ではこの扱いが決まっていません。

A. そのまま残す（読み込み直しても同じリンクとして開き直せる。トークンは完了するまでアドレス欄と履歴に残る）

## Q3. 完了の要求が 400 `VALIDATION_FAILED` で拒否されたとき、画面にどう出しますか？

理由: 今の共通の変換（`backend/src/main/java/cherry/mastersmith/common/error/web/GlobalExceptionHandler.java`）の `VALIDATION_FAILED` は、どの項目が誤りかを応答に持ちません。契約 C6 も項目の一覧の形を決めていません（U3 の BR4.1 は「項目ごと」としていますが、応答の形は既存のまま）。CR6.1 は「送信で誤りが返ったら最初の誤りの項目にフォーカスを移す」としています。設計の要点 9 のとおり画面で同じ決まりを先に確かめるため、サーバーの 400 は画面の確かめをすり抜けた場合（空白の文字の種類の判定の差など）に限られる見込みです。なお画面はサーバーの説明文（`detail`）を出さないため（設計の要点 16）、CR1 の確かめ方「11 文字のパスワードで登録を完了しようとするとエラーの説明文が en」は、画面の言語 en の文言で確かめ、サーバーの説明文の言語は U3（`Accept-Language` の en）と U4（ApiClient が画面の言語を送る）のテストで確かめる形になります。

A. サーバーの 400 は項目に結び付けず、フォームの上に `role="alert"` で「入力を確かめてください。直しても登録できないときは、招待した管理者に連絡してください」の趣旨の誤りを出し、入れた値を残す（契約とサーバーは変えない）
