# NFR Requirements — Questions（U6 登録の完了の画面 / u6-registration-ui）

U6 は、招待メールのリンクから開く登録の完了の画面（`/register`）を受け持つ画面の単位です（種類 ui のため、作る成果物は性能・セキュリティ・技術の選択・traceability の4つです。拡張性・信頼性・観測性は service の単位だけ）。画面の単位の非機能の多く（WCAG 2.1 AA・実際のブラウザのアクセシビリティの検査・ブラウザの保存・公開の API にトークンを付けないこと・CSP）は U4 の NFR 要件で決まり、API の時間と回数の制限は U3 の NFR 要件で決まっています。招待のトークンの扱い（D1〜D3）・二重の送信の防止（W8）・E2E-1 の流れ（W13）も承認済みの機能設計で決まっています。そのため、まず NFR の要点（案）を示し、上流から決まらない2点（リンクを開いてからフォームが出るまでの時間の目標、実際のブラウザのアクセシビリティの検査でフォームの状態をどう出すか）だけを質問にします。狭い幅での崩れの確かめ方は、U5 の質問で出た画面の3つ（U5〜U7）に共通する依頼者の決定で決まったため、「決まっていること」に置きます。

## NFR の要点（案）

1. **性能（リンクを開いてからフォームが出るまで）**: 画面は機能の登録の遅延読み込みで、開いたときに画面の塊を読み、リンクの確かめ（`POST /api/registration/verify`、U3 の NFR6.3 で同時 10 件の p95 1 秒）の答えを待ってフォームを出す（W4・W5）。確かめの答えが返るまでは「確かめています」を出す。画面の数値の目標をどう置くかは Q1 で決める。
2. **性能（登録の完了）**: 完了の API（`POST /api/registration/complete`、U3 の NFR6.4 で同時 10 件の p95 1 秒）の時間は U3 の目標と Performance Validation の k6 で押さえる。画面は送信の間「登録しています」を出し、待ちに上限を置かない（応答か通信の失敗まで待つ。既存の ApiClient のまま）。
3. **性能（初回の JavaScript）**: U6 の画面は遅延読み込みの塊に入り、入口の JavaScript を増やさない。U4 の NFR6.3 の目安（初回の読み込みの JavaScript は gzip で 500KB 以内、超えたら警告で統合は止めない）をそのまま当て、B5 のコード生成で、登録の完了の画面の塊が入口のファイルと分かれていることと、その大きさを記録する。
4. **セキュリティ（招待のトークンの画面の側の扱い）**: トークンはフラグメントの `token` だけから取り、描画の確定の後に置き換えの移動でアドレス欄から消し、画面のメモリだけに持ち、要求の本文だけで送る（D1〜D3、W2）。ブラウザの保存・URL のパスと問い合わせ・画面の文言・エラーの表示・`console` に出さない（`project.md` の Forbidden、要件 NFR1）。確かめ方は次のとおり。(a) 画面部品のテストで、描画の後の URL にフラグメントが無く、localStorage・sessionStorage のどの鍵にもトークンが無く、確かめの要求の本文にだけトークンがあること（`frontend-components.md` の 8節）。(b) 画面部品のテストで `console` の各関数（`log`・`info`・`warn`・`error`・`debug`）を見張り、開く・確かめの失敗・完了の失敗のどの流れでも呼ばれないこと（呼ばれたときは引数にトークンが無いことも見る）。(c) E2E-1 で、リンクを開いた後のアドレス欄にフラグメント（`#token=`）が無いこと（W13 の4）。
5. **セキュリティ（リファラー）**: フラグメント（`#` の後）は、ブラウザの決まりで `Referer` に載らない。加えて、アプリはすでに `Referrer-Policy: same-origin` を付け（`SecurityConfig`）、CSP（`default-src 'self'` ほか）で外部の読み込みを許していない。登録の完了の画面に外部へのリンクは無い（「ログインの画面へ」は同じオリジンの `/login`）。そのため、リファラーのための新しい手当ては足さない。確かめは、CSP と `Referrer-Policy` の設定に差分が無いこと（U4 の NFR9.4 のまま）と、要点 4 のフラグメントの消去で足りるとする。
6. **セキュリティ（公開の API とトークンを付けないこと）**: 確かめ・完了の API にはアクセストークンを付けず、401 でも更新と送り直しをしない。これは U4 の ApiClient の公開の API のパス（U4 の NFR9.1）が持ち、U6 は ApiClient を変えない。サーバー側の公開の範囲（2つの POST だけ）と認可は U3 のサーバー側のテスト（U3 の NFR4.2）で確かめ、画面の側の扱いをその代わりにしない（要件 NFR4、`team.md`）。
7. **セキュリティ（列挙の防止の画面の側）**: 確かめ・完了の 404 `REGISTRATION_LINK_INVALID` は、理由によらず同じ「このリンクは使えません…」の表示にし、サーバーの `detail` を画面に出さない（D5・D10、要件 NFR3）。画面部品のテストで、理由の違う 404 の応答（`detail` の文字を変えたもの）で表示が同じで、`detail` の文字が画面に出ないことを確かめる。
8. **セキュリティ（回数の制限）**: 公開の2つの API に回数の制限は設けない（U3 の NFR4.5、依頼者の決定 Q2 A）。後の段で前段に回数の制限が入ったときの拒否（例: 429）は、確かめでは「読み込めませんでした」と「もう一度読み込む」、完了では「登録できませんでした」の扱い（5節の表の「それ以外の応答」）に入り、「リンクが使えない」とは見せない（D5）。U6 で新しい手当ては足さない。
9. **セキュリティ（パスワードの入力）**: パスワードの2つの欄は `type="password"`・`autocomplete="new-password"`。画面の確かめ（12 コードポイント以上・72 バイト以下・2回の一致）はサーバーと同じ決まりで行うが、判定はサーバーが正で、画面の確かめはその代わりにしない（D8、U2 の BR1.x、`team.md`）。パスワードは入力の欄と送信の本文だけに持ち、ブラウザの保存・URL・`console` に出さず、画面を離れると部品とともに捨てる（8節）。失敗のときに値を残すのは画面のメモリの中だけ（D9）。確かめ方は `frontend-components.md` の 8節の境界のテストと、要点 4 の (a)(b) と同じ見張りで、localStorage・sessionStorage にパスワードが無いことも見る。
10. **セキュリティ（二重の送信の防止）**: 送信の間は、make-you-chic-ui の Button の `loading`（`aria-disabled`・`aria-busy`）に加えて、フック側でも送信の操作を無視し、氏名・パスワードの欄は `readOnly`、ラジオは選んでも値を変えない（W8 の1）。画面部品のテストで、送信の答えを返さない間にボタンを2回押す・Enter キーで送る・ラジオを選ぶの操作をしても、完了の要求が1回だけで、送った本文の値が変わらないことを確かめる（`frontend-components.md` の 8節）。「ログアウトして続ける」も同じく、ログアウトの要求が1回だけであることを確かめる。サーバーの側でも、同じトークンでの2回目の完了は U3 の決まり（使い終えた招待は有効でなく、404 `REGISTRATION_LINK_INVALID` になる。U3 の BR7.5 と `team.md` の必須テスト）で拒否されるため、画面の防止は利用の体験のためのもので、サーバーの守りの代わりにしない。
11. **セキュリティ（招待のメールアドレス）**: メールアドレスは読み取り専用の欄と、U4 の受け渡し（メモリだけ・1回、U4 の NFR2.1）だけに持ち、URL・ブラウザの保存・`console` に出さない（要件 NFR2、D11）。確かめ方は `frontend-components.md` の 8節の完了の 204 のテスト（URL にメールアドレスが無い）と、要点 4 の (b) の見張り。
12. **セキュリティ（CSP と依存）**: CSP は変えず、埋め込みのスクリプト・スタイルを足さない（U4 の NFR9.4 のまま）。U6 が足す実行時の依存は無い。make-you-chic-ui の新しい版（RadioGroup の `legend`・選択肢ごとの `lang`、Button の `loading`）は B4 の固定先の更新（U4 の NFR9.7、専用のコミットで前後のハッシュを記録）に頼り、U6 の B5 はその後。`frontend/src/shared/validation/` は自前のコードで、新しい依存を持たない。
13. **アクセシビリティ**: 目標は WCAG 2.1 AA（U4 の NFR7.1）。画面部品ごと（`RegistrationPage`・`RegistrationStatus`・`RegistrationUnavailable`・`RegistrationLoggedInNotice`・`RegistrationForm`）に vitest-axe の検査を1件入れ、違反 0 件とする（要件 NFR7、`team.md`）。言語の選択肢は「日本語」「English」に `lang` を付け、切り替えた後もフォーカスを選んだラジオに残し、`<html lang>` を変える（W6、U4 の NFR7.4）。U4 の NFR7.3 の実際のブラウザの検査（テーマ2×文字の大きさ3の6組と、ブランドカラー4×テーマ2の8組で、axe-core の違反 0 件と横のはみ出しが無いこと）に、B5 で登録の完了の画面を足す（U4 の NFR7.5）。どの状態を検査するか（フォームを出す手段）は Q2 で決める。狭い幅は、U5〜U7 に共通する依頼者の決定のとおり、同じ検査に表示の幅 375px を1つ足し、テーマ2×文字の大きさ3の6組で横のはみ出しが無いことと axe-core の違反 0 件を確かめる（B5 で登録の完了の画面に当てる。Q2 で検査する状態ごと）。
14. **多言語**: U6 が足す文言（`registration.` で始まる鍵）は ja・en の両方を用意し、鍵をそろえる（要件 NFR8、機能設計の 7節）。言語の名前は U4 の `LANGUAGE_NAMES`（訳さない、U4 の NFR8.2）。画面部品のテストで、足した鍵が ja・en の両方にあり空でないこと、en の招待・en を選んだときに文言・画面の確かめの誤り・`<html lang>`・完了の要求の `Accept-Language` が en になることを確かめる（機能設計の 9節の CR1 の読み替え）。
15. **テストとカバレッジ**: フロントエンドのカバレッジの下限（行 80%・分岐 70%）を守り、U6 のために計測の除外を増やさない（要件 NFR9、`team.md`）。性質ベースのテスト（fast-check、失敗時の種を記録）を `shared/validation` の関数（`countCodePoints`・`utf8ByteLength`・`trimDisplayName`・`validateDisplayName`・`validateNewPassword`）に当てる（機能設計の 9節）。既存の画面のテストと既存の E2E（010〜040）が通り続けることを確かめる。
16. **E2E-1（招待から登録の完了まで）**: この Intent の代表の流れの1本として U6 が持ち、`frontend/e2e/` に足して `./gradlew e2eTest` で動かす（`verify` と CI の外、W13、`team.md`）。前のテストの状態に頼らず、管理者のログインと招待を自分で行う。流れ全体の時間の目標は置かない（Playwright の既定の時間切れのまま。流れの成否だけを見る）。招待するメールアドレスは実行ごとに重ならない値で、既存の初期管理者と同じく予約済みのドメイン（`example.com`）を使い、実在の宛先へ送らない。メールは E2E が起動したアプリの手元の受け手だけに送り、外部の SMTP へ送らない（`team.md` の Deployment、`project.md` の Forbidden）。招待メールのリンクの取り出し方（手元の受け手の API から読むなど。JVM の中の受け手は使えない）と、E2E の WAR への SMTP の設定の渡し方は infrastructure-design の持ち主のまま。E2E のトークン・パスワードは実行ごとの一時の内部DB の中の使い捨ての値で、失敗のときに残るトレース（`trace: 'retain-on-failure'`）と報告は手元だけに置かれ、`.gitignore` の対象のためコミットされない。
17. **traceability の見込み**: U6 に当たる要件の非機能は NFR1（要点 4・5）・NFR2（要点 11）・NFR3（要点 7）・NFR6（要点 1〜3。Q1）・NFR7（要点 13。Q2 と狭い幅の共通の決定）・NFR8（要点 14）・NFR9（要点 9・10・12・15・16）。当たる ID の無い画面の側の要件（二重の送信の防止・パスワードの画面の側の扱い・依存）は、U4 の前例と同じく NFR9 の枝番に寄せる。NFR4（サーバー側の認可は U3。画面の側の扱いは U4 の NFR9.1）・NFR5・NFR10・NFR11（手元の受け手を見る手順は U1・U3 の持ち主。E2E-1 の受け手の手段は infrastructure-design）は `N/A` とし、理由を書く。

## Q1. 招待のリンクを開いてから登録のフォームが出るまでの時間の目標を、どうしますか？

理由: 要件 NFR6 は API の応答時間だけを決めており、画面の時間の目標はありません。U4 では、ログインの画面が出るまでを「手元の PC のブラウザで、キャッシュが空の状態で 2 秒以内。E2E の中で5回測って記録し、統合の関門にはしない」としました（U4 の NFR6.1）。登録の完了の画面は、それに加えて遅延読み込みの画面の塊とリンクの確かめ（p95 1 秒）を待つため、ログインの画面より待ちが長くなりえます。リンクの確かめは内部DB を変えず監査もしないため（U3 の BR7.1）、同じリンクを完了の前に何度開いても状態は変わらず、E2E-1 の中で繰り返し測れます。U5 の質問で、画面の3つ（U5〜U7）に共通して「画面の時間の目標を置き、実際のブラウザで5回ずつ測って記録し、統合の関門にはしない」と決まったため（U5 は一覧 2 秒・次ページ 1.5 秒）、B と C はこの決定に沿った選択肢で、A はこの決定と合いません。

- A. 画面の数値の目標は置かない。API の目標（確かめ p95 1 秒）で押さえ、画面の側は「確かめています」の表示を部品のテストで確かめる
- B. 目標を置く。手元の PC のブラウザで、キャッシュが空の新しいブラウザのコンテキストで招待のリンクを開いてから、登録のフォーム（メールアドレスの欄）が出るまで 2 秒以内。E2E-1 の中で、完了の前に同じリンクを新しいコンテキストで5回開いて測り、Build and Test の結果に記録する。統合の関門にはしない（U4 の NFR6.1 と同じ扱いで、U5〜U7 に共通する「目標を置き、5回ずつ測って記録する」決定に沿う）（推奨）
- C. B に加えて、「登録を完了する」を押してからログインの画面（登録が終わった旨の案内）が出るまでも 2 秒以内を目標にし、E2E-1 の中で1回測って記録する（完了は1回しかできないため1回だけ）。統合の関門にはしない

## Q2. 実際のブラウザのアクセシビリティの検査（U4 の NFR7.3）で、登録の完了の画面のどの状態を、どう出して検査しますか？

理由: U4 の NFR7.5 で、B5 で登録の完了の画面を実際のブラウザの検査に足すことが決まっています。ただし、フォームの状態を出すには有効な招待のトークンが要ります。本物のトークンを得るには、管理者でログインして招待し、手元の受け手から招待メールのリンクを取り出す必要があり、その手段は infrastructure-design の持ち主でまだ決まっていません（E2E-1 と同じ手段に頼ることになる）。検査は描画と色の確かめで、サーバーの動きの確かめではないため、Playwright の要求の差し替え（`page.route`）で確かめの API の答えを返してフォームを出す方法もあります（アプリの CSP とコードは変えない。検査のブラウザのコンテキストの中だけ）。「リンクが使えない」の状態は、フラグメントの無い `/register` を開けば本物のまま出せます。確かめ中・読み込めない・ログイン中の案内の状態は、vitest-axe（構造）でも検査されます（要点 13）。

- A. 本物の流れで出す。管理者でログインして招待し、E2E-1 と同じ手段で受け手からリンクを取り出し、フォームの状態を検査する。「リンクが使えない」の状態も検査する。受け手の手段（infrastructure-design）に頼り、検査のファイルは流れの E2E と分ける
- B. 要求の差し替えで出す。確かめの API（`POST /api/registration/verify`）だけを検査のブラウザのコンテキストの中で差し替えて 200（`example.com` のメールアドレス・言語 `ja`）を返し、フォームの状態を検査する。「リンクが使えない」の状態は、フラグメントの無い `/register` を本物のまま開いて検査する。受け手に頼らず、本物の流れは E2E-1 が確かめる。どちらの状態も U4 の NFR7.3 の組（6組と8組）と、狭い幅 375px の6組（共通の決定）で検査する（推奨）
- C. 「リンクが使えない」の状態だけを実際のブラウザで検査し、フォームの状態は vitest-axe（構造）だけにする（フォームのコントラストと崩れは実際のブラウザでは確かめない）
