# Security Requirements — U6 登録の完了の画面（u6-registration-ui）

U6 のセキュリティの要件です。U6 は画面の単位で、サーバー側の認可を持ちません。ここでは、招待のトークンの画面の側の扱い、招待のメールアドレス、列挙の防止の画面の側、公開の API、回数の制限が入ったときの扱い、パスワードの入力、二重の送信の防止、CSP を扱います。答えは `nfr-requirements-questions.md`（Q1: B、Q2: B、Consolidated Summary Confirmation: Looks correct）です。

出典の略号:
- NFR・FR は `aidlc/spaces/default/intents/260925-user-management/inception/requirements-analysis/requirements.md`
- D・W と「n節」は、この単位の `construction/u6-registration-ui/functional-design/functional-spec.md`
- 「部品 n節」は、同じフォルダの `frontend-components.md` の n節
- 「要点 n」は、この段の `nfr-requirements-questions.md` の「NFR の要点（案）」の番号

枝番はこの単位の中で振ります。ほかの要件の置き場は `performance-requirements.md` の冒頭の表のとおりです。依存とアクセシビリティの検査の要求の差し替えは `tech-stack-decisions.md`（NFR9.6・NFR9.7・NFR7.5）に置きます。

要件に当たる ID が無い画面の側のセキュリティの要件（公開の API・回数の制限・パスワードの入力・二重の送信・CSP）は、NFR9 の枝番（NFR9.1〜NFR9.5）に寄せました。どれもテストで確かめ方を決める要件だからです。U4・U8 が当たる ID の無い要件を NFR9 に寄せた前例と同じ扱いです。

## 前提

- 招待のトークン・メールアドレス・パスワードの扱いは、承認済みの機能設計の D1〜D3・D9・D11 と 8節で決まっています。この文書は、その確かめ方を要件として決めます。
- 招待のトークンを、ログ・監査ログ・トレースの属性・エラー応答に含めません。メールアドレスをアプリのログとエラー応答に含めません（`project.md` の Forbidden）。サーバーの側の漏えいの確かめ（AC3.2.15）は U3 が持ちます。
- サーバー側の公開の範囲（認証なしで呼べるのは `POST /api/registration/verify` と `POST /api/registration/complete` だけ）と認可は、U3 のサーバー側のテスト（U3 の NFR4.2）で確かめます。画面の側の扱いは、その代わりにしません（要件 NFR4、`team.md` の Testing Posture）。
- 公開の2つの API に回数の制限は設けません（U3 の NFR4.5、依頼者の決定）。
- GitHub のリポジトリは公開のため、テストのデータに実在の個人に関する値を使いません（`team.md` の Way of Working）。

## 2. 公開の API・回数の制限・入力・送信・CSP

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR9.1 | 確かめ・完了の呼び出しは U4 の ApiClient（`apiRequest`）を通し、`Authorization` の見出しと `Accept-Language` を呼び出し側で付けない。公開の API のパスにトークンを付けず 401 で更新しない扱いは、U4 の ApiClient（U4 の NFR9.1）が持ち、U6 は ApiClient を変えない | `registrationApi` の単体テストで、要求のパス・メソッド・本文の形と、呼び出し側で見出しを付けていないことを見る。ApiClient の扱いは U4 の NFR9.1 のテスト | 要点 6、部品 3節、U4 の NFR9.1、契約 C6 |
| NFR9.2 | 後の段で前段に回数の制限などが入り、想定外の応答（例: 429）が返っても、確かめでは「読み込めませんでした」と「もう一度読み込む」、完了では「登録できませんでした」の扱いにし、「リンクが使えない」とは見せない。U6 で回数の制限の手当ては足さない | `failureKind` の単体テストに、404 でも 400 でもない応答（例: 429・503）の行を入れ、確かめは読み込み直せる失敗、完了は登録できない失敗に振り分けられることを見る | 要点 8、D5・W4 の3・5節、U3 の NFR4.5 |
| NFR9.3 | パスワードの2つの欄は `type="password"`・`autocomplete="new-password"` とする。送信の前に画面でもサーバーと同じ決まり（12 コードポイント以上・UTF-8 で 72 バイト以内・2回の一致）を確かめ、誤りがあれば送らない。判定はサーバーが正で、画面の確かめはその代わりにしない。パスワードは入力の欄と送信の本文だけに持ち、ブラウザの保存・URL・`console` に出さず、画面を離れると部品とともに捨てる。失敗のときに値を残すのは画面のメモリの中だけ | 画面部品のテスト（部品 8節の `RegistrationForm`）で、欄の属性と、境界の値（11・12 コードポイント、72・73 バイト、絵文字 11・12 文字、不一致）で送られないことを見る。localStorage・sessionStorage にパスワードが無いことを NFR1.2 と同じテストで見る。サーバーの判定は U3 の BR7.2 のテスト | 要点 9、D8・D9・8節、CR6.9、U3 の BR7.2 |
| NFR9.4 | 二重の送信を防ぐ。送信の間は Button の `loading`（`aria-disabled`・`aria-busy`）に加えてフックでも送信の操作を無視し、氏名・パスワードの欄を `readOnly` にし、ラジオを選んでも値を変えない。「ログアウトして続ける」も、ログアウトの間はもう一度押しても何もしない。画面の防止は利用の体験のためのもので、サーバーの守り（使い終えた招待は 404、U3 の BR7.5）の代わりにしない | 画面部品のテスト（部品 8節の送信の間・ログアウト中）で、完了の要求に答えを返さない間に、ボタンを2回押す・Enter キーで送る・ラジオを選ぶの操作をしても、完了の要求が1回だけで、送った本文の値が変わらないことを見る。ログアウトの要求も1回だけであることを見る | 要点 10、W3・W8、CR6.3 |
| NFR9.5 | CSP を変えず、埋め込みのスクリプト・スタイルを足さない（U4 の NFR9.4 のまま）。画面にサーバーの応答の値を HTML としてそのまま差し込まない（HTML を直接埋め込む書き方は既存のリンタの決まり `react/no-danger` で止める）。アクセシビリティの検査（NFR7.3）のためにアプリの CSP を緩めない | B5 のコード生成で、`application.yaml` の CSP に差分が無いことと、ビルドした `index.html` に埋め込みのスクリプト・スタイルが無いことを確かめる。Build and Test の E2E で、ブラウザのコンソールに CSP の違反が出ないことを記録する | 要点 12、U4 の NFR9.4 |

## 3. 脅威と扱い

| 脅威 | 扱い | 要件 |
|---|---|---|
| トークンがアドレス欄・閲覧の履歴・同期された履歴・画面の写しに残り、別の人に使われる | 取り出したらすぐにフラグメントを消し、メモリだけに持つ。読み込み直しでは使えない | NFR1.1・NFR1.3 |
| トークンがブラウザの保存や開発者ツールのコンソールに残る | ブラウザの保存と `console` に出さない | NFR1.2 |
| トークンがリファラーで外部に漏れる | フラグメントはリファラーに載らない。`Referrer-Policy: same-origin` と CSP を保ち、外部へのリンクと外部の読み込みを置かない | NFR1.4 |
| テストの値やトレースが公開のリポジトリに入る | テストのトークンとパスワードは使い捨て・見本の値。トレースと報告はコミットしない | NFR1.5 |
| 招待のメールアドレスが URL に載り、履歴・リファラー・アクセスログに残る | 受け渡しはメモリだけで、URL に載せない | NFR2.1 |
| 表示の違いから、招待や利用者の有無を推測される | 404 は理由によらず同じ表示で、`detail` を出さない | NFR3.1 |
| 期限切れのアクセストークンが公開の API で 401 を起こし、登録の完了が妨げられる | 公開の API にトークンを付けず、401 で更新しない（U4 の ApiClient） | NFR9.1 |
| 前段の回数の制限の拒否を「リンクが使えない」と見せ、使えるリンクを捨てさせる | 想定外の応答は読み込み直せる失敗・登録できない失敗として扱う | NFR9.2 |
| パスワードがブラウザに残る・画面の確かめだけで弱い値が通る | 保存しない。判定はサーバーが正 | NFR9.3 |
| 二重の送信で同じ招待を2回使おうとして、2回目の失敗の表示が利用者を混乱させる | 画面とフックで要求を1回にする。サーバーでも2回目は拒否される | NFR9.4 |
| 埋め込みのスクリプト・応答の値の差し込みによるスクリプトの実行 | CSP を変えず、HTML に差し込まない | NFR9.5 |
