# Scalability Requirements — U2 利用者のプリファレンスとパスワードの変更（u2-user-preferences）

U2 の拡張性の要件です。アプリは当面1台で、内部DB は組み込みの H2 です（要件の4節の制約、前の Intent の Domain Design の ADR-008）。出典の略号は `performance-requirements.md` と同じ。

## 要件

| ID | 要件 | 確かめ方と持ち主の段 | 出典 |
|---|---|---|---|
| NFR6.7 | 想定の規模（利用者 最大 50 名、同時 10 件の要求）を1台で処理する。U2 の3本の API も、この規模で NFR6.1〜NFR6.4 の目標を満たす | performance-validation の負荷の試験（NFR6.1〜NFR6.4） | NFR6、前 U2 の NFR1.6 |
| NFR5.3 | 内部DB の接続の数の見積もり: プリファレンスの取得・保存と、パスワードの変更の誤り・入力の誤りは要求1件に1本、パスワードの変更の成功は確定の後の監査の記録で2本（NFR5.2）。同時 10 件がすべて成功でも最大 20 本で、接続プールの上限（既定 30、`MASTERSMITH_DB_MAXIMUM_POOL_SIZE`）に収まる。bcrypt の計算の間は接続を持たない（NFR5.1）ため、1本を持つ時間は短い | 見積もりの記録（本書）。実際に尽きないことは NFR5.2 の負荷の試験で確かめる（見積もりだけで済ませない） | NFR5、`project.md` の Corrections |

## データの増え方

| データ | 増え方 | 見積もり | 扱い |
|---|---|---|---|
| 利用者の行 | U2 は列を4つ足すだけで、行の数は増えない（行を作るのは U3 の登録の完了と初期管理者） | 最大 50 行 | 変更なし |
| 利用者の行の大きさ | 氏名（UTF-16 で最大 508）と3つの短い値の列が増える | 1行あたり最大 約 1KB の増え | 変更なし |
| 監査の行 | パスワードの変更の成功と今のパスワードの誤りで1件ずつ。プリファレンスの保存と入力の誤りでは増えない（BR3.5・BR4.1） | 変更は頻度が低く、ログインの監査（1日に利用者あたり数件）に比べて小さい。ただし NFR4.5 のとおり誤りの回数を制限しないため、総当たりを受けると誤りの数だけ増える | 監査の保存期間と削除は既存のまま（`project.md` の DECIDED、監査の共通化は後続の Intent） |
| 監査の列 | target_user_id・target_invitation_id の2列（空を許す整数）を足す | 1行あたり 16 バイト程度の増え | 変更なし |

## 複数台で動かす場合

当面は1台で、内部DB は組み込みの H2 のため複数台では動かしません。複数台にするときは内部DB を共有の DB に替える必要があり、その時点で U2 に次の影響があります（今は作りません）。

- プリファレンスの保存とパスワードの変更は、どちらも内部DB の行の書き換えだけで、アプリのメモリに状態を持たないため、そのまま共有できる（BR3.4 の後勝ちも DB の上で決まる）。
- 今のパスワードの誤りの回数を数えない（NFR4.5）ため、台をまたいだ回数の共有の問題は無い。
