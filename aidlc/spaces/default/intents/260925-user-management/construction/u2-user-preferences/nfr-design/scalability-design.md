# Scalability Design — U2 利用者のプリファレンスとパスワードの変更（u2-user-preferences）

U2 の拡張性の設計です。承認済みの `construction/u2-user-preferences/nfr-requirements/scalability-requirements.md`（NFR6.7・NFR5.3）を満たす作りを決めます。出典の略号は `performance-design.md` と同じ。

## 1. 規模と伸ばし方（NFR6.7）

- 想定の規模（利用者 最大 50 名、同時 10 件の要求）を、アプリ1台・組み込みの H2 で処理する。伸ばし方は、当面は VM・コンテナの資源を上げる縦の拡張だけとする（`project.md` の Deployment。複数台は内部DB を共有の DB に替えるまで作らない）。
- U2 はアプリのメモリに状態を持たない。セッション・キャッシュ・回数の数え上げを置かず、要求ごとに内部DB の1行を読み書きする。そのため、将来内部DB を共有の DB に替えれば、U2 のコードを変えずに複数台で動かせる（プリファレンスの後勝ち・パスワードの条件つきの更新はどちらも DB の上で決まる）。
- 処理の重さはパスワードの変更の bcrypt（CPU）に集まる。CPU を上げると直接効く。bcrypt の間は接続を持たないため、CPU の待ちが接続の不足に広がらない（`performance-design.md` 2節）。

## 2. 接続の数（NFR5.3）

| 操作 | 同時に持つ接続 | 持つ時間 |
|---|---|---|
| プリファレンスの取得・保存 | 1本 | 1行の読み取り・更新の間 |
| パスワードの変更の入力の誤り | 0本 | — |
| パスワードの変更の今のパスワードの誤り | 1本（読み取り）→ 返した後に監査で1本 | どちらも短い |
| パスワードの変更の成功 | 読み取りで1本 → 返す → 更新で1本、確定の後の監査で2本目 | bcrypt の間は0本 |

- 同時 10 件がすべて成功でも最大 20 本で、接続プールの上限（既定 30、`MASTERSMITH_DB_MAXIMUM_POOL_SIZE`）に収まる。ログインなど他の2本の経路と重なったときの余裕は、見積もりで済ませず performance-validation の負荷の試験で確かめる（`reliability-design.md` 5節）。
- 接続プールの設定（上限・借りる待ち 5 秒）は変えない。

## 3. データの増え方

- users は列が増えるだけで行は増えない（1行あたり最大 約 1KB の増え）。audit_events はパスワードの変更の成功と今のパスワードの誤りで1件ずつ増え、2列（1行あたり 16 バイト程度）が増える。索引は足さない（対象の2列で引く画面・API はこの Intent に無く、監査の件数も小さいため）。総当たりの見つけ方の問い合わせ（`observability-design.md` 3節）は、手元で時々流す調べ物のため、索引なしの全件の走査で足りる。
- 保存期間と削除は既存のまま（監査の共通化は後続の Intent、`project.md` の DECIDED）。

## 4. 見直す時点

- 利用者の規模が増えた、社外に公開する配備先が決まった、または複数台にする必要が出たとき。そのときは内部DB の置き換えと、監査の対象の列の索引と、今のパスワードの誤りの制限（残る危険 R1）を合わせて見直す。
