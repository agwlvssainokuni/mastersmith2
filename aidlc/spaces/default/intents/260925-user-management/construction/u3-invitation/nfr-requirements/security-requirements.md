# Security Requirements — U3 招待と登録の完了（u3-invitation）

U3 のセキュリティの要件です。要件定義の NFR1（招待のトークン）・NFR2（個人情報とメール）・NFR3（列挙の防止）・NFR4（認可）・NFR8（多言語のエラーの説明文とテンプレート）・NFR9（必須のテストと入力の上限）を、この単位の招待の管理の API（契約 C5）、登録の完了の公開の API（契約 C6）、招待メールの依頼（契約 C1・C10）、利用者の作成（契約 C2）、監査（契約 C8）に当てます。

出典の略号は `performance-requirements.md` と同じ。加えて、PM は `aidlc/spaces/default/memory/project.md`、TM は `aidlc/spaces/default/memory/team.md`。

## 守るもの

| 守るもの | 置き場 | 守り方 |
|---|---|---|
| 招待のトークン（招待の URL に含まれる値） | 招待メールの本文だけ（保存しない） | 内部DB には SHA-256 のハッシュだけを置く。ログ・監査・トレース・エラー応答・一覧などの応答に出さない（NFR1.2・NFR1.5） |
| トークンのハッシュ | 内部DB の招待の行 | Invitation の外へ出さない。応答・監査に含めない（NFR1.5） |
| 招待の URL | 招待メールの本文だけ | 設定のベース URL だけから組み立てる。ログ・監査・トレース・エラー応答に出さない（NFR1.4・NFR1.5） |
| 招待先と招待した管理者のメールアドレス | 内部DB の招待の行・利用者の行 | アプリのログとエラー応答に出さない。管理者だけが見る正常の応答（C5 の email）は除く（NFR2.1） |
| 登録の完了で入れるパスワード | 要求の本文だけ（保存はハッシュ） | 既存の `Password` の型で扱い、ログ・監査・トレース・エラー応答に出さない（NFR2.1） |
| 招待の状態（招待中・完了・取り消し） | 内部DB の招待の行 | 公開の API の応答から推測できないようにする（NFR3.1） |

## 要件

| ID | 要件 | 確かめ方と持ち主の段 | 出典 |
|---|---|---|---|
| NFR1.1 | 招待のトークンは、`SecureRandom` の 32 バイト（256 ビット。要件の 128 ビット以上を満たす）を URL で使える Base64（埋め草なし、43 文字）にして作る。作成と送り直しのたびに新しく作る | 単体テストで長さと文字の種類を確かめる。予測できる乱数を使っていないことは SpotBugs の `PREDICTABLE_RANDOM` の関門（NFR9.3）（code-generation） | NFR1、BR3.1、PM の Mandated、要点 7 |
| NFR1.2 | 内部DB には UTF-8 のトークンの SHA-256（32 バイト）だけを一意の値として保存し、トークンの値を保存しない。ハッシュに鍵（HMAC）や塩を使わない（256 ビットの乱数には辞書や事前計算の攻撃が成り立たず、既存のリフレッシュトークンと同じ作り） | 結合テストで、招待の行にトークンの値が無く、ハッシュが一意の制約を持つことを確かめる（code-generation） | NFR1、BR3.1、PM の Mandated、要点 7 |
| NFR1.3 | 招待は1回だけ有効で、有効期限を持つ。有効は state が PENDING で時計の今が有効期限より前のときだけ（時刻ちょうどは無効）。完了・取り消し・置き換え・送り直しの前のトークンは使えない。有効期限の長さは承認済みの BR1.6 のとおり時間の単位の正の整数（既定 24 時間）で、上限は設けない（Q3 C） | 境界のテスト（直前は有効・ちょうどと直後は無効）を注入した時計で行い、有効の判定は jqwik の性質ベースのテストにする。使用済み・取り消し済み・置き換え済み・送り直しの前のトークンの拒否を結合テストで確かめる（code-generation） | NFR1、BR3.3・BR6.1・BR7.5、BR1.6、PM の Mandated、Q3 C、TM の Testing Posture（招待と登録の完了） |
| NFR1.4 | 招待の URL は、使えるベース URL の値だけから「ベース URL ＋ `/register#token=` ＋ トークン」で組み立て、要求の Host ヘッダー・スキーム・ポートを使わない。トークンは URL のフラグメントにだけ置き、リンクの確かめと完了の API は要求の本文でトークンを受け取る（URL のパス・問い合わせで受け取らない） | 結合テストで、要求の Host を変えても招待メールの URL がベース URL で始まること、ベース URL が無いときは Host を変えても送らず 503 になることを確かめる（code-generation） | NFR1、BR3.4・BR3.5、PM の Forbidden、TM の Testing Posture（招待の URL） |
| NFR1.5 | 招待のトークン・ハッシュ・招待の URL を、アプリのログ・監査ログ・トレースの属性・エラー応答・一覧と招待と送り直しの応答に含めない | 既存の `*SecretLeakIT` と同じ形で、招待・送り直し・送信の失敗・リンクの確かめ・登録の完了の成功と拒否のそれぞれで、ログ・監査の行（U2 が足した後の列の一覧）・応答にトークンと URL が無いことを確かめる。トレースの属性は既存の `TraceAspect` が引数の値を属性にしないことを前提に、同じテストで確かめる（code-generation） | NFR1、BR5.4・BR8.6・BR9.4、PM の Forbidden、TM の Testing Posture（トークンと URL の漏えい） |
| NFR1.6 | 形の合わないトークン（無い・空・43 文字でない・URL で使える Base64 の文字以外を含む）は、内部DB を引かずに見つからないとする | 境界のテスト（42・43・44 文字、使えない文字）と jqwik の性質ベースのテスト（code-generation） | NFR1、BR3.2 |
| NFR2.1 | メールアドレス（招待先・招待した管理者）とパスワードを、アプリのログとエラー応答に含めない。パスワード（平文・ハッシュとも）は監査ログ・トレースの属性にも含めない。管理者だけが見る C5 の正常の応答の email・invitedBy（氏名）は除く | `*SecretLeakIT` の形で、招待の入力の誤り・登録済み・招待中・送信の失敗・登録の完了の成功と拒否のそれぞれで確かめる（code-generation） | NFR2、BR1.1・BR7.2・BR9.4、PM の Forbidden |
| NFR2.2 | 送信が失敗したとき（接続を拒む・応答しない・宛先を拒む・U1 の入力やテンプレートの誤り）、応答とログに宛先のメールアドレス・SMTP の応答の文面・メールの部品の例外のメッセージ・資格情報を含めない。応答は sendResult FAILED だけで、失敗の種類の細部を載せない | 結合テスト（SubEtha SMTP と `ServerSocket` で失敗を起こす）で、応答とログを確かめる（code-generation） | NFR2、BR4.5・BR9.4、PM の Forbidden、TM の Testing Posture（送信の失敗） |
| NFR3.1 | リンクの確かめと登録の完了の拒否は、期限切れ・使用済み・取り消し済み・置き換え済み・存在しない・改ざん・形の誤り・同時の完了・同じメールアドレスの利用者がいる、のどれでも、状態コード 404・code REGISTRATION_LINK_INVALID・説明文・応答の本文の項目の並びを同じにする。拒否の理由は監査にだけ残す | 結合テストで、理由ごとに応答の状態コード・本文（項目の名前と並び）が一致することを確かめる（code-generation） | NFR3、BR7.5・BR7.6、TM の Testing Posture（招待と登録の完了） |
| NFR3.2 | 公開の2つの API の応答の時間の差はそろえない。時間の差から分かるのは「そのトークンが有効か」だけで、それを知るには 256 ビットのトークンを持っている必要があり、推測で利用者・招待の有無を探れないため。招待の管理の API は管理者だけが呼べるため、登録済みと招待中を区別して返してよい（NFR3 の対象外）。ログインの時間の差をそろえる既存の仕組み（`DummyPasswordHash`）は変えない | 設計の判断の記録（本書）。テストの対象にしない | NFR3、BR2.1、BR3.2、要点 9 |
| NFR3.3 | 招待中（登録が終わっていない）の人は利用者の表にいないため、ログイン・トークンの更新・アクセストークンの認証のどれでも拒否される。招待の ID を主体にしたトークンを発行する経路を作らない。ログインの拒否は存在しない利用者と同じ 401 | 結合テストで、招待中の人のメールアドレスでのログイン、招待の ID と招待のメールアドレスを主体にした正しい鍵のアクセストークン、リフレッシュトークンの更新が、どれも拒否されることを確かめる（code-generation） | NFR3、BR7.7、ADR-001、TM の Testing Posture（招待と登録の完了） |
| NFR4.1 | 招待の管理の API（`/api/admin/invitations` の下のすべて）は、未認証なら 401 AUTHENTICATION_REQUIRED、管理者でなければ 403 ACCESS_DENIED を返し、何も読み書きせずメールを送らない。管理者なら処理する（201・200・204） | サーバー側の結合テストで、4本の API それぞれの 401・403・成功を確かめる（画面で隠すことを代わりにしない）（code-generation） | NFR4、BR9.1、TM の Testing Posture（認可） |
| NFR4.2 | 認証なしで呼べるのは `POST /api/registration/verify` と `POST /api/registration/complete` だけとする。`/api/registration/` のほかの道・この2つの道のほかのメソッドは、`/api/` の既定のログイン必須のまま。公開の決まりは Invitation の差し込み口（`SecurityRuleContributor`）で足し、既存の順番の値と重ならない | 結合テストで、2つの POST が未認証で処理され、ほかの道・メソッド（例: GET `/api/registration/verify`）が 401 になることを確かめる。順番の重なりは既存の `SecurityExtensionValidator` で起動が止まる（code-generation） | NFR4、BR9.2、ADR-011 |
| NFR4.3 | 公開の2つの API はクッキーを使わず、要求の本文でトークンを受け取るため、トークンの更新・ログアウトのような Origin の確かめは足さない（既存の `/api/` の扱いのまま） | SecurityFilterChain の設定のレビュー（NFR 設計・code-generation） | NFR4、BR3.5、要点 11 |
| NFR4.4 | 登録を完了した直後の利用者は管理者でなく（admin false）、自動ではログインしない（トークンを発行しない）。登録の完了の後にログインし直すと、招待の管理の API は 403 になる | 結合テストで、完了の応答にトークンが無いこと、完了した利用者のログインの後に招待の管理の API が 403 になることを確かめる（code-generation） | NFR4、BR7.3・BR9.1、AC3.2.12 |
| NFR4.5 | 公開の2つの API に、アプリでは回数の制限を設けない（Q2 A）。総当たりはトークンの強さ（NFR1.1）で防ぐ。未認証の要求で監査の REGISTRATION_FAILED の行と内部DB のファイルを増やせる点は、下の「残る危険」の R1 に記録する | 設計の判断の記録（本書と R1） | NFR4、Q2 A、ADR-011、契約 C6 の Open question |
| NFR8.1 | Invitation のエラーの code（INVITATION_EMAIL_REGISTERED 409・INVITATION_ALREADY_PENDING 409・INVITATION_NOT_CONFIGURED 503・INVITATION_NOT_FOUND 404・REGISTRATION_LINK_INVALID 404）を機能の一覧に1つの code に1つの状態コードで固定し、ja・en の説明文を持つ。説明文は要求の Accept-Language で選ぶ（それ以外は既定の ja）。内部の例外のメッセージ・メールの部品の例外・SMTP の応答を載せない | 結合テストで ja・en の説明文と本文の項目を確かめる。code の重複は既存の起動時の検査（code-generation） | NFR8、BR9.3、TM の Code Style |
| NFR8.2 | 招待メールは招待の言語（招待した管理者の言語ではない）の ja・en のテンプレートで描く。テンプレートは U1 の決まり（エスケープされる差し込みだけ・属性の値は二重引用符・Mustache のコメントのライセンスヘッダー）に従う | テスト用の受け手（SubEtha SMTP）で受けた ja・en のメールの件名・本文・`lang` を確かめる（code-generation） | NFR8、BR4.2・BR10.1〜BR10.3、U1 の NFR9.1 |
| NFR9.1 | `team.md` の招待と登録の完了の必須テストを書く: 招待の有効期限の境界（直前は有効・直後は無効）、使い終えた招待・取り消した招待の再使用の拒否、改ざんした招待・存在しない招待の拒否（応答から利用者の存在を推測できない）、招待中の利用者のログイン・トークンの更新・アクセストークンの認証の拒否（NFR1.3・NFR3.1・NFR3.3） | `./gradlew verify`（code-generation） | NFR9、TM の Testing Posture |
| NFR9.2 | `team.md` の利用者へメールを送る機能の必須テストを書く: 本文のエスケープ（差し込む値すべて、registrationUrl・validityHours）、テンプレートの描画（ja・en、件名が空でない、差し込み漏れが無い、ライセンスヘッダーが出ない）、招待の URL（NFR1.4）、トークンと URL の漏えい（NFR1.5）、ヘッダーへの差し込み（宛先に CR・LF を含む招待の入力を拒否する、BR1.1）、送信の失敗（NFR2.2）。有効期限の長さを 48 時間に設定したとき、本文に「48 時間」が出て 24 が出ず、expiresAt が ＋48 時間になること（BR10.2） | `./gradlew verify`（code-generation） | NFR9、TM の Testing Posture、BR1.1・BR10.2 |
| NFR9.3 | 既存の静的解析の関門（SpotBugs ＋ FindSecBugs の priority 1、`SQL_`・`PREDICTABLE_RANDOM`・`SMTP_HEADER_INJECTION` は priority にかかわらず）と、秘密情報の検出・依存関係の脆弱性検査を、そのまま通す。除外を足さない | `./gradlew verify`（code-generation・build-and-test） | NFR9、TM の Code Style、PM の Mandated |
| NFR9.12 | 入力の上限: 要求の本文は既存の上限（1MB、`mastersmith.web.max-request-body-size`）のまま。招待のメールアドレスは改行を拒否し、そろえた後で 254 文字まで。登録の完了の氏名は 1〜254 コードポイント（U2 の DisplayName）、パスワードは 12 コードポイント以上・UTF-8 で 72 バイト以内（既存の PasswordPolicy）、トークンは 43 文字の固定の形（NFR1.6）。入力の誤りは内部DB を使う前に集めて返し、入れた値を応答に返さない | 境界のテスト（254・255 文字、CR・LF、11・12 コードポイント、72・73 バイト）（code-generation） | NFR9、BR1.1・BR7.2、要点 13 |

## 脅威と扱い

| 脅威 | 扱い | 要件 |
|---|---|---|
| トークンの推測・総当たり | 256 ビットの乱数、形の合わないトークンは内部DB を引かない。回数の制限はしない | NFR1.1・NFR1.6・NFR4.5 |
| 内部DB の漏えいからのトークンの復元 | ハッシュだけを保存する | NFR1.2 |
| 使い終えた・取り消した・古いリンクの再使用 | 状態と有効期限の判定、送り直しでハッシュを置き換える | NFR1.3 |
| Host ヘッダーの偽装で招待の URL を攻撃者のサイトに向ける | ベース URL の設定だけから組み立てる | NFR1.4 |
| リンクの漏れ（アクセスログ・Referer） | トークンをフラグメントに置き、API は本文で受け取る | NFR1.4 |
| 公開の API から利用者・招待の有無を探る | 拒否の応答を理由によらず同じにする | NFR3.1・NFR3.2 |
| 招待中の人が登録の前にログインする | 利用者の表にいない構造で拒否される | NFR3.3 |
| 管理者でない利用者が招待する | サーバー側で 403 | NFR4.1・NFR4.4 |
| メールのヘッダーへの差し込み | 宛先の CR・LF を拒否、U1 の検査、SpotBugs の `SMTP_HEADER_INJECTION` | NFR9.2・NFR9.3 |
| メールの本文への HTML の差し込み | エスケープされる差し込みだけ（U1 の決まり） | NFR8.2・NFR9.2 |
| 秘密・個人情報の漏えい（ログ・監査・トレース・応答） | 出さない決まりと漏えいのテスト | NFR1.5・NFR2.1・NFR2.2 |
| 未認証の要求で監査の行を増やす | 制限しない。残る危険 R1 として受け入れる | NFR4.5 |

## 残る危険

| ID | 危険 | 受け入れる根拠 | 見直す時点 |
|---|---|---|---|
| R1 | 登録の完了の公開の API に誤ったトークンを送るたびに、監査に REGISTRATION_FAILED が1行増える（承認済みの BR8.3。見つからないトークンでも記録する）。回数の制限が無いため、未認証の要求を大量に送れば、監査の表と内部DB のファイルを増やせる。監査の行は既存の決まりで消さないため、増えた分は残る | (1) 依頼者の決定（Q2 A）。(2) 存在しないメールアドレスでのログインの失敗も監査に残す既存のログインと同じ性質で、前の Intent でもログインに IP ごとの回数の制限を設けなかった（利用者 50 名の社内向け）。(3) トークンは 256 ビットで、総当たりで有効なトークンを当てることは成り立たない。(4) 要求の本文は 1MB までで、1行の大きさは限られる。増え方は監査の REGISTRATION_FAILED・INVITATION_NOT_FOUND の件数で見つけられる（`observability-requirements.md`） | 社外に公開する配備先が決まったとき（前段のリバースプロキシ・WAF での制限を配備の段で考える）、または監査で REGISTRATION_FAILED の急な増えが見つかったとき |
| R2 | 有効期限の長さに上限が無いため、配備の設定で大きな値（例: 8760 時間）にすると、受信箱に残った招待のリンクで第三者が登録できる期間が長くなる | 依頼者の決定（Q3 C）。長さは配備の設定の責任とし、既定は 24 時間。README の設定の説明に、長くしすぎない旨を書く（code-generation） | 配備先が決まったとき |

## 上流との差

| ID | 上流 | 上流の記載 | この段の要件 | 理由と扱い |
|---|---|---|---|---|
| S-D1 | ADR-011 の悪い点と契約 C6 の Open question | 「公開の道が1つ増えるため、回数の制限などの守りを NFR 要件で考える必要がある」「登録の完了の公開の API の回数の制限を設けるか」 | アプリでは回数の制限を設けない（NFR4.5）。残る危険 R1 に記録した | 依頼者の決定（Q2 A）。持ち越された論点をこの段で閉じた。ADR と契約の文書は書き換えない |
