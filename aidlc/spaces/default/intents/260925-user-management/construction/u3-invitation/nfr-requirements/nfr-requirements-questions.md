単位 U3（`aidlc/spaces/default/intents/260925-user-management/inception/units-generation/unit-of-work.md`、種類 service。招待・一覧・送り直し・取り消し・リンクの確かめ・登録の完了）の非機能要件のための質問です。service の単位のため、成果物は `performance-requirements.md`・`security-requirements.md`・`scalability-requirements.md`・`reliability-requirements.md`・`observability-requirements.md`・`tech-stack-decisions.md`・`traceability.json` のすべてです。

## 設計の要点（案）

上流とコードの確認から導ける、この単位の非機能要件の見通しです。質問の答えで決まる点は（Qn）と書きます。

### 性能

1. **招待と送り直し（NFR6）**: 手元の受け手が正常に受けるとき、同時 10 件の要求で POST `/api/admin/invitations` と `.../{invitationId}/resend` の p95 が 5 秒以内（要件の [assumption] をそのまま目標にする）。受け手が応答しないときは U1 の時間切れ 3 秒（U1 の NFR6.1）の後に sendResult FAILED で応答し、時間切れが1回で済む場合は 5 秒に収まる。応答が時間切れの手前で遅れ続ける受け手では全体が数倍になりうるという U1 の既知の限界（U1 の NFR6.3）は、そのまま引き継いで記録する。
2. **一覧・取り消し・リンクの確かめ（NFR6）**: 同時 10 件の要求で p95 1 秒以内。どれも bcrypt を使わず、内部DB の数行の読み書きだけ。
3. **登録の完了（NFR6）**: 成功の目標は（Q1）。入力の誤り（400）とリンクの拒否（404）は bcrypt を使わないため、同時 10 件で p95 1 秒以内。
4. **bcrypt の cost は既定の 12 のまま変えない**（U2 の NFR6.6 と同じ）。
5. **接続の持ち方（NFR5）**: 招待・送り直しは、確定の短いトランザクション → 接続を持たない送信 → 結果の記録の短いトランザクション（BR4.1・BR4.3、ADR-009）。登録の完了で bcrypt を計算する間に接続を持つかは（Q4）。
6. **測り方と持ち主**: 性能の目標は、この Intent の流れにある performance-validation の段が使い捨ての環境の k6 で測る（`project.md` の Testing Posture）。使い捨ての環境では Mailpit（compose の profile `mail`）を受け手にして招待を使える設定にし、k6 の場面に招待・送り直し・一覧・取り消し・リンクの確かめ・登録の完了（成功・入力の誤り・リンクの拒否）を足す。

### セキュリティ

7. **トークン（NFR1）**: BR3.1 のとおり `SecureRandom` の 32 バイト（256 ビット。要件の 128 ビット以上を満たす）を URL で使える Base64（43 文字）にし、内部DB には SHA-256 のハッシュだけを一意の値として保存する。ハッシュに鍵（HMAC）や塩は使わない（256 ビットの乱数には辞書や事前計算の攻撃が成り立たず、既存のリフレッシュトークンと同じ作り）。SpotBugs の `PREDICTABLE_RANDOM` の関門で乱数の種類を守る。
8. **有効期限の長さの範囲**: 下限は承認済みの BR1.6（時間の単位の正の整数、既定 24）。上限は（Q3）。
9. **列挙の防止（NFR3）**: リンクの確かめ・登録の完了の拒否は、理由によらず状態コード・code・本文の項目の並びを同じにし（BR7.5）、理由ごとにテストで確かめる。**応答の時間の差はそろえない**。時間の差から分かるのは「そのトークンが有効か」だけで、それを知るには 256 ビットのトークンを持っている必要があり、推測で利用者・招待の有無を探れないため（形の合わないトークンは内部DB を引かない、BR3.2）。招待の管理の API は管理者だけが呼べるため NFR3 の対象外（BR2.1）。ログインの時間の差をそろえる既存の仕組み（`DummyPasswordHash`）は変えない。
10. **公開の API の回数の制限**: （Q2）。
11. **認可（NFR4）**: 招待の管理の API は、未認証 401・管理者でない 403・管理者 200（201・204）をサーバー側のテストで確かめる（BR9.1）。認証なしで呼べるのは `POST /api/registration/verify` と `POST /api/registration/complete` だけで、`/api/registration/` のほかの道・ほかのメソッドがログイン必須のままであることもテストで確かめる（BR9.2）。公開の2つはクッキーを使わず本文でトークンを受け取るため、Origin の確かめは足さない（既存の `/api/` の扱いのまま）。
12. **秘密（NFR1・NFR2）**: 招待のトークン・ハッシュ・招待の URL・メールアドレス・パスワード・SMTP の応答を、ログ・監査ログ・トレースの属性・エラー応答に含めない（BR8.6・BR9.4。管理者だけが見る C5 の正常の応答の email・invitedBy は除く）。既存の `*SecretLeakIT` と同じ形で、招待・送り直し・送信の失敗・登録の完了の成功と拒否を確かめ、監査の列の一覧は U2 が足した後の列で確かめる。
13. **入力の上限**: 要求の本文は既存の上限 1MB のまま。メールアドレス 254 文字、氏名 254 コードポイント、パスワード UTF-8 で 72 バイト（既存の PasswordPolicy）、トークンは 43 文字の固定の形（BR1.1・BR3.2・BR7.2）。
14. **静的解析**: 既存の関門（SpotBugs の priority 1、`SQL_`・`PREDICTABLE_RANDOM`・`SMTP_HEADER_INJECTION`）をそのまま通す。

### 拡張性

15. **想定の規模**: 利用者 最大 50 名・同時 10 名を1台で処理する（前の Intent と U2 と同じ）。内部DB は組み込みの H2 の単一インスタンスが前提（ADR-010）。招待の行は利用者の数と同じ程度で、終わった招待と期限切れの招待中は保存の日数（既定 90 日）の後に定期に消える（BR11.1）。監査の行は招待の操作ごとに1行と、登録の完了のリンクの拒否ごとに1行（未認証の要求で増えうる。Q2 と関わる）。
16. **同じメールアドレスの招待中を1件に限る仕組み**（BR2.5）と行の排他の作り（BR6.4）は、単一インスタンスを前提に NFR 設計で決める。この段では「同時の招待・操作でも1件だけが通る」を要件にし、結合テストで確かめる。

### 信頼性

17. **送信は1回で自動の再試行なし**（U1 の NFR6.3）。失敗は sendResult FAILED で記録し、管理者が送り直す（BR4.5）。送信の途中でアプリが止まったときは PENDING のまま残り、API では FAILED に見える（BR4.4）。
18. **監査の書き込みの失敗で操作を失敗させない**（BR8.5、既存の AuditLog の決まり）。出来事ごとに書き込みの失敗のテストを1件入れる。
19. **2本目の接続（NFR5、`project.md` の Corrections）**: 招待・送り直し・取り消し・登録の完了の成功は、確定の後の監査の記録で2本目の接続を借りる経路になる（既存の `AuditEventListener` の AFTER_COMMIT と `REQUIRES_NEW`）。要求1件で同時に持つ接続は最大2本、同時 10 件で最大 20 本で、上限 30 に収まる見込み。見積もりだけで済ませず、6. の k6 で、接続を借りる待ちの時間切れの累計が 0 であることを確かめる。
20. **定期の削除**: 件数の上限ごとに別のトランザクションで消し、失敗は ERROR（スタックトレース付き）で出して次の回に任せる（BR11.1、既存の `RefreshTokenCleanupJob` と同じ形）。既定の時刻と件数の上限はコード生成で決める（機能設計の7節）。
21. **V8 の後方互換（NFR10、BR11.3）**: 新しい表を足すだけの前進の変更で、1つ前の版のアプリは招待の表を読まずに起動できる。
22. **想定外の誤り**: 内部DB の障害などは既存の 500 の扱い（例外のメッセージを載せない）。

### 観測

23. **新しい指標と警報は足さない**: API の応答時間と状態コードは既存の HTTP の指標で取れる。送信の失敗は一覧の sendResult とアプリのログ（invitationId・結果の種類・U1 の失敗の種類をキーと値で。宛先・SMTP の応答は出さない）で追え、招待・登録の出来事は監査ログで追える。定期の削除は消した件数を INFO、失敗を ERROR で出す。ログは既存の決まり（4xx は WARN 以下でスタックトレースなし、トレースID を含む）。

### 技術

24. **新しい依存は足さない**: `SecureRandom`・`MessageDigest`（SHA-256）・Spring の `@Scheduled`・Spring Data JPA・Flyway・H2・jqwik（有効の判定とトークンの形の性質ベースのテスト）・ArchUnit・U1 が足す SubEtha SMTP で作る。（Q2 で B を選ぶと、回数を数える仕組みが要る）

### テストとカバレッジ（NFR9）

25. **カバレッジ**: 新しいパッケージ `invitation` は自動でパッケージごとの下限（行 80%・分岐 70%）の対象になる。B2 で一覧から外した後の `packagesJudgedByTotal` を前提に、U3 で手を入れた一覧のパッケージがあれば外して下限を満たす。実測は `:backend:cleanTest :backend:cleanIntegrationTest` を付けた `./gradlew verify` で取り、記録する。
26. **必須のテスト**: `team.md` の招待と登録の完了の必須テスト（期限の境界・再使用と改ざんの拒否・応答から存在を推測できない・招待中の人の3経路での拒否）、利用者へメールを送る機能の必須テスト（エスケープ・テンプレートの描画・招待の URL をベース URL だけから組み立てる・トークンと URL の漏えい・ヘッダーへの差し込み・送信の失敗）、認可（401・403・200）、監査（出来事ごとの必須の項目と書き込みの失敗）、E2E の代表の流れ1本（招待から登録の完了まで。持ち主は U6・基盤の設計）。

## Q1. 登録の完了の成功の応答時間の目標と、測る負荷をどうしますか？

理由: 要件 NFR6 は「登録の完了の API は既存の API と同じく p95 1 秒以内」を [assumption] としています。登録の完了の成功は、新しいパスワードのハッシュで bcrypt を1回計算します（cost 12 で1回 約 278 ms）。同じく bcrypt 1回のログインは、同時 10 件の p95 が CPU 4 で 940 ms（余裕 60 ms）でした。登録の完了はこれに利用者・ロックの状態・招待の書き込みが加わるため、同時 10 件では 1 秒を少し超えるおそれがあります（まだ測っていません）。一方で、登録の完了は招待された人1人につき1回だけで、同時 10 件は起きにくい操作です。U2 のパスワードの変更は「bcrypt の回数に合わせる」（2回で 2 秒）と決めました。

A. 同時 10 件で p95 1 秒以内とする（bcrypt 1回のログインと同じ目標。U2 の Q1 A の考え方で bcrypt の回数に合わせる。performance-validation で超えたときは、その段で目標か作りを見直す）
B. 目標は 1 秒のまま、登録の完了だけ測る負荷を同時 2 件にする（1人1回の操作で、同時 10 件は起きにくいため）。同時 10 件の値は記録だけにする
C. 同時 10 件で p95 2 秒以内とする（書き込みが増える分の余裕を取る。要件の [assumption] 1 秒との差を成果物に記録する）
X. Other (please specify)

[Answer]: A

## Q2. 登録の完了の公開の API（リンクの確かめ・完了）に回数の制限を設けますか？

理由: 契約 C6 の Open question と ADR-011 の悪い点で、この段が持ち主です（機能設計の7節）。2つの API はログインなしで呼べます。トークンは 256 ビットの乱数のため、総当たりで有効なトークンを当てることは成り立たず、応答は理由によらず同じです（要点 9）。ただし、登録の完了にトークンの誤りを送るたびに、監査に REGISTRATION_FAILED が1行増えます（承認済みの BR8.3。見つからないトークンでも記録する）。そのため、未認証の要求を大量に送れば、監査の表と内部DB のファイルを増やせます。これは、存在しないメールアドレスでのログインの失敗も監査に残す既存のログインと同じ性質で、前の Intent ではログインに IP ごとの回数の制限を設けませんでした。

A. アプリでは回数の制限を設けない（トークンの強さで総当たりが成り立たず、既存のログインと同じ扱い。未認証の要求で監査の行を増やせることは残る危険として記録し、配備先が決まったときに見直す）
B. アプリの中で、送信元の IP ごとに2つの API の要求を数え、一定の回数（例: 1 分に 20 回）を超えたら 429（新しい code）で拒否する。数はメモリに持つ（単一インスタンスが前提、起動し直すと消える）。前段にプロキシを置く配備では送信元の IP の取り方（`X-Forwarded-For` を信じるか）を決める必要があり、回数を数える仕組みを作る（新しい依存を足すなら採用の前にライセンスを確かめる）
C. アプリでは設けず、配備先が決まったときに前段（リバースプロキシ・WAF など）で `/api/registration/` の回数を制限することを、配備の段への要件として記録する
X. Other (please specify)

[Answer]: A

## Q3. 招待の有効期限の長さに上限を設けますか？

理由: 承認済みの BR1.6 は、有効期限の長さを「時間の単位の正の整数」（既定 24 時間）とし、上限を決めていません。招待のリンクはメールの受信箱に残るため、長さを大きく設定すると（例: 8760 時間 ＝ 1 年）、漏れたメールのリンクで第三者が登録できる期間が長くなります。一方で、配備先ごとの運用（週末をまたぐ招待など）で長めの値を使いたい場合があります。上限を超える値は、BR1.6 の下限の誤りと同じく起動を止める扱いを想定しています。

A. 上限を 168 時間（7 日）とし、超える値は起動を止める（BR1.6 の下限と同じ扱い。承認済みの BR1.6 に上限を足す差として成果物に記録する）
B. 上限を 72 時間（3 日）とし、超える値は起動を止める
C. 上限を設けない（承認済みの BR1.6 のまま。長さは配備の設定の責任とし、README に長くしすぎない旨を書く）
X. Other (please specify)

## Q4. 登録の完了で、パスワードのハッシュ（bcrypt）をトランザクションの中で計算しますか？
