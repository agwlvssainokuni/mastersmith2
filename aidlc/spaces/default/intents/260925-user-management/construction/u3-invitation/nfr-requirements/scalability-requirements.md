# Scalability Requirements — U3 招待と登録の完了（u3-invitation）

U3 の拡張性の要件です。アプリは当面1台で、内部DB は組み込みの H2 の単一インスタンスです（要件の4節の制約、ADR-010）。出典の略号は `performance-requirements.md` と同じ。

## 要件

| ID | 要件 | 確かめ方と持ち主の段 | 出典 |
|---|---|---|---|
| NFR6.7 | 想定の規模（利用者 最大 50 名、同時 10 件の要求）を1台で処理する。U3 の API も、この規模で NFR6.1・NFR6.3〜NFR6.5 の目標を満たす | performance-validation の負荷の試験（NFR6.1・NFR6.3〜NFR6.5） | NFR6、U2 の NFR6.7、要点 15 |
| NFR5.4 | 内部DB の接続の数の見積もり: 招待・送り直しは、確定のトランザクションで1本、確定の後の監査の記録で2本目（同時に持つのは最大2本）。その後の送信の間は0本で、送信の結果の記録で1本を短く持つ。取り消しと登録の完了の成功も、確定の後の監査の記録で最大2本。一覧・リンクの確かめ・登録の完了の拒否（REGISTRATION_FAILED は巻き戻しの後に要求の中で記録）は1本。同時 10 件がすべて2本の経路でも最大 20 本で、接続プールの上限（既定 30、`MASTERSMITH_DB_MAXIMUM_POOL_SIZE`）に収まる。登録の完了は bcrypt の間も1本を持つ（NFR5.2）ため、1本を持つ時間はほかの経路より長い | 見積もりの記録（本書）。実際に尽きないことは NFR5.3（`reliability-requirements.md`）の負荷の試験で確かめる（見積もりだけで済ませない） | NFR5、`project.md` の Corrections、要点 19、Q4 A |
| NFR6.10 | 同じメールアドレスの招待中を1件に限る決まり（BR2.5）と、同じ招待への送り直し・取り消し・登録の完了の排他（BR6.4）は、内部DB の単一インスタンス（組み込みの H2）を前提に作る。アプリを複数台にする配備は、この前提を見直すまで行わない | 仕組み（索引か行の排他か）は NFR 設計で決める（ADR-010、機能設計の7節）。同時の要求で1件だけが通ることは結合テストで確かめる（`reliability-requirements.md` の NFR9.8） | ADR-010、BR2.5・BR6.4、要点 16 |

## データの増え方

| データ | 増え方 | 見積もり | 扱い |
|---|---|---|---|
| 招待の行 | 招待1回に1行。送り直しは同じ行を書き換える（行は増えない）。期限切れのまま再招待すると古い行は REPLACED で残る | 利用者の数と同じ程度（最大 50 行に再招待の分）。1行は数百バイト | 終わった招待は終わった日時から、期限切れの招待中は有効期限から、保存の日数（既定 90 日）を過ぎたら定期に消す（BR11.1、`reliability-requirements.md` の NFR9.10） |
| 利用者の行 | 登録の完了1回に1行（admin false） | 最大 50 行 | 既存の利用者の表（U2 が列を足した後） |
| 監査の行 | 招待・送り直し・取り消し・登録の完了で1件ずつ、登録の完了のリンクの拒否ごとに1件（REGISTRATION_FAILED）。入力の誤り・リンクの確かめ・招待の管理の拒否では増えない（BR8.1〜BR8.3） | 招待の操作は頻度が低い。ただし NFR4.5 のとおり公開の API の回数を制限しないため、誤ったトークンでの登録の完了を大量に受けると、その数だけ増える（`security-requirements.md` の R1） | 監査の保存期間と削除は既存のまま（`project.md` の DECIDED、監査の共通化は後続の Intent） |
| 監査の列 | 増やさない（U2 が足した target_user_id・target_invitation_id と既存の列を使う） | — | 変更なし（BR8.4） |
