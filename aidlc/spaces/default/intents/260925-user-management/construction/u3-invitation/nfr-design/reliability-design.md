# Reliability Design — U3 招待と登録の完了（u3-invitation）

U3 の信頼性の設計です。承認済みの `construction/u3-invitation/nfr-requirements/reliability-requirements.md`（NFR5.3・NFR9.4・NFR9.8・NFR9.9・NFR9.10・NFR9.13・NFR10.1〜NFR10.3）を満たす作りを決めます。当面の配備先は開発者の PC 上のコンテナ1台で、可用性の数値の目標は配備先が決まってから決めます。出典の略号は `performance-design.md` と同じ。

## 1. 確定の単位（NFR9.13、BR7.3）

| 操作 | 1つのトランザクションで確定するもの | 何も変えずに終わる場合 |
|---|---|---|
| 招待 | 同じメールアドレスの期限切れの PENDING を REPLACED にする、新しい招待（PENDING・sendResult PENDING）、INVITATION_ISSUED の出来事 | 入力の誤り・使えない設定・登録済み・期限内の招待中（409） |
| 送り直し | トークンのハッシュ・有効期限・sendResult（PENDING）の置き換え、INVITATION_RESENT の出来事 | 使えない設定（503）・無い・終わった（404） |
| 取り消し | state を CANCELLED・endedAt、INVITATION_CANCELLED の出来事 | 無い・終わった（404） |
| 登録の完了 | 利用者の作成（`createUser`、UserCreatedEvent でロックの状態の行）と招待の COMPLETED・endedAt・completedUserId、REGISTRATION_COMPLETED の出来事 | 入力の誤り（400）・リンクの拒否と同じメールアドレスの利用者（404、巻き戻し） |
| 送信の結果の記録 | 条件つきの更新1回（別の短いトランザクション） | 条件に当たらなければ何もしない |

- トランザクションは `invitation.service` の中の `TransactionTemplate` だけで作る（`team.md` の Code Style、既存の ArchUnit「トランザクションの境界は service の層だけ」）。
- 内部DB の障害などの想定外の誤りは巻き戻り、既存の 500 の扱い（内部の例外のメッセージを載せない）にする。確定の前の失敗ではメールを送らない。

## 2. 同じメールアドレスの招待中を1件に限る（NFR9.8・NFR6.10、BR2.2・BR2.5、Q2 A）

### 2.1 仕組み

内部DB の制約で守る。組み込みの H2 は条件つきの一意の索引（WHERE 付き）を持たないため、state が PENDING のときだけメールアドレスになり、それ以外は空（NULL）になる生成列を置き、その列に一意の制約を付ける。H2 の一意の制約は空を重ねてよいため、終わった招待は同じメールアドレスでいくつでも残せる。

```sql
CREATE TABLE invitations (
    invitation_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(254) NOT NULL,
    state VARCHAR(16) NOT NULL,
    token_hash BINARY(32) NOT NULL,
    -- ほかの列は entities.md のとおり（言語・招待した管理者・日時・送信の結果・完了した利用者）
    pending_email VARCHAR(254) GENERATED ALWAYS AS (CASE WHEN state = 'PENDING' THEN email END),
    CONSTRAINT uk_invitations_token_hash UNIQUE (token_hash),
    CONSTRAINT uk_invitations_pending_email UNIQUE (pending_email),
    CONSTRAINT ck_invitations_state CHECK (state IN ('PENDING', 'COMPLETED', 'CANCELLED', 'REPLACED'))
);
```

- エンティティ `Invitation` は `pending_email` を持たない（Hibernate の `ddl-auto: validate` は表にある余分な列を見ない）。書き込みで値を渡さず、DB が計算する。
- この段の使い捨ての試し（本番のコードとは別、メモリの中の H2 2.4.240）で、(a) PENDING の2件目の追記が一意の違反（SQLState 23505）で拒まれる、(b) PENDING でない行は同じメールアドレスで複数持てる、(c) PENDING を CANCELLED にすると同じメールアドレスで新しい PENDING を作れる、(d) 確定していない同時の追記は、先の追記の確定を待った後に一意の違反で拒まれ、PENDING は1件だけ残る、を確かめた。

### 2.2 招待の流れの中の扱い

1. 同じメールアドレスの PENDING の行を `PESSIMISTIC_WRITE`（待ち 3 秒）で読む。期限内なら 409 INVITATION_ALREADY_PENDING、期限切れなら REPLACED にする（BR2.2・BR2.4）。
2. 新しい招待を追記する（IDENTITY の主キーのため追記はその場で DB に届き、一意の違反はトランザクションの中で分かる）。
3. 同時の招待で負けた側は、一意の違反（`DataIntegrityViolationException`）でトランザクションが巻き戻る。業務処理は `TransactionTemplate` の外でこれを受け、短い読み取りのトランザクションで勝った側の PENDING の invitationId と page（BR2.3）を引き、409 INVITATION_ALREADY_PENDING を返す。メールを送らず、INVITATION_ISSUED を記録しない（出来事は巻き戻しで捨てられる）。
4. 3 で勝った側の PENDING が見つからない（その間に取り消し・完了された、またはトークンのハッシュの重なりという起きない場合）ときは、招待の作成を最初から1回だけやり直す。2回目も一意の違反なら想定外の誤り（500）とする。

### 2.3 確かめと切り替え

- B3 の最初の結合テストで、Flyway の V8 と Hibernate の `validate` の上で 2.1 の (a)〜(d) を確かめる。同時の招待は待ち合わせ（テストの中の同期の仕組み）で確実に重ね、1件だけが作られ、もう一方が 409 でメールを送らず監査に残らないことを確かめる（NFR9.8）。
- 成り立たなければ、承認どおり B（固定の1行を `PESSIMISTIC_WRITE` で排他して招待の作成を1つずつ行う）に切り替え、切り替えたことをコード生成の成果物に記録する。

## 3. 同じ招待への同時の操作と登録の完了の巻き戻し（NFR9.8・NFR9.13、BR6.4・BR7.4）

- 送り直し・取り消し・登録の完了は、どれも対象の行を `PESSIMISTIC_WRITE`（待ち 3 秒）で読み、読んだ時点の state とトークンのハッシュで判定する。先に確定した操作の後、待っていた操作は新しい状態を読み、送り直し・取り消しは 404 INVITATION_NOT_FOUND、登録の完了は 404 REGISTRATION_LINK_INVALID になる。送り直しが先なら、前のトークンのハッシュでは行が見つからない。
- 登録の完了で拒否が決まったら、`TransactionTemplate` の中で自分の `TransactionStatus#setRollbackOnly` を付けて抜ける。`createUser` が EmailAlreadyUsed で付けた印は、参加したトランザクション全体の印（global）であり、呼び出し元が自分の印（local）を付けずに確定しようとすると `UnexpectedRollbackException` になる。自分の印があると確定の処理は例外なしで巻き戻す。

```java
Outcome outcome = transaction.execute(status -> {
    Outcome o = completeInTransaction(token, newUser);   // 排他・判定・createUser・完了
    if (o instanceof Outcome.Rejected) {
        status.setRollbackOnly();                         // 利用者も招待の変更も残さない
    }
    return o;
});
```

- 確かめ（結合テスト、待ち合わせで重ねる）: 同じ招待の2回の完了で利用者は1人、完了と取り消しで取り消しが先なら利用者は作られない、完了と送り直し、EmailAlreadyUsed の巻き戻しで利用者が増えず招待が PENDING のまま成功の監査が残らない、`UnexpectedRollbackException` が起きない。

## 4. 定期の削除（NFR9.10、BR11.1・BR11.2）

| 項目 | 作り |
|---|---|
| 部品 | `InvitationCleanupJob`（`invitation.service`）。既存の `RefreshTokenCleanupJob` と同じ形 |
| 動かし方 | `@Scheduled(cron = 設定の値)`。`@EnableScheduling` は今 `auth.service.AuthSchedulingConfig` にだけあるため、`invitation` の中にも置く（例: `InvitationSchedulingConfig`。重ねて置いても害が無く、`auth` の設定に黙って頼らない） |
| 境目 | 注入した `Clock` の今 − 保存の日数（既定 90 日） |
| 消す行 | COMPLETED・CANCELLED・REPLACED で `ended_at` ≦ 境目、PENDING で `expires_at` ≦ 境目 |
| 1回の量 | 件数の上限ごとに `TransactionTemplate` で1回ずつ、上限に届かなくなるまで繰り返す |
| 同時の送り直しとの重なり | 対象を選ぶ副問い合わせだけでなく、外側の DELETE の条件にも状態と日時の条件を重ねる。選んだ後に送り直された行（有効期限が新しくなった PENDING）は消さない |
| ログ | 消した件数を INFO、失敗は ERROR（スタックトレース付き）で出し、例外を外へ出さず次の回に任せる |
| 既定の値の案 | 時刻 `0 45 3 * * *`（既存のリフレッシュトークンの削除の 3 時 30 分と重ならない）、件数の上限 1000（既存と同じ）。最終の値と設定の項目の名前はコード生成で決める |
| 消えた後 | 消えた招待のリンクは「存在しない」と同じ（監査の理由 INVITATION_NOT_FOUND）、ID は 404。監査の記録は消さない（参照の制約を置かない） |

- 確かめ（結合テスト、注入した時計）: 境目ちょうど・直前の行、件数の上限を超える行、途中の失敗のときに次の回で消えること、選んだ後に送り直した行が消えないこと。

## 5. 2本目の接続と負荷の試験（NFR5.3）

- 作りは既存のまま（`AuditEventListener` の AFTER_COMMIT と `AuditEventRecorder` の `REQUIRES_NEW`）。招待・送り直し・取り消し・登録の完了の成功が最大2本の経路になる（`scalability-design.md` 2節）。
- performance-validation の k6 で、招待と登録の完了の成功をそれぞれ同時 10 件で流し、使い捨ての環境にだけ `MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE=health,metrics` を渡して、hikaricp の接続を借りる待ちの時間切れの累計が 0、借りるまでの待ちの最大が 5 秒より十分小さいこと、流した成功の件数と監査の INVITATION_ISSUED・REGISTRATION_COMPLETED の件数が一致することを確かめる（承認どおり）。

## 6. 送信の失敗と結果の記録（NFR9.9、BR4.3〜BR4.5、ADR-009）

- 送信は U1 の `send` を1回だけ呼び、自動でやり直さない（U1 の NFR6.3）。結果が FAILED（種類によらない）でも、招待と新しいトークン・有効期限は確定したまま、sendResult を FAILED で記録し、201・200 で返す。
- 結果の記録は、送ったトークンのハッシュを今も持ち sendResult が PENDING の行だけを書き換える条件つきの更新1回（`performance-design.md` 2節）。
- 送信の途中でアプリが止まったときは PENDING のまま残り、API（C5）では FAILED として返す（管理者が一覧で見つけて送り直せる）。
- U1 が想定外の失敗で `MailUnexpectedException` を投げたときは捕まえず、既存の 500 の扱いに任せる（U1 の `logical-components.md` 4節）。招待は確定したまま PENDING で、一覧では FAILED に見える。
- 確かめ（結合テスト）: 受け手が接続を拒む・応答しない・宛先を拒むときの sendResult と応答、受け手が受けた接続が1回だけ、PENDING の行が API で FAILED に見える、記録の時点で tokenHash が変わっていれば書かない。

## 7. 監査の記録（NFR9.4、BR8.1〜BR8.5、C8）

- 出来事の型5つ（`InvitationIssuedEvent`・`InvitationResentEvent`・`InvitationCancelledEvent`・`RegistrationCompletedEvent`・`RegistrationFailedEvent`）を `invitation.domain` に置く。どれもトークン・ハッシュ・URL・メールアドレス・パスワードを持たない（持つのは invitationId・利用者 ID・失敗の理由・`RequestOrigin`）。
- `audit.domain.AuditEventFactory` が出来事から監査の行を組み立て、`AuditEventListener` に受け取りを5つ足す（AFTER_COMMIT・`fallbackExecution = true`、失敗は受け止めて ERROR）。成功の出来事は確定の後に、REGISTRATION_FAILED はトランザクションの外（巻き戻しの後）で知らせてその場で記録される。`invitation` は `audit` に依存しない。
- 監査の書き込みが失敗しても元の応答は変わらない。確かめは既存の `AuditWriteFailureIT` と同じ形で5つの出来事ごとに1件、巻き戻しで成功の監査が残らないことは `AuditRollbackIT` と同じ形で確かめる。
- 監査の種類5つと失敗の理由5つ（EMAIL_ALREADY_REGISTERED を含む）を `AuditEventType`・`AuditFailureReason` に足す（B2 で `audit.domain` はパッケージごとの下限の対象に戻っている）。

## 8. スキーマと後方互換（NFR10.1〜NFR10.3、BR11.3）

- 招待の表は、U2 の V7 の後の V8 の1つの前進の変更で新しく足す（2.1 の表と、招待した管理者・完了した利用者への参照）。既存の表と V1〜V7 は変えない。適用の失敗は既存の Flyway の扱いで起動を止める。
- 後方互換の確かめは、U2 の V7（U2 の NFR 設計の Q4 A）と同じ2段にする。
  1. 自動の結合テストで、V8 まで当てた内部DB に対して、V7 までしか知らない Flyway の設定（移行の置き場を V7 までの複写に向ける）で検証が失敗しないことを確かめる（Flyway の既定が知らない新しい移行を無視することの固定）。
  2. deployment-execution の戻しの練習で、1つ前の版のイメージを V8 の後の内部DB の複写で起動し、健全性・ログイン・トークンの更新・監査の記録を確かめる（手順は deployment-pipeline で書き、U2 の練習と合わせて行う）。
- 1つ前の版へ戻した後に今の版へ戻し直すと、招待の表は戻す前の状態のまま使われ、戻している間に有効期限を過ぎた招待は期限切れになる。これを戻しの手順（deployment-pipeline）に書く（NFR10.3）。

| 送信の途中でアプリが止まる | sendResult は PENDING のまま、API では FAILED | 6節 |
