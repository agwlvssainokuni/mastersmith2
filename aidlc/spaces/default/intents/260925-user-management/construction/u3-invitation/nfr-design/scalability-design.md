# Scalability Design — U3 招待と登録の完了（u3-invitation）

U3 の拡張性の設計です。承認済みの `construction/u3-invitation/nfr-requirements/scalability-requirements.md`（NFR6.7・NFR5.4・NFR6.10）を満たす作りを決めます。出典の略号は `performance-design.md` と同じ。

## 1. 1台・組み込みの H2 の前提（NFR6.7・NFR6.10、ADR-010）

- アプリは1台、内部DB は組み込みの H2 の単一インスタンスのまま（前の Intent と同じ）。U3 はアプリのメモリに状態を持たない（回数の数え上げ・キャッシュ・招待ごとの錠を持たない）。
- 次の3つは、内部DB の単一インスタンスを前提にする。アプリを複数台にする配備は、この前提を見直すまで行わない（承認どおり）。

| 仕組み | 前提 | 複数台にするときに見直すこと |
|---|---|---|
| 招待中を1件に限る（生成列 `pending_email` の一意の制約、`reliability-design.md` 2節） | 制約を持つ DB が1つ | 共有の DB に移るときは、その DB の条件つきの一意の索引（部分索引）か同じ生成列で作り直す |
| 同じ招待の行の排他（`PESSIMISTIC_WRITE`、`performance-design.md` 6節） | 行の排他を持つ DB が1つ | 共有の DB の行の排他でそのまま成り立つ見込み（DB に依存する挙動を確かめ直す） |
| 定期の削除（`reliability-design.md` 4節） | 同じ時刻に動くのは1台だけ | 複数台が同時に消しても条件を DELETE の中で確かめ直すため壊れないが、重なりを避ける仕組み（1台だけで動かす）を配備の段で考える |

## 2. 接続の数の見積もり（NFR5.4）

承認済みの見積もりをそのまま作りに当てる。

| 経路 | 同時に持つ接続 | 持つ間 |
|---|---|---|
| 招待・送り直し | 最大2本（確定のトランザクション＋確定の後の監査の `REQUIRES_NEW`） | 確定と監査の記録の間。送信の間は0本、結果の記録で1本を短く |
| 取り消し | 最大2本 | 確定と監査の記録の間 |
| 登録の完了の成功 | 最大2本 | 1本目は bcrypt の間も持つ（NFR5.2）、確定の後の監査で2本目 |
| 登録の完了の拒否 | 1本（巻き戻しの後に監査の1本、重ならない） | 短い |
| 一覧・リンクの確かめ | 1本 | 短い |

- 同時 10 件がすべて2本の経路でも最大 20 本で、接続プールの上限（既定 30、`MASTERSMITH_DB_MAXIMUM_POOL_SIZE`）に収まる。見積もりだけで済ませず、performance-validation の k6 で確かめる（`reliability-design.md` 5節、`project.md` の Corrections）。
- 送信の間に接続を持たないことは、送信の入口の確かめと結合テストで守る（`performance-design.md` 2.1）。

## 3. データの増え方と上限

| データ | 増え方 | 抑え方 |
|---|---|---|
| 招待の行 | 招待1回に1行、送り直しは同じ行、期限切れの再招待で古い行が REPLACED で残る | 保存の日数（既定 90 日）を過ぎたら定期の削除（`reliability-design.md` 4節） |
| 監査の行 | 招待の操作ごとに1件、登録の完了のリンクの拒否ごとに1件 | 既存のとおり消さない。公開の API の回数を制限しないため、誤ったトークンの大量の要求で増えうる（`security-design.md` の R1） |
| 生成列 `pending_email` | 招待の行と同じ | PENDING でない行は空（NULL）で、一意の索引の中で重なってよい |

## 4. 想定の規模を超えるとき

- 想定は利用者 最大 50 名・同時 10 件の要求（NFR6.7）。招待の操作は管理者だけで頻度が低く、U3 が規模の上限を決めることは無い見込み。接続の上限を決めるのは、既存のログインと合わせた bcrypt の経路（登録の完了を含む）である。
- 規模を超えるときの手は、既存のとおり接続プールの上限の見直し（設定の値だけ）と、配備先が決まった後の DB の見直し（1節の表）とする。今は作らない。

## 上流との差

なし。承認済みの見積もりと前提を、決めた仕組み（Q2 A の生成列）に当てただけで、要件は変えていない。
