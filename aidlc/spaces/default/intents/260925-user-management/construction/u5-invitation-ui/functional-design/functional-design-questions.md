# Functional Design の質問 — u5-invitation-ui

単位 U5（`aidlc/spaces/default/intents/260925-user-management/inception/units-generation/unit-of-work.md`、種類 ui）の機能設計のための質問です。U5 は主に受け持つストーリーを持たず、US1.1・US2.1・US2.2 の画面の部分と、共通の決まり CR1（文言）・CR6（画面の共通の決まり）を受け持ちます（`unit-of-work-story-map.md`）。契約は C5（受ける側、招待の管理の API）・C9（受ける側、表示の設定の口）（`aidlc/spaces/default/intents/260925-user-management/inception/contract-design/contract-summary.md`）。画面は `refined-mockups/` の S1・S1-M1・S1-M2（`mockups.md`・`interaction-spec.md`・`design-system-mapping.md`）。依存する単位の機能設計 `construction/u3-invitation/functional-design/`（API のふるまいと、U5 に回された受け入れ基準 AC1.1.1・AC1.1.8・AC1.1.9・AC2.1.4・AC2.1.6・AC2.2.11・AC2.2.12）と `construction/u4-display-foundation/functional-design/`（C9 の口と `LANGUAGE_NAMES`）、既存のコード `frontend/src/features/dsl/`（前の Intent の管理画面の作り）・`frontend/src/features/admin/`・`frontend/src/app/registry/types.ts`・`frontend/src/shared/api-client/`・`vendor/make-you-chic-ui/`（変更しない）を確かめました。

ui の単位のため、成果物は `functional-spec.md`（画面の流れと状態の移り変わりの正本）・`frontend-components.md`・`traceability.json` です（`entities.md`・`rules.md` は作りません）。

## 設計の要点（案）

上流の決定とコードの確認から導ける、この単位の機能設計の見通しです。質問の答えで決まる点は（Qn）と書きます。

1. **置き場と登録**: 新しい機能 `frontend/src/features/invitation/`（featureId `invitation`）。`registration.ts` で画面 `/admin/invitations`（`layout: 'SHELL'`・`access: 'ADMIN'`）と、サイドバーの項目「利用者の招待」（`visibleWhen: 'ADMIN'`、order 220。既存の「管理」200・「DSL」210 の次）を登録する。骨組み（`src/app/`）と AdminArea（`features/admin`）は変えない（`unit-of-work.md` の「今回変更しない部品」）。ほかの機能（`features/dsl` など）のコードは読み込まない（今のコードに機能どうしの読み込みは無い）。
2. **部品の構成**: 画面 `InvitationAdminPage`（見出し「利用者の招待」・「招待する」・警告・結果の表示・一覧）の下に、`InvitationList`（素の `table` とページ送り）・`InviteDialog`（S1-M1）・`CancelConfirmDialog`（S1-M2）を置く。状態と API の呼び出しは1つのフック（`useInvitationAdmin`）にまとめ、部品は表示と操作の受け渡しだけにする（DSL の管理画面の `useDslAdmin` と同じ形）。
3. **API の呼び出し（C5）**: `features/invitation/api/invitationApi.ts` に、一覧（`GET /api/admin/invitations?page=n`）・招待（`POST`）・送り直し（`POST /{id}/resend`）・取り消し（`POST /{id}/cancel`）の4つを、既存の ApiClient 経由で置く。トークン・401 での更新・`Accept-Language`（U4 が付ける）は ApiClient に任せる。応答の型は C5 のとおり（`sendResult` は SENT・FAILED の2値、`expired` は真偽値、日時は ISO 8601 の UTC）。知らない項目は無視する。
4. **一覧の表示（AC2.1.1・AC2.1.2・AC2.1.8、CR6.5・CR6.6）**: 列はメールアドレス・言語・招待した管理者・招待した日時・有効期限・送信の結果・状態・操作。言語は U4 の `LANGUAGE_NAMES`（「日本語」「English」、`lang` 属性つき）。送信の結果は Badge で「送信済み」「送信に失敗」（AC2.1.1 の言葉。「成功」「届いた」とは書かない）。状態は Badge で**期限内の行にも「期限内」**、期限切れの行に「期限切れ」を文字で出す（AC2.1.2 は両方を文字で示すことを求めるため。画面イメージは期限切れの印だけだった）。色は補助で、文字だけで意味が分かる。長いメールアドレスは折り返す。
5. **招待した管理者（U3 の R-01 の直した後の形）**: `invitedBy` の値をそのまま出す（氏名だけ）。空の文字列（利用者がいないとき。今は起きない）は「（不明）」／「(Unknown)」と出す。画面の側でメールアドレスに切り替えることはしない。
6. **日時（CR6.8）**: 招待した日時と有効期限を、ブラウザのタイムゾーンで、画面の言語（`useDisplaySettings().language`）の書式で出す。書式と関数の置き場は（Q1）。
7. **並びとページ送り（Q7: B、AC2.1.5）**: 並びはサーバーの順（招待した日時の新しい順）のまま画面では並べ替えない。20 件ごとで、ページの数は `total` を 20 で割った切り上げ。ページ送りは「前へ」「次へ」のボタンと「2 / 3」、件数の範囲「21〜40 件目 / 全 43 件」を文字で示し、ページを変えた後に件数の範囲を `aria-live="polite"` で伝える。件数の範囲・ページの数・取り消しの後のページ（下の 12.）は純粋な関数にし、性質ベースのテスト（fast-check、失敗時の種を記録）の対象にする（`team.md`）。今のページの持ち方は（Q2）。
8. **状態（S1 の状態の表）**: 読み込み中（文字つき）・空（「招待中の人はいません。『招待する』から招待できます。」、AC2.1.4）・成功・失敗（`role="alert"` と「もう一度読み込む」）。一覧の読み直しが重なったときは、最後に始めた読み直しの答えだけを使う（前の答えは捨てる）。開いたままの間の期限切れの映り方は（Q3）。
9. **招待を使えないとき（FR1.8、AC1.1.6・AC2.2.9）**: 一覧の応答の `invitationEnabled` が false なら、画面の上に警告（Alert の警告の種類）を出し、「招待する」とすべての行の「送り直す」を押せなくする。「取り消す」は押せる（AC2.2.9）。警告は `unavailableReasons` ごとに文を分け、両方なら2つを並べる（最終の文言は下の表）。一覧をまだ読んでいない・読めなかった間は、使えるか分からないため「招待する」を押せなくする（読めなかったときは失敗の表示と「もう一度読み込む」が理由を示す）。設定は動いている間は変わらない（U3 の BR1.4）ため、警告は一覧を読むたびに応答の値で置き換える。

   | 理由 | 日本語 | 英語 |
   |---|---|---|
   | SMTP_NOT_CONFIGURED | 招待を使えません: メールの送り先が設定されていません。運用者に設定を依頼してください。 | Invitations are unavailable: the mail server is not configured. Ask the operator to configure it. |
   | BASE_URL_NOT_CONFIGURED | 招待を使えません: 招待のリンクに使うアプリの URL が設定されていません。運用者に設定を依頼してください。 | Invitations are unavailable: the application URL for invitation links is not configured. Ask the operator to configure it. |
   | 両方 | 見出し「招待を使えません」の下に、上の2つの理由（「招待を使えません: 」を除いた文）を並べる | 同じ形 |

10. **招待の入力（S1-M1、AC1.1.1・AC1.1.3・AC1.1.9）**: Modal を開くたびに、メールアドレスは空、言語は `useDisplaySettings().language`（ログインの後は管理者自身の言語、U4 の約束）で始める。画面で前もって確かめるのは「空（空白だけを含む）でない」ことだけとし、形式・長さ・改行はサーバー（U3 の BR1.1）の判定に任せる（既存のログインの画面の `validateLoginInput` と同じ考え方。画面とサーバーの判定の食い違いを作らない）。送る値は入れたまま（正規化はサーバー）。送信中は「招待する」を押せなくして「送信しています」と `aria-busy`、あわせて「やめる」・閉じるボタン・Esc でも閉じない（結果を必ず画面に出すため）。背景のクリックでは閉じない（画面イメージの決定）。
11. **招待の結果（C5 の応答ごと）**:

    | 応答 | 画面の動き | 出典 |
    |---|---|---|
    | 201・`sendResult` SENT | Modal を閉じ、Toast「招待を送りました」、一覧を1ページ目で読み直す（新しい招待は最も新しいため1ページ目に載る）。フォーカスは「招待する」へ | AC1.1.2・AC1.1.8 との差（`mockups.md` の 10 節） |
    | 201・`sendResult` FAILED | Modal を閉じ、一覧の上に `role="alert"`「招待は作りましたが、メールを送れませんでした。一覧から送り直せます。」、一覧を1ページ目で読み直す | AC1.1.5・AC1.1.7 |
    | 400 VALIDATION_FAILED | Modal を閉じず、メールアドレスの項目の下に「メールアドレスの形式が正しくありません。」（言語は選択肢から選ぶため誤りにならない。項目ごとの誤りの形に頼らない）、項目にフォーカス、入れた値は残す | AC1.1.3、CR6.1 |
    | 409 INVITATION_EMAIL_REGISTERED | Modal を閉じず、項目の下に「このメールアドレスの利用者はすでに登録されています。」 | AC1.1.4・AC1.1.10 |
    | 409 INVITATION_ALREADY_PENDING | Modal を閉じず、項目の下に「すでに招待中です。一覧から送り直してください。」とリンク「一覧でこの招待を見る」。押すと Modal を閉じ、応答の `page` のページを読み、`invitationId` の行を目立たせて行の「送り直す」にフォーカス（押せないときは行のメールアドレスのセル）。行がそのページに無ければ（ほかの操作で位置が動いた）表の見出しにフォーカス | AC1.1.4・AC1.1.13 |
    | 503 INVITATION_NOT_CONFIGURED | Modal の中に `role="alert"` で 9. の理由の文、入れた値は残す。閉じた後に一覧を読み直して警告を出す | AC1.1.6 |
    | 403・そのほかの 4xx・5xx・通信の失敗 | Modal の中に `role="alert"` で状態コードの種類ごとの一般の文言（DSL の管理画面の `failureMessageKey` と同じ考え方）、入れた値は残す | CR6.4 |
    | 401 | 既存の ApiClient の更新と、ログイン状態の変化によるログインの画面への移動に任せる | 既存の決まり |

    エラーの文言はサーバーの `detail` を使わず、`code` から画面の文言の鍵を選ぶ（前の Intent の DSL の画面と同じ）。通信の失敗の後にもう一度送り、実はサーバーで招待が作られていたときは INVITATION_ALREADY_PENDING の案内で一覧の行へ移れる。
12. **送り直し（AC2.2.1〜AC2.2.3・AC2.2.8・AC2.2.12）**: 押すとその行の「送り直す」と「取り消す」を押せなくし、「送り直す」を「送信しています」と `aria-busy` にする。ほかの行の操作は押せるまま。200・SENT は Toast「招待を送り直しました」、200・FAILED は一覧の上に `role="alert"`「招待を送り直しましたが、メールを送れませんでした。もう一度送り直せます。」。どちらも今のページを読み直し、同じ行の「送り直す」にフォーカスを戻す（送り直しでは招待した日時が変わらず、行の位置は変わらない）。404 INVITATION_NOT_FOUND は `role="alert"`「この招待は見つかりません。ほかの管理者が取り消したか、登録が完了した可能性があります。」と読み直し、503 は 9. の理由の文と読み直し、ほかは一般の文言。
13. **取り消し（S1-M2、AC2.2.4・AC2.2.10・AC2.2.11）**: 行の「取り消す」で確かめの Modal（`alertdialog`、本文にその行のメールアドレス、はじめのフォーカスは「やめる」、背景のクリックで閉じない、Esc と「やめる」で閉じて元の「取り消す」にフォーカスを戻す、CR6.7）。「取り消す」を押すと要求中はどちらのボタンも押せなくする。204 は Modal を閉じて Toast「招待を取り消しました」、今のページを読み直す。行が無くなるため、フォーカスは表の見出し（`caption`）に置き、一覧が空になったら空の表示の文に置く。今のページが最後のページを超えたら（最後の1件を取り消した）、1つ前のページを読む。404 は Modal を閉じて 12. と同じ見つからない旨と読み直し、ほかの失敗は Modal を閉じて一覧の上に `role="alert"`、フォーカスは元の「取り消す」へ。
14. **結果の表示の決まり（CR6.4）**: 成功は Toast（`aria-live="polite"`）だけ、失敗は一覧の上の `role="alert"` の表示に残す（閉じるボタン付き）。`role="alert"` の表示は1つだけにし、次の操作の結果で置き換える。表示にメールアドレス以外の個人に関する値・トークン・URL を載せない（一覧の応答にもトークンと URL は無い、AC2.1.7）。
15. **行のボタンの名前（AC2.1.6）**: 「a@example.test への招待を送り直す」「a@example.test への招待を取り消す」のように、見える文字は「送り直す」「取り消す」のまま、読み上げの名前にその行のメールアドレスを含める。
16. **表のアクセシビリティ**: `caption`「招待中の人」、列見出しは `th scope="col"`。狭い幅では表を横に動かして見る（`interaction-spec.md`）ため、表を包む領域にキーボードで届くようにし（`tabIndex=0` と名前）、横に動かせない問題（axe の scrollable-region-focusable）を避ける。目立たせた行（11. の案内から移った行）は色だけでなく枠の線でも示し、ページを変える・次の操作をするまで残す。
17. **文言**: 画面の文言は ja・en の両方を機能の文言（鍵は `invitation.` で始める）として持つ（NFR8）。言語の選択肢は `LANGUAGE_NAMES`（訳さない）。有効期限の長さ（24 時間）は画面の文言に書かない（U3 の R-02 で設定の値として差し込む形になり、画面は値を受け取らないため）。
18. **テスト**: 部品のテスト（Vitest・Testing Library・user-event、部品ごとに vitest-axe を1件、説明文は英語、対象と同じ場所の `*.test.ts(x)`）で、AC1.1.1・AC1.1.2・AC1.1.4〜AC1.1.9 の画面の部分、AC2.1.1・AC2.1.2・AC2.1.4・AC2.1.6〜AC2.1.8 の表示、AC2.2.3・AC2.2.4・AC2.2.8〜AC2.2.12 の画面の部分、CR6.1・CR6.3〜CR6.8 を確かめる。API は `invitationApi` の関数を差し替えて作る（前の Intent の DSL の画面のテストと同じ形）。日時の書式はタイムゾーンを固定して確かめる。フロントエンドのカバレッジの下限（行 80%・分岐 70%）を守る。招待から登録の完了までの E2E は U6 が持つ（`unit-of-work.md`）。
19. **上流との差（成果物に明記する）**: (a) AC1.1.8 の「成功の後もフォームが開いたまま」は、Refined Mockups の承認の決定（R-01）で「Modal を閉じて Toast、一覧に1行」に変わった。承認済みのストーリーは書き換えず差を記録する。(b) AC2.1.8・`mockups.md` の「氏名が得られないときはメールアドレス」は、U3 の R-01 の直しで「氏名だけ、無ければ空」になった（U2 で氏名は必須のため、今は起きない）。(c) 期限内の行にも「期限内」を出す（4.）。

## Q1. 招待した日時と有効期限を、どの書式で出し、書式の関数をどこに置きますか？

理由: CR6.8 は「ブラウザのタイムゾーンで、利用者の言語の書式」とだけ決めています。画面イメージは「09/25 21:00」の短い形でしたが、前の Intent の DSL の管理画面は年と時差の略号を付けた形（`2026-09-25 21:00 JST`・`Sep 25, 2026, 21:00 GMT+9`）で、その関数は `frontend/src/features/dsl/format.ts` にあります。今のコードに機能どうしの読み込みは無いため、同じ書式を使うなら置き場を決める必要があります。有効期限は日をまたぐことが多く、年や時差が無いと読み違えるおそれがあります。

## Q3. 一覧を開いたままの間に有効期限を過ぎた招待を、どう映しますか？
