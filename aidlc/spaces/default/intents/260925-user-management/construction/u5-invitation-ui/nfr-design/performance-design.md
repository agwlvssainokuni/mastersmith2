# Performance Design — U5 招待の管理の画面（u5-invitation-ui）

U5 の性能の設計です。U5 は画面の単位で、自分の API を持ちません。この文書では次の4つの作りを決めます。

- 一覧の読み方と描き方（重なった読み直し、読み直しの間の表示）
- 要求の待ちの見せ方と、画面の側に時間切れを置かないことの扱い
- 画面の時間（一覧 2 秒・次のページ 1.5 秒）の測り方と、21 件以上の招待の用意
- 初回の JavaScript の大きさ

答えは `nfr-design-questions.md` にあります（Q1: A、Q2: A、Q3: A、Consolidated Summary Confirmation: Looks correct）。

出典の略号:

- NFR: この単位の NFR 要件 `construction/u5-invitation-ui/nfr-requirements/` の枝番（この単位の中で振った番号）
- D・W・4.1・6節: この単位の機能設計 `construction/u5-invitation-ui/functional-design/functional-spec.md`
- 部品 n節: 同じフォルダの `frontend-components.md`
- 要点 n: この段の `nfr-design-questions.md` の「NFR 設計の要点（案）」の番号
- U3・U4 の NFRx.y: それぞれの単位の `nfr-requirements/` の枝番

この単位（種類 ui）の成果物と置き場は、次の表のとおりです。拡張性・信頼性・観測性の設計は service の単位だけが作ります。U5 での扱いは `logical-components.md` の4節に書きます。

## 1. 予算の前提

| 項目 | 値 | 持ち主 |
|---|---|---|
| 一覧（`GET /api/admin/invitations`）・取り消し | 同時 10 件で p95 1 秒 | U3 の NFR6.3 |
| 招待・送り直し（SMTP の送信を含む） | 同時 10 件で p95 5 秒 | U3 の NFR6.1 |
| 受け手が応答しないとき | U1 の時間切れ（3 秒）の後に `sendResult` FAILED。応答の手前で遅れ続ける受け手では時間切れの数倍になりうる | U3 の NFR6.2、U1 の NFR6.3 |
| 一覧の1ページ目が出るまで | 手元の PC のブラウザで 2 秒以内 | この単位の NFR6.1 |
| 次のページが出るまで | 1.5 秒以内 | この単位の NFR6.2 |

- 1ページは最大 20 行で、描く量は小さい。画面の待ちは主に一覧の API の時間と、初めて開くときの画面の塊（遅延読み込み）の読み込みです。
- API の時間は Performance Validation の段の k6 で測ります（U3 の持ち主）。この文書の測定は、それに画面の側の時間を足した利用者の体感の時間です。

## 2. 一覧の読み方と描き方（NFR6.3、D1・D2・4.1）

### 2.1 作り

| 項目 | 作り |
|---|---|
| 読む時点 | 画面を開いたとき・ページを変えたとき・操作（招待・送り直し・取り消し）の応答を受けた後・「もう一度読み込む」のときだけ。決まった間隔の読み直しはしない |
| 1ページの量 | 20 行（`paging.ts` の `PAGE_SIZE`）。サーバーの順のまま描き、画面で並べ替えない |
| 重なった読み直し | `useInvitationAdmin` が読み直しごとに番号を増やし、答えが来たときに番号が最後のものと一致するときだけ使う。画面を離れた後（部品を外した後）の答えは捨てる（`useDslAdmin` の `statusSeq`・`mounted` と同じ形） |
| 読み直しの間の表示 | 一度読めた後の読み直しの間は、Table とページ送りのボタンを描いたまま `data` を空にする。最初の読み込み・空・読めなかったときだけ Table を描かない（4.1） |
| 中断 | 古い要求を `AbortController` で止めない。答えを捨てるだけにする（ApiClient を変えないため。要点 2） |

```ts
// 重なった読み直しの扱い（設計の意図を示す例。実装はコード生成で書く）
const seq = ++loadSeq.current
const result = await api.listInvitations(page).then(ok, fail)
if (!mounted.current || seq !== loadSeq.current) return // 古い答え・離れた後は捨てる
applyListResult(result)
```

### 2.2 確かめ

| 確かめ | 置き場 |
|---|---|
| 2つの読み直しを重ね、先の答えを後に返しても、後の読み直しの答えだけが表示される | `InvitationAdminPage` の画面部品のテスト |
| 部品を外した後に答えを返しても、状態が変わらず警告も出ない | 同上 |
| 読み直しの間も Table とページ送りのボタンが残る | `InvitationList` の画面部品のテスト |
| 偽の時計（`vi.useFakeTimers`）を数分進めても、一覧の API が追加で呼ばれない | `InvitationAdminPage` の画面部品のテスト |

## 3. 待ちの見せ方と時間切れ（NFR6.4・NFR6.5、D9）

| 場面 | 作り |
|---|---|
| 招待の送信中 | 「招待する」を Button の `loading` にして「送信しています」。フォーカスは「招待する」に残る。「やめる」は `disabled`。Esc・閉じるボタンの `onClose` を無視し、Modal を閉じない |
| 取り消しの要求中 | 「取り消す」を `loading` にして「取り消しています」。「やめる」は `disabled`。Modal を閉じない |
| 送り直しの処理中 | その行の「送り直す」を `loading`、その行の「取り消す」だけを `disabled`。ほかの行は押せるまま（`resendingIds` の集合、複数の行を同時に送り直せる） |
| 時間切れ | 画面の側に時間切れ・中断・再試行を置かない。待ちの上限はサーバーの時間切れ（U1 の SMTP の時間切れ）に任せる |

- 受け手が応答の手前で遅れ続ける既知の限界（U1 の NFR6.3）の間は、招待の Modal が「送信しています」のまま閉じられません。画面の単位ではこの限界を変えず、失敗の範囲として `logical-components.md` の3節に書きます。配備先が決まり U1 の NFR6.3 を見直すときに、画面の側の扱いも合わせて見直します。
- 確かめは、要求にまだ答えを返さない状態で、表示・`aria-busy`・フォーカス・閉じないことを見る画面部品のテストです（`InviteDialog`・`CancelConfirmDialog`・`InvitationList`）。

## 4. 画面の時間の測り方（NFR6.1・NFR6.2、Q2: A・Q3: A）

### 4.1 置き場

- U5 の実際のブラウザの検査のファイル（`logical-components.md` の5節、`050-` の後の番号の新しいファイル）の中に、測定のテストを1件置きます。E2E-1（U6）は変えません。
- 流れの E2E ではないため、`team.md` の「代表の流れを1本まで」の本数に数えません（NFR9.9）。
- 一覧の API の答えは差し替えず、本物のサーバーの一覧を読みます（差し替えると API の時間が入らないため）。見た目の設定（`/api/appearance`）も差し替えません（U4 の `performance-design.md` の3節と同じ）。

### 4.2 招待の用意

| 手順 | 作り |
|---|---|
| 1. 前提の確かめ | テストの初めに、そのテストの要求の口（Playwright の `request`）で管理者としてログインの API（`POST /api/auth/login`）を呼び、応答のアクセストークンを得る。続けて一覧の API を読み、`invitationEnabled` が偽なら、測定を行わずに `test.skip` にして理由（招待を使える設定が無い）を注記に残す。Build and Test はこれを `Unverified` とし、持ち主の段（Build and Test）を明記して引き継ぐ |
| 2. 21 件を置く | 招待の API（`POST /api/admin/invitations`）で 21 件を置く。メールアドレスは実行ごとに重ならない値で、予約済みのドメイン `example.com` の下（例: 実行の印と番号を組み合わせた `u5-perf-<印>-<番号>@example.com`）。言語は `ja` |
| 3. 応答の確かめ | 各応答が 201 であることを確かめる。`sendResult` は SENT・FAILED のどちらでもよい（受け手に届かなくても招待は置かれる） |

- 置く方法を API にしたのは、Modal の操作を 21 回繰り返すと準備が長くなるためです（Q2: A）。メールの送信と監査は本物と同じ道を通ります。
- メールは E2E が起動した WAR に渡した受け手だけに送られます。実在の宛先・外部の SMTP へは送りません（`team.md` の Deployment、`project.md` の Forbidden）。受け手の設定の渡し方は infrastructure-design の持ち主です。
- アクセストークンは、そのテストの変数だけに持ち、注記・添付・ログに出しません。
- 置いた招待は、同じ WAR と内部DB を使う後のファイルに残ります。後のファイル（U6 の E2E-1 など）は一覧の件数や順に頼らない作りにします（U4 の NFR9.11）。これは B5 のコード生成の計画で U6・U7 とそろえます（`logical-components.md` の5.1）。

### 4.3 手順

5回の繰り返しの1回ごとに、次を行います。

1. `browser.newContext()` で、キャッシュが空の新しいコンテキストを作る。
2. ログインの画面のフォームから管理者でログインし、骨組みの画面が出るまで待つ（Q3: A。`logical-components.md` の5.4）。
3. サイドバーの「利用者の招待」を押す直前から、一覧の 20 行目が見えるまでの時間を、テストの側の時計で測る（NFR6.1 の「サイドバーの項目を選んでから」）。
4. 「次へ」を押す直前から、2ページ目の最初の行が見えるまでの時間を測る（NFR6.2）。
5. 「前へ」で1ページ目へ戻し、コンテキストを閉じる。

- 「見える」は、Playwright の要素の見え方の待ち（`toBeVisible`）が通った時点です。テストの側の時計は待ちの間隔を含むため、実際より長めに出ます。長めに出る側で判定します。
- 20 行目と2ページ目の最初の行は、行の数ではなく、表の本文の行の位置（`nth`）で待ちます。一覧の順はサーバーの順のため、特定のメールアドレスの行には頼りません（後のファイルと同じ考え方）。
- 画面の塊は新しいコンテキストごとに読み直されるため、各回の一覧の時間には遅延読み込みの塊の読み込みが入ります（悪い側の条件）。

### 4.4 記録

- 5回の値（一覧・次のページ）を、テストの注記（`test.info().annotations`）と添付（JSON）で残し、Build and Test の結果に写します。
- 時間で失敗させません（統合の関門にしない。NFR6.1・NFR6.2）。目標を超えたときは目標を緩めず、要求の一覧で一覧の API の時間と画面の描画のどちらが遅いかを確かめ、結果とともに依頼者に相談します（NFR 要件の2節）。
- 長い計測は `caffeinate -i` を付けて流します（`project.md` の Testing Posture）。

## 5. 初回の JavaScript の大きさ（NFR6.6、要点 5）

- 画面は機能の登録で遅延読み込み（`lazy`）の塊に入れ、入口のファイルを増やしません（DSL の画面と同じ）。
- U5 は新しい依存を足しません（NFR9.4）。`formatDateTime` の置き場を `frontend/src/shared/format/` へ移しても、入口から静的に読み込まれるかどうかは読み込む側で決まり、DSL と招待の画面の塊に入ります。
- 既存の `frontend/scripts/check-bundle-size.mjs`（`./gradlew verify` の中、gzip で 500KB の目安、超えたら警告だけ）で、U5 の変更の前後の値をコード生成で記録します。あわせて、U5 の画面の塊が入口と別のファイルに出ることと、その塊の大きさ（圧縮前と gzip）を記録します。上限は置きません。

## 6. 上流との差

承認済みの文書は書き換えません（`aidlc/spaces/default/memory/project.md` の Way of Working）。

| 決定 | 文書 | 承認済みの記述 | この段での扱い |
|---|---|---|---|
| 測る場を U5 の検査のファイルに決めた（Q2: A） | NFR 要件の NFR6.1 | どの検査のファイルで測るか（Playwright＋axe-core の検査か E2E-1 か）はコード生成で決める | この段で前倒しで決めた。E2E-1 は変えない。食い違いではない |
| 招待の用意を API で行う（Q2: A） | NFR 要件の NFR6.1 | 招待は測る前にその検査の中で自分で用意する | 用意の手段を招待の API に決めた。NFR 要件のとおりで、食い違いではない |
| 招待を使える設定が無いときは測定を飛ばして `Unverified` で引き継ぐ（Q2: A） | NFR 要件の前提（E2E の WAR の設定は infrastructure-design） | 前提として書かれていた | 設定が無いときの扱いを決めた。目標を緩めず、Build and Test で `Unverified` とし持ち主を明記する（`project.md` の Testing Posture）。追加 |
| 測定のテストで要求の口からログインの API を呼ぶ | この段の Q3: A | 画面はログインの画面から開く | Q3 A は画面の開き方の決定で、準備の要求（招待を置くためのトークンの取得）には当てない。画面の計測の各回は Q3 A のとおりログインの画面から開く。食い違いではない |
| 古い読み直しを中断せず答えを捨てるだけにする | 機能設計の D2 | 最後の読み直しの答えだけを使い、離れた後の答えを捨てる | 捨て方を番号と部品の状態に決めた。D2 のとおりで、食い違いではない |
