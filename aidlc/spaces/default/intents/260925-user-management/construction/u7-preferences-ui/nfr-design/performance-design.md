# Performance Design — U7 プリファレンスとパスワードの変更の画面（u7-preferences-ui）

U7 の性能の設計です。U7 は画面の単位で、自分の API を持ちません。この文書では次の4つの作りを決めます。

- 画面を開くときの要求の数と、答えの捨て方
- 送信の間の表示と二重送信の防止、画面の側に時間切れ・中断を置かないこと
- 画面の時間（開く 2 秒・保存 1.5 秒・パスワードの変更 2.5 秒）の測り方と、測りに使う利用者の作り方
- 初回の JavaScript の大きさ

答えは `nfr-design-questions.md` にあります（Q1: A、Q2: A、Q3: A、Consolidated Summary Confirmation: Looks correct）。

出典の略号:

- NFR: この単位の NFR 要件 `construction/u7-preferences-ui/nfr-requirements/` の枝番（この単位の中で振った番号）
- D・W・6節・9節・10節: この単位の機能設計 `construction/u7-preferences-ui/functional-design/functional-spec.md`
- 部品 n節: 同じフォルダの `frontend-components.md`
- 要点 n: この段の `nfr-design-questions.md` の「NFR 設計の要点（案）」の番号
- R-01・R-02: NFR 要件の段のレビューの Minor の指摘（承認の場で Accepted risk）
- U2・U4・U5 の NFRx.y と NFR 設計: それぞれの単位の `nfr-requirements/`・`nfr-design/`

この単位（種類 ui）の成果物と置き場は、次の表のとおりです。拡張性・信頼性・観測性の設計は service の単位だけが作ります。U7 での扱いは `logical-components.md` の4節に書きます。

## 1. 予算の前提

| 場面 | 画面の目標 | 中に入るもの | 押さえ |
|---|---|---|---|
| プリファレンスの画面を開く | 2 秒（NFR6.1） | 画面の塊の遅延読み込み、`GET /api/me/preferences` 1回、フォームの描画 | GET は U2 の NFR6.1（同時 10 件で p95 1 秒） |
| パスワードの変更の画面を開く | 2 秒（NFR6.1） | 画面の塊の遅延読み込み、フォームの描画。API は呼ばない | — |
| 保存 | 1.5 秒（NFR6.2） | `PUT /api/me/preferences` 1回、`applyUserPreferences` の後の描画、Toast | PUT は U2 の NFR6.2（p95 1 秒） |
| パスワードの変更 | 2.5 秒（NFR6.3） | `POST /api/me/password` 1回（bcrypt 2回）、Toast | U2 の NFR6.3（p95 2 秒） |

- 画面の側の処理は小さい（フォームの項目は最大4つ、確かめは純粋な関数）。画面の時間の多くは API の時間と遅延読み込みです。
- API の時間は U2 の目標で押さえ、U7 では k6 で測りません（NFR6.4）。

## 2. 画面を開くときの読み込み（NFR6.4、D1・W2・W9）

| 項目 | 作り |
|---|---|
| 読み込みの開始 | `usePreferencesForm` が、部品が付いたときに `GET /api/me/preferences` を始める。パスワードの変更の画面（`usePasswordChangeForm`）は開いても API を呼ばない |
| 重なった読み込み | 読み込みごとに番号を増やし、答えの番号が最後に始めたものと一致するときだけ使う（部品 3節）。開発時の StrictMode の二重の実行で要求が2本になっても、使う答えは1つだけ。「もう一度読み込む」も同じ番号で扱う |
| 離れた後の答え | 部品が付いているかの印で、離れた後の読み込みの答えを捨てる（W2 の6） |
| 読み込みの間 | フォームを出さず「読み込んでいます」を出す（D1）。値の無いフォームで保存できない |
| 読んだ値のそろえ | 読んだ値が当たっている値と違えば、同じ答えの中で `applyUserPreferences` を1回呼ぶ（D2）。要求は増えない |

- 本番の作りでは要求の数は画面を開くたびに1回です。StrictMode の二重の実行は開発時だけで、画面部品のテスト（StrictMode なし）では GET が1回だけ呼ばれることを見ます（NFR6.4）。

## 3. 送信の間と二重送信の防止（NFR6.5、D10）

| 項目 | 作り |
|---|---|
| 送信中の印 | フックの中で、送信中の印を描画の外の値（`useRef`）に持つ。`save()`・`submit()` は、印が立っていれば何もせずに戻り、立っていなければ同じ呼び出しの中で印を立ててから要求を始める。答えが来たら（成功・失敗とも）印を下ろす |
| 状態だけで持たない理由 | 状態（`useState`）の更新は次の描画まで見えない。描画の前に2回目のクリック・Enter が来ると、状態だけの印では止められない |
| 画面の表示 | 状態の `saving`・`sending` で、Button の `loading`（`aria-disabled`・`aria-busy`、文言「保存しています」「変更しています」）、文字の項目の `readOnly`、「元に戻す」の `disabled` を描く。ラジオの組は `disabled` にせず、フックが送信の間の選択を受け付けない（D10） |
| 時間切れ・再送・中断 | 画面の側に置かない。既存の ApiClient も持たない。待ちの上限はサーバーと通信の側に任せる |
| 離れた後の答え | 部品が付いているかの印で見分ける。パスワードの変更は捨てる（W10 の5）。保存は 200 のときだけ `applyUserPreferences` を呼び、Toast とフォーカスの移動はしない（W6 の3）。失敗は捨てる |

```text
// 送信中の印の考え方（説明用の擬似コード。名前は仮）
const inFlight = useRef(false)
async function save(): Promise<void> {
  if (inFlight.current) return
  const problems = validateForm(form)          // 共用の確かめの関数（U6）
  if (problems.length > 0) { showProblems(problems); return }
  inFlight.current = true
  setSaving(true)
  try { handleResult(await putPreferences(form)) }
  finally { inFlight.current = false; if (mounted.current) setSaving(false) }
}
```

- 確かめは画面部品のテストで、偽の API に答えを返さない状態でボタンを続けて押す・文字の項目で Enter を押しても、API の関数の呼び出しが1回だけであることを見る（NFR6.5）。

## 4. 画面の時間の測り方（NFR6.1〜NFR6.3、Q1: A、R-01）

### 4.1 置き場

- U7 の実際のブラウザの検査のファイル（`logical-components.md` の5節。`050-` の後の番号の新しいファイル、例 `05x-preferences-accessibility.e2e.ts`）の中に、測りのテストを1件置きます。NFR 要件の承認の場の R-01（置き場を決める）は、この決定で閉じます。
- 流れの E2E ではないため、`team.md` の「代表の流れを1本まで」の本数に数えません（NFR9.9）。E2E-1（U6）は変えません。
- 測りは本物の応答で行います。`/api/me/preferences`・`/api/me/password`・`/api/appearance` を差し替えません（差し替えると API の時間が入らないため。U4 の `performance-design.md` の3節と同じ）。
- ファイルの番号と並び、共用の手伝いに足す関数の形は、B5 のコード生成の計画で U5・U6 とそろえて決めます（`logical-components.md` の 5.1）。

### 4.2 測りに使う利用者の用意

承認済みの NFR6.3 のとおり、測りのテストが自分で作った利用者で測ります。初期管理者の設定とパスワードは変えません。

| 手順 | 作り |
|---|---|
| 1. 前提の確かめ | そのテストの要求の口（Playwright の `request`）で、初期管理者としてログインの API（`POST /api/auth/login`）を呼び、アクセストークンを得る。招待の一覧の API で招待を使える設定（`invitationEnabled`）を確かめ、偽なら測りを行わずに `test.skip` にして理由を注記に残す（U5 の `performance-design.md` の 4.2 と同じ扱い）。受け手からリンクを取り出す手段が使えないときも同じく飛ばす |
| 2. 招待 | 招待の API（`POST /api/admin/invitations`）で1件を置く。メールアドレスは実行ごとに重ならない `example.com` の値（例: `u7-perf-<実行の印>@example.com`）、言語は `ja`。201 と `sendResult` SENT を確かめる |
| 3. リンクの取り出し | E2E が起動した WAR の手元の受け手から、そのメールアドレス宛ての招待のメールを読み、`#token=` の値を取り出す。手段は U6 の E2E-1 と同じもので、infrastructure-design の決定に頼る |
| 4. 登録の完了 | 登録の完了の API（`POST /api/registration/complete`、C6）を、要求の口から呼ぶ。パスワードは実行ごとに作る値（`randomBytes` から作る、12 コードポイント以上 72 バイト以下）、テーマ `light`・文字の大きさ `md`・言語 `ja`。204 を確かめる |
| 5. 変更の後のパスワード | パスワードの変更の測りで交互に使う2つ目のパスワードも、実行ごとに作る |

- 登録の完了は画面ではなく API で行います。画面の流れは E2E-1（U6）が確かめるためで、測りの準備を短くします。メールの送信・招待の消費・利用者の作成・監査は本物と同じ道を通ります。
- アクセストークン・招待のトークン・パスワードは、そのテストの変数だけに持ち、注記・添付・ログに出しません（`security-design.md` の6節）。
- 作った利用者と招待は、同じ WAR と内部DB を使う後のファイルに残ります。後のファイルは利用者や招待の件数・順に頼らない作りにします（U4 の NFR9.11、U5 の 4.2 と同じ）。

### 4.3 手順

3つの場面を、それぞれ5回ずつ測ります。

| 場面 | 1回ごとの手順 | 測る区間 |
|---|---|---|
| 開く（NFR6.1） | `browser.newContext()` でキャッシュの空の新しいコンテキストを作り、ログインの画面から作った利用者でログインし、骨組みの画面が出るまで待つ（時間に入れない）。ユーザーメニューを開く。2つの画面は、それぞれ別の新しいコンテキストで5回ずつ測る（1回の測りに1つのコンテキスト） | ユーザーメニューの項目（「プリファレンス」または「パスワードの変更」）を押す直前から、「保存する」または「変更する」のボタンが見えるまで |
| 保存（NFR6.2） | プリファレンスの画面を開いた状態で、テーマを今の値と違う値（`light` と `dark` を回ごとに交互）に選ぶ | 「保存する」を押す直前から、Toast「保存しました」が見えるまで |
| パスワードの変更（NFR6.3） | パスワードの変更の画面で、今のパスワードと新しいパスワードを回ごとに入れ替えて3つの項目を埋める | 「変更する」を押す直前から、Toast「パスワードを変更しました」が見えるまで |

- 「見える」は、Playwright の見え方の待ち（`toBeVisible`）が通った時点です。テストの側の時計は待ちの間隔を含むため、実際より長めに出ます。長めに出る側で判定します。
- 開くの測りは、回ごとに新しいコンテキストを使うため、画面の塊の遅延読み込みが毎回入ります（悪い側の条件。NFR6.1 の「遅延読み込みを含む」）。
- 保存とパスワードの変更の測りは、1つのコンテキストの中で5回続けて行います。パスワードの変更は1回ずつ順に送り、同じ利用者で同時に送りません（U2 の条件つきの更新に当たらない。U2 の `performance-design.md` と同じ考え方）。5回目の後の利用者のパスワードは、どちらでもよい（後のファイルは使わない）。
- 保存の測りで言語は変えません（Toast の文言を日本語のまま待つため）。
- WAR はヘルスチェックが通った後に測ります（`playwright.config.ts` の `webServer.url`）。

### 4.4 記録

- 場面ごとの5回の値を、テストの注記（`test.info().annotations`）と添付（JSON）で残し、Build and Test の結果に写します。
- 時間で失敗させません（統合の関門にしない）。目標を超えたときは目標を緩めず、要求の一覧で API の時間・画面の塊の読み込み・描画のどこが遅いかを確かめ、結果とともに依頼者に相談します（NFR 要件の2節）。
- 4.2 の1で飛ばしたときは、Build and Test が NFR6.1〜NFR6.3 を `Unverified` とし、持ち主の段（Build and Test）と理由を明記して引き継ぎます（`project.md` の Testing Posture）。
- 長い計測は `caffeinate -i` を付けて流します。

## 5. 初回の JavaScript の大きさ（NFR6.6）

- 2つの画面は `registration.ts` の画面の登録で `React.lazy` の遅延読み込みにし、入口から静的に読み込まない。`features/preferences` の部品を `frontend/src/app/` やほかの機能から静的に読み込まない。
- 骨組みの変更（`types.ts`・`validateRegistrations.ts`・`ShellLayout.tsx`）は入口の塊に入るが、数行の型と判定の追加だけです。
- 既存の `frontend/scripts/check-bundle-size.mjs`（`./gradlew verify` の中、gzip 500KB の目安で警告だけ）で、U7 の変更の前後の値をコード生成で記録します。上限は変えません。
