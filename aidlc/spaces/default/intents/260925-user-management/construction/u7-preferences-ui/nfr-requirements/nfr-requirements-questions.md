## NFR の要点（案）

1. **性能（API の時間）**: 画面の待ちは U2 の API の目標で押さえる。プリファレンスの取得・保存は同時 10 件で p95 1 秒（U2 の NFR6.1・NFR6.2）、パスワードの変更の成功は p95 2 秒（U2 の NFR6.3）、今のパスワードの誤り・入力の誤りは p95 1 秒（U2 の NFR6.4）。測るのは Performance Validation の段の k6 で、U7 では測らない。
2. **性能（画面の時間）**: U5〜U7 に共通する依頼者の決定（U5 の段）に合わせ、画面の時間の目標を置く。Build and Test で実際のブラウザで場面ごとに5回ずつ測って記録し、統合の関門にはしない（U4 の Q1 B、U5 の一覧 2 秒・次のページ 1.5 秒と同じ扱い）。プリファレンスの画面は開くたびに1回だけ GET を送り（D1）、読み終わるまでフォームを出さない。パスワードの変更の画面は開いても API を呼ばない（W9）。場面と値は Q1 で決める。
3. **性能（送信中の表示と二重送信の防止）**: パスワードの変更は成功で最大 2 秒ほど待つため、送信の間は make-you-chic-ui の Button の `loading`（`aria-disabled`・`aria-busy`、文言「変更しています」「保存しています」）で示し、ボタン・Enter のどちらでも二重に送らない。送信の間は文字の項目を `readOnly`、ラジオの選択を受け付けない（D10）。画面の側に独自の時間切れや再送は足さない（既存の ApiClient のまま）。部品のテストで、送信の間に押しても・Enter でも要求が1回だけであることを確かめる（`frontend-components.md` の 7節）。
4. **性能（初回の JavaScript の大きさ）**: 2つの画面は既存の画面と同じく遅延読み込み（`React.lazy`）で登録し、初回の読み込みの JavaScript を増やさない。既存の目安（gzip で 500KB 以内、超えたら警告で統合は止めない）をそのまま当てる。新しい依存は足さない。
5. **セキュリティ（パスワードの値）**: 3つのパスワードの値は React の状態（メモリ）だけに持ち、localStorage・sessionStorage・Cookie・URL に置かない。成功で3つを空に戻す（W10）。失敗の文言はサーバーの `detail` を使わず、応答の値と入力の値をブラウザのコンソールに出さない（D13、`project.md` の Forbidden）。3つの項目は `type="password"` と `autocomplete`（`current-password`・`new-password`）を付ける（CR6.9）。コード生成のテストで、送信の前後と失敗の後に、ブラウザの保存（localStorage・sessionStorage）のどの鍵にもパスワードの値が入らず、コンソールに出力が無いことを確かめる。
6. **セキュリティ（プリファレンスの値の保存）**: ブラウザに保存するのは U4 の鍵の3つの表示の設定だけで、U7 は保存に直接触れない（保存は U4 の `applyUserPreferences` が行う、U4 の NFR の要点 5）。氏名は保存に置かない。
7. **セキュリティ（今のパスワードの誤りとログイン状態）**: 今のパスワードの誤りは 400 `PASSWORD_CURRENT_MISMATCH` で、ApiClient の 401 の更新の流れに乗らず、ログインしたままでログインの画面へ移らない（AC5.1.6）。今のパスワードの誤りの回数の制限は置かない（U2 の決定のまま）。画面の側の確かめはサーバーの確かめの代わりにしない（D7・D8。サーバーの 401・200 は U2 のサーバー側のテスト、NFR4）。
8. **セキュリティ（骨組みの変更の影響）**: ユーザーメニューの `path` の項目（9節）は、登録された画面の URL だけを許し（登録の検査で起動を止める）、外の URL へ移る道を作らない。既存の `validateRegistrations.test.ts`・`ShellLayout.test.tsx`・`navigationItems.test.ts` に足し、既存のログアウトの項目が変わらず動くことを確かめる。画面・認証に関わる変更のため、統合の前に既存の E2E（`./gradlew e2eTest`）を手元で流す（`team.md`）。
9. **アクセシビリティ**: 目標は WCAG 2.1 AA（U4 の NFR7.1）。画面部品（`PreferencesPage`・`PasswordChangePage`）ごとに vitest-axe の検査を1件入れ、違反 0 件（NFR7、`team.md`）。実際のブラウザの検査（U4 の NFR7.3。テーマ2×文字の大きさ3の6組と、ブランドカラー4×テーマ2の8組で axe-core の違反 0 件と横のはみ出しが無いこと）に、プリファレンスとパスワードの変更の2つの画面を B5 で足す（U4 の NFR7.5）。ログインの後の画面のため、検査は利用者などの前提を自分で作る（U4 の NFR9.11）。
10. **狭い幅（768px 未満）**: `interaction-spec.md` のとおり1列に積み、ラジオの選択肢は折り返す。U5〜U7 に共通する依頼者の決定（U5 の段）に合わせ、U4 の Playwright＋axe-core の検査（U4 の NFR7.3）に幅 375px を1つ足し、テーマ2×文字の大きさ3の6組で、横にはみ出さないことと axe の違反 0 件を確かめる。B5 で、U7 のプリファレンスとパスワードの変更の2つの画面にも当てる（U5・U6 の画面と同じ）。U4 の NFR 要件の 6節で B5 の計画に持ち越していた点は、この決定で決まった。
11. **多言語**: U7 が足す文言（`preferences.` で始まる鍵）は ja・en の両方を用意し、鍵をそろえる（NFR8）。言語の選択肢の名前は U4 の固定の値（U4 の NFR8.2）を使う。理由と項目の名前のすべての組が ja・en に文言を持つことをテストで確かめる（`errorMessages.ts`）。
12. **テストとカバレッジ**: フロントエンドのカバレッジの下限（行 80%・分岐 70%）を守り、計測の除外を増やさない（NFR9、`team.md`）。性質ベースのテスト（fast-check、失敗時の種を記録）を、項目ごとの誤りの読み取り（`fieldErrors.ts`）に当てる。共用の確かめの関数の境界と性質ベースのテストは U6 が持つ。`team.md` のパスワードの変更の必須テスト（今のパスワードの確かめ・規則の境界・変更の後のリフレッシュトークン）のうち、サーバーの判定は U2 が持ち、U7 は画面の確かめの境界（11・12 コードポイント、72・73 バイト）と今のパスワードの誤りの表示を画面のテストで確かめる。E2E の流れは足さない（この Intent の1本は U6）。
13. **traceability の見込み**: U7 に当たる要件の非機能は NFR6（画面の時間の目標（Q1）、API の時間は U2 の目標、送信中の表示）・NFR7（アクセシビリティ）・NFR8（文言）・NFR9（テスト・カバレッジ・既存の E2E）。NFR2（U7 はメールアドレスを扱わない。パスワードの値の扱いは NFR9 の枝番とセキュリティの要件に書く）・NFR1・NFR3・NFR4（サーバー側の認可は U2）・NFR5・NFR10・NFR11 は `N/A` とし、理由を書く。

## Q1. U7 の2つの画面の時間の目標を、どの場面にいくつ置きますか？

理由: U5〜U7 に共通する決定で、画面の時間の目標を置き、Build and Test の実際のブラウザで5回ずつ測って記録し、統合の関門にはしないことになりました（要点 2）。U5 は、画面を開いて一覧が出るまで 2 秒（遅延読み込みと API 1回を含む）、次のページが出るまで 1.5 秒（API 1回だけ）です。U7 の API の目標は、プリファレンスの取得・保存が p95 1 秒、パスワードの変更の成功が p95 2 秒（bcrypt を2回計算するため）です（U2 の NFR6.1〜NFR6.3。どれも同時 10 件のときの値で、画面の測定は1人で操作するため、ふつうはこれより短くなります）。パスワードの変更の画面は、開いても API を呼びません。測る場面の区切り（押してから Toast が出るまで など）は、どの選択肢でも同じにします。

- A. 次の3つの場面に目標を置く。(1) 開く: ユーザーメニューで選んでから、プリファレンスの画面のフォームが出るまで・パスワードの変更の画面の項目が出るまで、どちらも 2 秒（U5 の一覧と同じ。遅延読み込みと、プリファレンスは GET 1回を含む）。(2) 保存: 「保存する」を押してから、保存の結果が画面に当たり Toast が出るまで 1.5 秒（U5 の次のページと同じ。PUT 1回）。(3) パスワードの変更: 「変更する」を押してから Toast が出るまで 2.5 秒（API の目標 2 秒に、U5 の 1.5 秒と 1 秒の差と同じ 0.5 秒の余裕を足す）（推奨）
- B. 開く場面（A の (1)、2 秒）だけに目標を置く。保存とパスワードの変更の送信の後は、U2 の API の目標（p95 1 秒・2 秒）で押さえ、画面では測らない
- C. A と同じ3つの場面に目標を置くが、パスワードの変更も 1.5 秒にそろえる（bcrypt を2回計算するため、API の目標 2 秒より厳しく、1人の操作でも超えうる）
