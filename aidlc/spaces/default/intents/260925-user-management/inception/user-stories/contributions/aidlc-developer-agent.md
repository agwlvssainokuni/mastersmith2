### 6. 判断が要る点

依頼者の答えを変えずに、リードまたは依頼者が決める必要がある点。いずれも「どちらの立場も成り立つ」。

- **J1 招待メールの有効期限の表示**: 保存は UTC（`project.md` の Corrections）だが、招待された人には利用者の設定が無い。表示のタイムゾーンを、固定（例: Asia/Tokyo）・招待の言語で決める・UTC と明記する、のどれにするか。決まらないと AC3.1.2 の期待値が書けない。
- **J2 招待メールに差し込む利用者の値**: 招待した管理者の氏名（プリファレンスで利用者が入れる値）や招待先のメールアドレスを本文・件名に入れるか。入れないとエスケープとヘッダーへの差し込みのテスト（`team.md` の必須）の対象がリンクと期限だけになる。
- **J3 2回入力の一致の確かめの場所**: 画面だけで確かめてサーバーには1つだけ送るか、サーバーにも2つ送って確かめるか。FR4.4・FR6.2 は場所を決めていない。「前提と読み方」の「拒否される」（Problem Details で返る）を当てるならサーバー側になる。
- **J4 登録の完了の時点で同じメールアドレスの利用者がいるとき（AC3.2.10）の応答**: 期限切れ・存在しない招待などと同じ応答にする（列挙の防止を優先、NFR3）か、理由の分かる応答にするか。
- **J5 リンクを開いたとき（トークンの確かめ）の失敗を監査に残すか**: FR9.1 は「登録の失敗」を残すとしている。確かめの要求は公開で、ログインなしで何度でも呼べるため、開いたときの失敗まで残すと追記だけの監査の表が外から増やせる。完了の要求の失敗だけを残すことを提案する。
- **J6 ログインしていない要求のエラーの説明文の言語**: 登録の完了の画面（招待の言語）とログインの画面（最後に保存された言語）の API の呼び出しに、画面の表示言語を `Accept-Language` として付けるか、今までどおりブラウザの言語に任せるか。FR7.2 は「今までどおり `Accept-Language`」とだけ書いている。
