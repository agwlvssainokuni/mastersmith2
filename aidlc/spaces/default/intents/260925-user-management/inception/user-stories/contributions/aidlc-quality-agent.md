## Contribution

品質担当として、下書き（`aidlc/spaces/default/intents/260925-user-management/inception/user-stories/stories.md`）の受け入れ基準を、合否がはっきり決まるか・失敗の場合の抜け・`aidlc/spaces/default/memory/team.md` の必須テストとの対応・要件（FR・NFR）との対応の4点で確かめた。質問ファイルの確定した答え（Q1 A・Q2 A・Q3 C・Q4 C・Q5 B・F1 B）は変えない前提で、共通の決まり（CR）とストーリーの受け入れ基準への追加・訂正だけを出す。新しい受け入れ基準は、各ストーリーの既存の番号の続きで ID を振った。「訂正」は既存の ID の文言を置き換える案である。判断が分かれる点は最後の「判断が要る点」にまとめた。

### 1. 「合否の判定の仕方」への追加

- **境界の書き方**: 有効期限の境界は「期限の時刻より前（例: 1 秒前）は有効、期限の時刻ちょうど以降は無効」の形で、注入できる時計の値で書く。「ちょうど前」のような語は使わない（期限の時刻ちょうどを有効側・無効側のどちらに入れるかは「判断が要る点」J1）。
- **「拒否される」の追加の確かめ**: 招待のリンクを使う操作が拒否されたときは、内部DB が変わらないことに加えて、その招待が消費されない（使用済みにならない）ことを確かめる。
- **「送られない」の確かめ方**: テスト用の SMTP の受け手が受けたメールが0通であることで確かめる。
- **「同じ応答」の範囲**: 状態コード・`code`・説明文に加えて、応答の本文の項目の並び（余分な項目が無いこと）も同じであることを確かめる。応答の時間の差は確かめの対象にしない。
- **ログ・監査ログ・トレースへの漏えい**: 既存の `*SecretLeakIT`（`backend/src/test/java/cherry/mastersmith/auth/web/AuthSecretLeakIT.java` など）と同じ形で、流れを通した後の出力を文字列で探して確かめる。

### 2. 共通の決まりへの追加・訂正

- **CR1（訂正の案・確かめ方の追加）**: 確かめ方に次を足す。
  - 言語 en の管理者が言語 ja で招待すると、招待メールは ja で送られる（管理者の言語ではなく招待の言語）。
  - 登録の完了の画面（ログインなし）のエラーの説明文の言語は「判断が要る点」J4 で決めた側で確かめる。
- **CR3（確かめ方の追加）**:
  - 招待メールの送信の失敗と、氏名・言語・テーマ・文字の大きさの変更の後に、監査ログの件数が増えていないこと（FR9.2 を「残さない」側から確かめる）。
  - 監査ログの書き込みに失敗したときの動作は、既存の監査と同じ決まり（前の Intent で決めた動作）に従い、新しい出来事ごとに1件ずつ確かめる。
  - 未ログインの操作（登録の完了とその失敗）の「操作した人」と、存在しない・改ざんしたリンクの「対象」に何を残すかは「判断が要る点」J5 で決め、決めた値（「無し」を含む）が記録されることを確かめる。
- **CR4（訂正の案）**: 「未認証 401、管理者でない 403」に「管理者 200（または成功の状態コード）」を足し、API ごとに3つそろえて確かめると明記する。対象の API: 招待の作成・招待の一覧・送り直し・取り消し（401・403・成功）、プリファレンスの取得と保存・パスワードの変更（401・成功）、登録の完了の画面のための招待の確かめと登録の完了（ログインなしで成功）。
- **CR5（確かめ方の追加）**: 確かめ方: 招待・送り直し・取り消し・登録の完了（成功と失敗）・パスワードの変更・送信の失敗（接続を拒む・応答しない・SMTP のエラーの応答）の各流れを通した後、アプリのログ・トレースの属性・エラー応答に、招待のトークン・招待のリンクの URL・メールアドレス・SMTP の応答の文面・SMTP の資格情報・パスワードの値が含まれないこと。監査ログについては、トークン・URL・パスワードが含まれないこと（CR3）。

### 4. E2E の代表の流れ（NFR9、team.md の E2E の決まり）

stories.md に E2E の代表の流れが書かれていないため、次の1本を「前提と読み方」か US3.2 の補足に足す案を出す。

- **流れ E2E-1（招待から登録の完了まで）**: 管理者でログイン → 管理画面で、実行ごとに重ならないメールアドレス（例: 実行時刻を含む）と言語 ja で招待 → 手元の受け手で招待メールを受け、本文のリンクを取り出す → リンクを開き、パスワード（2回）と氏名を入れて登録を完了 → ログインの画面へ移る → 新しい利用者でログイン → 管理メニューが表示されず、管理画面の URL を直接開いても使えない → ログアウト
- **条件**: 前のテストが作った状態に頼らず、管理者のログインと招待を自分で行う（team.md）。`./gradlew e2eTest` で動かし、`./gradlew verify` と CI の外に置く。
- **設計の段で決めること**: E2E で招待メールのリンクを取り出す方法（手元の受け手の API から読むなど）。E2E の受け手は JVM の中の受け手ではなく、起動したアプリが送れる受け手が要る。

### 6. 要件との対応（出典と traceability.json）

- F1 B の「要件との対応は関わるストーリーに付ける」に対し、共通の決まりにだけ書いた要件が、どのストーリーの「出典」にも無い。traceability.json の `OK` は `USx.y` を名指しする必要があるため、次を各ストーリーの出典に足す案を出す。
  - FR8（CR2）: 画面を持つすべてのストーリー（US1.1・US2.1・US2.2・US3.2・US4.1・US5.1）。優先度 Should は CR2 に書いてあるとおり
  - FR9（CR3）: US1.1・US2.2・US3.2・US5.1（残さない側は US4.1）
  - FR10（CR4）と NFR4: US1.1・US2.1・US2.2（管理者だけ）、US4.1・US5.1（ログインした利用者）、US3.2（ログインなし）
  - FR7.2（CR1）: US4.1 に加えて、エラーを返すすべてのストーリー
  - NFR2: US1.1・US2.2・US3.1（送信の失敗とメールアドレス）
  - NFR7・NFR8: 画面を持つすべてのストーリー（NFR8 はテンプレートのため US3.1 も）
  - NFR10: US4.1（AC4.1.8）
- 受け入れ基準で観測しないため、traceability.json では `Deferred` にするのが正直なもの:
  - NFR6（応答時間）: US1.1 の出典にあるが、受け入れ基準が無い。`Deferred`（持ち主: nfr-requirements で値を決め、確かめは build-and-test。この Intent に Performance Validation の段が無ければ `project.md` の学びどおり build-and-test）
  - NFR5 の後半（同時の要求で接続プールが尽きない負荷の試験）: `Deferred`（build-and-test）。前半（送信の間に接続を持たない）は AC1.1.7（訂正）
  - NFR9 の E2E とカバレッジ: E2E は第4節の流れ E2E-1、カバレッジと `packagesJudgedByTotal` の一覧から戻す作業は `Deferred`（code-generation・build-and-test）
  - NFR11（手元の受け手）: `Deferred`（infrastructure-design か deployment-pipeline）。利用者のストーリーではないため
- FR1.6（招待に招待した管理者を記録する）は、一覧に「招待した管理者」を表示しないため観測の口が無い。監査ログ（CR3）の「操作した人」で観測するか、一覧に表示するかを決める必要がある（J11）。

### 7. 判断が要る点

依頼者の確定した答えは変えない。以下は答えや要件だけでは合否が1つに決まらず、ストーリーか後の段で決める必要がある点。

- **J1 有効期限の時刻ちょうどの扱い**: 期限の時刻ちょうどを有効にするか無効にするか。案: 無効（既存のアクセストークンの有効期限の扱いに合わせる。合わせる相手は機能設計でコードを見て確かめる）。
- **J2 ベース URL の値が不正なとき**（URL の形でない、`http` など）: 「設定されていない」と同じ扱いにするか、起動時の警告だけにするか。FR1.8 は「設定されていない」だけを決めている。
- **J3 完了の時点で同じメールアドレスの利用者がいたときの応答**（AC3.2.11）: 無効なリンクと同じ応答にする（列挙の防止を優先）か、理由の分かる応答にするか。
- **J4 登録の完了の画面のエラーの説明文の言語**: 画面は招待の言語で出す（FR4.3）が、ログインしていない要求のエラーの説明文は `Accept-Language` で決める（FR7.2）。ブラウザが en で招待が ja のとき、説明文を招待の言語にそろえるか、画面側が `code` から自前の文言を出すか。
- **J5 未ログインの操作の監査の値**: 登録の完了の「操作した人」（無しか、作った利用者か）と、存在しない・改ざんしたリンクの失敗の「対象」（無しか、招待の ID か。トークンは残せない）。
- **J6 送り直しで送信に失敗したときの前のリンク**（AC2.2.8）: 要件（FR3.2・FR2.3）から、前のリンクは無効になり新しいリンクも届かない状態になる。これを受け入れるか、送信が成功するまで前のリンクを残すか。
- **J7 招待メールの有効期限の表示**: 招待された人にはまだ利用者の設定が無いため、タイムゾーン（UTC と明記するか、設定の値か）と表示の形を決める必要がある。AC3.1.2 の合否に要る。
- **J8 空白だけの氏名**: 空として拒否するか、前後の空白を除いてから判定するか。
- **J9 今のパスワードの誤りの状態コード**: 401 にすると画面の既存のトークンの更新・ログアウトの処理を起こしうるため、401 以外（400 など）にするか。あわせて、誤りがロックの失敗回数に数えられるか（要件の未解決の点、NFR 要件）。
- **J10 テーマと文字の大きさのすべての組み合わせで崩れないこと（NFR7）の確かめ方**: 自動（画面の撮影の比較など）か、手元の目視の確認の一覧か。
- **J11 FR1.6 の「招待した管理者」の観測の口**: 一覧に表示するか、監査ログだけで観測するか。
- **J12 送り直しの監査の「結果」**: 送り直しの操作が成功して送信だけ失敗したとき、監査の結果は「成功」とし送信の結果を含めない（FR9.2 の読み方）でよいか。
