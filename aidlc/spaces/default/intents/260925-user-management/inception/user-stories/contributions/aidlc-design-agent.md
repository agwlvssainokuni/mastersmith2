## Contribution

デザイナーとして、下書き（`aidlc/spaces/default/intents/260925-user-management/inception/user-stories/stories.md`・`personas.md`）を、利用者の流れ・失敗のときの案内・表示の設定の当たり方・アクセシビリティ・ペルソナとの対応の観点で確かめた。質問ファイルで確定した答え（Q1: A、Q2: A、Q3: C、Q4: C、Q5: B、F1: B）は変えない。ストーリーの数と分け方はそのままにし、共通の決まりの追加と受け入れ基準の追加・訂正だけを出す。判断が分かれる点は「判断が要る」と明記した。

### 1. 流れ全体の確かめ（招待 → メール → 登録の完了 → ログイン → プリファレンス）

- 流れ: P1 が招待（US1.1）→ P2 が自分の言語のメールを受け取る（US3.1）→ リンクから登録の完了（US3.2）→ ログインの画面へ移る（FR4.7）→ 初めてのログインで内部DB の設定が当たる（FR5.4）→ P3 としてプリファレンス・パスワードを変える（US4.1・US5.1）。
- つまずきが起きうる継ぎ目は次の4か所で、下の追加で埋める。
  - (a) 登録の完了の画面で、表示の言語（招待の言語）と、サーバーが返すエラーの説明文の言語（`Accept-Language`＝ブラウザの言語）が食い違う（K-5）。→ 2 の CR1 の追加
  - (b) 登録の完了の直後のログインの画面が、登録で選んだ言語・テーマ・文字の大きさではなく、ブラウザに前から残っている値で出る。→ 4 の AC3.2.12（判断が要る J1）
  - (c) ログインの画面へ移った後に「登録が終わった」ことと「何でログインするか（メールアドレス）」が分からない。→ AC3.2.10・AC3.2.11
  - (d) リンクが無効なとき、P2（IT への慣れが低〜中）が次に何をすればよいか分からない。→ AC3.2.2 の訂正

### 2. 共通の決まりへの追加・訂正

**CR1 言語の適用（追加）**

- 追加の文: ログインしていない画面（ログインの画面・登録の完了の画面）では、画面が表示している言語を要求の `Accept-Language` として送り、サーバーのエラーの説明文を画面の言語とそろえる（FR7.2 の「ログインしていない要求は `Accept-Language` で決める」の範囲の中で、画面の側が送る値をそろえる）。
- 追加の文: 画面の言語が変わったら、`<html lang>` も同じ言語に変える（WCAG 3.1.1。今は起動時に1回だけ決まる、K-5）。
- 追加の確かめ方:
  - 言語 en の招待のリンクを、ブラウザの言語が ja の状態で開き、11 文字のパスワードで登録を完了しようとすると、エラーの説明文が en であること
  - プリファレンスで言語を en にして保存すると、`<html lang>` が `en` になること

**CR6 画面の共通の決まり（新設の提案、Must）**

新しい5つの画面（招待・招待の一覧・登録の完了・プリファレンス・パスワードの変更）に共通の決まりとして一度だけ書き、各受け入れ基準に繰り返さない（Q3: C と同じ書き方）。出典は NFR7・NFR8 と、前の Intent の画面の決まり（`project.md` の Corrections にある確かめる表示の決まり）。

- **CR6.1 入力の誤り**: 入力の誤りは、項目のすぐ下に文字で出し、項目と結び付ける（`aria-describedby`・`aria-invalid`）。送信で誤りが返ったら、最初の誤りの項目にフォーカスを移す。誤りがあっても、入れた値（パスワードを含む）は消さない。色だけで誤りを示さない。
- **CR6.2 入力の前の案内**: 決まりのある項目は、入力の前に決まりを文字で示す（例: パスワードは「12 文字以上」）。
- **CR6.3 処理中**: 送信の間はボタンを押せなくし、処理中であることを文字でも示す（二重の送信を防ぐ）。招待・送り直しは最長で数秒かかる（NFR6）ため、特に必要。
- **CR6.4 結果の知らせ**: 成功は Toast（`aria-live="polite"`）で知らせ、失敗は画面の中に `role="alert"` で残す（Toast だけで失敗を知らせない。消えて読み逃すため）。
- **CR6.5 状態の表し方**: 期限切れ・送信の失敗などの状態は、色だけでなく文字で示す。
- **CR6.6 言語の選択肢**: 言語の選択肢は、それぞれの言語の名前で示す（「日本語」「English」）。いまの画面の言語が読めない人でも自分の言語を見つけられるため。
- **CR6.7 取り消せない操作の確かめ**: 招待の取り消しは、確かめる表示（Modal）を出してから行う。確かめる表示は前の Intent の決まりにそろえ、背景のクリックで閉じず、はじめのフォーカスを「やめる」に置き、Esc で閉じ、閉じたら元のボタンにフォーカスを戻す。
- **CR6.8 日時の表示**: 画面に出す日時（招待した日時・有効期限）は、ブラウザのタイムゾーンで、利用者の言語の書式で表示する。
- **CR6.9 パスワードの項目**: 登録の完了とパスワードの変更の新しいパスワードの項目は `autocomplete="new-password"`、今のパスワードは `autocomplete="current-password"` とし、パスワードの管理の道具が正しく働くようにする。
- 確かめ方: 各画面の部品のテストで、誤りの表示と結び付き、処理中にボタンが押せないこと、取り消しの確かめる表示のフォーカスを確かめる。アクセシビリティの検査（vitest-axe）は画面部品ごとに1件（NFR7）。

### 6. ペルソナの訂正

- **P3 の困りごと**「同じ PC をほかの人と使うと、前の人の表示の設定のまま画面が出る」: 要件（FR5.4・FR5.5、RQ8）で解けるのはログインの後だけで、ログインの前の画面（ログインの画面）は前の人の値で出る。ペルソナか一覧の前提に「ログインの前の画面は、そのブラウザで最後に使った人の設定で出る（決めた動作）」と明記し、ストーリーで全部解けると読ませない。あわせて、ログインの画面に言語の切り替えが無いため、前の人の言語が読めない人はそのまま進むしかない。**判断が要る J6**: ログインの画面と登録の完了の画面に言語の切り替えを置くか（新しい要件。置くなら Could を勧める）。
- **P1 の困りごと**「メールが届かなかったときに分からない」: 分かるのは SMTP への受け渡しの失敗だけで、宛先の誤りによる不達（戻りのメール）は分からない。困りごとの後ろに「（この Intent で分かるのは送信の失敗まで）」と添える。
- **P1 の目的**「誰がいつ招待したかを後から追える」: J4 の結果に合わせて、一覧で見られるのか、監査ログに残るだけなのかを書き分ける。
- **P2**: 目的に「登録を終えた後、どのメールアドレスでログインすればよいか分かる」を足す（AC3.2.10・AC3.2.11 と対応）。

- J4 招待の一覧に招待した管理者を出すか（勧め: 出す）

## Positions

- AGREE: ペルソナを3人にし、流れの順に群を作る形は、同じ人が立場を移る流れと合っており、つまずきの継ぎ目を見つけやすい。
- AGREE: 言語・見た目・監査を共通の決まりに一度だけ書く形は妥当で、画面の共通の決まり（CR6）も同じ形で足せる。
