# User Stories — user-management

## 前提と読み方

- 出典の要件は `aidlc/spaces/default/intents/260925-user-management/inception/requirements-analysis/requirements.md`（FR・NFR の ID）。ペルソナは `personas.md`（P1 管理者・P2 招待された人・P3 ログインした利用者）。答えと依頼者の判断は `aidlc/spaces/default/intents/260925-user-management/inception/user-stories/user-stories-questions.md`（Q1〜Q5・F1・M1〜M9）。
- ストーリーは利用者の流れで分け（Q2: A）、目的ごとに大きめにまとめる（Q5: B、7件）。画面をまたぐ要件（言語の適用・インスタンスの見た目・監査ログ・利用者ごとの可否・秘密と個人情報・画面の共通の決まり）はストーリーにせず、下の「共通の決まり」に一度だけ書く（Q3: C、F1: B）。各ストーリーの受け入れ基準は、共通の決まりを前提として読む。共通の決まりにした要件の対応は、関わるストーリーの「出典」に付ける。
- 優先度は、インスタンスの見た目の設定（CR2）だけが Should、ログインの前の画面の言語の切り替え（CR1.5）だけが Could で、ほかはすべて Must（Q4: C、M6: B）。

- 参加者3名（デザイナー・開発・品質）の意見の取り込み方は、最後の「参加者の意見の扱い」に書く。この段で決めずに後の段に回す点は「後の段に回す点」に持ち主の段とともに並べる。

### 合否の判定の仕方（すべての受け入れ基準に当てる）

- 「拒否される」は、既存のエラー応答の形（Problem Details、画面が分岐に使う `code` 付き）で返り、内部DB が変わらないことを確かめる。招待のリンクを使う操作が拒否されたときは、あわせてその招待が消費されない（使用済みにならない）ことを確かめる。
- 「同じ応答」は、状態コード・`code`・説明文と、応答の本文の項目の並び（余分な項目が無いこと）がすべて同じであることを確かめる。応答の時間の差は確かめの対象にしない。
- 「表示される」は、画面の部品のテストで確かめ、あわせて画面部品ごとにアクセシビリティの検査（vitest-axe）を1件入れる（NFR7）。
- 時刻に関わる境界（有効期限）は、注入できる時計の値で書き、確かめる。有効期限の時刻より前（例: 1 秒前）は有効、有効期限の時刻ちょうどと、それより後（例: 1 秒後）は無効とする（リードの決定）。「ちょうど前」のような語は使わない。
- メールの送信は、テストの中で JVM に起動するテスト用の SMTP の受け手で実際に受けて確かめる（NFR9）。「メールは送られない」は、その受け手が受けたメールが0通であることで確かめる。応答しない受け手は、テストの中で開いた ServerSocket（受け付けて何も返さない）で作り、テストの構成では時間切れを短くして実時間の待ちを抑える。
- ログ・監査ログ・トレースの属性への漏えいは、既存の `*SecretLeakIT`（例: `backend/src/test/java/cherry/mastersmith/auth/web/AuthSecretLeakIT.java`）と同じ形で、流れを通した後の出力を文字列で探して確かめる。
- 「決めた動作として確かめる」は、要件で決めた動作（例: パスワードを変えてもほかの端末のリフレッシュトークンは使える）を、そのとおりであることを明示したテストにする。

### 共通の決まり

- **CR1 言語の適用（FR7、NFR8、Must。CR1.5 だけ Could）**
  - **CR1.1** ログインの後の画面の文言と、ログインした利用者の要求へのエラーの説明文は、利用者の言語（ja・en）で出す。
  - **CR1.2** ログインの前の画面（ログインの画面・登録の完了の画面）は、画面が表示している言語を要求の `Accept-Language` として送り、サーバーのエラーの説明文の言語を画面の言語とそろえる（M2: A。FR7.2 の「ログインしていない要求は `Accept-Language` で決める」の範囲の中で、画面の側が送る値をそろえる）。
  - **CR1.3** 画面の言語が変わったら、`<html lang>` も同じ言語に変える（NFR7。今は起動時に1回だけ決まる、K-5）。
  - **CR1.4** 利用者へのメールは利用者の言語で送り、招待メールは招待の言語で送る（招待した管理者の言語ではない）。新しい画面の文言・エラーの説明文・メールのテンプレートは ja・en の両方を用意する（NFR8）。
  - **CR1.5（Could）** ログインの前の画面（ログインの画面・登録の完了の画面）に、表示の言語を切り替える手段を置く。切り替えると、画面の文言・`<html lang>`・CR1.2 で送る言語が切り替えた言語になる。出典: `user-stories-questions.md` の M6（要件に無い追加。依頼者の判断 M6: B で Could として足した）。置き場と、ブラウザに保存するか、登録の完了の画面の「言語」の項目との関係は「後の段に回す点」のとおり refined-mockups で決める。
  - 確かめ方:
    - 言語 en の利用者がブラウザの言語 ja でログインし、入力の誤りの応答の説明文が en であること
    - 言語 en の招待のリンクを、ブラウザの言語が ja の状態で開き、11 文字のパスワードで登録を完了しようとすると、エラーの説明文が en であること（CR1.2）
    - プリファレンスで言語を en にして保存すると、`<html lang>` が `en` になること（CR1.3）
    - 言語 en の管理者が言語 ja で招待すると、招待メールは ja で送られること（CR1.4）
    - （CR1.5 を入れたとき）ログインの画面で言語を en に切り替えると、画面の文言と `<html lang>` が en になり、誤ったパスワードでのログインの説明文が en であること
- **CR2 インスタンスの見た目の設定（FR8、Should）**: ブランドカラー（blue・green・purple・orange）とフォントファミリー（sans・serif）は `application.yml` で決め、ログインの前後を問わず全画面に当てる。利用者の操作では変えられない。無いときは blue・sans、許されない値のときも blue・sans にして警告のログを出し、起動は止めない。
  - 確かめ方（サーバー側）: green・serif を設定すると画面へ渡す値が green・serif になること。red を設定すると起動し、渡す値が blue になり、警告のログが1件出ること
  - 確かめ方（画面側）: 渡された値が、ログインの画面・登録の完了の画面・管理画面のどれでも当たり（例: `<html>` の `data-brand`・`data-font-family`）、利用者の操作では変えられないこと。画面へ渡す方法は設計の段で決める（要件の未解決の点）
- **CR3 監査ログ（FR9、Must）**: 次の操作を、操作した人・対象・結果とともに監査ログに残す。パスワード・招待のトークン・招待のリンクの URL は残さない。
  - 管理者の招待・送り直し・取り消し（US1.1・US2.2）
  - 登録の完了と、期限切れ・使用済み・取り消し済み・存在しない・改ざんしたリンクによる登録の完了の要求の失敗（US3.2）。リンクを開いただけ（登録の完了の画面を出すための招待の確かめ）の失敗は残さない（リードの決定。確かめの要求はログインなしで何度でも呼べ、追記だけの監査の表を外から増やせるため。FR9.1 の「登録の失敗」は登録の完了の要求の失敗と読む）
  - パスワードの変更の成功と、今のパスワードの誤りによる失敗（US5.1）
  - 招待メールの送信の失敗と、氏名・言語・テーマ・文字の大きさの変更は残さない（FR9.2）
  - 確かめ方:
    - 上の操作ごとに必須の項目が記録され、どの記録にもパスワード・トークン・URL の値が含まれないこと。必須の項目（未ログインの操作の「操作した人」、存在しない・改ざんしたリンクの失敗の「対象」を含む）は機能設計で決め、決めた値（「無し」を含む）が記録されることを確かめる
    - 招待メールの送信の失敗の後と、氏名・言語・テーマ・文字の大きさの変更の後に、監査ログの件数が増えていないこと
    - リンクを開いただけの失敗の後に、監査ログの件数が増えていないこと
    - 監査ログの書き込みに失敗したときの動作は、既存の監査と同じ決まりに従い、新しい出来事ごとに1件ずつ確かめること
- **CR4 利用者ごとの可否（FR10、NFR4、Must）**: API ごとに次の3つ（または2つ）をサーバー側のテストでそろえて確かめ、画面で隠すことを代わりにしない。
  - 招待の作成・招待の一覧・送り直し・取り消し: 未認証 401、管理者でない 403、管理者は成功
  - プリファレンスの取得と保存・パスワードの変更: 未認証 401、ログインした利用者は成功
  - 登録の完了の画面のための招待の確かめ・登録の完了: ログインなしで成功
- **CR5 秘密と個人情報（NFR1・NFR2、Must）**: 招待のトークンと招待のリンクの URL、メールアドレス、SMTP の応答の文面と資格情報、パスワードの値は、アプリのログ・トレースの属性・エラー応答に含めない（監査ログの扱いは CR3）。
  - 確かめ方: 招待・送り直し・取り消し・登録の完了（成功と失敗）・パスワードの変更・送信の失敗（接続を拒む・応答しない・SMTP のエラーの応答）の各流れを通した後、アプリのログ・トレースの属性・エラー応答に、上の値が含まれないこと
- **CR6 画面の共通の決まり（NFR7・NFR8、Must）**: 新しい5つの画面（招待・招待の一覧・登録の完了・プリファレンス・パスワードの変更）に当てる。出典は NFR7・NFR8 と、前の Intent の画面の決まり（`aidlc/spaces/default/memory/project.md` の Corrections にある確かめる表示の決まり）。
  - **CR6.1 入力の誤り**: 項目のすぐ下に文字で出し、項目と結び付ける（`aria-describedby`・`aria-invalid`）。送信で誤りが返ったら、最初の誤りの項目にフォーカスを移す。誤りがあっても入れた値（パスワードを含む）は消さない。色だけで誤りを示さない。
  - **CR6.2 入力の前の案内**: 決まりのある項目は、入力の前に決まりを文字で示す（例: パスワードは 12 文字以上）。
  - **CR6.3 処理中**: 送信の間はボタンを押せなくし、処理中であることを文字でも示す（二重の送信を防ぐ。招待・送り直しは送信を含むため特に要る、NFR6）。
  - **CR6.4 結果の知らせ**: 成功は Toast（`aria-live="polite"`）で知らせ、失敗は画面の中に `role="alert"` で残す（Toast だけで失敗を知らせない）。
  - **CR6.5 状態の表し方**: 期限切れ・送信の失敗などの状態は、色だけでなく文字で示す。
  - **CR6.6 言語の選択肢**: 言語の選択肢は、それぞれの言語の名前で示す（「日本語」「English」）。
  - **CR6.7 取り消せない操作の確かめ**: 招待の取り消しは、確かめる表示（Modal）を出してから行う。背景のクリックで閉じず、はじめのフォーカスを「やめる」に置き、Esc で閉じ、閉じたら元のボタンにフォーカスを戻す。
  - **CR6.8 日時の表示**: 画面に出す日時（招待した日時・有効期限）は、ブラウザのタイムゾーンで、利用者の言語の書式で表示する。
  - **CR6.9 パスワードの項目**: 新しいパスワードの項目は `autocomplete="new-password"`、今のパスワードは `autocomplete="current-password"` とする。
  - 確かめ方: 各画面の部品のテストで、誤りの表示と結び付き、処理中にボタンが押せないこと、取り消しの確かめる表示のフォーカスを確かめる。アクセシビリティの検査は画面部品ごとに1件（NFR7）。

## US1 招待する

### US1.1 利用者を招待する

- **ストーリー**: 管理者（P1）として、使う人のメールアドレスと言語を入れて招待したい。それは、その人に自分で登録してもらい、利用者を増やすためだ。
- **優先度**: Must
- **出典**: FR1.1〜FR1.8、FR2.3〜FR2.6、FR7.4（CR1）、FR8（CR2）、FR9（CR3）、FR10.1（CR4）、NFR1、NFR2、NFR4、NFR5（前半）、NFR7、NFR8
- **受け入れ基準**:
  - **AC1.1.1** Given 言語が en の管理者 / When 招待の画面を開く / Then 言語の初期値が en になっている
  - **AC1.1.2** Given 管理者 / When 登録も招待もされていないメールアドレスと言語 ja で招待する / Then 招待が作られ（有効期限は作成から ★24 時間）、ja の招待メールが送られ、画面に招待した旨が表示される
  - **AC1.1.3** Given 形式の正しくないメールアドレス、255 文字のメールアドレス、CR または LF を含むメールアドレス、または ja・en 以外の言語 / When 招待する / Then 入力の誤りとして拒否され、招待は作られず、メールは送られない。Given 254 文字の正しい形式のメールアドレス / When 招待する / Then 招待が作られる
  - **AC1.1.4** Given 登録済みの利用者のメールアドレス / When 招待する / Then 登録済みであることを示すエラーで拒否される。Given 招待中（期限内・取り消していない・未完了）の人のメールアドレス / When 招待する / Then 招待中であることと一覧から送り直す案内を示すエラーで拒否され、案内から一覧のその行へ移れる。この API は管理者だけが呼べるため、登録済み・招待中を区別して返してよい（NFR3 の列挙の防止の対象外）
  - **AC1.1.5** Given SMTP の受け手が接続を拒む / When 招待する / Then 招待は作られ、送信の結果は「送信に失敗」として記録され、画面に送信に失敗した旨と一覧から送り直せる旨が表示される。応答とログに宛先のメールアドレスと SMTP の応答は含まれない
  - **AC1.1.6** Given ベース URL か SMTP の接続先が設定されていない / When 招待の画面を開く / Then 入力の項目と招待のボタンは押せない状態になり、どの設定が足りないかが分かる理由が画面の上部に文字で表示される（設定の値そのものは出さない）。When API で招待する / Then 理由を示すエラーで拒否され、招待は作られず、メールは送られない
  - **AC1.1.7** Given SMTP の受け手が接続を受け付けて何も返さない / When 招待する / Then ★時間切れ（値は NFR 要件で決める）の後に応答が返り、送信の結果は「送信に失敗」として記録され、画面に送信に失敗した旨が表示される。応答とログに宛先のメールアドレスと SMTP の応答は含まれない。送信を待つ間に内部DB の接続を持たない（観測の案: 接続プールの上限を1にした試験の構成で、受け手が応答しない間に内部DB を使う別の要求が時間切れを待たずに応答する。最終の確かめ方は nfr-design で決める）
  - **AC1.1.8** Given 管理者 / When 招待が成功する / Then 招待した旨が Toast で知らされ、正規化したメールアドレスが一覧に加わり、メールアドレスの項目は空に戻り、言語の項目は元の値のままで、フォーカスはメールアドレスの項目に戻る
  - **AC1.1.9** Given 管理者 / When 招待を送っている間 / Then 招待のボタンは押せず、処理中と表示される（CR6.3）
  - **AC1.1.10** Given 登録済みの利用者のメールアドレスを、前後に空白を付け大文字を混ぜて入れる / When 招待する / Then 正規化した値で比べられ、登録済みであることを示すエラーで拒否される
  - **AC1.1.11** Given ベース URL が設定されていない / When 要求の Host ヘッダーを `evil.example.test` にして招待する / Then 拒否され、テスト用の受け手が受けたメールは0通で、どの出力にも `evil.example.test` から始まる招待の URL が出ない
  - **AC1.1.12** Given SMTP の受け手が宛先を拒む応答（例: 550 と、宛先のメールアドレスを含む文面）を返す / When 招待する / Then 招待は作られ、送信の結果は「送信に失敗」として記録され、応答とログに宛先のメールアドレスと SMTP の応答の文面は含まれない
  - **AC1.1.13** Given 登録も招待もされていないメールアドレス / When 2人の管理者が同時に同じメールアドレスを招待する / Then 招待は1件だけ作られ、もう一方は招待中であることを示すエラーで拒否される（作り方は設計で決める）
- **INVEST**: 独立（招待の作成だけで価値がある）。一覧・送り直しは US2 に分けた。受け入れ基準が多いのは失敗の場合（送信の失敗・設定の不足・同時の操作）を網羅したためで、操作は招待の1つに閉じている。

## US2 招待を管理する

### US2.1 招待の状況を一覧で確かめる

- **ストーリー**: 管理者（P1）として、まだ登録を終えていない招待の状況を一覧で見たい。それは、送信に失敗した・使われていない招待に気づいて手を打つためだ。
- **優先度**: Must
- **出典**: FR3.1、FR1.6、FR2.4、FR8（CR2）、FR10.1（CR4）、NFR1、NFR4、NFR7、NFR8
- **受け入れ基準**:
  - **AC2.1.1** Given 招待中の人が2人（うち1人は送信に失敗）/ When 一覧を開く / Then 2人のメールアドレス・言語・招待した管理者・招待した日時・有効期限・送信の結果が表示され、送信の結果は「送信済み」「送信に失敗」のどちらかの言葉で示され、1人に「送信に失敗」が表示される（「成功」「届いた」とは言わない。SMTP に渡せたことしか分からないため）
  - **AC2.1.2** Given 有効期限の1秒前の招待と、有効期限の時刻ちょうどの招待（時計で固定）/ When 一覧を開く / Then 前者は期限内、後者は期限切れであることが文字で表示される（色だけで示さない）
  - **AC2.1.3** Given 登録を完了した招待と取り消した招待 / When 一覧を開く / Then どちらも一覧に表示されない（要件の前提 A1）
  - **AC2.1.4** Given 招待が1件も無い / When 一覧を開く / Then 招待が無い旨が表示される
  - **AC2.1.5** Given 招待が複数ある / When 一覧を開く / Then 招待した日時の新しい順に並ぶ
  - **AC2.1.6** Given 一覧の各行 / When スクリーンリーダーで送り直し・取り消しのボタンに移る / Then ボタンの名前にその行のメールアドレスが含まれる（例: 「user@example.com の招待を取り消す」）
  - **AC2.1.7** Given 招待中の人がいる / When 一覧を開く / Then 一覧の表示と API の応答に、招待のトークンと招待のリンクの URL が含まれない
  - **AC2.1.8** Given 管理者 A が招待した招待 / When 管理者 B が一覧を開く / Then 招待した管理者の欄に A の氏名が表示される。氏名が得られないときは A のメールアドレスが表示される（M9: A）
- **INVEST**: 小さい（読み取りだけ）。送り直し・取り消しは US2.2。

### US2.2 招待を送り直す・取り消す

- **ストーリー**: 管理者（P1）として、一覧から招待を送り直したり取り消したりしたい。それは、送信に失敗した・期限が切れた招待をやり直し、誤った招待を使わせないためだ。
- **優先度**: Must
- **出典**: FR3.2、FR3.3、FR1.4、FR1.5、FR1.8、FR2.3、FR2.4、FR8（CR2）、FR9（CR3）、FR10.1（CR4）、NFR2、NFR4、NFR7、NFR8
- **受け入れ基準**:
  - **AC2.2.1** Given 招待中の人（時計の時刻 T に作成）/ When 時刻 T+1 時間に送り直す / Then 新しいトークンで招待メールが送られ、新しい有効期限は T+1 時間から ★24 時間後になり、前のリンクは US3.2 の AC3.2.2 と同じ応答で拒否され、新しいリンクが有効になる
  - **AC2.2.2** Given 期限切れの招待 / When 送り直す / Then 送り直せて、新しいリンクが有効になる
  - **AC2.2.3** Given 送信に失敗した招待 / When 送り直して送信に成功する / Then 一覧の送信の結果が「送信済み」になる
  - **AC2.2.4** Given 招待中の人 / When 取り消しを確かめて取り消す / Then その招待のリンクは拒否され、一覧から消える
  - **AC2.2.5** Given 取り消した招待と同じメールアドレス / When 新しく招待する / Then 招待できる（要件の前提 A4）
  - **AC2.2.6** Given 期限切れの招待と同じメールアドレス / When 新しく招待する / Then 招待でき、期限切れの古い招待は無効になって一覧から消える [assumption]（要件の確認の指摘 R-02。FR1.4 の「招待中」は期限内だけを指すため）
  - **AC2.2.7** Given ほかの管理者がすでに取り消した招待、登録が完了した招待、または存在しない招待の ID / When 送り直す・取り消す / Then 3つとも同じ状態コードと `code` で、招待が見つからない旨で拒否される
  - **AC2.2.8** Given 招待中の人と、接続を拒む SMTP の受け手 / When 送り直す / Then 送り直した時点で前のリンクは拒否されるようになり、新しいトークンと有効期限が保存され、新しい招待は送信の結果「送信に失敗」として一覧に残り、画面に送信に失敗した旨が表示される（もう一度送り直せる）。応答とログに宛先のメールアドレスと SMTP の応答は含まれない（M3: A）
  - **AC2.2.9** Given ベース URL か SMTP の接続先が設定されていない / When 一覧を開く / Then 送り直しのボタンは押せず理由が表示される。When API で送り直す / Then 理由を示すエラーで拒否され、招待のトークンと有効期限は変わらず、前のリンクは有効なままで、メールは送られない。取り消しは設定が無くても行える
  - **AC2.2.10** Given 期限切れの招待 / When 取り消す / Then 取り消せて、一覧から消える
  - **AC2.2.11** Given 招待中の人 / When 取り消しを押す / Then 確かめる表示が出て、「やめる」を選ぶと招待は変わらず、「取り消す」を選ぶと取り消される（CR6.7）
  - **AC2.2.12** Given 招待中の人 / When 送り直しが成功する / Then 送り直した旨が Toast で知らされ、一覧のその行の有効期限と送信の結果が新しい値になる。送り直しの間はその行の送り直しのボタンを押せない
  - **AC2.2.13** Given 招待の取り消しと、同じ招待での登録の完了を同時に行う / When 両方を送る / Then 「利用者が作られ招待は使用済みで、取り消しは見つからない旨で拒否される」か「招待は取り消され、登録の完了は AC3.2.2 と同じ応答で拒否され、利用者は作られない」のどちらか一方だけになる（取り消した招待で利用者が作られる状態にならない）
- **INVEST**: 送り直しと取り消しはどちらも一覧の同じ行の操作で、同じ招待の状態を扱うため1つにまとめた。

## US3 登録を完了する

### US3.1 自分の言語で招待メールを受け取る

- **ストーリー**: 招待された人（P2）として、自分の言語で書かれた招待メールを受け取りたい。それは、何をすればよいかを迷わず理解し、期限内に登録するためだ。
- **優先度**: Must
- **出典**: FR2.1、FR2.2、FR1.5、FR1.7、FR7.3（CR1）、NFR2、NFR8
- **受け入れ基準**:
  - **AC3.1.1** Given 言語 en の招待と言語 ja の招待 / When 招待メールが送られる / Then それぞれの言語のテンプレートから作られた HTML のメール（`Content-Type` が `text/html`、文字コード UTF-8）で、件名はそれぞれのテンプレートの `<title>` の文面と一致し、空でない
  - **AC3.1.2** Given 招待 / When テスト用の受け手で招待メールを受け取る / Then 本文に招待のリンクと、リンクが 24 時間有効である旨（ja は「このリンクは 24 時間有効です」、en は同じ意味の文）が載っており、有効期限の日時は載っていない（M1: C。日時を書かないため、表示のタイムゾーンの論点は無い。FR2.2 の「有効期限を載せる」は、この有効な期間の文で満たす）。招待した管理者の氏名は載っていない（M5: A）。本文のリンクを開くと登録の完了の画面が表示される
  - **AC3.1.3** Given ベース URL `https://ms.example.test` を設定し、要求の Host が別の値 / When 招待メールを作る / Then リンクは `https://ms.example.test` から始まり、要求の Host は含まれない
  - **AC3.1.4** Given 本文と件名に差し込むすべての利用者の値に `<`・`>`・`&`・`"`・`'` を含む / When 招待メールを作る / Then タグや属性としてそのまま出ず、エスケープされた形で出る。差し込む利用者の値が何か（例: 招待先のメールアドレス）は、このエスケープのテストの対象として機能設計で決める（M5: A により招待した管理者の氏名は差し込まない）
  - **AC3.1.5** Given ja・en のすべての招待メールのテンプレート / When 描く / Then どれも描けて、件名が空でなく、ライセンスヘッダーの文面と差し込み漏れ（`{{` の残り）が本文と件名に出ない
  - **AC3.1.6** Given ja・en の招待メールのテンプレート / When テンプレートの中身を調べる / Then 利用者の値をエスケープしない差し込み（`{{{ }}}`・`{{& }}`）が無く、属性の値に差し込む箇所はすべて二重引用符で囲まれている（エンジンの `{{ }}` が `'` を置き換えないため）
  - **AC3.1.7** Given 宛先・件名・差し込む値に改行（CR・LF）を含む / When 招待メールを作って送る / Then メールのヘッダーは増えず（受け手が受けたメールは0通）、送信は拒否される
  - **AC3.1.8** Given 招待メール / When 受け取る / Then 本文に、MasterSmith から利用者として招待されたこと、リンクから登録を終えるとログインできること、心当たりが無ければ何もしなくてよいこと、が招待の言語で書かれている
  - **AC3.1.9** Given 招待メール / When 受け取る / Then リンクの文言は行き先が分かる文（「こちら」だけにしない）で、リンクを押せない環境のために URL も文字として本文に載っている
  - **AC3.1.10** Given 招待メール / When 描く / Then HTML の `lang` 属性が招待の言語になっている
- **INVEST**: テストできる（受け手で実際に受けて確かめる）。US1.1 と同じ Bolt で作る。

### US3.2 招待のリンクから登録を完了する

- **ストーリー**: 招待された人（P2）として、招待のリンクから自分でパスワードと氏名・表示の設定を決めて登録を完了したい。それは、自分の決めたパスワードで MasterSmith にログインできるようになるためだ。
- **優先度**: Must
- **出典**: FR4.1〜FR4.7、FR1.3、FR5.2、FR5.5、FR7.2（CR1）、FR8（CR2）、FR9（CR3）、FR10.3（CR4）、NFR1、NFR3、NFR4、NFR7、NFR8
- **受け入れ基準**:
  - **AC3.2.1** Given 言語 ja の有効な招待と、ブラウザの言語が en / When リンクを開く / Then ログインせずに、アプリの枠（サイドバーとトップバー）の外の単独の画面で、登録の完了の画面が ja で表示され（`<html lang>` も ja）、氏名にメールアドレス、言語に ja、テーマに system、文字の大きさに md が入っている。テーマと文字の大きさの表示は、そのブラウザに最後に保存された値で行う（フォームの初期値と画面の表示が食い違いうる点は「後の段に回す点」のとおり refined-mockups で扱う）
  - **AC3.2.2** Given 期限切れ・使用済み・取り消し済み・存在しない・改ざんしたリンク / When 開く・登録を完了する / Then どれも同じ応答で拒否され、応答から利用者や招待の有無を推測できない。画面には、理由によらず同じ文で「このリンクは使えません。いちばん新しい招待メールのリンクを使うか、招待した管理者に送り直しを頼んでください」の趣旨の案内が表示される。開いたときの拒否は監査ログに残らず、登録の完了の要求の拒否は残る（CR3）
  - **AC3.2.3** Given 招待の有効期限の1秒前（時計で固定）/ When リンクを開く・登録を完了する / Then どちらも通る。Given 有効期限の時刻ちょうど、または1秒後 / When リンクを開く・登録を完了する / Then どちらも AC3.2.2 と同じ応答で拒否される
  - **AC3.2.4** Given 次のパスワード / When 登録を完了する / Then 次のとおりになる
    - 11 文字（コードポイント）、空、UTF-8 で 73 バイト（例: 「あ」24 文字＋「a」）、2回の入力が一致しない: 理由の分かるエラーで拒否される（長すぎるときは、長すぎることが利用者に分かる言葉で示す）
    - 12 文字（コードポイント）、UTF-8 で 72 バイトちょうど（例: 「あ」24 文字）、絵文字 12 文字（UTF-16 では 24 単位・48 バイト）: 通る
    - 絵文字 11 文字（UTF-16 では 22 単位）: 拒否される（UTF-16 の単位ではなくコードポイントで数えることの確かめ）
  - **AC3.2.5** Given 正しい入力 / When 登録を完了する / Then 管理者フラグの無い利用者が作られ、入れた氏名・言語・テーマ・文字の大きさが保存され、ログインの画面へ移る（自動ではログインしない）。設定したパスワードでログインできる
  - **AC3.2.6** Given 登録を完了した招待 / When 同じリンクをもう一度使う / Then 拒否される
  - **AC3.2.7** Given 同じ招待で登録の完了を同時に2回行う / When 両方を送る / Then 利用者は1人だけ作られ、もう一方は拒否される
  - **AC3.2.8** Given 招待中（登録を終えていない）の人のメールアドレス / When そのメールアドレスでログインする / Then 存在しない利用者と同じ 401 になる
  - **AC3.2.9** Given 空の氏名、または上限を1文字超える氏名（上限は機能設計で決める）/ When 登録を完了する / Then 入力の誤りとして拒否される。Given 上限ちょうどの氏名 / When 登録を完了する / Then 通る（空白だけの氏名の扱いは「後の段に回す点」）
  - **AC3.2.10** Given 有効な招待 / When 入力の誤り（11 文字のパスワードや空の氏名）で登録の完了が拒否された後、同じリンクで正しい入力を送る / Then 登録を完了できる（拒否で招待が消費されない）
  - **AC3.2.11** Given 有効な招待と同じメールアドレスの利用者が、完了の時点ですでにいる / When 登録を完了する / Then AC3.2.2 と同じ応答で拒否され、利用者は増えず、招待は使用済みにならない（リードの決定。NFR3 の列挙の防止を優先する）
  - **AC3.2.12** Given 登録を完了した直後の利用者 / When 管理者だけの API（招待の一覧など）を呼ぶ / Then 403 になる。あわせて、内部DB のパスワードの値が入れた文字列と異なり bcrypt のハッシュの形であること、保存したメールアドレスが正規化した値であることを確かめる
  - **AC3.2.13** Given 登録を完了した利用者 / When ロックのしきい値の回数だけ誤ったパスワードでログインする / Then 既存の利用者と同じくロックされる（FR4.5 の「アカウントのロックの状態の用意」の確かめ）
  - **AC3.2.14** Given 招待中（登録を終えていない）の人 / When 招待の ID またはメールアドレスを主体にした、正しい鍵で署名したアクセストークンで API を呼ぶ / Then 401 になる。リフレッシュトークンについては、招待中の人に発行される経路が無いこと（ログインが 401 になる、AC3.2.8）と、招待中の人を主体にしたリフレッシュトークンでの更新が拒否されることで確かめる（主体の形は既存のトークンの作りに合わせて設計で決める）
  - **AC3.2.15** Given 有効な招待のリンク / When リンクを開き、登録を完了する / Then 招待のトークンは、画面の配信の要求とトークンを確かめる要求のどちらでも、アプリのログ・トレースの属性・エラー応答に含まれない（CR5 のうち、URL にトークンが載る経路に絞った確かめ）
  - **AC3.2.16** Given 有効な招待 / When 登録の完了の画面を開く / Then ログインに使うメールアドレスが、変えられない値として表示される（`autocomplete="username"` を持ち、パスワードの管理の道具がメールアドレスとパスワードを組で保存できる）
  - **AC3.2.17** Given 正しい入力 / When 登録を完了してログインの画面へ移る / Then ログインの画面に、登録が終わった旨と、設定したパスワードでログインするよう案内が表示される。メールアドレスは URL に載せない
  - **AC3.2.18** Given 言語 en・テーマ dark・文字の大きさ lg を選び、ブラウザには ja・light・md が保存されている / When 登録を完了してログインの画面へ移る / Then 選んだ en・dark・lg がそのブラウザに保存され、ログインの画面は en・dark・lg で表示される（M4: A）
- **INVEST**: 登録の完了の画面の1つの操作。見積もれるよう、氏名の長さの上限は機能設計で決める（要件の未解決の点）。

## US4 プリファレンスを変える

### US4.1 自分の表示の設定と氏名を変える

- **ストーリー**: ログインした利用者（P3）として、自分の言語・テーマ・文字の大きさ・氏名を変えて保存したい。それは、どの PC でも自分の見やすい表示で使い、自分の名前で表示されるためだ。
- **優先度**: Must
- **出典**: FR5.1〜FR5.5、FR7.1、FR7.2、FR7.4（CR1）、FR8（CR2）、FR9.2（CR3）、FR10.2（CR4）、NFR4、NFR7、NFR8、NFR10
- **受け入れ基準**:
  - **AC4.1.1** Given ログインした利用者 / When ユーザーメニューからプリファレンスの画面を開く / Then 今の氏名・言語・テーマ・文字の大きさが表示される。テーマが system の利用者には、今の見た目（ライト・ダーク）ではなく system が選ばれた状態で表示される
  - **AC4.1.2** Given テーマを dark、文字の大きさを lg にする / When 保存した直後と、ブラウザに保存された値を消してからログインし直したとき / Then どちらも dark・lg で表示される（ブラウザの保存ではなく内部DB から当たることの確かめ）
  - **AC4.1.3** Given テーマが system / When OS の配色の設定がダーク / Then ダークで表示される（開いている間の切り替えに追従するかは機能設計で決める）

## US5 パスワードを変える

### US5.1 自分のパスワードを変える

- **ストーリー**: ログインした利用者（P3）として、今のパスワードを確かめたうえで新しいパスワードに変えたい。それは、パスワードが漏れた疑いがあるときなどに、自分で安全を保つためだ。
- **優先度**: Must
- **出典**: FR6.1〜FR6.3、FR4.4、FR7.2（CR1）、FR8（CR2）、FR9（CR3）、FR10.2（CR4）、NFR4、NFR7、NFR8
- **受け入れ基準**:
  - **AC5.1.1** Given 正しい今のパスワードと規則に合う新しいパスワード（2回入力が一致）/ When 変更する / Then 新しいパスワードでログインでき、前のパスワードではログインできない
  - **AC5.1.2** Given 誤った今のパスワード / When 変更する / Then 400 系の業務エラーで拒否され（401 にはしない。ログイン中の画面のトークンの更新の仕組みと混同しないため。状態コードは機能設計で決める）、パスワードは変わらない
  - **AC5.1.3** Given 新しいパスワードが AC3.2.4 と同じ一覧の値（11 文字・12 文字・空・72 バイト・73 バイト・絵文字 11 文字と 12 文字・2回の入力の不一致）/ When 変更する / Then AC3.2.4 と同じく通る・拒否されるが決まり、拒否されたときパスワードは変わらない
  - **AC5.1.4** Given 端末 A と B でログイン中 / When 端末 A でパスワードを変える / Then 端末 A も B もリフレッシュトークンで更新でき、ログインし直さなくてよい（決めた動作として確かめる）
  - **AC5.1.5** Given 端末 A でログイン中（アクセストークンの有効期限内）/ When 端末 A でパスワードを変える / Then 変える前に発行されたアクセストークンで、有効期限まで API を呼べる（決めた動作として確かめる）
  - **AC5.1.6** Given 誤った今のパスワード / When 変更する / Then 拒否されても、その利用者はログインしたままで（アクセストークンとリフレッシュトークンが使え）、画面はログインの画面へ移らない
  - **AC5.1.7** Given 誤った今のパスワード / When 変更する / Then 誤りは今のパスワードの項目に結び付けて表示され、新しいパスワードの2つの項目の値は消えない（CR6.1）
  - **AC5.1.8** Given 正しい入力 / When パスワードの変更が成功する / Then 変更した旨が Toast で知らされ、3つのパスワードの項目は空に戻り、ログインしたままでいる
  - **AC5.1.9** Given ログインした利用者 / When ユーザーメニューを開く / Then パスワードの変更の画面を開ける（FR10.2）
- **INVEST**: 1つの画面の1つの操作。パスワードの規則の検証（コードポイントの数とバイト数）は登録の完了と共通の純粋な関数とし、性質ベースのテスト（jqwik）を当てる対象にする。今のパスワードの誤りが続いたときの制限は NFR 要件で決める（要件の未解決の点）。

## E2E の代表の流れ（NFR9）

`team.md` の E2E の決まり（Intent ごとに代表の流れを1本まで足す）に沿って、この Intent では次の1本を足す。

- **E2E-1 招待から登録の完了まで**（US1.1・US3.1・US3.2・CR4）: 管理者でログイン → 管理画面で、実行ごとに重ならないメールアドレス（例: 実行時刻を含む）と言語 ja で招待 → 手元の受け手で招待メールを受け、本文のリンクを取り出す → リンクを開き、パスワード（2回）と氏名を入れて登録を完了 → ログインの画面へ移る → 新しい利用者でログイン → 管理メニューが表示されず、管理画面の URL を直接開いても使えない → ログアウト
- **条件**: 前のテストが作った状態に頼らず、管理者のログインと招待を自分で行う。`./gradlew e2eTest` で動かし、`./gradlew verify` と CI の外に置く。
- **後の段で決めること**: E2E で招待メールのリンクを取り出す方法（起動したアプリが送れる手元の受け手の API から読むなど。JVM の中の受け手は使えない）。持ち主は infrastructure-design。
