# Bolt Plan — user-management

Bolt は、1つ以上の単位（Unit）をまとめて作り終え、動くものができる1回の作る区切りのこと。この文書は Bolt の順と、それぞれの完了の条件を示す。

出典: 単位 `aidlc/spaces/default/intents/260925-user-management/inception/units-generation/unit-of-work.md`、依存 `unit-of-work-dependency.md`、ストーリーとの対応 `unit-of-work-story-map.md`、契約 `aidlc/spaces/default/intents/260925-user-management/inception/contract-design/contract-summary.md`、要件 `requirements.md`、ストーリー `stories.md`、画面 `mockups.md`、部品 `components.md`、チームの進め方 `team-practices.md`、この段の答え `delivery-planning-questions.md`（Q1〜Q4・F1）。順の理由は `risk-and-sequencing-rationale.md`。

## 前提

- 作る順は危険の大きいものを先にする（Q1: A）。関係の深い単位をまとめて5つの Bolt にする（Q2: B・F1: A）。
- 設計の段（機能設計・NFR 要件・NFR 設計・基盤の設計）はすべての単位を通してから、コード生成を最後に行う（Q3: A）。コード生成と統合は下の Bolt の順に行う。
- 単位は1つずつ作り、並行して作らない。1人のチーム（依頼者と AI）で、依頼者が段ごとに承認する（Q4: A）。
- 最初の Bolt だけを単独で動かして承認を待つ特別な手順（walking skeleton の儀式。アーキテクチャの端から端までを最初に通す最小の作り）は行わない。アプリの骨格はすでにある（`team.md`）。
- すべての Bolt の共通の完了の条件: 統合の前に1コマンドの検査（`./gradlew verify`）が通る（フォーマット・リンタ・ライセンスヘッダー・ビルド・全テスト・対象DB の結合テスト・カバレッジの下限・秘密情報の検出・静的解析・依存関係の脆弱性検査）。統合は `develop` へ squash（サブモジュールの固定先の更新を含む B1 は fast-forward）。統合後の CI が通る。

## B1 メールの土台（U1）

- **単位**: U1 u1-mail
- **完了の条件**:
  - java-mustache-processor がサブモジュール `vendor/java-mustache-processor` と composite build で組み込まれ、取得元を Maven Central だけにする決まりが保たれ、部品の推移依存が lockfile と脆弱性検査の対象に入っている（満たせなければ Maven Central への公開に切り替え、この Bolt でその判断を記録する）
  - テンプレートの描画（件名は `<title>`）と SMTP の送信が、JVM の中のテスト用の受け手で確かめられている（送信の失敗・ヘッダーへの差し込みの拒否・エスケープのテストを含む）
  - SpotBugs の関門に `PREDICTABLE_RANDOM`・`SMTP_HEADER_INJECTION` が加わり、既存の1件の指摘が確かめられている
  - テンプレートのライセンスヘッダーの検査が加わっている
  - 手元でメールを見る受け手を compose の profile で起動できる
- **確かめたいこと（confidence hypothesis）**: 前例の無い自前の部品の取り込みが、チームの供給網の決まり（lockfile・脆弱性検査・取得元の固定）を崩さずにできるか。
- **見せ方**: 結合テストで、受け手に届いた ja・en のメールの件名と本文を確かめる。

## B2 利用者の設定（U2）

- **単位**: U2 u2-user-preferences
- **完了の条件**:
  - 利用者の表に氏名とプリファレンスの列が足され、既存の利用者に初期値が入っている（前進のみ・後方互換）
  - プリファレンスの読み書きとパスワードの変更の API（C4）が、401・200 のテストと、パスワードの規則の境界・今のパスワードの誤り・ほかの端末のリフレッシュトークンが使えることのテストで確かめられている
  - ログインと更新の応答に氏名とプリファレンスが入っている（C3）
  - 監査の表に対象の2列が足され、パスワードの変更の成功と失敗が記録され、パスワードの値が出ない（C8）
  - 既存の `user`・`audit`（と手を入れたなら `auth`）のパッケージがパッケージごとのカバレッジの下限の対象に戻っている
- **確かめたいこと**: 既存の利用者の表と監査の表を、既存の機能（ログイン・監査）を壊さずに広げられるか。
- **見せ方**: API の結合テストと、既存のログイン・監査のテストが通ること。

## B3 招待と登録の完了（U3）

- **単位**: U3 u3-invitation
- **完了の条件**:
  - 招待・一覧・送り直し・取り消しの API（C5）と登録の完了の API（C6）が動き、`team.md` の必須テスト（招待の期限の境界・再使用と改ざんの拒否・同じ応答・招待中の人の拒否・メールの本文・トークンと URL の漏えい）が通る
  - 送信はトランザクションの外で行われ、送信の失敗が招待に記録される（C1・ADR-009）
  - 招待の出来事と登録の出来事が監査に記録される（C8）
  - 招待を使えない設定のときに理由つきで拒否される
- **確かめたいこと**: 状態の移り変わり・トークン・同時の操作・送信の失敗を含む招待の流れが、利用者を増やす入口として安全に動くか。
- **見せ方**: API の結合テストで、招待 → メールの受け取り → 登録の完了 → ログインまでを通す。

## B4 見た目と表示の土台（U8・U4）

- **単位**: U8 u8-instance-appearance、U4 u4-display-foundation
- **完了の条件**:
  - 見た目の設定の API（C7）が既定への置き換えと警告を含めて確かめられている
  - 表示の設定を当てる仕組み（C9）が、ログインの前後・ブラウザに残った値・テーマ system・言語の切り替え・要求の言語について部品のテストで確かめられている
  - ユーザーメニューに氏名が出て、ログインの画面に言語の切り替えがある（Could）
  - 既存の画面のテストと E2E が通る（骨組みの変更のため）
- **確かめたいこと**: 変更できない make-you-chic-ui の上で、利用者ごとの表示の設定とインスタンスの見た目を全画面に当てられるか。
- **見せ方**: 画面を起動し、ログインの前後でテーマ・文字の大きさ・言語が変わることを見る。

## B5 画面（U5・U6・U7）

- **単位**: U5 u5-invitation-ui、U6 u6-registration-ui、U7 u7-preferences-ui
- **完了の条件**:
  - 3つの画面が画面イメージ（`mockups.md`）のとおりに動き、画面部品ごとにアクセシビリティの検査が通る
  - 招待から登録の完了までの E2E の代表の流れ1本（管理者でログイン → 招待 → 手元の受け手でリンクを取り出す → 登録の完了 → 新しい利用者でログイン → 管理画面に入れない → ログアウト）が通る
  - ja・en の文言がそろっている
- **確かめたいこと**: 利用者が画面だけで、招待・登録・自分の設定の変更を迷わずに終えられるか。
- **見せ方**: E2E の流れと、画面の手動の確かめ。
