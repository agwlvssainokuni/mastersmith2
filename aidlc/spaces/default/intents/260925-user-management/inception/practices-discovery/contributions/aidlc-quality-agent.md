### 2. 下書きへの追加・訂正の提案（そのまま統合できる形）

#### 2.1 メール送信のテストの行（team-practices.md Testing Posture の「（確認待ち）外へ送るメール…」）

受け手の道具を設計の段に回すこと自体には賛成だが、道具の種類が Way of Working の「コンテナが無いときに飛ばしてよいのは対象DB のテストだけ」の決まりと直接ぶつかるため、進め方としての条件をこの段で決める必要がある（F4・E9）。下の形への書き直しを提案する。

- （確認待ち）外へ送るメール（SMTP）を使う機能の結合テストは、送信の部品をモックで置き換えて済ませず、テストの中で起動するメールの受け手（テスト用の SMTP サーバー）で実際に受け、宛先・件名・本文（HTML）・言語を確かめる。実在の宛先へは送らない。受け手は、コンテナの実行環境を要しない JVM の中で動くものを第一とする（コンテナの受け手にするなら、Way of Working の「コンテナが無いときに飛ばしてよいもの」にメールのテストを加えるかを同時に決める）。具体の道具は設計の段で、ライセンスの確認とあわせて決める。
- （確認待ち）メールの送信を確定の後や別のスレッドで行う場合、届くまでの待ちは固定の `sleep` ではなく、上限の時間を決めて条件（受け手に届いた件数など）が成り立つまで待つ形にする（`team.md` の「`sleep` や実時刻に依存しない」の具体化）。
- （確認待ち）送信の失敗の場合（受け手が接続を拒む・応答しない）のテストを必ず含める。応答しない相手は、テストの中で開いて何も返さない `ServerSocket` で再現してよい（`project.md` Testing Posture の TIMEOUT の学びと同じ形）。失敗のときの業務の動作（招待を失敗させるか、再送に回すか）は要件・設計の段で決め、決めた動作をこのテストで確かめる。

#### 2.2 認証に関わる必須テストの一覧への追加（「（確認待ち）招待と登録の完了」「（確認待ち）メールの本文」）

主担当の3行に賛成し、次を足すことを提案する。

- 招待と登録の完了の行の末尾に: 「招待のトークン・招待の URL が、アプリのログ・監査ログ・エラー応答に含まれないこと（既存の `*SecretLeakIT` と同じ形で確かめる）」。今の必須テストの「秘密情報の漏えい」はパスワード・トークンの値としか書いておらず、招待のトークンが入るかが読み手によって分かれるため（F5、discovered-rules の Forbidden の候補と対になる）。
- メールの本文の行を次のように具体化する: 「差し込む値に `<`・`>`・`&`・`"`・`'` を含めても、タグ・属性としてそのまま出ないこと。テンプレートは利用者の値を `{{{ }}}`・`{{& }}` で差し込まず、属性は二重引用符で囲む（テンプレートのファイルを読んで確かめるテストでもよい）。すべてのテンプレートを日本語と英語の両方で描いて、件名が空でないこと・差し込み漏れ（`{{` の残り）が無いこと・ライセンスヘッダーが本文に出ないことを確かめる。招待の URL は設定したベースURLから組み立て、要求のヘッダーから組み立てないこと」。理由は F3（`'` はエスケープされない）と、テンプレートは JaCoCo の計測の外にあり、描く組み合わせを数で押さえないと片方の言語だけが確かめられずに残りうるため。

#### 2.3 パッケージごとの下限の行（「（確認待ち）全体の合計で判定している既存のパッケージ…」）

向き（一覧を減らすだけ）に賛成し、あいまいさを減らすために次を足すことを提案する。

- 実測はその Bolt のテストを足した後に `:backend:cleanTest :backend:cleanIntegrationTest` を付けた `verify` で行い（`project.md` Testing Posture の学び）、下限を満たしたパッケージは一覧から外し、以後は戻さない。満たさなかったパッケージは一覧に残し、実測の値を Build and Test の成果物に記録する。
- 面談では、この行と別に「新しい機能を既存の `user` に足すか、新しいパッケージに置くか」でカバレッジの守られ方が変わる（F1）ことを依頼者に伝える。どちらに置くかは設計の段の選択だが、既存のパッケージに足すときに上の手順が効く、という関係を示しておくと、設計の段で迷わない。

#### 2.4 E2E の行（「（確認待ち・記録の更新）E2E の道具は Playwright…」）

記録の更新（道具は Playwright、`verify` と CI の外）に賛成する。本数の決まりの直し方と、招待から登録の完了までの流れを足すかは、面談で決める必要がある。足す場合は次の2点も進め方として決めておかないと、E2E の実行の前提が変わる。

- メールの受け手: 招待の流れの E2E は、WAR から届く受け手と、受けたメールから招待の URL を取り出す口が要る（F4）。コンテナの受け手にすると E2E もコンテナの実行環境に依存する。
- 実行順への依存: 今の E2E はファイル名の順に1本ずつ流す前提（F4）。新しい流れは前のファイルが作った状態に頼らず、自分で利用者を作って確かめる形にすることを提案する（招待の流れは利用者を新しく作るので自然に満たせる）。
- 実行の時点: 下書きの「統合の前とリリースの前に手元で実行する」は、すべての Bolt の統合の前か、画面・認証に関わる Bolt だけかが読み分かれる。`team.md` の統合前の関門（1コマンドの検査）には E2E が入っていないため、どちらかを明記することを提案する。
