# User Stories の計画と質問（Intent 261102-timezone-ui-polish）

## ストーリーの計画（案）

- **ペルソナの作り方**: 要件（`requirements.md`）の利用者を、作業ロールの権限の違いで分ける。前の Intent のペルソナ（業務データを見る人・直す人・管理者）を引き継ぎ、今回のタイムゾーンの設定・ホーム・アイコンの目的を足す（Q1）。
- **ストーリーの形**: 「As a [ペルソナ], I want [目的], so that [得られること]」。INVEST（独立・交渉できる・価値がある・見積もれる・小さい・確かめられる）を満たすように分ける。ID は `US{群}.{番号}`、受け入れ基準は Given/When/Then で `AC{群}.{番号}.{番号}`。
- **優先度**: MoSCoW（Must・Should・Could・Won't）。要件で合意した範囲は原則 Must とし、Should は Q3 で決める。MVP の境は Delivery Planning で決める。
- **分け方**: Q2 で決める。
- **合否の判定の仕方**: 状態コードと code、「含まれない」「変わらない」の確かめ方、3種類の対象DB、画面の共通の決まり（言語・アクセシビリティ）は、前の Intent と同じく「前提と読み方」に一度だけ書き、各受け入れ基準では繰り返さない。
- **要件のレビューの指摘（R-01〜R-08）の扱い**: 要件の承認で「User Stories と設計で具体にする」とした8件のうち、リードが決められるもの（R-01 往復・R-03 重なる時刻の往復・R-05 `timetz` の入力・R-07 カードの移り先・R-08 直しの合格の条件）は、受け入れ基準に書く。依頼者の判断が要る3件（R-02・R-04・R-06）は Q5〜Q7 で尋ねる。

## Q4. [品質] 利用者に直接は見えない確かめ（FR5・FR6・FR8.4・FR11.4）の扱い

PostgreSQL の接続のタイムゾーン（FR5）と日時の型の不具合の確かめ（FR6）は、直すと「値が変わらない」「端数が落ちない」という形で利用者に見えます。仮の画面の検査の移し（FR8.4）と許すアイコンの名前の一覧のそろえ（FR11.4）は、利用者に見えません。

**推奨: A。** 理由: 利用者の結果になるもの（値が変わらない・端数が落ちない・桁つきの型が時点として変換される）は、受け入れ基準で確かめるのが自然です。見えないもの（検査の移しと一覧のそろえ）は、ストーリーにすると読み手が混乱するため、追跡の表で後の段へ回す形が読みやすくなります。

A. FR5・FR6 は、日時のストーリーの受け入れ基準（利用者に見える結果）にする。FR8.4 と FR11.4 はストーリーにせず、追跡の表で Build and Test・Code Generation へ Deferred にする
B. 4つとも、開発する人の視点のストーリーにする
C. 4つともストーリーにせず、追跡の表で後の段へ回す

## Q5. [開発] ブラウザとサーバーで IANA のタイムゾーンの名前が食い違うとき（レビューの指摘 R-02）

選べる名前は「ブラウザが知っているすべて」ですが、保存の検証はサーバーが知っている名前で行います。ブラウザとサーバーで IANA の版が違う、または別名（例: `Asia/Calcutta` と `Asia/Kolkata`）が違うと、画面が出した名前をサーバーが拒否することがあります。また、保存済みの名前を、後で使う端末のブラウザが知らないことがあります。

**推奨: A。** 理由: 保存の値を勝手に書き換えず、画面の側で安全に見せられます。サーバーが知らない名前はサーバー側の検証（FR1.3）が正で、拒否のとき選択が残るため、利用者が選び直せます。

A. サーバーが知らない名前は保存を拒否し（入力の誤り）、画面は選択を残して誤りを出す。保存済みの名前を今のブラウザが解釈できないときは、保存の値は変えず、表示だけ「ブラウザに合わせる」と同じ扱いにして、そのことを画面に出す
B. 保存済みの名前をブラウザが解釈できないときは、保存の値も「ブラウザに合わせる」（値が無い状態）に直す
C. 選べる一覧をサーバーが知っている名前に絞る（ブラウザが知っていてもサーバーが知らない名前は出さない）
X. Other (please specify)

[Answer]: A

## Q6. [プロダクト] 設定の読み込みが終わる前の時刻の表示（レビューの指摘 R-06）

表示のタイムゾーンはサーバーに保存した設定のため、画面を開いた直後は、読み込みが終わるまで設定が分かりません。

**推奨: A。** 理由: ブラウザのタイムゾーンの時刻が一瞬出てから切り替わると、読み違えたまま操作する恐れがあります。ログイン後は設定を読んでから画面を出すため、待ちを増やさずにそろえられます。

A. 読み込みが終わるまで、時刻の欄は出さない（読み込み中の表示にする）
B. 読み込みの前はブラウザのタイムゾーンで出し、設定が分かったら切り替える
X. Other (please specify)

[Answer]: A

## Q7. [プロダクト] 検索の範囲の端（レビューの指摘 R-04）

時点を表す型の検索で範囲（始まりと終わり）を入れるとき、終わりの時刻を含むか、日付だけを入れたときの一日の境目が決まっていません。

**推奨: A。** 理由: 前の Intent の範囲の決まり（検証の範囲は両端を含む）とそろえると、利用者が覚えることが増えません。日付だけの入力は、表示のタイムゾーンの 0 時から 24 時の一日を表すと決めておけば、日付の変わり目がずれません。

A. 始まりも終わりも含む（両端を含む）。時点を表す型の検索には日付だけを入れる口を置かず、日時で入れる（日付だけの型のカラムは今どおり日付で入れる）
B. 始まりは含み、終わりは含まない（半開区間）。日付だけを入れたときは、表示のタイムゾーンの一日の 0 時から翌日の 0 時までとする
