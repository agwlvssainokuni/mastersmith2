# User Stories の実施の判断（Intent 261102-timezone-ui-polish）

## 判断

**Execute（実施する）**

## 理由

- 利用者の画面に直接見える変更が中心である。表示のタイムゾーンの設定（プリファレンス）、業務データの日時の表示・入力・検索、ホームの入口、アイコンと favicon、管理メニューと業務メニューのアイコンは、いずれも利用者が見て触るもの。
- 立場の違う利用者が関わる。業務データを見る人・直す人・管理者で、同じ日時の画面を別の目的で使い、管理の入口や廃止する仮の画面は管理者にだけ関わる。
- 業務の決まりが複雑である。時点を表す型と時差を持たない型の区別、夏時間で存在しない時刻・重なる時刻、往復（読んだ値をそのまま送り返しても対象DB の値が変わらない）、3種類の対象DB の型の違いなど、境目の多い決まりを、合否の分かる受け入れ基準にして残す必要がある。
- 要件のレビュー（READY、指摘 R-01〜R-08）が「User Stories と設計で具体にする」とした点を、受け入れ基準で決める場所が要る。

## 考えた要素

- **種類**: 既存の機能の拡張（N6・ホーム・アイコン）と画面の削除（管理の仮の画面）。新しい機能の画面は、ホームのカードとプリファレンスのタイムゾーンの選択だけ。
- **利用者に見える範囲**: 大きい。ストーリーにして確かめる価値がある。
- **複雑さの印**: 3種類の対象DB・夏時間・往復・上流（make-you-chic-ui）の対応待ち（ロゴとアイコン）。
- **規模**: 要件 FR11 群・NFR6 群。Standard の深さで、群5つ・ストーリー十数件にする見込み。

## ストーリーが特に効く場所

- 日時の往復と夏時間の境目（US2.3・US2.5）: 画面と対象DB の間で時点がずれないことを、利用者の結果として確かめる。
- タイムゾーンの名前の食い違い（US1.1・US1.2）: ブラウザとサーバーの知っている名前が違うときの、利用者への見え方を決める。
- ホームのカードの移り先（US3.1）: 子を持つ項目・権限で子が見えない項目の移り先を決める。

## 代わりの手段（実施しない場合）

該当なし。要件だけでは、受け入れの合否（往復・夏時間・権限・アクセシビリティ）を利用者の言葉で確かめられない。
