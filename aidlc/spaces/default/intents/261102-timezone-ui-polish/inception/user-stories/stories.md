# ユーザーストーリー — timezone-ui-polish（Intent 261102-timezone-ui-polish）

出典: `aidlc/spaces/default/intents/261102-timezone-ui-polish/inception/requirements-analysis/requirements.md`（FR1〜FR11・NFR1〜NFR6）、ストーリーの質問と答え（`user-stories-questions.md` の Q1〜Q7）、要件のレビューの指摘（`inception/requirements-analysis/reviews/review-01.md` の R-01〜R-08）。ペルソナは `personas.md`（P1 見る人・P2 直す人・P3 管理者）。

## 前提と読み方（すべての受け入れ基準に共通）

### 分け方・優先度

- **分け方**: 目的ごとの群（Q2 A）。群1 表示のタイムゾーンの設定、群2 業務データの日時の表示と入力、群3 ホームと管理の仮の画面の廃止、群4 アイコン、群5 横断の決まりと日時の型の不具合の確かめ。
- **優先度**: 要件で合意した範囲は Must。上流（make-you-chic-ui）の対応を待つ部分だけ Should（Q3 A）: 上のバーのロゴ（FR9.4、US4.2）と、上流に無い管理メニューのアイコン（FR10.2）。1つのストーリーに Should の部分が混ざるときは、ストーリーを Must とし、その受け入れ基準に **〔Should〕** と印を付ける（US4.3 の AC4.3.3）。Should を見送っても Must の確かめが抜けないよう、Must と Should は別の受け入れ基準に分ける。MVP の境は Delivery Planning で決める。
- **ID**: ストーリーは `US{群}.{番号}`、受け入れ基準は `AC{群}.{番号}.{番号}`。

### 日時の型の読み方

- **時点を表す型**: PostgreSQL の `timestamptz`、MySQL・MariaDB の `timestamp`。表示のタイムゾーンに直して見せ、入力と検索も表示のタイムゾーンで入れる（FR2.1・FR3.1・FR3.2）。
- **時差を持たない型**: MySQL・MariaDB の `datetime`・`date`・`time`、PostgreSQL の `timestamp`・`date`・`time`。DB の値のまま見せ、時差を添えない（FR2.3・FR3.5）。
- **`timetz`**: PostgreSQL の日付の無い時差つきの型。変換せず、DB の値と時差のまま見せ、入れる（FR2.4。前提 A1）。
- **表示のタイムゾーン**: プリファレンスで選んだタイムゾーン。選んでいなければ（「ブラウザに合わせる」）ブラウザのタイムゾーン（FR1.5）。
- **時差の添え方**: 時点を表す型の値には、表示のタイムゾーンに直した時刻に時差（例: `+09:00`）を添える（FR2.2）。

### 業務の決まりの読み方

- **往復（R-01・R-03）**: 画面が読んだ値をそのまま更新に送っても、対象DB の値は変わらない。時点を表す型が主キー・同時更新の判定の値・参照の値になるときも、行の特定と衝突の判定は、表示のタイムゾーンへの変換の前後で変わらない。そのため、画面は表示用の文字列とは別に、元の時点を保った値を持ち、送り返す。夏時間の重なる時刻も、表示した値を送り返して保存した時点が変わらない。値の持ち方（時差つきの形など）は機能設計で決める。
- **夏時間の存在しない時刻（FR3.4）**: 入れた時刻が表示のタイムゾーンで存在しないときは、画面とサーバーの両方で、その項目の入力の誤りとして拒否し、保存しない。サーバーの拒否は既存の入力の誤り（`VALIDATION_FAILED`）と同じ形で、どの項目かを示す。
- **夏時間の重なる時刻（R-03）**: 同じ時刻が2回ある時刻は、どちらの時点かを失わず保つ。入れ方（時差を添える・どちらかを選ぶなど）は機能設計で決め、決めた側の動作を明示したテストにする。
- **検索の範囲の端（Q7 A・R-04）**: 時点を表す型の範囲は、始まりも終わりも含む。日付だけを入れる口は置かず、日時で入れる。日付だけの型（`date`）のカラムは今どおり日付で入れる。
- **名前の食い違い（Q5 A・R-02）**: サーバーは IANA の名前として知らないタイムゾーンの保存を、入力の誤りとして拒否し、保存済みの値を変えない。画面は選択を残して誤りを出す。保存済みの名前を今のブラウザが解釈できないときは、保存の値を変えず、表示だけ「ブラウザに合わせる」と同じ扱いにして、そのことを画面に出す。
- **読み込みの前（Q6 A・R-06）**: 設定を読み込むまで、時刻の欄は出さず、読み込み中の表示にする。ブラウザのタイムゾーンの時刻を一瞬出して切り替えることはしない。
- **ホームのカードの移り先（R-07）**: 業務メニューの最上位の項目のカードを押すと、その項目の画面へ移る。子を持つ項目（フォルダ）は、メニューの並びで最初に画面を持つ（テーブルかビューを指す）子孫へ移る。見える子孫に画面を持つものが無い項目は、メニューの応答に出ないため、カードも出さない。
- **日時の型の不具合の直しの合格の条件（R-08）**: FR6.1 は、3 桁・6 桁の秒の端数が、既定の DSL の生成・保存・往復で落ちないこと。FR6.2 は、桁つきの時差つきの型（`timestamp(n) with time zone`）が時点を表す型として変換されること。確かめて不具合でなければ、直さずに確かめた結果を記録する（FR6.3）。
- **判定の仕方**: 「含まれない」「変わらない」は、応答・対象DB・内部DB・ログの中身を確かめて判定する。画面の確かめは、`ja` と `en` の両方の言語で行う。サーバー側の拒否は Problem Details（`code` つき）の形で返す。

### 共通の受け入れ基準の読み方

- **アクセシビリティ**: ホーム・プリファレンス・業務データの一覧・詳細・入力・検索の画面とログインの画面は、WCAG 2.1 AA を満たし、実際のブラウザの axe で違反 0 件にする。ブランドカラーとテーマのすべての組で確かめる（NFR3.1）。個々の確かめは US5.2 にまとめ、各ストーリーでは、そのストーリー固有の点だけを書く。
- **言語**: 足す画面の文言は日本語と英語の両方を用意し、既定は日本語（NFR6.1）。
- **テストの時差**: テストのタイムゾーンは固定し、別の時差を確かめるテストはその時差を明示に指定する（NFR5.2）。

## 群1 表示のタイムゾーンの設定

### US1.1 表示のタイムゾーンを選んで保存する 〔Must〕

As a 業務データを見る人（P1）や直す人（P2）, I want プリファレンスの画面で、自分が使うタイムゾーンを選んで保存したい, so that 業務データの日時を、頭の中で直さず自分のタイムゾーンで読み書きできる。

- **AC1.1.1** Given ログイン中の利用者 / When プリファレンスの画面を開く / Then 表示のタイムゾーンの選択があり、「ブラウザに合わせる」（既定）と、ブラウザが知っている IANA のタイムゾーンを選べる。各項目は IANA の名前と今の時差で示す（例: `Asia/Tokyo (+09:00)`）
- **AC1.1.2** Given 利用者が `Asia/Tokyo` を選んだ / When 保存する / Then 設定はサーバー側の利用者の設定として保存され、別の端末・別のブラウザでログインしても同じタイムゾーンで見える。「ブラウザに合わせる」を選んで保存したときは、値が無い状態として保存される
- **AC1.1.3** Given 保存の要求のタイムゾーンが IANA の名前として存在しない（例: `Mars/Phobos`・空でない不正な文字列） / When サーバーが保存の要求を受ける / Then 入力の誤り（`VALIDATION_FAILED`）で拒否し、保存済みの値を変えない。画面は選択を残し、誤りを出す（Q5 A）
- **AC1.1.4** Given 画面が出した名前をサーバーが IANA の名前として知らない（IANA の版の違い・別名の違い） / When 保存する / Then AC1.1.3 と同じく拒否され、選択が残るため、利用者は別の名前を選び直せる。保存済みの値は変わらない
- **AC1.1.5** Given 要求の本文に、他の利用者の ID や他の利用者の表示のタイムゾーンを入れた / When 保存を要求する / Then 他の利用者の設定は変わらない。自分の設定だけが変わる（一括代入・IDOR の防止。NFR1.2）
- **AC1.1.6** Given 利用者が未認証 / When 表示のタイムゾーンを保存する API を呼ぶ / Then 401。ほかの利用者の設定を読む・変える API は無い
- **AC1.1.7** Given キーボードだけで操作する利用者、または読み上げを使う利用者 / When タイムゾーンの選択を操作する / Then キーボードだけで選べ、選んだ値と時差が読み上げられる（NFR3.3）
- **AC1.1.8** Given 内部DB の利用者の表に表示のタイムゾーンの列を足す移行 / When 前の版のアプリで起動する / Then 前の版は足した列を読まずにそのまま動く（足すだけの変更。NFR4.1）

### US1.2 選んだタイムゾーンが、画面の時刻にすぐ効く 〔Must〕

As a 業務データを見る人（P1）や管理者（P3）, I want タイムゾーンを変えたら、開いている画面の時刻もそのタイムゾーンで見えてほしい, so that 画面を読み込み直さなくても、画面ごとの時刻が食い違わない。

- **AC1.2.1** Given 一覧に時点を表す型の値が `+09:00` で出ている / When プリファレンスで別のタイムゾーン（例: `America/New_York`）を保存する / Then 画面を読み込み直さなくても、表示中の画面の時刻がそのタイムゾーンと時差で出る（FR1.4）
- **AC1.2.2** Given 利用者が「ブラウザに合わせる」を選んでいる / When 画面の時刻を見る / Then ブラウザのタイムゾーンで出る（FR1.5）
- **AC1.2.3** Given 利用者の一覧・招待の一覧・DSL の状態と履歴など、今ブラウザのタイムゾーンで時刻を見せている画面 / When 表示のタイムゾーンを `Asia/Tokyo` にして見る / Then それらの時刻も `Asia/Tokyo` で出る。業務データの画面と同じ時点は同じ時刻に見える（FR4.1）
- **AC1.2.4** Given 保存済みの名前を今のブラウザが解釈できない / When 画面の時刻を見る / Then 保存の値は変えず、表示はブラウザのタイムゾーンで出て、設定を解釈できないことを画面に出す。利用者はプリファレンスで選び直せる（Q5 A・R-02）
- **AC1.2.5** Given 設定の読み込みが終わっていない最初の描画 / When 時刻の欄を出す画面を開く / Then 時刻の欄は出さず、読み込み中の表示にする。読み込みが終わってから、表示のタイムゾーンの時刻を出す。ブラウザのタイムゾーンの時刻が一瞬出ることはない（Q6 A・R-06）
- **AC1.2.6** Given 各画面の時刻の整形 / When 実装を見る / Then 変換は画面の側の1か所（`src/shared/format/`）に閉じ、各画面はその部品だけを使う。ブラウザの既定のタイムゾーンを暗に使わず、時差を明示に渡す（FR4.2。確かめるのは機能設計・コード生成）

## 群2 業務データの日時の表示と入力

### US2.1 時点を表す型の値を、自分のタイムゾーンで見る 〔Must〕

As a 業務データを見る人（P1）, I want 一覧・詳細・参照の選択肢で、時点を表す日時を自分のタイムゾーンと時差つきで見たい, so that UTC のままの日付の1日のずれに惑わされない。

- **AC2.1.1** Given PostgreSQL の `timestamptz` の値 `2026-11-01T15:00:00Z` と、表示のタイムゾーン `Asia/Tokyo` / When 一覧・詳細を見る / Then `2026-11-02 00:00:00 +09:00` のように、日付が変わった時刻に時差を添えて出る（日付の変わり目）
- **AC2.1.2** Given MySQL・MariaDB の `timestamp` の値 / When 同じ表示のタイムゾーンで見る / Then 同じ時点は同じ時刻に見える。3種類の対象DB で、同じ時点が同じ表示になる（FR2.1。3種類の対象DB は結合テストで確かめる）
- **AC2.1.3** Given 参照の選択肢と表示名に時点を表す型の値が含まれる / When 選択肢を見る / Then 表示のタイムゾーンに直して出る（FR2.1）
- **AC2.1.4** Given 秒の端数が 0・3・6 桁の値 / When 見る / Then DB の値の桁のまま出て、表示で丸めない（FR2.5）
- **AC2.1.5** Given 夏時間のある地域（例: `America/New_York`）と、夏時間の切り替わりの前後の時点 / When 見る / Then 時差が `-04:00` と `-05:00` に切り替わって出る。分の端数の時差（`+05:45`・`+09:30`・`-03:30`）も、端数のまま出る
- **AC2.1.6** Given MySQL の `timestamp` の上限（2038 年）の値、時差の無い型の範囲を超える値 / When 見る / Then 読めない値の扱いを機能設計で決め、決めた側の動作を明示したテストで確かめる（K-99。要件の範囲の端）
- **AC2.1.7** Given 対象DB への問い合わせの数 / When 日時の変換を足す / Then 業務データの API が使う対象DB・内部DB の問い合わせの数は増えない（NFR2.1）

### US2.2 時差を持たない型と `timetz` は、DB の値のまま見る・入れる 〔Must〕

As a 業務データを見る人（P1）や直す人（P2）, I want 日付だけ・時刻だけ・時差の無い日時のカラムは、DB に入っている値のまま見て入れたい, so that 時差の無い値が、知らないうちにずれない。

- **AC2.2.1** Given MySQL・MariaDB の `datetime`・`date`・`time`、PostgreSQL の `timestamp`・`date`・`time` の値 / When 表示のタイムゾーンを何に変えても見る / Then DB の値のまま出て、時差は添えない。タイムゾーンを変えても値は変わらない（FR2.3）
- **AC2.2.2** Given PostgreSQL の `timetz` の値 / When 見る / Then 変換せず、DB の値と時差のまま出る（FR2.4。前提 A1）
- **AC2.2.3** Given 作成・更新・検索で時差を持たない型と `timetz` のカラム / When 値を入れる / Then 時差を持たない型は DB の値のまま、`timetz` は DB の値と時差のまま入れる。表示のタイムゾーンでは入れない（FR3.5・R-05）
- **AC2.2.4** Given PostgreSQL の対象DB の接続 / When 接続を作る / Then セッションのタイムゾーンを UTC に明示に設定する（読み取りと書き込みの両方）。JVM の既定のタイムゾーンに頼らない。この変更の前後で、時差を持たない型の読み書きの値は変わらない（FR5。MySQL・MariaDB と同じ形。結合テストで3種類を確かめる）

### US2.3 表示のタイムゾーンで日時を入力して、作成・更新する 〔Must〕

As a 業務データを直す人（P2）, I want 時点を表す日時を自分のタイムゾーンで入れて保存したい, so that UTC に頭の中で直して入れる間違いを無くす。

- **AC2.3.1** Given 作成の画面、時点を表す型のカラム、表示のタイムゾーン `Asia/Tokyo` / When `2026-11-02 00:00:00` と入れて保存する / Then 画面は時差つきで送り、サーバーは時点 `2026-11-01T15:00:00Z` として保存する。一覧・詳細で `2026-11-02 00:00:00 +09:00` に見える（FR3.1）
- **AC2.3.2** Given 入力の欄の案内 / When 時点を表す型の欄を見る / Then 「UTC で入れる」の案内ではなく、表示のタイムゾーンを示す案内（例: `Asia/Tokyo (+09:00) で入力`）が出る（FR3.6）
- **AC2.3.3** Given 夏時間の切り替わりで存在しない時刻（例: `America/New_York` の `2026-03-08 02:30:00`） / When 入れて保存する / Then 画面とサーバーの両方で、どの項目かを示す入力の誤りとして拒否し、保存しない。サーバーは `VALIDATION_FAILED` で、API を直接呼んでも同じ（FR3.4。前提 A2）
- **AC2.3.4** Given 夏時間の重なる時刻（例: `America/New_York` の `2026-11-01 01:30:00`、2回ある） / When 入れて保存する・保存した値を見る / Then どちらの時点かを失わず保存し、表示した値を見ても、どちらの時点か分かる。決める入れ方は機能設計で決め、決めた側の動作を明示したテストにする（R-03）
- **AC2.3.5** Given 時点を表す型のカラムに、日時として読めない値を入れた / When 保存する / Then 画面で保存の前に、どの項目かを示す入力の誤りが出る。画面を通さずに API を直接呼んでも、サーバーが同じ誤りで拒否する（サーバー側を正とする）
- **AC2.3.6** Given MySQL・MariaDB・PostgreSQL の3種類 / When 時点を表す型を作成・更新する / Then どの対象DB でも保存した時点が同じ。時差を持たない型は DB の値のまま保存される（結合テストで確かめる）

### US2.4 日時で行を探す 〔Must〕

As a 業務データを見る人（P1）や直す人（P2）, I want 時点を表す日時を、自分のタイムゾーンで検索の条件に入れて行を絞りたい, so that 「昨日の日本時間 0 時以降」のような探し方が、そのまま通る。

- **AC2.4.1** Given 時点を表す型のカラムの検索の条件 / When 表示のタイムゾーンで日時を入れる / Then 画面は時差つきで送り、サーバーはその時点で絞る。値を入れる欄の案内は表示のタイムゾーンを示す（FR3.2）
- **AC2.4.2** Given 範囲（始まりと終わり）を入れる検索 / When 始まりの時点ちょうど・終わりの時点ちょうどの行がある / Then どちらも結果に含まれる（両端を含む。Q7 A・R-04）。始まりが終わりより後のときは入力の誤り（400）
- **AC2.4.3** Given 時点を表す型の検索 / When 入力を見る / Then 日付だけを入れる口は無く、日時で入れる。日付だけの型（`date`）のカラムは今どおり日付で入れる（Q7 A）
- **AC2.4.4** Given 夏時間の存在しない時刻を検索の条件に入れた / When 検索する / Then 入力の誤りとして、どの項目かを示して拒否する（AC2.3.3 と同じ決まり）
- **AC2.4.5** Given 検索の値に `'`・`"`・`;`・`--`・改行を含めた / When 検索する / Then SQL として解釈されない（今までの SQL の組み立ての決まりが、日時の変換を足しても保たれる）

### US2.5 読んだ値をそのまま送り返しても、日時が変わらない（往復） 〔Must〕

As a 業務データを直す人（P2）, I want 別のカラムだけを直して保存したとき、日時のカラムの値が変わらない, so that 変えていない日時が、変換で黙ってずれない。

- **AC2.5.1** Given 時点を表す型のカラムを持つ行を更新の画面で開き、別のカラムだけ変えて保存する / When 保存する / Then 時点を表す型のカラムは、画面で「変えた」と扱われず、対象DB の値は変わらない（FR3.3）
- **AC2.5.2** Given 時点を表す型の値を、読んだままの値で更新に送る（API を直接呼ぶ） / When 更新する / Then 対象DB の値は変わらない。秒の端数（0・3・6 桁）も落ちない・丸められない（FR2.5）
- **AC2.5.3** Given 時点を表す型のカラムが主キー・同時更新の判定の値・参照の値になる行 / When 一覧・詳細で表示のタイムゾーンに直して見て、そのまま更新・削除・詳細へ移る / Then 画面は表示用の値とは別に元の時点を保って送り返し、行の特定と衝突の判定は、変換の前後で変わらない。表示用の丸めた値や時差つきの文字列を送っても行が特定できない・更新が衝突扱いになることはない（R-01）

## 群5 横断の決まりと日時の型の不具合の確かめ

- **AC5.1.5** Given 日時の型の確かめ（K-95・K-98 は未検証） / When NFR 設計か Code Generation の前の捨ての試しで確かめる / Then 結果の要点を成果物に写し、不具合のときの直しを同じ Intent の単位に入れる

## INVEST の確かめ

- **Independent**: US1.1・US4.1・US3.3 は単独で確かめられる。US2.x は US1.2 に依存するが、表示のタイムゾーンが「ブラウザに合わせる」の既定でも単独で確かめられる。
- **Negotiable**: 図柄・アイコンの割り当て・ホームの配置・入れ方は、画面イメージと機能設計で決める。
- **Valuable**: どのストーリーも、利用者（P1・P2・P3）の読み違い・入れ間違い・迷いが減る。
- **Estimable**: 要件の FR ごとに範囲が決まっている。上流の対応待ちは Should に分けた。
- **Small**: US2.x は型・操作ごと、US3.x は画面ごと、US4.x は図柄・ロゴ・メニューごとに分けた。
- **Testable**: 受け入れ基準は Given/When/Then で、日付・時差・境界の値を具体にした。
