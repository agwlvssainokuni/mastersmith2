## 2. 共通の決まり

- **幅**: 狭い幅（375 px）から広い幅まで。サイドバーは今の AppShell の動き（狭い幅では折りたたむ）のまま。横の画面全体のスクロールを出さない。開いたメニュー・ポップアップも画面の中に収める（`project.md` の学び）。
- **言語**: 日本語と英語の両方。既定は日本語。文言の鍵は機能ごとに持つ。
- **アイコン**: make-you-chic-ui の `Icon`。飾りのときは読み上げから外し（`aria-hidden`）、意味を持つときだけ名前（`aria-label`）を付ける。
- **時刻の出し方**: 時点を表す型は `YYYY-MM-DD HH:mm:ss[.SSS|.SSSSSS] ±HH:mm`。時差を持たない型は DB の値のまま（時差なし）。変換の部品は `src/shared/format/` の1か所。
- **読み込みの前**: 設定を読み込むまで時刻の欄は出さない。読み込み中の表示（今の画面の読み込み中の形）にする（ストーリー Q6 A）。

## 3. S1 プリファレンス（表示のタイムゾーン）

氏名・言語の次に、表示のタイムゾーンを足す（Q1 A）。部品は `Select`。

```text
┌ プリファレンス ─────────────────────────────────────────┐
│ 氏名            [ 佐藤 花子                          ]  │
│ 言語            (●) 日本語  ( ) English                   │
│ 表示のタイムゾーン                                         │
│   [ ブラウザに合わせる                              ▼ ]  │
│   時刻の欄に使うタイムゾーンです。業務データの日時と、   │
│   利用者の一覧などの時刻に効きます。                      │
│ テーマ …                       文字の大きさ …            │
│                                 [元に戻す] [保存する]     │
└──────────────────────────────────────────────────────────┘
```

- 選択肢: 先頭が「ブラウザに合わせる」（既定。保存は値が無い状態）。続けて `Asia/Tokyo (+09:00)` の形で、IANA の名前と今の時差を並べる。地域（Asia・America など）ごとのまとまりが `Select` で使えるかは機能設計で確かめる。ブラウザが知らない名前は並べない。
- 状態:
  - 読み込み中: フォーム全体の読み込み中の表示（今のまま）。
  - 保存中: 「保存する」を loading にし、選択は変えられない（今の言語と同じ）。
  - 保存の拒否（サーバーが知らない名前）: 選択を残し、`Select` の下に誤りの文を出す（`FormField` の誤り）。例: 「このタイムゾーンは使えません。別のタイムゾーンを選んでください。」（AC1.1.3・AC1.1.4）。
  - 保存済みの名前を今のブラウザが解釈できない: `Select` の上に `Alert`（warning）を出す。例: 「保存したタイムゾーン（Mars/Phobos）をこの端末では使えないため、ブラウザのタイムゾーンで表示しています。」保存の値は変えず、選び直せる（AC1.2.4）。
  - 保存の成功: 今のプリファレンスの保存の知らせと同じ（`Toast` か画面の知らせ）。保存の後は、読み込み直さなくても画面の時刻が切り替わる（AC1.2.1）。
- 英語の文言: 「Display time zone」「Follow the browser」「This time zone is not available. Choose another one.」「The saved time zone (…) is not available on this device, so times are shown in the browser time zone.」。

## 4. S2 業務データの一覧・詳細（時刻の表示）

見出しの近くに、1行の案内を出す（Q2 B）。

```text
┌ 受注（orders）─────────────────────────────────────────┐
│ 表示のタイムゾーン: Asia/Tokyo（プリファレンスで変更）   │
│ ┌ 受注ID ┬ 受注の時刻（timestamptz）──────┬ 納期（date）┐ │
│ │ 1001   │ 2026-11-02 00:00:00 +09:00     │ 2026-11-05  │ │
│ │ 1002   │ 2026-11-02 09:30:15.123 +09:00 │ 2026-11-06  │ │
│ └────────┴────────────────────────────────┴─────────────┘ │
└─────────────────────────────────────────────────────────┘
```

- 案内の1行の3つの形:
  - 設定あり: 「表示のタイムゾーン: Asia/Tokyo（プリファレンスで変更）」。「プリファレンスで変更」はプリファレンスへのリンク。
  - ブラウザに合わせている: 「表示のタイムゾーン: ブラウザのタイムゾーン（Asia/Tokyo）（プリファレンスで変更）」。
  - 保存済みの名前を解釈できない: 「保存したタイムゾーンを使えないため、ブラウザのタイムゾーン（Asia/Tokyo）で表示しています（プリファレンスで変更）」。
- 時点を表す型の値だけ時差を添える。`date`・`time`・`datetime`・`timestamp`（PostgreSQL）は DB の値のまま、時差を添えない（AC2.2.1）。`timetz` は DB の値と時差のまま（AC2.2.2）。
- 秒の端数は DB の値の桁のまま。丸めない（AC2.1.4）。夏時間の地域は時差が `-04:00` と `-05:00` に切り替わって出る（AC2.1.5）。
- 詳細の画面も同じ（項目の値に時差、見出しの近くに案内の1行）。参照の選択肢・表示名の時刻も同じ形（AC2.1.3）。
- 一覧・詳細の読み込みの前は、案内の1行も時刻の欄も出さず、読み込み中にする。

## 5. S3 作成・更新（時点を表す型の入力）

入力は文字の入力（`TextInput`）にする（Q3 A）。ブラウザの `datetime-local` は使わない（選んだタイムゾーンと食い違い、秒の端数を入れられないため）。

```text
受注の時刻 *
[ 2026-11-02 09:30:15                        ]
 Asia/Tokyo (+09:00) で入力。例: 2026-11-02 09:30:15（秒の端数は .123 のように付けられます）
```

- 欄の下の案内に、書式の例と「Asia/Tokyo (+09:00) で入力」を出す（FR3.6）。案内は欄に `aria-describedby` で結び付ける。
- 空欄: NULL になる型は空欄で保存できる（前の Intent の M2 の決まりのまま）。更新の画面で、変えていない欄は送らない（AC2.5.1）。
- 夏時間の誤り（Q4 A）:

```text
受注の時刻 *
[ 2026-03-08 02:30:00                        ]   ← 誤り
 America/New_York では、この時刻はありません（夏時間の切り替えで 02:00 から 03:00 に進みます）。
```

```text
受注の時刻 *
[ 2026-11-01 01:30:00                        ]
 America/New_York では、この時刻は2回あります。どちらですか。
   (●) 先（夏時間、-04:00）   ( ) 後（標準時、-05:00）
```

  - 存在しない時刻: 欄の下に誤りの文を出し、保存させない。サーバーも `VALIDATION_FAILED` で拒否する（AC2.3.3）。
  - 重なる時刻: 欄の下に「2回あります」と、先・後の2つのラジオ（`RadioGroup`）を出す。選ぶまで保存させない（AC2.3.4）。選んだ値の時差を保存に使う。更新の画面で、重なる時刻の値を変えずに別の欄だけ直すときは、元の時点を保つため、このラジオは出さない（AC2.5.4）。
  - 重なる時刻の入れ方（時差を送る形など）は機能設計で決める。ここは画面の形だけ。
- 読めない値: 日時として読めないときは、欄の下に入力の誤りを出す（AC2.3.5）。
- 時差を持たない型の欄は、今のまま（案内に「UTC」「表示のタイムゾーン」を出さない）。

## 6. S4 検索（時点を表す型）

```text
受注の時刻（timestamptz）  から [ 2026-11-01 00:00:00 ]  まで [ 2026-11-30 23:59:59 ]
 Asia/Tokyo (+09:00) で入力。始まりも終わりも含みます。
```

- 範囲の2つの欄は `TextInput`。日付だけを入れる口は置かない（ストーリー Q7 A）。案内で「始まりも終わりも含む」と伝える。
- 日付だけの型（`date`）の条件は、今の日付の入力のまま。
- 始まりが終わりより後のときは、画面で入力の誤りを出す（サーバーは 400。AC2.4.2）。夏時間の存在しない時刻は S3 と同じ誤り（AC2.4.4）。

## 7. S5 ホーム

見出しで業務と管理を分ける（Q5 A）。

```text
┌ ホーム ──────────────────────────────────────────────────┐
│ 作業ロール: 商品マスタ担当                                  │
│                                                            │
│ 業務                                                       │
│ ┌────────┐ ┌────────┐ ┌────────┐                          │
│ │ ☰ 商品 │ │ ☰ 受注 │ │ ☰ 顧客 │                          │
│ └────────┘ └────────┘ └────────┘                          │
│ 管理（管理の権限を持つ人にだけ）                            │
│ ┌────────┐ ┌────────┐ ┌──────────┐ ┌────────┐ …          │
│ │ ● 利用者│ │   招待 │ │ ◆ ロールの│ │ ✎ DSL  │            │
│ └────────┘ └────────┘ │   受け渡し │ └────────┘            │
│                        └──────────┘                        │
└────────────────────────────────────────────────────────────┘
```

- 構成: 見出し（h1「ホーム」）、作業ロールの1行、「業務」の見出し（h2）とカードの並び、管理の権限を持つ人にだけ「管理」の見出し（h2）とカードの並び。
- カード: アイコンと名前だけ（説明文は無し）。幅に合わせて折り返す。部品は `Card` のリンク（押すと移る）。名前とアイコンはサイドバーと同じ規則で決める（FR7.2）。
- 業務のカードの移り先: テーブル・ビューは、その項目の画面。フォルダ（子を持つ項目）は、メニューの並びで最初に画面を持つ子孫の画面（AC3.1.4）。見える子孫に画面を持つものが無い項目は、メニューの応答に出ないため、カードも出ない。
- 管理のカード: サイドバーの管理の区画と同じ項目（利用者・招待・グループ・ロール・ロールの受け渡し・DSL）。権限の無い人には見出しごと出さない（AC3.2.2）。
- 状態: 読み込み中は出さない。業務メニューが無い・作業ロールが無い・何も見えない・読み込みの失敗は、今の案内（`home.notConfigured`・`home.noRole`・`home.nothingVisible`・`home.loadError`）を `Alert` で出し、失敗のときは「もう一度」を添える（AC3.1.6）。管理の権限を持つ人は、業務の案内が出ていても、管理のカードは出る。
- 作業ロールが無いときの1行は「作業ロール: なし」とする。「自分の権限を見る」のリンクは、今どおり案内に添える。
- 英語の見出し: 「Home」「Work role: …」「Business」「Administration」。

## 8. S6 サイドバーのアイコン

```text
 ホーム
 ── 業務 ──
 ☰ 商品                ← DSL の icon があればそれ。無いときは今の既定（取り込むまで1種類）
 ▸ 受注（フォルダ）
 ── 管理 ──
 ● 利用者   (user)
   招待                ← 上流に依頼して取り込むまでアイコン無し
   グループ            ← 同上
   ロール              ← 同上
 ⇩ ロールの受け渡し (download)
 ✎ DSL (edit)
```

- 管理の区画（Q7 A）: 今の登録のアイコンで意味が近い3項目にだけ付ける（利用者＝`user`、ロールの受け渡し＝`download`、DSL＝`edit`）。招待・グループ・ロールは、上流に新しいアイコン（`mail`・`users`・`shield`）を依頼し、取り込むまでアイコンを付けない。取り込んだら付ける（ストーリー AC4.3.3）。
- 業務の区画（Q8 A）: DSL の `icon` があればそれ（今どおり、許す一覧で照らす）。無いときの既定は、上流にテーブル・ビュー・フォルダ（`table`・`view`・`folder`）を依頼し、取り込むまで今のまま。取り込んだら、3種類で見分ける（ストーリー AC4.4.2）。
- 「管理」の仮の項目は無くなる（AC3.3.1）。
- アイコンはすべて飾り（`aria-hidden`）。項目の名前が文字で伝わる。

## 10. S8 タブと枠

- favicon: SVG の favicon（固定のブランドの色）と、SVG を読めないブラウザ向けの `.ico` か `.png`（元の SVG から作る手順を README か記録に書く）。`/favicon.ico` には画像を返す（AC4.1.3）。
- 上のバーのロゴ（Should、ストーリー US4.2）: make-you-chic-ui の Topbar にロゴを置く口を上流に依頼し、取り込めたら、左端に小さなアイコンを出す。取り込むまでは出さない。

## 11. アイコンの図柄（Q6 A）

- 鍛冶の金床の上にハンマーがある、輪郭の1色の図柄。小さな画面（16〜32 px の favicon）でも形が読めるよう、線を太めにし、細部を減らす。
- アプリの中は `currentColor` でテーマ（ライト・ダーク）に追従する。favicon は固定のブランドの色で、背景が明るくても暗くても読める。
- SVG にはスクリプト・イベントの属性・外部の参照を入れず、先頭に Apache License 2.0 のヘッダー（`<!-- ... -->`）を置く（NFR1.1）。図柄の最終の形は、コード生成で作った SVG を、この段の方向と合わせて確かめる。

## 13. ストーリー・要件との差

- **AC4.3.1（管理メニューのアイコン）**: 「項目ごとに違うアイコン」は、今の登録で意味が近い3項目（利用者・ロールの受け渡し・DSL）に限る（Q7 A）。招待・グループ・ロールは AC4.3.3（Should）の取り込み後に付ける。ストーリーのレビューの指摘 R-02 の解決。承認済みのストーリーは書き換えず、この差を記録する。
- **AC4.4.2（業務メニューの既定のアイコン）**: 3種類の見分けは、上流の取り込み後に満たす（Q8 A）。取り込むまでは今の既定のまま。承認済みのストーリーは Must としているが、上流の対応に左右される（Should に近い）。Delivery Planning で、取り込みの時期と、待ちが長引いたときの自前の SVG への切り替えを依頼者に諮る（`team.md`）。
- **FR10.1・FR11.2**: 上の2つのとおり、取り込みの時期に左右される。
- 要件に新しい要件は足していない。
