# Bolt の計画 — timezone-ui-polish

Bolt は、1つ以上の作る単位（Unit of Work）を、設計から統合まで通して動くものにする1回の作り込みのこと。この文書は、Construction で作る Bolt の順と、それぞれの終わりの条件（Definition of Done）と、確かめたいこと（confidence hypothesis: その Bolt を出すと何が分かるか）を書く。

出典: 要件 `aidlc/spaces/default/intents/261102-timezone-ui-polish/inception/requirements-analysis/requirements.md`（FR1〜FR11・NFR1〜NFR6）、単位 `aidlc/spaces/default/intents/261102-timezone-ui-polish/inception/units-generation/unit-of-work.md`・`unit-of-work-dependency.md`・`unit-of-work-story-map.md`、契約 `aidlc/spaces/default/intents/261102-timezone-ui-polish/inception/contract-design/contract-summary.md`、この段の答え `delivery-planning-questions.md`（Q1〜Q4: すべて A）、チームの進め方 `aidlc/spaces/default/memory/team.md`。

## 前提

- 作業は依頼者1名と AI で、Bolt は1つずつ順に作る。Bolt ごとに `develop` から短命のブランチ（`feature/261102-timezone-ui-polish-b<n>` など）を作り、squash で `develop` に戻す。サブモジュールの固定先の更新を含む Bolt（B6）は、固定先の更新の専用のコミットを残すため、その部分を fast-forward で統合してよい。統合の前に `./gradlew verify` を通す。
- 最初の Bolt だけを単独で承認する手順（walking skeleton: 最初に全体を一通り動かす薄い作り込み）は行わない（`team.md` の Walking Skeleton。アプリの骨格は既にある）。
- Construction は単位ごと（unit-major、Q4: A）。1つの単位を設計の段からコード生成まで通し、確かめてから次の単位へ進む。大きい単位（U4・U5）は、設計の段では1つの単位として通し、コード生成の計画で Bolt の中の手順に分ける（`project.md` の学び）。
- E2E は、`frontend/index.html`・`frontend/public/`・`frontend/src` の本体、または認証・権限・業務データ・`navigation` の本体に触れる Bolt で、統合の前に流して通す（`team.md`）。この Intent は、ほぼすべての Bolt がこれに当たる。足す E2E は、N6 の日時の代表の流れ1本まで（B4）。既存の E2E の書き換え・移しは本数に数えない。
- Bolt の並びは、単位の依存（U2→U1、U4→U1・U2・U3、U5→U6）を守る（トポロジー順。下の確かめ参照）。

## B1 U3 対象DB の日時

- **単位**: U3 `u3-target-db-time`
- **中身**: PostgreSQL の対象DB の接続（読み取り・書き込み）のセッションのタイムゾーンを UTC に明示する（K-95）。既定の DSL の生成で MySQL・MariaDB の日時の秒の端数の桁を読んで反映する（K-98）。`timestamp(n) with time zone` を時点を表す型として扱う（K-98）。`timetz` の応答を UTC への正規化から DB の時差のままに直す（契約 C4）。秒の端数が末尾のゼロを落とさない（DB の定義の桁に固定）。確かめた結果が不具合でなければ、直さずに結果を記録する（FR6.3）。
- **Definition of Done**: US5.1・AC2.2.4・AC2.1.6・US2.5 のサーバー側の受け入れ基準が、3種類の対象DB（MySQL・MariaDB・PostgreSQL）の結合テストで通る。K-95・K-98 の確かめの結果（不具合か・直したか）が記録に残る。時差を持たない型の読み書きが、接続の設定の変更の前後で変わらない。カバレッジの下限（全体と新しいパッケージごと）を満たす。`./gradlew verify` と E2E が通る。
- **確かめたいこと**: PostgreSQL の接続の時差を UTC に明示しても、時差を持たない型の値が変わらないか。MySQL・MariaDB の `datetime(6)` で、端数の上限が 0 になる不具合が実際にあるか。`timetz` の直しで、前の版の画面が壊れないか。
- **見せるもの**: 3種類の結合テストの結果と、確かめの結果の記録（架空の値）。

## B2 U1 変換の部品

- **単位**: U1 `u1-time-zone-conversion`
- **中身**: `frontend/src/shared/format/` の純粋な関数（契約 C1）。時点を表示のタイムゾーンの時刻と時差に直す、ローカル時刻を時点に直す（夏時間の存在しない・重なる・ひとつに決まる・読めない）、名前を今のブラウザが解釈できるか、元の時点の往復の関数。
- **Definition of Done**: `fast-check` の性質ベースのテスト（変換して戻すと元の時点に戻る、時差を持たない型は時差を変えても値が変わらない）と、夏時間の切り替わりの前後・分の端数の時差（`+05:45`・`+09:30`・`-03:30`）・うるう日・秒の端数 0・3・6 桁の単体テストが通る。テストはタイムゾーンを明示に指定する。`./gradlew verify` と E2E が通る。
- **確かめたいこと**: ブラウザの `Intl` だけで、夏時間の存在しない時刻・重なる時刻を安定して判定できるか（ブラウザの IANA の版による違い）。
- **見せるもの**: 性質ベースのテストの結果。

- **単位**: U2 `u2-display-time-zone`
- **中身**: 利用者の設定に表示のタイムゾーンの列を足す移行（前進のみ）、`PUT/GET /api/me/preferences` の `displayTimeZone`（項目が無いときは変えない・`null` は消す。契約 C3）、名前の照合（サーバーが知っている IANA の名前だけ）、プリファレンスの `Select`、表示のタイムゾーンの決定と配布（読み込み中・解釈できない名前）、利用者の一覧・招待の一覧・DSL の状態と履歴の時刻。
- **Definition of Done**: US1.1・US1.2・US5.3（列を足すだけ）の受け入れ基準が、サーバー側のテスト（本人だけ・未認証 401・要求の本文の改ざん・項目が無い／`null`／名前の値／不正な値）と画面の部品のテスト（vitest-axe を含む）で通る。名前の照合は `jqwik` の性質ベースのテストを持つ。プリファレンス・管理の画面の axe（ブランドカラーとテーマのすべての組）で違反 0 件。前の版のアプリが足した列を読まずに動く確かめ（互換）が通る。`./gradlew verify` と E2E が通る。
