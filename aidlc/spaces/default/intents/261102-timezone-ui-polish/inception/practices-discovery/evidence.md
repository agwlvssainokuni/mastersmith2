## 面談で決める論点（チームの進め方に当たるもの）

各論点に推奨の答えとその理由を先に書く（team.md の Corrections のとおり、選ぶ前に推奨を伝える）。論点の番号は `team-practices.md` の候補の印と同じ。

### I1: 業務データの日時の受け渡しの決まり（Code Style）を書き直すか

- 背景: team.md の Code Style に「日時はタイムゾーンを足さずに DB の値のまま渡す」とある。N6 は日時のタイムゾーンの変換が目的で、この行と食い違いうる。今の実装も時差つきの型は UTC にそろえて `+00:00` 付きで返している（K-94）ため、文言はすでに実装と厳密には合っていない。
- 選択肢: A. 行を「変換の形は要件定義で決め、サーバー側の1か所（`ColumnValueCodec`）と画面の1か所（`src/shared/format/`）に閉じ、既定のタイムゾーンを暗に使わず時差を明示に渡す」に書き直す（具体の形は要件定義の後に設計で書き足す） / B. 今の文言のまま残し、要件定義で差を記録する / C. 行を消す / X. Other
- 推奨: A。残すと N6 の要件・設計・コード生成のすべての段で「team.md との差」を記録し続けることになる。消すと「変換を1か所に閉じる」守りも失う。

### I2: 日時のタイムゾーンの変換のテストの必須の一覧を足すか

- 選択肢: A. 足す（3種類の対象DB と型・日付の変わり目・夏時間と端数の時差・秒の端数・範囲の端・往復・性質ベースのテスト。`team-practices.md` の候補の全部） / B. 一部だけ足す（3種類の対象DB と型・日付の変わり目・往復だけ） / C. 足さない（既存の「3種類の対象DB の境界の値」の決まりで足りる） / X. Other
- 推奨: A。日時の変換の誤りは、日付の変わり目・夏時間・端数の時差・秒の端数など境目でだけ出やすく、既存の決まり（最大の整数・桁の多い小数・NULL）はそれを名指ししていない。業務データ・役割・メールなど危ない機能ごとに必須の一覧を置いてきた今の形にもそろう。夏時間の確かめを結合テストまで広げるかは、時差を利用者ごとに選べるか（要件定義）で変わるため★にした。

### I3: テストの時差を固定するか

- 選択肢: A. 画面のテスト（Vitest）と E2E（Playwright の `timezoneId`）の時差を固定し、別の時差の確かめは明示に指定する。バックエンドの変換の部品は時差と時計を注入して確かめる / B. 固定しない（手元の `Asia/Tokyo` と CI の UTC の両方で通ることに頼る） / C. バックエンドだけ（今の `user.timezone`）のままにする / X. Other
- 推奨: A。今は手元が `Asia/Tokyo`、CI の機械が UTC で、画面のテストだけ時差が揃っていない。N6 で日時の表示のテストが増えると、手元で通り CI で落ちる（不安定に見える）失敗が出やすく、team.md の「不安定なテスト」の決まりで手戻りが大きい。B は両方で通る書き方を毎回求めることになり、確かめたい時差が暗になる。

### I4: 実行時のタイムゾーンの設定を変えるときの揃え先を決まりにするか

- 選択肢: A. Dockerfile・compose・テストの JVM・E2E の起動の4か所をそろえ、配備の記録に書く決まりを足す / B. 足さない（必要になったときに設計で決める） / X. Other
- 推奨: A。今も3か所で `Asia/Tokyo` を重ねて書いており（`-Dh2.compactThreads=1` と同じ形）、N6 で JVM の既定の時差を変える・外す判断が出うる。1か所だけ変えると、本番とテストで違う時差で動き、テストが本番の誤りを拾わない。

### I5: 自作の SVG（アイコン・favicon）のライセンスヘッダーと検査

- 背景: project.md の Mandated は「生成するソースファイルの先頭に Apache License 2.0 ヘッダー」。SVG は文字のファイルで `<!-- -->` を置ける。今の検査（`check-license-header.mjs`）は `.svg` を見ていない。
- 選択肢: A. 自作の SVG に `<!-- -->` のヘッダーを置き、検査の対象に `.svg` を足す。`.ico`・`.png` は対象外とし、元の SVG から作る手順を書く。SVG にスクリプト・イベントの属性・外部の参照を入れない / B. 画像はヘッダーの対象外とする（SVG にもヘッダーを置かない） / C. ヘッダーは置くが検査はしない / X. Other
- 推奨: A。HTML（`<!-- -->`）と同じ扱いで、Mandated の「ソースファイル」の読みがそろう。ヘッダーで SVG が数百バイト増えるが、favicon・ロゴの大きさでは問題にならない。検査しないと付け忘れが残る（C）。SVG は描画の中でスクリプトを動かせるため、自作でも入れない決まりにしておく。これを固い制約（NEVER）として `project.md` に残すかも、あわせて尋ねる。

### I6: make-you-chic-ui へのアイコンの依頼の扱い

- 背景: team.md は「make-you-chic-ui に無い部品」を設計の段で一覧にして依頼する決まり。アイコン（`Icon` の登録の名前）が「部品」に入るか、画面イメージの段で一覧にするか、待つ間に別の単位を進めてよいかは書かれていない。依頼文は「画面イメージの段で一覧にして上流へ依頼し、待つ間に N6 を先に進める」と述べている。
- 選択肢: A. 決まりに「アイコンも含む。画面イメージの段で一覧にし、待つ間はアイコンに頼らない単位を先に進めてよい。自前の SVG に代えるかはその時点で諮る」と書き足す / B. 今の決まりで足りる（アイコンも部品と読む。進める順は Delivery Planning で決める） / C. 依頼せず、frontend の側に自前の SVG を置く / X. Other
- 推奨: A。依頼文の進め方を後の Intent でも同じに読めるようにするため。B でも今回は進められるが、「部品」と「アイコン」で依頼の段が違って読める。C は make-you-chic-ui をデザインシステムとして使う project.md の Tech Stack と食い違う。

### I7: 管理の仮の画面を廃止したときの E2E の扱い

- 背景: 廃止するかどうかは要件定義で決める（機能の中身）。廃止すると E2E 030・090・130 と単体テストの多くを書き換える（K-104）。
- 選択肢: A. 書き換え・削除は本数に数えない。ただし、その画面で確かめていた検査（403 の表示・axe・管理の確認の API）は別の画面か別のテストへ移して残し、前後の件数を記録する / B. 本数に数えず、移すことも求めない / C. 書き換えも本数に数える / X. Other
- 推奨: A。既存の決まり（既存の E2E の書き換えは本数に数えない）にそろえつつ、画面を消すことで 403 の表示や axe の確かめが黙って減るのを防ぐ。

### I8: この Intent で足す E2E の本数

- 背景: この Intent は N6 と画面の仕上げを束ねている。team.md は「束ねた元の Intent ごとに数える」。
- 選択肢: A. N6 の日時の代表の流れ1本＋画面の仕上げの1本（最大2本） / B. 全体で1本 / C. N6 の1本だけとし、画面の仕上げ（アイコン・favicon・ホーム）は既存の E2E の書き換えと axe で確かめる。管理の仮の画面に新しい操作の流れを足すと決めたら、要件定義で1本を足すかを決める / X. Other
- 推奨: C。画面の仕上げは表示の変更が中心で、新しい操作の流れが無い。axe と表示の確かめは本数に数えない読み（project.md の学び）で足りる。管理の画面に中身（操作）を作ると決まった場合だけ、流れの1本が要る。

### I9: 統合の前に E2E を流すかを決める「frontend の本体」の範囲

- 背景: team.md は「`frontend/src`（テストのファイルを除く）」を本体とする。favicon の `<link>` は `frontend/index.html`、アイコンの置き場は `frontend/public/` になりうる（K-102）。
- 選択肢: A. `frontend/index.html` と `frontend/public/` も本体に含める / B. 含めない（今のまま） / X. Other
- 推奨: A。`index.html` の誤りは画面全体が出ない失敗になり、`./gradlew verify` の画面のテスト（jsdom）では拾えない。実際のブラウザで読む E2E で確かめるのがよい。

## 残る不確かさ（要件定義・設計で確かめる）

- K-95: PostgreSQL の接続のセッションの時差が JVM の既定に従う見込みは未検証。Q4 の「4か所をそろえる」決まりと、Q1 の「時差を明示に渡す」決まりはこの見立てに頼る。要件定義で接続のセッションの時差を固定するかを決め、NFR 設計か最初の Bolt で実際の3種類の対象DB で確かめる。
- 画面のテストの時差が固定されていない今、手元（`Asia/Tokyo`）と CI（UTC）で結果が変わるという見立ても未検証。Q3 の固定を入れる Bolt で、固定の前後の結果を記録する。
- E2E の起動のアプリの JVM のタイムゾーンの指定（Q4 の4か所目）は今のところ確かめていない。設計の段で `frontend/playwright.config.ts` の `webServer` の起動の引数を確かめる。
- Q1 の書き直しは置き場の決まりだけで、具体の変換の形（どの型をどの時差で見せ・入れるか、時差の無い型をどの時差の値とみなすか）は要件定義で決める。決まった形を team.md に書き足すのは、次の Practices Discovery か学びの道で行う。
- Q2 の★（表示に使う時差を利用者ごとに選べるか）は要件定義で決める。選べないなら、夏時間の地域の確かめは変換の部品の単体テストに限る。
- Q8 の本数は、管理の仮の画面を廃止するか中身を作るか（K-104、要件定義）で変わりうる。
- Q5 の SVG の Forbidden は「自作の」SVG に当てる。make-you-chic-ui から取り込むアイコンは上流のリポジトリの側の扱いで、このリポジトリからは変えない（`project.md` の Forbidden）。

## 要件定義・設計に回す論点（ここでは尋ねない）

機能の中身に当たるため、Practices Discovery では決めない。

- 業務データの日時をどの時差で見せ・入れるか（UTC のまま・端末の時差・利用者ごとの設定・アプリ全体の設定）、時差の無い型（`datetime`・`timestamp`）をどの時差の値とみなすか（K-95・K-96・K-97）。
- PostgreSQL の接続のセッションの時差を固定するか（K-95、未検証の確かめを含む）。
- 秒の端数の上限を既定の DSL の生成で読むか（K-98）、範囲の端の値の扱い（K-99）。
- ホームに何を置くか（K-103）、管理の仮の画面に中身を作るか廃止するか（K-104）。
- アプリのアイコンの図柄と置き場、favicon の形式（`.ico`・`.svg`・`.png`）と `/favicon.ico` の応答（K-102）。
- 管理メニューの項目ごとのアイコン、業務メニューのテーブルとビューのアイコン、メニューの応答にテーブルかビューかの印を足すか（K-100・K-101）。make-you-chic-ui へ依頼するアイコンの一覧は画面イメージの段で作る。
- N6 と画面の仕上げの単位の分け方と進める順（待つ間に N6 を先に進める）: Units Generation・Delivery Planning。
