既存のアプリへの変更のため、部品の大半は今ある部品への足し・直しです。質問は、承認済みのストーリーと設計の境目で、部品の持ち主が変わる点だけにしました。

## 決まっていること（質問にしない）

- **設定の置き場**: 表示のタイムゾーンは、言語と同じ利用者の設定として、内部DB の利用者の設定に列を1つ足して保存する（要件 FR1.2・NFR4.1）。前の版は足した列を読まずに動く。
- **変換の置き場**: 表示のタイムゾーンへの変換は、画面の側の1か所（`src/shared/format/`）に閉じ、サーバー側は `ColumnValueCodec` の1か所に閉じる（`team.md`）。サーバーの内部DB・監査・ログの時刻は今どおり UTC（前提 A6）。
- **ホーム**: 今のメニューの API と作業ロールの API のほかに、新しい API を呼ばない（FR7.5・NFR2.2）。
- **メニューの応答**: 項目に、テーブルかビューかの印を足すだけにする（FR11.3・NFR4.2）。
- **アイコンの配布**: 自作の SVG と favicon は `frontend/public/` に置き、`/favicon.ico` は静的なファイルとして画像を返す（FR9.5）。
- **管理の仮の画面**: 画面とサイドバーの項目だけを外す。サーバー側の管理の権限の確認 API と 403 の判定は残す（FR8.3）。

## Q1. [開発] 時点を表す型の入力を、サーバーへどの形で送るか（ストーリーのレビューの指摘 R-01 の解決）

要件 FR3.1 は「画面は時差つきで送り、サーバーは時点として保存する」、FR3.4 は「夏時間で存在しない時刻は画面とサーバーの両方で拒否する」としています。ところが、時差つきの値（例: `2026-03-08T07:30:00Z`）は、その時点が必ず存在するため、サーバーには「存在しない時刻」の情報が届きません。2つの要件は、このままではサーバー側の拒否が成り立ちません。

**推奨: A。** 理由: 要件 FR3.1・`team.md`（変換を画面の側とサーバーの側の1か所ずつに閉じ、JVM・ブラウザの既定を暗に使わない）に沿い、サーバーに新しい入力の形（ローカル時刻とタイムゾーン名）を作らずに済みます。API を直接呼んでも、時点として存在する値だけが保存されるため、壊れた値は保存されません。存在しない時刻の拒否は、利用者が打ち間違える画面の側だけで足ります。

A. 時点だけを送る。画面が表示のタイムゾーンで時点（時差つき）に直して送り、サーバーは時差つきの値を時点として受ける。夏時間で存在しない時刻の拒否は画面の側だけとし、ストーリー AC2.3.3・AC2.4.4 のサーバー側の拒否は「時差のない値・読めない値は拒否」に直す（要件 FR3.4 との差として記録する）
B. ローカル時刻とタイムゾーン名を送る。サーバーが `ZoneId` で時点に直し、存在しない時刻と重なる時刻も判定して拒否する。時点を表す型の入力・検索の API の入力が変わり、主キー・参照の値の往復も別の形で持つ必要がある（要件 FR3.4 のとおりになる）
