# 設計の決定の記録（ADR）— Intent 261102-timezone-ui-polish

出典: `components.md`（部品の一覧）、要件・ストーリー、質問 Q1（A）、コード知識ベースの所見 K-94〜K-105。実現可能性の評価（Feasibility）の段が無いため、実現できるかの判断は ADR-009 にまとめた（`project.md` の学び）。

## ADR-001: 表示のタイムゾーンは、言語と同じ利用者の設定の行に列を1つ足して保存する

- **Status**: Accepted
- **Context**: 要件 FR1.2 は、サーバー側の利用者の設定として保存し、「ブラウザに合わせる」は値が無い状態とする。NFR4.1 は、内部DB の変更を利用者の表への列1つの追加に限り、前の版が足した列を読まずに動くこと、前進のみとすることを求める。今の自分の設定（言語）は利用者の設定の行にある。
- **Decision**: 利用者の設定の行（内部DB の利用者の表）に、表示のタイムゾーンの列（NULL 可、既定は NULL）を1つ足す。新しい表は作らない。移行は前進のみで、足した列を消す移行は後の Intent も含めて今回は無い。保存の要求の名前は TimeZoneNamePolicy で照らす。本人だけが自分の分を読み書きし、要求の本文で他人の設定を変えられない。
- **Consequences**:
  - 良い点: 言語と同じ置き場・同じ API の項目の追加で済み、別の端末でも同じ設定で見える。前の版へ戻しても足した列は読まれないだけで動く。
  - 悪い点: 前の版へ戻すと、表示のタイムゾーンの選択は使えなくなる（列は残る）。設定の項目が増えるたびに利用者の表の列が増える。
- **Alternatives Rejected**:
  - 新しい表（利用者の ID と設定の組）: 設定の追加の自由度は増えるが、表・移行・前の版との互換の確かめが増える。今は1項目だけのため見送った。
  - ブラウザの中だけ（端末ごとの設定）: 別の端末で同じ設定にならない。要件 FR1.2 の前提（サーバー側の設定）に反する。

## ADR-002: 時点を表す型の入力は、画面が時点（時差つき）に直して送り、サーバーに新しい入力の形を足さない

- **Status**: Accepted（質問 Q1: A）
- **Context**: 要件 FR3.1 は「画面は時差つきで送り、サーバーは時点として保存する」、FR3.4 は「夏時間で存在しない時刻は画面とサーバーの両方で拒否する」としている。ストーリーのレビュー（R-01）は、この2つが両立しないことを指摘した。時差つきの値（例: `2026-03-08T07:30:00Z`）は、その時点が必ず存在するため、サーバーには「存在しない時刻」の情報が届かない。今のサーバーは、時差つきの値を `Z`・`±hh:mm` で受けて UTC の時点に直し、オフセットが無い値は UTC とみなす（K-94）。
- **Decision**: 時点を表す型の入力と検索は、画面が表示のタイムゾーンで時点（時差つき）に直して送り、サーバーは時差つきの値を時点として受ける。サーバーにローカル時刻とタイムゾーン名を受ける新しい入力の形は足さない。夏時間で存在しない時刻の拒否は、画面の側だけが行う。重なる時刻は、画面が先・後の2択で選ばせ、選んだ側の時差で時点に直して送る。サーバーの拒否は、時差の無い値・読み込めない値に限る（今のサーバーはオフセットの無い値を UTC とみなすため、時点を表す型については、オフセットの無い値の扱いを機能設計で決める）。
- **Consequences**:
  - 良い点: サーバーの入力の形が変わらず、主キー・同時更新の判定・参照の値の往復も今の時点の形のまま保てる。API を直接呼んでも、時点として存在する値だけが保存される。
  - 悪い点: 要件 FR3.4・ストーリー AC2.3.3・AC2.4.4 の「サーバー側の拒否」が成り立たない。画面を通さずに API を直接呼ぶ人が、夏時間で存在しない時刻を入れたつもりの値は、別の時点として保存されても気づけない（ただし、その値は時点として存在する値で、壊れた値ではない）。
  - 要件・ストーリーとの差: FR3.4 のサーバー側の拒否は「時差の無い値・読み込めない値の拒否」に読み替える。AC2.3.3・AC2.4.4 のサーバー側の合否も同じに直す。承認済みの要件・ストーリーは書き換えず、この差を次の段の成果物で扱う（`project.md` の決まり）。
- **Alternatives Rejected**:
  - ローカル時刻とタイムゾーン名を送る形（質問 Q1 の B）: サーバーが `ZoneId` で時点に直し、存在しない時刻・重なる時刻も判定して拒否できる（要件 FR3.4 のとおり）。しかし、時点を表す型の入力・検索の API の入力が変わり、主キー・参照の値の往復を別の形で持つ必要がある。ブラウザに合わせる利用者のタイムゾーン名を毎回送ることにもなる。変更の量に見合う利点が小さいと判断した。
  - サーバーが利用者の保存済みのタイムゾーンで時点に直す形: 「ブラウザに合わせる」の利用者はタイムゾーンをサーバーが知らず、成り立たない。

## ADR-003: 変換は画面の側の1か所に置き、サーバー側の変換の部品は足さない

- **Status**: Accepted
- **Context**: `team.md` は、変換をサーバー側（`ColumnValueCodec`）と画面の側（`src/shared/format/`）の各1か所に閉じ、JVM・ブラウザの既定のタイムゾーンを暗に使わないと決めている。今、業務データは UTC の文字のまま見せ、DSL・招待・利用者の管理の画面は端末のタイムゾーンで直している（K-96）。
- **Decision**: 表示のタイムゾーンへの変換と、ローカル時刻からの時点への変換（夏時間の存在しない・重なるの判定を含む）は、画面の側の1か所（TimeZoneConversion、`src/shared/format/`）に閉じ、すべての画面がその部品だけを使う。サーバーは、今の UTC の時点の形を保ち、新しい変換を足さない。タイムゾーンは明示に渡し、ブラウザの既定を暗に使わない。時差を持たない型と `timetz` は変換しない。
- **Consequences**:
  - 良い点: 業務データと管理の画面の時刻の見せ方が1つにそろい（K-96 の二系統の解消）、テストを1か所の純粋な関数の性質ベースのテストにできる。
  - 悪い点: 利用者のタイムゾーンの規則（夏時間など）はブラウザの実装に頼る。ブラウザごとの IANA の版の違いが画面の動きに出うる（ADR-009）。
- **Alternatives Rejected**:
  - サーバーで表示のタイムゾーンへ直して文字で返す: 応答の形が変わり、主キー・参照の値の往復と性能（NFR2.1）に影響する。画面ごとのタイムゾーン（未保存のブラウザに合わせる）をサーバーが知らない。
  - 画面ごとに変換を書く: 二系統が増えるだけで、K-96 を解消しない。

## ADR-004: 対象DB の接続のセッションのタイムゾーンは、3種類とも UTC に明示する

- **Status**: Accepted
- **Context**: MySQL・MariaDB は、読み取りと書き込みのプールが接続を作るときに `SET time_zone = '+00:00'` を行う。PostgreSQL は何も設定せず、JVM の既定（`Asia/Tokyo`）に従う見込み（K-95、未検証）。時差を持たない型（`timestamp` など）の値は、読み書きの接続のセッションのタイムゾーンに左右されうる。
- **Decision**: PostgreSQL の読み取りと書き込みの両方の接続にも、セッションのタイムゾーンを UTC に明示に設定する。JVM の既定のタイムゾーンに頼らない。この直しの前後で、時差を持たない型の読み書きの値は変わらないことを、3種類の対象DB の結合テストで確かめる。
- **Consequences**:
  - 良い点: 3種類の対象DB が同じ前提（UTC の壁時計）になり、JVM の `user.timezone` の変更に影響されない。
  - 悪い点: 直す前に PostgreSQL の `timestamp` に `CURRENT_TIMESTAMP` などの既定値が入った行があれば、解釈が変わる恐れがある（見本の対象DB・テストの確かめで確かめる）。
- **Alternatives Rejected**:
  - JVM の既定のタイムゾーンに頼る: `Dockerfile`・compose・テストの JVM の4か所の設定（`team.md`）に結果が預けられる。
  - 読み取りだけに設定する: 書き込みの値がずれうる。

## ADR-005: メニューの応答には、テーブルかビューかの印を足すだけにする

- **Status**: Accepted
- **Context**: アイコンを項目の種類（テーブル・ビュー・フォルダ）で変えるには、画面が種類を知る必要があるが、メニューの応答 `GET /api/me/navigation` には印が無い（K-101）。`MenuFilter` は `DslModel.findTable` で `DslTable.view` を引ける位置にある。前の版の画面は今の応答を読む（NFR4.2）。
- **Decision**: 応答の項目に、テーブルかビューかの印（種類）を足す。既存の項目の形は変えず、足すだけにする。印は、利用者が見られる項目にだけ付き、見られない項目の存在を明かさない。フォルダ（子を持つ項目）は子の有無で決まるため、印を足さない。
- **Consequences**:
  - 良い点: 前の版の画面が読んでも壊れない。サーバー側の判定（`MenuFilter`）に近い位置で決まり、画面が権限を足さない。
  - 悪い点: 応答の項目が1つ増える。
- **Alternatives Rejected**:
  - 画面が定義の API から種類を引く: 業務のメニューのたびに追加の呼び出しが要り、ホームが新しい API を呼ばない（FR7.5）に反する。
  - DSL の `icon` に種類を書かせる: 利用者が毎回書く必要が出る（要件の範囲の外。Q10 C）。

## ADR-006: アイコンは今の登録の名前だけを使い、足りないものは上流へ依頼して取り込むまで付けない

- **Status**: Accepted（質問 Refined Mockups Q7: A・Q8: A）
- **Context**: make-you-chic-ui の `Icon` の登録は 18 個で、管理の区画の 6 項目のうち意味が近いのは 3 項目（利用者・ロールの受け渡し・DSL）だけ。業務メニューの既定（テーブル・ビュー・フォルダ）に合う図柄は無い（K-100）。許す名前の一覧は、画面の `allowedIcons.ts` とサーバーの `allowed-icons.txt` の2か所にある。`vendor/make-you-chic-ui` は直接変えない（`project.md` Forbidden）。
- **Decision**: アイコンは、今の登録の名前だけを使う。意味が近い3項目にだけ付け、近いものが無い項目は上流に新しいアイコン（`mail`・`users`・`shield`・`table`・`view`・`folder`）を依頼し（`make-you-chic-ui-request-8.md`）、取り込むまで付けない・今の既定のままにする。取り込みは、使う Bolt の前に固定先の更新の専用のコミットで行う。許す名前の一覧は、固定先のアイコンとそろえ、画面とサーバーの2か所を同じ名前にする。
- **Consequences**:
  - 良い点: 誤読を招く仮のアイコンを使わず、上流を変えずに済む。
  - 悪い点: 取り込みが遅れると、承認済みのストーリーの AC4.3.1・AC4.4.2（Must）を満たせない時期が出る。Delivery Planning で、取り込みの時期と、待ちが長引いたときの自前の SVG への切り替え（`team.md`）を依頼者に諮る。
- **Alternatives Rejected**:
  - 今の 18 個から意味の遠いものを仮に割り当てる: 誤読を招く。
  - frontend の側で自前の SVG を最初から作る: 上流の対応を待たずに済むが、上流との二重管理になる（`team.md`: 待ちが長引いたときに諮る）。

## ADR-007: 管理の仮の画面は、画面とサイドバーの項目だけを外し、サーバー側の確認 API は残す

- **Status**: Accepted
- **Context**: 管理の仮の画面（`/admin`）は、確認の API を呼んで案内を出すだけで、役割が無い（K-104）。一方、`GET /api/admin/check` と 403 の判定は、k6 と E2E 130 が使い、E2E 030・090・130 と単体テストの多くが画面に頼る。
- **Decision**: 画面（`frontend/src/features/admin`）とサイドバーの「管理」の項目を外す。廃止した画面の道は、ほかの存在しない道と同じ「見つからない」画面にする（特別な移し先は作らない。前提 A3）。サーバー側の管理の権限の確認 API と 403 の判定は残す。仮の画面で確かめていた検査（403 の表示・アクセシビリティ・確認の API）は、別の画面か別のテストへ移して残し、移す前と後の件数を Build and Test で記録する。
- **Consequences**:
  - 良い点: 役割の無い項目が消え、管理の区画は実際の項目だけになる。サーバー側の判定は変わらず、負荷の試験と E2E が使い続けられる。
  - 悪い点: 仮の画面に頼る既存のテストの書き換え・移しが要る（本数に数えない。`team.md`）。
- **Alternatives Rejected**:
  - 仮の画面を管理の入口のページにする: 要件の範囲の外（Q7 B）。ホームが入口を持つ。
  - API も外す: k6 と E2E の確かめが失われる。

## ADR-008: アプリのアイコンと favicon は `frontend/public/` に置き、静的なファイルとして返す

- **Status**: Accepted
- **Context**: `frontend/index.html` に favicon の `<link>` が無く、`frontend/public/` も無い。見つからない画面の URL は `index.html` を返すため、`/favicon.ico` に HTML が返る見込み（K-102、未検証）。自作の SVG は、スクリプト・イベントの属性・外部の参照を入れず、先頭にライセンスヘッダーを置く（`team.md`・`project.md`）。
- **Decision**: 自作の SVG・`.ico`・`.png` を `frontend/public/` に置き、ビルドの結果（`dist`）のルートから静的なファイルとして返す。`index.html` に favicon の `<link>` を足す。`/favicon.ico` は画像を返す。SVG の安全とライセンスヘッダーは、ライセンスヘッダーの検査の対象に `.svg` を足して確かめる。`.ico`・`.png` は元の SVG から作る手順を README か記録に書く。
- **Consequences**:
  - 良い点: 配信の仕組みは今のまま（WAR に同梱した `dist` の静的なファイル）で、サーバーの変更が要らない。
  - 悪い点: 統合の前の E2E の要否は、`frontend/index.html`・`frontend/public/` を含む「frontend の本体」の決まりで決まる（`team.md`）。バイナリはヘッダーを置けず検査の対象の外になる。
- **Alternatives Rejected**:
  - サーバーに `/favicon.ico` の道を作る: 静的なファイルで足り、サーバーの変更が増える。
  - データ URI で `index.html` に埋める: `.ico` を読むブラウザの既定の要求には効かない。

## ADR-009: 実現できるかの判断（Feasibility の段が無いため）

- **Status**: Accepted（確かめる段を持ち主とともに記録）
- **Context**: Feasibility の段が無い。この Intent には、実際に動かして確かめるまで分からない前提がある。
- **Decision**: 次の前提を置き、確かめる段と、確かめられなかったときの切り替え先を決める。

| 前提 | 確かめる段 | 確かめられなかったときの切り替え |
|---|---|---|
| PostgreSQL の接続のタイムゾーンを UTC に明示しても、時差を持たない型の値が変わらない（K-95） | NFR Design の捨ての試し／Code Generation の結合テスト | 変わるなら、既存の値を壊さない移行の段取りを計画に足す |
| MySQL・MariaDB の `datetime(6)` で既定の DSL の端数の上限が 0 になる・`timestamp(n) with time zone` が時点を表す型として読まれない（K-98） | NFR Design の捨ての試し | 不具合でなければ直さず、確かめた結果を Build and Test に記録（FR6.3） |
| ブラウザの `Intl.supportedValuesOf('timeZone')` と `Intl.DateTimeFormat` が、対象のブラウザで使える | NFR Requirements（対象のブラウザの確かめ）／ Code Generation | 使えないブラウザには「ブラウザに合わせる」だけを出し、名前の選択を隠す |
| `Select` に地域ごとのまとまりの口が無い（レビューの指摘）。400 件超の一覧の探しやすさ | Functional Design | 並び順（よく使う地域を先頭）か、`Select` の `placeholder` と文字入力で探せる並べ方に決める |
| `Card` をリンクにする口が無い | Functional Design | リンクの中に `Card` の見た目を置く |
| 上流の取り込みの時期（アイコン6つ・ロゴの口） | Delivery Planning | 待ちが長引いたら、自前の SVG に替えるかを依頼者に諮る（`team.md`） |

- **Consequences**:
  - 良い点: 動かして確かめる前の判断が、持ち主の段とともに残り、後の段で漏れない。
  - 悪い点: 確かめた結果によっては、後の段の計画が変わる。
- **Alternatives Rejected**:
  - Feasibility の段を足す: 確かめる対象が少なく、各段（NFR Design・Code Generation）の捨ての試しで足りる。
