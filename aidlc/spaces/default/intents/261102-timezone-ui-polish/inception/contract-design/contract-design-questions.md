# Contract Design の質問（Intent 261102-timezone-ui-polish）

## 決まっていること（質問にしない）

- **契約の数と種類**: 単位の間の辺5本（U2→U1、U4→U1・U2・U3、U5→U6）と、外に出る口（`PUT/GET /api/me/preferences`、`GET /api/me/navigation`、`/api/tables`、静的なファイル、上流 make-you-chic-ui）を、契約にする。
- **仕組み**: 単位の間の画面の側の契約は、TypeScript の関数・フックの型（同じアプリの中の呼び出し）。サーバーの口は同期の REST（JSON、Problem Details）。非同期・イベントは無い。
- **所有**: 口の持ち主は、口を作る単位（`PUT/GET /api/me/preferences` は U2、`GET /api/me/navigation` は U5、`/api/tables` は U3）。変更は足すだけで、消す・意味を変えるときは契約を直して依頼者に諮る。
- **版の決まり**: API に版は付けない（今と同じ）。応答に足す項目は、受け取る側が知らない項目を無視する前提で足す（前の版の画面が読んでも壊れない。NFR4.2）。
- **誤りの形**: RFC 9457 Problem Details に安定した `code`（今の `VALIDATION_FAILED`、401 `AUTHENTICATION_REQUIRED` など）と、入力の誤りの項目ごとの情報（今の形のまま）を足す。タイムゾーンの名前の誤りは `VALIDATION_FAILED` にそろえ、新しい `code` は足さない。
- **IANA の名前の範囲**: サーバーが受けるのは、`ZoneId` が IANA の地域の名前（`Asia/Tokyo`・`UTC` など）として知っているものだけ。固定のオフセット表記（`+09:00`・`Z`）は受けない。ブラウザの `Intl.supportedValuesOf('timeZone')` が出す名前で、サーバーが知らないものは拒否になる（ストーリー Q5 A）。

## Q1. [開発] プリファレンスの保存で、表示のタイムゾーンの項目が本文に無いとき

今の `PUT /api/me/preferences` は、氏名・言語・テーマ・文字の大きさの4つを「まとめて置き換える」口です。ここに5つ目（表示のタイムゾーン）を足します。画面は配備のたびに更新されますが、利用者のブラウザが古い画面を持っている間は、5つ目を送らない保存の要求が来えます。

**推奨: A。** 理由: 古い画面が来ても、利用者が選んだタイムゾーンを黙って消さずに済みます。値を消す操作（「ブラウザに合わせる」への切り替え）は、明示の値（`null`）で伝えられます。

A. 項目が無いとき（本文に `displayTimeZone` の名前が無い）は、保存済みの値を変えない。`null` は「ブラウザに合わせる」（値を消す）。空の文字列は入力の誤り
B. 項目が無いときは、`null`（ブラウザに合わせる）として置き換える。ほかの4つと同じ「まとめて置き換える」の扱い

## Q2. [開発] 業務データの時点を表す型で、時差の無い値が送られてきたとき（ドメイン設計のレビューの指摘 R-01）

ADR-002 のとおり、新しい画面は必ず時差つきの時点を送ります。今のサーバーは、時差の無い値（例: `2026-03-08T02:30:00`）を UTC とみなして受けます。API を直接呼ぶ k6・E2E・結合テストが、時差の無い値を送っている可能性があります。

**推奨: A。** 理由: 前の版との互換（NFR4.2）を保て、既存の呼び出し元に影響しません。画面は必ず時差つきで送るため、利用者が意図せず UTC とみなされる経路はありません。API を直接呼ぶ人に向けては、契約に「時差の無い値は UTC」と書いて示せます。

A. 今のまま、UTC とみなして受ける。契約に明記する。ストーリー AC2.3.3・AC2.4.4 のサーバー側の拒否は「読めない値（日時として読めない値）」に限る
B. 時点を表す型については、時差の無い値を入力の誤りとして拒否する（`VALIDATION_FAILED`）。既存の呼び出し元（k6・E2E・結合テスト）を洗い出して直す。時差を持たない型は今のまま

[Answer]: A
