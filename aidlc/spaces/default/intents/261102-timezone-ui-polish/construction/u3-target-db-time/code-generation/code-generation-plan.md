# コード生成の計画 — u3-target-db-time

## Summary

- Builds: 対象DB の日時・時刻の読み書きの直し（PostgreSQL の接続を UTC に固定、秒の端数を結果の列情報の桁に固定、読めないセルだけ DB の文字で返す、`timetz` を時差ごと保存、桁つきの時差つきの型の分類、既定の DSL の生成が日時の桁を書く）。新しい依存・API・表・列・code は足さない
- Touches: `backend/src/main/java/cherry/mastersmith/` の `targetdb/config`・`businessdata/repository`（新しい小さな部品 `TemporalCells` と `CellValue.Raw` を含む）・`businessdata/domain`（桁の確かめ）・`targetdb/repository`（スキーマの問い合わせの桁）・`dslmanage/generate`、と既存のテストの期待の直し
- Tests: 単体テスト約 70 件（部品ごと 5〜8 件。性質ベース 4 件、変換の費用の測り 2 件を含む）と、結合テスト約 40 件（3種類の対象DB の実物。日時の型・読めない値・桁・往復・初期化・初期化の失敗・漏えい・接続の数）。E2E の流れは足さない

出典: 機能設計（`construction/u3-target-db-time/functional-design/functional-spec.md`・`rules.md` の BR3.1〜BR3.19・`entities.md`）、NFR Requirements（`nfr-requirements/security-requirements.md`・`tech-stack-decisions.md`）、NFR Design（`nfr-design/security-design.md` の SD1〜SD7・`logical-components.md` の LC1〜LC9・差の表 D1〜D5・捨ての試しの結果）、Infrastructure Design（`infrastructure-design/cicd-pipeline.md`）、各段のレビュー（`reviews/review-01.md`）、前の単位の計画の書き方（`construction/u1-time-zone-conversion/code-generation/code-generation-plan.md`）。既存のコードは読み取りだけで確かめた（`RowSqlExecutor`・`ColumnValueCodec`・`CellValue`・`RowDialect` と2つの方言・`TargetDataSourceConfig`・`TargetWriteDataSourceConfig`・`SchemaRows`・両 `SchemaQueries`・`DslTreeBuilder`・`WriteRequestValidator`）。

## 方針

- 方法は test-after（`team.md` Testing Posture）。層（接続 → 桁と型の名前 → 読み取り → 書き込み・検索 → 生成 → 結合）ごとに実装を書き、同じ Bolt の中でその層のテストを書いて実行し、通ってから次の層へ進む。その層の変更で落ちる既存のテストは、その層のテストの手順の中で直す（下の「影響の範囲」）。
- 置き場は論理の部品 LC1〜LC6（`nfr-design/logical-components.md`）のとおり、`targetdb.config` と `businessdata.repository` に閉じる。service の層は DB の種類で分岐しない。種類ごとの差（初期化の文・桁の取り出し・番兵の確かめ・比較の束縛）は `TargetDataSourceConfig` の1か所の対応と、`RowDialect` の2つの方言のクラスに置く。
- 新しいクラスは `TemporalCells`（`businessdata.repository`、package-private）の1つだけ。日時・時刻のセルの整形（桁ごとの書式の定数 LC5）・桁を固定した整形・読めない文字の見分けの純粋な部分を持ち、JDBC の文を作らず・実行しない（変換の費用の測り NFR2.1.3・NFR2.1.4 を、モックの `ResultSet` に頼らず測るため）。`RowSqlExecutor` 以外が文を作る場所は増やさず、`BusinessDataBoundaryArchitectureTest` の許可の一覧と SpotBugs の `SQL_` の除外は変えない。
- 新しい依存を足さない。`backend/build.gradle.kts`・`backend/gradle.lockfile`・Dockerfile・compose・`db/migration`・実行時のタイムゾーンの設定の4か所は変えない（BR3.19・SD6.1。手順 21 で差分を確かめる）。
- 測れる目標（500 ミリ秒・平均 0.05 ミリ秒）は緩めない。外れたときは原因を確かめて依頼者に諮る。

### この計画で決めたこと（NFR Design のレビュー R-01〜R-03 の確定。承認の場で変えてよい）

- **D-P1 `CellValue` の持たせ方（NFR Design レビュー R-01）**: `CellValue` に `record Raw(String text) implements CellValue` を足す（`toString` は `Raw[value=***]` で値を伏せる）。`Text`・`Unreadable` は変えない。`ColumnValueCodec.readCell` は **日時・時刻の型（DATE・DATETIME・DATETIME_TZ・TIME・TIME_TZ）だけ**、型として読めない値を `Raw`（DB が送った文字）で返す。ほかの型（真偽値・数・文字）の読めない値は今までどおり `Unreadable` で、`RowSqlExecutor.readRow` が行全体を `READ_CONVERSION` の失敗（409 `BUSINESS_TARGET_DB_MISMATCH`）にする。`readRow` は `Raw` を `Text` と同じにマップへ入れる（上限で切らない。日時の文字は短い）。`generatedKeys` は `Text` だけを鍵に使い、`Raw` は鍵を返さない（今の「文字として読めない鍵」と同じ）。
- **D-P2 主キーが読めない行（BR3.12）**: 読めない主キーの値は、一覧の行の主キーに読めない文字のまま入れる（画面が U1 の `unreadable` として出す）。その文字を詳細・更新・削除に送り返しても、既存の主キーの値の読み取り（`KeyValidation`）が型として読めず、行を特定せずに拒否する（状態は変わらない）。拒否の応答は既存の入力の誤り（400 `VALIDATION_FAILED`、どの項目か）で、機能設計 BR3.12 の「行を1件に決められない操作の既存の拒否」（409 `BUSINESS_ROW_OPERATION_NOT_ALLOWED`）とは状態コードが違う。**推奨は 400（既存の経路をそのまま使い、service の層に特例の分岐を足さない。読めない文字を送り返す操作は不正な入力であり、画面は読めない主キーの行の操作を出さない）**。409 にするには詳細・更新・削除の service に「日時の主キーが読めない」を見分ける分岐が要り、追加の手順（`BusinessDataReadService.get`・`BusinessDataWriteService` の主キー検証）とテストが増える。承認の場で選ぶ（下の「承認の場で確かめたい点」）。
- **D-P3 `timetz` の比較（BR3.6・BR3.13 から導く）**: `timetz` を時差のまま保持すると、PostgreSQL の比較（列側だけを `AT TIME ZONE 'UTC'` に直す今の SQL）が、時差が +00 でない値の検索・主キー・参照で一致しなくなる。そこで `BoundValue` の `TIME_TZ` は要求の時差を保ち（書き込みはそのまま束縛）、**比較に使うとき**だけ UTC に直して束縛する: `RowDialect` に `comparisonValue(BoundValue)` を足し（PostgreSQL は `TIME_TZ` を UTC に直す、MySQL・MariaDB は恒等）、比較の値を作る5か所（`RowSqlBuilder` の `where` と参照先の条件、`RowWriteSqlBuilder` の主キー・一意の確かめ・参照の確かめ）で通す。挿入・更新の `SET` の値は通さない。`BoundValue` の説明（「TIME_TZ は UTC」）を直す。非 UTC の時差の `timetz` で、検索・主キー・更新の往復を PostgreSQL の結合テストで確かめる。
- **D-P4 桁の取り出しの置き場（LC2）**: 桁は `RowDialect` の新しい `Integer fractionDigits(ResultSetMetaData, int index, ValueType)` で、方言ごとに決める（PostgreSQL・MariaDB は `getScale`。MySQL は `getPrecision` から導出: `datetime`・`timestamp` は 19 なら 0 桁、そうでなければ値 − 20、`time` は 10 なら 0 桁、そうでなければ値 − 11。SD2.1）。`RowSqlExecutor` は **結果の1つにつき1回**、選んだカラムに日時・時刻の型があるときだけ `resultSet.getMetaData()` を取り、桁の配列を作って各行の `readCell` に渡す（行ごとには取らない）。メタデータが無い（`null`）・桁が得られない（`null`）ときは、今までどおり桁を固定せず出す（桁の取れない型が結合テストで見つかったら設計に戻す。Q2: A）。これで、`getMetaData()` を設定していないモックの `ResultSet` を使う既存の単体テストが動き続ける。
- **D-P5 PostgreSQL の番兵の読み方（LC4・SD2.3）**: PostgreSQL の日時・時刻は型付きで1回だけ読み、**オフセットの変換の前に**番兵（`LocalDateTime`・`OffsetDateTime`・`LocalDate` の最大・最小、端数が 999999999 ナノ秒の `LocalTime`・`OffsetTime`）かを確かめる。番兵のときだけ同じセルを `getString` で読み直して `Raw` にする（問い合わせも接続も増えない）。`OffsetDateTime` の最大・最小は UTC に直す前に確かめる（直すと範囲外になりうる）。
- **D-P6 既定の DSL の生成の桁の出どころ（BR3.8）**: 両 `SchemaQueries` のカラムの問い合わせの「精度」の列を `COALESCE(NUMERIC_PRECISION, DATETIME_PRECISION)`（PostgreSQL は `numeric_precision`・`datetime_precision`）にして、日時・時刻の列の秒の端数の桁を `TargetDbType.precision` に載せる（日時・時刻の型では `NUMERIC_PRECISION` は NULL のため、数値の型の値は変わらない）。`DslTreeBuilder` は **日時・時刻の分類（`TypeCategory.DATETIME`・`TIME`）の列だけ**、桁がその製品の既定（PostgreSQL 6・MySQL/MariaDB 0）と違うときに限って `dbType.precision` に書き、それ以外の列（`DATE`・`interval` を含む）には桁を書かない（今までどおり null）。型のレコード（`TargetDbType`）に項目は足さない。
- **D-P7 型の名前の分類（BR3.7）**: `RowDialect.baseName` は括弧の後ろを全部落としているため（レビューで確認）、`timestamp(3) with time zone` が `timestamp`（時差を持たない日時）になる。符号なしの印の特例（`int(10) unsigned`）と同じ形で、**頭が `timestamp`・`time` のときだけ**、括弧の後ろの `with time zone`・`without time zone` を残す（それ以外の型の名前の扱いは変えない）。先に失敗する単体テスト（`RowDialectTest`）で不具合を確かめてから直し、結果を `code-summary.md` に記録する（BR3.18）。生成が日時の桁を読まない点（D-P6）も、先に失敗するテストで確かめてから直す。
- **D-P8 書き込みの端数の確かめ（BR3.9）**: `ColumnValueCodec.fractionDigits` を「型の名前の `(n)` → DSL の `dbType.precision` → **確かめない（null）**」にし、製品の既定の桁（PostgreSQL 6・MySQL/MariaDB 0）へ戻さない。`ColumnKind.fractionDigits` が null なら `WriteRequestValidator` は確かめない（今の実装がそのまま対応する）。**気づいた点（承認の場で知っておいてほしいこと）**: BR3.8（既定と同じ桁は DSL に書かない）と BR3.9（明示のない桁は確かめない）を合わせると、生成した DSL の MySQL・MariaDB の `datetime`・`timestamp`・`time`（既定の 0 桁）の列に端数のある値を送っても、サーバー側は拒否せず、DB が丸める（以前は 400 で拒否していた）。機能設計の `[assumption]`（桁の無い手書きの DSL を拒否しない）の帰結で、設計どおり。Build and Test の結合テストで DB の動作（丸め）を明示して固定する。
- **D-P9 引き継ぎ**: 初期化の失敗の見分け方は Incident Response の手順書へ、既存の p95 の前後の値は Build and Test へ引き継ぐ（コードの手順ではない）。最悪の場合（1万のセルがすべて読めない値）の測りは手順 9 の単体テストの合格基準にする（NFR Design レビュー R-03）。

### 承認の場で確かめたい点

1. **D-P2**: 読めない主キーの行の詳細・更新・削除の拒否を、既存の主キーの値の検査による 400（推奨。理由は上のとおり）にするか、機能設計どおりの 409 `BUSINESS_ROW_OPERATION_NOT_ALLOWED` にするか。
2. **D-P8**: 生成した DSL の既定の桁の列は端数を確かめない（DB が丸める）ことの受け入れ。
3. 計画の影響の範囲に挙げた既存のテスト・テスト用のデータの期待の書き換え（「影響の範囲」の表）。ArchUnit の境界テストと SpotBugs の除外は書き換えない。
