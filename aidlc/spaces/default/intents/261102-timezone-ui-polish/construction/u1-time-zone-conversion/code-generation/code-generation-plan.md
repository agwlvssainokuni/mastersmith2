# コード生成の計画 — u1-time-zone-conversion

## Summary

- Builds: 画面の側の純粋な日時変換の関数群（時点 → 表示の文字、ローカル時刻 → 時点、名前の解釈、元の時点の保持、時点の比べ）。新しい依存は足さない
- Touches: `frontend/src/shared/format/timeZone/`（新しいフォルダ。ソース 7 本とテスト 8 本）と、`frontend/eslint.config.js`（このフォルダだけに通信・保存・DOM・`console` の使用を禁じる上書きを足す）。既存の `formatDateTime.ts` は変えない
- Tests: Vitest の単体テスト約 55 件（部品ごと 5〜8 件）と、`fast-check` の性質ベース 6 件、性能の測り 1 件。E2E の流れは足さない（U1 は画面を持たない）

出典: 機能設計（`construction/u1-time-zone-conversion/functional-design/functional-spec.md`・`rules.md`・`entities.md`）、NFR Design（`nfr-design/security-design.md`・`logical-components.md`）、契約 C1（`inception/contract-design/contract-summary.md`）、単位の定義（`inception/units-generation/unit-of-work.md`）、要件（`inception/requirements-analysis/requirements.md`）。

## 方針

- 方法は test-after（`team.md` Testing Posture）。層（部品）ごとに実装を書き、同じ Bolt の中でその部品のテストを書いて実行し、通ってから次の部品へ進む。
- 置き場は `frontend/src/shared/format/timeZone/`。論理の部品 LC1〜LC6（`nfr-design/logical-components.md`）を1ファイルずつにする。依存の向きは LC4・LC5 → LC2・LC3 → LC1（逆向きを作らない）。公開の入口は `index.ts` の名前付きのエクスポートだけ。
- 先に決めた設計（NFR Design の Q1: A 壁時計の差から時差を求める・Q2: A 範囲外の年は `unreadable`）に従う。
- **NFR Design のレビューの指摘（助言）を、この計画で確定する**（承認の場で変えてよい）:
  - ローカル時刻を UTC の時点に直した結果の年が 0001〜9999 を外れるとき（例: `9999-12-31 23:00:00` を `America/New_York` で入力すると UTC は 10000 年）は、`{kind: "invalid", reason: "out-of-range"}` を返す（5桁の年の文字を作らない）。承認済みの機能設計に無い扱いのため、`code-summary.md` に差として記録する。
  - 名前と時刻の文字が両方不正なときは、名前の検査が先（BR1.12 の手順 2）で、`invalid-time-zone` を返す。
  - `compareInstants` の結果の型は `{kind: "ok", order: <負・0・正>}` か `{kind: "unreadable", side: "a" | "b" | "both"}`。
  - 暦は 1582 年より前・0001 年付近も先発グレゴリオ暦で往復することを、テストに含めて確かめる。
  - 性能の測りは、判定を5回の測りの中央値で行い、失敗時は測った値と環境を出す。目標（500 ミリ秒・0.05 ミリ秒）は緩めない。
- 既存の検査（`frontend/scripts/check-bundle-size.mjs`・ライセンスヘッダー・Prettier・oxlint・ESLint・tsc・Vitest のカバレッジ）に入る。サイズの上限に収まることを `./gradlew verify` で確かめる。
