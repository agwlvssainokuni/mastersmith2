## 方針

- 方法は test-after（`team.md` Testing Posture）。層（移行 → バックエンドの保存と API → バックエンドの結合 → 画面の配布 → プリファレンスの画面 → 管理の画面 → ESLint → E2E → 負荷の場面 → 記録）ごとに実装を書き、同じ Bolt の中でその層のテストを書いて実行し、通ってから次の層へ進む。その層の変更で落ちる既存のテストは、その層のテストの手順の中で直す（「影響の範囲」の表）。例外は 2 つ。(1) 保存の 1 文は、成り立つかが未確認（H5）のため、実装より先に最小の確かめを書く（Step 5）。(2) 文の数の基準は、今の実装の数を変更の前に固定する（Step 2。変更の前の実装を測るだけで、新しい動作のテストではない）。
- 置き場は論理の部品 LC1〜LC11 のとおり。バックエンドは `user` の 4 層の中に閉じ、`UserBoundaryArchitectureTest` の依存の向きを変えない（`user` は `common` だけに依存。新しい部品は JDK と Jackson だけを使う）。画面は `features` が `app` を読む向きだけで、`shared` は `app`・`features` を読まない。機能どうしは import しない。
- 新しい依存を足さない（`backend/build.gradle.kts`・`backend/gradle.lockfile`・`frontend/package.json`・`package-lock.json`・`config/npm-build-tools.txt`・Dockerfile・compose・`.env.example` は変えない。Step 22 で差分を確かめる）。実行時のタイムゾーンの設定の 4 か所（Dockerfile の `-Duser.timezone`・compose の `TZ`・テストの JVM の `user.timezone`・E2E の起動）も変えない。
- 測れる目標は緩めない（選択肢の組み立て 100 ミリ秒の 5 回の中央値、文の数、k6 の p95 1 秒）。外れたときは原因を確かめて依頼者に諮る。除外・規則の無効化・既知の違反の一覧への追加で通さない（`project.md` Forbidden）。
- ソースの先頭に Apache License 2.0 のヘッダー（`/* ... */`、年 2026、著作権者 `agwlvssainokuni`）。コメントは日本語、テストの説明文は英語。個人に関する値・秘密は置かない（テストの利用者は `example.com`、名前は公開の地域の名前と架空の氏名だけ）。

### 承認の場で確かめたい点（推奨を先に示す）

1. **D8（管理の画面に案内を足さない扱い）**: 保存済みの名前を今のブラウザが解釈できないとき、管理の画面の時刻はブラウザのタイムゾーンで**時差の数字つきで**出し、案内の行は足さない（BR2.22。案内はプリファレンスの画面と業務データの画面の案内の行に出す）。ストーリーの AC1.2.4 は管理の画面にも案内を求めうるため、読みが食い違う。**推奨: 案内を足さない（承認済みの機能設計のとおり）**。理由: 時刻に `+09:00` のように時差が付くため、ずれたまま気づかないことは起きにくく、管理の画面 3 つに案内の行を足すと部品と文言とテストが増える。案内を足す形を選ぶなら、機能設計に戻す（`DisplayTime` は案内の口を足せる形にしてある）。
2. **D9（整形の呼び出し回数の上限）**: NFR2.1.7 の「表示する時刻の数を超えない」を「表示する時刻の数 + 1」（今の時刻の整形を 1 ページ 1 回）と読む。**推奨: この読み（D-P10）**。理由: 趣旨（行数に比例した無駄な整形をしない）と目標（1 つの変換が平均 0.05 ミリ秒以内、1 ページ最大 1 万個で 500 ミリ秒以内）は保たれ、要件の文言に合わせるために今の時刻を行ごとに整形し直すほうが無駄が大きい。
3. **D-P2 の (b)**: 保存の 1 文が Spring Data の `@Query` で成り立たないとき、`EntityManager` のネイティブの問い合わせを持つ断片を `user.repository` に足してよいか。**推奨: 足してよい**（要件を緩めずに済む。(c) まで進むときは生成を止めて改めて諮る）。
4. **D-P9 の `vitest.config.ts` の変更**: ESLint の規則の確かめのテストを `eslint-config` のプロジェクト（ほかより先に単独で流す）に入れる。**推奨: 入れる**。理由: ESLint の部品の読み込みが重く、jsdom のテストと同時に始めると beforeAll の上限を超えて落ちた前例がある（`vitest.config.ts` の説明）。上限の時間は延ばさない。
5. **使われなくなる整形の削除**: `formatDateTime.ts`・`lockedUntil.ts` とそのテスト（`formatDateTime.test.ts` の 3 件・`lockedUntil.test.ts` の 6 件）を**消し**、新しい整形のテストに置き換える（SD6。規則を通すための例外を置かない）。**推奨: 消す**。消す前後のテストの件数を Build and Test で記録する。
6. **D-P6**: 文の数の基準を変更の前に固定してから変える（Step 2）。**推奨: そうする**。理由: 「今の数を超えない」を実測で守れる。
7. **H3 の洗い出しに無かった既存のテスト**: `PreferencesPartialUpdateIT`（`PreferencesCommand` を 4 つの引数で作る 4 か所）を、NFR Design の見込みに足して直す。承認済みの記録は書き換えず、差を `code-summary.md` に書く。
