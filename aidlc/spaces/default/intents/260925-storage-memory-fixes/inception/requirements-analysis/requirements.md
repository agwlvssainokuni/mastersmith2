# 要件定義 — 内部DB のファイルの伸び・DSL のメモリ・AccessTokenApiIT・perf の説明

## 意図の分析

- 依頼: 前の Intent（260924-followup-fixes）と前の振り返り（260923-dsl-schema-loader の束 2）で後に回した4件を直す [desc]。
  - (1) 動いている間、DSL の投入と適用のたびに内部DB のファイルが伸び、止めるまで縮まない件（U4-STORAGE-RUN）。
  - (2) 10MB の DSL の投入とログインを重ねると、プロセスのメモリが上限 2g の 93% に達する件。
  - (3) `AccessTokenApiIT` が一度だけ接続の失敗で落ちた件。
  - (4) `perf/dsl-timing.sh` 33 行の説明が、前の Intent の決定（2g）と食い違う件。
- 種類: 不具合の修正（Workflow-selected scope: bugfix）[scope]。深さは Minimal。
- 目的: 大きな DSL を扱っても、アプリを止めずに内部DB のファイルを元の大きさへ戻せるようにする。メモリの使い方の実態を測り、減らせる分を減らす。一時的なテストの失敗の原因を確かめる。業務の機能は増やさない。管理者向けの API の操作が1つ増えるだけとする。
- 出どころ: 今回のコードの調査の結果（`aidlc/spaces/default/codekb/mastersmith2/code-quality-assessment.md` の TD-1〜TD-4）。業務の背景は `business-overview.md`、本文が書かれる道は `architecture.md` の Interaction Diagrams、ファイルの置き場は `code-structure.md`。
- 依頼の番号（1〜4）と、要件の番号（FR1〜FR4）は同じ順に対応させる。直した後の負荷の試験は FR5 とする。

## 機能要件

### FR1 管理者の操作で、アプリを止めずに内部DB のファイルを詰め直す（1件目）

- **FR1.1** 管理者向けの API に、内部DB（組み込みの H2）のファイルを詰め直す操作を足す。H2 は接続が1本でも生きている間は詰め直さないため、この操作では、アプリを止めずにすべての接続を閉じ、詰め直し、接続を使える状態に戻す [desc][Q1][F1]。
  - 合格の条件: 結合テストで、操作の前にプレビューと履歴を入れ替えてファイルを伸ばし、操作の後にファイルが小さくなっていることを確かめる。アプリは同じプロセスのまま応答を続ける。
- **FR1.2** 詰め直しは、管理者が操作したときだけ行う。自動では行わない [F1][F4]。
  - 合格の条件: 操作をしない間は、今と同じ動き（投入と適用でファイルが伸びる）であることを確かめられる。自動の詰め直しの仕組みが無い。
- **FR1.3** 入口は管理者向けの API（`/api/admin/**` の下）だけとし、画面は作らない。呼び方は README に書く [F5]。
  - 合格の条件: サーバー側のテストで、未認証は 401、管理者でない利用者は 403、管理者は成功になる（team.md の Testing Posture の認可のテスト）。
- **FR1.4** 詰め直しの直後に、ファイルの大きさが、保存している本文の論理的な最大（プレビュー1件と履歴 20 件がすべて 10MB のとき約 210MB）に余裕を足した値以下に戻る。余裕の値は設計（コード生成の計画）で決める [Q1][F4]。
  - 合格の条件: Build and Test で、10MB の DSL の投入と適用を 40 回続けてファイルを伸ばしたあと、アプリを止めずにこの操作を行い、ファイルの大きさが決めた値以下になる（FR5）。
- **FR1.5** 詰め直しの間に届いた、内部DB を使う要求は、詰め直しが終わるまで待たせる。今の接続を借りる待ちの上限（5 秒）を超えたら、今と同じ失敗の応答になる [F2]。
  - 合格の条件: 結合テストで、詰め直しの最中に内部DB を使う要求を送り、詰め直しの後に成功すること（待ちが上限の内側のとき）を確かめる。上限を超えたときの応答が今と同じ形であることも確かめる。
- **FR1.6** 詰め直しの操作は、監査ログに残す。記録する項目は、誰が・いつ・結果（成功・失敗）・詰め直しの前と後のファイルの大きさとする [F6]。
  - 合格の条件: 結合テストで、成功した操作と失敗した操作のそれぞれで、監査イベントに必須の項目が記録されていることを確かめる（team.md の Testing Posture の監査ログのテスト）。
- **FR1.7** 詰め直しの最中に、ほかの操作（ログインなど）の監査の記録が失敗したときは、今の監査の決まりに従う（記録に失敗しても元の操作は成功し、アプリのログに ERROR が1回出る）[F6]。
- **FR1.8** 表の形（`dsl_previews`・`dsl_applied_revisions` の列と、本文をバイト列のまま置く中身の形）は変えない。H2 の設定や保存の仕方の工夫だけで直す。これにより、1つ前の版のアプリのイメージへ戻せることを保つ [Q2]。
  - 合格の条件: DSL の表への Flyway の移行を足さない。本文の識別（SHA-256）とダウンロードがバイト単位で一致する既存のテストが通る。
- **FR1.9** 操作をしない間のファイルの伸びは受け入れ、README の既知の制約（U4-STORAGE-RUN）を、詰め直しの操作の呼び方と、いつ行うとよいかの目安に書き直す [F4][F5]。
- **FR1.10** 詰め直しの操作を同時に複数受け付けない。重い DSL の操作（生成・投入・プレビューの表示・戻し）との重なりの扱いは、設計で決める [assumption]。
- **FR1.11** 不具合を再現するテスト（投入と適用でファイルが伸び、操作で縮むこと）を、直しと同じコミットに入れる（project.md の Mandated）。

### FR2 10MB の DSL の投入とログインを重ねたときのメモリを測り、減らせる分を減らす（2件目）

- **FR2.1** 直す前に、前の Intent と同じ `dslMixed` の条件で、プロセスのメモリの内訳（ヒープ・ヒープ以外・ページキャッシュ）を測る。測り方（GC のログ・NMT・`memory.stat` の `anon` と `file` の分け方など）は、コード生成の計画で決める [desc][Q3]。
  - 合格の条件: 内訳の測定の結果が、直す前の値として記録されている。
- **FR2.2** 数値の目標は、FR2.1 の結果を見て、コード生成の計画の承認の場で依頼者が決める [Q3]。
- **FR2.3** 減らす対象は、測った内訳のうちアプリで減らせる分（本文の複写、読み込みの途中の形を同時に持つ時間、持ち続けるモデルなど）とする。DSL を信頼できない入力として扱う決まり（大きさ・深さ・別名の上限、タグの拒否、重複キーの誤り、誤りの行と列）を弱めない [desc]。
  - 合格の条件: DSL の信頼できない入力のテスト（team.md の Testing Posture の一覧）が変更の後も通る。
- **FR2.4** 直した後に、同じ `dslMixed` の条件で測り、FR2.2 で決めた目標を満たすかを確かめる（FR5）。

### FR3 `AccessTokenApiIT` の一時的な失敗の原因を確かめる（3件目）

- **FR3.1** 原因の候補（(a) PC の負荷、(b) colima のポートの転送とテストのアプリの空いた番号の衝突、(c) 1つの JVM に多数の Spring の文脈がたまることによる資源の使い過ぎ）について、再現と切り分けを試す [desc][Q4]。
  - 合格の条件: 試した手順と結果（再現したか、どの候補を否定・支持したか）が記録されている。
- **FR3.2** 原因が確かめられたときだけ直す。直すときは、再現するテストか再現の手順を同じコミットに入れる [Q4]。
- **FR3.3** 再現できなかったときは、`AccessTokenApiIT` を「不安定なテストと確かめられていない」扱いとし、調べた結果を記録して、この Intent を統合してよい（team.md の「不安定なテストは原因を直すまで統合しない」は、不安定と確かめられたテストに当てる）[F3]。

### FR4 `perf/dsl-timing.sh` の説明を 2g に合わせる（4件目）

- **FR4.1** 33 行の説明の「要件の条件は 1g」を、前の Intent の決定（2g）に合わせて直す。既定の値（55 行）と `perf/README.md` 109 行はすでに 2g のため変えない [desc]。
  - 合格の条件: 説明の文と既定の値が一致している。

### FR5 直した後の負荷の試験

- **FR5.1** Build and Test で、k6 の `dslMixed`・`dslCycle` と `perf/dsl-timing.sh` を、使い捨ての環境（`perf/README.md` の手順）で流す。この Intent には Performance Validation の段が無いため、持ち主は Build and Test とする（project.md の決まり）。
- **FR5.2** 直す前の値は、前の Intent の実測を使う: `dslMixed` で `anon` 1,894MiB（2g の 93%）、`memory.events` の `max` 2,340 回。10MB の投入と適用で1回あたり約 10.8MB 伸び、40 回で約 483MB。
- **FR5.3** FR1.4（詰め直しの直後の大きさ）と FR2.4（メモリの目標）を確かめる。配備先の環境が要る目標は Unverified とし、持ち主の段を書いて引き継ぐ（project.md の決まり）。

## 非機能要件

- **NFR1 可用性**: 詰め直しの操作の間も、アプリのプロセスは止めない。内部DB を使う要求は、詰め直しの間は待たされる（FR1.5）。詰め直しにかかる時間は、10MB の本文が 21 件ある状態で Build and Test で測り、README に目安として書く。
- **NFR2 秘密情報と個人に関する値**: パスワード（平文・ハッシュ値とも）・トークン・署名鍵を、ログ・監査ログ・外部への送り出し・エラー応答に含めない（project.md の Forbidden）。DSL の本文をログに出さない。`.env`・`.env.targetdb` の値をコミット・記録・表示しない。
- **NFR3 認可**: 詰め直しの操作は管理者だけに限り、サーバー側で検査する（FR1.3）。
- **NFR4 品質の下限の維持**: カバレッジの下限（行 80%・分岐 70%）を下げず、除外も増やさない。新しいパッケージを作るときは、パッケージごとの下限も満たす（team.md の Testing Posture）。
- **NFR5 統合前の関門**: `./gradlew verify` のすべての検査を通してから統合する。対象DB のテストを飛ばした状態では統合しない（team.md の Way of Working）。
- **NFR6 既存の動作の維持**: ログイン・ロック・監査・DSL の管理の、既存の結合テストと E2E が変更の後も通る。

## 制約

- DSL の表の形は変えない（FR1.8）。DB のスキーマの変更は前進のみとし、1つ前の版のアプリが動く後方互換を保つ（team.md の Deployment）。
- 監査ログは追記だけで、変える・消す処理を持たない（README の「監査ログ（U4）」）。
- 配備先は開発者の PC 上のコンテナだけとする。クラウドの基盤は作らない（team.md の Deployment）。
- `vendor/make-you-chic-ui` の中身を変更しない（project.md の Forbidden）。この Intent では画面を変えない（FR1.3）。
- `origin` へのプッシュは依頼者が行う（team.md の Way of Working）。

## 前提

- H2 は、接続が1本でも生きている間はファイルを詰め直さない。すべての接続を閉じたときに、`DEFRAG_ALWAYS=TRUE`（`application.yaml` 137 行）に従って詰め直す。これは依頼者の補足による前提で、コード生成の段で実際に確かめる [Q1]。
- 今の接続のプール（Hikari、上限 30、待ちの上限 5 秒）は接続を持ち続けるため、DB が閉じるのはアプリの停止時だけである（`application.yaml`）。
- 監査イベントの種類の列は `VARCHAR(32)` で、種類を限る制約は無い（`V4__u4_audit_event.sql`）。新しい種類を足すのに表の変更は要らない。
- 1回目の `AccessTokenApiIT` の失敗の報告は上書きされていて、後から確かめる材料はほぼ残っていない（`code-quality-assessment.md` の TD-3）。

## 範囲の外

- 詰め直しを自動で行うこと（しきい値・時刻による実行）[F4]。
- 詰め直しの操作の画面 [F5]。
- DSL の表の形の変更（本文の置き場を1か所にする、圧縮する、DB の外のファイルに置く）[Q2]。
- 監査ログを見る画面・API、監査ログの保存の期間と古い記録の扱い。
- 前の振り返りの束 3（古い版の起動の確かめ、アクセシビリティの手での確認、SLO の正式な値と配備先の決定）。

## 残る未確定の点

- すべての接続を閉じて詰め直す具体的な方法（プールの一時停止と接続の破棄、H2 の `SHUTDOWN` の使い分けなど）と、閉じたことの確かめ方は、コード生成で決める（FR1.1）。
- 詰め直しの直後の大きさの余裕の値は、コード生成の計画で決める（FR1.4）。
- 詰め直しの操作と重い DSL の操作が重なったときの扱い、監査イベントの種類の名前、前と後のファイルの大きさを監査の表のどの列に置くか（新しい列が要るなら、前進のみで後方互換の移行とする）は、コード生成で決める（FR1.6・FR1.10）。
- 詰め直しが接続の待ちの上限（5 秒）より長くかかると、その間の要求が失敗しうる。かかる時間は Build and Test で測る（FR1.5・NFR1）。
- メモリの内訳の測り方と数値の目標は、コード生成の計画で決める（FR2.1・FR2.2）。
- `AccessTokenApiIT` の再現の手順は、コード生成の計画で決める（FR3.1）。
