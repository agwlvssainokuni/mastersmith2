# Functional Design — U1 対象DB（u1-target-db）— 設計の要点の確認

U1 の論点は、要件・Domain Design（ADR-006・ADR-010）・Contract Design（C1・C3）でほぼ決まっている。そのため質問は作らず、機能設計の要点を案として示して確かめる（`aidlc/spaces/default/memory/project.md` の Way of Working）。待ち時間の数値・接続のプールの大きさは NFR の段で決める。

## 設計の要点（案）

- **扱うデータ**: アプリが持つデータは、読み取ったスキーマの写し（テーブル・ビュー・カラム・型・主キー・外部キー・NOT NULL・既定値・コメント）だけで、保存しない（要求のたびに読む）。接続先の設定は Spring Boot の設定の仕組みの値なので、エンティティにせず決まりとして書く（project.md の Code Style）。
- **最初に作る DB の種類**: PostgreSQL で規則とエラーの扱いを作り切り、MySQL・MariaDB は U3 の回（B3）で揃える（Bolt の計画のとおり）。
- **読み取りの範囲**: 設定したスキーマの中のテーブルとビューだけ。システムのスキーマ・ほかのスキーマ・シノニム・マテリアライズドビューは含めない。
- **読み取りの方法**: テーブルごとに問い合わせを繰り返さず、スキーマ全体をまとめて読む（100テーブル×100カラムで 30 秒の目標のため）。具体の方法（JDBC のメタデータか、情報スキーマの問い合わせか）は NFR 設計で比べる。
- **識別子**: 物理名は DB が返す大文字・小文字のまま扱う。識別子を SQL に組み込むときは、読み取った名前の一覧にあるものだけを、DB の種類に合った引用符で囲む。利用者の入力から識別子を作らない。
- **結果の種類**: 成功（スキーマの写し）／設定が無い（必須の項目の欠け・種類が対応外を含む）／接続できない（接続の失敗・待ち時間の超過）の3つ（契約 C1）。どれにも接続先・ユーザー名・パスワード・内部の例外のメッセージを含めない。
- **起動時の点検**: `mastersmith.target-db.*` の必須の項目（種類・ホスト・ポート・DB 名・スキーマ名・ユーザー名・パスワード）を点検し、欠け・不正があれば項目の名前だけを WARN で1件出して起動を続ける。設定がまったく無いときは、WARN を出さず「使わない」として扱う（Q12 で決めた、設定が無くても起動する扱いに合わせる）。
- **接続**: 「既定の候補にしない」指定で足す（ADR-006）。読み取り専用、自動の確定（autocommit）、小さなプール。対象DB への接続は、初めて使うときに開く（起動時には接続しない）。ヘルスチェックには含めない。
- **パスワード**: 設定の型の文字列表現では伏せ字にする。ログ（TRACE を含む）にも出さない。
