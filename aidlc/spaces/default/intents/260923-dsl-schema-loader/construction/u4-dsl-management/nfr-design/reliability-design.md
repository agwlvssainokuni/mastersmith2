# Reliability Design — U4 DSL の管理（u4-dsl-management）

U4 の信頼性の要件（`construction/u4-dsl-management/nfr-requirements/reliability-requirements.md`）を満たす作りの方針。

## 1. 適用（NFR8.1・NFR8.2）

- 業務処理の層の1つのトランザクション（`@Transactional` は業務処理の層だけ）で、プレビューの行を読み `previewId` を確かめる → 履歴に1行足す → `previewId` を指定してプレビューの行を消す（消した件数が 0 なら巻き戻して 409）→ 上限を超えた古い履歴を消す。
- 確定の後にだけ、適用中のモデルの差し替え（U2 の ActiveDslModelHolder）と監査の出来事を行う。確定の後の処理は既存の「確定の後に記録する」仕組み（監査の出来事の受け手）を使う。
- 途中で失敗したら全部を巻き戻し、差し替えも出来事もしない。

## 2. プレビューを置く（NFR8.3）

- 固定の鍵の1行への MERGE（1文）。後に確定した方が残る。置いたらプレビューの読み込みの結果の保持を捨てる。

## 3. 起動と障害（NFR8.4・NFR8.5・NFR7.8）

- 起動時（要求を受ける前）に履歴の最新を読み、U2 で読めれば適用中のモデルに入れる。読めなければ ERROR を1件出し、「無い」で起動を続ける。
- 監査の書き込みに失敗しても、既存の仕組みのとおり DSL の操作は成功させ、アプリのログに1件出す（本文・接続先を含めない）。
- 対象DB が止まっていても、照合は警告になり、生成だけが失敗する（U1 の結果の種類で分ける）。今の状態・履歴・適用・破棄・ダウンロードは対象DB に触れない。

## 4. 戻しと保存

- DB スキーマの変更（プレビューと履歴の表、監査の表の列）は Flyway の前進のみで、1つ前の版のアプリが動く後方互換を保つ（新しい表と列を足すだけ）。
- 内部DB のバックアップは既存の手順のまま。履歴はバックアップの代わりにしない。
