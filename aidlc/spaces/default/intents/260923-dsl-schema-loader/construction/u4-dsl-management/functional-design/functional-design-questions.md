# Functional Design — U4 DSL の管理（u4-dsl-management）— 設計の要点の確認

U4 は DSL の管理の操作（スキーマの読み込み・投入・プレビュー・適用・破棄・履歴・ダウンロード）と、その保存・監査を受け持つ。流れと API の形は要件・ストーリー・ADR-002・ADR-003・ADR-009・契約 C6・C7 で決まっている。残っている細部（契約の「Open questions」を含む）を案として示して確かめる（`aidlc/spaces/default/memory/project.md` の Way of Working）。数値の上限（待ち時間など）は NFR の段で決める。

## 設計の要点（案）

### 保存（内部DB、Flyway の移行で表を足す）

- **プレビューの表**: 最大1行。項目は、プレビューの識別（`previewId`、置くたびに新しい UUID）、YAML の本文、DSL の識別、出どころ（GENERATED・UPLOAD・PASTE・RESTORE）、置いた人（利用者の ID）、置いた日時（UTC）。
- **適用の履歴の表**: 適用ごとに1行。項目は、版の識別（`revisionId`、UUID）、YAML の本文、DSL の識別、出どころ、適用した人、適用した日時（UTC）。適用中は、適用した日時が最も新しい行（同じ日時なら追加の順）。
- **件数の上限**: 設定 `mastersmith.dsl.history-limit`（既定 20、1以上）。適用のたびに、上限を超えた古い行を消す。

### 操作の決まり

- **プレビューに置く**（生成・投入・履歴からの戻し）: U2 で検証を通ったものだけを置く。今のプレビューの行を置き換え、新しい `previewId` を振る。置く前に対象DB との照合を行い、その結果（警告）は保存せず、プレビューを表示するたびに照合し直す。
- **適用**: 1つのトランザクションで、(1) プレビューの行を読み、要求の `previewId` と同じかを確かめる（違う・無ければ `DSL_PREVIEW_CHANGED`）、(2) 履歴に1行足す、(3) プレビューの行を消す、(4) 上限を超えた古い履歴を消す。2人が同時に適用したときは、プレビューの行を消した側だけが成功するよう、プレビューの行の削除の件数（1件か0件か）で確かめる。確定の後に適用中のモデルを差し替え、監査の出来事を出す。
- **起動時**: 履歴の最新（適用中）を読み、U2 で解釈して適用中のモデルに入れる。読めない（検証を通らない）ときは、ERROR のログを1件出し、適用中のモデルを「無い」にして起動を続ける。
- **管理者の表示**: 置いた人・適用した人は、利用者の ID からメールアドレスを引いて示す（利用者が消えていたら「不明」）。

### 応答の形（契約 C6 の残り）

- **誤りの一覧を載せる口**: 既存の業務の例外（`BusinessException`）に「追加の項目」（名前と値の対応表、既定は空）を持たせ、共通の変換（`@RestControllerAdvice`）がそれを Problem Details の項目として載せる。`code`・`traceId` など既存の項目名は上書きしない。誤りの一覧は、この口に `errors`（先頭100件）と `total` を載せる。
- **ダウンロードのファイル名**: プレビュー中は `dsl-preview-<識別の先頭12文字>.yaml`、適用中は `dsl-applied-<識別の先頭12文字>.yaml`。
- **違いの「変わった」に数える項目**: テーブルは表示名・ビューかどうか・主キー・外部キー。カラムは表示名・DB 上の型・フォーム部品・検索・一覧・詳細・バリデーション・選択肢。項目の名前（例: `label.ja`・`list.order`）を `changedItems` に並べる。
- **表示名の未設定**（`missingDisplayNames`）: 先頭100件と総数を返す（誤りの一覧と同じ扱い）。
- **受け付けなかった投入の理由の種類**（監査の `rejectionKind`）: 誤りの一覧の最初の誤りの種類（検証は段ごとに止まるので、1つの段の種類になる）。大きさで読む前に止めたときは `SIZE_LIMIT`。

### 本文の大きさ

- 投入の API（`POST /api/admin/dsl/preview`）だけ、要求の本文を 5MB まで受ける。既存の本文の上限の仕組み（全要求 1MB）に、この API の道だけ上限を変える口を足す。1MB を何バイトとするかは NFR 設計で決める。

### 監査（既存の監査の拡張）

- 監査の表に、操作した人（利用者の ID）・DSL の識別・出どころ・理由の種類 の列を足す（Flyway の移行、前進のみ）。
- 出来事の種類に、DSL の生成・投入・受け付けなかった投入・適用・破棄を足す。履歴からの戻しは「投入」で、出どころ RESTORE。
- 記録は既存の決まりのとおり（確定の後、失敗しても元の操作は失敗させない、巻き戻れば記録しない）。
