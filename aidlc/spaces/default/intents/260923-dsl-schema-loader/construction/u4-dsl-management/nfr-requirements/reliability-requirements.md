# Reliability Requirements — U4 DSL の管理（u4-dsl-management）

U4 の状態の一貫性と、障害のときのふるまいを示す。配備先は開発者の PC 上のコンテナで、稼働率の目標（SLO）は配備先が決まってから決める（`aidlc/spaces/default/memory/team.md` の Deployment）。

## 1. 要件

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR8.1 | 適用は1つのトランザクションで、適用中の DSL・履歴・プレビューを一度に切り替え、途中で失敗したら全部を巻き戻す。適用中のモデルの差し替えと監査は確定の後だけ | 結合テスト（ストーリーの AC4.2.4、履歴の書き込みでの失敗を差し込む） | NFR8、BR4.2・BR4.6 |
| NFR8.2 | 2人が同じプレビューを同時に適用しても、1件だけ成功し、履歴は1件だけ増える | 結合テスト（待ち合わせで重なりを作る、AC4.2.3） | NFR8、BR4.3 |
| NFR8.3 | プレビューを置く操作どうしが重なっても、プレビューの行は1つで、後に確定した方が残る（重い処理は NFR1.13 で1つに絞られるため、実際に重なるのは起動直後などのまれな場合） | 単体・結合テスト | BR1.4 |
| NFR8.4 | 起動時に適用中の DSL を読めなくても（検証を通らない）、ERROR を1件出して「無い」で起動を続ける | 結合テスト | BR5.2 |
| NFR8.5 | 監査の書き込みに失敗しても、DSL の操作は成功させ、アプリのログに1件出す（本文・接続先を含めない） | 結合テスト（AC6.3.3） | 既存の決まり |
| NFR7.8 | 対象DB が止まっていても、プレビューの表示・今の状態・履歴・適用・破棄・ダウンロードは使える（照合は警告になる。生成だけが失敗する） | 結合テスト | NFR7 |

## 2. 失敗のときのふるまい

| 場合 | ふるまい |
|---|---|
| 対象DB が応答しない（照合） | 接続 3 秒・問い合わせ 5 秒で打ち切り、警告にして表示を続ける |
| 対象DB が応答しない（生成） | 接続 5 秒・問い合わせ 20 秒で打ち切り、503 `TARGET_DB_UNAVAILABLE` |
| 重い処理が重なった | 2つ目以降は 503 `DSL_BUSY`（待たない） |
| 適用の途中の失敗 | 巻き戻し、500。適用中は変わらない |
| メモリが足りない（10MB の DSL） | Build and Test で確かめる。起きたら、コンテナの上限の見直しを依頼者に諮る |

## 3. 戻し方と保存

- 内部DB（H2 のファイル）のバックアップと戻し方は、既存の配備の手順のまま（前の Intent の rollback-runbook）。
- DB スキーマの変更（プレビューと履歴の表、監査の表の列）は前進のみで、1つ前の版のアプリが動く後方互換を保つ（team.md の Deployment）。
- DSL の正本は業務の側のリポジトリにあり、履歴（最大 20 件）は戻しのためのもので、バックアップの代わりにしない。
