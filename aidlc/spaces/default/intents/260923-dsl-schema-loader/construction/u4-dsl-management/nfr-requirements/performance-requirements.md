# Performance Requirements — U4 DSL の管理（u4-dsl-management）

U4 の API の時間の目標を示す。測る場所は開発者の PC 上のコンテナ（既定のメモリの上限 1g）、利用は管理者が数名。答えは `nfr-requirements-questions.md`（Q1〜Q4）。NFR1 の枝番は単位の間で通しで振る（U1 は NFR1.1〜1.3、U2 は 1.4〜1.5、U3 は 1.6〜1.7）。

## 1. 目標

| ID | 対象 | 目標 | 条件 | 測り方 | 出典 |
|---|---|---|---|---|---|
| NFR1.8 | プレビューの表示（`GET /preview`、照合を含む）と、投入・戻しの応答（読み込み・検証・照合・保存） | 10 秒以内 | 想定の規模（100 テーブル × 100 カラム、既定の DSL の書き方で約 5.3MB）の DSL と同じ規模の対象DB、3種類の DB それぞれ。あわせて上限（10MB）の DSL の投入と表示でも 10 秒以内かを測る | Build and Test（ストーリーの AC3.2.5） | NFR1 |
| NFR1.9 | 照合の待ち時間の上限 | 接続 3 秒・問い合わせ 1回 5 秒。超えたら「照合できなかった」の警告（`TARGET_UNAVAILABLE`）にして表示を続ける | 対象DB が応答しないとき | 結合テスト（応答しない対象DB で、10 秒の内に警告つきで返る） | NFR1、Q1: A |
| NFR1.10 | 今の状態・履歴・破棄・適用 | 95% が 1 秒以内 | 想定の規模の DSL が適用中・プレビュー中、履歴 20 件 | Build and Test | Q3: A |
| NFR1.11 | ダウンロード（プレビュー中・適用中） | 10MB の DSL でも 2 秒以内 | 上限の大きさの DSL | Build and Test | Q3: A |
| NFR1.6 | スキーマの読み込み（生成の全体） | 30 秒以内（内訳は U3 の NFR1.7） | 想定の規模の対象DB | Build and Test（AC1.2.3） | NFR1、U3 |

## 2. 資源の目標

| ID | 対象 | 目標 | 測り方 |
|---|---|---|---|
| NFR1.12 | 10MB の DSL を1つ処理するときのヒープ | 1g のコンテナ（ヒープ 75%）で、ほかの利用（ログインなど）と同時に処理が失敗しない | Build and Test（NMT とヒープの最大の使用量）。足りなければコンテナの上限の既定の見直しを依頼者に諮る |
| NFR1.13 | 重い処理の同時の数 | アプリ全体で1つ（生成・投入・戻し・プレビューの表示） | 結合テスト（待ち合わせで重なりを作り、2つ目が `DSL_BUSY` になる）。詳しくは `scalability-requirements.md` |

## 3. 測り方の注意

- 性能の試験は、配備した環境とは別の使い捨ての環境で行い、本物のデータと監査ログを汚さない（`aidlc/spaces/default/memory/project.md` の Testing Posture）。
- 時間は画面を含まない API の応答で測る。
