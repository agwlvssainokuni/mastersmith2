# Scalability Requirements — U4 DSL の管理（u4-dsl-management）

U4 の規模の前提と、重い処理の同時の数の決まりを示す。答えは `nfr-requirements-questions.md`（Q2）。

## 1. 規模の前提

| 項目 | 値 | 出典 |
|---|---|---|
| アプリの数 | 1つ（組み込みの H2、水平に増やさない） | ADR-004 |
| 利用者 | 管理者が数名。DSL の操作は手動でまれ | 要件、ペルソナ |
| DSL の大きさ | 最大 10MB（想定の規模 100 × 100 で約 5.3MB） | U3 の NFR 要件（Q1: B） |
| 履歴 | 最大 20 件（`mastersmith.dsl.history-limit`） | 機能設計 BR4.4 |
| 内部DB の保存量 | 最大約 210MB（プレビュー1件と履歴 20 件がすべて 10MB のとき） | 上の値から |

## 2. 重い処理の同時の数（Q2: A）

| ID | 要件 | 確かめ方 | 出典 |
|---|---|---|---|
| NFR1.13 | 生成・投入・履歴からの戻し・プレビューの表示は、アプリ全体で同時に1つだけ処理する。重なった要求は待たずに 503・code `DSL_BUSY` で断る | 結合テスト: 待ち合わせで1つ目を止めた間に2つ目を送り、503 `DSL_BUSY` になること。1つ目は影響を受けないこと | NFR1、Q2: A |
| NFR1.14 | `DSL_BUSY` で断った要求は、状態を何も変えず、監査の出来事を出さない（受け付けなかった投入 `DSL_SUBMISSION_REJECTED` とは別。本文を読む前に断るため） | 結合テスト: 断った後のプレビュー・履歴・監査が変わらない | Q2: A、要点の確認 |
| NFR1.15 | 軽い処理（今の状態・履歴・ダウンロード・破棄・適用）は制限しない。適用の同時の実行は機能設計の決まり（BR4.3）で1件だけ成功する | 既存の機能設計のテスト | Q2: A |

## 3. 範囲外

- アプリを複数動かすこと（内部DB を共有できる DB に変える判断と合わせて、将来の Intent で扱う。ADR-004）。
- 重い処理の待ち行列（Q2: B は採らなかった）。
