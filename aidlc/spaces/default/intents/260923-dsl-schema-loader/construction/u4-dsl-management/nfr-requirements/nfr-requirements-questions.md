# NFR Requirements — U4 DSL の管理（u4-dsl-management）— 質問

この段では、U4 の非機能の要件を決めます。U4 は API を持つ単位（service）で、要件の NFR1 の一部（プレビューへの読み込みと照合を 10 秒以内）、NFR2（投入の API の本文の上限）、NFR5（エラー応答）、NFR8（適用の一度の切り替え）を受け持ちます（`inception/units-generation/unit-of-work.md`）。性能・拡張性・信頼性・観測の要件もこの単位で決めます。

すでに決まっていること:
- DSL の大きさの上限は 10MB（U3 の NFR 要件、Q1: B）。投入の API だけ本文を 10MB まで受け、ほかの API は今までどおり 1MB。
- 対象DB の読み取りの待ち時間は、接続 5 秒・問い合わせ 1回 20 秒（U1 の NFR 要件）。U2 の読み込みと検証は、想定の規模で 3 秒以内。
- アプリは1つだけ動く（組み込みの H2、ADR-004）。配備先は開発者の PC 上のコンテナ（既定のメモリの上限 1g、ヒープはその 75%）。
- 監査の書き込みに失敗しても操作は失敗させない（既存の決まり）。

## 前の単位のレビューから引き継いだ点

- U1 のレビュー（R-01）: 対象DB の読み取りの待ち時間（最大 5 秒＋20 秒）は、照合の 10 秒の目標を単独で超えうる。照合の待ち時間はこの単位で決める（Q1）。
- 10MB の DSL を読むと、1回の処理で数百 MB のメモリを一時的に使う見込み（本文・節の木・検証用の形・モデル）。同時に重なると、1g のコンテナで足りなくなるおそれがある（Q2）。

## Consolidated Summary Confirmation

- **照合の待ち時間**（Q1: A）: 照合だけ接続 3 秒・問い合わせ 1回 5 秒。超えたら「照合できなかった」の警告にして表示を続ける。スキーマの読み込み（生成）は U1 のとおり 5 秒・20 秒
- **重い処理の重なり**（Q2: A）: 生成・投入・履歴からの戻し・プレビューの表示は、アプリ全体で同時に1つだけ処理する。重なった要求は待たずに 503・新しい code `DSL_BUSY` で断る（監査の出来事は出さない。受け付けなかった投入の監査とは別）。承認済みの契約 C6 と U5 の機能設計に `DSL_BUSY` は無いため、書き換えずに差を tech-stack-decisions.md に記録し、U5 の NFR 要件とコード生成で画面の文言を足す
- **応答時間**（Q3: A）: 今の状態・履歴・破棄・適用は 95% が 1 秒以内、ダウンロードは 10MB でも 2 秒以内。プレビューの表示（照合を含む）は 10 秒以内、生成は 30 秒以内（NFR1）。Build and Test で測る
- **観測**（Q4: A）: 操作ごと（生成・投入・戻し・適用・破棄・照合）の時間と結果（成功・拒否・失敗・`DSL_BUSY`）を指標（Micrometer の Timer）に出し、既存の手元の監視のダッシュボードに DSL の操作の1枚を足す（ファイルでリポジトリに置く）。警報は足さない。ログは既存の構造化ログの決まりのとおり（本文・接続先を出さない）
- **拡張性**: アプリは1つだけ（ADR-004）。同時の利用は管理者が数名。水平に増やすことは今回の範囲外
- **信頼性**: 適用は1つのトランザクション（NFR8、機能設計の BR4.x）。内部DB（H2）の保存量は最大約 210MB（プレビュー1件と履歴 20 件が 10MB のとき）。バックアップは既存の内部DB の扱いのまま。起動時に適用中の DSL を読めなくても起動する（BR5.2）
- **メモリ**: 10MB の DSL を1つ処理するときのメモリを Build and Test で測り、1g のコンテナ（ヒープ 75%）で足りることを確かめる。足りなければ、コンテナの上限（`MASTERSMITH_CONTAINER_MEMORY`）の既定の見直しを依頼者に諮る
- **成果物**: U4 は service のため、performance・security・scalability・reliability・observability の各 requirements.md、tech-stack-decisions.md（差の一覧を含む）、traceability.json を作る
