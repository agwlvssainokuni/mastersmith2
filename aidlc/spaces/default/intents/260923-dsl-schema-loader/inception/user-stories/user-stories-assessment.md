# User Stories — 実施の判断

## 判断

**実施する（Execute）**

## 理由

- 管理者が画面で操作する機能が中心である。スキーマの読み込み、投入（アップロード・貼り付け）、プレビュー、適用、破棄、履歴、ダウンロードがこれに当たる（`requirements.md` の FR3〜FR9）。
- 操作の順序と状態の移り変わりが多く、業務の決まりが込み入っている。プレビューは1件だけ、適用は見たプレビューを指定する、検証を通らないものは受け付けない、照合の食い違いは警告にとどめる、などの決まりがある。利用者から見た流れと受け入れ基準に落とすと、設計とテストの抜けを防げる。
- 利用者の立場が複数ありうる。アプリの管理者のほかに、DSL を書く人（アプリの外で YAML を書き、業務の側のリポジトリで管理する人）と、対象DB の接続先を設定する運用者がいる。

## 考慮した要素

| 要素 | 内容 |
|---|---|
| 種類 | 既存のアプリへの機能の追加（ブラウンフィールド） |
| 利用者に見える範囲 | 管理画面の新しい機能一式と、DSL の書式（JSON Schema）そのもの |
| 複雑さ | プレビューと適用の状態の移り変わり、同時の操作、検証（構文・意味）、対象DB との照合、履歴 |
| 既存の仕組みとの関係 | 管理者向け領域と認可、監査ログ、エラー応答の形を使う（`aidlc/spaces/default/codekb/mastersmith2/business-overview.md`・`component-inventory.md`） |

## ストーリーが特に役立つところ

- プレビュー → 適用の流れと、同時の操作（見たプレビューが変わっていたら拒否）の受け入れ基準
- 検証を通らない DSL の扱いと、エラーの一覧の見せ方
- DSL の作者から見た、スキーマの書式（何を書けば検証を通るか）
- 対象DB に接続できないときの、各操作の振る舞い
