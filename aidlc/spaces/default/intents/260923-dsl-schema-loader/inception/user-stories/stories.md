# User Stories — dsl-schema-loader

## 前提と読み方

- ペルソナは `personas.md` の P1 管理者・P2 DSL の作者・P3 運用者。
- 形は「〔利用者〕として、〔したいこと〕をしたい。それは〔得られる価値〕のためだ」。受け入れ基準は Given/When/Then。
- 群は操作の流れの順（US1 読み込み → US2 投入 → US3 プレビュー → US4 適用 → US5 履歴・ダウンロード）に、US6 接続・アクセス制御・監査を加えた（Q2: A）。US1 は、生成の規則を作る US1.1 と、MySQL・MariaDB への対応と性能の US1.2 に分けた（M1: A）。
- 優先度は MoSCoW（Q5: B、F1: A）。最初に届ける範囲の線引きは Delivery Planning で決める。
- **DSL のスキーマ定義（要件の FR1）はストーリーにしない。** すべてのストーリーの前提とし、中身はドメイン設計で決める（Q4: B）。
- 各ストーリーの「要件」は `aidlc/spaces/default/intents/260923-dsl-schema-loader/inception/requirements-analysis/requirements.md` の ID。
- 監査の受け入れ基準は、その操作のストーリーに置く。監査の記録の形（必須の項目など）は US6.3 でまとめて確かめる。

### 合否の判定の仕方（すべての受け入れ基準に当てる）

- **判定の場**: 「表示される」は、サーバー側では応答の状態コードと Problem Details の `code` で、画面では表示された文言で判定する。`code` の一覧（大きさの超過・入れ子の深さ・別名の数・タグ・重複キー・構文・意味・版の非対応・対象DB の設定が無い・対象DB に接続できない・プレビューが無い・プレビューが変わった など）は契約の設計で決める。
- **「変わらない」**: プレビュー・適用中の DSL・履歴を持つ内部DB の行と、DSL の識別（ハッシュ値）が、操作の前後で同じであることで確かめる。
- **「含まれない」**: テストの設定で、対象DB の接続先・ユーザー名・パスワードに、ほかと重ならない目印の文字列を入れる。そのうえで、応答の本文・アプリのログ・監査ログの行・生成した DSL・ダウンロードしたファイルのどれにも目印が現れないことで確かめる。部品の例外については、部品に特有の文字列（例外のクラス名・パッケージ名）が応答に無いことで確かめる。
- **対象DB に関わる基準**: 対象DB に接続する基準（AC1.1.x、AC1.2.x、AC3.2.x、AC4.1.5、AC5.1.3）は、MySQL・MariaDB・PostgreSQL の3種類それぞれで確かめる（NFR12）。ただし、US1.1 の中で作るときは最初の1種類で確かめ、残りの2種類は US1.2 で確かめる。
- **性能の基準**（30 秒・10 秒）: API の要求を受けてから応答を返すまで（画面の描画を除く）を、コンテナで起動した対象DB に対して測る。100テーブル・各100カラムの対象DB は、準備のスクリプトで作る。手元で測れないときは、Build and Test で `Unverified` とし、持ち主の段を明記して引き継ぐ。
- **画面の基準の共通の決まり**（すべての画面に当てる）: 文言は ja・en を持つ（NFR9）。すべての操作をキーボードだけで行える。確かめる表示が開いている間はフォーカスが表示の中にとどまり、閉じると開く前の位置に戻る。操作の結果（成功・失敗・処理中）は、読み上げでも伝わる。状態は色だけで示さない。画面での確かめや入力の検査は使いやすさのためで、サーバー側の検証の代わりにしない（NFR3）。
- **時間のかかる操作**（スキーマの読み込み・投入・適用・履歴からの戻し）: 処理中であることを表示し、終わるまで同じ操作と、プレビューを変える操作をもう一度実行できないようにする。二重の実行の最終的な防ぎは、サーバー側の決まり（US4.2）が受け持つ。

## US1 スキーマの読み込み

### US1.1 対象DB のスキーマから既定の DSL を作る（最初の1種類の DB）

P1 管理者として、管理画面の操作で対象DB のスキーマを読み込み、既定の DSL を作りたい。それは、DSL を一から書かずに、対象DB の構造に合った土台を手早く用意するためだ。

- 要件: FR2.1、FR2.4、FR2.5、FR3.1〜FR3.6、FR10.1、NFR4、NFR5、NFR6
- 優先度: Must
- 依存: US6.1（接続先の設定と、2つ目の接続の配線）
- 作業の注記: 対象DB を実際に読む最初のストーリーなので、Testcontainers の導入をここに含める。最初の1種類（例: PostgreSQL）で、生成の規則とエラーの扱いを作り切る。

受け入れ基準:

- **AC1.1.1** Given 対象DB の設定したスキーマに、テーブル2つとビュー1つがある / When 管理者がスキーマの読み込みを実行する / Then 3つとも含む既定の DSL がプレビューに置かれ、ビューは読み取り専用として記録される。設定していない別のスキーマのテーブルは含まれない
- **AC1.1.2** Given コメント「氏名」を持つカラム `name` と、コメントの無いカラム `code` / When 既定の DSL を作る / Then `name` の表示名は ja が「氏名」・en が `name`、`code` の表示名は ja・en とも `code` になる
- **AC1.1.3** Given NOT NULL で長さ 50 の文字列のカラム / When 既定の DSL を作る / Then 必須と最大 50 文字のバリデーションが、DB から導いたものとして記録される
- **AC1.1.4** Given テーブルが `b_table`・`a_table` の順で作られている / When 既定の DSL を作る / Then メニューは1階層で、`a_table`・`b_table` の順に1項目ずつ並ぶ（大文字・小文字と記号の並べ方は機能設計で決め、その規則で確かめる）
- **AC1.1.5** Given 作った既定の DSL / When 構文と意味の検証をする / Then 通る（FR3.6）
- **AC1.1.6** Given 既にプレビューがある / When 管理者がスキーマの読み込みを実行しようとする / Then 今のプレビューを置き換えてよいかを確かめる表示が出る。表示には、今のプレビューの出どころ・置いた管理者・日時が示される。確かめたときだけ読み込みが始まり、プレビューが作った DSL に置き換わって、適用中の DSL は変わらない。取りやめたときは何も変わらない
- **AC1.1.7** Given 対象DB の設定が無い、または対象DB に接続できない / When スキーマの読み込みを実行する / Then 設定が無いのか、接続できないのかを区別した `code` のエラーになる。画面には、運用者に確かめてもらうよう促す案内が出る。応答・表示・ログ・監査ログには、接続先・ユーザー名・パスワードと JDBC の例外のメッセージが含まれない。プレビューと適用中の DSL は変わらない
- **AC1.1.8** Given 対象DB が接続の要求に応答しない / When スキーマの読み込みを実行する / Then 設定した待ち時間（数値は設計で決める）で打ち切られ、対象DB に接続できないことを示すエラーになる
- **AC1.1.9** Given テーブル名・カラム名に、引用符・空白・セミコロンなど SQL の記号を含むテーブルがある / When 既定の DSL を作る / Then そのテーブルも DSL に含まれ、対象DB のほかのテーブルとデータは変わらない（NFR6）
- **AC1.1.10** Given 対象DB のアカウントが読み取りの権限だけを持つ / When 既定の DSL を作る / Then 成功する（対象DB に書き込まないことを、権限で裏付ける）
- **AC1.1.11** Given 管理者が既定の DSL を作った / When 監査ログを見る / Then 生成の出来事が記録されている（形は US6.3）

INVEST: 対象DB の読み取りと DSL の生成までで閉じており、プレビューの表示（US3.1）とは別に確かめられる。生成した DSL がプレビューに置かれたことは、プレビューの有無と識別で確かめる。

### US1.2 MySQL・MariaDB でも、想定の規模で既定の DSL を作る

P1 管理者として、対象DB が MySQL・MariaDB・PostgreSQL のどれでも、想定の規模のスキーマから既定の DSL を待てる時間で作りたい。それは、対象DB の種類や大きさを気にせずに、同じ手順で土台を用意するためだ。

- 要件: FR2.1、FR3.2、NFR1、NFR12
- 優先度: Must
- 依存: US1.1

受け入れ基準:

- **AC1.2.1** Given MySQL・MariaDB・PostgreSQL のそれぞれを対象DB に設定した / When スキーマを読み込む / Then どれでも、US1.1 の AC1.1.1〜AC1.1.5・AC1.1.9 を満たす既定の DSL が作られる
- **AC1.2.2** Given 3種類の DB で、同じ意味の列（文字列・数値・日付・真偽値）を持つテーブル / When 既定の DSL を作る / Then 型の対応の規則（ドメイン設計で決める）のとおりに、フォーム部品とバリデーションが決まる
- **AC1.2.3** Given 100テーブル・各100カラムの対象DB（3種類それぞれ） / When スキーマの読み込みを実行する / Then 30 秒以内に既定の DSL がプレビューに置かれる

INVEST: 種類ごとの型の違いの吸収と性能に絞っている。規則そのものは US1.1 で作る。

## US2 投入

### US2.1 完成品の DSL をアップロードまたは貼り付けで投入する

P1 管理者として、DSL の作者から受け取った完成品の DSL を、ファイルのアップロードかテキストの貼り付けで投入したい。それは、業務の側のリポジトリで直した DSL をアプリに渡し、プレビューで確かめられるようにするためだ。

- 要件: FR4.1、FR4.2、FR4.5、FR10.1、NFR2
- 優先度: Must
- 作業の注記: YAML の読み込みの設定（大きさ・入れ子の深さ・別名の数の上限、タグの拒否、重複キーの誤り）は、このストーリーの最初から入れる。US2.3 はその境界のテストを揃えるストーリーで、同じ回（Bolt）で作る前提とする。投入の API だけ本文の上限を 5MB にする作り（今は全要求に 1MB）も、ここに含める。

受け入れ基準:

- **AC2.1.1** Given 構文と意味の検証を通る DSL のファイル / When 管理者がファイルを選んで投入する / Then その DSL がプレビューに置かれる
- **AC2.1.2** Given 構文と意味の検証を通る DSL の YAML / When 管理者がテキスト欄に貼り付けて投入する / Then その DSL がプレビューに置かれる
- **AC2.1.3** Given 既にプレビューがある / When 管理者が新しい DSL を投入しようとする / Then 今のプレビューを置き換えてよいかを確かめる表示が出る（今のプレビューの出どころ・置いた管理者・日時を示す）。確かめたときだけプレビューが置き換わる。取りやめたときは、プレビューも適用中の DSL も変わらず、選んだファイル・貼り付けた内容は画面に残る（確かめる表示は画面の働きで、サーバーは検証を通れば置き換える）
- **AC2.1.4** Given ファイルを選んでおらず、テキスト欄も空である / When 投入しようとする / Then 投入の操作はできず、ファイルを選ぶか貼り付けるよう案内される
- **AC2.1.5** Given 5MB を超えるファイルを選んだ / When 投入しようとする / Then 送る前に、大きさの上限を超えていることが表示される（サーバー側の拒否は AC2.3.1 で確かめる）
- **AC2.1.6** Given 管理者が DSL を投入し、受け付けられた / When 監査ログを見る / Then 投入の出来事が、アップロードか貼り付けかの区別つきで記録されている（形は US6.3）

### US2.2 検証を通らない DSL の誤りの場所を知る

P2 DSL の作者として、検証を通らない DSL を投入したとき、どこが誤っているかを一覧で知りたい。それは、手元の YAML のどこを直せばよいかをすぐに見つけるためだ。

- 要件: FR1.5、FR1.6、FR4.2、FR4.3、FR10.1、NFR4、NFR5
- 優先度: Must
- 依存: US2.1
- 作業の注記: 複数の誤りを返す応答の形（Problem Details の拡張）のため、バックエンドの `common/error` と画面の `shared/api-client` の両方に手が入る。検証の部品が返す位置を YAML の行・列に直す作りは、この Intent で最も技術的に不確かな点なので、見積もりに余裕を持たせる。

受け入れ基準:

- **AC2.2.1** Given 構文（JSON Schema）の誤りを2件含む DSL（それぞれ1件だけ報告される形の誤り。例: 必須の項目の欠け、型の違い） / When 投入する / Then 2件の誤りが、それぞれ YAML の行・列と、DSL の中の場所（テーブル・カラム・項目）つきで一覧に表示される
- **AC2.2.2** Given DSL に無いテーブルを指すメニュー項目を持つ DSL / When 投入する / Then 意味の誤りとして、そのメニュー項目の場所が表示される
- **AC2.2.3** Given 同じテーブル（または同じテーブルの同じカラム）を2回定義した DSL / When 投入する / Then 意味の誤りとして、2回目の定義の場所が表示される
- **AC2.2.4** Given 外部キー・参照ピッカーの参照先が DSL に無い DSL / When 投入する / Then 意味の誤りとして、その参照の場所が表示される
- **AC2.2.5** Given アプリが対応していない書式の版を名乗る DSL / When 投入する / Then 版が対応していないことが表示される
- **AC2.2.6** Given 対象DB の接続先（接続先・ユーザー名・パスワード）の項目を含む DSL / When 投入する / Then JSON Schema に無い項目の誤りになり、その値は応答・ログ・監査ログに現れない
- **AC2.2.7** Given 構文の誤りと意味の誤りを両方含む DSL / When 投入する / Then どちらを返すかの決まり（機能設計で決める）のとおりになる
- **AC2.2.8** Given 検証を通らない DSL / When 投入する / Then プレビューと適用中の DSL は変わらず、投入した DSL は保存されない。応答と表示には、YAML・JSON Schema の部品の例外のメッセージがそのまま含まれない
- **AC2.2.9** Given 貼り付けた DSL が検証を通らなかった / When 誤りの一覧が表示される / Then 貼り付けた内容はテキスト欄に残り、直してそのまま投入し直せる。ファイルで投入したときは、選んだファイル名が表示されたまま残る。誤りの件数が一覧の先頭に表示され、フォーカスが一覧の先頭に移り、件数が読み上げられる
- **AC2.2.10** Given 検証を通らない DSL を投入した / When 監査ログを見る / Then 受け付けなかった投入の出来事が、理由の種類（構文・意味・版）つきで記録され、DSL の本文は含まれない（M2: A）

INVEST: 誤りが多いとき（例: 100件を超える）の見せ方と、一覧をテキストとして写し取る働き（DSL の作者に伝えるため）は、機能設計で決める。

### US2.3 危険な形の DSL を受け付けない

P1 管理者として、大きすぎる・危険な形の DSL を投入しても、アプリが止まったり想定外の動きをしたりしないようにしたい。それは、誤って（または悪意で）作られたファイルからアプリを守るためだ。

- 要件: FR4.4、FR10.1、NFR2、NFR3、NFR5
- 優先度: Must
- 依存: US2.1（同じ回で作る）
- 注記: 大きさ以外の上限の数値（入れ子の深さ・別名の数）と、応答を返すまでの時間の上限は設計の段で決め、その値の境界で確かめる。5MB は YAML の本文（UTF-8）のバイト数で数え、アップロードと貼り付けで同じ値にする（1MB を何バイトとするかは設計で決める）。

受け入れ基準:

- **AC2.3.1** Given ちょうど 5MB の DSL / When 投入する（アップロード・貼り付けのそれぞれ） / Then 大きさの上限では拒否されない。Given 5MB を1バイト超える DSL / When 投入する / Then 大きさの上限の `code` で拒否される
- **AC2.3.2** Given 別名（アンカー）の数がちょうど上限の DSL / When 投入する / Then 別名の数の上限では拒否されない。Given 別名の数が上限を超える DSL（別名の展開が爆発する形を含む） / When 投入する / Then 別名の数の上限の `code` で拒否され、応答は決めた時間の内に返り、続けて送った別の要求も普通に処理される
- **AC2.3.3** Given 入れ子の深さがちょうど上限の DSL / When 投入する / Then 深さの上限では拒否されない。Given 上限を超える DSL / When 投入する / Then 深さの上限の `code` で拒否される
- **AC2.3.4** Given 任意の型を作るタグを含む DSL（テスト用の、呼ばれたら記録するクラスを指すタグ） / When 投入する / Then タグの `code` で拒否され、記録は0件（型は作られない）
- **AC2.3.5** Given 同じキーが2回現れる DSL / When 投入する / Then 重複したキーの `code` の誤りになり、後の値で黙って上書きされない
- **AC2.3.6** Given `$ref` のキーを含む DSL / When 投入する / Then JSON Schema に無い項目の誤りになり、外部への接続は起きない（テストで立てた、要求を数えるだけの受け口への要求は0件）
- **AC2.3.7** Given アプリの JSON Schema / When 検証の部品を用意する / Then JSON Schema はアプリに同梱したものだけから読み、外部の URL の取得は無効になっている（外部を指す `$ref` を含むスキーマを与えると、取りに行かずに失敗する）
- **AC2.3.8** Given 上の各理由で拒否される DSL / When 投入する / Then 応答は Problem Details の形で、理由ごとに別の `code` を持ち、YAML・JSON Schema の部品の例外のメッセージを含まない
- **AC2.3.9** Given DSL の投入以外の API / When 1MB を超える本文を送る / Then 今までどおり 413 になる（5MB は投入に限る）
- **AC2.3.10** Given 上の各理由で拒否される DSL / When 監査ログを見る / Then 受け付けなかった投入の出来事が、理由の種類つきで記録され、DSL の本文は含まれない（M2: A）

## US3 プレビュー

### US3.1 プレビューで DSL の要約と、適用中との違いを確かめる

P1 管理者として、適用の前に、プレビュー中の DSL の要約と、適用中の DSL との違いを見たい。それは、YAML を読み比べなくても、何が変わるかを確かめてから適用するためだ。

- 要件: FR5.1、FR7.1
- 優先度: Must
- 依存: US1.1 または US2.1
- 作業の注記: 適用のときに「見たプレビュー」を指定できるよう、プレビューの応答にプレビューの識別（版の値やハッシュ値）を含める（US4.1・US4.2 が使う）。違いの表示の部品は make-you-chic-ui に無いため、画面の側で作る。

受け入れ基準:

- **AC3.1.1** Given プレビュー中の DSL がある / When プレビューを表示する / Then 検証を通ったこと、テーブル数・カラム数、メニューの階層の木が表示される
- **AC3.1.2** Given en の表示名が空のカラムが1つあるプレビュー / When プレビューを表示する / Then 埋まっていない表示名が1件と、その場所が示される
- **AC3.1.3** Given 適用中の DSL にあるテーブル1つを除き、新しいテーブル1つを足したプレビュー / When プレビューを表示する / Then 減ったテーブルと増えたテーブルがそれぞれ1つ示される
- **AC3.1.4** Given 適用中とプレビューの両方にあるテーブルで、カラムを1つ足し1つ除き、別のカラムの表示名を変えた / When プレビューを表示する / Then そのテーブルの中で、増えたカラム・減ったカラム・変わったカラムがそれぞれ1つ示される（「変わった」に数える項目は機能設計で決める）
- **AC3.1.5** Given 適用中の DSL がまだ無い / When プレビューを表示する / Then すべてのテーブルとカラムが「増えた」として示される
- **AC3.1.6** Given プレビュー中の DSL がある / When プレビューを表示する / Then その出どころ（生成・アップロード・貼り付け・履歴からの戻し）、置いた管理者、置いた日時、DSL の識別が表示される
- **AC3.1.7** Given DSL の操作の画面を開く / When 画面が表示される / Then 適用中の DSL の識別・適用した管理者・適用した日時が表示される。適用中の DSL が無いときはまだ適用していないこと、プレビューが無いときはプレビューが無いことと読み込み・投入の操作への案内が表示される

### US3.2 プレビューで対象DB との食い違いを知る

P1 管理者として、プレビュー中の DSL が対象DB の今の構造と食い違っていないかを知りたい。それは、別の環境の DSL や古い DSL を、気づかずに適用しないためだ。

- 要件: FR5.2、FR2.4、FR2.5、NFR1、NFR4、NFR5
- 優先度: Must
- 依存: US3.1、US6.1

受け入れ基準:

- **AC3.2.1** Given 対象DB に無いテーブルを含む DSL / When プレビューに置く / Then そのテーブルについての警告が表示される
- **AC3.2.2** Given 対象DB に無いカラムを含む DSL / When プレビューに置く / Then そのカラムについての警告が表示される
- **AC3.2.3** Given 対象DB と型が食い違うカラムを含む DSL / When プレビューに置く / Then 型の食い違いの警告が表示される（型の対応の規則で判定する。DSL が DB 上の型を持たない設計になったら、この基準を見直す）
- **AC3.2.4** Given 対象DB に接続できない、または接続の要求に応答しない / When DSL をプレビューに置く / Then 設定した待ち時間の内に照合を打ち切り、照合できなかったことが警告として表示され、プレビューには置かれる。警告には、接続先と JDBC の例外のメッセージが含まれない
- **AC3.2.5** Given 100テーブル・各100カラムの DSL と、同じ規模の対象DB / When 投入する / Then 10 秒以内に検証と対象DB との照合が終わり、プレビューに置かれる
- **AC3.2.6** Given 照合を行った / When 対象DB を調べる / Then 対象DB のテーブル・ビューの一覧と各テーブルの行数は、照合の前後で同じ

INVEST: 警告があっても適用は止めない（要件の Q7）。警告を見落として適用しないための確かめは、適用の確認の表示（AC4.1.2）で行う。

### US3.3 プレビューを適用せずに捨てる

P1 管理者として、確かめた結果、適用しないと決めたプレビューを捨てたい。それは、誤った DSL がプレビューに残って、後で誤って適用されないようにするためだ。

- 要件: FR5.3、FR10.1
- 優先度: Must
- 依存: US3.1

受け入れ基準:

- **AC3.3.1** Given プレビューがある / When 管理者が破棄しようとする / Then 破棄してよいかを確かめる表示が出て、確かめたときだけ破棄される（M4: A）。取りやめたときは何も変わらない
- **AC3.3.2** Given プレビューがある / When 管理者が破棄を確かめる / Then プレビューは無くなり、適用中の DSL は変わらない
- **AC3.3.3** Given プレビューが既に破棄されている（別の管理者が破棄した） / When 破棄する / Then プレビューが無いことを示す `code` のエラーになり、適用中の DSL は変わらない
- **AC3.3.4** Given 管理者がプレビューを破棄した / When 監査ログを見る / Then 破棄の出来事が記録されている（形は US6.3）

### US3.4 プレビュー中の DSL をファイルとして取り出す

P2 DSL の作者として、プレビュー中の DSL（生成した既定の DSL など）を YAML のファイルとして取り出したい。それは、手元で業務に合わせて直し、業務の側のリポジトリで管理するためだ。

- 要件: FR8.1（プレビュー中の DSL）、NFR4
- 優先度: Must（F1: A）
- 依存: US3.1
- 作業の注記: プレビュー・適用中の DSL は YAML の本文として保存し、ダウンロードは保存した本文をそのまま返す。生成した既定の DSL も、生成の時点で YAML の本文にしてから保存する。

受け入れ基準:

- **AC3.4.1** Given 既定の DSL がプレビューにある / When ダウンロードする / Then その DSL の YAML のファイルが得られる
- **AC3.4.2** Given ダウンロードした YAML のファイル / When そのまま投入する / Then 検証を通り、プレビューの DSL の識別（ハッシュ値）が元と同じになる
- **AC3.4.3** Given プレビューが無い / When ダウンロードしようとする / Then プレビューが無いことを示す `code` のエラーになり、ファイルは得られない
- **AC3.4.4** Given プレビュー中の DSL / When ダウンロードする / Then ファイルに対象DB の接続先（接続先・ユーザー名・パスワード）は含まれない
- **AC3.4.5** Given プレビュー中の DSL をダウンロードした / When ファイル名を見る / Then プレビュー中のものであることと、DSL の識別が分かる名前になっている（具体的な形は機能設計で決める）

## US4 適用

### US4.1 確かめたプレビューを適用する

P1 管理者として、確かめたプレビューを適用し、アプリが使う DSL を切り替えたい。それは、確かめた内容だけを業務の画面の元として使うためだ。

- 要件: FR6.1、FR6.3、FR6.4、FR7.1、FR7.3、FR2.5、FR3.6、FR10.1〜FR10.3
- 優先度: Must
- 依存: US3.1
- 作業の注記: 履歴の書き込みと件数の切り詰めは、適用の処理の一部として同じトランザクションで行う（US5.1 を後回しにしても、戻す先の履歴が残るように）。後続の Intent（I・J・K）が使う、適用中の内部のモデルの提供口（名前は設計で決める）を1つ用意する。

受け入れ基準:

- **AC4.1.1** Given プレビュー中の DSL がある / When 管理者が適用を確かめる / Then 適用中の DSL がその内容に切り替わり、プレビューは無くなり、履歴に1件足される。画面には成功したことが通知され、適用中の DSL の表示が新しい版に変わる
- **AC4.1.2** Given プレビュー中の DSL がある / When 管理者が適用しようとする / Then 適用してよいかを確かめる表示が出て、違いの件数（増えた・減った・変わったテーブルとカラムの数）と、対象DB との照合の警告の件数が示される。確かめたときだけ適用され、取りやめたときは何も変わらない（M4: A）
- **AC4.1.3** Given 人が手で直した内容を含む DSL が適用中で、既定の DSL をプレビューに置いた / When 適用する / Then 適用中の DSL は既定の DSL の内容に全部置き換わる（差分のマージはしない）
- **AC4.1.4** Given DSL を適用した / When 再起動せずに、提供口から適用中のモデルを取り出す / Then 適用した DSL のメニュー・テーブル・カラムの定義が得られる
- **AC4.1.5** Given DSL を適用した / When アプリを再起動し、提供口から適用中のモデルを取り出す / Then 同じ DSL が適用中で、同じモデルが得られる
- **AC4.1.6** Given 適用中の DSL が無い / When アプリを起動し、提供口から取り出す / Then 起動し、適用中のモデルが無いことが分かる形で返る
- **AC4.1.7** Given DSL を適用した / When 対象DB を調べる / Then 対象DB のテーブル・ビューの一覧と各テーブルの行数は、適用の前後で同じ
- **AC4.1.8** Given 履歴が上限より1件少ない（既定 19件） / When 適用する / Then 履歴は 20件になり、何も消えない。Given 履歴が上限ちょうど（既定 20件） / When 適用する / Then 最も古い1件が消え、20件のまま
- **AC4.1.9** Given 適用中の DSL と同じ内容（同じハッシュ値）のプレビュー / When 適用する / Then 適用は成功し、履歴に1件足される（M3: A）
- **AC4.1.10** Given 管理者が DSL を適用した / When 監査ログを見る / Then 適用の出来事が記録されている（形は US6.3）

### US4.2 ほかの管理者が置き換えたプレビューを誤って適用しない

P1 管理者として、自分が確かめた後にほかの管理者がプレビューを置き換えたときは、適用を止めてほしい。それは、確かめていない内容を業務の画面に反映しないためだ。

- 要件: FR6.2、NFR8、FR10.3
- 優先度: Must
- 依存: US4.1

受け入れ基準:

- **AC4.2.1** Given 管理者 A がプレビュー（識別 X）を表示した後に、管理者 B が別の DSL を投入してプレビューを置き換えた / When 管理者 A が識別 X を指定して適用する / Then 「プレビューが変わった」の `code` で拒否され、適用中の DSL は変わらない。画面には、最新のプレビューを表示し直す操作が示され、それを選ぶと新しいプレビュー（出どころ・置いた管理者を含む）が表示される。新しいプレビューが自動で適用されることはない
- **AC4.2.2** Given 管理者 A がプレビューを表示した後に、管理者 B がプレビューを破棄した / When 管理者 A が適用する / Then 拒否され、適用中の DSL は変わらない。画面には、プレビューが無いことと、読み込み・投入の操作への案内が表示される
- **AC4.2.3** Given 同じプレビューを、管理者 A と管理者 B が同時に適用する / When 両方の要求が処理される / Then 一方だけが成功し、他方は拒否され、履歴は1件だけ足される（待ち合わせを使って重なりを確実に作る）
- **AC4.2.4** Given 適用の途中（テストで差し込む、履歴の書き込みでの失敗）で失敗が起きた / When 適用中の DSL・履歴・プレビューと、提供口のモデルを調べる / Then どれも適用の前のままで、一部だけ切り替わった状態は残らない。適用の監査の出来事は記録されない

## US5 履歴・ダウンロード

### US5.1 前に適用した版に戻す

P1 管理者として、前に適用した DSL の版を選んでプレビューに戻し、もう一度適用したい。それは、新しい DSL に問題があったときに、すぐに前の状態に戻すためだ。

- 要件: FR7.1、FR7.2、FR10.1
- 優先度: Should
- 依存: US4.1（履歴の書き込みは US4.1 が行う）

受け入れ基準:

- **AC5.1.1** Given 3回適用した / When 履歴を表示する / Then 3件が、適用した日時・適用した人・DSL の識別つきで、新しい順に表示される。今適用中の版は、色だけでなく文字（例: 「適用中」）で示される
- **AC5.1.2** Given まだ一度も適用していない / When 履歴を表示する / Then 履歴が無いことが表示される
- **AC5.1.3** Given 履歴に2つ前の版がある / When その版をプレビューに戻して適用する / Then 適用中の DSL がその版の内容になる
- **AC5.1.4** Given 既にプレビューがある / When 管理者が履歴の版をプレビューに戻そうとする / Then 今のプレビューを置き換えてよいかを確かめる表示が出て、確かめたときだけ置き換わる
- **AC5.1.5** Given 履歴から戻した版に、今の対象DB に無いカラムがある / When プレビューに戻す / Then 対象DB との食い違いの警告が表示される
- **AC5.1.6** Given 履歴から戻した版が、今のアプリの検証を通らない（例: 版が対応していない） / When プレビューに戻す / Then 投入と同じ誤りの一覧が返り、プレビューは変わらない
- **AC5.1.7** Given 管理者が履歴の版をプレビューに戻した / When 監査ログを見る / Then 投入の一種（履歴からの戻し）として記録されている（要件の前提 A2、形は US6.3）

INVEST: 日時は表示言語に合わせた書式で、時差が分かる形で表示する（保存は UTC）。書式は機能設計で決める。

### US5.2 適用中の DSL をファイルとして取り出す

P2 DSL の作者として、適用中の DSL を YAML のファイルとして取り出したい。それは、アプリの中で動いている DSL と、業務の側のリポジトリの正本が同じかを確かめるためだ。

- 要件: FR8.1（適用中の DSL）、NFR4
- 優先度: Should
- 依存: US4.1

受け入れ基準:

- **AC5.2.1** Given 適用中の DSL がある / When ダウンロードする / Then その DSL の YAML のファイルが得られ、その識別は適用中の DSL と同じ
- **AC5.2.2** Given 適用中の DSL がまだ無い / When ダウンロードしようとする / Then 適用中の DSL が無いことを示す `code` のエラーになり、ファイルは得られない
- **AC5.2.3** Given 適用中の DSL をダウンロードした / When ファイル名とファイルの中身を見る / Then 適用中のものであることと DSL の識別が分かる名前で、プレビュー中のものの名前と区別でき、対象DB の接続先は含まれない

## US6 接続・アクセス制御・監査

### US6.1 対象DB の接続先を設定し、対象DB の障害にアプリを巻き込まない

P3 運用者として、対象DB の接続先を設定ファイルと環境変数で設定し、対象DB が無い・止まっているときもアプリを起動したままにしたい。それは、秘密情報を漏らさずに接続し、対象DB の障害でログインや管理画面まで止めないためだ。

- 要件: FR2.1〜FR2.4、NFR4、NFR7
- 優先度: Must
- 作業の注記: 対象DB 用の2つ目の接続（`DataSource`）を足しても、内部DB の自動構成・JPA・Flyway・ヘルスチェック・名前の指定の無い `@Transactional`・ログインのトランザクションが内部DB を指し続ける配線を、ここに含める。スキーマの読み込み無しで確かめられる基準だけを置く（スキーマの読み込みの基準は US1.1・US1.2）。

受け入れ基準:

- **AC6.1.1** Given 対象DB の接続先を設定していない / When アプリを起動する / Then 起動し、ヘルスチェックは正常を返し、ログインと管理画面が使える
- **AC6.1.2** Given 対象DB が止まっている / When アプリを起動し、ヘルスチェックを要求する / Then 起動し、ヘルスチェックは正常を返し、応答に対象DB の状態は含まれない
- **AC6.1.3** Given 対象DB の接続先を設定した / When ログインし、監査ログが記録される / Then 監査の行は内部DB の `audit_events` にあり、対象DB には Flyway の履歴の表もアプリの表も作られていない
- **AC6.1.4** Given 対象DB の接続先とパスワード（環境変数）を設定した / When 接続先の設定の型を文字列にする（メソッドの追跡の TRACE のログを含む） / Then パスワードは伏せ字になり、値はログに出ない
- **AC6.1.5** Given 対象DB の接続先の設定の一部（例: スキーマ名）が欠けている、または種類が対応外である / When アプリを起動する / Then アプリは起動し、アプリのログに、どの設定の項目名（例: `mastersmith.target-db.schema`）に問題があるかが WARN で1件出る。項目の値（接続先・ユーザー名・パスワード）はログに含まれない

INVEST: 対象DB の設定が不正なときも起動する扱いは、要件の Q12（設定が無くても起動する）に合わせた読み方である。

### US6.2 DSL の操作を管理者だけに限る

P1 管理者として、DSL の読み込み・投入・プレビュー・適用・破棄・履歴・ダウンロードを、管理者だけが行えるようにしたい。それは、業務の画面の元になる DSL を、権限の無い人に変えられないようにするためだ。

- 要件: FR9.1〜FR9.3、NFR9、NFR10
- 優先度: Must
- 依存: 各操作のストーリー（それぞれの API ができたときに、その API で確かめる。すべての API を並べた一括の確かめは、最後の API（Should の US5.1・US5.2 を含む）ができるまで閉じない）

受け入れ基準:

- **AC6.2.1** Given ログインしていない / When DSL のすべての操作の API（スキーマの読み込み、投入（アップロード・貼り付け）、プレビューの取得、適用、破棄、履歴の一覧、履歴からの戻し、プレビュー中・適用中のダウンロード）をそれぞれ呼ぶ / Then どれも 401 が返り、内部DB の状態は変わらない
- **AC6.2.2** Given 管理者フラグの無い利用者 / When 同じすべての操作の API をそれぞれ呼ぶ / Then どれも 403 が返り、内部DB の状態は変わらず、アクセス拒否（`ACCESS_DENIED`）の監査の出来事が記録される
- **AC6.2.3** Given 管理者 / When 同じすべての操作の API をそれぞれ（前提の状態を用意して）呼ぶ / Then どれも成功する
- **AC6.2.4** Given 管理者 / When 管理画面を開く / Then DSL の操作の画面への入り口が管理者向け領域に表示される。管理者でない利用者には表示されない
- **AC6.2.5** Given 既存の画面と同じ言語の切り替えの方法で英語にした / When DSL の操作の画面を表示する / Then 画面の文言（誤り・警告・案内を含む）が英語で表示される。テーブル名・カラム名などの物理名は訳さない
- **AC6.2.6** Given DSL の操作の画面の各部品 / When アクセシビリティ検査（axe）を行う / Then 違反が0件

### US6.3 DSL の操作の監査の記録を、決まった形で残す

P3 運用者として、DSL の操作の監査の記録が、必要な項目を漏れなく持ち、秘密情報を含まない形で残ってほしい。それは、業務の画面の元が変わった経緯を、後から安心して確かめられるようにするためだ。

- 要件: FR10.1〜FR10.3、NFR4
- 優先度: Must
- 依存: US1.1、US2.1、US3.3、US4.1（各操作のストーリーが、自分の出来事の記録を受け入れ基準に持つ）
- 作業の注記: 今の監査の表（`audit_events`）には、操作した利用者と操作の対象（DSL の識別）を入れる列が無いため、Flyway の移行で列を足し、出来事の種類を広げる。この作業は、最初に監査を書くストーリーの回に含める。この Intent では、監査ログを画面で見る働きは作らない（確かめは内部DB の記録で行う）。

受け入れ基準:

- **AC6.3.1** Given 生成・投入（アップロード・貼り付け・履歴からの戻し）・受け付けなかった投入・適用・破棄のそれぞれ / When 監査ログを見る / Then どの出来事も、操作した管理者・日時・出来事の種類・DSL の識別（受け付けなかった投入は理由の種類）を持つ
- **AC6.3.2** Given 上のすべての出来事 / When 監査ログを見る / Then DSL の本文と、対象DB の接続先・ユーザー名・パスワードは含まれない
- **AC6.3.3** Given 監査ログの書き込みに失敗した / When DSL を適用する / Then 適用は成功し、書き込みの失敗はアプリのログに1件出る。そのログにも DSL の本文と接続先は含まれない
- **AC6.3.4** Given 適用が失敗して巻き戻った / When 監査ログを見る / Then 適用の出来事は記録されていない（確定の後に記録する決まり）

## INVEST の確認

- **独立**: 各ストーリーは1つの操作と、その結果の状態で閉じている。依存は一覧の「依存」の列のとおりで、循環は無い。US2.1 と US2.3 は、読み込みの設定を共有するため同じ回で作る前提とする。
- **小ささ**: 大きかった US1.1 は、1種類の DB で規則を作る US1.1 と、種類の違いと性能の US1.2 に分けた（M1: A）。最も技術的に不確かなのは US2.2（誤りの位置を行・列に直す作り）で、見積もりに余裕を持たせる。
- **テストできること**: 受け入れ基準は、サーバー側のテスト（結合テストを含む）か画面の部品のテストで確かめられる形にした。性能の基準（AC1.2.3・AC3.2.5）は、測る条件を「合否の判定の仕方」に書いた。測る場（`verify` の中か Build and Test か）は NFR 要件・Build and Test で決め、手元で測れないときは `Unverified` で引き継ぐ。
- **性質ベースのテストの候補**（設計の段で扱う）: 違いの計算（同じ DSL どうしなら違いは0件、入れ替えると増減が逆になる）、履歴の件数の切り詰め（何回適用しても上限を超えない）、既定の表示名の導き方、メニューの並び順、ダウンロード → 投入の往復で識別が同じ。
