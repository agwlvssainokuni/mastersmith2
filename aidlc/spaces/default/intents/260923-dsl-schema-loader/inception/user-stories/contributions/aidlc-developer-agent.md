## Contribution

開発の立場から、初稿（`stories.md`・`personas.md`）を、既存の構成の上で作れるか（実装の見通し）と、ストーリーの大きさの観点で見た。確かめた根拠は、コード知識ベース（`aidlc/spaces/default/codekb/mastersmith2/` の `architecture.md`・`code-quality-assessment.md` の C-1〜C-10）と、読み取りだけで確かめた既存のソース（`backend/src/main/resources/db/migration/V4__u4_audit_event.sql`・`backend/src/main/java/cherry/mastersmith/common/web/RequestSizeLimitFilter.java`・`backend/src/main/resources/application.yaml`・`backend/src/main/java/cherry/mastersmith/access/domain/AdminPaths.java`・`frontend/src/app/i18n/resolveLanguage.ts`）である。要件で依頼者が決めたこと（群の分け方、FR1 をストーリーにしないこと、優先度、粒度 12〜15件程度）は覆さない。

### 1. 全体の見通し

- どのストーリーも、既存の決まり（`web`・`service`・`domain`・`repository` の層と ArchUnit、`/api/admin/**` に置けば管理者のみになる `AdminPaths`、Problem Details と `code`、内部DB の H2 と Flyway の前進のみの移行、確定の後に別トランザクションで書く監査）の上に載せられる。決まりを変える必要のあるストーリーは無い。
- ただし、次の4点は既存の仕組みを「広げる」作業で、最初にそれを使うストーリーの大きさに効く。どのストーリーに入るかを明記しておくと、Delivery Planning で見積もりがぶれない。
  - **2つ目の `DataSource`**（C-2）: 対象DB 用の接続を足しても、自動構成の内部DB の `DataSource`・JPA・Flyway・ヘルスチェック・名前の指定の無い `@Transactional`・`LoginService` の `PlatformTransactionManager` が内部DB を指し続ける配線が要る。→ US6.1 に入る。
  - **Testcontainers と3種類の DB のイメージ**（C-4）: 依存の追加、`verify` の結合テストの段への組み込み、colima と CI の前提の文書化。→ 対象DB を実際に読む最初のストーリー（US1.1）に入る。
  - **複数のエラーを返す応答の形**（C-6）: 今の Problem Details の拡張の項目は `code`・`traceId` だけで、画面の `ApiError` も本文のほかの項目を渡さない。行・列つきの一覧を返すには、バックエンドの `common/error` と画面の `shared/api-client` の両方に手が入る。→ US2.2 に入る。
  - **監査の表と種類の拡張**（C-8、TD-2）: `audit_events`（V4）には、操作した利用者を指す列も、操作の対象（DSL の識別）を入れる列も無い（今あるのは `entered_email`・`failure_reason`・`request_path` など認証向けの列）。Flyway の V5 以降で列を足し、`AuditEventType`・`AuditEventFactory`・`AuditEventListener` の網羅の `switch` を広げる必要がある。→ US6.3（または下の 7. の案では最初に監査を書くストーリー）に入る。

### 2. 依存の循環の解消（US1.1 と US6.1）

初稿では US1.1 が US6.1 に依存する一方、US6.1 の AC6.1.1・AC6.1.5・AC6.1.6 は「スキーマを読み込む」ことで確かめる形になっており、US1.1 ができるまで US6.1 を確かめられない（実質の循環）。次のように受け入れ基準を移すと、US6.1 → US1.1 の一方向になる。

- **US6.1 に残す（スキーマの読み込み無しで確かめられるもの）**: AC6.1.2（設定が無くても起動・ヘルスチェック正常・ログインと管理画面が使える）、AC6.1.3（対象DB が止まっていても起動・ヘルスチェック正常）、AC6.1.4（ログインと監査は内部DB に対して行われる）。
- **US6.1 に足す案**:
  - Given 対象DB の接続先とパスワード（環境変数）を設定した / When 設定の値をログに出す（メソッドの追跡 `TraceAspect` の TRACE を含む）/ Then パスワードは伏せ字になり、値は出ない（TD-4 の決まりを対象DB の設定の型にも当てる）
  - Given 対象DB が止まっている / When ヘルスチェックを要求する / Then 応答の中に対象DB の状態は含まれず、内部DB だけで判断される（NFR7 の確かめ方を明示）
- **US1.1（または下の US1.2）へ移す**: AC6.1.1（設定したスキーマが読まれる）、AC6.1.5（接続できないときに接続先・ユーザー名・パスワードが表示・応答・ログ・監査ログに含まれない）、AC6.1.6（3種類の DB のどれでも既定の DSL が作られる）。

### 3. US1.1 の分け方（大きすぎる）

US1.1 は、メタデータの読み取り（3種類の DB で型の表し方・コメントの取り方・ビューの見分け方が違う）、型から部品・バリデーションへの対応の規則、生成、プレビューへの保存、30 秒の性能、を1つに抱えており、初稿の中で最も大きい。Q3 の粒度（1ストーリーが数日）に収めるには、DB の種類で分けるのが自然である（どちらも Must のまま）。

- **US1.1 対象DB のスキーマから既定の DSL を作る（1種類の DB で規則を確かめる）**: AC1.1.1〜AC1.1.5 と、2. で移した AC6.1.1・AC6.1.5。最初の1種類（例: PostgreSQL）で、生成の規則とエラーの扱いを作り切る。Testcontainers の導入もここに入る。
- **US1.2（新）MySQL・MariaDB でも既定の DSL を作れ、想定規模で間に合う**: 2. で移した AC6.1.6 と、AC1.1.6（30 秒）。種類ごとの型の違いの吸収と、100 テーブル × 100 カラムでの性能を確かめる。
  - 価値: 対象DB の種類を問わず同じ土台が得られる（FR2.1 の「種類は MySQL・MariaDB・PostgreSQL のいずれか」）。
  - 依存: US1.1

これで件数は 16 件になる（Q3 の「12〜15件程度」を1件超える）。超えたくない場合は、US1.2 を作らずに US1.1 を大きいまま残し、Delivery Planning で US1.1 を2つの Bolt に分ける、という扱いもできる（判断は依頼者に）。

### 4. 対象DB が応答しないときの待ち時間

AC1.1.5・AC3.2.4 は「接続できない」場合だが、対象DB が止まっているのではなく応答しない（接続の要求が返らない）場合、JDBC の既定では長く待つことがある。すると、投入（10 秒・NFR1）もスキーマの読み込みも、対象DB の障害に引きずられる。受け入れ基準に待ち時間の上限を入れておくと、設計で接続・問い合わせの待ち時間を必ず決めることになる。

- US3.2 に足す案: Given 対象DB が接続の要求に応答しない / When DSL をプレビューに置く / Then 設定した待ち時間（数値は設計で決める）で照合を打ち切り、照合できなかったことの警告つきでプレビューに置かれる
- US1.1 に足す案: Given 対象DB が接続の要求に応答しない / When スキーマの読み込みを実行する / Then 設定した待ち時間で打ち切られ、対象DB に接続できないことを示すエラーになる

### 5. 受け入れ基準の書き直しの案（実装の都合で確かめ方が決まらないもの）

- **AC4.1.4（内部のモデルを取り出す）**: 「アプリの中から取り出す」では、何を呼べば合格かが決まらない。後続の Intent（I・J・K）が使う提供口（Spring の Bean のインターフェース。名前は設計で決める）を1つ決め、それで確かめる形にする。
  - 案: Given DSL を適用した / When 後続の Intent 向けの提供口から適用中のモデルを取り出す / Then 適用した DSL のメニュー・テーブル・カラムの定義が得られる。適用中の DSL が無いときは「無い」ことが分かる形で返る
  - あわせて AC4.1.3 に「再起動の後も、提供口から同じモデルが得られる」を足す（起動時の読み込み、FR6.3）。結合テストでは、同じ H2 のファイルに対してアプリの起動を2回行えば確かめられる（既存の `TestDatabase` の一時ディレクトリの仕組みで作れる）。
- **AC4.2.3（適用の途中の失敗）**: DB の状態（適用中の DSL・履歴・プレビュー）に加えて、**メモリ上の内部のモデル**も切り替わらないことを含める。モデルの差し替えは確定の後に行う必要があり、DB の巻き戻しだけでは確かめられないため。失敗の起こし方は、テストで差し替えられる継ぎ目（例: 履歴の書き込みの部品）を設計で用意する。
  - 案: Given 適用の途中（履歴の書き込み）で失敗が起きた / When 適用中の DSL・履歴・プレビューと、提供口のモデルを調べる / Then どれも適用の前のままである
- **US4.2 に足す案（同時の適用）**: Given 2人の管理者が同じプレビューを同時に適用する / When 両方の要求が処理される / Then 1件だけ成功し、もう1件はプレビューが無い（変わった）として拒否され、履歴は1件だけ増える。FR6.2 の「見たプレビューを指定して適用する」には、プレビューの識別（版の値）を US3.1 の表示の応答に含める必要がある（US4.1・US4.2 が US3.1 の応答の形に依存する）。
- **AC2.3.6（外部の `$ref`）**: 投入された DSL は検証される側（インスタンス）であり、JSON Schema の検証の部品はインスタンスの中の `$ref` を解決しない。このため初稿の書き方では、何も作らなくても合格してしまう。危険があるのはアプリが持つ JSON Schema を読み込む側である。2つに分ける。
  - 案1: Given `$ref` のキーを含む DSL / When 投入する / Then スキーマに無い項目として検証の誤りになり、外部への接続は起きない
  - 案2: Given アプリの JSON Schema / When 検証の部品を用意する / Then スキーマはアプリに同梱したものだけから読み、外部の URL の取得は無効になっている（外部を指す `$ref` を含むスキーマを与えると、取りに行かずに失敗する）
- **AC2.3.2（別名の展開）**: 「処理は上限の範囲で打ち切られる」は確かめ方が決まらない。拒否の応答が Problem Details の `code` で返ること、および別名の爆発の形（いわゆる billion laughs）を与えても決まった時間（数値は設計で決める）の中で応答が返ること、の2点で確かめる形にする。
- **AC2.3.1（5MB）**: 実装では次の3点が絡むので、受け入れ基準に「上限ちょうどは受け付ける」を足し（`team.md` の Testing Posture の必須のテスト）、5MB が何の大きさかを決めておく。
  - 今の `RequestSizeLimitFilter` は全要求に1つの上限（既定 1MB）を当てるため、DSL の投入の API だけ 5MB にする作りが要る（C-7）。
  - マルチパートの上限は `application.yaml` に設定が無く、Spring Boot の既定（1ファイル 1MB）のまま。
  - 貼り付けを JSON の本文で送ると、改行や引用符の書き換えで本文が YAML より大きくなる。
  - 案: 「5MB は YAML の本文（UTF-8）のバイト数で数える。5MB ちょうどの YAML はアップロード・貼り付けのどちらでも受け付け、1バイト超えると拒否される」
- **AC3.4.2（ダウンロードしたものをそのまま投入）**: 「同じ内容」を何で比べるかを決める。プレビュー・適用中の DSL を YAML の本文として保存し、ダウンロードは保存した本文をそのまま返す作りにすると、「投入し直すと DSL の識別（ハッシュ値）が同じになる」で確かめられる。生成した既定の DSL も、生成の時点で YAML の本文にしてから保存する。
- **AC3.2.2（型の食い違い）**: DSL がカラムの DB 上の型を持つことが前提になる。持つかどうかはドメイン設計（OQ2）で決めるため、持たない設計になった場合はこの受け入れ基準を見直す、と注記しておく。
- **AC2.1.3（置き換えの確認）**: 確認の表示は画面だけの働きで、サーバーは検証を通れば必ず置き換える（FR4.5）。画面の部品のテストで確かめるものである、と注記しておく（サーバー側のテストで確かめようとして迷わないように）。
- **AC2.2.1（2件の誤り）**: JSON Schema の検証の部品は、1か所の誤りから複数の報告を出すことがある（`oneOf` などの組み合わせ）。テストの DSL は、それぞれ1件だけ報告される形の誤り（例: 必須の項目の欠け、型の違い）を選ぶ、と注記しておく。また、構文の誤りの「場所」は検証の部品からは JSON の位置（パス）で得られ、行・列に直すには YAML の解析の位置の情報と対応づける作りが要る（OQ3）。この Intent で最も技術的に不確かな点なので、US2.2 は見積もりに余裕を持たせる。

### 6. 履歴の記録は適用に入れる（US4.1 と US5.1）

FR7.1（適用した DSL を履歴に残す）と FR7.3（20件を超えたら古いものから消す）は、適用の処理の一部として同じトランザクションで行うものである（NFR8、AC4.2.3 でも履歴を一度に切り替える対象にしている）。初稿では AC5.1.4（20件の切り詰め）が US5.1（Should）にあるため、US5.1 を後回しにすると、適用しても履歴が残らない版を届けることになり、後で US5.1 を作ったときに戻す先が無い。

- 案: 履歴の書き込みと切り詰め（AC5.1.4）を US4.1 に移す。US5.1 は「履歴を一覧で見る（AC5.1.1）」「前の版をプレビューに戻して適用する（AC5.1.2・AC5.1.3）」に絞る。

### 7. 監査の受け入れ基準の置き場所（US6.3）

US6.3 は US1.1・US2.1・US3.3・US4.1 の後にまとめて来る形で、Must の操作が監査なしで「完成」扱いになりうる。一方、監査の表と種類の拡張（1. の4点目）は一度だけ行う作業である。次のどちらかにすると、各操作のストーリーが監査まで含めて閉じる。

- 案A（推奨）: 各操作のストーリーに、その操作の監査の受け入れ基準を移す（AC6.3.1 → US1.1、AC6.3.2 → US2.1、AC6.3.3・AC6.3.5 → US4.1、AC6.3.4 → US3.3）。US6.3 は「監査の記録に必須の項目（誰が・いつ・何を・DSL の識別）が揃い、DSL の本文と接続先を含まない」ことの横断の確認として残すか、各ストーリーに吸収して無くす。表と種類の拡張は、最初に監査を書くストーリーの作業に入れる。
- 案B: US6.3 をそのまま残し、Delivery Planning で US4.1 と同じ Bolt に入れることを前提として書く。

どちらでも、AC6.3.2 の「履歴からの戻し」の監査（前提 A2）は US5.1（Should）の操作なので、US5.1 の受け入れ基準に移す（今の形では US6.3 が US5.1 に依存しているのに、依存の列に書かれていない）。

### 9. 性能の受け入れ基準の測り方（AC1.1.6・AC2.1.4）

- 「30 秒以内」「10 秒以内」は、API の要求を受けてから応答を返すまで（画面の描画を除く）を、colima 上のコンテナの対象DB に対して測る、と書いておく。
- 100 テーブル × 100 カラムの対象DB を用意するのは、テストの前準備として重い（3種類の DB で毎回行うと `verify` の時間に効く。`team.md` の Testing Posture では、どこで実行するかは Build and Test で実測して決める）。受け入れ基準としては残し、測る場（`verify` の中か Build and Test か）は NFR 要件・Build and Test で決める、と注記しておく。
- 実装の見通し: 対象DB の `DatabaseMetaData` をテーブルごとに問い合わせると、DB の種類によっては 100 回以上の往復になる。まとめて読む方法（情報スキーマの一括の問い合わせなど）を設計で比べる必要がある。

### 10. そのほか（小さな点）

- AC6.2.5（英語の表示）: 画面の表示言語は、ブラウザの希望言語から ja・en を決める既存の仕組み（`frontend/src/app/i18n/resolveLanguage.ts`）に乗るので実装上の問題は無い。ただし、これはアクセス制御ではなく画面のすべてに当たる横断の基準なので、US6.2 ではなく「前提と読み方」の横断の基準（すべての画面の文言は ja・en を持つ、NFR9）に移すと、各画面のストーリーで確かめる対象になる。
- 画面の置き場: 管理者のみの画面は `features/<featureId>/registration.ts` に `access: 'ADMIN'` で登録する（C-10）。振り分けは URL の完全一致で1画面を出すだけ（TD-5）なので、投入・プレビュー・履歴を1つの画面の中のタブ（make-you-chic-ui の Tabs）で切り替えるか、画面を分けて登録するかは設計で決める。ファイルの選択と違いの表示の部品は make-you-chic-ui に無く、中身も変更できないため、画面の側で作る（US2.1・US3.1 の見積もりに含める）。
- AC4.1.5（対象DB を変えない）: テストでは適用の前後で対象DB のスキーマを比べればよい。加えて、対象DB の接続を読み取り専用（JDBC の読み取り専用の指定）で開く作りにしておくと、この基準を構造で守れる（前提 A3 の推奨と合わせる）。
