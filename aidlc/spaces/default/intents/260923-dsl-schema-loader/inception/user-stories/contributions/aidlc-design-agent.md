## Contribution

利用者の体験（UX）とペルソナへの忠実さの観点から、初稿（`aidlc/spaces/default/intents/260923-dsl-schema-loader/inception/user-stories/stories.md`・`personas.md`）への追加・修正の案を示す。依頼者が決めたこと（プレビューに YAML の本文を出さない〔要件の質問 Q5〕、検証を通らない DSL は保存しない〔Q6・F1〕、照合の食い違いは警告にとどめ適用は止めない〔Q7〕、プレビューは1件で置き換え時に確かめる〔F3: A〕、画面での DSL の編集は作らない〔制約〕）は前提とし、覆さない。画面の配置・部品の選び方は Refined Mockups・機能設計の段で決めるため、ここでは利用者から見える振る舞いだけを受け入れ基準として書く。

### 1. 置き換えの確認を、投入以外の操作にもそろえる（F3: A の反映漏れ）

要件の質問 F3 の答え A は「新しい生成・投入・履歴からの戻しは、今のプレビューを置き換える（画面で置き換えてよいかを確かめる）」である。初稿では投入（AC2.1.3）にだけ確認があり、スキーマの読み込み（US1.1）と履歴からの戻し（US5.1）に無い。次を足す。

- **AC1.1.7（追加）** Given 既にプレビューがある / When 管理者がスキーマの読み込みを実行しようとする / Then 今のプレビューを置き換えてよいかを確かめる表示が出て、確かめたときだけ読み込みが始まる。取りやめたときは、プレビューも適用中の DSL も変わらない
- **AC5.1.5（追加）** Given 既にプレビューがある / When 管理者が履歴の版をプレビューに戻そうとする / Then 今のプレビューを置き換えてよいかを確かめる表示が出て、確かめたときだけ置き換わる
- **AC2.1.3（修正）** 末尾に「取りやめたときは、プレビューも適用中の DSL も変わらず、選んだファイル・貼り付けた内容は画面に残る」を足す
- 確認の表示には、置き換えられる今のプレビューの出どころ（生成・アップロード・貼り付け・履歴からの戻し）と、置いた管理者・日時を示す（次の2節の情報を使う）。ほかの管理者が置いたプレビューを気づかずに消すことを防ぐため（P1 の困りごと「ほかの管理者と同時に作業すると…」）

### 2. プレビューと適用中の DSL の「今の状態」を見せる

P1 は月に数回しか使わない（`personas.md`）。画面を開いたときに、いま何が適用中で、何がプレビューに置かれているかが一目で分からないと、操作を誤りやすい。US3.1 に次を足す。

- **AC3.1.6（追加）** Given プレビュー中の DSL がある / When プレビューを表示する / Then そのプレビューの出どころ（生成・アップロード・貼り付け・履歴からの戻し）、置いた管理者、置いた日時、DSL の識別（ハッシュ値の先頭など）が表示される
- **AC3.1.7（追加）** Given 適用中の DSL がある / When DSL の操作の画面を開く / Then 適用中の DSL の識別、適用した管理者、適用した日時が表示される。適用中の DSL が無いときは、まだ適用していないことが表示される
- AC3.1.5（プレビューが無いときの案内）は良い。上の AC3.1.7 と合わせて、画面を開いた直後の「空の状態」を2種類（プレビューなし・適用中なし）とも決めておく

### 3. 適用の前の確認（取り消しにくい操作）

適用は業務の画面の元を切り替える操作で、履歴からの戻し（US5.1）は Should のため、最初に届ける範囲では取り消せない可能性がある。適用の前に確認を挟む。

- **AC4.1.6（追加）** Given プレビュー中の DSL がある / When 管理者が適用しようとする / Then 適用してよいかを確かめる表示が出て、その表示に違いの件数（増えた・減った・変わったテーブルとカラムの数）と、対象DB との照合の警告の件数が示される。確かめたときだけ適用され、取りやめたときは何も変わらない
- **AC3.2.3（修正）** 「Then 適用できる」を「Then 適用の確認の表示に警告があることが示され、確かめれば適用できる」とする（警告で止めない決定〔Q7〕は変えない。警告を見落として適用することだけを防ぐ）
- **AC4.1.7（追加）** Given 適用が成功した / When 画面が更新される / Then 成功したことが通知され、適用中の DSL の表示（AC3.1.7）が新しい版に変わり、プレビューが無いことが表示される

### 4. ほかの管理者がプレビューを変えたときの立て直し

AC4.2.1・AC4.2.2 は拒否までを書いているが、拒否の後に管理者が次に何をすればよいかが無い。

- **AC4.2.4（追加）** Given 管理者 A の適用が、プレビューが置き換わったために拒否された / When 拒否の表示を見る / Then 最新のプレビューを表示し直す操作が示され、それを選ぶと新しいプレビューの内容（出どころ・置いた管理者を含む）が表示される。新しいプレビューが自動で適用されることはない
- **AC4.2.5（追加）** Given 管理者 A の適用が、プレビューが破棄されたために拒否された / When 拒否の表示を見る / Then プレビューが無いことと、読み込み・投入の操作への案内が表示される

### 5. 時間のかかる操作の待ち方（30 秒・10 秒）

スキーマの読み込みは最大 30 秒、投入は最大 10 秒かかる（NFR1）。待っている間の見せ方と二重の操作の防ぎ方が受け入れ基準に無い。US1.1・US2.1 に次を足す（US4.1・US5.1 の適用・戻しにも同じ扱いを当てる）。

- **AC1.1.8（追加）** Given 管理者がスキーマの読み込みを実行した / When 処理が終わるまでの間 / Then 処理中であることが表示され、読み込み・投入・適用・破棄の操作はできない（二重の実行を防ぐ）。処理中であることは読み上げでも伝わる
- **AC2.1.5（追加）** Given 管理者が投入を実行した / When 処理が終わるまでの間 / Then 処理中であることが表示され、投入の操作をもう一度実行できない
- 補足: 画面で操作を止めるのは使いやすさのためで、二重の実行の最終的な防ぎはサーバー側（AC4.2 の「見たプレビューを指定する」決まり）に任せる（NFR3 と同じ考え方）

### 6. 検証エラーの一覧を「直せる」形で見せる（US2.2）

P2 の目的は「どこで間違っているかを、行・列と場所で知る」。一覧が出るだけでなく、直して出し直すまでの流れを支える。

- **AC2.2.6（追加）** Given 貼り付けた DSL が検証を通らなかった / When エラーの一覧が表示される / Then 貼り付けた内容はテキスト欄に残り、直してそのまま投入し直せる。ファイルで投入したときは、選んだファイル名が表示されたまま残る
- **AC2.2.7（追加）** Given 検証を通らない DSL を投入した / When エラーの一覧が表示される / Then エラーの件数が一覧の先頭に表示され、キーボードの操作の位置（フォーカス）が一覧の先頭に移り、件数が読み上げられる
- **AC2.2.8（追加）** Given エラーの一覧が表示されている / When 管理者が一覧を写し取る操作をする / Then 行・列・場所・内容を含むエラーの一覧を、テキストとしてクリップボードに写せる（管理者が DSL の作者に誤りを伝えるため。優先度は Should でよい）
- エラーが多いとき（例: 100 件を超える）の見せ方（件数の上限、残りの件数の表示）は機能設計で決める、と INVEST の注記に足す

### 7. 投入の入力の誤り（空・種類違い）

US2.1 に、送る前に分かる誤りを足す。いずれも画面での案内であり、サーバー側の検証の代わりにしない（NFR3）。

- **AC2.1.6（追加）** Given ファイルを選んでおらず、テキスト欄も空である / When 投入しようとする / Then 投入の操作はできず、ファイルを選ぶか貼り付けるよう案内される
- **AC2.1.7（追加）** Given 5MB を超えるファイルを選んだ / When 投入しようとする / Then 送る前に、大きさの上限を超えていることが表示される（サーバー側の拒否 AC2.3.1 は別に確かめる）
- ファイルとテキストの両方が入力されたときにどちらを使うか（例: 画面で「ファイル」「貼り付け」を切り替え、片方だけを入力できる形にする）は Refined Mockups で決める、と注記する

### 8. 破棄の確認

破棄したプレビューは戻せない（生成は作り直せるが、貼り付けた・アップロードした内容は画面に残らない）。

- **AC3.3.3（追加）** Given プレビューがある / When 管理者が破棄しようとする / Then 破棄してよいかを確かめる表示が出て、確かめたときだけ破棄される

### 9. 履歴の空の状態と、適用中の版の目印

- **AC5.1.6（追加）** Given まだ一度も適用していない / When 履歴を表示する / Then 履歴が無いことが表示される
- **AC5.1.7（追加）** Given 履歴が表示されている / When 一覧を見る / Then 今適用中の版がどれかが、色だけでなく文字（例: 「適用中」）で示される
- AC5.1.1 の「日時」は、表示言語に合わせた書式で、時差（タイムゾーン）が分かる形で表示する（保存は UTC、`project.md` の Corrections）。これは機能設計への注記でよい

### 10. ダウンロードしたファイルの見分け

P2 の困りごと「リポジトリの正本と食い違う」を解くには、手元に落としたファイルが何かを見分けられる必要がある。

- **AC3.4.5（追加）** Given プレビュー中の DSL をダウンロードした / When ファイル名を見る / Then プレビュー中のものであることと、DSL の識別（ハッシュ値の先頭など）が分かる名前になっている
- **AC5.2.3（追加）** Given 適用中の DSL をダウンロードした / When ファイル名を見る / Then 適用中のものであることと、DSL の識別が分かる名前になっている。AC3.4.5 の名前と区別できる
- ファイル名の具体的な形は機能設計で決める

### 11. 対象DB に接続できないときの見せ方（P1・P3 の困りごと）

P1 は、読み込みに失敗したとき、自分で直せるのか運用者に頼むのかを知りたい。P3 の困りごとは「接続先の設定を誤ったときに、どこが悪いのかが分かりにくい」だが、初稿の受け入れ基準に対応するものが無い。NFR4（接続情報を画面・ログに出さない）を守ったまま、次を足す。

- **AC1.1.5（修正）** Then に「表示には、対象DB の設定が無いのか、設定はあるが接続できないのかの区別と、運用者に確かめてもらうよう促す案内が含まれる（接続先・ユーザー名などの値は含まれない）」を足す
- **AC6.1.7（追加）** Given 対象DB の接続先の設定の一部（例: スキーマ名）が欠けている、または種類が対応外である / When アプリを起動する / Then アプリは起動し、アプリのログに、どの設定の項目名（例: `mastersmith.target-db.schema`）に問題があるかが WARN で1件出る。項目の値（接続先・ユーザー名・パスワード）はログに含まれない

### 12. アクセシビリティ（NFR10 の具体化）

NFR10 は「部品ごとに axe を通す」だが、axe では見つからない点がこの画面には多い（状態の移り変わり、確認の表示、長い処理）。US6.2 または各ストーリーの共通の受け入れ基準として次を足す。

- **AC6.2.6（追加）** Given キーボードだけを使う管理者 / When スキーマの読み込み・投入（ファイルの選択と貼り付けの両方）・プレビューの確認・適用・破棄・履歴からの戻し・ダウンロードを行う / Then すべての操作をマウスを使わずに完了できる。確認の表示が開いている間はフォーカスが表示の中にとどまり、閉じるとフォーカスは開く前の操作の位置に戻る
- **AC6.2.7（追加）** Given 違いの一覧（増えた・減った・変わった）と照合の警告 / When 表示する / Then 種類は色だけでなく文字またはアイコンと代わりの文字で示され、読み上げでも区別できる（WCAG 1.4.1）
- **AC6.2.8（追加）** Given 処理の完了・失敗・拒否（AC4.2）が起きた / When 画面が更新される / Then その結果が読み上げで伝わる（操作の位置が動かない通知は、ライブリージョンで知らせる）
- メニューの階層の木（AC3.1.1）は、開閉の操作を持つ木の部品ではなく、入れ子の一覧として見せれば、読み上げとキーボードの扱いが単純になる。これは Refined Mockups への提案とする

### 13. 日英の表示

- AC6.2.5 に「エラーの一覧・照合の警告・確認の表示・空の状態の案内の文言も英語で表示される。DSL の中の場所（テーブル名・カラム名などの物理名）は、表示言語によらず物理名のまま示す」を足す
- 違いの一覧で「表示名が変わった」と示すとき（AC3.1.3）、ja と en のどちらが変わったのかを区別して示す（AC3.1.1 の「ja・en で埋まっているか」と同じ粒度にそろえる）

### 14. ペルソナの立て方（`personas.md`）

- `personas.md` の「関係と優先度」は「この Intent の操作は、すべて管理者が画面で行う」「P2 は…管理者に渡す（管理者が投入する）」としている。一方、US2.2・US3.4・US5.2 の主語は P2 で、P2 が自分で投入・ダウンロードするように読める。主語を「P1 管理者（DSL の作者を兼ねる、または作者のために操作する）として…。それは、P2 DSL の作者が…ためだ」の形にするか、`personas.md` に「P2 のストーリーは、P2 が管理者を兼ねる場合を表す。兼ねない場合は、P1 が P2 のために操作する」と明記する
- P2 の困りごと「DSL の書式（スキーマ）に合っているかを、投入してみるまで確かめにくい」は、FR1 をストーリーにしない決定（Q4: B）により、どのストーリーでも解かれない。決定は覆さず、`personas.md` か `stories.md` の「前提と読み方」に「この困りごとは FR1（ドメイン設計）と要件の OQ6（JSON Schema の配り方、機能設計）で扱う」と書き、追えるようにする
- P3 の目的「誰がいつ DSL を変えたかを、監査ログで追える」について、今のアプリには監査ログを見る画面が無い（`aidlc/spaces/default/codekb/mastersmith2/api-documentation.md`）。US6.3 の「監査ログを見る」は内部DB の `audit_events` を調べることを指す、と注記しておくと、画面を期待する誤解を防げる
