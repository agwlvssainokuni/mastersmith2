### 1. 全体に当てる書き方の案（「前提と読み方」に足す）

- **判定の場の明記**: 受け入れ基準の「表示される」は、サーバー側（API の応答と内部DB の状態）で確かめるものと、画面の部品で確かめるものが混ざっている。サーバー側の基準は **応答の状態コードと Problem Details の `code`** で判定し、画面の基準は表示された文言で判定する、と前提に書く。`code` の一覧（大きさの超過・入れ子の深さ・別名の数・タグ・重複キー・構文・意味・版の非対応・対象DB に接続できない・プレビューが無い・プレビューが変わった など）は、契約の設計（OQ5）で決める。そうしないと、「上限を超えたことが表示され」をサーバーのテストで判定できない。
- **「変わらない」の確かめ方**: 「プレビューと適用中の DSL は変わらない」「保存されない」は、内部DB のプレビュー・適用中・履歴の表の行と DSL の識別（ハッシュ値）が、操作の前後で同じであることで確かめる、と前提に書く。
- **「含まれない」の確かめ方**: 秘密情報や部品の例外のメッセージが「含まれない」ことは、テストの設定で対象DB の接続先・ユーザー名・パスワードに他と重ならない目印の文字列を入れ、応答の本文・取り込んだアプリのログ・監査ログの行・生成した DSL のどれにも目印が現れないことで確かめる。部品の例外は、部品に特有の文字列（例外のクラス名やパッケージ名）が応答に無いことで確かめる。
- **対象DB に関わる基準**: 対象DB に接続する基準（AC1.1.x、AC3.2.x、AC4.1.5、AC5.1.3、AC6.1.x）は、MySQL・MariaDB・PostgreSQL の3種類それぞれで確かめる（NFR12、`project.md` の Mandated）、と前提に書く。AC6.1.6 だけに3種類を書くと、ほかの基準が1種類だけで済むと読める。
- **性質ベースのテストの候補**（team.md の jqwik・fast-check）: 適用中とプレビューの違いの計算（同じ DSL どうしなら違いは0件、入れ替えると増減が逆になる）、履歴の件数の刈り込み（何回適用しても上限を超えない、新しい順）、既定の表示名の導き方（コメントがあれば ja はコメント、en はいつも物理名）、メニューの並び順、ダウンロード → 投入の往復で内容が同じ。基準としては書かず、設計の段で扱う候補として INVEST の注に残す。
