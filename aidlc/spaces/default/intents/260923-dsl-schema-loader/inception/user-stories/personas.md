# Personas — dsl-schema-loader

この Intent に関わる利用者を3人に分ける（`user-stories-questions.md` の Q1: C）。小さな組織では、同じ人が2人・3人を兼ねることがある。その場合も、ストーリーは立場ごとに書く。

## P1 管理者（admin）

| 項目 | 内容 |
|---|---|
| 役割 | 管理者フラグを持つ MasterSmith の利用者。管理画面で、スキーマの読み込み・DSL の投入・プレビュー・適用・破棄・履歴の操作を行う |
| 目的 | ・誤った DSL を業務の画面に反映させない（プレビューで確かめてから適用する）<br>・対象DB の構造に合った DSL を、手間をかけずに用意する<br>・問題があったときに、前の DSL にすぐ戻す |
| 困りごと | ・DSL の中身を画面で読み比べるのは大変で、どこが変わったのかが分かりにくい<br>・ほかの管理者と同時に作業すると、確かめた内容と違うものを反映してしまうおそれがある |
| IT への慣れ | 中〜高（YAML は読めるが、毎日書くわけではない） |
| 利用の頻度 | 低い（導入時と、DSL を変えるときだけ。月に数回ほど） |

## P2 DSL の作者（DSL author）

| 項目 | 内容 |
|---|---|
| 役割 | アプリの外で DSL（YAML）を書き、業務の側のリポジトリでレビュー・差分の管理をする人。アプリの管理者とは限らない |
| 目的 | ・生成された既定の DSL を土台に、表示名・検索条件・一覧・バリデーションなどを業務に合わせて直す<br>・書いた DSL がどこで間違っているかを、行・列と場所で知る |
| 困りごと | ・DSL の書式（スキーマ）に合っているかを、投入してみるまで確かめにくい<br>・アプリの中にある DSL（生成したもの・適用中のもの）を手元に取り出せないと、リポジトリの正本と食い違う |
| IT への慣れ | 高（YAML・JSON Schema・Git を使える） |
| 利用の頻度 | 導入時に集中し、以降は業務の変更に合わせてときどき |

## P3 運用者（operator）

| 項目 | 内容 |
|---|---|
| 役割 | MasterSmith を配備・起動し、対象DB の接続先を `application.yml`（`mastersmith.target-db.*`）と環境変数に設定する人 |
| 目的 | ・対象DB の接続先を、秘密情報を漏らさずに設定する<br>・対象DB が止まっていても、アプリ（ログイン・管理画面）は止めない<br>・誰がいつ DSL を変えたかを、監査ログで追える |
| 困りごと | ・接続先の設定を誤ったときに、どこが悪いのかが分かりにくい<br>・対象DB の障害に、アプリ全体が巻き込まれたくない |
| IT への慣れ | 高（コンテナ・設定ファイル・環境変数を扱える） |
| 利用の頻度 | 配備・設定の変更のとき |

## 関係と優先度

- 優先度は **P1 管理者 > P2 DSL の作者 > P3 運用者** の順とする。この Intent の操作は、すべて管理者が画面で行う（要件の FR9）。
- P2 は、管理者が生成・ダウンロードした DSL を受け取って直し、直した DSL を管理者に渡す（管理者が投入する）。P2 が管理者を兼ねるときは、自分で投入する。
- P2 を主語にしたストーリー（誤りの場所を知る・ファイルとして取り出す）は、得られる価値が P2 のものであることを示す。画面の操作そのものは、P2 が管理者を兼ねるか、管理者が P2 のために行う。
- P2 の困りごとのうち「DSL の書式（スキーマ）に合っているかを確かめにくい」は、スキーマの定義（要件の FR1）と、スキーマを作者に配る方法（要件の OQ6）で扱う。この Intent のストーリーでは、投入したときの誤りの一覧（US2.2）で応える。
- P3 が接続先を設定し、アプリを起動してはじめて、P1 がスキーマを読み込める。P3 の「誰がいつ DSL を変えたかを追う」は監査ログ（内部DB の記録）で応える。監査ログを画面で見る働きは、この Intent では作らない。
