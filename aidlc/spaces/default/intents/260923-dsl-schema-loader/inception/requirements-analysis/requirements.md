## 1. Intent の分析

- **目的**: MasterSmith の挙動を決める DSL の土台を作る。ロードマップの Intent A（DSL のスキーマ定義）・D（スキーマの読み込みと既定の DSL の生成）・E（DSL の読み込み・検証と、プレビュー → 適用の流れ）を1つにまとめる（DESC、RD-9.3）。
- **背景**: MasterSmith は、実行時にスキーマを探索するのではなく、事前に確定した DSL に従って画面と処理を決める「静的設定駆動・インタープリタ方式」を採る（RD-0、RD-1、RD-3）。この Intent は、業務データ（対象DB）に触れる最初の機能になる（KB）。
- **利用者**: 管理者フラグを持つ利用者（管理者）。DSL の生成・投入・プレビュー・適用は管理者だけが行う（RD-5.7、RD-9.1）。
- **成功基準**:
  - 対象DB のメタデータから、スキーマに合った既定の DSL を管理画面の操作で生成できる
  - 人が書いた完成品の DSL を投入し、検証を通ったものだけをプレビューに置ける
  - プレビューを確かめてから適用し、アプリが使う DSL（適用中の DSL）を切り替えられる。再起動しても適用中の DSL が残る
  - 後続の Intent（I・J・K：メニュー・一覧・詳細と編集の画面）が、適用中の DSL を解釈した内部のモデルを使って画面を作れる
- **種類・規模**: 既存のアプリ（認証・監査の基盤）への機能の追加（ブラウンフィールド）。バックエンド・フロントエンド・内部DB・対象DB（新規）にまたがり、複雑さは標準より大きい。対象DB の接続、DSL の定義、読み込み・検証、画面のどれも、既存のコードは無い（KB: C-1）。

## 2. 機能要件

受け入れ基準は Given/When/Then で書く。★は設定で変更できる値で、表記は既定値。

### FR1 DSL のスキーマ定義

出典: DESC、RD-2.2〜RD-2.9（RD-2.6 を除く）、RD-3.1、RD-4、RQ9

- **FR1.1** DSL は YAML で書き、その構造を JSON Schema で定義する。アプリは、この JSON Schema で DSL の構文を検証する。
  - Given JSON Schema に合う DSL / When 構文を検証する / Then 通る
  - Given JSON Schema で必須の項目が欠けた DSL / When 構文を検証する / Then 欠けた項目の場所を示すエラーになる
- **FR1.2** DSL は、メニューの構成（N 階層、グループ、表示順、テーブルとの紐付け、アイコン）を記述できる。メニュー項目は、1つのテーブルに紐付けるか、複数のテーブルをまとめた業務メニューにできる（RD-2.3）。
  - Given 3階層のメニューを記述した DSL / When 構文と意味を検証する / Then 通る
- **FR1.3** DSL は、テーブル・カラムごとに次を記述できる（RD-2.4、RD-2.5、RD-2.7〜RD-2.9、RD-4）。
  - 表示名（ja・en の2言語の対）
  - 検索条件（検索に出すか、演算子（完全一致・部分一致・範囲・選択肢・IN など）、既定値、初期表示の状態）
  - 一覧表示（表示するか、並び順、列幅、並べ替えの可否、既定の並べ替え、表示の書式）
  - 詳細表示（詳細・編集画面に出すか）
  - バリデーション（必須、文字数の最小・最大、数値の範囲、正規表現、一意）。DB のスキーマから機械的に導いたものと、人が業務の要件として足したものを区別して記述できる
  - フォーム部品（text・textarea・checkbox・switch・radio・select・参照ピッカー など）
  - 選択肢の出どころ（DSL に直接書く固定の一覧、他のテーブルの参照、参照ピッカー）。参照ピッカーは、参照先のテーブルの通常の検索条件・一覧表示とは別の、専用の検索条件・一覧表示を持つ
  - Given 上の各項目を含むカラムの定義 / When 構文と意味を検証する / Then 通る
- **FR1.4** DSL は、テーブルがビューであること（読み取り専用の扱い）を記録できる（RQ9）。
  - Given ビューを読み取り専用として記録した DSL / When 構文と意味を検証する / Then 通る
- **FR1.5** DSL は、書式の版（DSL の形式の版）を持つ。アプリは、対応していない版の DSL を受け付けない。
  - Given アプリが対応していない版を名乗る DSL / When 投入する / Then 版が対応していないことを示すエラーになる
- **FR1.6** DSL には、対象DB の接続先（接続先・ユーザー名・パスワード）を書かない。接続先は FR2 の設定だけで扱う（RD-2.1、PM（Forbidden））。
  - Given 接続先の項目を含む DSL / When 構文を検証する / Then JSON Schema に無い項目としてエラーになる
- **FR1.7** 権限（NONE・READ・FULL、CREATE・DELETE）と、カラムの編集の可否は DSL に含めない。これらは後続の Intent F の権限モデルで扱う（RD-2.6、RD-5）。

### FR2 対象DB への接続

出典: DESC、RD-2.1、RQ1、RQ12、PM（Forbidden）

- **FR2.1** 対象DB の接続先（RDBMS の種類、ホスト、ポート、DB 名、スキーマ名、ユーザー名、パスワード）は、`application.yml` の `mastersmith.target-db.*` に書く。内部DB の設定（`spring.datasource.*`）とは分ける。対象DB は1つだけとし、種類は MySQL・MariaDB・PostgreSQL のいずれかとする。
  - Given `mastersmith.target-db.*` に PostgreSQL の接続先を設定した / When スキーマを読み込む / Then その PostgreSQL の、設定したスキーマを読む
- **FR2.2** 対象DB のパスワードは、`application.yml` に直接書かず、環境変数などの参照で渡す。
- **FR2.3** 既存の内部DB の働き（ログイン、監査ログ、Flyway の移行、ヘルスチェック）は、対象DB の接続を足した後も内部DB を使い続ける。
  - Given 対象DB の接続先を設定してアプリを起動した / When ログインし、監査ログが記録される / Then どちらも内部DB に対して行われる
- **FR2.4** アプリは、対象DB の接続先の設定が無くても、対象DB が止まっていても起動する。対象DB を使う操作（スキーマの読み込み、対象DB との照合）だけが、対象DB に接続できないことを示すエラーで失敗する（RQ12）。
  - Given 対象DB の接続先を設定していない / When アプリを起動する / Then 起動し、ヘルスチェックは正常を返す
  - Given 対象DB が止まっている / When スキーマの読み込みを実行する / Then 対象DB に接続できないことを示すエラーが返り、プレビューと適用中の DSL は変わらない
- **FR2.5** この Intent では、対象DB に対して行うのはメタデータの読み取りだけとし、対象DB のスキーマとデータを変更しない（RQ1）。

### FR3 スキーマの読み込みと既定の DSL の生成

出典: DESC、RD-2.2、RQ8、RQ9、RF3

- **FR3.1** 管理者は、管理画面の操作で対象DB のスキーマを読み込み、既定の DSL を生成できる。読み込みはこの操作のときだけ行い、アプリの起動時や定期的には行わない。スキーマの変更の自動検知はしない。
  - Given 管理者がログインしている / When スキーマの読み込みを実行する / Then 既定の DSL が生成され、プレビューに置かれる
- **FR3.2** 読み込みの対象は、設定で指定した1つのスキーマの中のテーブルとビューとする。テーブルごとに、カラム、型、主キー、外部キー、NOT NULL の制約、既定値、コメントを読み取る（RQ9）。
  - Given 対象のスキーマに2つのテーブルと1つのビューがある / When スキーマを読み込む / Then 既定の DSL に3つとも含まれ、ビューは読み取り専用として記録される
- **FR3.3** 既定の DSL の表示名は、ja・en の両方に物理名を入れる。テーブル・カラムに DB のコメントがあれば、ja にはコメントを入れる（RQ8）。
  - Given コメント「氏名」を持つカラム `name` / When 既定の DSL を生成する / Then 表示名は ja が「氏名」、en が `name` になる
  - Given コメントの無いカラム `code` / When 既定の DSL を生成する / Then 表示名は ja・en とも `code` になる
- **FR3.4** 既定の DSL のメニューは1階層とし、テーブル（ビューを含む）ごとに1項目を、物理名の順に並べる（RQ8）。
- **FR3.5** 既定の DSL のフォーム部品とバリデーションは、カラムの型と制約から機械的に決める（例: NOT NULL → 必須、型の長さ → 最大文字数）。機械的に導いたバリデーションは、その旨を DSL に記録する（RD-2.7、RD-2.8）。型から部品への対応の規則は設計の段で決める。
  - Given NOT NULL で長さ 50 の文字列のカラム / When 既定の DSL を生成する / Then 必須と最大 50 文字のバリデーションが、DB から導いたものとして記録される
- **FR3.6** 生成した既定の DSL は、FR4 と同じ検証を通してからプレビューに置く。今のプレビューがあれば置き換える（RF3）。既に適用中の DSL があっても、適用するまで適用中の DSL は変わらない。適用すると、人が手で直した内容も含めて全部が置き換わる（差分のマージはしない）（RD-2.2）。

### FR4 完成品の DSL の投入と検証

出典: DESC、RD-2.2、RD-2.2.1、RQ2、RQ6、RQ10、RF1、RF3、TP

- **FR4.1** 管理者は、完成品の DSL を、YAML のファイルのアップロードと、テキスト欄への貼り付けのどちらでも投入できる（RQ2）。
  - Given 管理者が YAML のファイルを選ぶ / When 投入する / Then 検証を通ればプレビューに置かれる
  - Given 管理者が YAML をテキスト欄に貼り付ける / When 投入する / Then 検証を通ればプレビューに置かれる
- **FR4.2** 投入された DSL は、構文（JSON Schema）と意味の両方で検証する。意味の検証には、少なくとも次を含む: メニューが DSL に無いテーブルを指していない、同じテーブル・カラムが2回定義されていない、参照（外部キー・参照ピッカー）の先が DSL にある。
  - Given 存在しないテーブルを指すメニュー項目を持つ DSL / When 投入する / Then 意味の検証のエラーになる
- **FR4.3** 検証を通らない DSL は受け付けず、保存もしない。投入の操作の結果として、同じ画面にエラーの一覧を返す。エラーごとに、YAML の行・列と、DSL の中の場所（どのテーブル・カラム・項目か）を示す（RQ6、RF1）。
  - Given 構文のエラーを2件含む DSL / When 投入する / Then 2件のエラーが、それぞれの行・列と場所つきで表示され、プレビューと適用中の DSL は変わらない
- **FR4.4** 投入された DSL は信頼できない入力として扱う。大きさ（上限 5MB）、入れ子の深さ、別名（アンカー）の数に上限を置き、任意の型を作るタグを拒否し、重複したキーをエラーにし、JSON Schema の外部の `$ref` を取りに行かない。上限の具体的な数値（大きさ以外）は設計の段で決める（RQ10、TP、PM（Mandated））。
  - Given 5MB を超える DSL / When 投入する / Then 大きさの上限を超えたことを示すエラーになる
  - Given 同じキーが2回現れる DSL / When 投入する / Then 重複したキーのエラーになる
  - Given 任意の型を作るタグを含む DSL / When 投入する / Then 拒否され、型は作られない
- **FR4.5** 検証を通った DSL は、今のプレビューを置き換えてプレビューに置く。画面では、既にプレビューがあるときに置き換えてよいかを確かめる（RF3）。

### FR5 プレビュー

出典: RD-2.2.1、RQ5、RQ7、RF1

- **FR5.1** 管理者は、プレビュー中の DSL について、次を画面で確かめられる（RQ5）。
  - 検証を通ったこと
  - 要約（テーブル数・カラム数、メニューの階層の木、表示名が ja・en で埋まっているか）
  - 適用中の DSL との違い（増えた・減った・変わったテーブルとカラム）。適用中の DSL が無いときは、すべてが増えたものとして示す
  - 対象DB との照合の警告（FR5.2）
  - Given 適用中の DSL にあるテーブル1つを除き、新しいテーブル1つを足したプレビュー / When プレビューを表示する / Then 減ったテーブルと増えたテーブルがそれぞれ1つ示される
- **FR5.2** プレビューに置くとき、DSL を対象DB のメタデータと照らし合わせる。対象DB に無いテーブル・カラムや、型の食い違いは警告として示す。警告があっても適用はできる。対象DB に接続できないときは、照合できなかったことを警告として示す（RQ7、RQ12）。
  - Given 対象DB に無いカラムを含む DSL / When プレビューに置く / Then そのカラムについての警告が示される
- **FR5.3** プレビューは適用せずに破棄できる。破棄すると、プレビューは無くなり、適用中の DSL は変わらない（RF3）。

### FR6 適用

出典: RD-2.2.1、RD-3、RQ1、RQ4、RQ7、RF3

- **FR6.1** 管理者は、プレビュー中の DSL を適用できる。適用すると、アプリが使う DSL（適用中の DSL）がプレビュー中の DSL に切り替わり、プレビューは無くなる。適用で対象DB には何も書き込まない（RQ1）。
  - Given プレビュー中の DSL がある / When 適用する / Then 適用中の DSL がその内容に切り替わる
- **FR6.2** 適用は、管理者が見たプレビューを指定して行う。その間にプレビューが置き換わっていたり破棄されていたりしたら、適用を拒否する（RF3）。
  - Given 管理者 A がプレビューを表示した後に、管理者 B が別の DSL を投入してプレビューを置き換えた / When 管理者 A が適用する / Then 適用は拒否され、プレビューが変わったことが示される
- **FR6.3** 適用中の DSL は内部DB に保存し、アプリを再起動しても残る。アプリは起動時に適用中の DSL を読み込む（RQ4）。
  - Given DSL を適用した / When アプリを再起動する / Then 同じ DSL が適用中である
- **FR6.4** アプリは、適用中の DSL を解釈した内部のモデル（メニュー・テーブル・カラムの定義）を、後続の Intent（I・J・K）の画面と処理が使える形で持つ。適用すると、内部のモデルも新しい DSL のものに切り替わる（RD-3、RD-9.3 の Intent E）。
  - Given DSL を適用した / When アプリの中から内部のモデルを取り出す / Then 適用した DSL のメニュー・テーブル・カラムの定義が得られる

### FR7 適用の履歴

出典: RQ4、RF2

- **FR7.1** 適用した DSL は、履歴として内部DB に残す。管理者は履歴を一覧で見られる（適用した日時、適用した人、DSL の識別（ハッシュ値など））。
- **FR7.2** 管理者は、履歴から前の版を選んでプレビューに戻し、もう一度適用できる。戻した DSL にも FR4 の検証と FR5.2 の照合を行う。
  - Given 履歴に2つ前の版がある / When その版をプレビューに戻して適用する / Then 適用中の DSL がその版の内容になる
- **FR7.3** 履歴は新しいほうから決まった件数（★20件）だけ残し、それを超えたら古いものから消す（RF2）。
  - Given 件数の上限まで履歴がある / When 新しく適用する / Then 最も古い履歴が消え、件数は上限のまま

### FR8 DSL のダウンロード

出典: RD-3.2、RQ3

- **FR8.1** 管理者は、プレビュー中の DSL と適用中の DSL を、YAML のファイルとしてダウンロードできる（RQ3）。
  - Given 既定の DSL がプレビューにある / When ダウンロードする / Then その DSL の YAML のファイルが得られ、そのファイルをそのまま投入すると検証を通る

### FR9 管理画面とアクセス制御

出典: RD-5.7、RD-9.1、KB、TP

- **FR9.1** この Intent の操作（スキーマの読み込み、投入、プレビュー、適用、破棄、履歴、ダウンロード）は、管理画面（AppShell の中の管理者向け領域）から行う。
- **FR9.2** この Intent の操作は管理者だけが行える。サーバー側で、未認証は 401、管理者でない利用者は 403、管理者は成功になることを確かめる（画面でメニューを隠すことはサーバー側の確認の代わりにしない）（TP）。
  - Given 管理者でない利用者 / When DSL の適用の API を呼ぶ / Then 403 が返り、適用中の DSL は変わらない
- **FR9.3** 画面の文言は日本語・英語に対応する（既存の画面と同じ扱い）。

### FR10 監査ログ

出典: RQ11、PM（DECIDED）、KB

- **FR10.1** 次の操作を、今の監査ログの仕組み（内部DB の `audit_events`）を広げて記録する: 既定の DSL の生成、DSL の投入（アップロード・貼り付け）、適用、プレビューの破棄（RQ11）。
- **FR10.2** 記録には、誰が・いつ・何をしたかと、対象の DSL の識別（ハッシュ値など）を含める。DSL の本文と、対象DB の接続先は記録しない。
  - Given 管理者が DSL を適用した / When 監査ログを見る / Then 適用の出来事が、管理者・日時・DSL のハッシュ値つきで記録され、DSL の本文は含まれない
- **FR10.3** 記録の仕方（元の操作の確定の後に記録する、書き込みに失敗しても元の操作は失敗させない）は、今の監査ログの決まりに従う（KB）。業務データの CRUD を含む監査の共通の仕組みは、この Intent では作らない（PM（DECIDED））。

## 3. 非機能要件

| ID | 分類 | 要件 | 出典 |
|---|---|---|---|
| NFR1 | 性能 | 想定規模（対象DB 100テーブル、1テーブル 100カラム）で、既定の DSL の生成は 30 秒以内、DSL のプレビューへの読み込みと検証（対象DB との照合を含む）は 10 秒以内に終わる | RQ10、RD-7 |
| NFR2 | 容量 | 投入できる DSL の大きさの上限は 5MB。既存の要求の本文の上限（1MB）は、DSL の投入に限り 5MB まで受け付けるようにする | RQ10、KB（C-7） |
| NFR3 | セキュリティ | 投入された DSL は信頼できない入力として扱う（FR4.4）。検証はサーバー側を正とし、画面での検証をサーバー側の代わりにしない | TP、PM（Mandated） |
| NFR4 | セキュリティ | 対象DB の接続情報（接続先・ユーザー名・パスワード・資格情報を含む JDBC の URL）を、生成した DSL・プレビューの応答・画面・ログ・監査ログ・エラー応答に含めず、画面・API・DSL から受け取らない（設定だけから受け取る） | PM（Forbidden） |
| NFR5 | セキュリティ | JDBC の例外や、YAML・JSON Schema の部品の例外のメッセージを、そのままエラー応答に含めない。エラー応答は Problem Details の形で、安定した `code` を持つ | PM（Forbidden）、TP |
| NFR6 | セキュリティ | 対象DB の表名・列名など識別子を SQL に組み込むときは、SQL インジェクションを防ぐ。SpotBugs の SQL インジェクション系の指摘は、priority によらず統合を止める | TP |
| NFR7 | 可用性 | 対象DB の接続先の設定が無い・対象DB が止まっていても、アプリは起動し、ヘルスチェックは内部DB だけで判断する。対象DB を使う操作だけが失敗する | RQ12 |
| NFR8 | 整合性 | 適用は、適用中の DSL・履歴・プレビューの状態を一度に切り替え、途中の状態（一部だけ切り替わった状態）を残さない | RQ4、RF3 |
| NFR9 | 多言語 | 画面の文言と、DSL の表示名は、日本語・英語に対応する | RD-2.9、TP |
| NFR10 | アクセシビリティ | 画面の部品ごとにアクセシビリティ検査（axe）を通す | TP |
| NFR11 | 保守性 | テストの行カバレッジ 80% 以上・分岐カバレッジ 70% 以上（バックエンド・フロントエンドとも、バックエンドはパッケージごとの下限も TP のとおり） | TP |
| NFR12 | 検証 | 対象DB に関わる結合テストは、版を固定したイメージのコンテナで起動した実際の MySQL・MariaDB・PostgreSQL で行う | PM（Mandated）、TP |

## 4. 制約

| 分類 | 制約 | 出典 |
|---|---|---|
| 方式 | インタープリタ方式とする。DSL からソースコードを生成してビルドする方式は採らない | RD-3 |
| DSL の管理 | DSL の正本は、導入先の業務の側のリポジトリで管理する。管理画面での DSL の編集は作らない。DSL の変更は、ファイルの編集 → 投入 → プレビュー → 適用 を経る | RD-3.2 |
| 対象DB | 種類は MySQL・MariaDB・PostgreSQL。接続は1つだけ。接続先は `mastersmith.target-db.*`、内部DB は `spring.datasource.*` | RD-2.1 |
| 内部DB | H2。DSL（プレビュー・適用中・履歴）を保存する表は Flyway の移行で足し、変更は前進のみ | TP、KB |
| 構成・層 | 既存の層の決まり（web・service・domain・repository、ArchUnit）、Problem Details と `code`、コンストラクター注入に従う | TP |
| 画面 | make-you-chic-ui を使い、サブモジュールの中身を直接変更しない | PM（Forbidden） |
| 依存 | 新しい依存（JDBC ドライバー・JSON Schema の検証部品・YAML の部品など）は、ライセンスを確かめ、Apache License 2.0 と異なるものは採用の理由を設計の記録に残す。lockfile で版を固定し、OSV の関門を通す | TP、PM（Mandated） |

## 5. 前提

| ID | 前提 | 理由 |
|---|---|---|
| A1 | プレビュー・適用中の DSL・履歴は、管理者全員で共有する（管理者ごとに別のプレビューは持たない） | プレビューは1件だけとした（RQ4、RF3） |
| A2 | 履歴からプレビューに戻す操作は、監査ログでは「投入」の一種として記録する | RQ11 の対象（生成・投入・適用・破棄）に、戻しが明示されていないため |
| A3 | 対象DB の接続に使うアカウントは、メタデータを読める権限があれば足りる。読み取りだけの権限のアカウントを使うことを推奨として文書に書く | 対象DB に書き込まない（FR2.5） |
| A4 | DSL の書式の版は 1 から始める | FR1.5 |
| A5 | DSL の表示名の言語は ja・en の2つに固定する | RD-2.9 |
