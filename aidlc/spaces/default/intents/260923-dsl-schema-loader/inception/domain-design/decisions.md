## ADR-001: 部品を targetdb・dsl・dslmanage の3つのパッケージに分ける

- **Context** — 今回の働きは、対象DB の接続とメタデータ、DSL の書式と解釈、DSL の管理の操作に分かれる。後続の Intent I・J・K は DSL の解釈とモデルを、F・J・K は対象DB を使うが、管理の操作は使わない。既存のコードは機能ごとのパッケージの中を層に分け、ArchUnit で確かめている（Q1）。
- **Decision** — `targetdb`（TargetDatabase）、`dsl`（DslDefinition・ActiveDslModel）、`dslmanage`（DefaultDslGeneration・DslPreviewAnalysis・DslLifecycle）の3つに分ける。後続の Intent は `dsl` と `targetdb` だけに依存する。
- **Consequences** — 良い点: 後続の Intent が使う安定した部分と、変わりやすい管理の操作が分かれる。パッケージの依存の向きを ArchUnit で確かめられる。悪い点: パッケージが3つ増え、置き場を選ぶ判断が増える。セキュリティ: 信頼できない入力の扱い（dsl）と、外部の DB への接続（targetdb）の境界がはっきりし、点検しやすい。
- **Alternatives Rejected** — (B) `targetdb` と `dsl` の2つ: 後続の Intent が管理の操作と同じパッケージに依存することになり、境界の検査で分けにくい。(C) `dsl` の1つ: 対象DB の障害の扱いと DSL の扱いが混ざり、変わる理由の違うものが一緒になる。

## ADR-002: DSL をプレビューの表と適用の履歴の表の2つで持つ

- **Context** — プレビューは1件、適用中は1件、適用の履歴は最大20件で、履歴から前の版に戻せる。適用は一度に切り替わり、同時の適用は1件だけ成功する必要がある（Q2、要件の FR6・FR7・NFR8）。
- **Decision** — プレビューの表（最大1行）と、適用の履歴の表を持つ。適用中の DSL は履歴の最新の1件とする。適用は1つのトランザクションで、プレビューの行を履歴に移し、上限を超えた古い行を消す。
- **Consequences** — 良い点: 「適用中」を別に持たないので、適用中と履歴の食い違いが起きない。プレビューの行の有無と識別で、見たプレビューの確認（同時の適用）がしやすい。悪い点: 適用で2つの表に触れるため、トランザクションの範囲を業務処理の層に置く必要がある（既存の決まりどおり）。セキュリティ・監査: 履歴は監査ログの代わりにしない（件数で消えるため）。操作の記録は AuditLog に残す。
- **Alternatives Rejected** — (B) 1つの表に状態を持たせる: 状態ごとの件数の決まりを表の制約で守る作りが H2 で複雑になり、適用で状態を2行書き換える必要がある。

## ADR-003: DSL は YAML の本文のまま保存し、識別は本文のバイト列から求める

- **Context** — DSL の正本は業務の側のリポジトリにある。ダウンロードしたものをそのまま投入し直すと、同じ識別になる必要がある（ストーリーの AC3.4.2）。コメントや並びは、作者にとって意味がある（Q3）。
- **Decision** — 投入・生成された YAML の本文（UTF-8）をそのまま保存する。識別（ハッシュ値）は本文のバイト列から求める。ダウンロードは保存した本文をそのまま返す。生成した既定の DSL も、生成の時点で YAML の本文にしてから保存する。
- **Consequences** — 良い点: 往復で識別が変わらない。作者のコメントが残る。悪い点: 書き方（空白・並び）だけが違う DSL も別の識別になり、違いの表では「変わらない」のに識別が違うことがある（違いの表は解釈したモデルで比べるため、画面の表示は正しい）。適用中の起動時の読み込みで毎回解釈する必要がある（件数が1件なので軽い）。セキュリティ: 保存する本文に接続先は入らない（DSL の書式に無いため）。本文は監査の記録に入れない。
- **Alternatives Rejected** — (B) 整えた形で保存: 往復でコメントが失われ、作者のリポジトリとの突き合わせが難しくなる。

## ADR-004: 適用中のモデルをアプリの中に1つ持つ（アプリ1つの前提）

- **Context** — 後続の Intent I・J・K は、画面を作るたびに適用中のモデルを使う。内部DB は組み込みの H2（ファイル保存）で、アプリは1つだけ動く（複数の起動でファイルを共有できない）。これは実現可能性の前提でもある（Q4、既存の前 Intent の判断）。
- **Decision** — 適用中の DSL を解釈したモデルを、アプリの中に1つ持つ（ActiveDslModel）。起動時に内部DB の適用中の DSL を読んで入れ、適用の確定の後に差し替える。後続の Intent には取り出す提供口を1つ渡す。
- **Consequences** — 良い点: 要求のたびに解釈しないので速い。取り出す側は内部DB を知らなくてよい。悪い点: 将来アプリを複数動かすと、アプリの間でモデルがずれる。そのときは、内部DB を共有できる DB に変える判断と合わせて、差し替えの知らせの仕組みを足す必要がある（今は範囲外）。差し替えは、読み手から見て一度に切り替わる作りにする必要がある。セキュリティ: モデルに接続先は入らない。
- **Alternatives Rejected** — (B) 要求のたびに内部DB から読んで解釈: 最大 5MB の YAML を毎回解釈することになり、後続の画面の応答に効く。

## ADR-005: DSL のカラムに DB 上の型の情報を記録する

- **Context** — プレビューで型の食い違いを警告する（ストーリーの AC3.2.3）には、DSL がカラムの DB 上の型を持つ必要がある。型はフォーム部品とバリデーションの元にもなる（Q5）。
- **Decision** — DSL のカラムに、DB 上の型の情報（型の名前・長さ・精度・NULL を許すか）を持たせる。既定の DSL の生成で機械的に入れ、人は通常直さない。3種類の DB の型の名前の違いをどう表すか（そのままか、共通の分類か）は、型の対応の規則とあわせて機能設計で決める。
- **Consequences** — 良い点: 照合で型の食い違いを示せる。後続の Intent が型に合った入力の扱いをしやすい。悪い点: DSL が長くなり、作者が型の項目を誤って直すと警告が出る。対象DB の種類を替えると、型の情報が合わなくなる（警告で分かる）。セキュリティ: 型の情報は秘密ではない。
- **Alternatives Rejected** — (B) 記録しない: 型の食い違いの警告ができず、ストーリーの AC3.2.3 を落とすことになる。

## ADR-006: 対象DB の接続は「既定の候補にしない」指定で別に足す

- **Context** — 内部DB の接続は Spring Boot が自動で作っている。接続（`DataSource`）の Bean を普通に足すと自動の作成が止まり、ログイン・監査・Flyway・ヘルスチェックが対象DB を向くか、起動に失敗するおそれがある（既存のコードの懸念 C-2）。対象DB の操作は手動でまれだが、後続の Intent J・K では業務データの読み書きに使う（Q6）。
- **Decision** — 対象DB の接続は、Spring Boot の「既定の候補にしない」指定（`@Bean(defaultCandidate = false)`）で足し、内部DB の自動の作成には手を入れない。対象DB の接続は小さなプール・読み取り専用・短い待ち時間（接続と問い合わせ）にする。**条件**: この指定が今の Spring Boot（4.1 系）で期待どおり働くことを、最初の Bolt の結合テスト（ログイン・監査・Flyway が内部DB を向き続けること）で確かめる。働かなければ、内部DB の接続を明示して既定（`@Primary`）にする形（Q6 の A）に切り替える。
- **Consequences** — 良い点: 既存の自動構成を変えずに済み、既存のテストへの影響が小さい。後続の Intent でもプールを使える。悪い点: Spring Boot の比較的新しい指定に頼るため、版を上げるときに見直しが要る（project.md の Tech Stack の注意と同じ扱い）。対象DB の接続のプールの分だけ、メモリと接続を使う（小さくする）。セキュリティ: 読み取り専用の接続と、読み取りの権限だけのアカウントの推奨で、書き込まないことを二重に守る。接続先は設定だけから受け取る。
- **Alternatives Rejected** — (A) 内部DB を明示して既定にする: 自動構成の一部を書き直すことになり、既存の設定・テストへの影響が大きい（切り替えの先としては残す）。(C) 操作のたびに接続を開いて閉じる: 今回の用途には足りるが、後続の Intent の業務データの操作で作り直しになる。

## ADR-007: DSL の検証はサーバー側だけで行い、JSON Schema は同梱の1つを正とする

- **Context** — 要件で、検証はサーバー側を正とし、画面の検証をその代わりにしない（NFR3）。投入された DSL は信頼できない入力として扱う（Q7）。
- **Decision** — 画面では DSL を検証しない。JSON Schema はバックエンドに同梱した1つを正とし、外部の URL を取りに行かない。誤りの一覧はサーバーの応答で示す。JSON Schema を DSL の作者に配る方法（要件の OQ6）は機能設計で決める。
- **Consequences** — 良い点: 検証の正が1つで、画面とサーバーの食い違いが起きない。画面に YAML・JSON Schema の部品を足さずに済む（依存と初回の読み込み量が増えない）。悪い点: 誤りに気づくのは送った後になる（最大 5MB を送る）。セキュリティ: 外部の `$ref` を取りに行かない構成で、JSON Schema の読み込みから外部へ接続しない。
- **Alternatives Rejected** — (B) 画面でも検証: 部品と JSON Schema を画面にも持つことになり、2か所の保守と食い違いの危険が増える。

## ADR-008: 誤りの行・列は YAML の位置の対応表から求める

- **Context** — ストーリーの US2.2 は、誤りを YAML の行・列で示す。JSON Schema の検証の部品は誤りの場所をパスで返すため、行・列に直す対応づけが要る。今回で最も技術的に不確かな点（Q8）。
- **Decision** — YAML を読むときに、各値の行・列を記録した対応表（パス → 行・列）を作り、検証の誤りのパスから行・列を引く。意味の検証の誤りも同じ対応表で行・列を付ける。**条件**: YAML の読み込みの部品と JSON Schema の検証の部品の選定では、この対応表が作れること（位置の情報を得られること、パスの表し方を合わせられること）を条件にし、NFR 要件の段で小さく試して確かめる。確かめられなければ、行・列を諦めてパスだけを示す案（Q8 の B）を依頼者に諮る。
- **Consequences** — 良い点: 作者が手元の YAML の直す場所をすぐに見つけられる。悪い点: 読み込みを2通り（位置つきの読み込みと検証用の形）持つことになり、作りが増える。別名（アンカー）で同じ値が複数の場所から参照されるときは、定義した場所の行・列を示す（機能設計で決める）。セキュリティ: 位置の対応表の大きさも、読み込みの上限の範囲に収める。
- **Alternatives Rejected** — (B) パスだけを示す: 作りは簡単だが、ストーリーの AC2.2.1 を見直す必要があり、作者の困りごとに応えきれない。

## ADR-009: 依存の向きを dslmanage → dsl・targetdb の一方向にし、監査は出来事で受ける

- **Context** — 後続の Intent は dsl と targetdb だけを使う（ADR-001）。一方、適用中のモデルは起動時に内部DB（dslmanage の表）から読む必要がある。既存の監査は、各機能が出す出来事を AuditLog が受ける形で、機能は監査を知らない。
- **Decision** — ActiveDslModel（dsl）は保持と提供口だけを持ち、内部DB を読まない。起動時の読み込みと、適用の確定の後の差し替えは DslLifecycle（dslmanage）が行う。こうして依存を dslmanage → dsl・targetdb の一方向にする。監査は、DslLifecycle がアプリの中の出来事を出し、AuditLog が受けて記録する（既存の形に合わせる）。
- **Consequences** — 良い点: 依存に循環が無く、ArchUnit で「dsl・targetdb は dslmanage に依存しない」を確かめられる。DslLifecycle は監査を知らない。悪い点: ActiveDslModel の中身が起動の順序に依存する（DslLifecycle の起動時の処理が終わるまで空）。後続の Intent は「無い」を扱う必要がある。セキュリティ・監査: 監査の決まり（確定の後に記録、失敗しても元の操作は失敗させない）がそのまま効く。
- **Alternatives Rejected** — ActiveDslModel が内部DB を直接読む: dsl が dslmanage の表に依存し、循環か境界の破れになる。DslLifecycle が AuditLog を直接呼ぶ: 既存の形と違い、監査の失敗が操作に波及しやすい。

## ADR-010: 実現可能性の見通しと、後の段で確かめる条件

- **Context** — Ideation の実現可能性の評価が無いため、既存のコードの懸念（`aidlc/spaces/default/codekb/mastersmith2/code-quality-assessment.md` の C-1〜C-10）と今回の決定から、実現できるかを判断する。
- **Decision** — 次の条件つきで「実現できる」と判断し、それぞれ持ち主の段で確かめる。
  - Jackson 3 系と組み合わせられる YAML・JSON Schema の部品があり、位置の対応表が作れる（ADR-008）→ NFR 要件
  - 「既定の候補にしない」指定が Spring Boot 4.1 系で働く（ADR-006）→ 最初の Bolt
  - DSL の投入の API だけ本文の上限を 5MB にできる（今は全要求に 1MB）→ NFR 設計・コード生成
  - 100テーブル×100カラムのメタデータを 30 秒以内に読める（テーブルごとの往復を避け、まとめて読む）→ NFR 設計・Build and Test
  - 3種類の DB の結合テストを Testcontainers で動かせ、colima の VM のメモリに収まる → Build and Test（team.md の Testing Posture で実測して決める）
  - JDBC ドライバーのライセンス（MySQL Connector/J は GPL v2＋FOSS 例外、MariaDB Connector/J は LGPL 2.1、PostgreSQL JDBC は BSD 2-Clause）を確かめ、採用の理由を記録する → NFR 要件（team.md の Code Style）
  - 組み込みの H2 によるアプリ1つの前提（ADR-004）→ 今回の範囲では変えない
- **Consequences** — 良い点: 不確かな点と、その確かめる段がはっきりする。悪い点: 条件のどれかが満たせないと、設計の見直し（ADR-006・ADR-008 の切り替え先）が要る。セキュリティ・コンプライアンス: ライセンスの確認は配布（GitHub のリリースの WAR）に関わるため、採用の前に行う。
- **Alternatives Rejected** — 実現可能性を確かめてから設計に入る（段を止める）: 今回の不確かな点はどれも小さく試せば分かるもので、設計を止めるほどではない。
