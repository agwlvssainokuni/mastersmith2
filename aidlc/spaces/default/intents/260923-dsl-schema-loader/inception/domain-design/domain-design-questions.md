# Domain Design — 質問

この段では、今回作る部品（書くコードのまとまり）の分け方と、それぞれが持つデータ、部品どうしの呼び出しを決めます。配備の形（1つのアプリか分けるか）は次の Units Generation で、道具（部品の選定）や性能の作りは NFR の段で決めます。

この Intent は Ideation の段（実現可能性の評価）を行っていないため、実現できるかどうかの判断もここで扱い、質問と設計の記録（ADR）に残します（`aidlc/spaces/default/memory/project.md` の Way of Working）。

前提（既存の構成、`aidlc/spaces/default/codekb/mastersmith2/architecture.md`）:
- アプリは1つのプロセスのモノリスで、機能ごとのパッケージ（`auth`・`access`・`audit`・`user`）の中が `web`・`service`・`domain`・`repository` の層に分かれている（ArchUnit で確かめている）。
- 内部DB は組み込みの H2 で、アプリは1つだけ動かす前提（ファイルを共有する複数の起動はできない）。
- 監査は `audit` が、アプリの中の出来事を受けて記録する。

今回の働きは、大きく「対象DB に接続してメタデータを読む・照合する」「DSL の書式と解釈（後続の Intent I・J・K が使うモデル）」「DSL の管理の操作（生成・投入・プレビュー・適用・履歴）」に分かれます。

B. 2つに分ける: `targetdb` と `dsl`（書式・解釈・管理の操作をまとめる）
C. 1つにまとめる: `dsl` の中にすべて

## Q2. DSL を内部DB にどう持つか

プレビュー1件・適用中1件・適用の履歴（最大20件、履歴から戻せる）を持ちます。

A. プレビューの表と、適用の履歴の表の2つに分ける。適用中の DSL は、履歴の中の最新の1件とする。適用では、プレビューの行を履歴に移し、古い履歴を消す
B. 1つの表「DSL の版」に、状態（プレビュー・適用中・過去の適用）を持たせる。状態ごとの件数の決まり（プレビューと適用中は最大1件）を表の制約で守る

[Answer]: A

## Q3. DSL を保存する形

A. 投入・生成された YAML の本文をそのまま保存し、識別（ハッシュ値）は本文のバイト列から求める。ダウンロードは保存した本文をそのまま返す（コメントや並びも残る）
B. 解釈した内容を決まった形に整えてから保存し、識別は整えた内容から求める（コメントは残らないが、書き方の違いだけでは別の版にならない）
X. Other (please specify)

[Answer]: A

## Q4. 適用中のモデルをアプリの中でどう持つか（後続の Intent が使う）

内部DB は組み込みの H2 のため、アプリは1つだけ動く前提です。

A. アプリの中に、適用中の DSL を解釈したモデルを1つ持つ。起動時に内部DB から読み、適用が確定した後に差し替える。後続の Intent には、モデルを取り出す提供口を1つ渡す
B. 要求のたびに内部DB から読んで解釈する（アプリの中には持たない）

## Q5. DSL に対象DB の上の型を記録するか

プレビューで「型の食い違い」を警告する（ストーリーの AC3.2.3）には、DSL がカラムの DB 上の型を持つ必要があります。

A. 記録する。既定の DSL の生成で、カラムごとに DB 上の型の情報（型の名前・長さ・精度・NULL を許すか）を機械的に入れる。人は通常この項目を直さない
B. 記録しない。照合はテーブル・カラムがあるかどうかだけにし、型の食い違いの警告はやめる（ストーリーの AC3.2.3 を見直す）

[Answer]: A

## Q6. 対象DB への接続の持ち方

内部DB の接続は、Spring Boot が自動で1つ作っています。ここに対象DB の接続を普通に足すと、自動の作成が止まり、ログイン・監査・Flyway が対象DB を向いてしまうおそれがあります（既存のコードの懸念 C-2）。

A. 内部DB の接続を明示して「既定」にし、対象DB の接続は名前付きの別の接続にする（小さなプール、読み取り専用、短い待ち時間）
B. 対象DB の接続は、既定の候補にならない別の接続として足す（Spring Boot の「既定の候補にしない」指定を使う）。内部DB の自動の作成には手を入れない。小さなプール・読み取り専用・短い待ち時間にする。この指定が今の Spring Boot の版で使えるかは、最初の Bolt で確かめ、使えなければ A に切り替える
C. 対象DB の接続を常には持たず、操作のたびに接続を開いて閉じる（プールを持たない）。操作は手動でまれなため
X. Other (please specify)

[Answer]: B

## Q7. 画面でも DSL を検証するか

要件で、検証はサーバー側を正とし、画面での検証をその代わりにしないことを決めています。

A. 画面では検証しない。JSON Schema はバックエンドに同梱した1つだけを正とし、誤りの一覧はサーバーの応答で示す
B. 同じ JSON Schema を画面にも取り込み、送る前に検証して早く知らせる（正はバックエンドのまま）

[Answer]: A

## Q8. 誤りの位置（YAML の行・列）の求め方の見通し

JSON Schema の検証の部品は、誤りの場所を JSON の位置（パス）で返します。行・列にするには、YAML を読むときに位置の情報を残して対応づける必要があります。ここは今回で最も技術的に不確かな点です（ストーリーの US2.2）。

A. YAML を読むときに、各値の行・列を記録した対応表を作り、検証の誤りのパスから行・列を引く設計にする。部品の選定（YAML・JSON Schema）では、この対応が作れることを条件にし、NFR 要件の段で試して確かめる
B. 行・列は求めず、DSL の中の場所（パス）だけを示す（ストーリーの AC2.2.1 を見直す）

[Answer]: A
