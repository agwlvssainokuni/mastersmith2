# Bolt Plan — dsl-schema-loader

Bolt（1回分の作りの区切り。設計から実装・テストまでを通し、動くものができて終わる）の順序と、それぞれの完了の条件を示す。確定した答えは `delivery-planning-questions.md` の Q1〜Q5、順序の理由は `risk-and-sequencing-rationale.md`。

## 前提

- Bolt は依存の順に1つずつ作り、並行しては作らない（Units Generation の Q4: B）。
- 設計と実装は、設計の段ごとにすべての単位を通し、最後にコード生成を Bolt の順に行う（Q4: A）。各段の承認は段ごと。
- walking skeleton（最初に全体を細く通して確かめる進め方）の特別な手順は行わない。アプリの骨格はすでにあり、`aidlc/spaces/default/memory/team.md` の Walking Skeleton の一式（1コマンドの検査・カバレッジの下限・CI など）は維持されている前提で、各 Bolt を通常どおり進める。
- 各 Bolt の作業ブランチは `develop` から作り、統合前の1コマンドの検査（`./gradlew verify`）がすべて通ってから `develop` へ squash マージする（1 Bolt が1コミット、日本語の件名）。`origin` へのプッシュは依頼者が行う（team.md の Way of Working）。
- すべての Bolt に共通する完了の条件: テストを含む（test-after、層ごとに実装してすぐテスト）、行カバレッジ 80%・分岐カバレッジ 70%（バックエンドはパッケージごとの下限も team.md のとおり）、ソースの先頭の Apache License 2.0 のヘッダー、秘密情報の検出・依存関係の脆弱性の検査（High 以上で止める）・SpotBugs（SQL インジェクション系は priority によらず止める）を通すこと。

## Bolt ごとの内容

### B1 DSL の定義（U2）

- **含む単位**: U2（DslDefinition・ActiveDslModel）
- **walking skeleton**: いいえ
- **完了の条件**:
  - DSL の書式（JSON Schema・書式の版 1）がアプリに同梱され、構文と意味の検証ができる
  - YAML の安全な読み込み（大きさ 5MB・入れ子の深さ・別名の数の上限、タグの拒否、重複キーの誤り）と、誤りの行・列・場所の一覧が返る
  - team.md の「投入 DSL の必ず書くテスト」（上限ちょうどと超え、タグ、重複キー、`$ref`、拒否の応答）がすべてある
  - 適用中のモデルの保持と提供口（C8）ができ、差し替えが一度に切り替わる
  - 選んだ YAML・JSON Schema の部品のライセンスを確かめ、記録してある
- **確かめたいこと（この Bolt で分かること）**: 誤りの行・列を、実用的な正しさで求められるか（ADR-008）。Jackson 3 系と組み合わせられる部品で、安全な読み込みと位置の対応表を両立できるか
- **見せ方（デモ）**: 誤りを含む DSL を読み込ませるテストで、行・列・場所つきの誤りの一覧が返ること。危険な形の DSL が上限で止まること

### B2 対象DB（U1）

- **含む単位**: U1（TargetDatabase）
- **walking skeleton**: いいえ
- **完了の条件**:
  - `mastersmith.target-db.*` の設定と起動時の点検（問題のある項目の名前だけの WARN）、パスワードの伏せ字
  - 対象DB の接続を「既定の候補にしない」指定で足し、ログイン・監査・Flyway・ヘルスチェックが内部DB を向き続けることを結合テストで確かめてある（ADR-006）
  - 対象DB の設定が無い・止まっている・応答しないときも起動し、使う操作だけが区別された結果で失敗する
  - 最初の1種類の DB でメタデータを読める（3種類は B3 で揃える）
  - Testcontainers の導入（依存・結合テストの段・colima と CI の前提の文書化・README の見直し）、コンテナが無いときは警告して対象DB のテストだけを飛ばす（統合前には必ず通す）
  - JDBC ドライバーのライセンスを確かめ、記録してある
- **確かめたいこと**: 既存の自動構成を変えずに2つ目の接続を足せるか。Testcontainers を colima と CI で動かせるか
- **見せ方**: 結合テストで、対象DB のメタデータが読め、同時にログインと監査が内部DB で動くこと

### B3 既定の DSL の生成（U3）

- **含む単位**: U3（DefaultDslGeneration）
- **walking skeleton**: いいえ
- **完了の条件**:
  - 表示名（ja・en に物理名、コメントがあれば ja にコメント）、1階層のメニュー（物理名の順）、ビューの読み取り専用、DB 上の型の情報、型と制約からのフォーム部品とバリデーション
  - MySQL・MariaDB・PostgreSQL の3種類で、既定の DSL が作られ、B1 の検証を通る
  - 100テーブル×100カラムで 30 秒以内（測れないときは `Unverified` として持ち主の段を明記する）
- **確かめたいこと**: 3種類の DB の型の違いを1つの規則で吸収できるか。メタデータを想定の規模で間に合う時間で読めるか
- **見せ方**: 3種類の DB のコンテナから作った既定の DSL が、同じ形で検証を通ること

### B4 DSL の管理（基本、U4 の Must）

- **含む単位**: U4（DslLifecycle・DslPreviewAnalysis・AuditLog の拡張）の Must の部分
- **walking skeleton**: いいえ
- **完了の条件**:
  - 管理者だけの API（`/api/admin/dsl/`）: 今の状態、スキーマの読み込み、投入（アップロード・貼り付け、5MB まで）、プレビューの取得、破棄、適用（見たプレビューの指定）、プレビュー中のダウンロード
  - プレビューの表と適用の履歴の表（Flyway の移行）、YAML の本文のままの保存、適用での履歴への書き込みと件数の上限（既定20件）、同時の適用は1件だけ成功、一度に切り替わる確定
  - 起動時の適用中のモデルの読み込みと、確定の後の差し替え
  - 要約・違い・対象DB との照合の警告
  - 共通のエラー応答の拡張（追加の項目の口）と、誤りの一覧の応答（422、先頭100件と総数）、新しい `code` の登録
  - 監査の拡張（表の列・出来事の種類）と、生成・投入・受け付けなかった投入・適用・破棄の記録
  - 各 API の 401・403・200 のテスト
- **確かめたいこと**: プレビュー → 適用の流れと同時の操作が、決めた契約（`inception/contract-design/contract-summary.md`）のとおりに動くか
- **見せ方**: API を順に呼ぶ結合テストで、読み込み → プレビュー → 適用 → 再起動の後も適用中、の流れが通ること。置き換えられたプレビューの適用が 409 で止まること

### B5 DSL の管理（履歴、U4 の Should）

- **含む単位**: U4 の Should の部分
- **walking skeleton**: いいえ
- **完了の条件**:
  - 履歴の一覧（新しい順、適用中の印）、履歴の版をプレビューに戻す（検証と照合を行う）、適用中のダウンロードの API
  - 戻しの監査（投入の一種）
  - 各 API の 401・403・200 のテスト
- **確かめたいこと**: B4 の履歴の書き込みの上に、戻しを足しても一貫した状態が保てるか
- **見せ方**: 3回適用した後に、2つ前の版に戻して適用できること

### B6 DSL の管理画面（U5）

- **含む単位**: U5（DslAdminUi・ApiClient の拡張）
- **walking skeleton**: いいえ
- **完了の条件**:
  - サイドバーの「DSL」（管理者だけ）、1つの画面の今の状態とタブ（プレビュー・投入・履歴）、`inception/refined-mockups/` のとおりの状態（空・処理中・誤り・拒否・確認）
  - ファイルの選択・違いの表の行の開閉・メニューの木を画面の側で作る（make-you-chic-ui は変更しない）
  - ApiClient が誤りの一覧を含む応答を受け渡せる
  - ja・en の文言、WCAG 2.1 AA、部品ごとの axe の検査
  - すべての DSL の操作の API を並べた一括の 401・403・200 の確かめ（US6.2）
- **確かめたいこと**: 管理者が画面だけで、読み込み → 確かめ → 適用 → 戻し まで迷わず操作できるか
- **見せ方**: 画面で、スキーマの読み込み → プレビューの確認 → 適用 → 履歴から戻す、を通して操作すること

## Construction の進め方の記録

- 設計の段ごとにすべての単位を通す（stage-major、Q4: A）。この Intent の状態には何も書き足さない（既定のまま）。
- 作るのは1つの場で、単位ごとにチームを分けない（solo）。
- 気がかりな2点（ADR-008 の行・列、ADR-006 の接続の足し方、Q5: A・B）は、コード生成が最後になるため、NFR 要件の段で小さく試して確かめる（本番のコードとは別の試しのコード）。確かめられなければ、ADR の切り替え先を依頼者に諮る。
