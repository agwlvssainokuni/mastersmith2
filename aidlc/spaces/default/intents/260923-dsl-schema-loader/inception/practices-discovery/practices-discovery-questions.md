# Practices Discovery — 質問

チームの進め方（`aidlc/spaces/default/memory/team.md` の5節）は前の Intent で確定済みです。今回の Intent（DSL の定義、対象DB（MySQL・MariaDB・PostgreSQL）のメタデータからの既定 DSL の生成、利用者が投入する DSL の読み込み・検証・プレビュー→適用）で、確定済みの進め方のままでは決まらない点だけを質問にしました。

次の点は、進め方ではなく要件や設計の中身なので、ここでは聞かず、後の段（要件定義・ドメイン設計・機能設計）で扱います。

- 「適用」が対象DB に書き込むのか、アプリの中の DSL を切り替えるだけなのか。これが決まるまで、規則の候補「NEVER 対象DB のスキーマやデータを変更しない」は保留にします。
- 2つ目の接続設定（対象DB 用の `DataSource`）の足し方、機能パッケージの切り方、画面の機能の置き場
- E2E に「DSL の生成 → プレビュー → 適用」の流れを足すか
- DSL の検証エラーを行・項目ごとに返す形と、そのための共通部品（`common/error`・`shared/api-client`）の変更

## Q1. 対象DB の3種類のテストを、どこで実行しますか

team.md では、内部DB（H2）以外の DB のテストは Testcontainers（テストのたびに本物の DB をコンテナで起動する仕組み）で行うと決めています。今回、MySQL・MariaDB・PostgreSQL の3種類が加わります。3種類とも毎回動かすと、統合前の1コマンドの検査（`./gradlew verify`）の時間と colima の VM のメモリが増えます。一方で team.md は「CI と同じ検査を、統合前にローカルの1コマンドで通す」と決めています。

A. 3種類すべてを `./gradlew verify` の中で毎回実行する（CI も同じ）。時間とメモリは Build and Test で実測する
B. 3種類すべてを `./gradlew verify` の中で実行するが、1種類ずつ順に起動し、同時に動くコンテナは1つだけにする（CI も同じ）
C. `verify` では代表の1種類だけを実行し、残り2種類は CI だけで実行する（統合前の検査と CI の検査が食い違う）
D. 実測してから決める。Build and Test までは A を仮に置く
X. Other (please specify)

[Answer]: D

## Q2. 対象DB のテストで、テストどうしが影響し合わないようにする方法

B. テストのクラスごとにコンテナを起動し直す（遅いが確実）
C. 設計の段で決める

## Q5. 利用者が投入する DSL（YAML）を信頼できない入力として扱う決まりを、チームの基準に入れますか

投入された YAML には、別名（アンカー）の展開の爆発、深すぎる入れ子、大きすぎる本文、任意の型を作るタグ（`!!`）、重複したキー、`yes`・`on` が真偽値に化けること、JSON Schema の `$ref` で外部の URL を取りに行くこと、などの危険があります。後続の Intent でも利用者の投入を扱います。

A. 基準に入れる。決まり（大きさ・入れ子の深さ・別名の数に上限を置く、タグと任意の型の生成を拒否する、重複キーをエラーにする、外部の `$ref` を取りに行かない、検証はサーバー側を正とする）と、それを確かめる「必ず書くテスト」（認証・認可・監査と同じ扱い）を team.md に加える。具体的な数値は設計の段で決める
B. 基準には入れず、今回の Intent の NFR 要件だけで扱う

## Q9. 固い制約（必ず守る規則）として加えるものを選んでください（select all that apply）

既存の Mandated 8件・Forbidden 4件はそのまま有効です。既存の Forbidden はパスワード・トークン・署名鍵だけを対象にしており、対象DB の接続先・ユーザー名・JDBC の URL は含みません。選んだものは `project.md` に日付つきで追記されます。

A. NEVER 対象DB の接続情報（接続先・ユーザー名・パスワード・資格情報を含む JDBC の URL）を、生成した DSL・プレビューの応答・画面・ログ・監査ログ・エラー応答に含めず、画面・API・DSL から受け取らない（設定だけから受け取る）
B. ALWAYS 対象DB の結合テストは、版を固定したイメージのコンテナで起動した実際の MySQL・MariaDB・PostgreSQL で行い、H2 などの別の DB やモックで代用しない
C. NEVER JDBC の例外や、YAML・JSON Schema の部品の例外のメッセージを、そのままエラー応答に含めない
D. ALWAYS 利用者が投入する DSL（YAML）は信頼できない入力として扱い、大きさ・入れ子の深さ・別名の数の上限を明示し、タグと任意の型の生成を拒否し、重複キーをエラーにする
E. どれも加えない
