# Risk and Sequencing Rationale — user-admin

この文書は、Bolt の順をなぜこう決めたかを示す。Bolt は、1つ以上の単位をまとめて作り終え、動くものができる1回の作る区切りのこと。

出典: `bolt-plan.md`、単位の依存 `aidlc/spaces/default/intents/260930-user-admin/inception/units-generation/unit-of-work-dependency.md`、ドメイン設計の ADR `aidlc/spaces/default/intents/260930-user-admin/inception/domain-design/decisions.md`、契約 `.../contract-design/contract-summary.md`、この段の答え `delivery-planning-questions.md`（Q1〜Q5）。

## 使った考え方

危険の大きいものを先にする考え方（Cohn のリスク優先）だけで順を決めた。WSJF（価値と急ぎ具合を大きさで割って点数を付け、高いものから作るやり方）の点数付けは使っていない。理由は2つある。

- 依存がほぼ決まっていて、順の選び方が U1・U2・U4 の前後だけにある。
- 5つの単位は、すべてそろって初めて利用者に価値が出る（管理の画面は1つ）。単位ごとの価値の差で順を決める意味が薄い。

前の Intent（dsl-schema-loader・user-management）と同じ扱い。

## 順と理由

| 順 | Bolt | 理由 |
|---|---|---|
| 1 | B1 U1 | 危険が最も大きい。認証の3つの入口すべてに手が入る。列挙の防止（ログインの時間と読み書きの回数をそろえる仕組み）を崩すと、ほかのすべての利用者に影響する。`auth` の一覧のパッケージの作業もここで済ませ、後の B3・B4 を軽くする。`.idea/.gitignore` は最初の Bolt に置く決定（UQ2 A）どおり B1 に入る |
| 2 | B2 U2・U4 | 既存のコード（招待のページ送り・管理の3つの画面）を、振る舞いを変えずに動かす土台の作業。U2 と U4 はどちらも招待の画面に手を入れるため、まとめて一度で直す（Q1 B、Units Generation のレビューの R-01）。B3 は U2 の Paging を使い、B5 は U2・U4 を使うため、B3 より前に置く |
| 3 | B3 U3 前半 | 一覧はほかの操作の確かめの土台になる（ストーリーの対応の「単位の中の順」）。行の排他と監査が無いため、危険の小さい半分を先に統合し、後半の差分を小さくする（Q2 B） |
| 4 | B4 U3 後半 | 最後の管理者の保護の同時性（ADR-007 の項目1）と、ログインの判定との排他の順（申し送り R-07）が最も難しい。B3 の一覧の上に作り、単独の Bolt で確かめる（Q2 B）。前倒しの試しのコードは作らない（Q5 A） |
| 5 | B5 U5 | 画面は、すべての API（B3・B4）と土台（B2）がそろってから作る。E2E は検索で利用者を探すため、検索も B3・B5 で一覧と一緒に作る（Q3 A） |

## 単位の依存の図との違い

単位の依存の図（U3 は U1・U2 の後、U5 は U2・U3・U4 の後）に反する順は無い。図では U1・U2・U4 のどれを先にしてもよく、この計画は U1 を最初に、U2・U4 を次に置いた（上の理由）。U3 を2つの Bolt に分けたが、同じ単位の中の分け方で、単位の間の依存は変わらない。

## 危険と手当て

| 危険 | 当たる Bolt | 手当て |
|---|---|---|
| 停止の判定で列挙の防止が崩れる | B1 | 停止中のログインで読み書きの回数をそろえる（ADR-008）。機能設計で成り立つかを確かめる（ADR-007 の項目4）。応答と時間のテストで確かめる |
| 同時の操作で有効な管理者が 0 人になる | B4 | 管理者の行を決まった順で排他する（ADR-007）。待ち合わせで重ねたテストで確かめる（`team.md`） |
| ロックの状態の行と users の行の排他の順の食い違いで、ログインと管理の操作が行き詰まる | B4 | 申し送り R-07 として機能設計・NFR 設計で順を決め、ログインと重ねたテストで確かめる |
| 検索の文字がログに出る | B3 | 申し送り R-06 として Converter を TraceAspect の対象の外に置き、TRACE を有効にした漏えいのテストで確かめる |
| 招待の画面の振る舞いが変わる | B2 | 招待の既存のテストを直さずに通すことを完了の条件にする |
| make-you-chic-ui の固定先の更新で、ほかの画面の表示が変わる | B5 | 固定先の更新を専用のコミットにし、E2E と画面部品の検査を流す。差が出たら更新の範囲を依頼者に確かめる |
| U3 を2つに分けたため、B3 と B4 の境目で設計がずれる | B3・B4 | U3 の設計は1つの単位として通してから、コード生成の計画で分ける（Q4 A） |
