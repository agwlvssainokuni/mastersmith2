# Bolt Plan — user-admin

Bolt は、1つ以上の単位（Unit）をまとめて作り終え、動くものができる1回の作る区切りのこと。作業ブランチ1本で作り、`./gradlew verify` を通して `develop` に統合するまでを1つと数える。この文書は Bolt の順と、それぞれの完了の条件を示す。

出典:
- 単位 `aidlc/spaces/default/intents/260930-user-admin/inception/units-generation/unit-of-work.md`、依存 `unit-of-work-dependency.md`、ストーリーとの対応 `unit-of-work-story-map.md`
- 契約 `aidlc/spaces/default/intents/260930-user-admin/inception/contract-design/contract-summary.md`
- 要件 `requirements.md`、ストーリー `stories.md`、画面 `mockups.md`、部品 `components.md`、チームの進め方 `team-practices.md`
- この段の答え `delivery-planning-questions.md`（Q1〜Q5）

順の理由は `risk-and-sequencing-rationale.md` に書いた。

## 前提

- U2 と U4 を1つの Bolt にまとめ（Q1 B）、U3 を前半と後半の2つの Bolt に分ける（Q2 B）。合わせて5つの Bolt になる。
- 設計の段（機能設計・NFR 要件・NFR 設計・基盤の設計）は段ごとにすべての単位を通し、コード生成を最後に下の Bolt の順で行う（Q4 A、stage-major）。U3 の設計は1つの単位として行い、コード生成の計画で前半と後半の2つの Bolt に分ける。
- Bolt は1つずつ順に作り、並行して作らない（Units Generation の UQ3 A）。
- walking skeleton（アーキテクチャの端から端までを最初に通す最小の作り）の特別な手順は行わない。アプリの骨格はすでにある（`team.md`）。
- すべての Bolt に共通の完了の条件:
  - 統合の前に1コマンドの検査（`./gradlew verify`）が通る。中身はフォーマット・リンタ・ライセンスヘッダー・ビルド・全テスト・対象DB の結合テスト・カバレッジの下限・秘密情報の検出・静的解析・依存関係の脆弱性検査。
  - カバレッジは `:backend:cleanTest :backend:cleanIntegrationTest` を付けて実測し、値を記録する。
  - 画面・認証に関わる Bolt（B1・B2・B5）は、統合の前に E2E（`./gradlew e2eTest`）を手元で流す。
  - 統合は `develop` への squash とする。B2 は単位ごとの squash（2コミット）にしてよく、どちらにするかはコード生成の計画で決める。B5 はサブモジュールの固定先の更新を含むため、fast-forward でよい。
  - 統合の後の CI が通る。

## B1 利用停止の土台（U1）

- **単位**: U1 u1-user-suspension（ストーリー US3.2）
- **完了の条件**:
  - `users` に停止の状態の列が V9 で足され、既存の利用者は「有効」になっている（前進のみ・後方互換、NFR10）。
  - 停止中の利用者が、3つの入口（ログインの照合・トークンの更新・アクセストークンの認証）のすべてで、入口ごとのほかの失敗と同じ応答で拒否される（FR3.2・FR3.4）。停止を解くと3つの入口すべてで受け付ける。これを入口ごとのサーバー側のテストで確かめている（`team.md` の利用停止の必須テスト）。
  - 停止中のログインで、失敗回数とロックの状態が変わらない。読み書きの回数がパスワードの誤りとそろっている（ADR-008、AC3.2.8）。
  - 監査に、ログインの失敗の理由 `ACCOUNT_SUSPENDED` が残る（C7）。
  - リフレッシュトークンをまとめて無効にする口（C1）が、同じトランザクションの中で動く。
  - `.idea/.gitignore` に `dataSources.xml`・`dataSources/` が足されている。
  - `auth.domain`・`auth.repository` が `packagesJudgedByTotal` の一覧から外れ、パッケージごとの下限を満たしている。2026-10-01 の実測は `auth.domain` が行 97.9%・分岐 100.0%、`auth.repository` が行 93.9%・分岐 50.0%（分岐は2つ）。
- **確かめたいこと**（confidence hypothesis。この Bolt を出すことで分かること）: 停止の判定を3つの入口に足しても、既存の列挙の防止（ログインの時間と読み書きの回数をそろえる仕組み）と、`user` が `auth` を知らない境界（NFR11）を崩さずに済むか。
- **見せ方**: 結合テストで、停止した利用者が3つの入口で拒否され、解くと通ること、監査の理由が残ることを示す。

## B2 共通の土台（U2・U4）

- **単位**: U2 u2-shared-paging（US1.1 のページ送り）・U4 u4-admin-forbidden-ui（US2.2）
- **完了の条件**:
  - サーバーのページ送りが `common.paging`（C2）に、画面のページ送りが `src/shared/`（C5）に移っている。招待の一覧の振る舞いは変わらず、招待の既存のテストが通ったまま。性質ベースのテスト（jqwik・fast-check）がある。
  - ApiClient と AppFrame が、`/api/admin/` の下の `ACCESS_DENIED`（403）を共通の扱いで表示する（C4）。管理の入口・DSL・招待の画面がこれに置き換わり、ログインの状態を読み直して管理のメニューを消す。既存の3つの画面のテストが新しい表示に合わせて直っている。
  - 自分の氏名と言語だけを画面に当てる口（C4 の `useApplyOwnProfile`）がある。
  - 新しい画面部品ごとにアクセシビリティの検査が1件ある。
  - 招待の画面（InvitationUi）は、この Bolt の中で一度だけ直す（Units Generation のレビューの R-01）。
- **確かめたいこと**: 既存の画面と招待のコードを、振る舞いを変えずに共通の部品へ移せるか。403 の扱いを骨組みに置く形（ADR-005）が、既存の3つの画面にそのまま当てはまるか。
- **見せ方**: 管理者でない利用者が管理の画面を開くと、どの画面でも同じ「この画面を使う権限がありません」が出る。403 はテストで差し替えて作る（Units Generation の R-02）。招待の一覧のページ送りが前と同じに動く。

## B3 一覧と氏名・言語の変更（U3 前半）

- **単位**: U3 u3-user-admin-api の前半（US1.1・US5.1 のサーバー側）
- **完了の条件**:
  - `GET /api/admin/users`（一覧・検索・ページ送り、C3）が、登録した順・20 件・全体の件数を返す。ロックの判定の結果は `locked`・`lockedUntil`・`resettable` だけで、失敗回数そのものは返さない（FR1.6）。
  - 検索が、大文字小文字を区別しない部分一致で動き、`%`・`_` を文字どおりに扱う。ページの番号・検索の文字の誤りは `VALIDATION_FAILED` になる。
  - `PUT /api/admin/users/{userId}/profile` が氏名と言語を変える（自分自身を含む、FR6）。対象がいなければ `USER_NOT_FOUND`（404）。
  - 新しいパッケージ `useradmin` とその境界テスト（`UserAdminBoundaryArchitectureTest`）がある。
  - TRACE を有効にした漏えいのテストで、検索の文字・メールアドレス・氏名がアプリのログとトレースの属性に出ないことを確かめている（AC1.1.6）。検索の文字は `SearchText` で受け、Converter の置き場は申し送り R-06 のとおり TraceAspect の対象の外にする。
  - 401・403・200 の認可のテストがある。
- **確かめたいこと**: 一覧のためのロックの判定の結果を、`user` が `auth` を知らない境界を保ったまま、`useradmin` で合わせられるか（C8）。
- **見せ方**: 結合テストで、ロック中・解除の予定の時刻の境界・行の無い利用者の一覧の表示と、検索の特殊文字の扱いを示す。

## B4 管理の操作と最後の管理者の保護（U3 後半）

- **単位**: U3 u3-user-admin-api の後半（US2.1・US3.1・US4.1 のサーバー側）
- **完了の条件**:
  - 5つの操作（grant-admin・revoke-admin・suspend・resume・reset-login-failures、C3）が、拒否の順（FR7.5）のとおりに code を返す。
  - 止める操作がリフレッシュトークンをまとめて無効にする（C1）。
  - 最後の有効な管理者を無くす操作は拒否され、状態が変わらない。これを、業務処理の層を直接呼ぶテストと、待ち合わせで重ねた2つの操作のテストの両方で確かめている（FR4.3・FR4.4）。
  - 失敗回数の取り消しとログインの判定が重なっても矛盾しない（FR5.4）。
  - 排他の待ちの上限切れは `USER_ADMIN_BUSY` になる。
  - 監査の出来事（C6）が、成功・拒否ごとに操作した人・対象・結果・理由とともに残る。
  - 申し送り R-04（`USER_ADMIN_BUSY` の監査）と R-07（行を排他する順）が、機能設計・NFR 設計で決めたとおりに作られている。
  - 管理の API の外（`/api/me`）から印や状態を変えられない（要求の改ざんのテスト）。
- **確かめたいこと**: 行の排他（ADR-007）で、同時の操作でも有効な管理者が 0 人にならず、ログインの判定とも行き詰まらないか（ADR-007 の項目1・項目4）。
- **見せ方**: 結合テストで、2人の管理者が同時に互いの印を外しても1人は残ること、監査の行を示す。

## B5 利用者の管理の画面（U5）

- **単位**: U5 u5-user-admin-ui（US1.1・US2.1・US3.1・US4.1・US5.1 の画面側）
- **完了の条件**:
  - make-you-chic-ui の固定先が `3481488` 以降に更新され、承認を得た専用のコミットに更新前後のハッシュが記録されている。
  - `frontend/.npmrc` に `ignore-scripts=true` があり、`vendor/make-you-chic-ui` のインストールとビルドが通る。
  - 画面イメージの S1〜S6 の一覧・検索・行の操作のメニュー・5つの確かめの表示・氏名と言語の入力・結果の知らせができている。自分の行の操作は押せない形で理由とともに出る（M6 B）。
  - 自分の氏名と言語を変えたら、画面に当たる（C4）。
  - 画面部品ごとのアクセシビリティの検査が、2語の氏名と誤りの状態で行われている（AC1.1.12、`project.md` の学び）。
  - E2E の代表の流れが1本ある。流れは、自分で作った利用者を検索で探し、ロック → 失敗回数を戻す → 止める → ログインできない → 停止を解く → ログインできる（M9 A、Q3 A）。初期管理者の状態は変えない。
- **確かめたいこと**: make-you-chic-ui の Dropdown（押せない項目と理由の文）で、行の操作のメニューが画面イメージどおりに作れるか。
- **見せ方**: E2E の流れと、画面のスクリーンショット（light・dark）。
