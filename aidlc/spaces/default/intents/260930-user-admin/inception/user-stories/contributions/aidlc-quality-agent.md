## Contribution

品質担当として、受け入れ基準（AC）の試験できる度合いを見た。合否がはっきりしない所・境界値の抜け・失敗の場合の抜け・`team.md` の必須テストとの対応の抜けを、AC の ID ごとに「直す案」「足す案」として書く。根拠のコードは読み取りだけで確かめた（パスはプロジェクトのルートからの相対パス）。

見出しの記号: **【直す】** 今の AC の文言を変える案、**【足す】** 新しい AC の案、**【判断】** どちらの考えもありうる点（依頼者に尋ねる候補）、**【設計へ】** AC は書けるが値や仕組みを後の段で決める点。

### 1. 前提と読み方（共通）に足すもの

- **【足す】判定の仕方（ロックの境界）**: 「ロック中」は `now < 解除の予定の時刻` のときだけとし、解除の予定の時刻ちょうどはロック中でない（`backend/src/main/java/cherry/mastersmith/auth/domain/LockPolicy.java` の BR3.3・BR3.4 と同じ）。一覧の表示・「失敗回数を戻せるか」・ログインの判定の3つが同じ境界を使うことを前提に書く。
- **【足す】利用者 ID の形の誤りと、いない利用者の区別**: パスの利用者 ID が数でない（`abc`・空・桁あふれ）は入力の誤り（`VALIDATION_FAILED`、監査に残さない）、数だが利用者がいないは「対象の利用者がいない」（業務の誤り、監査に残す、FR7.6）。この境目を前提に一度だけ書き、各ストーリーの「対象の利用者がいない」の AC はこの前提を参照する。今のままでは FR1.5・FR7.3（入力の誤りは残さない）と FR7.6（いない ID は残す）の境目が AC から読めない。
- **【足す】拒否したときの応答**: 業務の誤り4つ（対象の利用者がいない・自分自身への操作・変えるものが無い・最後の有効な管理者の保護）は、それぞれ別の安定した `code` と、1つの code に1つの状態コードを持つ Problem Details で返る（`team.md` の Code Style）。AC の「拒否される」は「その理由の code で拒否される」と読む、と前提に書く。code の名前と状態コードは機能設計で決める【設計へ】。
- **【直す】「状態が変わらない」の確かめ方**: 今の定義（印・停止・失敗回数・ロック・トークン）に「その利用者の `login_attempt_states` の行の有無」を足す。行の無い利用者への拒否で行が作られないことまで確かめられるようにするため（K-2）。
- **【足す】監査の確かめ方の対象**: 監査の行の「種類（event_type）」が操作ごとに別であること（印を付ける・外す・止める・解く・失敗回数を戻す の5つ）も確かめる。今の前提は操作した人・対象・結果・理由だけで、どの操作の行かを区別する項目が抜けている。種類の名前は機能設計（32 文字まで、K-6）【設計へ】。
- **【足す】業務の拒否の監査は、業務の取り消し（ロールバック）の後でも残る**: 拒否した操作のトランザクションは巻き戻るが、失敗の監査の行は残る（既存の `AuditRollbackIT` と同じ形）。監査の書き込みに失敗したときの扱いは既存の決まり（確定の後に記録、`AuditWriteFailureIT`）にそろえるのか、管理の操作だけ変えるのかを前提に書く【判断】（`team.md` の★「監査ログの書き込みに失敗したときに操作を失敗させるか」が、この Intent の操作についてはまだ決まっていない）。

### 4. US2.1 管理者の印

- **【直す】AC2.1.1・AC2.1.2**: 「次の要求から」を試験の形にする: 「印の変更の応答を受けた後、B の**同じアクセストークン**での次の管理の API の呼び出しが 200／403 になる」。画面の持つ古い印に頼らないことを、トークンを取り直さずに確かめる（`team.md` の必須テスト、既存 `AdminAccessIT` の "removing the administrator flag in the database denies the very next request" と同じ形）。
- **【直す】AC2.1.6 同時の重なりの合否**: 「0 人にならない」に加えて、合否を次の形で決める。
  - 2つの操作のうち**ちょうど1つが成功**し、もう1つは「最後の有効な管理者の保護」の code で拒否される。
  - 終わった後の有効な管理者はちょうど1人。監査は成功1行・失敗1行。
  - 重なりは、2つの操作が「有効な管理者の数を数える直前」でそろうまで待つ待ち合わせ（`invitation/testsupport/TestInvitationBarrier` と同じ形のテスト用の差し込み）で作り、待ち合わせの時間切れはテストの失敗とする。
  - **【判断／設計へ】後に動く側の「操作した人」がもう管理者でないとき**: A が B の印を外して確定した後に、B の「A の印を外す」が進むと、B は要求の入口の認可は通ったが、処理の中ではもう管理者でない。このとき拒否の理由を「最後の有効な管理者の保護」とするのか、処理の中で操作した人をもう一度確かめて別の理由（403 など）にするのかで、テストの期待が変わる。要件の理由の4つには「操作した人がもう管理者でない」が無い。今の AC の書き方（拒否された側は最後の管理者の保護）は前者を前提にしているので、設計で後者を選ぶなら AC を直す。
- **【足す】AC2.1.6 の組み合わせ**: 「A が B の印を外す × B が A を止める」の、**違う種類の操作の重なり**も1件足す（FR4.3 の「互いの印を外す・互いを止めるなど」。同じ種類どうしだけだと、印と停止を別の数え方で判定していても通ってしまう）。
- **【足す】数え方の境界（業務処理の層を直接呼ぶテスト、FR4.4）**: 次の3件を AC にする。
  1. 有効な管理者が対象 B だけで、ほかの管理者 C は**ロック中** → B の印を外す操作は受け付けられる（ロック中も数える、FR4.1）。
  2. 有効な管理者が対象 B だけで、ほかの管理者 C は**利用停止中** → 拒否され、B の印は変わらない（停止中は数えない）。
  3. 1 と同じで操作が「B を止める」でも同じ結果。
  今の AC2.1.6 の後半「有効な管理者が1人のときの印を外す操作が拒否される」だけでは、ロック中・停止中の数え方の違いを確かめられない。
- **【足す】停止中の利用者に印を付ける**: 受け付けるか（停止中でも印は持てる）を AC に書く。付けても有効な管理者の数は増えない。要件に書かれていないので【判断】（受け付ける案が自然と考える）。
- **【直す】AC2.1.7 要求の改ざん**: FR8.3 は「管理者の印・利用停止・失敗回数」の3つを挙げるが、AC2.1.7 は印だけ。止めることと失敗回数も含めて「`/api/me` と `/api/me/preferences`・`/api/me/password` など、管理の API の外の要求の本文に、管理者の印・停止の状態・失敗回数の項目を入れても、どれも変わらない」とする。また AC5.1.6（下記）の管理の API の側の改ざんと対にする。

### 6. US3.1・US3.2 利用停止

- **【直す】AC3.1.2 「止める前に出した B のトークンは使えないままである」— 要件と食い違う可能性が高い（重要）**: 要件 FR3.3 が無効にするのは**リフレッシュトークン**だけで、アクセストークンには失効の仕組みが無い（`project.md` DECIDED）。停止の判定は「アクセストークンの認証で DB の状態を見る」（要件 4節）ため、**停止を解くと、止める前に出したアクセストークンは有効期限（5 分）まで再び使える**のが今の設計の自然な結果になる。AC3.1.2 をそのまま試験にすると、実装が要件どおりでも落ちる。次のどちらかに決める【判断】:
  - (a) 止める前のアクセストークンは、停止を解いた後、有効期限までは再び受け付ける（ログアウトの後にアクセストークンが期限まで使えるのと同じ「決まった仕様」として AC に明記し、テストで確かめる。`team.md`: 停止の前に出したトークンの扱いは、決めた側の動作を明示したテストにする）。
  - (b) 止める前に出したアクセストークンは、停止を解いた後も拒否する（トークンの発行時刻と「最後に止めた時刻」を比べるなどの仕組みが要り、要件の追加になる）。
  AC3.2.4 の「止める前のリフレッシュトークンは使えない」は FR3.3 と合っているのでそのままでよい。
- **【足す】停止とトークンの更新の同時の重なり**: B のトークンの更新（新しいリフレッシュトークンを作る）と A の「B を止める（リフレッシュトークンをすべて無効にする）」が重なると、無効にした後に作られたリフレッシュトークンが残りうる。停止中は更新の入口で拒否されるので停止の間は害が無いが、**停止を解いた後にその残ったトークンが使える**と FR3.3（停止を解いても止める前のトークンは使えない）を破る。「待ち合わせで重ねた後に停止を解き、重なりの中で作られたリフレッシュトークンでの更新が 401 `REFRESH_FAILED` になる」を足す（既存の `RefreshConcurrencyIT` の形）。守り方（利用者の行の排他の順など）は設計【設計へ】。
- **【直す】AC3.2.3 応答の時間**: 「応答の時間をそろえる今の仕組みを崩さない」は壁の時計では合否が決まらない。「停止中の利用者のログインでも、パスワードの照合（ハッシュの比べ）とロックの状態の行の読み書きが、パスワードを誤ったときと同じ回数だけ行われる」など、仕組みの形で確かめる AC にする（`LoginServiceTest` の "an unknown email reads and writes a dummy row" と同じ考え方）。
- **【足す】停止中のログインの失敗と、ロック・監査の関係**: 要件に無い点で、試験の期待が決まらない。
  - 停止中の利用者が**誤った**パスワードでログインしたとき、失敗回数を数えるか（数えるとロックに進み、停止を解いた後にロック中で入れないことがある）【判断／設計へ】。
  - 停止中の利用者が**正しい**パスワードでログインしたとき、失敗回数を 0 に戻すか（戻すと、停止中にパスワードの正否を行の変化から推し量れる経路になる。応答からは分からない）【設計へ】。
  - ログインの失敗の**監査の行**には、停止による拒否だと分かる理由を残すか（応答は区別しないが、運用者は監査で区別したい）。`team.md` の監査の必須テスト（対象イベントごとに必須項目）に当たる。「応答は区別しない・監査は区別する」を AC にする案を推す【判断】。
- **【直す】AC3.2.1〜AC3.2.3**: 「止めた直後の次の要求から」を、AC2.1.1 と同じく「停止の応答を受けた後、同じトークンでの次の要求」と書く。停止を解いた直後に3つの入口がすべて受け付けること（`team.md`）は AC3.2.4 にあるが、「新しいリフレッシュトークンでの更新」「新しいアクセストークンでの API」を入口ごとに書き分ける。
- **【足す】ロック中の利用者を止める・止めた利用者の失敗回数を戻す**: 受け付けるか（拒否の理由の4つに当たらないので受け付ける読みが自然）を AC に1行書く。どちらの組も一覧の表示（利用停止かつロック中）がどうなるかを確かめる。

### 7. US4.1 ロックを解く

- **【直す】AC4.1.2 しきい値**: 「4回」「5回目」を「しきい値−1 回」「しきい値ちょうど」と書き、既定の 5 と、設定（`MASTERSMITH_AUTH_LOCK_THRESHOLD`）を変えた値（例: 3）の両方で確かめる。回数の計算は性質ベースのテスト（jqwik、任意のしきい値 n で「戻した直後から n−1 回はロックされず n 回目でロック」）に向く（`team.md` の対象「ロック判定の回数計算」）。
- **【足す】AC4.1.1 一覧の表示**: 戻した後の一覧で B はロック中と表示されず、「戻せるか」が偽になる。
- **【直す】AC4.1.5 同時の重なりの合否**: 「矛盾しない」は合否が決まらない。次の形にする。「A の取り消しと、B の誤ったパスワードでのログイン（しきい値ちょうどに届く1回）を、行の排他を先に取った側で待ち合わせて重ねる。終わった後の状態は、2つを順に行った結果のどちらか一方（取り消しが先なら失敗回数 1・ロックなし、ログインが先なら失敗回数 0・ロックなし）に一致し、それ以外（失敗回数がしきい値を超える、ロックの時刻だけ残る など）にならない」。重ね方は既存の `LoginAttemptStateRepositoryIT` の行の排他を持ち続ける形（`CountDownLatch`）が使える。
- **【足す】行の排他の待ちの時間切れ**: 既存のロックの判定は行の排他の待ちの上限が 3 秒。取り消しが待ちの時間切れになったときの応答（どの code か）と、そのとき監査に何を残すかが決まっていない。AC に「時間切れのときは状態が変わらず、〔決めた code〕で失敗する」を置き、値は NFR 設計で決める【設計へ】。
- **【直す】AC4.1.4**: 「行が無い利用者」は `team.md` の必須テスト（ロックの状態の行が無い利用者の解除）に当たる。「拒否の後に行が作られない」を足す（前提の「状態が変わらない」に行の有無を入れる案と対）。

### 8. US5.1 氏名・言語を直す

- **【直す】AC5.1.2「送るメール」**: 今、登録を終えた利用者へ送るメールは無い（メールのテンプレートは招待の2つだけ、`backend/src/main/resources/mail/templates/`）。「B の次の画面の表示・エラーの説明文が英語になる」に絞り、メールは「利用者の言語として保存され、今後利用者へ送るメールの言語に使われる」と前提で書くか、外す。今の文言では試験を書けない。
- **【直す】AC5.1.6 管理の API の側の改ざん（重要）**: 「要求の本文に入れても変わらない」の対象に、メールアドレス・パスワード・テーマ・文字の大きさに加えて、**管理者の印・停止の状態・失敗回数**を入れる。氏名と言語の変更の API は監査にも最後の管理者の保護にも当たらないので、この本文から印や停止を変えられると、監査と保護をすり抜ける近道になる。`team.md` の「要求の改ざん（一括代入の防止）」の趣旨に当たる。
- **【足す】AC5.1.4 境界**: 氏名の長さの上限ちょうどは受け付け、上限＋1 は拒否（上限はプリファレンスと同じ値、FR6.2）。空白だけの氏名の扱いもプリファレンスと同じ。言語 `JA`（大文字）・`fr` は拒否。
- **【足す】監査に残らないことの確かめ**: AC5.1.1 の「監査ログには残らない」を、失敗（いない利用者・入力の誤り）でも残らない、に広げる（FR6.4・FR7.3）。

### 11. E2E の代表の流れ（1本まで）

- **推す流れ**: 「管理者が、E2E の中で自分で招待して登録させた利用者 U を、検索で見つける → U がパスワードをしきい値の回数だけ誤りロックされる → 一覧で U がロック中と出る → 管理者が失敗回数を戻す → U が正しいパスワードでログインできる → 管理者が U を止める → U の画面の次の操作でログインの画面へ戻り、ログインもパスワードの誤りと同じ文言で拒否される → 管理者が停止を解く → U がログインできる」。管理者の印の付け外しは、サーバー側の結合テスト（AC2.1.1・AC2.1.2）で足り、画面の効き目（メニュー）は画面のテストで確かめる案。
  - 理由: 利用者の目に見える効き目（ロック・停止）が画面・API・認証の3層を通る唯一の流れで、単体・結合では確かめにくい「画面の 401 からログインへ戻る」を含む。
  - `team.md` の決まりどおり、状態を変えるのは自分で作った U だけで、初期管理者は変えない。自分自身への操作の拒否（初期管理者が自分を止めようとして拒否される）は状態を変えないので、流れに入れてもよい。
- **注意（検索が Should であることとの関係）**: E2E は1つの内部DB を全ファイルで共有し、前の E2E が作った利用者が積もるため、「登録した順」の並びでは U が1ページ目に出るとは限らない。U を見つけるには検索（AC1.1.4、〔Should〕）か、U のページを求める手段が要る。**検索を後の Bolt に回すと、E2E の書き方が変わる**。Delivery Planning で検索を Must の Bolt から外すなら、E2E の置き場（どの Bolt で足すか）も合わせて決める。
- **【判断】流れの長さ**: ロックの取り消しと停止の両方を1本に入れると長くなり（ログインの時間をそろえる仕組みで、しきい値の回数の失敗に時間がかかる）、どちらか一方に絞る案もある。私はロックを含む案を推すが、停止だけに絞る案も正当。
- Playwright のアクセシビリティの検査（一覧・操作の確かめの表示・誤りの状態）は、`project.md` の読み方どおり流れの本数に数えない。

### 12. 同時の操作の確かめ方（まとめ）

- 待ち合わせの口は、本番のコードを変えずにテストで差し替えられる部品（`TestInvitationBarrier`・`TestPasswordChangeBarrier` と同じ形）を、「有効な管理者を数える直前」「失敗回数の行を読む直前」に置く。置き場は設計で決める【設計へ】。
- 合否は「最終の状態が、2つの操作を順に行った結果のどれかに一致する」「監査の行の数と結果が最終の状態と合う」の2つで決める（2節・4節・7節）。
- 待ち合わせの時間切れはテストの失敗とし、上限は既存（`TIMEOUT_SECONDS`）にそろえる。時間の上限を原因を確かめずに延ばさない（`team.md`）。
- 対象の重なりの一覧: 印×印、停止×停止、印×停止（最後の管理者）、取り消し×ログイン（ロック）、停止×トークンの更新（リフレッシュトークンの残り）。

### 13. traceability について（リードへの申し送り）

- NFR7（アクセシビリティ）は今の案のどのストーリーの「出典」にも無い。US1.1 の出典に足すか、2節の AC1.1.7 の案を入れる。
