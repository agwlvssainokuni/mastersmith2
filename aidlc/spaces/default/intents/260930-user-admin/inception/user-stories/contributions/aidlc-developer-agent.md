### 1. 群1 利用者を探す（US1.1）

- **AC1.1.2 の直し【事実の食い違い】**: ロック中の判定は F2 のとおり `now < 解除の予定の時刻` だけ。境界を AC にする: 「Given 解除の予定の時刻が T / When 今が T の直前 / Then ロック中と表示し、今が T ちょうどなら表示しない」。注入した時計で動かす（TP の時刻の決まり）。
- **AC1.1.3 の「失敗回数を戻せるか（真偽）」の定義【判断】**: F2 により、解除の予定の時刻を過ぎた利用者は、行に回数が残っていても次の試みで 0 から数え直すため、回数を戻しても振る舞いは何も変わらない。定義の案は次の2つ。
  - 案A（実質で決める。開発担当の推し）: 「戻せる」＝ ロック中（`now < 解除の予定の時刻`）、または解除の予定の時刻が無く失敗回数が1以上。解除の予定の時刻を過ぎた利用者は「戻せない」（API は「変えるものが無い」で拒否）。監査に「何も変えていない成功」が残らない。
  - 案B（要件 FR5.1 の文字どおり）: 行の失敗回数が1以上なら「戻せる」。AC4.1.3 の「解除の予定の時刻を過ぎた場合を含む」はこちら。
  - どちらでも、AC1.1.3・AC4.1.3・AC4.1.4 の三つを同じ定義にそろえる。案A を採るなら AC4.1.3 の括弧を消し、AC4.1.4 の Given に「解除の予定の時刻を過ぎた利用者」を足す。
- **AC1.1.5 の「範囲の外」【事実の食い違い】**: F10 の前例では、最後のページより後の page は拒否せず空の一覧を返す。「範囲の外」を「1 未満」に限り、「最後のページより後の page は、全体の件数つきの空の一覧を返す」を AC に足すことを勧める（前例と画面の作りをそろえる。検索の結果が減ったときに画面が誤りにならない）。
- **AC1.1.4 の足し【抜け】**: `%`・`_` に加えて、エスケープに使う文字（`\` など）そのものも文字どおりに一致することを入れる。氏名の大文字小文字を問わない一致は、メールアドレス（保存の時に小文字にそろえている）と違い氏名側だけ比べ方を変える必要がある点を、機能設計への申し送りにする。
- **AC1.1.1 の並びの同順【抜け】**: 登録した日時が同じ利用者（初期管理者の作成とテストのデータなど）で並びが揺れないよう、「同じ日時なら利用者 ID の順」を足す（要件 7節で機能設計に回した点だが、ページ送りのテストの判定に要るため AC に置きたい）。
- **一覧に要る値の出どころ（参考）**: 今の `UserSummary` は登録した日時を持たない。ロックの値は `auth` の表にあり、`user` は `auth` を知らない（K-3）。一覧は `user` と `auth` の両方を読む処理が `user` の外に要る。AC は今のままで作れるが、この合わせ方が US1.1 を大きくする要因なので、見積もりで考える。

### 2. 群2 権限を管理する（US2.1・US2.2）

- **AC2.1.6 の足し（操作をまたぐ同時の重なり）【抜け】**: 同時の重なりは、同じ種類の操作どうし（印×印、停止×停止）だけでなく、**印を外す×止める** の組み合わせでも起きる（A が B の印を外すのと、B が A を止める）。最後の管理者の守りは、印と停止の両方の操作で同じ仕組みを通す必要があるため、AC2.1.6 か AC3.1.5 のどちらかに、この組を1件足す。
- **AC2.1.6・AC3.1.5 の「拒否された側」の中身【抜け】**: 行ごとの排他（対象の利用者の行だけを排他）では、2人が互いの別の行を変えるので守れない（書き込みの食い違い）。何かを共通に排他する作りになり、待ちの上限（今の決まりでは 3 秒）に当たると 5xx になりうる。AC に「一方だけが成功し、もう一方は業務の誤り（最後の有効な管理者の保護）として拒否され、どちらも 5xx にならない」と書き、待ちの上限切れで落ちる形を合格にしない。
- **AC2.2.2 の「最大 5 分後」【事実の食い違い】**: F6 のとおり、画面は 5 分ごとに更新しない。B が何も操作しなければメニューは残り続ける。正しくは「B のアクセストークンが期限切れになった後の最初の API の呼び出し（そこで更新が走る）、画面の再読み込み、またはログインのし直しの後に、管理のメニューが表示されなくなる」。
- **AC2.2.1 の 403 の表示【判断】**: F7 のとおり、今の管理者向け領域は 403 を「ページが見つかりません」と出して存在を隠している。FR2.3 の「管理者ではなくなった旨」は、(a) 新しい利用者の管理の画面だけに当てるか、(b) 既存の管理画面（DSL・招待・管理者向け領域）もそろえるかで作業の量が変わる。あわせて、403 を受けた時点でログイン状態を読み直してメニューを消すか（AC2.2.2 の待ちを無くせる）も選べる。開発担当の推しは (a)＋403 で読み直し。
- **AC2.2.1 の監査【抜け】**: 印を外された B の管理の API の呼び出しは、今の仕組み（F8）で「アクセスの拒否（NOT_ADMIN）」として監査に残る。AC に書いておくと、運用者の観点（ペルソナで扱わないと決めた部分）が1件で確かめられる。
- **AC2.1.7 の判定の形【抜け】**: F11 のとおり、`/api/me/preferences` に知らない項目（`admin` など）を入れても 400 にならず無視される。AC の Then を「要求は今までどおり受け付けられ（200）、印は変わらない」と、状態コードまで書く。管理の API の外で状態を変えうるのは `/api/me/preferences` と `/api/me/password` だけなので、この2つを対象として挙げるとテストの範囲が決まる。

### 3. 群3 利用を止める（US3.1・US3.2）

- **AC3.1.2 の「止める前に出した B のトークンは使えないまま」【事実の食い違い・判断】**: リフレッシュトークンは止めた時に無効にするので守れる。しかしアクセストークンには失効の仕組みが無い（F5）。止めてから 5 分以内に停止を解くと、止める前に出したアクセストークンは署名も期限も正しく、利用者も停止していないので、**再び使える**。
  - 案A: AC を「止める前に出したリフレッシュトークンは使えない。アクセストークンは、停止を解いた後、元の有効期限（最大 5 分）まで再び使える」と決めた側の動作として明示する（TP の「停止の前に出したトークンの扱いは、決めた側の動作を明示したテスト」に当たる）。作りは増えない。
  - 案B: 利用者に「この時刻より前に出したトークンは受け付けない」時刻を持たせ、アクセストークンの `iat` と比べて拒否する（`iat` はすでにある）。停止・解除の後も止める前のトークンは確実に使えないが、スキーマと認証の入口に手が増える。
  - 開発担当は案A を推す（DECIDED の「アクセストークンの失効の仕組みは持たない」と、有効期限を短くしている理由に合う）。どちらでも AC を1件足す。
- **止めるのと、トークンの更新が同時に重なったとき【抜け】**: 止める処理がリフレッシュトークンを無効にしている間に、B の更新が停止の確定の前の状態を読んで新しいリフレッシュトークンを作ると、そのトークンは無効にされずに残りうる。停止中は更新の入口で拒否するので害は出ないが、**停止を解いた後にそのトークンが使えてしまう**（AC3.1.2・AC3.2.4 の「止める前のリフレッシュトークンは使えない」に反する）。「停止の確定と重なって出たリフレッシュトークンも、停止を解いた後に使えない」を AC に足すか、残る隙として受け入れて記録するかを決めたい【判断】。足すなら、更新の側で利用者の行を読む順番・排他を設計で決める必要がある。
- **AC3.2.3 のロックの失敗回数との関係【抜け・判断】**: 停止中の B のログインを、ロックの判定（F2）の前で止めるか後で止めるかで振る舞いが変わる。
  - 前で止める（存在しない利用者と同じくダミーの行で判定する）: 停止中はロックの状態が動かない。
  - 後で止める: 停止中でも誤りで回数が増え、正しいパスワードでは回数が 0 に戻る（ロックが解ける）のに拒否される。
  - どちらでも応答は同じにできる（照合は必ず1回なので時間もそろう）。開発担当は「前で止め、ロックの状態を変えない」を推す。AC3.2.3 に「停止中のログインの試みで、B の失敗回数とロックの状態は変わらない」（または決めた側）を足す。
- **停止による拒否の監査【抜け】**: 要件は停止中の利用者の拒否を監査に残すかを決めていない。今の仕組みでは、ログインの失敗は監査に残り（理由が要る）、`/api/admin/` の下の 401 も残る（F8）が、ほかの道の 401 とトークンの更新の失敗は残らない。AC に入口ごとの監査を書く。
  - ログイン: 「ログインの失敗」として、理由は新しい区分（停止中）で残す案と、既存の区分に寄せる案がある。監査は応答に出ないので、区別して残しても列挙の防止（NFR2）は崩れない。開発担当は区別して残す案を推す。
  - アクセストークン: 管理の API の道では「アクセスの拒否」として残る（AC3.2.5）。理由を今の `USER_NOT_FOUND` に寄せると、監査を読む人が「いない利用者」と取り違えるため、区分を足すかを決める。区分を足すと `access.domain`・`auth.domain`（F13）に手が入る。
- **AC3.2.1 の画面の動き【抜け】**: F6 のとおり、B の画面は 401 を受けて更新を試み、更新も 401 `REFRESH_FAILED` になるのでログイン画面へ移る。「B の画面はログイン画面に移る」を足すと、P2 の目で確かめられる。
- **AC3.1.1 の「リフレッシュトークンはすべて無効」【抜け】**: F4 のとおり新しい手段が要る。判定の形として「止める前に出した B のリフレッシュトークン（複数の端末の分）のどれで更新しても 401 `REFRESH_FAILED`、ほかの利用者のトークンは使える」と、他人のトークンに及ばないことも入れる。

### 4. 群4 ロックを解く（US4.1）

- **AC4.1.1 の足し【抜け】**: 「失敗回数を 0 に戻す」は、解除の予定の時刻も消す（無しにする）ことを含む。回数だけ 0 にすると F2 の判定でロック中のままになる。AC4.1.1 の Then に「失敗回数は 0、解除の予定の時刻は無し」を入れる。
- **AC4.1.5 の判定の形【抜け】**: 「矛盾しない」は合否の判定にしにくい。待ち合わせで順番を固定して、両方の順番を確かめる形にする。
  - B のログインの判定が先に行の排他を持つ → 取り消しは待ち、ログインの判定の後の状態を 0 に戻す（取り消しが後に勝つ）
  - 取り消しが先 → ログインは 0 に戻った状態で判定される（正しいパスワードなら成功、誤りなら回数 1）
  - どちらも 5xx にならない（待ちの上限 3 秒の中で終わる）
- **AC4.1.2 のしきい値の書き方【抜け】**: しきい値は設定で変えられる（既定 5）。「しきい値−1回ではロックされず、しきい値ちょうどでロックされる」と書き、既定の値を括弧に置く（TP の書き方にそろえる）。
- **AC4.1.4 の「ロックの状態の行が無い」【抜け】**: F3 のとおり、行は作成の知らせかログインで作られるので、ふつうは無い状態にならない。テストでは行を消して作る必要がある。「行が無い利用者を指定したとき、行を新しく作らずに『変えるものが無い』で拒否する」まで書くと、実装の分岐が一意になる。

### 5. 群5 利用者の情報を直す（US5.1）

- **AC5.1.2 の「送るメール」と「エラーの説明文」【事実の食い違い】**: F12 のとおり、既存の利用者に送るメールは今は無く、エラーの説明文の言語は画面の言語（`Accept-Language`）で決まる。AC5.1.2 は今のままでは確かめようがない。直しの案: 「B が次にログインする（または画面を読み直す・トークンが更新される）と、B の画面の文言が英語になり、画面が付ける言語が英語になるので、エラーの説明文も英語になる」。メールは「今後 B に送るメールがあれば英語」とし、今回は確かめない、と明記する。
- **AC5.1.3 の足し【抜け】**: 自分の氏名を直したときも、上の帯などに出る自分の氏名が直後に変わることを入れる（言語と同じく、画面が持つログイン状態を読み直す作りが要るため）。
- **AC5.1.6 の判定の形【抜け】**: AC2.1.7 と同じく、要求の本文に知らない項目を入れたときの状態コード（無視して成功か、400 か）を決めて書く。管理の API の要求の型に氏名・言語だけを持たせれば、メールアドレスなどは無視されて変わらない。

### 6. 横断: 拒否の理由の順と、操作の種類ごとの当てはまり

- **FR7.5 の順と操作の組み合わせの表【抜け】**: 4つの理由が当たる操作は、操作ごとに違う（氏名・言語の変更は「対象の利用者がいない」だけ、失敗回数の取り消しは「自分自身への操作」を持たない）。「前提と読み方」に次の表を置くと、テストの組み合わせが漏れない。

| 操作 | 対象がいない | 自分自身 | 変えるものが無い | 最後の管理者 |
|---|---|---|---|---|
| 印を付ける | ○ | ○（自分に付ける＝すでに管理者だが、判定の順で「自分自身」が先） | ○ | ― |
| 印を外す | ○ | ○ | ○ | ○ |
| 止める | ○ | ○ | ○ | ○ |
| 停止を解く | ○ | ○（自分は停止中ではありえないが、判定の順で「自分自身」が先） | ○ | ― |
| 失敗回数を 0 に戻す | ○ | 要件に無い【判断】 | ○ | ― |
| 氏名・言語を変える | ○ | 許す（FR6.1） | 当てない（FR6.6） | ― |

- **自分自身の失敗回数を戻す【判断】**: FR2.4・FR3.6 は印と停止だけを自分自身への操作として拒否する。ログイン中の管理者は、ふつうロック中ではないが、失敗回数が 1〜4 のことはある。自分の回数を戻す操作を許すか（害は小さい）、ほかと同じく拒否するかを決め、AC4.1 に1件置く。
- **監査の理由の名前**: F9 のとおり 32 文字まで。「対象の利用者がいない」を既存の `USER_NOT_FOUND`（ログインの入力のメールアドレスの利用者がいない、アクセストークンの利用者がいない）に寄せるか、別の区分にするかは機能設計でよいが、監査を読む人の取り違えを避けるため別の区分を推す。

### 7. 大きさと分け方（Delivery Planning への申し送り）

- **依存の図は「画面」と「API」で分けると独立性が上がる**: 今の図では US1.1 がすべての入口だが、これは画面の上の依存である。API の上では、印・停止・取り消し・氏名の変更は一覧が無くても作れて、サーバー側のテストで確かめられる。INVEST の「独立」は、API の単位で見れば △ から ○ に上げられる。
- **共通の部品が先に要る**: US2.1 と US3.1 は「最後の有効な管理者の保護」と「拒否の理由の判定の順・監査」を共有する。同じ Bolt に入れるか、共通の部品を先の Bolt に置く。別々の Bolt で2回作らない。
- **US3.2 が最も重い**: 認証の3つの入口・リフレッシュトークンのまとめての無効化（F4）・監査の区分・スキーマの変更（NFR10）・画面の遷移に及び、`auth`・`access` のパッケージのカバレッジの作業（F13）も付く。US3.1（止める操作）より先に、停止の状態と3つの入口の拒否だけを作る（状態は DB でテストのデータとして入れて確かめる）順番も取れる。
- **US4.1 は `auth` に閉じる**: ロックの取り消しは `auth.repository`（F13 の一覧の中）に手が入るため、見積もりにカバレッジの作業を含める。
- **US1.1 は `user` と `auth` を合わせる処理（K-3）を最初に作る**: 一覧のロックの表示と、各操作の「対象」の読み取りに同じ処理を使えるので、一覧を先に作ると後が軽くなる。
- **大きめのままでよい（SQ5 B）が、US3.2 の AC は今の6件から8〜9件に増える**（上の足しを入れた場合）。分けるなら「3つの入口での拒否（サーバー）」と「P2 が画面で受ける動き」の2つに割るのが自然。

## Positions

- AGREE: 群の分け方と、操作をまたぐ要件を各ストーリーに入れる形（SQ2 A・SQ3 A） — 1件ずつのテストの範囲が各ストーリーで閉じ、実装の単位とも合う。
- AGREE: 拒否の理由の判定の順を「前提と読み方」に一度だけ書き、各 AC で参照する形 — 実装では1つの判定の関数にでき、テストもそれに合わせられる。
- AGREE: AC3.2.1〜AC3.2.3 で状態コードと code を入口ごとに固定したこと — 今の `AUTHENTICATION_REQUIRED`・`REFRESH_FAILED`・`AUTHENTICATION_FAILED` と一致し、列挙の防止（NFR2）をそのままテストにできる。
- OBJECT: AC3.1.2「止める前に出した B のトークンは使えないまま」 — アクセストークンに失効の仕組みが無く、5 分以内に停止を解くと止める前のアクセストークンが再び使えるので、今の文言は作れない。決めた側の動作を明示する必要がある（判断）。
- OBJECT: AC2.2.2「最大 5 分後」 — 画面は間隔で更新せず、401 か再読み込みのときにだけ更新するので、上限の時間は無い。
- OBJECT: AC5.1.2 の「送るメール・エラーの説明文」 — 既存の利用者に送るメールは無く、エラーの説明文は画面の言語で決まるため、今の文言は確かめられない。
- OBJECT: AC4.1.3 の「解除の予定の時刻を過ぎた場合を含む」と AC1.1.3 の「失敗回数を戻せるか」の定義が未定 — 解除の予定の時刻を過ぎた利用者は次の試みで回数を数え直すため、戻しても何も変わらない。定義を1つに決めてそろえたい（判断）。
- OBJECT: AC1.1.5 の「範囲の外」の page を拒否すること — 前例（招待の一覧）は最後のページより後を空の一覧で返しており、そろえたい。
- OBJECT: AC2.1.6・AC3.1.5 が同じ種類の操作の重なりしか持たないこと — 印を外す操作と止める操作の重なりでも有効な管理者が 0 人になりうる。
- OBJECT: 停止中の利用者の拒否の監査とロックの状態への影響が、どの AC にも無いこと — 入口ごとに監査の有無と理由、停止中のログインで失敗回数が動くかを決めないと、実装が一意に決まらない。
