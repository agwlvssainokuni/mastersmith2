### D-1 「前提と読み方」に画面の共通の決まりを足す（すべての画面の受け入れ基準に共通）

初稿の前提は API と監査の読み方が中心で、画面の側の合否の決め方が無い。各 AC に繰り返さず、前提に一度だけ次を足す案（dsl-schema-loader の user-stories で「前提と読み方」に画面の共通の決まりを一度だけ書いた前例に合わせる）。

- **画面の状態**: 利用者の管理の画面は、読み込み中・表示・0件・読み込みの失敗の4つの状態を持ち、それぞれ利用者の言語の文言で示す。読み込み中は「読み込んでいます」の旨を支援技術にも伝える。
- **操作の結果の知らせ**: 操作の成功は短い知らせ（`Toast`、`role="status"` 相当）で伝え、失敗は理由ごとの文言を操作の近くに残る形（`Alert` 相当）で伝える。成功・失敗のどちらも、操作の後に一覧を読み直して最新の状態を見せる（今のページの番号と検索の文字は保つ）。
- **処理中**: 操作を送ってから応答までの間、その行の操作のボタンは押せず、処理中である旨の読み上げの名前に変わる（二重の送信の防止。招待の画面の「送信しています」と同じ型）。
- **読み上げの名前**: 行ごとの操作のボタンは、対象の利用者が分かる読み上げの名前を持つ（例「山田 太郎（yamada@example.com）の利用を止める」）。ボタンの見た目の文字が同じでも、どの行の操作かを支援技術で区別できる。
- **色だけに頼らない**: 管理者の印・状態（有効／利用停止）・ロック中は、色に加えて文字（`Badge` の文言）で示す。
- **キーボード**: 一覧・検索・ページ送り・各操作・確かめの表示は、キーボードだけで操作でき、フォーカスの位置が見える。
- **確かめの表示**（D-3 で対象を決める）: 対象の利用者の氏名とメールアドレス、操作の効き目を示す。はじめのフォーカスは「やめる」、Escape で閉じ、背景のクリックでは閉じない。閉じたら、開いたボタン（成功で行が変わったときは同じ行の操作）にフォーカスを戻す。
- **日時の表示**: 登録した日時・解除の予定の時刻は、利用者の言語の書式と画面の時間帯で表示する。
- **テーマと文字の大きさ**: light・dark と文字の大きさ sm・md・lg のどの組でも、一覧の列と操作のボタンが重ならず読める（NFR7）。実際のブラウザでの axe の検査は、誤りを出した状態と2語の氏名を含むデータで行う（`project.md` の Corrections、user-management の U7 の学び）。

### D-2 US1.1 に画面の状態の受け入れ基準を足す

初稿の US1.1 は表示の中身と応答の中身はあるが、空・読み込み中・失敗の状態が無い。管理者（P1）の目的「一目で確かめたい」には、読めない状態で何が起きているかが分かることが要る。

- **AC1.1.7（足す）** Given 管理者が一覧を開いた / When 応答を待っている間 / Then 読み込み中である旨が表示され、支援技術にも伝わる。応答が来たら一覧に置き換わる。
- **AC1.1.8（足す）** Given 一覧の読み込みが失敗した（5xx・通信の失敗） / When 画面を見る / Then 失敗した旨と、もう一度読み込む操作が表示される。前に表示していた行を、最新の状態のように見せ続けない。
- **AC1.1.9（足す、〔Should〕）** Given 「zzz」に当たる利用者がいない / When 「zzz」で検索する / Then 「『zzz』に当たる利用者はいません」の旨と、検索を消して全体に戻す操作が表示される。検索したときは1ページ目に戻り、ページを送っても検索の文字は保たれる。
  - 補足: 一覧の全体が 0 件になることは無い（見ている管理者自身が必ずいる）ため、「0件」は検索の結果だけを考えればよい。
- **AC1.1.10（足す、〔Should〕）** Given 検索の入力欄 / When 上限より長い文字を入れようとする / Then 画面は上限を超えて入れられないか、送る前に上限を知らせる（誤りを起こしにくくする）。サーバー側の拒否（AC1.1.5）は、画面の制限の有無にかかわらず残す。
- **AC1.1.1（直す）** 「各行に…表示され」に「自分自身の行には『あなた』の印が付く」を足す（D-5 の前提。P1 が自分の行を見分けて誤操作を避けるため）。
- **AC1.1.2（直す）** 「解除の予定の時刻が表示され」を「解除の予定の時刻が利用者の言語の書式・画面の時間帯で表示され」に。

### D-3 取り消しにくい操作の確かめを受け入れ基準にする（判断が分かれる）

要件の 7節は「各操作の前に確かめの表示（Modal）を出すか」を画面イメージに回しているが、「確かめを出すか」は操作の流れ（誤操作で利用者の仕事を止める・管理者を減らす）に関わり、受け入れ基準で合否を決めたほうがよい。形（Modal か行の中か）は画面イメージに任せる。

案（推奨）: 効き目が大きく、すぐには元に戻らない操作だけを確かめる。

| 操作 | 確かめ | 理由 |
|---|---|---|
| 利用を止める | 出す | 止めた利用者はすぐに使えなくなり、停止を解いても止める前のトークンは戻らない（ログインし直しが要る、FR3.3） |
| 管理者の印を外す | 出す | 相手が管理の画面を使えなくなる。最後の管理者の保護に近い操作 |
| 管理者の印を付ける | 出す | 権限を与える操作で、誤った相手に付けると管理のすべてができてしまう |
| 停止を解く | 出さない | 利用者を使える状態に戻すだけで、誤っても止め直せる |
| 失敗回数を 0 に戻す | 出さない | 問い合わせを受けたその場で素早く済ませたい（P1 の目的）。誤っても害が小さい |

- **AC3.1.7（足す）** Given 管理者 A が一覧で利用者 B の「利用を止める」を選ぶ / When 確かめの表示が出る / Then B の氏名・メールアドレスと「B はすぐに使えなくなり、停止を解いた後もログインし直しが要る」旨が示され、「やめる」を選ぶと要求は送られず、B の状態は変わらず、監査ログにも残らない。
- **AC2.1.8（足す）** Given A が B の管理者の印を付ける・外すを選ぶ / When 確かめの表示が出る / Then B の氏名・メールアドレスと効き目（付ける: 次の操作から管理の画面が使える。外す: 次の操作から管理の画面が使えなくなる）が示され、「やめる」では何も変わらない。
- 別案: (a) 5つすべてを確かめる（一貫するが、ロックの解除の手数が増える）、(b) 止めるだけを確かめる（手数は最小だが、印の付け外しの誤操作を防げない）。**判断が分かれる**ため依頼者に尋ねたい。

### D-4 US2.2 の「管理者でなくなった」ときの表示を、今の管理の画面の振る舞いと合わせて決める（判断が分かれる）

初稿の AC2.2.1 は「画面は『管理者ではなくなった』旨を表示する」とするが、根拠の事実のとおり、今の管理の画面は 403 を「ページが見つかりません」（入口・DSL）か一般の 4xx の文言（招待）で出しており、「管理者ではなくなった」を表示する画面は無い。次の2点を決める必要がある。

1. **文言**: 403 は「管理者の印が外された」以外（そもそも管理者でない人が URL を直接開く・画面の古い印）でも起きうる。「管理者ではなくなった」と言い切ると、印を持ったことの無い人には誤りになる。案: 「この画面を使う権限がありません。管理者の印が外された可能性があります。」のように、原因を言い切らない文言にする（ja・en）。
2. **範囲**: (a) 利用者の管理の画面だけで新しい表示にし、入口・DSL・招待は今のまま（差を記録する）。(b) 管理の画面すべて（入口・DSL・招待・利用者の管理）で同じ表示にそろえる（P2 の目的「管理の画面が使えなくなったことを分かりやすく知りたい」は画面を選ばないため、そろえるほうが忠実だが、既存の画面と既存のテストの変更が今回の範囲に入る）。**判断が分かれる**。推奨は (a) とし、(b) は差として記録して後続の Intent に回す（今回の依頼文は利用者の管理の画面に限るため）。

足す・直す AC の案:

- **AC2.2.1（直す）** Given B は利用者の管理の画面を開いている / When A が B の印を外した後、B が一覧を読む・操作する / Then サーバーは 403 を返し、画面は一覧と操作を出さずに、権限が無くなった旨（D-4 の 1 の文言）を B の言語で表示し、管理の画面の外（自分の設定など）へ移る手段を示す。開いていた確かめの表示・入力の表示は閉じる。
- **AC2.2.4（足す）** Given B の画面はまだ B を管理者として扱っている（トークンの更新の前） / When B が管理の画面を開き直す / Then 同じく権限が無くなった旨が表示され、一覧の行（他の利用者のメールアドレス・氏名）は表示されない。

### D-5 自分自身の行の操作を、誤りの後ではなく前に防ぐ（判断が分かれる）

AC2.1.3・AC3.1.3 はサーバーの拒否（自分自身への操作）を確かめるが、画面が自分の行に「印を外す」「止める」を出したままだと、P1 は押してから拒否の文言を読むことになる（誤りの防止のほうがよい）。最後の有効な管理者は、1件ずつの操作では自分自身しかありえない（FR4.2）ため、自分の行の操作を出さなければ、最後の管理者の拒否は同時の重なりのときだけになる。

- **AC2.1.9（足す）** Given 管理者 A が一覧を見る / When 自分自身の行を見る / Then 自分の行には「管理者の印を外す」「利用を止める」の操作が出ない（または押せず、自分自身には行えない旨が読める）。サーバー側の拒否（AC2.1.3・AC3.1.3）は、画面の表示にかかわらず残す（`project.md` の Mandated: 画面で隠すことをサーバー側の判定の代わりにしない）。
- **判断が分かれる**点: 操作を「出さない」か「押せない形で出して理由を示す」か。押せないボタンはキーボードのフォーカスが当たらず理由が支援技術に伝わりにくいため、推奨は「出さない」＋行の「あなた」の印（D-2 の AC1.1.1 の直し）。形は画面イメージで決めてもよいが、「自分の行から自分を止める・印を外す要求を送れない」ことは受け入れ基準にしておきたい。

### D-6 拒否の理由ごとに、管理者が次にすることが分かる文言にする

前提 A2 の理由（「後の人に『すでに変わっていた』ことを知らせるため」）は、画面が理由を区別して伝え、一覧を最新に直して初めて成り立つ。応答の code を区別するだけでは P1 に届かない。各ストーリーに1件ずつ足すより、共通の AC として US2.1 に置き、US3.1・US4.1 から参照する案。

- **AC2.1.10（足す）** Given 利用者 B の状態を、画面を開いた後に別の管理者が変えた / When A が古い表示のまま B に操作する / Then 「変えるものが無い」の拒否を受けた画面は、「ほかの管理者がすでに変えた可能性がある」旨を A の言語で表示し、一覧を読み直して B の今の状態を見せる。
- **AC2.1.11（足す）** Given 拒否の理由が「最後の有効な管理者の保護」 / When 画面を見る / Then 有効な管理者が 0 人になるため受け付けられなかった旨と、先にほかの利用者に管理者の印を付ける必要がある旨が表示され、一覧を読み直す。
- **AC2.1.12（足す）** Given 拒否の理由が「対象の利用者がいない」 / When 画面を見る / Then 対象が見つからない旨が表示され、一覧を読み直す（利用者は消さないため通常は起きないが、要求の改ざんや古い画面で起きうる）。
- 読み方: 「自分自身への操作」は D-5 により画面からは通常起きないが、起きたときも理由の文言を出す。これらの文言は ja・en の両方を用意する（NFR8）。

### D-7 US3.2・US3.1 に、止められた利用者から見た画面の振る舞いを足す

P2 の困りごと「止められたかどうかを画面から推測できてしまうのは困る」と、NFR2 の列挙の防止は、API の応答だけでなく画面の表示でも守る必要がある。

- **AC3.2.7（足す）** Given B は画面を開いたまま止められた / When B が次に操作する / Then 画面はトークンの更新に失敗してログインの画面へ移り、止められたことを示す文言は出さない（ほかの理由でログインが切れたときと同じ表示）。
- **AC3.2.8（足す）** Given 止められた B がログインの画面で正しいパスワードを入れる / When 拒否される / Then 画面の文言はパスワードを誤ったときと同じで、停止・ロックのどちらかを見分けられない。
- **AC3.1.8（足す）** Given A が B を止めた / When 一覧を見る / Then B の行は「利用停止」の文字の印で示され、操作は「停止を解く」に変わる（色だけで区別しない）。

### D-8 US4.1 に、一覧の表示の古さへの対処を足す

ロック中の表示は「開いた時点の今の時刻」で決まるため、画面を開いたまま解除の予定の時刻を過ぎることがある（P1 は問い合わせを受けてから操作するため、その間に時刻を過ぎうる）。

- **AC4.1.7（足す）** Given 一覧で B はロック中と表示されたが、操作の前に解除の予定の時刻を過ぎた / When A が B の失敗回数を 0 に戻す / Then 失敗回数が残っていれば成功し〔ロック中でない利用者の取り消しは Should〕、残っていなければ「変えるものが無い」の拒否として D-6 のとおり一覧を読み直す。どちらの場合も、画面は操作の後に B の今のロックの表示を見せる。
- **AC4.1.1（直す）** 「B は直後に正しいパスワードでログインでき」に「一覧の B の行はロック中でなくなり、『失敗回数を戻す』の操作が消える」を足す（P1 が問い合わせの相手に「もう入れます」と言える確かさのため）。

### D-9 US5.1 に入力の体験を足す

- **AC5.1.7（足す、〔Should〕）** Given A が B の氏名・言語を直す入力を開いた / When 見る / Then 氏名と言語には B の今の値が入っている。「やめる」を選ぶと値は変わらない。入力の誤り（空の氏名など）は、その入力欄のすぐ近くに利用者の言語で示され、入力した値は消えない。
- **AC5.1.2（読み方の確認）** B がすでに開いている画面の言語は、B の次の画面の読み込み（再読み込み・ログイン）で変わる、という読みで合っているか。管理者の操作で B の開いている画面の言語がその場で変わることは求めない、と明記したほうが合否が決めやすい。

### D-10 ペルソナの直し

- **P2 の役割の範囲**: P2 は「管理者の印は無い」利用者と定義されているが、US2.2 の主語は「管理者の印を外された元の管理者」で、P2 の定義に当たらない。案: (a) P2 の役割に「管理者の印を外された元の管理者を含む（外された後は印の無い利用者として扱う）」を足す、(b) US2.2 の主語を P1（担当を外れた管理者）にする。推奨は (a)（外された後の体験は P2 と同じ「管理の画面が使えなくなる」側のため）。
- **P1 の困りごとに1つ足す**: 「2〜3人の管理者で同じ利用者を同時に扱うと、ほかの人がすでに変えたことに気づけない」。前提 A2 と D-6 の根拠がペルソナにたどれるようにするため（P1 は「ほかの管理者は1〜2人いる」とあり、忠実さを保てる）。
- **P1 の使い方に1つ足す**: 「問い合わせ（電話・チャット）を受けながら操作する」。ロックの解除に確かめを出さない推奨（D-3）と、操作の後に今の状態を見せる AC（D-8）の根拠にする。
- **アクセシビリティの前提**: ペルソナの技術への慣れ・頻度に加え、「キーボードや読み上げを使う管理者もいる」旨を P1 に1行足すと、D-1 の共通の決まりの根拠がペルソナにたどれる（必須ではない）。

### D-11 E2E の代表の流れの候補（参考）

`team.md` の「Intent ごとに代表の流れを1本まで」「自分で作った利用者だけを対象にし、初期管理者の状態は変えない」に合う候補: 管理者が、流れの中で招待から登録させた利用者を一覧で検索して見つけ、止める（確かめを経る）→ その利用者でログインできないことを確かめる → 停止を解く → ログインできる。印の付け外し・ロックの解除は画面部品のテストとサーバー側のテストに任せる。どの流れを代表にするかは後の段で決めてよいが、US3.1・US3.2 が代表の流れの素材になることをストーリーに注記しておくと後の段が迷わない。
