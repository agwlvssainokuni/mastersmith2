# User Stories の実施の判断

## 判断

**Execute**（ユーザーストーリーを作る）

## 理由

- 利用者が直接使う画面（利用者の管理の画面）を足す機能で、管理者の操作の流れと受け入れの判定を、利用者の目で書き分ける価値がある（`requirements.md` の FR1〜FR8）。
- 立場の違う人が関わる。操作する管理者のほか、止められる・ロックを解かれる利用者と、監査ログを見る運用者の観点が要る（`requirements.md` の 1節）。
- 業務の決まりが込み入っている。最後の有効な管理者の保護・自分自身への操作の拒否・拒否の理由の判定の順・停止の前に出したトークンの扱い・ロックの判定を時刻で行うことなどがあり、受け入れ基準を Given/When/Then で具体にしておくと、後の設計とテストの抜けを防げる（`requirements.md` の FR3〜FR5・FR7）。
- `team.md` の必須テスト（利用停止・管理者の印・ロックの解除・最後の管理者・認可・改ざん・監査・漏えい）を、受け入れ基準の形で先に確かめておける。

## 考えた点

| 観点 | 見立て |
|---|---|
| 種類 | 既存のアプリへの機能の追加（ブラウンフィールド）。リファクタリング・不具合の修正・基盤だけの変更ではない |
| 利用者が触れる範囲 | 管理画面に新しい画面を1つ足し、ログイン・トークンの更新・管理の画面の振る舞いも変わる |
| 複雑さ | 同時の操作・時刻の判定・列挙の防止・監査の理由の判定など、境界の多い決まりがある |
| 関わる部品 | `user`・`auth`・`access`・`audit` と画面（コード知識ベースの K-1〜K-9） |

## ストーリーが特に役立つところ

- 利用停止と停止の解除（3つの入口での拒否と、停止の前のトークンの扱い）
- 最後の有効な管理者の保護と、自分自身への操作の拒否（同時の操作を含む）
- 失敗回数の取り消し（ロック中なら解除を兼ねる）と、ロックの判定の時刻の扱い
- 拒否した操作の監査と理由の判定の順
- 一覧と検索での個人に関する値の扱い（応答・ログ）

統合の結果: mob の3人の意見と依頼者の決定（M1〜M9）を取り込み、7ストーリー・75 の受け入れ基準にした。承認済みの要件と違う形になった7点は `stories.md` の「要件との差」に記録した。
