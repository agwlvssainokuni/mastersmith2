# User Stories — ストーリーの計画と質問

## 計画の案

- **ストーリーの書き方**: 「〔利用者〕として、〔したいこと〕をしたい。それは〔得られる価値〕のためだ」の形で書き、INVEST（独立・交渉可能・価値がある・見積もれる・小さい・テストできる）を満たすようにする。受け入れ基準は Given/When/Then で、1ストーリーに3〜6件とし、失敗の場合を必ず含める。
- **ID**: ストーリーは `US{群}.{番号}`、受け入れ基準は `AC{群}.{番号}.{連番}`。
- **優先度**: MoSCoW（Must / Should / Could / Won't）を付ける。どこまでを最初に届けるかの線引きは、後の Delivery Planning で決める。
- **出典**: 各ストーリーに、元になった要件（`requirements.md` の FR・NFR）を示す。
- **要件の見直しで持ち越した点**: 応答時間の件数の想定（R-05）は NFR 要件の段で決めるため、ストーリーには入れない。

以下の点を決めてください。

## 参加者の意見で判断が分かれた点

デザイナー・開発・品質の担当の意見（`contributions/`）のうち、どちらの考えもありうる判断を尋ねます。専門の知識で決まるもの（事実の食い違いの直し、境界値の書き方、同時の重なりの合否の書き方、監査の書き込みの失敗は既存の決まりどおり操作を失敗させないこと、重なって負けた側の理由は「最後の有効な管理者の保護」とすること、印を外された元の管理者もペルソナ P2 に含めること、自分自身の失敗回数を戻す操作は許すこと など）は、リードが決めてそのまま取り込みます。

## M1. 停止を解いた後の、止める前のアクセストークン

アクセストークンには失効の仕組みがありません（決定済み）。停止中は状態を見て拒否しますが、止めてから 5 分以内に停止を解くと、止める前のアクセストークンが期限まで再び使えます。承認済みの要件 FR3.3 は「停止を解いても、止める前に出したトークンは使えない」と書いていますが、無効にするのはリフレッシュトークンだけで、この点と食い違います（開発・品質の担当が指摘）。

A. 止める前のアクセストークンは、停止を解いた後、期限（最大 5 分）まで再び使えることを、決めた側の動作としてストーリーに明記する。承認済みの要件は書き換えず、差をストーリーに記録する
B. 利用者に「これより前に出したトークンは無効」という時刻を持たせ、止めたときにその時刻を進め、アクセストークンの発行時刻と比べて拒否する（要件に仕組みを足す）
