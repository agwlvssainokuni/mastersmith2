## Q1. 認証・認可・監査の「必ず書くテスト」の一覧に、利用者の管理の項目を足すか

`team.md` には、認証・認可・監査について「必ず書くテスト」の一覧があります（アカウントロック・ログイン・トークン・招待など）。今回は管理者が利用者の状態と権限を変えるため、品質担当とセキュリティ担当が次の項目を足す案を出しました。★の値や動作（停止を応答から推測できてよいか、停止や印を外す前に出したトークンの扱い、最後の管理者の数え方、拒否した操作を監査に残すか など）は、要件定義で決めてからテストを書きます。

- 利用停止: 停止中の利用者は、ログインの照合・トークンの更新・アクセストークンの認証の3つの入口すべてで拒否される。停止を解いた直後は3つとも受け付ける。停止の前に出したトークンの扱いは、決めた側の動作を明示したテストにする。
- 管理者の印の変更: 付けた直後・外した直後の次の要求で、管理の API の 403／200 がサーバー側で切り替わる。自分の印を外す操作の扱いを明示する。
- ロックの解除: 解除の直後に正しいパスワードで入れる。解除の後の失敗回数の境界。ロックの状態の行が無い利用者の解除。時刻は注入した時計で動かす。
- 最後の管理者の保護: 最後の有効な管理者の印を外す・止める操作は拒否され、状態が変わらない。2人の管理者が同時に互いを外す・止めても、有効な管理者が 0 人にならない（重なりは待ち合わせで確実に作る）。
- 管理の API の認可: 足す管理の API のすべてで、未認証 401・管理者フラグなし 403・管理者 200 を確かめる。停止中の管理者は管理の API を呼べない。
- 要求の改ざん: 管理の API の外（`/api/me` など）から、本文の値を変えて自分の印や状態を変えられない。
- 監査: 4つの操作ごとに、操作した人・対象の利用者・結果が記録される。
- 漏えい: 一覧・詳細の応答と監査の行に、パスワードのハッシュ・リフレッシュトークン・ロックの内部の値が入らない。TRACE のログを有効にしても、一覧のメールアドレス・氏名がアプリのログに出ない（既存の `*SecretLeakIT` と同じ形）。

A. 上の項目をすべて一覧に足す
B. 利用停止・管理者の印・ロックの解除・最後の管理者・認可だけを足し、改ざん・監査・漏えいは設計の段で決める
C. 一覧は足さず、設計の段で個別に決める
X. Other (please specify)

[Answer]: A

## Q6. 不安定なテストと CI の失敗の扱い
