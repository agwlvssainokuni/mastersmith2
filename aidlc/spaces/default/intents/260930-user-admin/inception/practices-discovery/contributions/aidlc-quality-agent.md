### 2. 今回の Intent で、進め方として決めておくべきテストの点

今回の4つの操作（一覧・管理者の印の付け外し・利用停止・ロックの解除）は、認証・認可・監査の芯に触れる。主担当の P1 に賛成で、そのうえで次の具体化を提案する。★は要件定義で値・動作を決めてからテストを書くもの（`team.md` の既存の書き方にそろえる）。

#### 2.1 P1 の具体化: 「認証・認可・監査に関わる機能では、次のテストを必ず書く」に足す行の案

面談で依頼者が確かめたら、`team.md` の Testing Posture の一覧（既存の「招待と登録の完了」などと同じ階層）に次を足す案。

- 利用停止: 停止中の利用者は、ログインの照合・トークンの更新・アクセストークンの認証の**3つの入口のすべて**で拒否されることを、入口ごとにサーバー側のテストで確かめる（既存の `InvitedPersonAuthenticationIT` の「招待中の利用者は3つの入口のどれでも拒否」と同じ形）。停止を解いた直後に3つの入口で受け付けられること。停止の前に出したリフレッシュトークン・アクセストークンの扱いは、決めた側の動作を明示したテストにする。★停止を応答から推測できてよいか、停止の前のトークンの扱い
- 管理者の印の変更: 印を付けた直後・外した直後の次の要求で、管理の API の 403／200 がサーバー側で切り替わること（画面の古い印に頼らない。K-4）。自分の印を外す操作の扱いを明示したテストにする。★自分の印の扱い
- ロックの解除: 解除の直後に正しいパスワードで入れること、解除の後の失敗回数の境界（しきい値−1回ではロックされない／しきい値ちょうどでロックされる）、ロックの状態の行が無い利用者の解除（K-2）。時刻は `MutableClock` で動かし、実時刻と `sleep` に頼らない。★解除の後の失敗回数の扱い、行が無いときの応答
- 最後の管理者の保護: 最後の有効な管理者の印を外す・止める操作が拒否されること、拒否の後に状態が変わっていないこと。2人の管理者が同時に互いを外す・止める競合で、有効な管理者が 0 人にならないこと。競合のテストはスレッドの数に頼らず、既存の待ち合わせの形（`TestPasswordChangeBarrier`、`project.md` の学び「LongSupplier で待ち合わせる」）で重なりを確実に作る。★最後の管理者の数え方（止めた管理者を数えるか）
- 管理の API の認可: 足す管理の API の**すべて**について、未認証（401）・管理者フラグなし（403）・管理者（200）をサーバー側のテストで確かめる（既存の「認可」の行を、新しい API の一つひとつに当てることの確認）。停止中の管理者が管理の API を呼べないこと。
- 監査: 4つの操作ごとに、操作した人・対象の利用者・結果が記録されること。★拒否した操作（403・最後の管理者の拒否）を残すか
- 漏えい: 一覧・詳細の応答にパスワードのハッシュとロックの内部の値が含まれないこと。一覧の型と応答が `TraceAspect` の TRACE のログに出るとき、メールアドレス・パスワードのハッシュが含まれないこと（K-8。既存の `*SecretLeakIT` と同じ形で、TRACE を有効にして確かめる）。

根拠: K-1・K-2・K-4・K-6・K-8（`evidence.md`）、`code-quality-assessment.md` の既存のテストの表、`project.md` の Mandated「認証・認可・監査ログに関わる変更には、失敗の場合のテストを含める」。

性質ベースのテストの当て先: 「最後の管理者かどうかの判定（有効な管理者の数え方）」が純粋な関数として切り出せるなら、`team.md` の「性質ベースのテストを純粋な関数に一部適用する」の対象に入れる。これは決まりの追加ではなく、既存の決まりの当て先の確認で足りる（設計に回してよい）。

#### 2.2 P4 の補足: E2E の代表の流れは「自分で作った利用者だけ」を操作する

E2E は1つの WAR・1つの内部DB・1人の初期管理者を全ファイルで共有し、順に流れる（1節の補足）。今回の流れが初期管理者を止める・印を外す・ロックすると、その後のファイル（`adminLogin.ts` で初期管理者に頼るもの）がすべて落ちる。逆に、初期管理者は `020-auth.e2e.ts` の誤りのログインで失敗回数を持っているため、初期管理者をロックの対象に使うと前のファイルの状態に頼ることになり、`team.md` の「前のテストが作った状態に頼らない」に反する。

提案（`team.md` の E2E の行への一文の追加の案）: 「利用者の状態を変える操作（停止・印の変更・ロック）を行う E2E は、その流れで作った利用者（`support/registeredUser.ts`）だけを対象にし、初期管理者の状態は変えない」。

流れの中身（例: 管理者が別の利用者を止める → その利用者はログインできない → 解く → ログインできる）は設計に回してよい、という主担当の見立てに賛成。最後の管理者の保護と競合は E2E ではなくサーバー側の結合テストで確かめる（初期管理者しか管理者がいない共有の環境では、E2E で安全に作れない）。

#### 2.3 P3 の補足: 「手を入れる」の範囲と、見込む時点

- 1節の補足のとおり、今の運用では説明文の書き直しでも一覧から外す作業が付いている。今回は `auth.repository`（一覧を作った時点で分岐 50.0%）・`auth.domain`・`access.domain`・`audit.repository` に及びうる（K-7）。どれも「失敗の理由の列挙に1つ足す」程度の変更でも、そのパッケージ全体の下限を満たすテストが要る。
- 決まりを変える提案ではない。面談では、(a) 「手を入れる」は本体のソース（`src/main`）の変更のすべてを指し、テストだけの変更は含まない、という今の読み方を確かめる、(b) Delivery Planning とコード生成の計画で、手を入れる一覧のパッケージとその時点のカバレッジ（`:backend:cleanTest :backend:cleanIntegrationTest` を付けた実測）を先に並べて作業を見込む、の2点を確かめれば足りる。
- 設計の段で「一覧のパッケージに手を入れない置き場」を選ぶ動機になりうる（K-3 の置き場の判断）が、カバレッジの作業を避けるために設計を曲げないこと、も合わせて確かめたい。
