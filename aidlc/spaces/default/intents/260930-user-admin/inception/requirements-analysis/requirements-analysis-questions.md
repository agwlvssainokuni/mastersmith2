# Requirements Analysis の質問

依頼文（「利用者の管理の画面を作る（一覧・管理者の印・利用停止・ロックの解除）」）、コード知識ベースの所見（K-1〜K-9）、`team.md`・`project.md` の決まりをもとに、要件を決めるのに足りない点を尋ねます。

## 決まっていること（質問にしない）

- **操作できる人:** 管理者だけです。管理の API は `/api/admin/**` に置き、今の決まり（要求ごとに DB の管理者の印を見て 401／403）に乗せます（K-5）。画面は今の管理の入口（`/admin`）の下に置き、日本語と英語の両方を用意します（`team.md`）。
- **4つの操作:** 一覧・管理者の印の付け外し・利用停止（と停止の解除）・ロックの解除です（依頼文）。今は DB を直接直すか、ロックの解除時刻を待つしかありません（K-1・K-2・K-4）。
- **固い制約（`project.md`、今回の Practices Discovery で確定）:**
  - 最後の有効な管理者を無くす操作（印を外す・利用を止める）は受け付けない。
  - 利用者の状態（停止・管理者の印）の判定は、ログインの照合・トークンの更新・アクセストークンの認証のすべてでサーバー側で行う。
  - 権限・状態を変える管理の操作は、操作した人・対象の利用者・結果を監査に残す。
  - API の応答（成功の応答を含む）に、パスワードのハッシュ値・ロックの判定の内部の値を含めない。
  - メールアドレスはアプリのログに出さない（管理者に見せる一覧の応答に載せるのは、招待の一覧と同じく可）。
- **決まっている仕様:** ログアウトはアクセストークンを失効させない（`project.md` の DECIDED）。アクセストークンの有効期限は 5 分、ロックはしきい値 5 回・30 分です（今の設定の既定、K-2）。
- **必ず書くテスト:** `team.md` の一覧（利用停止・管理者の印・ロックの解除・最後の管理者・認可・改ざん・監査・漏えい）のとおりです。★の値は、下の質問の答えで決めます。

質問は Standard の目安（5〜8）より多い 12 問です。今回は、認証の3つの入口・トークン・ロック・監査という既存の仕組みのそれぞれに、新しい振る舞いの境目があるためです。画面の組み立て（確認の表示の要否・配置）は画面イメージの段で、処理の置き場（どの機能に置くか）は設計の段で扱います。
