## 1. Intent の分析

- **目的**: 管理者が、すでにいる利用者を画面から管理できるようにする。具体的には、利用者の一覧を見て、管理者の印を付け外しし、利用を止めて（解いて）、ロックを解除し、氏名・言語を直せるようにする（DESC、RQ2）。
- **背景**: 今は、利用者を作る道（招待と登録の完了）はあるが、作った後の利用者を管理する画面・API・問い合わせがどの層にも無い。管理の手段は、DB を直接直すことと、ロックの解除時刻（30 分）を待つことだけである（KB `business-overview.md`）。利用停止を表す状態も無い（K-1）。
- **利用者**:
  - 管理者（管理者の印を持つ利用者）: 利用者を一覧し、印・状態・ロック・氏名・言語を管理する（DESC）
  - 管理される利用者: 止められるとログインできなくなり、解かれると再びログインできる。ロックを解かれると、解除の予定の時刻を待たずにログインできる
  - 運用者・監査者: 管理の操作が監査ログに残る（PM（Mandated））
- **成功基準**:
  - 管理者が管理画面で利用者を探し（ページ送りと検索）、状態・印・ロックを一目で確かめられる
  - 管理者が利用者を止めると、その利用者は次の要求からどの入口でも使えなくなり、解くと再びログインできる
  - 管理者が、ロック中の利用者を待たずにログインできる状態に戻せる
  - どんな操作・同時の操作でも、利用停止していない管理者が 0 人にならない
  - 権限・状態を変える操作と、業務の理由で拒否した操作が、監査ログに残る
- **種類・規模**: 既存のアプリへの機能の追加（ブラウンフィールド）。認証の3つの入口（ログインの照合・トークンの更新・アクセストークンの認証、K-1）、ロックの状態（`auth`、K-2）、監査（`audit`、K-6）、利用者（`user`）に手が入り、利用者とロックの状態を合わせる処理は `user` の外に置く必要がある（K-3）。新しい管理の画面を1つ足す（K-9）。

## 2. 機能要件

Given/When/Then は受け入れの判定の例で、網羅はユーザーストーリーの段で行う。

### FR1 利用者の一覧

出典: DESC、RQ3、RQ4、KB K-5・K-8

- **FR1.1** 管理者は、管理画面で利用者の一覧を見られる。一覧の各行には、メールアドレス・氏名・管理者の印・状態（有効／利用停止）・ロック中かどうか・登録した日時を表示する。ロック中の利用者には、解除の予定の時刻も表示する（RQ3）。
  - Given 管理者がログインしている / When 利用者の一覧を開く / Then 各利用者のメールアドレス・氏名・印・状態・ロックの有無・登録した日時が表示される
- **FR1.2** ロック中かどうかは、表の値だけでなく、今の時刻と解除の予定の時刻を比べて決める。解除の予定の時刻を過ぎた利用者は、失敗回数が残っていてもロック中と表示しない。ロックの状態の行が無い利用者は、ロックしていない（失敗回数 0）として扱う（K-2）。
  - Given 解除の予定の時刻を過ぎた利用者がいる / When 一覧を開く / Then その利用者はロック中と表示されない
- **FR1.3** 一覧は1ページ 20 件のページ送りとし、並びは登録した順とする。一覧の応答には、全体の件数とページの番号を含める（RQ4、K-5）。
- **FR1.4** 管理者は、メールアドレスまたは氏名の一部を入れて利用者を探せる（部分一致）。大文字と小文字を区別しない。`%`・`_` などの特殊文字は、ワイルドカードではなく文字どおりに一致させる。検索の結果もページ送りする。状態（管理者だけ・停止中だけ・ロック中だけ）での絞り込みは持たない（RQ4）。
  - Given 氏名に「山田」を含む利用者が2人いる / When 「山田」で検索する / Then その2人だけが一覧に出る
- **FR1.5** ページの番号や検索の文字が不正なとき（数でない、範囲の外、長すぎる など）は、入力の誤りとして拒否する（K-5）。検索の文字の長さの上限は機能設計で決める。
- **FR1.6** 一覧の応答には、パスワードのハッシュ値・リフレッシュトークン・ロックの判定の内部の値（連続の失敗回数の生の値、ダミーの行など）を含めない（PM（Forbidden））。ロックについて応答に含めるのは、今の時刻で判定した結果の3つ（ロック中かどうか、ロック中なら解除の予定の時刻、FR5 の操作を出せるかどうかの真偽）だけとし、失敗回数そのものは含めない。固い制約の「ロックの判定の内部の値」は判定に使う生の値（連続の失敗回数・ダミーの行など）を指し、この3つの判定の結果は含めてよい（依頼者の決定、Request Changes の R-02）。

### FR2 管理者の印の付け外し

出典: DESC、RQ7、RQ8、RQ9、PM（Forbidden・Mandated）

- **FR2.1** 管理者は、一覧から利用者に管理者の印を付けられ、外せる。
- **FR2.2** 印を付けた・外した直後の、その利用者の次の要求から、管理の API の可否（200／403）がサーバー側で切り替わる。印はトークンに入れず、要求ごとに DB から読む今の仕組みのまま扱う（RQ7、K-4）。
  - Given 管理者 A が利用者 B の印を外す / When B が次に管理の API を呼ぶ / Then 403 が返る
- **FR2.3** 印を外しても、その利用者のアクセストークン・リフレッシュトークンは無効にしない。画面は次のトークンの更新（最大 5 分後）かログインで印を反映する。管理の画面で 403 を受けたときは、管理者ではなくなった旨を表示する（RQ7）。
- **FR2.4** 管理者は、自分自身の印を外せない。最後の管理者でなくても拒否する（RQ8）。
- **FR2.5** 印を外すと利用停止していない管理者が 0 人になる操作は拒否する（PM（Forbidden）、RQ9）。数え方は FR4.1 のとおり。

### FR3 利用停止と停止の解除

出典: DESC、RQ5、RQ6、RQ8、RQ12、PM（Mandated・Forbidden）

- **FR3.1** 管理者は、一覧から利用者の利用を止められ、止めた利用者の停止を解ける。止めた理由は記録しない（誰がいつ止めたかは監査ログに残る、RQ12）。
- **FR3.2** 利用停止中の利用者は、ログインの照合・トークンの更新・アクセストークンの認証の3つの入口のすべてでサーバー側で拒否する（PM（Mandated）、K-1）。止めた直後の次の要求から拒否する（RQ5）。
  - Given 管理者が利用者 B を止める / When B が止める前に出したアクセストークンで API を呼ぶ / Then 401 が返る
  - Given 管理者が利用者 B を止める / When B が止める前に出したリフレッシュトークンで更新する / Then 拒否される
- **FR3.3** 止めたときに、その利用者のリフレッシュトークンをすべて無効にする。停止を解いても、止める前に出したトークンは使えない（RQ5）。
  - Given 利用者 B を止めて、停止を解く / When B が止める前のリフレッシュトークンで更新する / Then 拒否され、B はログインし直す必要がある
- **FR3.4** 停止中の利用者の拒否は、入口ごとに、今のほかの失敗と同じ応答にし、停止していることを応答から推測できないようにする（RQ6）。ログインは、存在しないメールアドレス・パスワードの誤り・ロック中と同じ 401 `AUTHENTICATION_FAILED`。トークンの更新は、無効・期限切れのリフレッシュトークンと同じ 401 `REFRESH_FAILED`。アクセストークンの認証は、無効・期限切れのアクセストークンと同じ 401 `AUTHENTICATION_REQUIRED`（R-04）。
  - Given 停止中の利用者 B が正しいパスワードでログインする / When 応答を見る / Then パスワードの誤りと同じ応答（401 `AUTHENTICATION_FAILED`）である
- **FR3.5** 停止を解いた直後から、その利用者は3つの入口のすべてで受け付けられる（新しくログインすれば使える）。
- **FR3.6** 管理者は、自分自身を止められない。最後の管理者でなくても拒否する（RQ8）。
- **FR3.7** 止めると利用停止していない管理者が 0 人になる操作は拒否する（PM（Forbidden））。
- **FR3.8** 停止中の管理者は、管理の API を呼べない（FR3.2 の結果として）。
- **FR3.9** 停止中の利用者のメールアドレスは、今までどおり「登録済み」として扱い、そのメールアドレスへの招待を拒否する [assumption]（KB `code-quality-assessment.md` の招待の確かめ）。

### FR4 最後の有効な管理者の保護

出典: RQ9、PM（Forbidden）、TP

- **FR4.1** 「有効な管理者」は、管理者の印を持ち、利用停止していない利用者とする。ロック中の管理者も数える（RQ9）。
- **FR4.2** 印を外す（FR2.5）・利用を止める（FR3.7）操作で、有効な管理者が 0 人になる場合は拒否し、利用者の状態を変えない。自分自身への操作は FR2.4・FR3.6 で拒否し、操作する管理者は有効な管理者であるため、1件ずつの操作ではこの拒否は起きない。この保護は、操作が同時に重なったとき（FR4.3）と、ほかの経路で状態が変わったときの守りとして、判定を操作ごとに必ず行う。
  - Given 有効な管理者が A と B の2人である / When A が B の印を外す / Then 受け付けられ、有効な管理者は A の1人になる
- **FR4.3** 2人の管理者が同時に互いの印を外す・互いを止めるなど、操作が同時に重なっても、有効な管理者が 0 人にならない（TP の必須テスト）。
- **FR4.4** FR4.2 の拒否は API の1件ずつの操作では起きないため、`team.md` の必須テスト（最後の有効な管理者の印を外す・止める操作は拒否され、状態が変わらない）は、業務処理の層を直接呼ぶテスト（操作する管理者を有効な管理者の数に含めない状態を用意する）と、待ち合わせで作った同時の重なり（FR4.3）の両方で確かめる（R-08）。

### FR5 ロックの解除（失敗回数の取り消し）

出典: DESC、RQ10、KB K-2

- **FR5.1** 管理者は、ログインの失敗回数が1回以上ある利用者について、失敗回数を 0 に戻せる。ロック中の利用者なら、この操作でロックも解ける（RQ10）。
- **FR5.2** ロックの状態の行が無い利用者と、失敗回数が 0 の利用者には、この操作を出さない。API にそのような利用者を指定したときは、変えるものが無い旨の業務の誤りとして拒否する（RQ10）。
- **FR5.3** 操作の直後から、その利用者は正しいパスワードでログインでき、しきい値（既定 5 回）まで失敗できる。
  - Given 利用者 B がロック中である / When 管理者が B の失敗回数を 0 に戻す / Then B は直後に正しいパスワードでログインできる
  - Given 失敗回数を 0 に戻した直後の B / When B がパスワードを4回誤る / Then B はロックされない（5回目でロックされる）
- **FR5.4** 同じ利用者のログインの判定と、この操作が同時に重なっても、失敗回数とロックの状態が矛盾しない（ログインの判定と同じ行の排他で順番をそろえる、K-2）。

### FR6 氏名・言語の変更（管理者）

出典: RQ2、RF1、RF2

- **FR6.1** 管理者は、一覧から利用者の氏名と言語（ja・en）を変えられる。自分自身の氏名・言語も変えられる（RQ2、RF2）。
- **FR6.2** 氏名と言語の検証は、利用者が自分でプリファレンスの画面から変えるときと同じ規則とする（氏名は空にできない、言語は ja・en のどちらか）。
- **FR6.3** 変えた言語は、その利用者の次の画面の表示・エラーの説明文・送るメールに当たる。管理者が自分自身の言語を変えたときは、変えた直後から自分の画面に当たる（既存のプリファレンスの動作に合わせる）。
- **FR6.4** 氏名・言語の変更は、監査ログに残さない（RF1）。
- **FR6.5** メールアドレス・パスワード・テーマ・文字の大きさは、管理者は変えられない（RQ2）。
- **FR6.6** 対象の利用者がいないときは、ほかの操作と同じ「対象の利用者がいない」業務の誤りとして拒否する。今と同じ値のまま保存したときは、プリファレンスの保存と同じく成功として受け付ける（監査に残さない操作のため、前提 A2 の「変えるものが無い」拒否は当てない）（R-04）。

### FR7 監査ログ

出典: RQ11、RF1、PM（Mandated）、KB K-6

- **FR7.1** 次の成功した操作を、操作した人・対象の利用者・結果とともに監査ログに残す（PM（Mandated））。
  - 管理者の印を付ける・外す
  - 利用を止める・停止を解く
  - 失敗回数を 0 に戻す（ロックの解除を兼ねる）
- **FR7.2** FR7.1 の操作を業務の理由で拒否したときも、失敗として理由とともに残す（RQ11）。理由は次の4つを区別する: 対象の利用者がいない・自分自身への操作（FR2.4・FR3.6）・変えるものが無い（FR5.2、すでに管理者の利用者に印を付ける など）・最後の有効な管理者の保護（FR4.2）。
  - Given 管理者 A が自分自身を止めようとする / When 拒否される / Then 監査ログに、操作した人 A・対象 A・失敗・理由（自分自身への操作）が残る
- **FR7.5** 1つの操作が複数の拒否の理由に当たるときは、「対象の利用者がいない → 自分自身への操作 → 変えるものが無い → 最後の有効な管理者の保護」の順に判定し、最初に当たった理由1つで拒否し、その理由を監査に残す。応答もその理由の誤りとする（R-01）。
  - Given 有効な管理者が A だけである / When A が自分自身を止めようとする / Then 理由は「自分自身への操作」として拒否され、監査にもその理由が残る
- **FR7.6** 対象の利用者がいないときは、要求で指定された利用者 ID をそのまま監査の対象の利用者として残す（R-01）。
  - Given 利用者 ID 99999 の利用者はいない / When 管理者 A が ID 99999 の利用者を止めようとする / Then 「対象の利用者がいない」として拒否され、監査ログに、操作した人 A・対象の利用者 ID 99999・失敗・理由（対象の利用者がいない）が残る（R-07）
- **FR7.3** 管理者でない利用者が管理の API を呼んだとき（403）は、今までどおり「アクセスの拒否」として残す。入力の誤り（FR1.5）と一覧の閲覧は残さない。氏名・言語の変更は残さない（RF1）。
- **FR7.4** 監査ログには、パスワード（平文・ハッシュ値とも）・トークン・ロックの判定の内部の値を残さない（PM（Forbidden））。

### FR8 画面の置き場と API

出典: DESC、TP、KB K-5・K-9

- **FR8.1** 利用者の管理の画面は、管理者だけが使える管理画面の中に置き、サイドバーの管理のメニューから開けるようにする（招待の画面と同じ形、K-9）。
- **FR8.2** 管理の API は `/api/admin/` の下に置き、今の決まり（要求ごとに DB の管理者の印を見る）で管理者だけに許す。未認証は 401、管理者でない利用者は 403 とし、サーバー側のテストで確かめる（画面で隠すことを代わりにしない、TP）。
- **FR8.3** 管理の API の外（`/api/me` など）からは、要求の本文の値を変えても、管理者の印・利用停止・失敗回数を変えられない（TP の必須テスト「要求の改ざん」）。

## 3. 非機能要件

- **NFR1 認証の一貫性**: 利用者の状態（利用停止・管理者の印）の判定は、ログインの照合・トークンの更新・アクセストークンの認証のすべてでサーバー側で行う。画面で操作を隠すことをサーバー側の判定の代わりにしない。出典: PM（Mandated）、K-1
- **NFR2 列挙の防止**: 停止中の利用者の拒否は、ほかの認証の失敗と同じ応答とし、応答・応答時間の違いから停止を推測しにくくする（ログインの時間をそろえる今の仕組みを崩さない）。出典: RQ6、KB K-2
- **NFR3 個人情報と秘密情報**: メールアドレスをアプリのログとエラー応答に含めない（伏せ字は可）。一覧の型を含む受け渡しの値は、TRACE のログに文字列で出ても、メールアドレス・氏名・パスワードのハッシュ値が出ない形にする。API の応答（成功の応答を含む）にパスワードのハッシュ値・ロックの判定の内部の値を含めない。一覧の検索の文字（メールアドレスが入りうる）は、アプリのログ・トレースの属性・監査ログに出さない（要求の形は設計で決める）（R-03）。出典: PM（Forbidden・Corrections）、K-8
- **NFR4 同時の操作**: 最後の有効な管理者の保護（FR4.3）と、失敗回数の取り消しとログインの判定（FR5.4）は、同時の重なりでも矛盾しない。テストでは、スレッドの数に頼らず待ち合わせで重なりを確実に作る。出典: TP、PM（Forbidden）
- **NFR5 応答時間**: 一覧（検索を含む）と各操作の API は、既存の API と同じく 95 パーセンタイルで 1 秒以内に応答する [assumption]（件数の想定と測り方は NFR 要件の段で決める）。出典: 既存の API の目標（前の Intent）
- **NFR6 接続の使い方**: 操作1件で内部DB の接続を2本使う経路（確定の後の監査の記録）を含め、同時の要求で接続プールが尽きないこと（既存の上限 30）を、必要なら負荷の試験で確かめる。出典: PM（Corrections）
- **NFR7 アクセシビリティ**: 利用者の管理の画面の画面部品ごとにアクセシビリティの検査を1件入れ、WCAG 2.1 AA を満たす。テーマ（light・dark）と文字の大きさ（sm・md・lg）のどの組み合わせでも表示が崩れない。実際のブラウザでの検査を足すかは設計で決める。出典: TP
- **NFR8 多言語**: 利用者の管理の画面の文言と、新しいエラーの説明文は、ja・en の両方を用意する。出典: TP
- **NFR9 テスト**: `team.md` の必須テスト（利用停止・管理者の印の変更・ロックの解除・最後の管理者の保護・管理の API の認可・要求の改ざん・管理の操作の監査・利用者の管理の漏えい）を書く。E2E は代表の流れを1本まで足し、状態を変える操作はその流れで自分で作った利用者だけを対象にし、初期管理者の状態は変えない。カバレッジの下限（行 80%・分岐 70%）を守り、一覧で外している既存のパッケージに手を入れたら（説明文だけの直しを含む）、パッケージごとの下限の対象に戻す。出典: TP
- **NFR10 スキーマの変更**: 内部DB のスキーマの変更（利用停止の状態の列など）は Flyway の V9 以降の前進のみとし、1つ前の版のアプリが動く後方互換を保つ。既存の利用者は「有効（停止していない）」を初期値とする。出典: TP、KB
- **NFR11 構造の決まり**: 利用者とロックの状態を合わせる処理は、`user` が `auth` を知らない境界（ArchUnit の境界テスト）を緩めずに置く。境界テストを緩める・消す必要が出たときは、コード生成の計画に明記して依頼者の承認を得る。出典: TP、KB K-3

## 4. 制約

- 管理者かどうかは管理者の印だけで決める。ロール・グループは扱わない。
- アクセストークンは失効の仕組みを持たない（PM（DECIDED））。利用停止を次の要求から効かせるのは、アクセストークンの認証で DB の状態を見ることによる（FR3.2）。
- 内部DB は組み込みの H2 で、1インスタンスだけで動く前提（KB `architecture.md`）。
- make-you-chic-ui は変更しない。足りない部品は frontend の側で作り、作った場合は make-you-chic-ui 側への取り込みを依頼者に諮る（PM（Forbidden・Corrections））。
- 新しい依存を足すときは、採用の前にライセンスを確かめる（TP）。
- 今回の Bolt で、`frontend/.npmrc` に `ignore-scripts` を入れ、`.idea/.gitignore` に `dataSources.xml`・`dataSources/` を足す（今回の Practices Discovery の決定。機能の要件ではないが、この Intent の作業として扱う）（TP）。

## 5. 前提

- **A1** 停止中の利用者のメールアドレスへの招待は、今までどおり「登録済み」として拒否する（FR3.9）[assumption]。理由: 利用者を消さないため、同じメールアドレスの2人目の利用者を作らない。
- **A2** 「変えるものが無い」操作（すでに管理者の利用者に印を付ける、すでに停止中の利用者を止める、失敗回数が 0 の利用者の回数を戻す など）は、業務の誤りとして拒否し、監査ログに失敗として残す（FR7.2）[assumption]。受け付けて何もしない（成功として扱う）形は取らない。理由: 2人の管理者が同じ利用者を同時に操作したとき、後の人に「すでに変わっていた」ことを知らせるため。
- **A3** 一覧の「登録した日時」は、利用者の表の作成日時（登録の完了の日時、初期管理者は作成の日時）とする [assumption]。
- **A4** 一覧に出すのは利用者（登録を完了した人）だけで、招待中の人は含めない。招待中の人は、今までどおり招待の一覧で見る [assumption]。
- **A5** 管理者の印を付けたときは、トークンを無効にしない。付けた直後の次の要求から管理の API を呼べ、画面は次のトークンの更新かログインで印を反映する [assumption]（FR2.3 と同じ扱い）。
- **A6** （確定済み・前提ではない）固い制約「API の応答にロックの判定の内部の値を含めない」の読み方は、依頼者の Request Changes（R-02）で確定し、FR1.6 に要件として書いた。
