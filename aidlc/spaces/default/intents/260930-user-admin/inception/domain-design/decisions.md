# 設計の決定（ADR）— user-admin

出典の表記は `components.md` と同じ。日付はすべて 2026-09-30、状態はすべて Accepted（この段の承認で確定）。

## ADR-001: 利用者の管理を新しい部品 UserAdministration に置く

- **Context**: 一覧は利用者（`user` の表）とロックの状態（`auth` の表）を合わせ、操作は印・停止（`user`）と失敗回数・リフレッシュトークン（`auth`）にまたがる。境界の決まりで `user` は `auth` を知らない（K-3）。拒否の理由の順・最後の有効な管理者の保護・管理の操作の監査という、どちらの部品にも属さない業務の決まりがある。
- **Decision**: 新しい部品 UserAdministration（パッケージ `useradmin`、`/api/admin/` の下の API）を作り、`user` と `auth` の service の口を使う。監査には出来事で知らせる。新しい部品の境界の検査（`<機能>BoundaryArchitectureTest`、`team.md` の Code Style）を足し、`useradmin` は `user`・`auth` の service の口と値の型だけを使い、`invitation`・`dsl` 系に依存しないことを確かめる。`audit` の既存の境界の検査（`AuditBoundaryArchitectureTest`）は変えない（`audit` から他の機能への依存を制限する決まりは今も無い）。代わりに `useradmin` 側に新しい境界の検査を足し、`invitation` の検査と同じ形で「`useradmin` の外から依存してよいのは `audit` だけで、`audit` からは出来事の型だけ」を確かめる（アーキテクチャの見直しの R-02 を受けて直した）。
- **Consequences**:
  - 良い点: 業務の決まりが1か所に集まり、`user`・`auth` の既存の責務を広げすぎない。`access`・`dslmanage` と同じく、`auth` に依存してよい側の部品になる。
  - 悪い点: 部品が1つ増え、境界の検査が1本増える。
  - 中立: 一覧の行ごとにロックの判定の結果を読むため、読みの回数は 1ページ 20 件で増える（件数の想定と測り方は NFR 要件）。
- **Alternatives Rejected**:
  - `auth` に置く（DQ1 B）: 依存の向きは足りるが、`auth` の責務が「ログインとトークン」から「利用者の管理」まで広がり、`auth` の境界の検査の意味が変わる。
  - `access` に置く（DQ1 C）: `access` は判定と入口だけを持ち、状態を変える業務の決まりを持たない。責務が混ざる。

## ADR-002: 利用停止の状態は利用者（UserAccount）が持つ

- **Context**: 停止の状態は3つの入口（ログインの照合・トークンの更新・アクセストークンの認証）が読み、一覧にも出す。管理者の印は利用者の表にあり、入口は `user` の service の口から読んでいる（K-1・K-4）。
- **Decision**: `users` の表に停止の状態を Flyway の V9 以降で足し（既存の利用者は「有効」）、UserAccount が持つ。入口は今と同じ口で利用者を読み、停止の判定は Authentication が行う。移行は前進のみで、1つ前の版のアプリが動く後方互換を保つ（NFR10、TP）。
- **Consequences**:
  - 良い点: 印と停止が同じ行にあり、最後の有効な管理者の数え上げが1つの表で済む。入口の読み取りが増えない。
  - 悪い点: `user` のパッケージ（今は一覧で外していない）に手が入り、パッケージごとのカバレッジの下限の対象のまま作業が付く。
  - 中立: 停止の理由は持たない（RQ12）。
- **Alternatives Rejected**:
  - `auth` が持つ（DQ2 B）: 入口はすべて `auth` にあるが、一覧と最後の管理者の数え上げが `user` と `auth` の両方の表を読むことになる。
  - 新しい部品が持つ（DQ2 C）: 入口が新しい部品を読むことになり、`auth` から `useradmin` への依存が生じて循環しうる。

## ADR-003: 止めたときのリフレッシュトークンの無効化は、同じトランザクションで直接呼ぶ

- **Context**: 止めたら、その利用者のリフレッシュトークンをすべて無効にする（FR3.3）。リフレッシュトークンは `auth` の表にあり、まとめて無効にする問い合わせは今は無い（K-1）。
- **Decision**: UserAdministration の止める処理が、同じトランザクションの中で Authentication の「利用者のリフレッシュトークンをまとめて無効にする」口を直接呼ぶ。止める操作とトークンの更新が同時に重なったときに残る隙は塞がず、記録する（ストーリーの M8 B）。
- **Consequences**:
  - 良い点: 停止と無効化が同じ確定に入り、処理の流れが1か所で読める。
  - 悪い点: UserAdministration が Authentication の口に直接依存する（ADR-001 で許した向きの範囲）。まとめての無効化の問い合わせを `auth.repository` に足すため、`packagesJudgedByTotal` の一覧にある `auth.repository` に手が入り、パッケージごとの下限（行 80%・分岐 70%）を満たして一覧から外す作業が付く（`team.md`。過去の実測は分岐 50.0%。量は Delivery Planning とコード生成の計画で実測して見積もる）。
  - 中立: 停止を解いても、止める前のリフレッシュトークンは使えない。アクセストークンは失効の仕組みを持たない（PM の DECIDED、ストーリーの差1）。
- **Alternatives Rejected**:
  - 停止の出来事を `auth` が受けて無効にする（DQ3 B）: `UserCreatedEvent` と同じ形で `auth` が止める側を知らずに済むが、処理の流れが2か所に分かれ、出来事を出すのが `useradmin` か `user` かの決めごとが増える。

## ADR-004: ページ送りの計算を共通の置き場に移して共有する

- **Context**: 招待の一覧のページ送り（サーバーの `InvitationPaging`、画面の `features/invitation/paging.ts`）は、境界の決まりで利用者の管理から直接使えない（K-3、`invitation` の外から依存してよいのは `audit` だけ）。
- **Decision**: サーバーは `common` の下の新しいパッケージ `common.paging`（部品 Paging。`packagesJudgedByTotal` の一覧に無いパッケージに置き、新しいパッケージとしてパッケージごとの下限の対象にする）、画面は `src/shared/`（部品 UiPaging）に移し、招待と利用者の管理で共有する。招待の振る舞いは変えない。
- **Consequences**:
  - 良い点: 1ページ 20 件・ページの番号の検証・最後のページより後の扱いが1か所に決まる。性質ベースのテストも1か所で済む。
  - 悪い点: 招待のコードに手が入る。`invitation` のパッケージは `packagesJudgedByTotal` の一覧に入っていない（すでにパッケージごとの下限の対象）ため、一覧から外す作業は付かないが、移した後も下限を満たす必要がある。
  - 中立: 移す範囲（計算だけか、文言も含むか）はコード生成の計画で決める。
- **Alternatives Rejected**:
  - 利用者の管理の側に同じ形を作る（DQ4 B）: 招待のコードに触れずに済むが、同じ計算が2か所に重なり、片方だけ直す誤りが起きやすい。

## ADR-005: 管理の画面すべての 403 の扱いを画面の骨組みに置く

- **Context**: 管理の画面すべて（入口・DSL・招待・利用者の管理）で、403 を受けたら同じ表示にし、ログインの状態を読み直して管理のメニューを消す（ストーリーの M5 B・差2、画面イメージの S6）。今は入口と DSL が「ページが見つかりません」、招待が一般の誤りの文言で出している。
- **Decision**: ApiClient が管理の API の 403 を「権限が無い」と分かる形で知らせ、AppFrame が共通の表示（S6）への切り替えとログインの状態の読み直しを行う。各管理の画面はこの共通の扱いを使う。
- **Consequences**:
  - 良い点: 4つの画面の 403 の扱いが1か所に集まり、後で足す管理の画面も同じ形になる。
  - 悪い点: 既存の3つの画面（入口・DSL・招待）と、それらのテスト（403 を「ページが見つかりません」として確かめているもの）を書き換える範囲が今回に入る。
  - 中立: 表示の文言は「この画面を使う権限がありません」（画面イメージの RQ6 C）。
- **Alternatives Rejected**:
  - 表示の部品だけを共通にし、403 の扱いは各画面で書く（DQ5 B）: 変更は小さいが、4つの画面に同じ扱いが重なり、読み直しの漏れが起きやすい。

## ADR-006: 管理の操作の監査は、既存の出来事の仕組みに種類と理由を足す

- **Context**: 権限・状態を変える管理の操作は、操作した人・対象・結果を監査に残す（PM の Mandated）。業務の理由で拒否した操作も、失敗として理由とともに残す（FR7.2）。監査の仕組みは、出来事を受けて確定の後に別のトランザクションで記録する（K-6）。
- **Decision**: UserAdministration が操作ごとに監査の出来事を出し、AuditLog が受けて記録する。出来事の種類は5つ（印を付ける・外す・止める・停止を解く・失敗回数を戻す）、失敗の理由は5つ（対象の利用者がいない・自分自身への操作・対象の利用者が停止中・変えるものが無い・最後の有効な管理者の保護）と、ログインの「停止中」を足す。業務の拒否で巻き戻しても失敗の行が残る既存の形（`AuditRollbackIT`）にそろえ、監査の書き込みに失敗しても元の操作は失敗させない（`AuditWriteFailureIT`）。共通の監査の仕組みは作らない（PM の DECIDED）。
- **Consequences**:
  - 良い点: 既存の監査の決まり・テストの形をそのまま使える。列を足す移行は要らない見込み（K-6）。
  - 悪い点: `audit` の3ファイル（`AuditEventListener`・`AuditEvent`・`AuditEventFactory`）がさらに大きくなる（`code-quality-assessment.md` の技術的負債）。`audit.repository` などに手が入れば、カバレッジの一覧の作業が付く。
  - 中立: 種類と理由の名前は 32 文字まで（K-6）。名前は機能設計で決める。
- **Alternatives Rejected**:
  - 監査を UserAdministration から直接書く: 既存の境界（監査の repository を使えるのは `audit` だけ）と「確定の後に記録」の決まりに反する。
  - 監査の共通の仕組みを今回作る: PM の DECIDED（業務データの CRUD を扱う後続の Intent で検討）に反する。

## ADR-007: 実現できるかの判断（実現可能性の評価の段の代わり）

- **Context**: classic の範囲では実現可能性の評価の段が無い。この Intent には、作れるかを先に確かめておくべき点が3つある（`project.md` の学び: 実現可能性の判断はドメイン設計で扱い ADR に記録する）。
- **Decision**: 次の3点は実現できると判断し、確かめる条件と持ち主の段を決める。
  1. **最後の有効な管理者の保護の同時性**（FR4.3、NFR4）: 内部DB は組み込みの H2 で1インスタンスだけ（KB `architecture.md`）。2人の管理者が互いの別の行を変えるため、対象の行の排他だけでは守れない（mob の開発の担当）。排他の持ち主は UserAccount とし、UserAccount の service が「管理者の印を持つ行を決まった順（利用者 ID の小さい順）でまとめて排他する」口を出す（利用者の表を読み書きできるのは `user` だけのため）。UserAdministration は、1つのトランザクションの中で、まずこの口で管理者の行を排他し、次に対象の行を扱い、操作する管理者自身が今も有効な管理者かを確かめ直してから、有効な管理者を数える（操作者の印は要求の認証のときに読まれており、待っている間に外されうるため）。排他の順序をそろえることで、2人が互いの印を外す同時の操作でもデッドロックにならず、後の側は待ってから「最後の有効な管理者の保護」で拒否される。既存の排他（`PESSIMISTIC_WRITE`・待ちの上限 3 秒）にそろえる。排他の細部（対象が管理者でない操作でも管理者の行を排他するか、など）は機能設計・NFR 設計で決め、待ち合わせで重ねた結合テスト（ストーリーの AC2.1.6・AC2.1.12・AC3.1.5）で確かめる。負けた側は業務の誤りで返し 5xx にしない。
  2. **リフレッシュトークンのまとめての無効化**（FR3.3）: 利用者 ID ごとの更新の問い合わせを足せば作れる（`auth.repository`）。性能は1人の利用者のトークンの数に比例し、問題にならない見込み。確かめは結合テスト（AC3.1.1）。
  3. **管理の画面すべての 403 の扱い**（ADR-005）: 既存の3つの画面とテストの書き換えが要るが、仕組みは画面の骨組みに置けるため作れる。範囲の大きさは Delivery Planning で見積もる。
  4. **停止中のログインの読み書きの回数をそろえること**（ADR-008）: 停止中は失敗回数とロックの状態を変えない一方で、ロックの状態の行の読み書きの回数をパスワードの誤りのときと同じにする必要がある。何もしない書き込み（ダミーの行への書き込みなど）で回数をそろえる形が成り立つかを、機能設計で確かめる（アーキテクチャの見直しの R-04）。成り立たなければ、応答時間の差の大きさを測って NFR 要件で扱いを決める。
- **Consequences**:
  - 良い点: 作れないと分かる危険を先に減らし、確かめる段がはっきりする。
  - 悪い点: 1. の守り方を決めるまでは、待ちの上限切れの扱い（AC4.1.11 と同じ形）が未定のまま残る。
  - 中立: 1. が待ち合わせのテストで守れないと分かったら、切り替え先として「最後の管理者の保護を、操作の対象の行に加えて管理者の行すべての排他で行う」形に寄せる（機能設計で比べる）。
- **Alternatives Rejected**:
  - 実現できるかの判断を後の段に任せる: 同時性の仕組みはドメインの境界（どの部品が排他を持つか）に関わるため、ここで持ち主を決めておく。
  - 最後の管理者の保護を画面だけで行う: 固い制約（状態の判定はサーバー側）に反する。

## ADR-008: 停止中のログインの判定は、ロックの判定より前に Authentication で行う

- **Context**: 停止中の利用者のログインは、失敗回数とロックの状態を変えず、応答はほかの失敗と同じにし、監査の理由で「停止中」を区別する（ストーリーの M3 A・差5）。応答の時間をそろえる今の仕組み（照合とロックの状態の行の読み書きの回数）を崩さない（AC3.2.3）。
- **Decision**: Authentication のログインの照合の中で、停止の確かめをロックの判定より前に置く。停止中でも、パスワードの照合とロックの状態の行の読み書きの回数を、パスワードを誤ったときと同じにする（ダミーの行を使うなどの形は機能設計で決める）。出来事の失敗の理由に「停止中」を足し、AuditLog が記録する。
- **Consequences**:
  - 良い点: 停止中の利用者のログインで失敗回数が増えず、停止を解いた直後にロックが残らない。
  - 悪い点: 回数をそろえる仕組みに、停止の分岐が1つ増える。`auth.domain`・`auth.service` に手が入り、`auth.domain` はカバレッジの一覧の作業が付く（K-7）。
  - 中立: トークンの更新とアクセストークンの認証では、停止中を無効なトークンと同じ応答にする（FR3.4）。
- **Alternatives Rejected**:
  - ロックの判定の後で停止を確かめる（ストーリーの M3 B）: 依頼者の決定で採らない。停止中に誤ったパスワードで失敗回数が増え、停止を解いた後にロックが残りうる。
