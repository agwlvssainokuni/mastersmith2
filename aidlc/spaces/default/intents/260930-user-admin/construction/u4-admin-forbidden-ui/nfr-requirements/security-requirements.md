# Security Requirements — U4 管理の画面の 403 の共通の扱い（u4-admin-forbidden-ui）

U4 のセキュリティの要件です。U4 は画面の単位（種類 ui）で、サーバー側の認可と監査を持たず、サーバーのコードも変えません。ここでは、画面の判定をサーバーの判定の代わりにしないこと、「権限が無い」の判定の条件、管理者でない利用者が管理の画面を開いたときの扱い、401・ログアウト・読み直しの失敗の扱い、画面の側の印と自分の氏名・言語の反映、画面に出す値と E2E の報告、静的検査と CSP を扱います。セキュリティ・コンプライアンス・品質の視点は、この段（inline）の中で重ねて書きました。答えは `nfr-requirements-questions.md` です（Q1: B、Q2: A、Consolidated Summary Confirmation: Looks correct）。

枝番はこの単位の中で振ります。ほかの要件の置き場は `performance-requirements.md` の冒頭の表のとおりです。上流に当たる ID が無い静的検査と CSP の要件は、テストと検査の関門で確かめる NFR9 の枝番に寄せました（NFR9.5）。

## 前提

- 管理の API の 401・403・200 の判定と、監査の「アクセスの拒否」は、今のサーバーの動作のままです。U4 では変えず、サーバー側のテストは U3 が受け持ちます（AC2.2.6、8節）。
- 画面の側の管理者の印（`LoginState.admin`）は、トークンの応答（ログイン・更新）からだけ入ります（1節の用語）。トークンと利用者の情報はメモリだけに持ちます（既存の `frontend/src/features/auth/authSession.ts`）。
- S6 が出す値は、見出し（登録されたサイドバーの項目の名前、または共通の見出し）・決まった文言・「ホームへ戻る」だけです（D11・D12）。
- GitHub のリポジトリは公開です。テストのデータに実在の個人に関する値を使わず、メールアドレスは予約済みのドメイン（`example.com` など）の下の値を使います（TM の Way of Working・Testing Posture）。

## 4. 脅威と扱い

| 脅威 | 扱い | 要件 |
