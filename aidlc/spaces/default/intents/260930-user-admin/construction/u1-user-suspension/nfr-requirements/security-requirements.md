# Security Requirements — U1 利用停止の状態と3つの入口（u1-user-suspension）

U1 のセキュリティの要件です。U1 は種類 library の単位のため、この段の成果物は `security-requirements.md`・`tech-stack-decisions.md`・`traceability.json` の3つです。性能・規模・信頼性・観測の前提は、別の文書を作らず、この文書の後半の節に置きます。

要件定義の NFR1（認証の一貫性）・NFR2（列挙の防止）・NFR3（個人情報と秘密情報）・NFR5（応答時間）・NFR6（接続の使い方）・NFR9（テスト）・NFR10（スキーマの変更）・NFR11（構造の決まり）を、この単位の3つの入口（ログインの照合・トークンの更新・アクセストークンの認証）、C1 の口（`isSuspended`・`setSuspended`・`revokeAllRefreshTokens`）、C7 の監査の理由 `ACCOUNT_SUSPENDED` に当てます。この段の質問の答え（Q1 A・Q2 A）と、まとめの確認（Looks correct）で決めました。

枝番は単位の中で .1 から振ります。上流に当たる ID が無い要件は、次のとおり寄せました（`project.md` の学び）。

- 想定の規模と観測（指標・警報）は、応答時間の NFR5 の枝番に寄せた（NFR5.4・NFR5.5）。
- ログの中身は、個人情報と秘密情報の NFR3 の枝番に寄せた（NFR3.2）。
- C1 の口のトランザクションの属性は、構造の決まりの NFR11 の枝番に寄せた（NFR11.2）。
- 静的解析・カバレッジ・テストの道具は、テストの NFR9 の枝番に寄せた（NFR9.4〜NFR9.6、うち NFR9.5・NFR9.6 は `tech-stack-decisions.md`）。

出典の略号: FS は機能設計 `aidlc/spaces/default/intents/260930-user-admin/construction/u1-user-suspension/functional-design/functional-spec.md`、BR は同じフォルダの `rules.md` の決まり、要点 n はこの段の `nfr-requirements-questions.md` の設計の要点、CS は契約 `aidlc/spaces/default/intents/260930-user-admin/inception/contract-design/contract-summary.md`、ADR は `aidlc/spaces/default/intents/260930-user-admin/inception/domain-design/decisions.md`、PM は `aidlc/spaces/default/memory/project.md`、TM は `aidlc/spaces/default/memory/team.md`、前 U2 の NFR は `aidlc/spaces/default/intents/260922-auth-audit-base/construction/u2-authentication/nfr-requirements/security-requirements.md`。

## 守るもの

| 守るもの | 置き場 | 守り方 |
|---|---|---|
| 利用停止の状態（`users.suspended`） | 内部DB の利用者の行（V9 で足す） | 変えられるのは C1 の `setSuspended` だけで、呼ぶのは U3 の止める・解く処理だけ。利用者自身の API から変える経路を持たない（NFR1.4） |
| リフレッシュトークン | 内部DB の `refresh_tokens` の行（ハッシュだけ） | 止めるときにまとめて無効にした行は、停止を解いても戻さない（NFR1.3）。止める確定と同時に作られて無効化を逃れた行は、停止の間は拒否され、解いた後は使えうる（NFR1.5）。値をログ・監査・応答に出さない（NFR3.1） |
| アクセストークン | 利用者の手元だけ（サーバーは持たない） | 停止中は要求ごとの判定で拒否する（NFR1.1）。値を出さない（NFR3.1） |
| パスワード（平文・ハッシュ） | 要求の本文と内部DB の利用者の行 | 停止中のログインでも照合を1回行うが、値を出さない（NFR3.1） |
| メールアドレス | 内部DB の利用者の行・ログインの要求 | 停止中のログインの出来事とアプリのログに出さない（NFR3.1） |
| 停止しているという事実 | 内部DB | 3つの入口の応答に載せず、ほかの失敗と同じ応答にする（NFR2.1）。監査の LOGIN_FAILED・ACCOUNT_SUSPENDED にだけ残す |

## 性能と規模の前提

この単位の性能は、既存の入口の目標を保つことと、U3 の止める操作に含まれるまとめての無効化だけです。目標は緩めません（PM の Testing Posture）。測定の持ち主は Performance Validation の段で、この Intent の流れにはその段があります。

| ID | 要件 | 確かめ方と持ち主の段 | 出典 |
|---|---|---|---|
| NFR5.1 | ログインと更新の既存の目標（同時 10 件の要求で p95 1 秒以内）を変えない。停止の判定は、3つの入口がすでに読んでいる利用者の要約の suspended を見るだけで、内部DB の問い合わせを増やさない（アクセストークンの認証の読み取りも1回のまま） | `SqlStatementCounter` で、3つの入口の問い合わせの回数が変わらないことを単体・結合テストで確かめる（code-generation）。既存の k6 のログイン・更新の場面で目標を満たすことを確かめる（performance-validation） | NFR5、BR1.3、要点 1 |
| NFR5.2 | リフレッシュトークンのまとめての無効化には U1 だけの時間の目標を置かず、U3 の止める操作の目標（同時 10 件の要求で p95 1 秒以内）に含める。測るときは、対象の利用者に未無効の行 100 件と無効の行 1,000 件を持たせた悪い側の条件にする | 使い捨ての環境の k6 で、U3 の止める操作の場面をこの条件で測る（performance-validation。台本の用意と `k6 inspect` の確かめは build-and-test） | NFR5、ADR-007 の項目2、Q2 A、要点 3・4 |
| NFR5.3 | まとめての無効化は、利用者 ID の索引（`ix_refresh_tokens_user_id`）で引く1回の更新にし、未無効の行だけを書き換える（期限切れの行も含む）。0 件でも成功とする | 結合テストで、未無効の 100 件がすべて無効になり、無効の行・ほかの利用者の行が変わらないこと、0 件で成功することを、件数だけで確かめる。時間は比べない（code-generation） | NFR5、BR5.1、Q2 A |
| NFR5.4 | 想定の規模は前の Intent と同じく、利用者 最大 50 名・同時 10 件の要求を1台で処理する。利用者の行に列を1つ足すだけで行の数は増えない。監査の行は停止中のログイン1回に1行で、今のログインの失敗と同じ量。1人の未無効のリフレッシュトークンは、1日 10 回ログインしてログアウトしない利用者でも約 80 件の見込み。導き方は「1日のログインの回数 10 回 × 1件の行が残る日数 8 日（有効期限 24 時間＝1日 ＋ 期限の後に定期の削除まで残す期間 7 日）＝ 80 件」。未無効の行は期限切れの後も削除までは残り、まとめての無効化の対象になる（NFR5.3） | 見込みの根拠（`application.yaml` の `refresh-token-ttl` 24h と `refresh-token-cleanup.retention` 7d）を確かめた。NFR5.2 の悪い側の条件（未無効 100 件・無効 1,000 件）は、未無効の 80 件を上回り、無効の行も同じ期間に作りうる数より多い | NFR5、要点 4・13、前の Intent の NFR |
| NFR5.5 | 新しい指標と警報は足さない。停止中のログインと更新は、既存の HTTP の指標と p95 の警報（`ms-login-p95`・`ms-refresh-p95`）に含まれ、停止中のログインの理由は監査ログで追える | 既存の警報の決まり（`docker/monitoring/provisioning/alerting/mastersmith.yaml`）が変わらないことをレビューで確かめる（code-generation）。観測の確かめは observability-setup | NFR5、要点 18 |

## 脅威と扱い

| 脅威 | 扱い | 要件 |
|---|---|---|
| 止めた利用者が手元のトークンで使い続ける | 要求ごとの判定でアクセストークンを拒否し、リフレッシュトークンはまとめて無効にする | NFR1.1・NFR1.3・NFR5.3 |
| 停止を解いた後に古いリフレッシュトークンで戻る | 止めるときに無効にしたトークンを戻さない。止める確定と同時に作られて残ったトークンは、解いた後に使えうることを受け入れる（R1） | NFR1.3・NFR1.5 |
| 応答や応答時間から停止中の利用者を見分ける（列挙） | 同じ応答と同じ読み書きの回数 | NFR2.1・NFR2.2 |
| 停止中の管理者が管理の操作を続ける | 認証の入口で 401 にし、認可と業務に届かせない | NFR2.3 |
| 利用者が自分の停止の状態を書き換える | C1 の口だけが変えられ、利用者自身の API に経路が無い | NFR1.4 |
| 秘密・個人情報の漏えい（ログ・監査・トレース・応答） | 出さない決まりと、伏せる必要の無い型の口、漏えいのテスト | NFR3.1・NFR3.2 |
| SQL インジェクション | 名前つきの引数の問い合わせと、静的解析の関門 | NFR9.4 |

## 残る危険

| ID | 危険 | 受け入れる根拠 | 見直す時点 |
|---|---|---|---|
| R1 | 止める確定の前に同時に走った更新やログインの照合が作った新しいトークンが残りうる。停止を解くと、残ったリフレッシュトークンは使える（NFR1.5、BR5.5） | 停止している間は、残ったトークンも次のアクセストークンの認証と更新で拒否されるため害が無く、アクセストークンの有効期限は既定 5 分と短い。停止を解いた後に使えうる点は、ログインの経路ではパスワードを知る本人に限られ、本人は停止を解けば同じログインができるため、新しく得る力は無い。更新の経路では、止める直前に更新した手元の端末が、解いた後もそのまま使い続けられる。読み直しを足すと入口の読み書きの回数が変わり NFR2.2 と NFR5.1 に響く。機能設計の承認の場の決定（R-03）で受け入れた | 停止の判定を要求ごとの内部DB の読み取りから外す変更をするとき |
| R2 | 1つ前の版のイメージに戻している間は停止が効かない（NFR10.3） | 戻すのは問題が起きたときの短い間で、配備先は手元の PC だけ。機能設計の承認の場の決定（R-02）で受け入れ、戻す前に停止中の利用者を確かめる手順で補う | 配備先が決まったとき、または停止中の利用者が増えたとき |
| R3 | 停止中のログインとパスワードの誤りは、書き戻す値と出来事の理由だけが違い、応答時間のわずかな違いは測っていない（NFR2.2） | 応答時間の大半は bcrypt の照合（cost 12 で1回 約 278 ms）で、手元の k6 では同時 10 件のログインの p95 が成功 940 ms・失敗 926 ms と揺れの方が大きい。読み書きの回数がそろうことで足りるとした（Q1 A、前 U2 の NFR の「照合と SQL の回数を確かめる」決まり と同じ形） | 社外に公開する配備先が決まったとき |
