# Security Requirements — U5 利用者の管理の画面（u5-user-admin-ui）

U5 のセキュリティの要件です。U5 は画面の単位（種類 ui）で、サーバー側の認可と監査を持ちません。ここでは、画面で操作を隠すことをサーバーの判定の代わりにしないこと、403・401 の画面の側の扱い、個人に関する値（メールアドレス・氏名・検索の文字）を画面の外に出さないこと、失敗の文言、応答の項目の読み方、E2E の報告、静的検査と CSP を扱います。セキュリティ・コンプライアンス・品質の視点は、この段（inline）の中で重ねて書きました。答えは `nfr-requirements-questions.md` です（Q1: A、Q2: B、Consolidated Summary Confirmation: Looks correct）。

出典の略号:
- NFR・FR は要件 `aidlc/spaces/default/intents/260930-user-admin/inception/requirements-analysis/requirements.md` の ID
- D・W・4節〜10節は、この単位の `construction/u5-user-admin-ui/functional-design/functional-spec.md`
- 「部品 n節」は、同じフォルダの `frontend-components.md` の節
- 「要点 n」は、この段の `nfr-requirements-questions.md` の「設計の要点（案）」の番号
- C3・C4 は契約 `aidlc/spaces/default/intents/260930-user-admin/inception/contract-design/contract-summary.md` の C3・C4
- U3 の NFRx.y は `construction/u3-user-admin-api/nfr-requirements/`、U4 の NFRx.y は `construction/u4-admin-forbidden-ui/nfr-requirements/`
- PM は `aidlc/spaces/default/memory/project.md`、TM は `aidlc/spaces/default/memory/team.md`

枝番はこの単位の中で振ります。ほかの要件の置き場は `performance-requirements.md` の冒頭の表のとおりです。上流に当たる ID が無い静的検査と CSP の要件は、テストと検査の関門で確かめる NFR9 の枝番に寄せました（NFR9.1）。

## 前提

- 7つの管理の API の 401・403・200（204）の判定、停止中の管理者の拒否、最後の管理者の保護、一括代入の防止、管理の操作の監査は、サーバー側の U3（U3 の NFR1.1〜NFR1.5）と U1 が受け持ち、サーバー側のテストで確かめます。U5 の画面の扱いは、その代わりにしません（要件 NFR1、PM の Mandated、TM の Testing Posture）。
- 一覧の応答の行は、C3 の決めた11項目と `self` だけです。パスワードのハッシュ値・リフレッシュトークン・ロックの判定の内部の値は応答に含まれません（U3 の NFR3.2、PM の Forbidden）。
- トークンと利用者の情報はメモリだけに持ちます（既存の `frontend/src/features/auth/authSession.ts`）。アクセストークンの付与・401 での更新・`Accept-Language` の付与は既存の ApiClient が受け持ちます（機能設計 2節）。
- GitHub のリポジトリは公開です。テストのデータに実在の個人に関する値を使わず、メールアドレスは予約済みのドメイン `example.com` の下の値だけを使います（TM の Way of Working・Testing Posture）。

## 4. 脅威と扱い

| 脅威 | 扱い | 要件 |
|---|---|---|
| 画面で操作を押せない形にするだけで、管理者でない人や自分自身への操作が通る | サーバー側で要求ごとに判定し、U3 のサーバー側のテストで確かめる。画面の扱いはその代わりにしない | NFR1.1 |
| 印を外された管理者の画面に一覧・Modal が残り、続けて操作できる | 403 を U4 の共通の扱いに渡し、画面の部品を外す。操作してもサーバーが 403 を返す | NFR1.2 |
| 共用の PC で、ほかの利用者のメールアドレス・氏名・検索の文字がブラウザに残る | 保存・URL・履歴に載せず、画面の中の状態だけに持つ | NFR3.1 |
| コンソールの出力から個人に関する値が漏れる（画面の写し・共有・拡張機能） | 応答の値と検索の文字をコンソールに出さない | NFR3.1 |
| サーバーの説明文（`detail`）に内部の情報や利用者の値が混じり、画面に出る | 文言は `code` から選び、`detail`・`title` を使わない | NFR3.2 |
| 氏名に入れた記号による画面への差し込み（XSS） | React の文字として描き、HTML を直接埋め込まない。リンタで止める | NFR3.2・NFR9.1 |
| 応答に秘密の項目が誤って加わり、画面に出る | 決めた項目だけを型で読み、知らない項目を捨てる | NFR3.3 |
| E2E の報告（公開のリポジトリの外へ持ち出されうる）に資格情報・宛先・作った利用者の値が残る | 題・注記・添付・locator の名前に入れず、110・120 は trace を残さず、json・html・trace を報告の部品で探す。資格情報は環境変数で渡す | NFR3.4 |
| 検査の E2E が初期管理者や本物の利用者の状態を変える | 120 は `/api/admin/` の下の GET 以外を本物へ通さず（見本で返すか打ち切る）、110 は自分で作った利用者だけを変える | NFR3.4・NFR3.5 |
| CSP の緩み・外部の資源の読み込み | CSP を変えず、埋め込みのスクリプト・スタイルを足さない | NFR9.1 |
| 依存の脆弱性・悪意のあるパッケージ・インストール時のスクリプト | 新しい依存を足さず、`ignore-scripts=true` を足し、make-you-chic-ui は固定先の更新で取り込み lockfile を OSV-Scanner の対象のままにする | NFR9.2〜NFR9.4（`tech-stack-decisions.md`） |

## 5. コンプライアンスと品質の視点

- 個人に関する値の扱いは PM の Forbidden（メールアドレスをアプリのログとエラー応答に含めない、API の応答にハッシュ値・ロックの判定の内部の値を含めない）と Mandated（利用者の状態の判定はサーバー側）に沿っています。画面の側の守り（NFR3.1〜NFR3.3）はこれらをブラウザの側に広げたものです。
- 管理の操作の監査（操作した人・対象の利用者・結果）は U3 の持ち物で、画面は監査を書きません。画面が送る要求は C3 のとおりで、監査に要る値を画面から足しません。
- 認証・認可・監査に関わる失敗の場合のテスト（PM の Mandated）は、画面の側では 403・401・業務の失敗（404・409）・通信の失敗の扱いとして `UserAdminPage.test.tsx` に入れます（NFR1.2・NFR3.2）。
