# Infrastructure Design — 承認の場の決定

この段の承認の場での依頼者の決定を、承認の操作の理由とは別に記録する（`aidlc/spaces/default/memory/project.md` の学び「承認の場の決定は成果物の記録に残す」）。

## 1回目の承認の場（Request Changes、2026-10-02）

各単位の `cicd-pipeline.md` の終わりの「承認の場の決定（Request Changes、2026-10-02）」の節に記録した。要点は次のとおり。

| 単位 | 決定 |
|---|---|
| U1 | R-03（V9 の後方互換と戻しの練習を置かない）を条件つきで受け入れる。戻す前に停止中の利用者がいるかを確かめ、いれば扱いを依頼者に確かめる手順を deployment-pipeline で必ず決める |
| U3 | R-01（戻し方の誤り）を直す。戻し先の版は V9 の停止の列を知らず、戻すと停止中の利用者が3つの入口を通れることを明記した |
| U4 | R-01・R-02（403 の数え方の言い方）を直す |
| U5 | R-01（画面の時間は記録のみ・本番の判定は Unverified）、R-03（確かめの戻し忘れを `git diff`・`git status` で確かめる）、R-04（公開の側の確かめ方と CI の取得の失敗の手当て）を直す |
| U5 R-02（全単位に関わる） | B1・B2・B4 と、B5 の中で `playwright.config.ts` を直す前の E2E の実行の後は、json の報告から結果を記録してから `frontend/playwright-report/` と `frontend/test-results/` を消し、消したことと共有していないことをその Bolt のコード生成の記録に書く。いま手元に残っている報告は B1 の始めに消す |

## 2回目の承認の場（Approve、2026-10-02）

5単位の再レビューはすべて READY。再レビューの新しい Minor は、次の段へ申し送る。

| 単位 | 申し送り先 | 中身 |
|---|---|---|
| U1 | B1 のコード生成の計画 | 始めに残っている報告を消す手順と、E2E の後に記録してから消す手順。`LoginCommand`・`AuthenticatedUser`・`CurrentUserResponse` の `toString` のテストと、一覧の外の `auth.service`・`auth.web`・`RefreshTokenRevocationService` の下限の実測 |
| U1 | deployment-pipeline | 戻す前に停止中の利用者がいたときの対処（先に再開する・戻さない など）を質問に入れる |
| U2 | B2 のコード生成の計画 | 単位ごとの squash の条件を計画の前提にする。報告を消す前に json から記録する項目（件数と 060・090 の結果） |
| U3 | deployment-pipeline | 停止中の利用者の件数を確かめる場所（内部DB の複写を読み取りで開くか、画面・API か）。戻し先のイメージのコミットでの、監査の読み取りの経路が無いことの再確認。戻すと停止を判定しなくなることと `team.md` の「1つ前の版が動く後方互換」との差の明記 |
| U4 | B2 のコード生成の計画・Build and Test | `monitoring-design.md` 4節の参照（`cicd-pipeline.md` 4.4 は 5節と読み替える）。Build and Test で E2E を流した後の報告の片付けの持ち主と、記録してから消す順 |
| U5 | B5 のコード生成の計画 | 確かめの前の「コミットしておく」は、stash か差分だけの形にするか、コミットの前に依頼者の承認を得ると書く |
| U5 | B3 のコード生成の計画 | B3 で E2E を流すなら、記録の後に報告を消す同じ扱いにする |

前の承認の場から残っている申し送り（U1 R-01・R-02、U2 R-01〜R-03、U3 R-02〜R-04、U3 の書き手の3点、スモークテストの中身）は、各単位の `cicd-pipeline.md` の決定の節のとおり。
