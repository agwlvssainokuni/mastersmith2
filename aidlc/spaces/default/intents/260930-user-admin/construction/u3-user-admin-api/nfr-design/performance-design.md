# Performance Design — U3 利用者の管理の API（u3-user-admin-api）

U3 の性能の設計です。承認済みの `construction/u3-user-admin-api/nfr-requirements/performance-requirements.md`（NFR5.1〜NFR5.7）を満たす作りを決めます。索引の要否（NFR10.2）もこの文書で決めます。

出典の略号は `reliability-design.md` と同じ。試しのコードの記録は `reliability-design.md` 1節です。

## 1. 時間の見積もりと考え方

| API | 重い処理 | 内部DB の接続 | 目標 |
|---|---|---|---|
| 一覧 GET `/api/admin/users` | なし（3回の問い合わせ。検索ありは全体の走査） | 読み取りだけのトランザクションで1本 | 1,000 名・同時 10 件で p95 1 秒（NFR5.1） |
| 氏名と言語の変更 PUT `/{userId}/profile` | なし（DB の外の検証と2列の更新） | 1本 | 同時 10 件で p95 1 秒（NFR5.3） |
| 印を付ける・外す・止める | 管理者の行と対象の行の排他（同時の3つの操作は1つずつ通る） | 1本と、確定の後の監査で2本目 | 操作ごとに p95 1 秒（NFR5.4） |
| 止める（悪い側の条件） | 上に加えて、未無効 100 件のリフレッシュトークンのまとめての無効化 | 同上 | 同上（NFR5.5） |
| 停止を解く | 対象の行だけの排他 | 同上 | 同上 |
| 失敗回数を戻す | ロックの状態の行だけの排他と明示の更新1回 | 同上 | 同上 |
| 上限切れ（409 USER_ADMIN_BUSY） | 排他の待ち 3000 ミリ秒 | 待つ間は1本を持つ | 1 秒の目標の例外。ただし目標の負荷で1件でも出たら不合格（NFR5.6） |

- 7つの API はどれもパスワードの照合（bcrypt）をしない。1件の処理は内部DB の数回の読み書きで、ログイン（同時 10 件の p95 が 940 ms）よりずっと軽い見込み。
- 応答時間を左右するのは、5つの操作では排他の待ち（前の操作の確定を待つ時間）、一覧では検索ありの全体の走査。

## 2. 一覧の問い合わせ（NFR5.1・NFR5.2、BR1.1・BR1.6・BR1.7）

### 2.1 作り

| 順 | 問い合わせ | 読む列・形 |
|---|---|---|
| 1 | 条件に当たる全体の件数 | 検索なし: `count`。検索あり: `email ilike :p escape '\' or displayName ilike :p escape '\'` で数える |
| 2 | 20 件までの行（読み始めの位置が全体の件数以上なら読まない） | 利用者 ID・メールアドレス・氏名・言語・印・停止・登録した日時だけを投影で読む（パスワードのハッシュの列を読まない）。`order by createdAt, id`、`offset` と `limit 20` |
| 3 | 2 で読んだ利用者 ID のロックの判定の結果 | `auth.repository` で `subjectId in (:ids)` の1回。行が無い利用者は `LockView(false, null, false)` |

- 3つは同じ読み取りだけのトランザクションで読む（BR1.6）。行の数で問い合わせの回数が増えない。最後のページより後の page では 2・3 を読まない。
- 確かめ: 既存のテストの部品 `SqlStatementCounter` で、20 件のページと空のページの問い合わせの回数を結合テストで確かめる（NFR5.2）。全体が 0 件の一覧も確かめる（FS の 8.2 の申し送り）。

### 2.2 試しのコードの 1,000 名の結果（確かめ 5）

利用者 1,000 名（登録した日時は ID の順とずらし、同じ日時も作った）と、その 3 分の 1 にロックの状態の行を入れました。一覧の1回の要求に当たる3つの問い合わせ（全体の件数・20 件の行・その 20 名のロックの状態の `IN`）を、JDBC で 50 回の慣らしの後に 200 回流し、合計の時間を測りました。検索は `email ILIKE ? ESCAPE '\' OR display_name ILIKE ? ESCAPE '\'`。版と設定は `reliability-design.md` 1.1 のとおりです。

実行計画（索引なし）:

- 全体の件数（検索なし）: `UK_USERS_EMAIL_INDEX` を使う direct lookup
- 行（検索なし）: 表の全体の走査と並べ替え（`ORDER BY created_at, user_id`）
- 件数・行（検索あり）: 表の全体の走査
- ロックの状態: 主キーの索引で `IN` を引く

| 場面 | total | 行 | 索引なし 中央値・p95・最大（ミリ秒） | `created_at` の索引あり（比べるため） |
|---|---|---|---|---|
| a 検索なし 1ページ目 | 1000 | 20 | 0.03・0.10・0.36 | 0.01・0.01・0.01 |
| b 検索なし 最後のページ（50） | 1000 | 20 | 0.02・0.02・0.05 | 0.01・0.01・0.01 |
| c 多く当たる検索 1ページ目 | 1000 | 20 | 0.29・0.51・0.92 | 0.12・0.16・0.49 |
| c' 多く当たる検索 最後のページ（50） | 1000 | 20 | 0.28・0.35・0.59 | 0.28・0.63・1.12 |
| d 当たらない検索 | 0 | 0 | 0.11・0.14・5.81 | 0.08・0.10・0.41 |

d の最大 5.81 ミリ秒は 200 回のうち1回だけで、JVM の一時の止まりと見ます。この時間は DB の中の時間だけで、Hibernate・HTTP・同時 10 件の影響は含みません（それは performance-validation の NFR5.1 で測る）。

### 2.3 索引を足さない（Q2 A、NFR10.2）

- `users.created_at` の索引は足さない。索引が無くても、どの場面も DB の中の時間は p95 1 ミリ秒未満で、NFR5.1 の 1 秒に比べて十分に小さい。索引を足すと検索なしは速くなるが差は 0.1 ミリ秒未満で、検索ありには効かない（c' はむしろ遅くなった）。
- 足さないため、Flyway の移行（V10）と、1つ前の版のアプリが新しい移行の済んだ内部DB で動くことの確かめは加わらない。NFR10.2 は当てはまらない（`reliability-design.md` 9節）。
- 氏名を小文字にそろえる列も足さない。比べ方は `ilike`（Q3 A、`security-design.md` 6.2）で、前後に `%` が付く部分一致のため、どの比べ方でも全体の走査になる。
- performance-validation の NFR5.1 で目標に届かなければ、目標を緩めず、索引を足す直しを依頼者に諮る（NFR 要件の P-D2）。

## 3. 5つの操作（NFR5.4〜NFR5.6）

- 排他の待ちの上限は既存と同じ 3000 ミリ秒のまま（Hibernate は `for update wait 3` として出す）。試しのコードで、上限切れまで待った時間は 3004〜3171 ミリ秒だった（`reliability-design.md` 1.6）。
- 印を付ける・外す・止めるは管理者の行の全体と対象の行を排他するため、同時に流すと1つずつ通る。1件の排他を持つ時間は、判定・書き換え・確定までの数回の問い合わせ（止めるはまとめての無効化を含む）で、試しのコードの止める操作のまとめての無効化（3 行）は 13 ミリ秒だった。目標の負荷（同時 10 件を5つの操作に分ける）で待ちが 3 秒に届く見込みは無いが、BUSY が1件でも出たら不合格とする（NFR5.6）。
- 止める操作のまとめての無効化は U1 の口（`refresh_tokens` の利用者 ID の索引で引く1回の更新）を使う。悪い側の条件（未無効 100 件・無効 1,000 件、NFR5.5）は performance-validation で測る。
- 失敗回数を戻すは利用者の行を排他しないため、ほかの3つの操作とは待ち合わない。

## 4. 氏名と言語の変更（NFR5.3、BR5.2）

- 検証は DB を使わずに行い、通ったときだけ2列（氏名・言語）の更新1回を行う。行の排他はしない。更新した行が 0 なら 404。

## 5. 接続の持ち方

- 5つの操作の1本目は、排他を待つ間（最大 3000 ミリ秒）も持ち続ける。確定の後の監査の記録で2本目を借りる。接続の数の見積もりは `scalability-design.md` 2節、確かめは `reliability-design.md` 8節。

## 6. キャッシュを置かない

- 管理者の判定・停止の判定・有効な管理者の数え・ロックの判定は、要求ごとに内部DB の今の値で行う（NFR1.2、BR3.1）。キャッシュを置くと古い印で判定しうるため置かない。1,000 名でも DB の中の時間は小さく（2.2）、キャッシュの得が無い。

## 7. 測り方（performance-validation へ渡すこと、NFR5.7）

| 場面 | 条件 | 判定 |
|---|---|---|
| 一覧 a〜d | 試験用の利用者 1,000 名を SQL で入れる。同時 10 件を場面ごとに 100 回以上 | 場面ごとの `http_req_duration` の p95 1000 ms 以内、`checks`（200 と total の値）の率 1 |
| 氏名と言語の変更 | 各 VU が自分の対象の利用者を使う。100 回以上 | p95 と `checks` の率 1 |
| 5つの操作 | 5つを合わせて同時 10 件、操作ごとに 100 回以上。組で状態を戻しながらくり返す。操作する管理者と初期管理者は対象にしない、対象は VU ごとに分ける | 操作ごとの p95、`checks`（204）の率 1。409（BUSY・NO_CHANGE）と 5xx は 0 件 |
| 止める（悪い側） | 対象ごとに未無効 100 件・無効 1,000 件のトークンの行を入れ直す | 5つの操作と同じ |
| 接続プール（NFR6.2・NFR6.3） | `reliability-design.md` 8節 | 同節 |

- 台本は既存の `perf/k6/scenarios.js` に場面を足し、手順を `perf/README.md` に書く。build-and-test では `k6 inspect`（`--include-system-env-vars` を付ける）で読み込みと場面の名前を確かめる。
- 正とする値は k6 の値。サーバー側の `http.server.requests` の p95 は参考として並べる。長い試験は `caffeinate -i` で台本全体を包む。試験の前に、この表と台本の手順を1つずつ突き合わせる（PM の Testing Posture）。
- NFR 要件のレビューの R-07・R-08（上限 10 の場面の条件と BUSY の件数の扱い）は、performance-validation の台本で扱う。
