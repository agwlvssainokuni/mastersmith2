# Scalability Design — U3 利用者の管理の API（u3-user-admin-api）

U3 の拡張性の設計です。承認済みの `construction/u3-user-admin-api/nfr-requirements/scalability-requirements.md`（NFR5.8・NFR6.1）を満たす作りを決めます。配備先は当面、開発者の PC 上のコンテナ1台（colima の VM、コンテナの上限 CPU 4・メモリ 2g）で、内部DB は組み込みの H2 です。クラウドの基盤は作りません（`aidlc/spaces/default/memory/project.md` の Deployment）。

出典の略号は `reliability-design.md` と同じ。

## 1. 規模と伸ばし方（NFR5.8）

| 項目 | 設計 |
|---|---|
| 想定の規模 | 利用者 最大 50 名、同時 10 件の要求を1台で処理する |
| 悪い側の規模 | 一覧は 1,000 名で目標を満たす。試しのコードで DB の中の時間は p95 1 ミリ秒未満（`performance-design.md` 2.2） |
| 伸ばし方 | 縦（コンテナの CPU・メモリ）だけ。アプリのメモリに状態を持たない（排他は DB の行、判定は要求ごとの読み取り）ため、U3 が複数台の妨げを足すことは無い。複数台にする妨げは組み込みの H2 で、U3 の外の制約 |
| 新しく持つ状態 | 無い。キャッシュ・アプリのメモリの集合・定期の処理を持たない |

## 2. 接続の数（NFR6.1）

| API・結果 | 1件の接続 | 理由 |
|---|---|---|
| 一覧・氏名と言語の変更 | 1本 | 監査を記録しない |
| 5つの操作の成功・業務の拒否・確かめ直しの 403 | 2本（確定の後の監査で2本目） | 既存の `AuditEventListener`（AFTER_COMMIT）と `AuditEventRecorder`（`REQUIRES_NEW`） |
| 409 USER_ADMIN_BUSY・入力の誤り・認可の入口の 401 と 403 | 1本以下 | 監査を記録しない（認可の入口の 403 は既存のアクセスの拒否の記録） |

- 同時 10 件がすべて5つの操作でも最大 20 本で、接続プールの上限（既定 30、`MASTERSMITH_DB_MAXIMUM_POOL_SIZE`）に収まる。
- 排他を待つ間（最大 3000 ミリ秒）は1本目を持ち続けるため、5つの操作が重なると1本を持つ時間が延びる。印を付ける・外す・止めるは1つずつ通るため、同時に流すと後の要求が前の確定を待つ間も1本ずつ持つ。
- 見積もりそのもの（1件に2本）は上限を 10 に下げた場面で、上限 30 の余裕は同時 10 件の場面で確かめる（`reliability-design.md` 8節）。
- 管理の操作 10 件とログインの失敗 10 件が重なると見積もりは最大 40 本で上限 30 を超えうる。これは前の Intent で既知の制約として記録した危険と同じもので、想定の規模を超えるため、この単位では確かめない（NFR 要件の「同時の数の扱い」）。

## 3. 排他と直列化の伸び方

| 操作 | 排他する行 | 同時に流したとき |
|---|---|---|
| 印を付ける・外す・止める | 管理者の印を持つ行の全体と対象の行（利用者 ID の昇順） | 互いに1つずつ通る。管理者の数が増えると排他する行が増えるが、想定は少数（数名）で、行の数に比べて問い合わせの時間は小さい |
| 停止を解く | 対象の行だけ | 対象が違えば待ち合わない。印の操作と同じ対象なら待つ |
| 失敗回数を戻す | 対象のロックの状態の行だけ | 同じ利用者のログインの判定とだけ待ち合う |
| 氏名と言語の変更・一覧 | 排他しない | 待ち合わない |

- 印の操作が1つずつ通るのは最後の有効な管理者を守るための意図した形で、管理の操作はまれのため、規模の妨げにならない見込み。目標の負荷（同時 10 件）で BUSY が出ないことを performance-validation で確かめる（NFR5.6）。

## 4. データの増え方

| データ | U3 による変化 | 扱い |
|---|---|---|
| `users` の行 | 作らない。列も索引も足さない（Q2 A） | 変更なし |
| `login_attempt_states` の行 | 既存の行を書き換えるだけで作らない | 変更なし |
| `refresh_tokens` の行 | 止める操作が未無効の行を無効にするだけ | 変更なし（消すのは既存の定期の削除） |
| `audit_events` の行 | 5つの操作1回に1行（成功・業務の拒否・確かめ直しの 403） | 管理の操作はまれで、ログインの監査に比べて小さい。保存期間と削除は既存のまま |

## 5. 複数台・別の DB へ移すとき（今は作らない）

| 論点 | 今の前提 | 移すときに確かめ直すこと |
|---|---|---|
| 最後の有効な管理者の保護 | H2 の `FOR UPDATE` は待った後に最新の値で行を選び直し、排他の後の別の問い合わせは待つ間に確定した変更を数える（`reliability-design.md` 1.3） | 替える DB で同じ振る舞いになるか。分離レベルと `FOR UPDATE` の評価のし直し方は DB ごとに違う |
| 行を取る順 | H2 は主キーの走査の順に1行ずつ排他する（同 1.4） | 替える DB の実行計画と排他の順 |
| 排他の待ちの上限 | `jakarta.persistence.lock.timeout` を Hibernate が `for update wait 3` にする | 替える DB で上限の効き方と上限切れの例外の型 |
| 上限切れの例外の文 | H2 の例外の連なりに行の値が入る（`security-design.md` 7節） | 替える DB の例外の文に値が入るか。U3 は例外の文を出さない作りのため、出し方は変わらない |
| 検索の比べ方 | H2 の `ILIKE`（`security-design.md` 6.2） | 替える DB に `ILIKE` があるか。無ければ小文字の比べ方と既知の差を決め直す |

## 6. 見直す時点

| 時点 | 見直すこと |
|---|---|
| performance-validation で NFR5.1 に届かなかったとき | `users (created_at, user_id)` の索引を足す直しを依頼者に諮る（`performance-design.md` 2.3） |
| 管理者の数が数十名を超えるとき | 印の操作で排他する行の数と、BUSY の出やすさ |
| 配備先が決まったとき（複数台・共有の DB） | 5節の表 |
