# Reliability Requirements — U3 利用者の管理の API（u3-user-admin-api）

U3 の信頼性の要件です。要件定義の NFR4（同時の操作）・NFR6（接続の使い方）・NFR9（テスト）を、5つの操作の排他と最後の有効な管理者の保護、確定の後の監査の記録に当てます。当面の配備先は開発者の PC 上のコンテナ1台で、可用性の数値の目標（SLO）は配備先が決まってから決めます（`aidlc/spaces/default/memory/team.md` の Deployment、`project.md` の Deployment）。出典の略号は `performance-requirements.md` と同じ。

## 要件

| ID | 要件 | 確かめ方と持ち主の段 | 出典 |
|---|---|---|---|
| NFR4.1 | 最後の有効な管理者の保護: 印を外す・止める操作で、対象を除くと有効な管理者（印あり・停止なし。ロック中も数える）が 0 人になるときは 409 USER_ADMIN_LAST_ADMIN で拒否し、状態を変えない。2人の管理者が同時に互いの印を外す・止める・一方が外し他方が止めるときも、有効な管理者が 0 人にならない（一方が成功、他方が LAST_ACTIVE_ADMIN で拒否） | 業務処理の層を直接呼ぶテスト（API の1件ずつでは起きない場合: 操作した人がロック中・停止中の管理者）と、待ち合わせの口で作る同時の重なりの結合テスト（AC2.1.6・AC2.1.12・AC3.1.5 の形）で、拒否の後に状態と有効な管理者の数を確かめる。重なりはスレッドの数に頼らず待ち合わせで確実に作る（code-generation） | NFR4、FR4、BR3.1・BR3.2・BR3.6、FS の 2.9・2.10、PM の Forbidden、TM の Testing Posture（最後の管理者の保護） |
| NFR4.2 | 失敗回数を戻す操作とログインの判定が同時に重なっても、結果は2つを順に行ったどちらかの結果に一致し、5xx にならない（どちらもロックの状態の行を排他して読む） | 待ち合わせの口（ロックの状態の行を排他した直後、ログインの判定と戻す操作の両方）で、どちらが先に排他を取る場合も作り、失敗回数とロックの状態を確かめる結合テスト（AC4.1.5）。時刻は注入した時計で動かし、`sleep` と実時刻に頼らない（code-generation） | NFR4、FR5.4、BR3.4・BR3.6、FS の 2.9、TM の Testing Posture（ロックの解除） |
| NFR4.3 | 行き詰まりを作らない: どの操作も利用者の行とロックの状態の行を同時に排他せず、管理者の行は利用者 ID の小さい順に取る。排他の待ちが上限（3000 ミリ秒）を超えたときは、業務処理がトランザクションに巻き戻しの印を明示的に付けて巻き戻し、409 USER_ADMIN_BUSY を返す。巻き戻しの印が付いたまま確定を試みて 500 にならない。BUSY は状態を変えず、監査に残さない | 排他を持ち続けて上限切れを起こす結合テストで、409 と状態が変わらないこと、500（UnexpectedRollbackException）にならないこと、監査の行が増えないことを確かめる（code-generation）。H2 と Hibernate の上での巻き戻しの作りは NFR 設計で確かめる | NFR4、BR3.1・BR3.4・BR3.5、FS の 2.2 と 8.2、機能設計の承認の場の決定 R-02、要点 15 |
| NFR4.4 | 排他の待ちの上限は既存と同じ 3000 ミリ秒のまま変えない。テストの待ち合わせの口で止める時間は、この上限より短くする（止めている間に相手が BUSY にならないように） | 設定の値のレビューと、待ち合わせのテストの止める時間の上限のレビュー（code-generation） | BR3.1・BR3.6、機能設計の承認の場の決定 R-03 と申し送り、NFR5.6 |
| NFR4.5 | BR3.1 の根拠（排他した管理者の行の集合が古くても保護が成り立つこと、待った後の読み取りが確定済みの印の変更を数えに含めるか）が H2 と Hibernate の上で成り立つかを確かめる。成り立たないときは、BR3.1 の切り替え先（固定の1行を排他して、印・停止を変える操作を1つずつ通す）に移る | NFR 設計で確かめ方を決め、試しのコードか結合テストで確かめる（nfr-design・code-generation）。切り替えたときは NFR5.4 の測り方は変えない | 機能設計の承認の場の決定 R-02 と申し送り、FS の 8.2 節 |
| NFR6.2 | 5つの操作は、成功も業務の拒否も確定の後の監査の記録で2本目の接続を借りる経路になる（`AuditEventListener` の AFTER_COMMIT と `AuditEventRecorder` の `REQUIRES_NEW`）。管理の操作（NFR5.4 の場面）と一覧を合わせて同時 10 件で流しても接続プールが尽きず、監査の記録が欠けない | performance-validation の k6 で、使い捨てのアプリにだけ `MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE=health,metrics` を渡し、`/actuator/metrics` の hikaricp の値で、接続を借りる待ちの時間切れの累計が 0 であることを確かめ、借りるまでの待ちの最大を記録する。数秒ごとの使用中の数では判断しない。あわせて 500 が 0 件であることと、流した5つの操作の件数と監査の行（5つの種類の SUCCESS）の件数が一致することを、アプリを止めて内部DB を読み取りで開いて確かめてから片付ける（配備したアプリの公開の範囲は変えない） | NFR6、Q3 A、PM の Corrections・Testing Posture（hikaricp の学び、片付けの学び）、要点 14、BR6.3 |
| NFR9.4 | 監査の書き込みが失敗しても、5つの操作の応答（成功の 204、業務の拒否の 404・409、確かめ直しの 403）と判定の結果を変えない。失敗はアプリのログに ERROR で残し、メールアドレス・氏名を含めない | 既存の `AuditWriteFailureIT` と同じ形の結合テストで、成功と拒否の両方を確かめる（code-generation） | NFR9、BR6.3、既存の AuditLog の決まり、要点 13 |
| NFR9.5 | 5つの操作と氏名と言語の変更は、1つのトランザクションで確定するか、何も変えないかのどちらか。止める操作は、停止の状態とリフレッシュトークンのまとめての無効化を同じトランザクションで行い、巻き戻れば両方が戻る。業務の拒否は書き込みをせずに確定させ、失敗の監査だけを残す。内部DB の障害などの想定外の誤りは既存の 500 の扱い（内部の例外のメッセージを載せない。確定しないため監査も残らない） | 結合テスト（止める操作の途中で失敗させて停止とトークンの両方が戻ること、業務の拒否で状態が変わらず失敗の監査が1行残ること）（code-generation） | NFR9、BR2.4・BR4.3・BR4.6、FS の 4節、U1 NFR の NFR11.2、要点 16 |

## 障害のときのふるまい

| 障害 | ふるまい | 要件 |
|---|---|---|
| 排他の待ちの上限切れ（3000 ミリ秒） | 409 USER_ADMIN_BUSY、巻き戻し、監査なし、アプリのログに WARN で code | NFR4.3 |
| 同時の操作で有効な管理者が 0 人になりかける | 後の操作を 409 USER_ADMIN_LAST_ADMIN で拒否、状態は変わらない | NFR4.1 |
| 排他を待つ間に操作した人の印が外れた・止められた | 403 ACCESS_DENIED、状態は変わらない、監査に NOT_ADMIN | `security-requirements.md` の NFR1.4 |
| 監査の書き込みの失敗 | 元の応答のまま、アプリのログに ERROR、既存の警報「監査の書き込みの失敗」（`ms-audit-fail`） | NFR9.4 |
| 接続プールの待ちの時間切れ（5 秒） | 既存の 500 の扱い。確定の後の監査の記録で起きると監査が欠けうる（既知の制約） | NFR6.2、`scalability-requirements.md` の NFR6.1 |
| 内部DB の障害 | 既存の 500 の扱い、トランザクションは巻き戻る | NFR9.5 |

## 確かめる段の一覧

| 論点 | 持ち主の段 |
|---|---|

| 接続プールの負荷の試験と監査の件数の一致（NFR6.2） | performance-validation（台本の用意は build-and-test） |
