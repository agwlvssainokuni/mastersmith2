# Scalability Requirements — U3 利用者の管理の API（u3-user-admin-api）

U3 の拡張性の要件です。アプリは当面1台で、内部DB は組み込みの H2 です（要件の4節の制約）。想定の規模と接続の数の見積もりを、要件定義の NFR5（応答時間）と NFR6（接続の使い方）の枝番に置きます（枝番の寄せ方は `performance-requirements.md` の冒頭）。出典の略号は `performance-requirements.md` と同じ。

## 要件

| ID | 要件 | 確かめ方と持ち主の段 | 出典 |
|---|---|---|---|
| NFR5.8 | 想定の規模（利用者 最大 50 名、同時 10 件の要求）を1台で処理する。一覧は想定の 20 倍の利用者 1,000 名でも目標（NFR5.1）を満たし、ほかの API は同時 10 件で目標（NFR5.3〜NFR5.5）を満たす。管理者は少数で、5つの操作の頻度は低い見込み | performance-validation の負荷の試験（NFR5.1〜NFR5.5） | NFR5、Q1 B、要点 12、前 U2 の NFR6.7 |
| NFR6.1 | 内部DB の接続の数の見積もり: 一覧と氏名と言語の変更は要求1件に1本。5つの操作は、成功・業務の拒否・確かめ直しの 403 のどれも確定の後の監査の記録で2本目を借りる（1件に2本）。409 USER_ADMIN_BUSY・入力の誤り・認可の入口の 401 と 403 は監査を記録しないため1本以下。同時 10 件がすべて5つの操作でも最大 20 本で、接続プールの上限（既定 30、`MASTERSMITH_DB_MAXIMUM_POOL_SIZE`）に収まる。排他を待つ間（最大 3000 ミリ秒）は1本目を持ち続けるため、5つの操作が重なると1本を持つ時間が延びる | 見積もりの記録（本書）。実際に尽きないことは `reliability-requirements.md` の NFR6.2 の負荷の試験で確かめる（見積もりだけで済ませない、PM の Corrections） | NFR6、BR3.1・BR6.3、要点 14、Q3 A |

## 同時の数の扱い

- 想定の規模は「全体で同時 10 件」で、NFR6.2 の確かめもこの範囲（管理の操作と一覧を合わせて同時 10 件、Q3 A）で行う。
- 管理の操作 10 件にログインの失敗 10 件が重なる場合は、ログインの失敗も確定の後に2本目を借りるため、見積もりは最大 40 本になり上限 30 を超えうる。これは前の Intent で上限を 30 に上げたときに既知の制約として記録した危険（PM の Decided、README の「監査ログ（U4）」）と同じもので、想定の規模を超える負荷のため、この単位では確かめない（Q3 で B を選ばなかった）。起きたときは既存の警報「コネクションプールの待ち」（`ms-pool-pending`）と 500 の増加で気づく。

## データの増え方

| データ | 増え方 | 見積もり | 扱い |
|---|---|---|---|
| 利用者の行 | U3 は行を作らない（作るのは登録の完了と初期管理者）。列も足さない（停止の列は U1 の V9） | 想定 最大 50 行。試験では 1,000 行 | 変更なし |
| ロックの状態の行 | 失敗回数を戻す操作は既存の行を書き換えるだけで、行を作らない（BR4.5） | 増えない | 変更なし |
| リフレッシュトークンの行 | 止める操作はその利用者の未無効の行を無効にするだけで、行は増えない（消すのは既存の定期の削除） | 1人あたり約 80 件の見込み（U1 NFR の NFR5.4）。試験の悪い側は未無効 100 件・無効 1,000 件（NFR5.5） | 変更なし |
| 監査の行 | 5つの操作1回に1行（成功・業務の拒否・確かめ直しの 403）。一覧・氏名と言語の変更・BUSY・入力の誤りでは増えない（BR6.4） | 管理の操作はまれで、ログインの監査に比べて小さい。負荷の試験の使い捨ての環境では流した回数だけ増えるが、終わったら消す | 監査の保存期間と削除は既存のまま（PM の Decided、監査の共通化は後続の Intent） |

## 検索と並びの伸び方

一覧の検索は、小文字にそろえた部分一致のため、全体を走査します（BR1.5）。全体の件数を数える問い合わせも同じ条件で走査します。行の数に比例して遅くなるため、想定の 20 倍（1,000 名）で目標を満たすかを測ります（NFR5.1）。索引（`users.created_at` の索引など）を作るかは NFR 設計で決めます（`performance-requirements.md` の「索引の要否との関係」）。

## 複数台で動かす場合

当面は1台で、内部DB は組み込みの H2 のため複数台では動かしません。複数台にするときは内部DB を共有の DB に替える必要があり、その時点で U3 に次の影響があります（今は作りません）。

- 最後の有効な管理者の保護は、DB の行の排他（BR3.1）で守るため、アプリのメモリに状態を持たず、共有の DB の上でもそのまま成り立つ見込み。ただし排他の待ちの上限（`jakarta.persistence.lock.timeout`）の効き方と、待った後の読み取りが確定済みの変更を含むかは DB ごとに違うため、替える DB で確かめ直す（NFR 設計の申し送りと同じ論点）。
- 一覧の検索の小文字化と部分一致の SQL は DB ごとに違いうるため、替えるときに確かめ直す。
