# Security Requirements — U3 利用者の管理の API（u3-user-admin-api）

U3 のセキュリティの要件です。要件定義の NFR1（認証の一貫性）・NFR3（個人情報と秘密情報）・NFR8（多言語）・NFR9（テスト）を、この単位の7つの API（契約 C3）、UserAccount と Authentication の口（契約 C8・C1）、管理の操作の監査（契約 C6）に当てます。セキュリティ担当・コンプライアンス担当・品質担当の視点は、この文書と `tech-stack-decisions.md` に重ねて書きました。

出典の略号は `performance-requirements.md` と同じ。枝番の寄せ方も同じ文書の冒頭のとおり。

## 守るもの

| 守るもの | 置き場 | 守り方 |
|---|---|---|
| 管理者の印（`users.admin_flag`） | 内部DB の利用者の行 | 変えられるのは U3 の印を付ける・外すだけ（C8 の setAdmin を呼ぶのは `useradmin` だけ）。最後の有効な管理者を無くす操作を受け付けない（`reliability-requirements.md` の NFR4.1）。利用者自身の API から変える経路を持たない（NFR1.5） |
| 利用停止の状態（`users.suspended`） | 内部DB の利用者の行（U1 の V9） | 変えられるのは U3 の止める・停止を解くだけ（C1 の setSuspended）。止めるときはリフレッシュトークンをまとめて無効にする（BR4.3） |
| ログインの失敗回数と解除の予定の時刻 | 内部DB のロックの状態の行 | 応答に回数そのものを載せず、ロック中か・解除の予定の時刻・戻せるかの3つだけを返す（NFR3.2）。戻すのは U3 の失敗回数を戻すだけ |
| パスワードのハッシュ値・招待のトークンのハッシュ値・リフレッシュトークン | 内部DB | 一覧で読まない・返さない。監査とログに出さない（NFR3.1・NFR3.2） |
| メールアドレス・氏名・検索の文字 | 内部DB の利用者の行、要求の q と本文 | controller から repository の口まで伏せ字の型のまま渡し、アプリのログ・トレースの属性・監査ログ・エラー応答に出さない（NFR3.1）。一覧の応答では管理者にだけ返す |
| 監査の記録 | 内部DB の `audit_events` | 5つの操作の成功と拒否を、操作した人・対象・結果・理由つきで残す（`observability-requirements.md` の NFR9.3） |

## 要件

| ID | 要件 | 確かめ方と持ち主の段 | 出典 |
|---|---|---|---|
| NFR1.1 | 7つの API のすべてで、管理者かどうかをサーバー側で判定する。未認証は 401 AUTHENTICATION_REQUIRED、管理者でない利用者は 403 ACCESS_DENIED、管理者は 200（一覧）・204（変更と5つの操作）を返す。401・403 では業務処理を呼ばず、何も読み書きしない。画面で管理のメニューや操作を隠すことを、この判定の代わりにしない | 7つの API のそれぞれで、未認証・管理者でない利用者・管理者の3つの場合をサーバー側の結合テストで確かめる（code-generation） | NFR1、BR7.1、PM の Mandated、TM の Testing Posture（管理の API の認可）、要点 6 |
| NFR1.2 | 管理者の印を付けた・外した確定の後の次の要求から、その利用者の管理の API の 403 と 200 がサーバー側で切り替わる（要求ごとに内部DB の今の値で判定し、トークンや画面が持つ古い印に頼らない）。印を付けても外してもトークンには触れない（BR4.1・BR4.2）。印を外す前に出したアクセストークンでも、外した後の管理の API は 403 になる | 印を付けた直後・外した直後の次の要求で、管理の API が 200・403 に切り替わることを結合テストで確かめる。自分の印を外す操作が 409 USER_ADMIN_SELF_OPERATION で拒否されることも、決めた側の動作として確かめる（code-generation） | NFR1、TM の Testing Posture（管理者の印の変更）、BR2.2・BR4.1・BR4.2 |
| NFR1.3 | 停止中の管理者は、7つの API のどれも呼べない。アクセストークンの認証の入口（U1）で 401 AUTHENTICATION_REQUIRED になり、認可と業務処理に届かず、管理の操作の監査もアクセスの拒否の監査も残らない | 停止中の管理者が7つの API を呼んで 401 になり、状態と監査が変わらないことを結合テストで確かめる（code-generation） | NFR1、U1 NFR の NFR2.3、TM の Testing Posture（管理の API の認可）、要点 6 |
| NFR1.4 | 5つの操作は、判定の後・書き換えの前に操作した人が今も有効な管理者か（いて・印を持ち・停止していない）を確かめ直し、外れていれば状態を変えずに 403 ACCESS_DENIED を返し、その操作の失敗（理由 NOT_ADMIN）として監査に残す | 待ち合わせで、排他を待つ間に操作した人の印が外れた・止められた場合を作り、403 と監査の NOT_ADMIN と状態が変わらないことを結合テストで確かめる（code-generation） | NFR1、BR2.5・BR2.6、FS の 9節の D4・D5、要点 6 |
| NFR1.5 | 管理の API の外から、要求の本文の値を変えて、自分やほかの利用者の管理者の印・停止の状態・失敗回数を変えられない（一括代入の防止）。氏名と言語の変更の本文は displayName と language だけを読み、知らない項目（admin・suspended・失敗回数など）は無視する。`/api/me`・`/api/me/preferences` の本文に同じ項目を入れても変わらない | 氏名と言語の変更、`/api/me`、`/api/me/preferences` の本文に印・停止・失敗回数の項目を足して送り、その値が変わらないことを結合テストで確かめる（code-generation） | NFR1、BR5.4・BR7.2、TM の Testing Posture（要求の改ざん）、要点 7 |
| NFR3.1 | 検索の文字・メールアドレス・氏名は、controller の引数から repository の口まで、すべての経路で伏せ字の型（SearchText・検索のパターンの RedactedText・ProfileCommand・ProfileUpdate・UserAdminSummary）のまま渡し、文字列にするのは伏せ字の型の record の中と Spring Data の問い合わせの SpEL の中だけにする。アプリのログ・トレースの属性・監査ログ・エラー応答に、これらの値を出さない | TRACE のログを有効にした `UserAdminSecretLeakIT` で、7つの API（一覧は q を付けた要求を含む）を呼び、アプリのログ・監査の行・応答にメールアドレス・氏名・検索の文字が出ないことを確かめる（既存の `*SecretLeakIT` と同じ形）。どの層の引数にも String で渡していないことをレビューで確かめる（code-generation） | NFR3、BR1.3・BR1.5・BR5.2・BR7.4、FS の 9節の D13、PM の Forbidden・Corrections（TraceAspect の学び）、要点 8 |
| NFR3.2 | API の応答（成功の応答を含む）に、パスワードのハッシュ値・招待のトークンのハッシュ値・リフレッシュトークン・ログインの失敗回数そのもの・ロックの判定の内部の値・ダミーの行を含めない。一覧の行は決めた11項目と self だけを返す | 一覧の応答の項目を結合テストで確かめる。`UserAdminSecretLeakIT` で、応答と監査の行にハッシュ値・トークンの値・失敗回数が無いことを確かめる（code-generation） | NFR3、BR1.7・BR7.5、PM の Forbidden、TM の Testing Posture（利用者の管理の漏えい）、要点 8 |
| NFR3.3 | エラー応答は、項目の名前と理由と code だけを返し、入れた値（検索の文字・氏名）、内部の例外のメッセージ、スタックトレースを載せない。q が長すぎる誤りは q・TOO_LONG だけを返す。409 USER_ADMIN_BUSY は、どの排他で待ったかや対象の利用者の値を載せない | 結合テストで、400・404・409 の応答の本文を確かめる（code-generation） | NFR3、BR1.4・BR3.5、TM の Code Style（Problem Details）、要点 8 |
| NFR8.1 | 足す code（404 USER_NOT_FOUND、409 USER_ADMIN_SELF_OPERATION・USER_ADMIN_TARGET_SUSPENDED・USER_ADMIN_NO_CHANGE・USER_ADMIN_LAST_ADMIN・USER_ADMIN_BUSY）に ja・en の説明文を付け、要求の Accept-Language で選ぶ（それ以外は既定の ja）。1つの code に1つの状態コードを固定し、`useradmin.domain` の UserAdminProblemTypes に置く。共通の code（VALIDATION_FAILED・AUTHENTICATION_REQUIRED・ACCESS_DENIED）は既存の定義を使い回し、重ねて定義しない | 結合テストで ja・en の説明文を確かめる。code と状態コードの重複は既存の起動時の検査（ProblemTypeCatalog）で確かめる（code-generation） | NFR8、BR2.3、TM の Code Style、FS の 3節 |
| NFR9.1 | 入力の上限と問い合わせの安全: q は前後の空白を除いて 254 コードポイントまで、page は共通のページ送りの検証（U2 の Paging）、userId は整数として結び付け読めなければ 400、要求の本文は既存の上限（1MB）のまま。検索の文字は名前つきの引数だけで問い合わせに渡し、`%`・`_`・`\` をエスケープして文字どおりに扱う。文字列をつなげて問い合わせを作らない | 境界のテスト（q の 254・255 コードポイント、空白だけの q、page の 0・数でない・桁あふれ）と、`%`・`_`・`\` を含む検索が文字どおりに一致することの結合テスト（code-generation） | NFR9、BR1.1・BR1.4・BR1.5・BR2.7、TM の Code Style、要点 9 |
| NFR9.2 | 既存の静的解析の関門（SpotBugs ＋ FindSecBugs の priority 1、`SQL_`・`PREDICTABLE_RANDOM`・`SMTP_HEADER_INJECTION` は priority にかかわらず）と、秘密情報の検出・依存関係の脆弱性検査を、除外を足さずにそのまま通す | `./gradlew verify`（code-generation・build-and-test） | NFR9、TM の Code Style、PM の Mandated、要点 10 |

## 脅威と扱い

| 脅威 | 扱い | 要件 |
|---|---|---|
| 管理者でない利用者が管理の API を呼ぶ | サーバー側の認可で 401・403。画面で隠すことに頼らない | NFR1.1 |
| 印を外された・止められた管理者が、古いトークンや開いたままの画面で操作を続ける | 要求ごとに今の印と停止の状態で判定し、操作の中でも確かめ直す | NFR1.2・NFR1.3・NFR1.4 |
| 本文の改ざんで自分を管理者にする・停止を解く | 知らない項目を無視し、書き換えの口を `useradmin` の操作だけに置く | NFR1.5、`tech-stack-decisions.md` の NFR11.1 |
| 最後の有効な管理者を無くし、誰も管理できなくする（同時の操作を含む） | 管理者の行を ID 順に排他して数え、0 人になる操作を拒否する | `reliability-requirements.md` の NFR4.1、PM の Forbidden |
| 個人に関する値・秘密の漏えい（ログ・トレース・監査・応答） | 伏せ字の型で受け渡し、出さない項目の決まりと漏えいのテスト | NFR3.1・NFR3.2・NFR3.3 |
| 検索の文字による SQL インジェクション・ワイルドカードの悪用 | 名前つきの引数とエスケープ、長さの上限、静的解析の関門 | NFR9.1・NFR9.2 |
| 管理の操作の否認（誰が権限を変えたか分からない） | 5つの操作の成功と拒否を監査に残す | `observability-requirements.md` の NFR9.3、PM の Mandated |

## 残る危険

| ID | 危険 | 受け入れる根拠 | 見直す時点 |
|---|---|---|---|
| R1 | 管理の API に要求の回数の制限が無い。管理者のアクセストークン・リフレッシュトークンが漏れると、その間に印の付け外しや利用停止を続けて行える | (1) 管理の API は管理者だけが呼べ、利用者 50 名の社内向け。前の Intent でも IP ごとの回数の制限をしなかった（要点 11）。(2) アクセストークンの有効期限は既定 5 分と短い。(3) 5つの操作は成功も拒否もすべて監査に残り、後から追える（NFR9.3）。(4) 最後の有効な管理者は無くせない（NFR4.1） | 社外に公開する配備先が決まったとき、または利用者の規模が増えたとき |
| R2 | 停止を解く・失敗回数を戻すの確かめ直しは操作した人の行を排他せずに読むため、読んだ直後に別の操作が確定する短い隙が残る | 有効な管理者を減らす操作ではないため、最後の管理者の保護（不変条件）は壊れない。機能設計の承認の場で受け入れた（FS の 9節の D5、R-04） | 権限の種類を増やすとき |
| R3 | 管理者による氏名と言語の変更は監査に残らない（BR5.3） | 要件の決定（FR6・FR7 の範囲）。氏名と言語は権限・状態ではなく、PM の Mandated（権限・状態を変える操作を監査に残す）の対象の外。変更は内部DB の今の値で確かめられる | 氏名を業務の識別に使うようになったとき |
