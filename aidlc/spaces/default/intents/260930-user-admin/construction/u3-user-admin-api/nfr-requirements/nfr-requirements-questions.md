## 設計の要点（案）

上流とコードの確認から導ける、この単位の非機能要件の見通しです。質問の答えで決まる点は（Qn）と書きます。枝番は単位の中で .1 から振ります（`project.md` の学び）。応答時間は NFR5、接続の使い方は NFR6 の枝番にします。観測の指標は NFR5、ログの中身は NFR3 の枝番に寄せ、寄せたことを成果物の冒頭に書きます。

### 性能

1. **一覧（GET `/api/admin/users`、検索あり・なし）**: 同時 10 件の要求で p95 1 秒以内（要件 NFR5 の [assumption] をそのまま目標にする）。1回の要求で読むのは、全体の件数・20 件の行・その 20 件のロックの判定の結果（1回の問い合わせ）だけで、パスワードのハッシュの列を読まない（BR1.6・BR1.7）。測るときの利用者の件数は（Q1）。
2. **氏名と言語の変更（PUT `/{userId}/profile`）**: 同時 10 件で p95 1 秒以内。排他も監査もしない利用者の1行の更新のため、余裕は大きい見込み。
3. **5つの操作（grant-admin・revoke-admin・suspend・resume・reset-login-failures）**: 目標と測る負荷は（Q2）。印の付け外しと止める操作は、すべての管理者の行を利用者 ID の順に排他するため（BR3.1）、同時の操作は1つずつ通る。止める操作は同じトランザクションでその利用者のリフレッシュトークンをまとめて無効にする（BR4.3）。
4. **排他の待ちの上限 3000 ミリ秒の例外**: 上限切れの 409 USER_ADMIN_BUSY は約 3 秒で返り、1 秒の目標の例外として扱う（承認の場の決定）。性能の試験では、目標の負荷で BUSY が出ないことを合わせて確かめる（Q2）。
5. **測り方と持ち主**: 使い捨ての環境の k6 で、場面ごとに p95 と `checks` の率 1 を閾値に置く（`perf/README.md` の決まり。目標を緩めない）。測定は Performance Validation の段が行い、Build and Test は台本を用意して `k6 inspect` で読み込めることを確かめる（前の Intent と同じ分け方）。利用者の状態を変える場面は、場面のために入れた試験用の利用者だけを対象にし、監査の行が増えることを受け入れる（使い捨ての環境のため本物の監査ログは汚さない）。

### セキュリティ

6. **認可（NFR1・NFR9）**: 7つの API のすべてで、未認証 401・管理者でない 403・管理者 200（変更は 204）をサーバー側のテストで確かめる。停止中の管理者は管理の API を呼べない（U1 の3つの入口）。操作の中の確かめ直し（BR2.5）で外れたら 403 ACCESS_DENIED。
7. **一括代入の防止（NFR1、BR5.4・BR7.2）**: 氏名と言語の変更の本文と `/api/me`・`/api/me/preferences` の本文に、印・停止・失敗回数の項目を入れても変わらない。
8. **個人に関する値と秘密（NFR3、BR7.4・BR7.5）**: 検索の文字・メールアドレス・氏名は、controller から repository の口まで伏せ字の型のまま渡し、アプリのログ・トレースの属性・監査ログ・エラー応答に出さない。応答にパスワードのハッシュ値・リフレッシュトークン・失敗回数そのもの・ダミーの行を載せない。TRACE を有効にした `UserAdminSecretLeakIT` で、7つの API と q を付けた要求で確かめる。
9. **入力の上限**: q は前後の空白を除いて 254 コードポイントまで、page は Paging の検証、本文は既存の上限 1MB のまま（BR1.1・BR1.4）。検索の文字は名前つきの引数だけで問い合わせに渡し、`%`・`_`・`\` をエスケープする（BR1.5）。
10. **静的解析**: 既存の関門（SpotBugs の priority 1、`SQL_`・`PREDICTABLE_RANDOM`・`SMTP_HEADER_INJECTION`）をそのまま通す。
11. **回数の制限はしない**: 管理の API は管理者だけが呼べ、利用者 50 名の社内向けのため、要求の回数の制限は足さない（前の Intent で IP ごとの制限をしなかったのと同じ）。管理の操作は成功も拒否も監査に残る（BR6.1）。

### 拡張性

12. **想定の規模**: 前の Intent と同じ、利用者 最大 50 名・同時 10 件の要求を1台で処理する。表と列は増えない（停止の列は U1 の V9）。監査の行は5つの操作1回に1行で、頻度は低い。検索は部分一致（索引を使わない走査）のため、件数が増えると遅くなる。測る件数と、索引の要否を決める材料は（Q1）。索引を作るかは NFR 設計で決める（機能設計 8.2 節）。

### 信頼性

13. **監査の書き込みの失敗で操作を失敗させない**（BR6.3、既存の AuditLog の決まり）。失敗はアプリのログの ERROR と既存の警報「監査の書き込みの失敗」で気づく。
14. **2本目の接続（NFR6、`project.md` の Corrections）**: 5つの操作は、成功も業務の拒否も、確定の後の監査の記録で2本目の接続を借りる。見積もりだけで済ませず、負荷の試験で接続を借りる待ちの時間切れの累計が 0 であることを確かめる（hikaricp の値は使い捨てのアプリだけに公開する）。試験の形は（Q3）。
15. **排他と行き詰まり（NFR4）**: どの操作も利用者の行とロックの状態の行を同時に排他せず、管理者の行は ID の順に取るため、行き詰まりは起きない設計（BR3.1・BR3.4）。上限切れは 500 にせず 409 USER_ADMIN_BUSY で巻き戻す（BR3.5）。確かめ方は NFR 設計と結合テスト（機能設計 8.2 節の申し送り）。
16. **想定外の誤り**: 内部DB の障害などは既存の 500 の扱い（例外のメッセージを載せない、確定しないため監査も残らない）。

### 観測

17. **既存の仕組みで見る**: 7つの API の応答時間と状態コードは既存の `http.server.requests`（`uri` のラベルは道の型で、利用者 ID と検索の文字を含まない）で取れる。BUSY は既存のエラー応答の仕組みが WARN で code を出す。確かめ直しの 403 は既存の警報「管理画面への拒否の増加」（403 の数）に数えられる。新しい指標・警報を足すかは（Q4）。
18. **SLO は決めない**: 手元の監視を常に動かしていないため、前の Intent と同じく SLO は決めず、配備先が決まったときに決め直す（`project.md` の Deployment）。

### 技術

19. **新しい依存は足さない**: 既存の Spring Boot・Spring Security・Spring Data JPA（`PESSIMISTIC_WRITE` と `jakarta.persistence.lock.timeout`）・H2・jqwik（LockView の判定）・ArchUnit で作る。

### テストとカバレッジ（NFR9）

20. **パッケージごとの下限**: `useradmin` の新しいパッケージは自動でパッケージごとの下限（行 80%・分岐 70%）の対象になる。U3 で手を入れる `auth.domain`・`auth.repository` は B1 で `packagesJudgedByTotal` から外れる計画のため、U3 では下限を満たし続ける。`auth.service`・`user` の各パッケージはすでに対象。`access.domain` は使うだけで本体を変えないため作業は付かない。実測は `:backend:cleanTest :backend:cleanIntegrationTest` を付けた `./gradlew verify` で取る。
21. **必須のテスト**: `team.md` の管理者の印の変更・ロックの解除・最後の管理者の保護（業務処理の層を直接呼ぶテストと待ち合わせの重なり）・管理の API の認可・要求の改ざん・管理の操作の監査・利用者の管理の漏えい。

## Q1. 一覧の性能を測るとき、内部DB に利用者を何人入れて測りますか？

理由: 要件 NFR5 が「件数の想定と測り方は NFR 要件の段で決める」としています。一覧は全体の件数を数え、検索ありではメールアドレスと氏名の部分一致（小文字にそろえて比べる）で行を探すため、索引を使わず全体を走査します。想定の 50 名では差が出ず、索引の要否（NFR 設計の申し送り）を決める材料になりません。試験用の利用者は使い捨ての環境に SQL で入れられます（`perf/README.md` の手順）。

A. 想定どおり 50 名で測る（1〜3 ページ目と検索あり・なし）
B. 想定は 50 名のままとし、悪い側の条件として 1,000 名を入れて、1ページ目・最後のページ・検索あり（当たる行が多い文字と、ほとんど当たらない文字）を同時 10 件で p95 1 秒以内か測る（推奨: 入れる手間は小さく、想定の 20 倍の余裕と索引の要否の材料が得られる）
C. 10,000 名を入れて同じように測る（余裕の確かめは大きいが、使い捨ての環境の準備と内部DB のファイルが大きくなる）

## Q2. 5つの操作の応答時間の目標と、測る負荷をどうしますか？

理由: 要件 NFR5 は各操作も p95 1 秒以内を [assumption] としています。ただし、印の付け外しと止める操作はすべての管理者の行を排他するため（BR3.1）、同時に流すと1つずつ通り、後の要求は前の確定を待ちます。1件は利用者の行の読み書きと監査の記録だけで短い見込みですが（bcrypt なし。止める操作はリフレッシュトークンの無効化が加わる）、同時 10 件では待ちが重なり、待ちが 3000 ミリ秒を超えると BUSY になります。現実には管理者が同時に操作することはまれです。測る場面は、試験用に入れた管理者と対象の利用者だけを使い、印を付けて外す・止めて解く・ロックさせて戻す、のように組で状態を戻しながらくり返す形を見込みます（細部は Performance Validation の台本）。

A. 5つの操作を合わせて同時 10 件で流し、操作ごとに p95 1 秒以内とする。あわせて 409 USER_ADMIN_BUSY が 0 件であること（`checks` の率 1）を合格の条件にする（推奨: ほかの API と同じ負荷で、排他の待ちが目標の負荷で上限に届かないことも確かめられる）
B. 目標は 1 秒のまま、測る負荷を同時 2 件にする（管理者の同時の操作はまれなため）。同時 10 件の値と BUSY の件数は記録だけにする
C. 操作は1件ずつ（同時 1 件）で p95 1 秒以内とし、同時の重なりは結合テスト（待ち合わせ）の確かめに任せる
X. Other (please specify)

[Answer]: A

## Q3. 接続プール（上限 30）が尽きないことを、どの負荷で確かめますか？

理由: 要件 NFR6 と `project.md` の Corrections により、2本目の接続を使う経路は負荷の試験で確かめます。5つの操作は成功も業務の拒否も確定の後に2本目の接続で監査を記録するため、同時 10 件では最大 20 本の見積もりで上限 30 に収まります。一方、ログインの失敗も同じく2本使う経路で、管理の操作 10 件にログイン 10 件が重なると見積もりは最大 40 本になり、上限を超えうります（前の Intent で上限を 30 に上げたときに既知の制約として記録した危険）。想定の規模は「全体で同時 10 件」です。

A. 管理の操作（Q2 の場面）と一覧を合わせて同時 10 件で流し、接続を借りる待ちの時間切れの累計が 0・500 が 0 件であることを確かめる。待ちの最大も記録する（推奨: 想定の規模の範囲で、見積もり 20 本が上限に収まることを実測で裏付ける）
B. A に加えて、管理の操作 10 件とログインの失敗 10 件を重ねる混在の場面も流し、待ちの時間切れの累計が 0 であることを確かめる（想定を超える負荷。時間切れが出たら既知の制約として記録し、依頼者に相談する）
C. 負荷の試験はせず、見積もり（最大 20 本）だけを記録する（`project.md` の Corrections と食い違うため、差として記録が要る）

## Q4. 管理の操作のために、新しい指標・ログ・警報を足しますか？

理由: 前の Intent の招待の管理（U3）は、新しい指標・警報を足さず、既存の HTTP の指標・監査ログ・アプリのログで見えるようにしました。この単位でも、応答時間と状態コードは既存の指標で取れ、成功と拒否はすべて監査ログ（内部DB）に残ります。ただし、監査ログは内部DB にあるため、手元の監視（Loki・Prometheus）からは見えず、管理者の印を付けた・利用を止めたといった権限の変更を警報で知ることはできません。警報の通知の先は配備先が決まるまで無く、手元の監視も見たいときだけ起動します。

A. 新しい指標・ログ・警報は足さない（推奨: 管理者は少数で操作はまれ、権限の変更は監査ログで後から追える。確かめ直しの 403 は既存の警報「管理画面への拒否の増加」に、BUSY は既存の WARN のログに出る。配備先が決まったときに見直す）
B. 5つの操作の成功と拒否を、アプリのログに INFO（操作の種類・結果・理由・操作した人と対象の利用者 ID だけ。メールアドレス・氏名は出さない）で1行ずつ出し、管理者の印を付けた操作と、最後の管理者の拒否に Loki の警報を足す（権限の変更に気づきやすいが、監査ログと同じ事実を二重に持つ。Observability Setup で式を確かめる）
C. 警報だけを足す: 409 USER_ADMIN_BUSY の WARN のログが一定の数を超えたら鳴らす（排他の待ちが上限に届く兆しに気づける。権限の変更は監査ログで追う）
