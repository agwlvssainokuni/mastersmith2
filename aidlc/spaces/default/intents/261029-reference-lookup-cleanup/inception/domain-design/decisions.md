# 設計の決定の記録（Domain Design）— reference-lookup-cleanup

形式は ADR（Context・Decision・Consequences・Alternatives Rejected）で、番号は ADR-001 から順に振る。出典の Q は `domain-design-questions.md`。

## ADR-001: 参照先を読む処理を、新しい論理の部品 `ReferenceLookup` にする

- **Context** — 今回は、(1) 作成・更新の画面の定義に載せる選択肢（REFERENCE）、(2) ピッカーの検索とラベルの1件読み（LOOKUP）、(3) 保存前の確かめ、の3つが「参照先の行を利用者の権限で読む」という共通の仕事になる。既存の `BusinessData` は一覧・詳細・作成・更新・削除、権限の判定、監査の出来事までを持ち、すでに責務が大きい。コード知識ベースの K-80 と `team.md` により、参照先の処理は `businessdata` の内側に置き、`role`・`dsl`・`targetdb` の境界テストは緩めない。
- **Decision** — `businessdata` の内側に `ReferenceLookup` を新しい論理の部品として置く（Q1: A）。参照先の権限の判定、DSL の名前との照合、件数の上限（200 件・201 件目の判定）、存在の確かめをここに集め、`BusinessData` はそれを呼ぶ。画面入出力・業務処理・DB アクセスの層は既存の `businessdata` の層に従う。
- **Consequences**
  - 良い点: 3つの仕事が同じ決まりを1か所で持ち、確かめやすい。`BusinessData` の責務がこれ以上広がらない。
  - 悪い点: 部品が1つ増え、`BusinessData` との呼び合い（定義・検索・保存前の確かめ）の契約を後の段（Contract Design）で決める必要がある。新しいクラスを作るときは、コード生成の計画に明記して承認を得る決まり（`team.md`）に従う。
- **Alternatives Rejected**
  - 既存の `BusinessData` に3つの仕事を足す（Q1: B）: 部品は増えないが、`BusinessData` が参照先の権限と上限まで持ち、変わる理由がさらに混ざる。

## ADR-002: 行の SQL の部品を `RowSqlGateway` として独立した部品に数え、参照先の読み取りは既存の `search`・`detail` を使い回す

- **Context** — 行の SQL は `RowSqlExecutor`・`RowDialect` だけが組み立てて実行し、SpotBugs の `SQL_` の除外はそのメソッド名ごとに書いてある。`BusinessData` と `ReferenceLookup` の両方が行の SQL を頼む。この SQL の部品を `BusinessData` の内側に数えると、`BusinessData → ReferenceLookup → BusinessData` の循環ができる。新しいメソッドで SQL を組むと、除外の追加を計画に明記して承認を得る必要がある。
- **Decision** — 行の SQL の部品を `RowSqlGateway` として独立した部品に数え、`BusinessData` と `ReferenceLookup` の両方が呼ぶ（依存は一方向）。参照先の読み取りは新しいメソッドを足さず、既存の `search`・`detail` に「出すカラムの指定」と「上限+1件読み」を渡せるようにして使い回す（Q2: A）。SpotBugs の除外は増やさず、`BusinessDataBoundaryArchitectureTest` の許可の一覧も緩めない。
- **Consequences**
  - 良い点: 呼び合いの循環が無く、SQL を組む場所が1つのまま。除外の追加と承認が要らない。
  - 悪い点: 既存の `search`・`detail` に口を足すため、既存の一覧・詳細への影響を結合テストで確かめる必要がある（3種類の DB で、出すカラムを絞った読み取りと上限+1件読みの境界）。部品の数え方が前の Intent の記録（`RowSqlExecutor` は `BusinessData` の責務）と変わる。
- **Alternatives Rejected**
  - 参照先専用のメソッドを足す（Q2: B）: 既存の読み取りに触れずに分けられるが、メソッドごとの `SQL_` の除外の追加と承認が要る。
  - `RowSqlGateway` を `BusinessData` の内側に数え、`ReferenceLookup` から `BusinessData` を呼ぶ: 循環ができる。

## ADR-003: 更新の保存前の確かめは、読み取りの接続で先に行い、その後で書き込みの接続で保存する

- **Context** — 更新では「値が変わった参照だけ」を確かめるため、更新前の行を読む必要がある（今の保存は更新前の行を読まない）。読み取りの接続（読み取りだけのアカウント）と書き込みの接続（SELECT・INSERT・UPDATE・DELETE のアカウント）は別で、対象DB を待つあいだ内部DB の接続を持たない決まりがある（`team.md`）。
- **Decision** — 更新前の行の読み取りと参照先の確かめを、まず読み取りの接続の中で順に行い、その後で書き込みの接続を借りて保存する（Q3: A）。確かめと保存の間に参照先が消えるすき間は、対象DB の外部キー違反を同じ誤りに変換する既存の守り（AC3.1.6）が最後の守りになる。
- **Consequences**
  - 良い点: 書き込みのアカウントで参照先を読まず、読み取りと書き込みで接続・資格情報を分ける決まりを守れる。書き込みの接続を長く持たない。
  - 悪い点: 確かめと保存の間にすき間が残る（既知の制約）。外部キーの無い参照では、すき間で消えた参照先を保存できてしまう。
- **Alternatives Rejected**
  - 書き込みのトランザクションの中で確かめる（Q3: B）: すき間は小さくなるが、書き込みのアカウントで参照先を読むことになり、権限の判定の流れが複雑になる。

## ADR-004: k6 の結果の JWT の伏せ字は、Node の独立した後処理の部品にし、`frontend/` の Vitest と fast-check で確かめる

- **Context** — k6 の結果（summary json）には使い捨ての環境のアクセストークン（JWT）が入り、記録（`evidence/`）に置く前に伏せる必要がある（前の Intent で CI が落ちた）。`team.md` は、仕組みに伏せ字のテスト（JWT の形が残らない・冪等・入れ子や配列や長い文字列の中でも伏せる・JWT 以外を壊さない）を付け、`./gradlew verify` と CI に入れることを求める。`perf/` には今シェルのテストがあり、Node は `frontend/` が使っている。
- **Decision** — 独立した後処理の部品 `PerfEvidenceRedactor` にする（Q4: A）。Node の1ファイル（依存なし）で `perf/` に置き（Q5: A）、置換の後に JWT の形が残っていないかの検査（置換とは独立の関数）も同じ部品に持つ。確かめは `frontend/` の Vitest と fast-check から呼び、`verify` が既に流すフロントの検査の仕組みに乗せる。k6 の標準出力・ログは対象外とし手順で扱う。
- **Consequences**
  - 良い点: k6 の実行方法に依存せず既存の結果にも使え、性質ベースのテストを `verify` に載せられる。
  - 悪い点: `frontend/` が `perf/` のファイルを読む配置になる。フロントの ESLint・oxlint・ライセンスヘッダーの検査の対象に入るかを設計・コード生成で確かめる必要がある。
- **Alternatives Rejected**
  - k6 の台本の `handleSummary` で伏せる（Q4: B）: `--summary-export` を上書きできるか未検証で、既存の結果や別の出力に効かない。
  - Java で書く（Q5: B）: perf の道具がアプリのソースに混ざる。シェル（jq）で書く（Q5: C）: 性質ベースのテストが書けず `team.md` の求めを満たせない。

## ADR-005: 参照先の権限の当て方と、拒否の応答をそろえること

- **Context** — 参照元の権限だけを持ち参照先の権限を欠く利用者の扱いを、要件定義とストーリーで決めた（US1.3・US2.1）。ストーリーの決定として、権限を欠く場合と参照先に存在しない場合を応答から区別できなくする（X13: 要件の「403」を「同じ応答」に読み替えることを依頼者が了承した）。
- **Decision** — 参照先のテーブルも、利用者の今の作業ロールの権限の写し（PermissionSnapshot）でサーバー側で判定する。読めない場合、選択肢は返さず、画面は入力不可（読み取り専用の欄に保存済みの値を出し、理由の説明文を添える）にする。主権限が NONE のカラムは応答に含めない。保存前の確かめでは、参照先に無い・読めないを同じ応答（409 `BUSINESS_REFERENCE_NOT_FOUND`）で拒否する。必須の参照項目で読めない、または候補が 201 件以上の作成は行き止まりを許容して拒否する（M1: A）。
- **Consequences**
  - 良い点: 応答から参照先の存在を推測できない。権限の判定の場所が1つ（サーバー）のまま。
  - 悪い点: 必須の参照が入れられない作成が行き止まりになる（管理者に権限の付与や DSL の変更を頼む必要がある）。ピッカーの検索と選択肢の取得で、権限を欠く場合の応答を既存の 403 とどうそろえるかは Contract Design で決める。
- **Alternatives Rejected**
  - 権限を欠く場合だけ 403 を返す: 参照先の存在を試せる。
  - 必須の参照項目で読めないときに文字入力へ切り替える: 権限を欠く人が参照先の存在を試せる。

## ADR-006: 実現できるかの判断（Feasibility の段が無いため、この段で扱う）

- **Context** — classic の範囲で Feasibility の段が無い。`project.md` の学びにより、実現できるかの判断はドメイン設計で扱い ADR に記録する。
- **Decision** — 次の点を、確かめる段と、だめだったときの切り替え先とともに受け入れる。

| 論点 | 見立て | 確かめる段 | だめだったときの切り替え先 |
|---|---|---|---|
| 既存の `search`・`detail` に出すカラムの指定と上限+1件読みを足しても、一覧・詳細が変わらない | 引数を足すだけで、既存の呼び出しは既定の値で今の動きのまま | コード生成（既存の結合テスト＋3種類の DB の新しい結合テスト） | 参照先専用のメソッドを足す（SpotBugs の除外の追加を計画に明記して承認を得る） |
| 200 件の上限と201件目の判定を3種類の DB で同じにする | 上限+1件を `LIMIT`（PostgreSQL・MySQL・MariaDB）で読めば同じになる | コード生成（AC1.2.x の結合テスト） | 件数の問い合わせ（`COUNT`）を別に行う（時間の上限つき） |
| REFERENCE が複数あっても読み取りの接続の借りる回数が1回 | 1つの接続の中で順に読めば満たせる（AC1.1.5） | NFR 設計・コード生成（`*ConnectionUsageIT` と同じ形の結合テスト） | 定義の取得を参照の項目ごとの別の要求に分ける（画面の変更が要る） |
| 更新で「値が変わった参照だけ」を確かめる | 保存前に更新前の行を読み、本文の値と比べる。型の違い（文字列と数）を列の型で正規化して比べる | 機能設計・コード生成（AC3.2.x） | 参照のすべてを確かめる（読み取りの数が増える） |
| 複合の主キー・主キーの無いテーブル・ビュー・自己参照を参照先にしたときの扱い | 値のカラムが単一のカラムのときだけ REFERENCE/LOOKUP を許す見込み（未検証） | 機能設計（Q(h) の決め）・結合テスト | 参照先として使えない定義を DSL の検証で拒否する |
| JWT の形の判定と置換が、入れ子・配列・長い文字列でも JSON を壊さない | 文字列の値を再帰で走査して置換する。JSON を一度読んで書き直すので壊れない | NFR 設計・コード生成（fast-check の性質） | 文字列の置換（正規表現）を行単位で行い、検査で JSON の読み直しを確かめる |
| `frontend/` の Vitest が `perf/` の Node のファイルを読める | ESLint・TypeScript・ライセンスヘッダーの検査の対象に入るかは未検証 | コード生成（`verify` の通過） | 後処理を `frontend/` の下に置く、または専用の小さな検査の入口を `perf/` に置く |
| コンテナの版そろえ（FR6） | `compose.yaml` から `--force-recreate --no-deps` で作り直し、`docker inspect` の RepoDigests で確かめる | Build and Test・Deployment Execution | 手動で作り直す手順に切り替える |

- **Consequences**
  - 良い点: 実現の危険を、確かめる段と切り替え先とともに先に見える形にした。
  - 悪い点: 切り替え先のいくつか（専用のメソッド、件数の別問い合わせ）は、計画の承認や依頼者の決定が要る。
- **Alternatives Rejected**
  - 実現の判断を後の段に任せて記録しない: `project.md` の学び（Feasibility を吸収したときはドメイン設計で扱う）に反する。
