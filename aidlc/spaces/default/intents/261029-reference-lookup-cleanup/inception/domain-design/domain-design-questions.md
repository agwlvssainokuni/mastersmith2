# Domain Design — 質問（Intent 261029-reference-lookup-cleanup）

承認済みの要件・ストーリー・画面イメージをもとに、部品（コードとして書く論理の部品）の分け方を決めます。ここで決めるのは部品の境界・持ち主・呼び合いだけで、配備の形・技術の選択・非機能の作りは後の段です。判断が分かれる点だけを尋ねます。

## 決まっていること（質問しません）

- 参照先を読む処理は `businessdata` の内側に置く。`role`・`dsl`・`targetdb` の境界テストを緩めず、`RoleBoundaryArchitectureTest` に依存してよい相手を足さない（コード知識ベースの K-80、`team.md` の Code Style）。
- 権限の判定は、利用者の今の作業ロールの権限の写し（`PermissionSnapshot`）で、API ごとにサーバー側で行う。参照先の表も、その利用者の権限で判定する。
- 画面は既存の `features/tables`（作成・更新の画面）に参照の項目を足す。ピッカーのダイアログは `features/tables` に置き、複数の機能で使うことになったら `src/shared/` へ移す。make-you-chic-ui への新しい依頼は出さない（Refined Mockups）。
- 選択肢の読み取りは作成・更新の画面の定義のときだけ。一覧・詳細の定義では参照先を読まない（US3.4）。
- エンティティは、アプリが独自に持つデータだけを書く。参照先の行は対象DB のデータで、エンティティにしない。今回の Intent で新しく持つデータは無い（内部DB のスキーマは変えない）。
- コンテナの版そろえ（Mailpit・otel-lgtm）、perf の文書の整理、Dependabot の取り込みは、コードとして書く部品ではない（設定・文書・取り込み）ため、部品にしない。JWT の自動の伏せ字の仕組みだけが、コードとして書く部品になる。

## Q1: 参照先を読む処理を、新しい論理の部品にするか
`businessdata` には、一覧・詳細・作成・更新・削除を受け持つ既存の部品（`BusinessData`）があり、権限の判定、行の SQL（`RowSqlExecutor`・`RowDialect`）、監査の出来事までを持っています。今回は、(1) 作成・更新の画面の定義に載せる選択肢（REFERENCE）、(2) ピッカーの検索とラベルの 1 件読み（LOOKUP）、(3) 保存前の確かめ、の 3 つが「参照先の行を、利用者の権限で読む」という共通の仕事になります。

A. `ReferenceLookup` という新しい論理の部品を `businessdata` の内側に作る。3 つの仕事の持ち主にし、参照先の権限の判定・上限・存在の確かめをここにまとめる。`BusinessData` はそれを呼ぶ。責務が分かれて確かめやすい代わりに、部品が 1 つ増える
B. 新しい部品は作らず、既存の `BusinessData` に 3 つの仕事を足す。部品は増えないが、`BusinessData` の責務がさらに広がる（すでに大きい）

## Q2: 参照先を読む SQL は、既存の読み取りを使い回すか、専用のメソッドを足すか
行の SQL は `RowSqlExecutor` だけが組み立てて実行し、SpotBugs の `SQL_` の除外は、その中のメソッド名ごとに書いてあります（`search`・`detail` など）。新しいメソッドで SQL を組むと、除外の追加が要り、コード生成の計画に明記して依頼者の承認を得る決まりです（`team.md`）。

A. 既存の `search`・`detail` を使い回す。参照先の表に対して、利用者の権限で「出してよいカラムだけ」の読み取り（LOOKUP は `lookupList` のカラムと `valueColumn`、REFERENCE は `valueColumn` と `labelColumn`）を頼む形にする。SpotBugs の除外は増えない。代わりに、`search`・`detail` に「出すカラムの指定」と「件数の上限+1 件読み」を渡せるようにする変更が要り、既存の一覧・詳細への影響を確かめる必要がある
B. 参照先専用のメソッド（選択肢・ラベルの 1 件読み）を足す。既存の一覧・詳細の読み取りに触れず分けて確かめやすい。代わりに、メソッドごとの SpotBugs の除外の追加を計画に明記して承認を得る

## Q3: 更新の「値が変わった参照だけの確かめ」の読み取りの順
更新では、保存前の確かめを「値が変わった参照だけ」に絞るため、更新前の行を読んで、変わった参照を知る必要があります（今の `write()` は更新前の行を読んでいません）。読み取りの接続（読み取りだけのアカウント）と書き込みの接続（SELECT・INSERT・UPDATE・DELETE のアカウント）は別です。

A. 更新前の行の読み取りと参照先の確かめを、まず読み取りの接続の中で順に行い、その後で書き込みの接続を借りて保存する。書き込みの接続を長く持たないが、確かめと保存の間に参照先が消えるすき間があり、最後の守りは対象DB の外部キー違反の変換（US3.1 の AC3.1.6）になる
B. 書き込みの接続の同じトランザクションの中で、更新前の行の読み取りと確かめを行う。すき間は小さくなるが、書き込みのアカウントで参照先を読むことになり、読み取りと書き込みで接続・資格情報を分ける決まりと、参照先の権限の判定の流れが複雑になる

## Q4: JWT の自動の伏せ字の置き場（部品の持ち主）
k6 の結果（summary json）の JWT を記録（`evidence/`）に置く前に伏せる仕組みです。要件は、置き場を設計で決めるとしています。

A. 独立した後処理の部品（スクリプト）にする。記録を置く手順が必ずそれを通し、置換の後に JWT の形が残っていないかの検査（置換とは独立の関数）も同じ部品に持つ。k6 の実行方法には依存せず、既存の結果にも使える。ただし、k6 の標準出力・ログは対象外（手順で扱う、要件のとおり）
B. k6 の台本の `handleSummary` で、出力を作る時点で伏せる。台本の中で完結するが、`--summary-export` を上書きできるかが未検証で、台本の変更が大きくなり、既存の結果や別の出力の経路には効かない

## Q5: 伏せ字の部品の言語と、確かめの置き場
`team.md` は、仕組みのテスト（置換の冪等・入れ子・JWT 以外を壊さない性質）を、性質ベースのテスト（Java は jqwik、フロントは fast-check）で `./gradlew verify` に入れることを求めています。`perf/` には今、シェルのテスト（`thresholds-test.sh` など）があり、Node は `frontend/` が使っています。

A. Node（TypeScript または ESM の 1 ファイル、依存なし）で `perf/` に置き、確かめは `frontend/` の Vitest＋fast-check から呼ぶ。`verify` が既に流すフロントの検査の仕組みに乗れる。代わりに、`frontend/` が `perf/` のファイルを読む配置になる
B. Java で書き、`backend/` のテスト（jqwik）で確かめる。性質ベースのテストの仕組みが既にある。代わりに、perf の道具がアプリのソースの中に混ざる
C. シェル（jq）で書き、`perf/` のシェルのテストで確かめる。perf の既存の流儀に合うが、性質ベースのテストが書けない（`team.md` の求めを満たせない）

## Consolidated Summary Confirmation

答え（Q1〜Q5 すべて A）と「決まっていること」から、次の部品の構成で成果物を作ります。

- 新しい論理の部品 `ReferenceLookup`（`businessdata` の内側）を置き、選択肢（REFERENCE）・ピッカーの検索とラベルの 1 件読み（LOOKUP）・保存前の確かめを受け持たせる。参照先の権限の判定（`PermissionSnapshot`）、件数の上限（200 件・201 件判定、ページ 20 件）、存在の確かめはここに集める。`BusinessData` は呼ぶ側になる。
- 参照先の SQL は新しいメソッドを足さず、`RowSqlExecutor` の既存の `search`・`detail` を使い回す（出すカラムの指定と上限+1 件読みを渡せるようにする）。SpotBugs の除外は増やさず、一覧・詳細への影響は設計・コード生成で確かめる。
- 更新の保存前の確かめは、読み取りの接続で更新前の行と参照先を先に確かめ、その後で書き込みの接続を借りて保存する。確かめと保存の間のすき間は、対象DB の外部キー違反の変換（AC3.1.6）が最後の守りになる。
- k6 結果の JWT の伏せ字は、独立した後処理の部品（Node の 1 ファイル、依存なし、`perf/` に置く）にし、置換の後に JWT の形が残っていないかの検査も同じ部品に持つ。確かめは `frontend/` の Vitest＋fast-check から呼ぶ。k6 の標準出力・ログは対象外。
- 既存の部品（`TargetDb`・`RoleManagement`・`DslDefinition`・`AuditLog`・`ApiClient`）には新しい依存を足さず、`BusinessDataBoundaryArchitectureTest` の許可の一覧も緩めない。エンティティは新しく持たない（内部DB のスキーマは変えない）。
