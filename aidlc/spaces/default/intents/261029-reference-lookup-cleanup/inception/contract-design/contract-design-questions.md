# Contract Design — 質問（Intent 261029-reference-lookup-cleanup）

承認済みの単位（`inception/units-generation/unit-of-work.md`・`unit-of-work-dependency.md`）・部品（`inception/domain-design/components.md`）・要件をもとに、単位の間の約束（契約）を決めます。書く前に既存のコードの口を確かめました: 定義の API は `POST /api/tables/definition`（本文 `schema`・`table`・`definitionId`）で、一覧・詳細・作成・更新の画面がどれも使う。定義のカラムの項目（`ColumnDefinitionResponse`）は `formPart`・`choices`（`value` と日英の `label`）を持ち、今は `lookup` を `text` に置き換えている。問題の種類は `BusinessDataProblemTypes`（`BUSINESS_REFERENCE_NOT_FOUND` は 409）で、403 は共通の `ACCESS_DENIED`。`ReadPurpose` は `GENERATE`・`COMPARE`・`LIST`・`DETAIL` の4つ。各質問の最初の選択肢を推奨とし、理由を添えます。

## 決まっていること（質問しません）

- 外部（アプリの外）に公開する API は無い。新しい API も同じ WAR の画面だけが使い、`@ApiAccess` の「ログインだけ」に分類し、判定は作業ロールの権限で行う（前の Intent の契約と同じ）。
- 版の番号は付けない（1 つの WAR で同じ版を配備）。応答に足す欄は、既存の画面が読み落としても壊れない足し方にする（NFR7）。
- 行の値（参照先の値・検索の値・ラベル）は道（URL）にも問い合わせの文字列にも載せず、本文で運ぶ（前の Intent の CQ1: A と同じ）。参照先のスキーマ・テーブル・カラムの名前は利用者から受け取らず、参照元のスキーマ・テーブル・カラムの指定から DSL で引く（FR2.2）。
- 対象DB の時間切れ・接続の失敗は、既存の 503 `BUSINESS_TARGET_DB_TIMEOUT`・`BUSINESS_TARGET_DB_UNAVAILABLE` を使い回す（FR1.5）。保存前の確かめの拒否は、既存の 409 `BUSINESS_REFERENCE_NOT_FOUND`（その項目の誤り）を使い回す（FR3.1）。
- `ReadPurpose` には参照先の読み取りの目的を足す。名前と時間の上限の値は機能設計・NFR 設計で決める。
- U4 → U5 の約束は、`perf/README.md` の伏せ字の手順の節と、伏せ字の道具の呼び方（入力・出力・終わりのコード）だけで、形はこの段で書く。

## Q1. [設計] ピッカーの検索 API で、権限が無い・DSL に無い・行が無いときの「同じ応答」を何にするか
ストーリーでは、参照先の存在や権限を推測させないため、権限を欠く場合・参照元の指定が DSL に無い場合・（ラベルの取得で）行が無い場合を、状態コード・`code`・構造・メッセージまで同じ応答にすると決めています（AC2.1.11、X13）。形はこの段で決めます。`team.md` の他テーブル参照の必須テスト (a) は「401・403・200」で書かれており、X13 は「403 以外に決まったら読み替える。了承が取り消されたら 403 に戻す」としています。

A. すべて 403 `ACCESS_DENIED`（既存の共通の code）にする（推奨）。新しい code を足さず、`team.md` の (a) の 401・403・200 の表をそのまま使える。代わりに、権限のある人がラベルの取得で消えた行を引いたときも 403 になる（画面は値だけを出すので、見た目は変わらない）
B. すべて 404 の新しい code（例: `BUSINESS_REFERENCE_UNAVAILABLE`）にする。「無い」に寄せた応答で、権限の不足だとは読めない。代わりに code が 1 つ増え、(a) の 403 を 404 に読み替えたままになる
C. 検索は 200 で 0 件、ラベルは 200 でラベル無し、にする。誤りにしないので画面の分岐が少ない。代わりに、権限の不足が「正常」に見え、(a) の 401・403・200 の確かめが成り立たない

## Q2. [設計] ラベルの 1 件読みを、検索 API の一つの形にするか、専用の API にするか
更新の画面で、保存済みの値のラベルを出すために、参照先の行を値で 1 件引きます（FR2.5、AC2.1.5）。

A. 検索 API を 1 本にし、本文に「検索の条件とページ」か「値」のどちらか一方を入れる形にする（推奨）。API の分類・権限の表（(a) の表）・漏えいの確かめが 1 本で済む。両方を入れた・どちらも無い本文は 400 `VALIDATION_FAILED` で拒否する
B. ラベルの専用の API を足す（検索とは別の道）。役割ははっきりするが、API が 2 本になり、分類と権限・漏えいの確かめを 2 本分書く

## Q3. [設計] 定義の API で、作成・更新のための取得をどう指定するか
選択肢は作成・更新の画面の定義のときだけ読み、一覧・詳細の定義では参照先を読みません（AC3.4.2）。今の定義の API は 4 つの画面が同じ形で呼んでいます。

A. 定義の本文に任意の `purpose`（`VIEW`・`CREATE`・`UPDATE`）を足し、無いときは `VIEW`（今のまま、参照先を読まない）とする（推奨）。既存の画面は変えなくても今のまま動き、作成・更新の画面だけが `purpose` を付ける
B. 作成・更新のための定義の API を別の道で足す。役割ははっきりするが、定義の応答の作り方が 2 か所に分かれ、API が 1 本増える

## Q4. [設計] 定義のカラムの項目に、参照の情報をどう足すか
REFERENCE は選択肢と「読めない」「多すぎる」の印、LOOKUP はピッカーの情報（検索条件・一覧のカラム・並び）を画面に渡します（FR1.1〜FR1.3・FR2.1）。今の `choices` は DSL の固定の選択肢で、ラベルは日英の表示名です。参照先のラベルは対象DB の値（1 つの文字列）です。

A. カラムの項目に、参照のときだけ値を持つ入れ子の欄 `reference` を 1 つ足す（推奨）。中身は、種類（`REFERENCE`・`LOOKUP`）、状態（`AVAILABLE`・`NO_PERMISSION`・`TOO_MANY`）、REFERENCE の選択肢（値と、文字列か null のラベル）、LOOKUP のピッカーの情報。`formPart` は `lookup` を `text` に置き換えるのをやめて本当の値を返す。参照でないカラムは `reference` が null で、既存の画面は読み落としても壊れない。201 件以上の印は、Problem の code ではなく、この状態（`TOO_MANY`）で渡す
B. 今の `choices` に参照先の選択肢も入れ、状態とピッカーの情報は平らな欄で足す。欄の数は少ないが、`choices` のラベルの型（日英の表示名と、対象DB の文字列）が混ざり、固定の選択肢と参照の選択肢を画面が見分けにくい

## Q5. [設計] 定義の取得の中で、選択肢の読み取りが時間切れ・接続の失敗になったとき
要件 FR1.5 は、選択肢の読み取りの時間切れ・接続の失敗を「既存の業務データの読み取りと同じ誤り（503）」としています。一方で、201 件以上（FR1.2）は項目ごとの印で、フォーム全体を失敗にしません。

A. 要件のとおり、定義の取得そのものを 503（`BUSINESS_TARGET_DB_TIMEOUT`・`BUSINESS_TARGET_DB_UNAVAILABLE`）で失敗にする（推奨）。要件と食い違わず、対象DB が落ちているときに半端なフォームを出さない。代わりに、参照の項目 1 つの時間切れで作成・更新の画面全体が開けない
B. 項目ごとの状態（例: `UNAVAILABLE`）にして、ほかの項目は入力できるようにする。使える範囲は広がるが、要件 FR1.5 との差を記録する必要があり、保存しても参照先の確かめ（U2）で同じ失敗が起きうる
