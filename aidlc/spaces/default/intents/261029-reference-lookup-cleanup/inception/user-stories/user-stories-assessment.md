# ユーザーストーリーの要否（reference-lookup-cleanup）

## 判定

- **Decision**: Execute（ストーリーを書く）

## 理由

- 利用者から見える変更がある。フォームの選択肢、参照ピッカー（検索ダイアログ）、保存前の確かめ、権限を欠く人の表示が変わる。
- ペルソナが複数いる。参照先を選ぶ人（P2）、権限を欠く人（P1）、権限の効き方を確かめる管理者（P3）、運用・性能を測る人（P4）。
- 業務の決まりが複雑。参照先の権限、200 件の上限、値が変わった参照だけを確かめる更新、拒否の監査、ラベルを見せない範囲など。

## 検討した要素

- 種類: 既存の機能（業務データの作成・更新）への機能追加と、持ち越しの片付け。
- 利用者に見える範囲: 画面の入力部品と誤りの表示。一覧・詳細は変えない。
- 複雑さ: 権限の判定、DB の種類ごとの差、画面のアクセシビリティ。

## ストーリーが特に効く場所

- 権限を欠く人の扱い（入力不可で値だけ見える）と、更新が失敗しないこと（US1.3・US3.2）。
- 境界の値（200 件ちょうど・201 件）と、拒否の応答をそろえること（US1.2・US2.3）。
- ピッカーの操作とアクセシビリティ（US2.1・US2.4）。

## ストーリーにしないもの

- Dependabot の取り込み（FR8）: 決まりが `team.md` に既にあり、利用者の価値が薄いため、`traceability.json` で N/A（質問 Q5: A）。
