### 1. 実現の見通し（足し方）

- **SQL の置き場**: 選択肢（`labelColumn` 昇順・201 件まで）、ピッカーの検索（条件・ページ）、ラベルの 1 件読み、保存前の存在確認は、どれも `RowSqlExecutor` と `RowSqlBuilder`・`RowDialect`（`MysqlFamilyRowDialect`・`PostgresRowDialect`）への足し方で書ける（A8 は成り立つ見込み）。既存の `search`（件数とページ、`setMaxRows`、`classifyAndMark`）がピッカーの検索にほぼそのまま使える。新しいクラスは要らない見込みで、`team.md` の「新しいクラスは計画で承認」に当たらない。
- **境界テストと SpotBugs**: `prepareStatement` を呼ぶ場所は今の部品に閉じたままなので、ArchUnit の境界テストは緩めない。ただし SpotBugs の `SQL_` の除外は「クラス・メソッド・パターン名の 3 つで絞る」決まりのため、足すメソッド名ごとに除外の追加が要る。これは「除外を足す・広げる」に当たり、コード生成の計画に明記して依頼者の承認が要る（ストーリーではなく計画の論点。US1.4 の備考として残す）。
- **`packagesJudgedByTotal`**: `businessdata` は一覧に無い（新しいパッケージ側）ので、パッケージごとの下限（行 80%・分岐 70%）がそのまま当たる。7 パッケージのうち手を入れる見込みがあるのは、エラーの code を足す場合の `common.error.*` のみ。code は `businessdata.domain.BusinessDataProblemTypes` に置き、403 は共通の `ACCESS_DENIED`、409 は既存の `BUSINESS_REFERENCE_NOT_FOUND` を使い回すので、`common.*` に手が入らない見込み。実測は Delivery Planning。
- **3 種類の DB の差**: NULL を最後に並べる書き方は MySQL 系（`col IS NULL, col`）と PostgreSQL（`NULLS LAST`）で違い、既存の `RowDialect` の持ち分に収まる。ただし文字の並びは照合順序で決まるため、3 種類で同じ並びになるとは限らない（下の OBJECT 1）。
- **値の型**: 保存前の確認で束ねる値は、参照元のカラムの型ではなく、参照先の `valueColumn` の型で束ねる。PostgreSQL は型が合わない比較を拒み、MySQL は暗黙変換で通るため、参照元と参照先の型が違う DSL（INT と BIGINT、数字の文字列と整数など）で DB ごとに結果が割れる。型が合わない場合の動作を受け入れ基準に足す。

### 2. 定義の応答に選択肢を載せる場所（大きな論点）

今の定義の応答（`ColumnDefinitionResponse`）は、一覧・詳細・作成・更新の画面のすべてが同じ呼び出しで読む。ここに REFERENCE の実行時の読み取り（最大 201 件 × REFERENCE の数）を入れると、**一覧・詳細を開くだけで参照先を読む**ことになり、FR4.1（一覧・詳細は変えない）と NFR2 の線に反する。フォームの用途（作成・更新）のときだけ選択肢を読む形（別の呼び出し、または用途の指定）を Contract Design で決める必要がある。ストーリーには「一覧・詳細の定義の取得では参照先を読まない」を受け入れ基準として足すのが安全（US3.4 に足す）。

### 3. 更新で「値が変わった参照だけ」を確かめる実現

- 今の `write()` は更新前の行を読んでいない。変わったかの判定には、更新前の行（参照のカラムの保存値）を対象DB の読み取りの接続で 1 回読む必要がある。**この読み取りと、参照先の存在確認は、同じ読み取りの接続 1 本の中で順に行う**（NFR3 を守る）。書き込みの接続（`writeAccess.withWrite`）は、確認が済んでから借りる（内部DB・対象DB の接続を持ったまま待たない）。
- 確認から保存までの間に行や参照先が変わりうる（読み取りと書き込みは別の接続）。最後の守りは既存の外部キー違反の変換（FR3.3）。外部キーを持たない DB のテーブルでは最後の守りが無いことを、既知の制約として一言書く。
- 比べ方は、更新前の値と本文の値を、型に直した値（`TypedValue`）の同値で比べる。照合順序で同じとみなされる値（大文字小文字違いなど）は「変わった」扱いで確かめに回すだけで、安全側に倒れる。
- 更新前の行が無い（ROW_NOT_FOUND）場合は、参照の確認より前に既存の応答にそろえる（行の有無を、参照の拒否で漏らさない）。この判定順を受け入れ基準に足す。

### 4. NOT NULL の参照カラムで読めない・201 件超のとき

- 作成: 入力不可（FR1.3）か選択肢なし（FR1.2）のまま NOT NULL なら、値を入れられず保存できない。サーバー側は、本文の値が来ても AC3.1.3 と同じ 409（`BUSINESS_REFERENCE_NOT_FOUND`）で拒否する。画面は送信前に項目の誤りを示す（項目が入力不可の旨と原因を見せる）。AC3.1.5 の「機能設計で決める」は、この 409 に決めて閉じられる（動作の変更は不要で、決めた動作を明示したテストにする）。
- LOOKUP は 201 件超でも検索で選べるので、この問題は REFERENCE だけに起きる（ピッカーへの案内が出る）。
- 更新: 値が変わらない限り保存できる（AC3.2.1）。

### 6. 受け入れ基準どうしの実装上の食い違い

- **読めないカラムの扱い（AC1.3.2・AC2.1.6・AC2.3.3・FR1.3 と FR2.3）**: FR1.3 は「`lookupList` のカラムの主権限が NONE なら提供しない」、FR2.3 と AC2.1.6 は「読めないカラムは応答から除く」で、一方は全体を止め、他方は部分を除く。実装は部分を除く方が素直（`valueColumn` が読めないときだけ止める）。ただし**検索条件のカラム（`lookupSearch`）が NONE のとき、検索に使うと中身が推測できる**ため、NONE の条件は入力に出さず、サーバーも拒否する。この三つ組の決め方を受け入れ基準に書く。
- **AC1.1.4 と AC1.2.3**: 1 件の項目が 201 件超でも定義は失敗にならない（項目ごとの誤り）一方、時間切れ・接続の失敗は全体が 503。接続は時間切れの後に「壊れたとみなす」印が立つ（`classifyAndMark`）ため、同じ接続で後続の項目を読み続けられない。したがって 503 は全体の失敗と明記する（項目ごとに 503 を付ける形は実装できない）。
- **AC1.1.5 と NFR2**: REFERENCE が多い画面で、1 本の接続で順に読むと、最悪 `項目数 × 問い合わせの時間の上限` かかる。REFERENCE の数に上限を置くか、全体の時間の上限を置くかを設計で決める（受け入れ基準は「数が上限以内」と書く）。
- **共通の読み方「3 種類で同じ結果」と AC1.1.1 の並び**: 並びは照合順序の影響を受ける（OBJECT 1）。
- **画面の項目の印（AC1.3.1・AC1.2.2）**: 「権限なし」と「件数が多い」は定義の応答の項目ごとの状態で、どちらも古い画面の部品が読み落としても壊れない足し方（AC3.4.2）にする。応答の欄を足すだけで済む。

### 7. 足したい受け入れ基準（短く）

1. 一覧・詳細の定義の取得では、参照先を読まない（US3.4）。
2. 更新前の行が無いときは、参照の拒否より先に既存の「行が無い」の応答になる（US3.2）。
3. 参照元と参照先の型が合わない・`labelColumn` が読めない型（バイナリ・巨大な文字列）のときの動作は、機能設計で決め、決めた動作を明示したテストにする（US1.4 の AC1.4.4 に並べる）。
4. 検索条件のカラムが NONE のとき、入力に出さず、サーバーも拒否する（US2.1）。
5. `team.md` の (f)（ラベルを信頼できない入力として文字で描く）を、US1.1（選択肢）にも受け入れ基準として足す（今は US2.1・US2.2 だけ）。選択肢の `label` に `<script>` が入っても文字で出ることを部品テストで確かめる。
6. 検索 API（とラベルの 1 件読み）を、API の分類の網羅のテストに載せる（US2.3）。
7. 新しい record（選択肢・検索の結果・ラベル）は `toString` を上書きして値を伏せ、TRACE を有効にした `XxxSecretLeakIT` で確かめる（US1.4）。
