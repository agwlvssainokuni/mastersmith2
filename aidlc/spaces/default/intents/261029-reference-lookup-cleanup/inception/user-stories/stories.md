## 前提と読み方（すべての受け入れ基準に共通）

### 分け方・優先度

- 優先度は MoSCoW。参照の選択肢・ピッカー・保存前の確かめ・JWT の伏せ字を Must、コンテナの版そろえ・perf の文書の整理を Should とする（Q3: A）。最小の範囲（MVP）の線は Delivery Planning で決める。

### 業務の決まりの読み方

- **権限**: 作業ロールの権限（主権限 NONE・READ・FULL、補助権限 CREATE・DELETE）で、API ごとにサーバー側で判定する。画面の出し分けは代わりにならない（PM の Mandated）。作業ロールを切り替えた直後・割り当てを変えた直後の次の要求で、判定が切り替わる。
- **参照元・参照先**: 参照元は参照する側の表のカラム、参照先は参照される側の表。参照先は同じスキーマの中の表に限る（要件の制約）。
- **要る権限だけを欠く利用者**: 403 や「権限を欠く応答」を確かめる利用者は、権限が何も無い利用者ではなく、確かめる 1 つの権限だけを欠く利用者（ほかの権限は持つ）にする。欠く権限は次の 4 種類を別々に用意し、パラメーターを使う表で書く。(1) 参照元のカラムが FULL でない、(2) 参照先の表の主権限が NONE、(3) 参照先の `valueColumn`（REFERENCE は `labelColumn` も）の主権限が NONE、(4) LOOKUP の `lookupList` のカラムの主権限が NONE。停止中の利用者は、権限があっても通らない。
- **読めないカラム（主権限 NONE）**: 応答に含めない。画面で隠すことを代わりにしない（PM の Mandated）。ピッカー（LOOKUP）は、`valueColumn` または `lookupList` に読めないカラムがあるときは、提供しない（部分的に落として提供することはしない。SL③）。
- **同じ応答**: 「区別させない」「同じ応答」の合否は、2 つの要求で、状態コード・`code`・項目の誤りの構造・メッセージが同一であること。
- **API 別の期待**（`team.md` の (a) の 401・403・200 の表に載せる形）:

| API | 未認証 | 要る権限を欠く | 権限あり |
|---|---|---|---|
| 作成・更新の画面の定義の取得 | 401 | 200＋その項目に「権限なし」の印（403 にしない） | 200＋選択肢またはピッカーの情報 |
| 参照先の検索 API（ラベルの取得を含む） | 401 | 同じ応答（形は Contract Design で決める） | 200 |
| 作成・更新（参照の値を入れる） | 401 | 409 `BUSINESS_REFERENCE_NOT_FOUND`（その項目の誤り。存在しない値と同じ） | 200 |

- **参照先の行の値**（選択肢の値・ラベル、検索の値）は、アプリのログ・トレースの属性・エラー応答・監査に含まれない（PM の Forbidden）。各ストーリーに繰り返さず、ここで一度だけ書く。確かめる受け入れ基準は AC1.4.2・AC1.4.7・AC2.1.15・AC3.3.2 に置く。
- **誤り**: Problem Details の形で返り、画面が分岐に使う安定した `code` を持つ。内部の例外メッセージを含まない。1 つの `code` に 1 つの状態コードを固定する。
- **画面の文言と誤りのメッセージ**は日本語と英語の両方（既定は日本語）。次の 6 つは必ず両方を用意する（D）。「権限なし」「件数が多い」「0 件」「検索中」「検索の失敗」「選択済みを消す」。
- **3 種類の対象DB**（MySQL・MariaDB・PostgreSQL）のすべてで、結合テストで確かめる。ただし文字の並びは各 DB の照合順序に従い、3 種類で同じ並びは求めない（SL④）。並びの規則（昇順・NULL は最後・ラベルが同じなら `valueColumn` の昇順）を確かめるテストの値は、並びが割れない値（半角英数字のラベル）にする（V・Q）。
- **競り合い**は、スレッドの数に頼らず、待ち合わせで確実に作る（PM）。時刻は注入した時計で動かす。
- **部品の有無**: make-you-chic-ui の部品が足りるかは、ストーリーの合否ではない。受け入れ基準は、部品に依らない振る舞いで書く。足りない点は Refined Mockups で一覧にし、`make-you-chic-ui-request-<n>.md` で上流へ依頼する（TP の Way of Working）。部品に頼らない自作のピッカーは、キーボード操作と `aria` の属性を画面のテストで確かめる。
- **画面のテスト**は、描画の後の効果で出る値を `waitFor` で待って確かめる（TP）。

## 群1 参照の選択肢（REFERENCE）

### US1.1 参照先の選択肢から値を選ぶ 〔Must〕

P2（鈴木さん）として、他のテーブルを参照する項目（`select`・`radio`）で、参照先の行を選択肢から選びたい。それは、ID を覚えず、打ち間違いなく入力するためである。

- **AC1.1.1（直した）** Given 参照先の表を読める利用者が、REFERENCE のカラムを持つ表の作成・更新の画面を開いたとき、When 画面の定義を取得するとき、Then 参照先の `valueColumn` を値、`labelColumn` を表示にした選択肢が `choices` として返り、並びは `labelColumn` の昇順（同じラベルは `valueColumn` の昇順）になる。ラベルが半角英数字のとき、3 種類の DB で並びが一致する。それ以外のラベルは各 DB の照合順序に従う。
- **AC1.1.2（直した）** Given ラベルが NULL の参照先の行があるとき、When 選択肢が返るとき、Then その行は並びの最後に置かれ、画面では値が表示される。`valueColumn` が NULL の行は選択肢に含まれない。NULL を最後に置く書き方の DB ごとの差は repository の層で閉じ、3 種類の DB で結合テストにより確かめる。
- **AC1.1.3（直した）** Given 更新の画面で、保存済みの参照の値が選択肢にあるとき、When 画面が表示されるとき、Then その選択肢が選ばれた状態で出る。保存済みの値が選択肢に無いとき（参照先の行が消えた、または 201 件以上）は、値そのものが表示され、ほかの項目の更新を妨げない（AC3.2.1）。
- **AC1.1.4（直した）** Given 参照先の読み取りが時間切れ・接続の失敗になったとき、When 作成・更新の画面の定義を取得するとき、Then 定義の取得**全体**が既存の業務データの読み取りと同じ誤り（503）で返り、画面はやり直しを促す。項目ごとの 503 にはしない（時間切れの後、その接続は壊れたとみなされ、後続の項目を同じ接続で読めないため。V）。JDBC の例外のメッセージが応答にもログにも出ない。
- **AC1.1.5（直した）** Given 1 つの画面に REFERENCE のカラムが 1・3・5 個あるとき、When 定義を取得するとき、Then 参照先の読み取りは、対象DB の読み取りの接続の借りる回数が 1 のまま順に行われる（REFERENCE が 1・3・5 個のどれでも、借りる回数は 1。結合テストで数える）。1 つの画面に置ける REFERENCE の数の上限と、全体の時間の上限（最悪で項目数×問い合わせの時間の上限かかるため。V）は、機能設計で決め、「後の段で決める点」に載せる。
- **AC1.1.6** Given 参照先の表が空のとき、When 定義を取得するとき、Then 選択肢は空で返り、誤りにならない。画面には「選べる候補がありません」が出る。NOT NULL の項目では、保存できない理由が分かる（US1.5）。
- **AC1.1.7** Given 選択肢の取得の途中のとき、When 画面に出るとき、Then 項目は読み込み中と分かる表示（`aria-busy`）で、入力できないことが伝わる。
- **AC1.1.8** Given ラベルが長い、または同じラベルが複数あるとき、When 選択肢が出るとき、Then 長い名前は折り返すか省略して全文を取れ、同じラベルは値を併記して見分けられる。
- **AC1.1.9** Given 参照先のスキーマ・テーブル・カラムの名前に大文字小文字が混ざる、または引用符を含むとき、さらに値のカラムが `BIGINT` の最大値・`DECIMAL` の桁の多い値・ラベルが NULL の行を含むとき、When 選択肢を読むとき、Then MySQL・MariaDB・PostgreSQL のすべてで結合テストにより正しく読める。件数の境界 199・200・201 を含める（AC1.2.1）。
- **AC1.1.10** Given 選択肢のラベル・値に `<script>`・`<img onerror>`・`"`・`'`・`javascript:` が含まれるとき、When `select`・`radio` に出るとき、Then 文字として出る（HTML として描かない、リンクの先にしない）。画面のテストで 1 組の fixture を AC2.2.9・AC2.3.3 と共有する。

### US1.2 参照先が多すぎるとき、ピッカーへ案内される 〔Must〕

P2 として、参照先の行が多すぎて選択肢にできないとき、その旨と次の手段が分かるようにしたい。それは、画面が重くなったり、一部だけ見えて誤った選択をしたりしないためである。

- **AC1.2.1（直した）** Given 参照先の行が 199・200 件のとき、When 定義を取得するとき、Then すべてが選択肢として返る。201 件のときは AC1.2.2 になる。3 種類の DB の結合テストで、この 3 点を確かめる。
- **AC1.2.2（直した）** Given 参照先の行が 201 件以上のとき、When 定義を取得するとき、Then 選択肢は返らず、その項目に「参照ピッカー（LOOKUP）を使うよう案内する誤り」が、固定した 1 つの `code` で付く。判定は 201 件目まで読んで行う。
- **AC1.2.3** Given 参照先が 201 件以上の項目があるとき、When 同じ画面のほかの項目を見るとき、Then ほかの項目は通常どおり表示され、フォーム全体の定義の取得は失敗にならない。
- **AC1.2.4（直した）** Given 参照先が 201 件以上の項目の保存済みの値があるとき、When 更新の画面を開くとき、Then その項目は入力できず、値そのもの（保存されている値）だけが表示される（見た目は AC1.3.3 と同じ）。表示する文言は権限不足とは別で、「候補が多いため検索して選んでください」が出る（AC1.3.6 と見分けられる。D）。その項目に LOOKUP が定義されていないカラムでは、行き場のない案内にならないよう、文言で管理者へ依頼するよう伝える。
- **AC1.2.5** Given 参照先が 10,000 件あるとき、When 選択肢を読むとき、Then 読む行は 201 件を超えない（取り出しの上限 `setMaxRows` または問い合わせの上限を置き、上限を超える行を内部で読まないことを、文の上限と取り出した行数のテストで確かめる。TP の (c)）。

### US1.3 参照先を読む権限が無いとき、入力不可で値だけ見える 〔Must〕

P2 として、参照先のテーブルを読む権限が無いとき、参照先のラベルを見せられない旨と、すでに入っている値は分かる状態にしたい。それは、権限を越えて情報が漏れないためである。なお、入力不可の項目を見るのは編集できる利用者（更新の画面を開ける人）に限るため、主語は P2 に絞る。P1 は一覧・詳細で関わる（US3.4。D）。

- **AC1.3.1** Given 利用者が参照先の表の主権限を欠く（NONE）とき、When REFERENCE のカラムを持つ表の作成・更新の画面の定義を取得するとき、Then 選択肢は返らず、その項目に「参照先を読む権限がありません」の印が付き、定義の取得は 403 にならない。
- **AC1.3.2（直した）** Given 参照先の `valueColumn` または `labelColumn` の主権限が NONE のとき（LOOKUP は `valueColumn` または `lookupList` のカラムのいずれかが NONE のとき）、When 定義を取得するとき、Then AC1.3.1 と同じ扱いになる。LOOKUP では、ピッカーそのものを提供しない（SL③）。
- **AC1.3.3** Given AC1.3.1 の項目があるとき、When 画面に表示されるとき、Then その項目は入力不可で、保存されている値そのものだけが表示される（参照先のラベルは出ない）。
- **AC1.3.4** Given LOOKUP のカラムで、参照先を読む権限を欠くとき、When 定義を取得するとき、Then 参照先の表の名前は載らず、AC1.3.1〜AC1.3.3 と同じ扱いになる。
- **AC1.3.5（直した）** Given 参照元の権限だけを持ち、参照先の権限を欠く利用者（他の権限は持つ）がいるとき、When 次の各応答を調べるとき、Then 参照先のラベルの文字列がどれにも含まれない。(1) 定義の取得、(2) 検索 API（ラベルの取得を含む）、(3) 作成・更新の誤りの応答、(4) 一覧、(5) 詳細。パラメーターを使う表で書く（サーバー側の判定。画面で隠すことを代わりにしない）。
- **AC1.3.6** Given 権限を欠いて入力不可になった項目があるとき、When 画面を見る・読み上げるとき、Then 項目名の近くに「参照先を読む権限がないため変更できません」の説明が文字で出て、入力欄は `aria-disabled` または `readonly` で支援技術に伝わる。灰色だけで示さない（色だけに頼らない。D）。
- **AC1.3.7** Given 入力不可の項目に保存済みの値が入っているとき、When キーボードで移動するとき、Then 値を読み上げで確かめられ（値を読めない `disabled` だけにしない）、フォーカスは項目に止まるか、説明に到達できる（D）。
- **AC1.3.8** Given 作業ロールを切り替えた直後、または参照先の権限の割り当てを変えた直後のとき、When 次の定義の取得を行うとき、Then 選択肢（ピッカーの情報）が出る・出ないが切り替わる（画面が持つ古い権限に頼らない。Q）。

### US1.4 参照先の読み取りが守られ、値が漏れない 〔Must〕

P3（佐藤さん）として、参照先の読み取りが、権限と上限で守られ、値がログなどに出ないことを確かめたい。それは、運用の説明として、権限どおりに効いていることを言えるためである。

- **AC1.4.1** Given 参照先のスキーマ・テーブル・カラムの名前が適用中の DSL に無いとき、When その名前で参照先を読もうとするとき、Then 読まれず、DSL にある名前だけが使われる。識別子は DSL と照らしてから引用し、値はバインド変数で渡す。
- **AC1.4.2（直した）** Given 参照先の読み取りが行われたとき、When アプリのログ（TRACE を有効にした `XxxSecretLeakIT`）・トレースの属性（外部へ送る設定を有効にした結合テスト）・エラー応答を調べるとき、Then 参照先の行の値・ラベル・主キーの値と、対象DB の接続情報が含まれない。確かめる経路は、定義の取得（選択肢）・検索・ラベルの取得・保存前の確かめの 4 つ。
- **AC1.4.3** Given 参照先の読み取りが時間の上限を超えたとき、When 誤りになるとき、Then JDBC の例外のメッセージが応答にもログにも出ない（SQLState・業者のエラーの番号・例外のクラスの名前だけ）。
- **AC1.4.4（直した）** Given 参照先が、複合の主キー・主キーの無いテーブル・ビュー・自己参照・`valueColumn` が一意でないテーブルのとき、When 選択肢を読む、またはピッカーで検索するとき、Then REFERENCE と LOOKUP の両方で、(1) 500 にならない、(2) 行の値がログに出ない、(3) 設計で決めた側の動作に固定される。決めた動作を明示したテストにする（TP の (h)。動作の確定は機能設計）。
- **AC1.4.5** Given 参照元と参照先の型が合わない（`INT` と `BIGINT`、数字の文字列と整数など）、または `labelColumn` が読めない型（バイナリ・巨大な文字列）のとき、When 選択肢・検索・保存前の確かめを行うとき、Then 動作は機能設計で決め（保存前の確かめは参照先の `valueColumn` の型で束ねる）、決めた動作を、3 種類の DB で明示したテストにする。PostgreSQL は型が合わない比較を拒み、MySQL は暗黙変換で通るため、DB ごとに結果が割れないことを確かめる（V）。
- **AC1.4.6** Given 新しい record（選択肢・検索の結果・ラベル・検索の条件）を層をまたいで渡すとき、When TRACE のログを調べるとき、Then `toString` を上書きして値が伏せられている。TRACE を有効にした `XxxSecretLeakIT` で確かめる（V、TP の Code Style）。
- **AC1.4.7** Given 既存の境界テスト（`TargetDbBoundaryArchitectureTest`・`RoleBoundaryArchitectureTest` など）と `backend/config/spotbugs-exclude.xml` があるとき、When 今回の変更の差分を見るとき、Then 足す方向だけで、緩めた行が無い。`prepareStatement`・`createStatement` を呼んでよい場所が増えていない。SQL を足すメソッドごとの `SQL_` の除外の追加と、新しい SQL のクラスを作ることは、コード生成の計画に明記され、依頼者に承認される（TP の (k)、V、Q）。

### US1.5 必須の参照項目に値を入れられないとき、理由が分かる 〔Must〕

P2 として、必須（NOT NULL）の参照項目で、参照先を読めない、または候補が 201 件以上のとき、行を作れない理由と次の手が分かるようにしたい。それは、入力できない項目の前で何が起きているか分からず、止まらないためである（M1: A）。

- **AC1.5.1** Given NOT NULL の REFERENCE の項目が入力不可（参照先を読めない、または 201 件以上）のとき、When 作成の画面を開くとき、Then 項目の近くに「必須の参照項目に値を入れられません」が出て、理由（権限がない／候補が多い）と、管理者へ権限またはピッカー（LOOKUP）への切り替えを頼むことが伝わる。送信の前に項目の誤りとして示される。
- **AC1.5.2** Given NOT NULL の REFERENCE の項目が AC1.5.1 の状態で、要求の本文にその項目の値が来たとき、When 作成するとき、Then 保存されず、409 `BUSINESS_REFERENCE_NOT_FOUND`（その項目の誤り）で拒否される（AC3.1.3 と同じ応答）。本文の値が空のときは、項目の誤りとして拒否される（既存の必須の誤りになるか 409 になるかは機能設計で確かめ、どちらかに固定したテストにする）。
- **AC1.5.3** Given LOOKUP のカラムが NOT NULL で、参照先を読む権限を欠くとき、When 作成するとき、Then AC1.5.1・AC1.5.2 と同じ扱いになる。LOOKUP は 201 件以上でも検索で選べるため、201 件以上による行き止まりは REFERENCE だけに起きる。
- **AC1.5.4** Given 更新の画面で、NOT NULL の参照項目が AC1.5.1 の状態で、保存済みの値があるとき、When ほかのカラムを更新するとき、Then 値が変わらないため更新は成功する（AC3.2.1）。

## 群2 参照ピッカー（LOOKUP）

### US2.1 参照先を検索し、値で 1 件引く API が権限で守られる 〔Must〕

P2 として、参照先の行を条件で検索し、選んだ値のラベルを引ける API が欲しい。P3 は、この API が権限のない人に使われないことを確かめる。それは、参照先のラベルが漏れないためである。

- **AC2.1.1** Given 検索の要求を受けたとき、When 入力を調べるとき、Then 入力は、参照元のカラムの指定と、`lookupSearch` の条件の値、ページだけである。参照先の表・カラムは適用中の DSL から決め、利用者の入力から直接は受け取らない。要求の本文に、許していない項目や参照先の表・カラムの名前を足しても無視され、結果は変わらない。
- **AC2.1.2** Given 権限を満たす利用者が検索するとき、When 結果が返るとき、Then 結果は `lookupList` のカラムと `valueColumn` だけで、`lookupList` の並び順に従い、1 ページ 20 件で返る。読めないカラム（NONE）は応答に含まれない。
- **AC2.1.3** Given 参照先の該当が 0 行・20 行ちょうど・21 行のとき、When 検索するとき、Then 0 行は空の結果、20 行は次のページ無し、21 行は 2 ページ目に 1 行になる。ページ番号が範囲外（0・負・最終ページより後・極端に大きい値）のときは、空の結果か `VALIDATION_FAILED` のどちらかに固定する（機能設計で決め、決めた側を明示したテストにする）。深いページでも、内部で読む行は、ページの先頭＋20 件を超えない（取り出しの上限を置き、読んだ行数をテストで確かめる。TP の (c)）。
- **AC2.1.4** Given 検索の条件の値がすべて空のとき、When 検索するとき、Then サーバーは検索を実行せず、`VALIDATION_FAILED` で拒否する（画面は AC2.2.5 のとおり入力を促す）。
- **AC2.1.5** Given 保存済みの値（`valueColumn` の値）を指定して、そのラベルを引く要求のとき、When 呼ぶとき、Then 権限を満たす利用者には、その 1 件の行のラベル（`lookupList` の先頭のカラムなど、ラベルに使うカラムは Contract Design で決める）が返る。権限は検索と同じ判定である。
- **AC2.1.6** Given 検索の値が 1,000 文字（Unicode のコードポイント）ちょうどのとき、When 検索するとき、Then 受け付けられる。1,001 文字のときは `VALIDATION_FAILED` になる（実装の上限は設計で確かめ、違えばそれに合わせる。FR2.6）。
- **AC2.1.7** Given 検索の値に `%`・`_`・`\`・引用符・`;`・`--`・改行が含まれるとき、When 部分一致で検索するとき、Then MySQL・MariaDB・PostgreSQL のすべてで、(1) `%` だけの検索が「`%` を文字として含む行」だけに一致し全件には一致しない、(2) `_` が 1 文字のワイルドカードにならない、(3) `\` が MySQL・MariaDB でエスケープの文字として働かない（PostgreSQL と同じ結果）、(4) SQL として解釈されない。演算子が完全一致のときは、エスケープの対象外であることも 1 件確かめる（TP の (e)）。
- **AC2.1.8** Given `lookupSearch` のカラムが主権限 NONE のとき、When 検索条件を作るとき、Then 画面はその条件を入力に出さず、サーバーもその条件を指定した要求を AC2.1.11 の同じ応答で拒否する（NONE の列で検索できると値の有無から内容を推測できるため）。使える条件が 1 つも残らないときは、ピッカーを提供しない（AC1.3.2 と同じ扱い）。応答の組み立ての部品は、防御として NONE のカラムを必ず落とす（到達しない経路だが、部品を直接呼ぶ単体テストで確かめる。Q の C-1）。
- **AC2.1.9** Given 検索の条件の列に、`lookupSearch` に無い列・DSL に無い列・主権限 NONE の列を指定した要求のとき、When 呼ぶとき、Then AC2.1.11 の同じ応答になり、参照先の読み取りは行われず、状態は変わらない（TP の (b) の「検索の列」）。
- **AC2.1.10** Given 認可の表（TP の (a)）を、パラメーターを使う表として書くとき、When 呼ぶとき、Then 未認証は 401、「要る権限だけを欠く利用者」（前提の (1)〜(4) を 1 人ずつ）は AC2.1.11 の同じ応答、停止中の利用者は権限があっても通らず、満たす利用者は 200 になる。
- **AC2.1.11（直した）** Given 権限が無い、参照元の指定が DSL に無い（表・カラム）、ラベルの取得で参照先の行が無い、のそれぞれの場合、When 呼ぶとき、Then 状態コード・`code`・構造・メッセージが同一になり、存在や権限を推測させない。値は Contract Design で決める（状態コードと `code` を 1 つ決めて、この基準に書き入れる）。権限を欠く場合を 403 と書き分けない（Q の C-2）。
- **AC2.1.12** Given 作業ロールを切り替えた直後・割り当てを変えた直後のとき、When 次の要求で検索するとき、Then 結果が 200 と同じ応答のあいだで切り替わる（画面が持つ古い権限に頼らない）。
- **AC2.1.13** Given 応答しない対象DB（テストの中で開いた `ServerSocket` で、受け付けて何も返さない方式）のとき、When 検索・ラベルの取得を行うとき、Then 503 の誤りで返り、JDBC の例外のメッセージが応答にもログにも出ない。`ReadPurpose` に足す目的ごとに 1 件（Q）。
- **AC2.1.14** Given 新しい API（検索・ラベルの取得）を足すとき、When 「API の分類の網羅」のテストを流すとき、Then 両方が「権限が要る」に明示して分類され、分類の無い API があれば落ちる（TP。V）。
- **AC2.1.15** Given 検索の値とラベルを引く値を運ぶとき、When 要求の形を見るとき、Then 値は要求の本文で運ばれ、道（URL のパス・クエリ）に載らない。トレースの道の属性に値が残らないことを、外部へ送る設定を有効にした結合テストで確かめる（TP の (d)）。
- **AC2.1.16** Given 検索を MySQL・MariaDB・PostgreSQL で行うとき、When 識別子の大文字小文字・引用符を含む名前・NULL の並び・境界の値（`BIGINT` の最大値・桁の多い `DECIMAL`）を含む結合テストを流すとき、Then すべての DB で正しく動く（TP の (i)）。並びを確かめる値は半角英数字にする。

### US2.2 検索ダイアログで参照先を探して選ぶ 〔Must〕

P2 として、参照先が多いときに、検索のダイアログで条件を入れて探し、1 行を選んで値にしたい。それは、候補が多くても目的の行にたどり着くためである。

- **AC2.2.1** Given LOOKUP のカラムを持つ表の作成・更新の画面を、参照先を読める利用者が開いたとき、When ダイアログを開くとき、Then 検索の条件（`lookupSearch` のカラムと演算子）の入力が出て、検索するまで一覧は出ない（条件の入力を促す）。
- **AC2.2.2** Given 条件を入れて検索したとき、When 結果が返るとき、Then `lookupList` のカラムと並び順で、1 ページ 20 件の一覧が出る。ページ送りができ、現在のページと総ページの状態が読み上げられ、ページ送りの文言は日本語と英語で出る（D）。
- **AC2.2.3** Given 一覧の 1 行を選んだとき、When 選ぶとき、Then ダイアログが閉じて値が入力欄に入り、選んだ行のラベルが入力欄の隣に表示される。選べるのは 1 行だけで、各行は 1 行ずつ操作の対象（ボタンなど）になる。
- **AC2.2.4** Given 検索の結果が 0 件のとき、When 結果が返るとき、Then 「該当する行がありません」が出る。初期の状態（AC2.2.1）や、条件が空の促し（AC2.2.5）の文言と混ざらない。
- **AC2.2.5** Given 条件がすべて空のまま検索を押したとき、When 実行するとき、Then 要求は送られず、条件の入力を促す文言が出る（0 件の文言と混ぜない）。
- **AC2.2.6** Given 検索中のとき、When 結果を待つとき、Then 「検索中」が出て、検索ボタンの二重押しが防がれる。検索の失敗（503・時間切れ）は、条件を保ったまま「再度検索」を促す。
- **AC2.2.7** Given 選択済みのラベルが入力欄の隣にあるとき、When 値を変えたい・消したいとき、Then 再度ダイアログを開く操作があり、NULL を許す項目では値を消す操作がある。
- **AC2.2.8** Given ダイアログを「閉じる」・Esc・選ばずに戻るで閉じたとき、When 閉じるとき、Then 入力欄の値は変わらない。背景のクリックで閉じるかは Refined Mockups で決める（D。前の Intent の確かめる表示は閉じない）。
- **AC2.2.9** Given 一覧の行・ラベルに `<script>`・`<img onerror>`・`"`・`'`・`javascript:` が含まれるとき、When ダイアログの一覧と入力欄の隣に出るとき、Then 文字として出る（HTML として描かない、リンクの先にしない。TP の (f)）。
- **AC2.2.10** Given 長い名前の行があるとき、When 一覧に出るとき、Then 折り返すか省略して全文を取れる。
- **AC2.2.11** Given 画面の誤りを表示するとき、When 文言を見るとき、Then 業務の言葉と該当の項目で伝え、DB の制約の文や内部の語は出ない（P2 の慣れの水準。D）。

### US2.3 選んだ値のラベルが分かる 〔Must〕

P2 として、更新の画面で、すでに入っている参照の値のラベルを見たい。それは、ID だけでは何を指しているか分からないためである。

- **AC2.3.1** Given 保存済みの LOOKUP の値があるとき、When 更新の画面を開くとき、Then AC2.1.5 の 1 件読みでラベルが引かれ、入力欄の隣に表示される。
- **AC2.3.2** Given 参照先の行が無い、または読めないとき、When 更新の画面を開くとき、Then ラベルは出ず、値だけが表示される（両者を区別しない）。更新自体は妨げられない。
- **AC2.3.3** Given ラベルに `<script>`・引用符・`javascript:` が含まれるとき、When 入力欄の隣に出るとき、Then 文字として出る。
- **AC2.3.4** Given 一覧・詳細の画面を開くとき、When 表示されるとき、Then ラベルの 1 件読みは行われない（US3.4）。

### US2.4 ピッカーをキーボード・読み上げで使える 〔Must〕

P2 として、キーボードだけ・読み上げでも、ピッカーを開いて検索して選べるようにしたい。それは、マウスを使えない人も同じ操作ができるためである。

- **AC2.4.1** Given キーボードだけで操作するとき、When ダイアログを開く・条件を入れる・検索する・行を選ぶ・閉じるとき、Then すべてキーボードだけでできる。部品が make-you-chic-ui のものでないときは、キーボード操作と `aria` の属性を画面のテストで確かめる。
- **AC2.4.2** Given ダイアログを開いたとき、When フォーカスを見るとき、Then フォーカスはダイアログの中に入り、閉じたら開いた項目に戻る。
- **AC2.4.3** Given ダイアログを開いたとき、When 見出し・検索結果の件数・行の選択を読み上げるとき、Then ダイアログに名前（見出し）があり、結果の件数の変化が `aria-live` で伝わり、選択の行は 1 行ずつ操作の対象になる（D）。
- **AC2.4.4（直した）** Given 画面の検査（axe）を、ピッカーを開いた状態・結果の一覧が出た状態・0 件の状態・誤りを出した状態（検索の失敗・入力不可）・長い名前（100 文字以上、`<` を含む）・2 語以上の現実に近いデータで、ブランドカラーとテーマのすべての組について行うとき、When 検査するとき、Then 違反が 0 件である。検査の規則を外さない（PM の Forbidden）。
- **AC2.4.5** Given 狭い幅（375px）のとき、When ダイアログと表を開くとき、Then 横の画面全体のスクロールが出ず、ダイアログが画面に収まる（PM）。
- **AC2.4.6** Given 画面の言語が日本語か英語のとき、When ダイアログと誤りを表示するとき、Then 文言が選んだ言語で出る（既定は日本語。前提の 6 つの文言を含む）。

### US2.5 参照ピッカーの代表の流れを画面から通せる 〔Must〕

P2 として、参照ピッカーで探して選び、保存して、更新の画面で確かめるまでの流れが通ることを確かめたい。それは、部品の組み合わせが実際の画面で崩れないためである。E2E の代表の流れ 1 本とする（TP）。

- **AC2.5.1** Given 自作のロール（参照元の表が FULL、参照先の表が READ）と自作の利用者でログインしたとき、When 参照元の表の作成の画面で、LOOKUP の項目のピッカーをキーボードで開き、条件を入れて検索し、キーボードで行を選び、入力欄の隣のラベルを確かめ、保存し、更新の画面を開くとき、Then 更新の画面でも同じラベルが出る。同じ画面の REFERENCE の選択肢が出ることを、流れの中で 1 手確かめる（本数は増やさない。Q）。
- **AC2.5.2** Given この流れの前提のとき、When 準備するとき、Then 利用者・役割・専用のスキーマの参照先と参照元の表と行（架空の値）をすべて自作し、初期管理者・見本の行・見本の DSL を変えない。DSL の適用し直しは流れに入れない（適用中の DSL は全 E2E で共有されるため。Q。DSL への足し方は設計で決める）。
- **AC2.5.3** Given 資格情報を渡すとき、When 報告の json を文字列で検索するとき、Then 資格情報・接続先・トークンの値が入っていない（資格情報は `webServer.env` に置かず、プロセスの環境変数で渡す。TP）。
- **AC2.5.4** Given 権限を欠く利用者の確かめのとき、When 確かめる場所を見るとき、Then E2E ではなく結合テストで行う。画面のテストで「入力不可・値だけ表示・理由の表示」を 1 件持つ（AC1.3.3・AC1.3.6）。見本の対象DB（PostgreSQL の 1 種類）が動いていることを前提に、届かなければ始める前に失敗する。i18next 系の更新と既存の E2E の書き換えは本数に数えない（TP）。

## 群3 保存前の確かめと横断の確かめ

### US3.1 作成・更新の保存前に、参照先の存在と権限を確かめる 〔Must〕

P2 として、参照先に無い値や、権限のない参照先の値を入れたとき、保存の前に誤りを知りたい。それは、打ち間違いや値の差し替えで、おかしな参照が保存されないためである。

- **AC3.1.1** Given REFERENCE・LOOKUP のカラムに、存在する参照先の値を入れ、その利用者が参照先を読めるとき、When 作成・更新するとき、Then 保存される。
- **AC3.1.2** Given 参照先に存在しない値のとき、When 作成・更新するとき、Then 保存されず、409 `BUSINESS_REFERENCE_NOT_FOUND`（その項目の誤り）で返る。
- **AC3.1.3（直した）** Given 参照先の行はあるが、その利用者が参照先を読めないとき、When 作成・更新するとき、Then AC3.1.2 と同じ応答で返る（存在しない値と権限の無い値の 2 つの要求で、状態コード・`code`・項目の誤りの構造・メッセージが同一）。応答で区別できない。
- **AC3.1.4（直した）** Given 要求の本文の参照の値を、権限のない参照先の行を指す値に差し替えたとき、または本文に許していないカラム・参照先の表の名前を足したとき、When 送るとき、Then 保存されず、AC3.1.3 と同じ応答になる。足した名前は反映されない（IDOR・一括代入の防止。TP の (g)）。
- **AC3.1.5（直した）** Given 参照のカラムが NULL を許し、値が空のとき、When 作成・更新するとき、Then 確かめずに保存される。空文字列 `""` と NULL の扱い（数値型の参照で `""`）は、既存の業務データの作成・更新の扱いに合わせる。NOT NULL のカラムで参照先を読めない（または 201 件以上）ときの作成は、AC1.5.2 のとおり拒否される（M1: A で閉じた）。
- **AC3.1.6（直した）** Given 確かめた後で、保存の前に参照先の行が別の接続で消されたとき（待ち合わせで確実に作る）、When 保存するとき、Then 対象DB の外部キー違反が、同じ 409 の誤りに変換される。MySQL・MariaDB・PostgreSQL のすべてで確かめる。外部キーを持たない対象DB のカラムでは、この最後の守りが働かず、宙に浮いた参照が保存されうる。これは既知の制約として扱う（V・Q）。
- **AC3.1.7** Given 参照の誤り（409）が画面に出るとき、When 表示されるとき、Then その項目の近くに誤りが出て、フォーカスがその項目に移り、誤りは `aria-describedby` で結ばれる。存在しないのか権限がないのかは文言で区別しない（D）。
- **AC3.1.8** Given 保存前の確かめの読み取りが時間切れ・接続の失敗になったとき、When 作成・更新するとき、Then 503 で返り、保存されていない。誤りの本文とログに JDBC の例外のメッセージが出ない（Q）。

### US3.2 値が変わった参照だけを確かめる 〔Must〕

P2 として、参照先を読めない参照を持つ行でも、ほかの項目を更新したい。それは、参照先の権限が無いだけで、無関係な更新まで失敗しないためである。

- **AC3.2.1** Given 参照先を読めない利用者が、その参照を持つ行の、ほかのカラムを更新するとき、When 保存するとき、Then 更新は成功する（参照の値は変わらないため確かめない）。
- **AC3.2.2** Given 更新の本文に、入力不可の参照の項目が（変わらない値で）含まれていたとき、When 保存するとき、Then その項目は確かめられず、更新は成功する。
- **AC3.2.3** Given 参照の値が変わった更新のとき、When 保存するとき、Then 変わった参照だけが AC3.1.1〜AC3.1.4 のとおり確かめられる。
- **AC3.2.4** Given 更新前の値と本文の値を比べるとき、When 型に直した値（`TypedValue`）で正規化して比べるとき、Then 等しい・先頭ゼロ（`"007"` と `"7"`）・桁違い（`1.0` と `1`）の境界で、判定が決まる。大文字小文字の違いなど、照合順序で同じとみなされる値は「変わった」扱いで確かめに回り、安全側に倒れる（単体テスト。V・Q）。
- **AC3.2.5** Given 保存済みの参照がすでに宙に浮いている行のとき、When ほかのカラムを更新するとき、Then 成功する（確かめない）。同じ行で参照の値を別の存在しない値へ変えると 409 になる。各 1 件。
- **AC3.2.6** Given 更新前の行が無い（`ROW_NOT_FOUND`）とき、When 更新するとき、Then 参照の拒否より先に、既存の「行が無い」の応答になる（行の有無を参照の拒否で漏らさない。V）。
- **AC3.2.7** Given 更新で、更新前の行の読み取りと参照先の存在の確認を行うとき、When 対象DB の接続を数えるとき、Then 同じ読み取りの接続 1 本の中で順に行われ、書き込みの接続は確認が済んでから借りる。内部DB・対象DB の接続を持ったまま待たない。

### US3.3 拒否が監査に残り、確かめの読み取りは残らない 〔Must〕

P3 として、参照先の確かめで拒否された操作を、監査で追いたい。それは、権限の差し替えの試みなどを後から調べられるためである。

- **AC3.3.1** Given 保存前の確かめで拒否されたとき、When 監査の記録を見るとき、Then 既存の理由 `REFERENCE_NOT_FOUND` で、操作した人・対象・結果が残る。
- **AC3.3.2** Given 監査の行を調べるとき、When 見るとき、Then 参照先の行の値が含まれない。
- **AC3.3.3** Given 確かめのための参照先の読み取りが行われたとき、When 監査の記録を見るとき、Then その読み取りは残らない（読み取りは監査の対象外の決まりのまま）。

### US3.4 一覧・詳細は今のとおり値を出し、参照先を読まない 〔Must〕

P1（田中さん）として、一覧と詳細の画面が、今回の変更で変わらないことを確かめたい。それは、参照している値をラベルで見せるのを今回はやらない（範囲の外）ためである。

- **AC3.4.1** Given 参照のカラムを持つ表の一覧・詳細を開いたとき、When 表示されるとき、Then 参照している値は、今のとおり値（ID）のまま出る。
- **AC3.4.2** Given 一覧・詳細の画面の定義を取得するとき、When 参照先への問い合わせを数えるとき、Then 参照先は読まれない（選択肢の読み取りは、作成・更新の画面の定義のときだけ行う。V）。
- **AC3.4.3（直した）** Given 定義の応答に参照の情報の欄が足されたとき、When 新しい欄を含む定義の応答の fixture を既存の一覧・詳細・作成・更新の画面のテストに流すとき、Then 既存のテストがすべて通る（読み落としても壊れない）。
- **AC3.4.4** Given DSL の書式の版と内部DB のスキーマ（移行ファイル）があるとき、When 今回の変更の差分を見るとき、Then `backend/src/main/resources` の移行ファイルと DSL の JSON Schema に差が無い（NFR7。Q）。
- **AC3.4.5** Given 参照の項目が入力不可・案内つきになったとき、When 一覧・詳細を開くとき、Then 一覧・詳細の表示と操作は変わらない（入力不可の見た目が一覧・詳細に漏れない。D）。

### US3.5 参照先の読み取りが接続と時間を使いすぎない（横断の確かめ） 〔Must〕

P4（高橋さん）として、選択肢・検索・保存前の確かめが、対象DB の接続と時間を使いすぎないことを確かめたい。それは、負荷の下でも接続が尽きないためである。このストーリーは利用者の画面の体験ではなく運用の質を確かめる横断の確かめで、群1〜群3 のほかのストーリーと一緒に確かめる（D）。

- **AC3.5.1（直した）** Given 選択肢の読み取り・ピッカーの検索・保存前の確かめを行うとき、When `*ConnectionUsageIT` と同じ形の結合テストで、1 要求で使う対象DB の読み取りの接続の借りる回数を数えるとき、Then REFERENCE が 1・3・5 個の画面でも 1、検索（件数とページの 2 文）でも 1、複数の参照を持つ保存前の確かめでも読み取り 1 である（書き込みの接続は別）。
- **AC3.5.2（直した）** Given 応答しない対象DB（`ServerSocket` の方式）のとき、When 待っているあいだに内部DB の使用中の接続を数えるとき、Then 0 である（内部DB の接続を持ったまま対象DB を待たない）。
- **AC3.5.3** Given `ReadPurpose` に足す新しい目的（選択肢・検索・ラベル・保存前の確かめ）があるとき、When 時間の上限を調べるとき、Then 目的ごとに時間の上限が付き、応答しない対象DB で 503（保存前の確かめは「保存されていない」）になり、JDBC の例外のメッセージが出ない。確かめは AC1.1.4・AC2.1.13・AC3.1.8 の各 1 件。
- **AC3.5.4（直した）** Given 負荷の試験で測るとき、When `iteration_duration` の p95 を見るとき、Then 既存の業務データの読み取りの線（p95 が 1,000 ms 未満、部分一致を使う検索だけ 3,000 ms 未満）を目標とする。場面は 3 つ（(1) 参照先がちょうど 200 件の定義の取得、(2) ピッカーの部分一致の検索、(3) 保存前の確かめつきの作成）で、1 回の繰り返しは要求 1 つにし、3 種類の DB で測る。参照先の行数と種は NFR 要件で決め、負荷の台本で種から作る。接続プールが尽きる形の場面（上限を下げた場面）を置くかは NFR 設計で決め、置かないときは `*ConnectionUsageIT` で代える理由を書く。測るまでは Unverified とし、持ち主は Performance Validation にする。物差しは変えない。
- **AC3.5.5** Given カバレッジを測るとき、When 行と分岐を見るとき、Then 全体と新しく作るパッケージごとに行 80% 以上・分岐 70% 以上である。手を入れる `packagesJudgedByTotal` のパッケージ（`common.web` ほか、実際に手を入れるもの）は、テストを足して一覧から外す。実測は Delivery Planning・コード生成の計画で行う（`:backend:cleanTest :backend:cleanIntegrationTest` を付ける。PM）。

## 群4 持ち越しの片付け

### US4.1 k6 の結果の JWT が自動で伏せられる 〔Must〕

P4 として、k6 の結果に入る JWT を、記録に置く前に自動で伏せたい。それは、手で置換する漏れで、秘密が公開側に残らないためである。

- **AC4.1.1（直した）** Given k6 の summary json に JWT が入っているとき、When 記録に置く前の処理を通すとき、Then JWT がすべて `[REDACTED-JWT]` に置換される。JWT の形は `eyJ` で始まる base64url の 3 区間（`.` 区切り）とする。境界: 2 区間は置換しない。`eyJ` の前が英数字の文字列は置換しない。同じ文字列に複数あれば全部置換する。JSON の値・配列の要素・オブジェクトのキー名（k6 のタグ名に入りうる）・数 MB の長い文字列のどこにあっても置換する。`Bearer eyJ…` は JWT の部分だけを置換する（Q）。キー名の置換で、JWT だけが違う 2 つのキーが同じキーになる（衝突する）ときは、片方を消さず、失敗にして記録（`evidence/`）に置かない（構造を保つ。AC4.1.5 の (4) と両立させる。R-05）。
- **AC4.1.2（直した）** Given 置換の後の残存の検査（置換とは独立の関数）があるとき、When JWT の形を含む入力を渡すとき、Then 検査が検出して非 0 で終わる。
- **AC4.1.3（直した）** Given 残存の検査が失敗したとき、When 処理が終わるとき、Then `evidence/` にファイルが作られず、一時ファイルも残らない。
- **AC4.1.4** Given 入力が JSON でない、または空のとき、When 処理を通すとき、Then 失敗し、ファイルを置かない。
- **AC4.1.5（直した）** Given 仕組みのテストを性質ベースで書くとき、When ランダムな入力で確かめるとき、Then (1) 置換の後に JWT の形が無い、(2) 冪等（`f(f(x)) == f(x)`。`[REDACTED-JWT]` 自体が JWT の形に一致しない）、(3) JWT を含まない入力は変わらない（数値・場面名・真偽・null・入れ子・長い文字列）、(4) 出力は JSON として解析でき、構造（キーと型）が入力と同じ、が成り立つ。失敗時の乱数の種を記録する。ランダムな入力に、JWT に近い文字列（2 区間・`eyJ` の前に英数字・末尾の `=`）を混ぜる（TP、Q）。
- **AC4.1.6（直した）** Given 仕組みのテストがあるとき、When `./gradlew verify` と CI を流すとき、Then テストが実行され（スキップされない）、通る。`evidence/` に置くファイルに `gitleaks dir` を流して 0 件である。
- **AC4.1.7** Given 記録を `evidence/` に置く手順があるとき、When 手順を見るとき、Then 仕組みを通すスクリプトが唯一の入口で、手置きで抜けない（NFR8）。`evidence/` 以下の既存のファイルに JWT の形が無いことを確かめる検査が、`verify` か CI の段に置かれている。
- **AC4.1.8（直した）** Given `perf/README.md` を読むとき、When 手順を探すとき、Then 伏せる対象（summary json）と、対象外（k6 の標準出力とログ）が書かれ、対象外はどのコマンドで伏せるかの手順まで書かれている。
- **AC4.1.9** Given リフレッシュトークンと Authorization ヘッダーの値が summary json に入るかを設計で確かめるとき、When 結果を記録するとき、Then 入らないことを台本が書き出す項目の確認で裏付けて記録する。入ると分かったときは、置換の対象を広げるかを依頼者に諮る（M2: B。形による置換は JWT だけで、キー名による伏せ字は今回行わない）。

- **NFR 要件・NFR 設計**: 性能の測り方、参照先の行数、上限を下げた場面を置くか（AC3.5.4）。

## INVEST の確かめ

- **独立**: 群4 は群1〜群3 と独立。群1〜群3 は、権限と行を用意すれば単独で確かめられる。US3.4・US3.5 は横断で、ほかのストーリーと一緒に確かめる。
- **交渉可能**: 部品の有無に依らない振る舞いで書いた。文言の置き場・ダイアログの閉じ方は Refined Mockups で決める。
- **価値**: どのストーリーも P1〜P4 のいずれかの目的に結び付く。US3.5 は利用者の画面の体験ではなく運用の質で、P4 の目的に結び付ける。
- **見積もり**: 大きいのは US2.1（受け入れ基準 16）。サーバー側の検索（AC2.1.1〜AC2.1.9）と、認可・応答・分類・漏えいの確かめ（AC2.1.10〜AC2.1.16）の 2 つの Bolt に分ける余地がある。US1.3（8）と US3.5（5）は、Delivery Planning で Bolt に分ける材料として切れ目の案を置いた。
- **小ささ**: 初稿の US2.1 は分けた（検索 API とダイアログ）。必須の参照項目の行き止まりは、US1.5 として独立させた。
- **テストできる**: すべての受け入れ基準を Given/When/Then で書き、状態コードや件数の境界（199・200・201・20・21・1,000・1,001）を決めた。「設計で決める」と書いた基準は、決めた側の動作を明示したテストにする。
