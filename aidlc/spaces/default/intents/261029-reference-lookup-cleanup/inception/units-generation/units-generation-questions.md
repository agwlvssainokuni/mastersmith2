# Units Generation — 質問（Intent 261029-reference-lookup-cleanup）

承認済みの部品（`inception/domain-design/components.md`）・要件・ストーリー（US1.1〜US4.3 の 18 本）をもとに、作業の単位（Unit）の分け方を決めます。ここで決めるのは、単位の境界・種類・依存の向き（つなぎ方）だけです。作る順や Bolt の切り方は、次の Delivery Planning で決めます。判断が分かれる点だけを尋ねます。

## 決まっていること（質問しません）

- 単位の種類は、`service`（API を持つ処理）・`ui`（画面）・`library`（単独では動かない部品）・`packaging`（ビルドや配備の成果物・設定・文書）から選ぶ。内部DB のスキーマと DSL の書式は変えないため、`spec` の単位は無い。
- 配備の形は、これまでと同じく 1 つの実行可能 WAR（フロントエンドの `dist` を同梱）に全部入る。単位は独立して配備しない。統合は `develop` へ、単位または Bolt ごとの短命のブランチから行う（`team.md`）。
- Dependabot の #81・#82 の取り込み（FR8）は、決まりが `team.md` にあるためストーリーにせず、`traceability.json` で N/A とする（ストーリーの Q5: A）。どの単位にも入れない。
- 単位の依存は、「その単位のコードやテストが、別の単位のコードを要る」場合にだけ張る。作る順の選び方（経済的な優先）は Delivery Planning に回す。
- 部品との対応（Domain Design より）: ReferenceLookup・RowSqlGateway の変更・TargetDb の変更・BusinessData の変更・AuditLog は参照の読み書きの本体（サーバー側）、ApiClient・BusinessDataScreens は画面、PerfEvidenceRedactor は JWT の伏せ字の部品。コンテナの版そろえと perf の文書の整理は部品ではなく、設定・文書の作業。

## Q1. [設計] 単位の境界を、何の切り方にするか
参照の機能は、サーバー側（選択肢・ピッカーの検索・ラベル・保存前の確かめ）と画面（選択肢の部品・ピッカーのダイアログ）にまたがり、持ち越しの片付け（JWT の伏せ字・コンテナ・perf の文書）は、それとは別の作業です。

A. 機能のまとまりで 5 つに分ける。U1 参照の読み取り（サーバー: 選択肢・ピッカーの検索・ラベル、US1.1〜US1.4・US2.1・US2.3 のサーバー側・US3.4）、U2 保存前の確かめ（サーバー: US3.1〜US3.3・US1.5 のサーバー側）、U3 参照の画面（US1.1・US1.3・US1.5・US2.2〜US2.5 の画面側）、U4 JWT の伏せ字（US4.1）、U5 コンテナの版そろえと perf の文書の整理（US4.2・US4.3）。単位ごとに確かめやすく、U1 と U2 を別の Bolt に切れる。代わりに、単位が 5 つになり、横断のストーリー（US3.4・US3.5）の持ち主を決める必要がある
B. 層で 4 つに分ける。サーバー側の参照の読み取りと保存前の確かめを 1 つの単位（U1）にまとめ、U2 画面、U3 JWT の伏せ字、U4 コンテナと perf の文書。単位が少なく境界の契約も減るが、U1 が大きく（XL）なり、Delivery Planning で Bolt に分ける必要がある
C. ストーリーの群のとおり 4 つに分ける（群1 の選択肢、群2 のピッカー、群3 の保存前の確かめ、群4 の持ち越し）。ストーリーとの対応は分かりやすいが、群1 と群2 はサーバー側の読み取りの部品（ReferenceLookup）を共有するため、単位の間で同じ部品を取り合う

## Q2. [設計] 画面（参照の部品）を、どの単位と組にするか
参照の画面は、REFERENCE の選択肢の部品（`ReferenceSelectField`・`ReadonlyReferenceField`）と、LOOKUP のピッカー（`LookupField`・`LookupPickerDialog`）に分かれます。どちらも、サーバー側の API（定義・検索・ラベル・保存）の形に頼ります。Q1 で A を選んだ場合の話です（B・C のときは読み替えます）。

A. 画面は 1 つの単位（U3、種類 `ui`）にし、U1・U2 の両方に依存させる。画面の流れ（代表の E2E 1 本を含む）が 1 か所に集まり、保存の確かめ（U2）まで通した形で E2E を書ける
B. 画面を 2 つに分ける。U3 は REFERENCE の選択肢の部品だけ（U1 に依存）、U4 は LOOKUP のピッカーと E2E（U1・U2 に依存）。REFERENCE だけを先に出せるが、単位が 6 つになり、画面の API の呼び出し（ApiClient）を 2 つの単位で分け合う

## Q3. [品質] 横断のストーリー（US3.4・US3.5）と、性能の場面（k6）の持ち主
US3.4（一覧・詳細は今のとおりで、参照先を読まない）と US3.5（接続の数・時間の上限・性能の目標・カバレッジ）は、読み取りと保存前の確かめの両方にかかる横断のストーリーです。US3.5 の性能の確かめ（AC3.5.4）には、k6 の新しい場面が要ります。

A. US3.4・US3.5 の主の持ち主は U1（サーバーの読み取り）とし、U2・U3 が受け持つ受け入れ基準は、それぞれの単位で「部分」と書いて持つ。k6 の新しい場面（選択肢・ピッカーの検索）は、U1 のコード生成では書かず、Build and Test で書いて流す（`project.md` の決まり: Performance Validation の段が無いときは Build and Test）。横断の確かめの責任が U1 に集まる
B. 横断のストーリーを、専用の単位（U6、種類 `library` か `packaging`）にして、U1〜U3 が終わった後の確かめ（接続の数・時間・性能・カバレッジの実測）をまとめて持たせる。確かめの責任ははっきりするが、実装の無い単位が増える

## Q4. [運用] 持ち越しの片付け（群4）を、どの単位にまとめるか
US4.1（JWT の伏せ字）は `perf/` に Node のファイルを置き、`frontend/` の Vitest・fast-check から確かめる、コードとして書く部品です（ADR-004）。US4.2（コンテナの版そろえ）は設定と作業の確認、US4.3（perf の文書と台本の整理）は文書と `perf/k6/scenarios.js` の整理です。US4.1 と US4.3 は、どちらも `perf/` を触ります。

A. U4（JWT の伏せ字、種類 `library`）と U5（コンテナの版そろえと perf の文書の整理、種類 `packaging`）の 2 つに分ける。コードの部品と、設定・文書の作業が混ざらない。U4 と U5 が同じ `perf/README.md` を触るため、U5 は U4 に依存させ（U4 が書く伏せ字の手順の節を、U5 が整理した README に収める）、順を固定する
B. US4.1・US4.2・US4.3 をすべて 1 つの単位（種類 `packaging`）にまとめる。単位が減り、`perf/` の変更が 1 か所にそろう。代わりに、コードの部品（テストあり）と、設定・文書の作業が 1 つの単位に混ざる
C. 3 つに分ける。U4 JWT の伏せ字、U5 コンテナの版そろえ、U6 perf の文書の整理。単位は小さくなるが、単位が増え、US4.3 の整理は U4 の README の追記と、Build and Test の k6 の場面の追加の前後で衝突しうる

## Q5. [進行] 画面の単位と、サーバーの単位のつなぎ方（並行の度合い）
画面の単位（U3）は、サーバーの API の形（U1・U2）に頼ります。API の形は Contract Design で先に決まるため、画面の単位は、サーバー側のコードがまだ無くても、API の模擬（モック）で単独のテストが通せます。

A. 依存は、コードとテストが実際に要る向きだけにする。U3 は U1・U2 に依存する（E2E と、保存の確かめを通す画面のテストは、本物のサーバーを要る）。U4・U5 はほかの単位に依存しない（U5 は Q4 の A のとき U4 に依存）。並行できる単位は、依存の無いものだけ
B. 画面（U3）は API の形（契約）にだけ頼ると決め、U1・U2 のコードには依存させず、並行して作れるようにする。E2E だけを最後の確かめ（Build and Test）に置く。並行できるが、画面の単位の中で本物のサーバーに通す確かめができず、つなぎ目の不具合が後の段まで見つからない
