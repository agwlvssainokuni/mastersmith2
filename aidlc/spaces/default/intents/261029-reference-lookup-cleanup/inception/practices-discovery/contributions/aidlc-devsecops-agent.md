### 1. 既存の決まりで賄えるもの（新しい決まりを足さない）
- lint/format（Prettier・oxlint・ESLint・Stylelint・Spotless）、ライセンスヘッダー、Gitleaks の pre-commit と CI、OSV-Scanner、`ignore-scripts=true`、ダイジェスト固定は、今回の Intent の範囲（フロントの i18next 系の版上げ、参照ピッカー、perf 文書、コンテナの版そろえ）にそのまま当たる。新しいツールも設定も要らない。
- Dependabot #81・#82（i18next 26.5.10→26.5.11、react-i18next 17.1.8→17.1.9）は、手元で版と lockfile を更新し `./gradlew verify` で統合、PR を閉じる、で足りる。ただし取り込む前に `frontend/package-lock.json` の前後の差で `hasInstallScript` の付いた項目が増えていないかを読み取りで確かめて記録する（`frontend/.npmrc` の `ignore-scripts=true` が守るため必須ではないが、patch の2件でも推移依存は動きうる）。i18next 系を `ignore` に足す必要は無い。

### 2. 参照先テーブルの権限（IDOR・列挙）: 初稿 Q1 は「要件定義で決める」が正しいが、固い制約の候補を先に挙げる
- 参照の選択肢・ピッカーの読み取りは、新しい読み取り口になる。権限の論点（参照先の主権限が読めない利用者に選択肢を返さない、参照先のカラムの主権限が NONE のカラムをラベル・値に使わせない、参照先テーブルが DSL に無い・権限が無い・存在しないときの応答の状態コードと code をそろえて存在を推測させない）は、既存の Mandated（API ごとのサーバー側判定、NONE カラムを応答に含めない）の適用で足りるが、要件定義で「403 と 404 のそろえ方（列挙の防止）」と「参照先の権限は作業ロールの権限の写し（PermissionSnapshot）で判定する」を明示して決める。
- 抜けとして、参照元のテーブルの権限だけで参照先を読めてしまう（参照元に READ があれば参照先のラベルが漏れる）経路が最も危ない。必須テストの案 (a) に「参照元の権限だけを持ち参照先の権限を欠く利用者」を明記する（403 を確かめる利用者は要る権限だけを欠く利用者、の既存の決まりと同じ形）。
- 書き込み側にも抜けがある。作成・更新で参照の値を送るとき、サーバー側で参照先に実在するか・利用者がその参照先を読めるかを確かめないと、見えない参照先の存在を外部キー違反の応答の差で推測できる。外部キー違反の応答は参照先の存在を漏らさない同じ形（既存の「DB の制約の違反も同じ誤りに直す」と同じ扱い）にする点を要件で決める。
- 初稿の案 (a)〜(f) に追加を勧める: (g) 検索のキーワードと選択肢の件数の上限（列挙の抑止。件数は設計の段で決め、境界で確かめる）、(h) 参照先の識別子（table・valueColumn・labelColumn）は DSL 読み込み時だけでなく読み出しのたびに適用中の DSL と照らす（DSL の差し替えをまたぐ古い名前の拒否）、(i) 参照の値を道・問い合わせの文字列に載せない（主キーの値を道に載せない既存の決まり。選択肢の取り出しは本文で運ぶ）。

### 3. SAST（SpotBugs の `SQL_`）
- 初稿の案 (SQL の部品を1つに閉じる) のとおり。参照先の読み取りが既存の部品（DB の種類ごとのクラス）の中に収まるなら、`backend/config/spotbugs-exclude.xml` の除外は足さない。新しい SQL の口が要るときは、クラスの名前・メソッドの名前・パターン名の3つで絞り、コード生成の計画に明記して承認を得る（既存の決まり）。ArchUnit の `prepareStatement`・`createStatement` の許可場所も同じ扱い。
- 参照のラベル列・値列は識別子として引用する。ラベルを `CONCAT` などで組む設計にしない（組むなら DB の種類の差と識別子の引用が増える）。ラベルは単一のカラムに限る方が安全で、要件で決める。

### 4. JWT の自動の伏せ字（初稿 Q5）
- 推奨は初稿の A（後処理のスクリプトを `evidence/` に置く前の必須の1段にする）に賛成。ただし補足する: (1) k6 の `handleSummary` で伏せる B は、台本ごとに忘れる危険があり、台本が増えても漏れる。後処理は「入力のディレクトリを渡すと全ファイルを走査する」形にし、k6 以外の出力（`--out json`、ログ、`docker logs` の貼り付け）にも同じ道具を通せるようにする。(2) 伏せる対象は `eyJ` で始まる JWT の形だけでなく、リフレッシュトークン（形が違う不透明な値）・`Authorization` ヘッダーの値・`Set-Cookie` を含める。k6 のサマリーにはヘッダーが入ることがあるため、ヘッダーの値ごと伏せる規則を持たせる。(3) 伏せ字の確かめは「`eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}` に一致する物が0件」の検索と `gitleaks dir` の両方を道具の出力に当てる（既存の学びと同じ）。(4) 道具のテストに、偽の JWT（署名部が空のもの・署名部があるもの・URL の部分・JSON の値の中・複数行にまたがるもの）を入れる。偽の値は実際の鍵で署名しない合成の値にし、そのテストデータ自体が Gitleaks に当たらないよう、必要なら `.gitleaks.toml` の除外を、対象のパス（テストの入力のファイル）と値の形の両方で絞って理由を書く（既存の決まり）。(5) 穴: 伏せた後の再現性のため、元の（伏せる前の）出力をリポジトリの外に残すかを決める。残す場合は権限 600 の置き場（リポジトリの外）に限り、コミットしない。
- 固い制約にするかは、「NEVER k6 の結果・ログに入った認証の値（JWT・リフレッシュトークン・Authorization ヘッダー）を伏せずにリポジトリへ置かない」を Forbidden に足す案を勧める。理由: 既存の NEVER（トークンをログ・エラー応答などに含めない）はアプリの出力を対象とし、perf の記録（`evidence/`）は含まない。今回は 12 ファイル 120 件が CI で落ちるまで気づかなかった実害がある。道具で自動化しても、道具を通さない手置きが残るため、ルールとして置く価値がある。インタビューの Q5 に「固い制約にするか」を加える。

### 5. サプライチェーン（コンテナの版そろえ）
- 初稿 Q6 の A（入れ替えの後に `docker inspect` でコンテナのイメージ ID が compose.yaml の版・ダイジェストと一致することを確かめる）に賛成。Deployment の決まりとして足す価値がある。確かめる項目は、コンテナの `Image` のダイジェスト（`RepoDigests`）が compose.yaml の `@sha256:` と一致すること。タグの表示だけでは、同じタグの別ダイジェストを見分けられない。
- 事実の補足: Mailpit は `compose.yaml` と `docker/perf/compose.yaml` の2か所、README にも書かれ（`.github/dependabot.yml` の固定先の一覧）、otel-lgtm は `compose.yaml` だけ。版を上げずに、動いているコンテナを作り直して compose.yaml の版にそろえるだけなら固定先の更新は不要。版を上げるなら、固定先の一覧（docker/perf/compose.yaml・README・TargetDbImages）を同じ版とダイジェストにそろえ、複数アーキテクチャの index のダイジェストであることを確かめる。
- 古いコンテナを作り直すときは `docker compose up -d --force-recreate --no-deps <service>` を使い、入れ替えの後に確かめる（既存の学び）。lgtm の作り直しは VM のメモリの余裕（約 100 MiB）に注意し、アプリ・Mailpit との同時起動の可否を先に確かめる。
- OSV-Scanner と npm のスクリプトの無効化は、サブモジュールの `vendor/make-you-chic-ui` の `npm ci` には効かない（既存の学び）。make-you-chic-ui の固定先を今回も上げる場合に限り、team.md の `hasInstallScript` の確かめを適用する。今回の範囲に固定先の更新が無いなら適用外と記録すればよい。
