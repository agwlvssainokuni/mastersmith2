### 1. 他テーブル参照のテスト案 (a)〜(f) の過不足
- (a)〜(f) は妥当で、既存の「業務データ」の必須テストに沿う。次の4点が抜けている。
  - (g) 参照先の値は、参照元の行の更新・作成でも検証する。参照先に存在しない値、権限の無い参照先の値、他人の参照先を指す差し替え（IDOR）は拒否され、状態が変わらないこと。選択肢の読み取りだけでなく、書き込みの検証が本体である。
  - (h) 参照先の主キーが複合・主キー無し・ビューのときの扱い。決めた側の動作を明示したテストにする。
  - (i) 3種類の対象DB（MySQL・MariaDB・PostgreSQL）での結合テスト。識別子の大文字小文字、NULL の並び、境界の値を含める。
  - (j) 接続の数。選択肢の取り出しが1要求で使う対象DB・内部DBの接続を `*ConnectionUsageIT` の形で決定的に確かめる。
- `ColumnWriteRulesFactory` が `lookup` を `text` に落とす暫定（K-74）は、本実装で外す。外した後も暫定の振る舞い（文字入力として扱う）に頼る既存テストが残るため、影響の範囲を検索で洗い出すこと（project.md の学び）。
- REFERENCE（選択肢）と LOOKUP（ピッカー）で、必須テストの重なりと差を表にして要件・コード生成の計画に載せる。

### 2. 認可の確かめ方
参照先を読む新しい API は、未認証401・要る権限だけを欠く利用者の403・権限ありの200 を、パラメーターを使う表のテストで確かめる。「API の分類の網羅」のテストに、新しい API の分類を足し忘れると落ちる形を保つ。参照先の権限と参照元の権限が食い違うときの結果（参照元は読めて参照先は読めない）は、要件で決めてからテストを書く（★）。

### 3. 境界テストと除外
SQL の口を増やす場合の SpotBugs 除外と ArchUnit の許可の変更は、既存の決まりどおりコード生成の計画に明記して承認を得る。参照先の読み取りは、既存の SQL 部品に閉じる案を先に検討する。新しい機能の境界テストは、既存を書き換えずに足す。

### 5. E2E
初稿の案（参照ピッカーで1本）に賛成する。ただし、次の2点を決める。
- 流れは自分で作った参照先と参照元だけを対象にし、見本の行や初期管理者を変えない。参照先は流れの専用のスキーマに置く。
- axe は、ピッカーを開いた状態・長い名前・ブランドカラーとテーマのすべての組で行う。ピッカーが make-you-chic-ui の部品でなければ、team.md の「make-you-chic-ui の部品に頼る振る舞い」の扱いの対象外になるため、自前の部品のキーボード操作と `aria` の単体テストを必須にする。
- i18next 系の更新に伴う E2E の流し直しは本数に数えない。

### 6. Dependabot #81・#82
初稿の案に賛成する。`ignore` に足さず、手元で版と lockfile を更新し `./gradlew verify` を通して統合し、PR を閉じる。#81 と #82 は組みで上げ、i18next と react-i18next の版の組が lockfile で一つにそろうことを確かめる。frontend の本体に触れないため、team.md の決まりでは統合の前の E2E は不要だが、翻訳のキーの取得に関わるため、画面のテスト全件と Build and Test の E2E で表示の文言を確かめる。この Intent は frontend 本体にも触れるので、同じブランチにまとめるか分けるかを決める。分けるのが安全で、依存の版だけの専用のコミットにすれば、戻しが容易である。

### 7. JWT の自動の伏せ字
初稿の案（仕組みに伏せ字のテストを付ける）に賛成し、次を足す。
- テストは、JWT の形（`eyJ…` の三つ組）を入れた入力から、`[REDACTED-JWT]` に置き換わる、JWT 以外の値（数値・場面名）は壊れない、すでに伏せた入力に流しても結果が変わらない（冪等）、入れ子の JSON・配列・長い文字列の中でも伏せる、を確かめる。
- 性質ベースのテスト（fast-check か、スクリプトの言語に合う道具）を、「任意の JSON に JWT を埋めて伏せた後に `eyJ` の形が残らない」に当てる案を、人間に聞く。
- `gitleaks dir` を evidence/ に対して流すことを手順に残す。CI の gitleaksScan は履歴全体を見るため、混入が先にコミットされると force-push になる（前の Intent の事故）。記録に置く前に必ず仕組みを通す形にし、仕組みを通さない書き込みの経路（手での複写）を無くす。
- 置き場の決定（後処理のスクリプトか `handleSummary`）で、テストの動かし方が変わる。`perf/` の既存のシェルのテスト（`perf/k6/thresholds-test.sh`・`perf/lib/perf-db-url-test.sh` など）が `./gradlew verify` や CI に入っているか、grep では確かめられなかった。入っていなければ、新しい仕組みのテストが CI の外に置かれ、劣化に気づけない。入れ方（verify に呼ぶか、手動か）を決めてもらう。

### 8. コンテナの版そろえ
「入れ替えの後に `docker inspect` でイメージの版・ダイジェストが compose.yaml と一致することを確かめる」案に賛成する。Deployment の決まりとして足す価値がある（lgtm の 0.34.0 が残った事例）。確かめを手順書にだけ置くと再発するため、できれば小さなスクリプトにして、不一致で失敗させる。Mailpit は E2E の前提でもあるため、版の更新後に Mailpit を使うテスト（受け手を JVM の中に置く決まりの例外）が通ることも確かめる。lgtm は動いていないので、起動して取り込みの確かめ（`OtlpLogExportIT` の類とは別の、手元の監視の式）が通るかは Observability の段に回す。

### 9. perf/README.md・k6 台本の整理
文書の整理は、内容を変えない。次を守る。
- 整理の前後で、k6 の台本の `k6 inspect --include-system-env-vars` が全場面で同じ出力になること（場面の名前・しきい値・タグ）を、整理の確かめにする。台本の挙動を変える変更（物差し・しきい値）は含めない（物差しを変えるのは要件定義で明示に決めたときだけ）。

- 基準の持ち主を `perf/versions.env`・compose.yaml・`dependabot.yml` の固定先の一覧に寄せる方針は、初稿の推奨 B（実践に足さず、設計の段で決める）に賛成する。
