# Functional Design の質問 — U3 u3-reference-screens（Intent 261029-reference-lookup-cleanup）

U3（作成・更新の画面の参照の部品とピッカーのダイアログ）の機能設計で、画面イメージ（`inception/refined-mockups/`）・契約・U1 と U2 の設計が「機能設計で決める」とした点のうち、判断が分かれるものだけを尋ねる。各質問の最初の選択肢を推奨とし、理由を添える。

## 決まっていること（質問しません）

- 作成・更新の画面は、定義の取得に `purpose`（`CREATE`・`UPDATE`）を付ける。一覧・詳細の画面は付けない（契約 C2）。`formPart` が `lookup` を返すのは `purpose` を付けたときだけ（U1 の D2）。
- 検索条件の入力は、定義の `picker.searchFields` の 1 件ごとに 1 つ置き、演算子は DSL が決めた値（一致・部分一致のどちらか）のまま出す。演算子を選ぶ部品は置かない（U1 の D6 で演算子を一致と部分一致に限った）。入力の型はカラムの受け渡しの型（`valueType`）から決める。
- 「選ぶ」ボタンの読み上げの名前の「行を見分けるラベル」は、U1 の Q4: A のラベル（DSL の `labelColumn`、無ければ `lookupList` の最初のカラム）を使い、ラベルが null のときは値を使う。
- 更新の画面で、保存済みの値のラベルが引けない（403 の同じ応答）ときは、値だけを出す（FR2.5、AC2.3.2）。
- 409 の項目の誤りは、理由で文言を出し分ける。`REFERENCE_NOT_FOUND` は参照先に無い値と読めない値を区別しない文言、`NOT_EDITABLE_NOT_NULL` は US1.5 の文言（「必須の参照項目に値を入れられません」）。400 に「候補が多い」項目が必須の誤りとして並ぶときも、定義の状態から US1.5 の文言を出す（U2 からの引き継ぎ）。503 は「保存されていない」と扱う。
- 画面イメージの段で決めたこと（ダイアログの組み立て・背景のクリックで閉じない・選んだ値の見せ方・入力不可の見せ方・「候補が多い」の案内の場所・狭い画面でのダイアログ・最初のフォーカス・状態の知らせ方・誤りのまとめへのフォーカス）は、そのまま使う。

## Q1. [設計] 作成・更新の画面で、定義の取得が 503 になったときの見せ方（契約の未解決の点）

参照の選択肢の読み取りが時間切れ・接続の失敗になると、定義の取得ごと 503 になる（契約の Q5: A）。そのため、対象DB の不調の間は、作成・更新の画面全体が開けない。

A. 既存の一覧・詳細の画面と同じ「開けない・つながらない」の表示（誤りの文・もう一度読み込むボタン・一覧へ戻る道）を、作成・更新の画面にも使う（推奨）。前の Intent の画面と見た目と操作がそろい、新しい部品が要らない。フォームは出さない
B. 作成・更新の画面だけの表示にして、「参照の候補を読めないため、いまは作成・更新できません」と理由を分けて出す。理由ははっきりするが、503 の中身（参照の読み取りか、ほかの読み取りか）を画面で見分ける手段が無く、文言が誤りうる
X. Other (please specify)

[Answer]: A

## Q2. [設計] ピッカーの結果の表で、「選ぶ」ボタンの位置（画面イメージの段から回った点）

結果の表は make-you-chic-ui の Table を使い回し、横にスクロールする。狭い画面（375px）では、右端の「選ぶ」が画面の外に出て見えないことがある。

A. 画面の幅によらず、「選ぶ」をいつも最初の列に置く（推奨）。どの幅でも見え、キーボードで行に入ってすぐ選べる。画面の幅で並びを変えないので、テストと読み上げの順が 1 通りで済む
B. 狭い幅のときだけ「選ぶ」を最初の列に移し、広い幅では右端に置く。広い画面の見た目は一覧の画面の操作の列とそろうが、幅で並びが変わり、確かめる組が増える
C. 行全体を押して選べるようにし、「選ぶ」ボタンは置かない。押す場所は広いが、行の中のほかの操作と重なり、キーボードと読み上げでの選び方を別に作る必要がある
