## 9. 計画の承認で確かめたいこと（推奨と理由）

1. **Q4（メールアドレスの検索）の読み方**: 今の README のコードブロックの中のコマンド（使い捨ての環境の利用者・初期管理者）に `@example.test` が 13 か所あり、コマンドは 1 文字も変えない決まりのため、NFR8.90・5.6節 Q4 の「`example.com` 以外のメールアドレスが 0 件」は整理の前から満たせない。推奨: 「予約のドメイン（`example.com`・`example.test`）以外のメールアドレスが 0 件」と読む（どちらも実在しない予約のドメインで、守りたいもの（実在の宛先を置かない）は同じ）。代わりの案: コマンドの `example.test` を `example.com` に替える（使い捨ての環境の手順の文字を変えるため、5.7節 L3 との差になる）。
2. **935 行のコメントの古い線**: コードブロックのコメントが「peak / max が 0.9 未満であること（… 0.95 未満に緩めた …）」と前の線を今の線として書いている。推奨: 本文のコメントを「peak / max が 0.95 未満であること（前の線 0.9 も並べて記録する。「今の基準の一覧」を参照）」に直し、「Intent 261027-perf-targets-review で 0.95 未満に緩めた」を履歴へ移す（コマンドの部分は変えない。対応表に書く）。理由: そのまま本文に残すと、5.4節の組の比べで今の線と違う値の組が残り、前の線と今の線が混ざらないという US4.3 の目的に反する。代わりの案: コメントの線の部分も含めて履歴へ移し、本文のコメントは参照だけにする。
3. **`REF_P95_LIMIT_MS` を区画に入れること**（8節）: 推奨: 入れる（5.2.2節の決まりそのままで、入れないと「1 か所」にならない）。
4. **アプリの起動を `docker compose start app` にすること**（8節）: 推奨: そうする（作り直しを確実に避ける）。
5. **VM の空きの基準 1792 MiB**（2節）: 推奨: このまま（lgtm の上限に余裕 256 MiB）。
