# Functional Design の質問 — U1 u1-reference-read（Intent 261029-reference-lookup-cleanup）

U1（参照の読み取り: REFERENCE の選択肢・LOOKUP の検索とラベル・権限・上限・接続）の機能設計で、上流（要件・ストーリー・契約）が「機能設計で決める」とした点のうち、判断が分かれるものだけを尋ねる。各質問の最初の選択肢を推奨とし、理由を添える。書く前に既存のコードを確かめた: DSL の検証（`DslSemanticValidator`）は参照先のテーブルとカラムがあることだけを確かめ、`valueColumn` の一意や主キーは求めていない。一覧の検索の値の上限は `SearchRequestValidator.MAX_VALUE_LENGTH` = 1,000 文字、一覧のページは 1 から `PageRequest.MAX_PAGE`（1,000,000）まで。

## 決まっていること（質問しません）

- `ReadPurpose` に足す目的の名前は `REFERENCE` とする（選択肢・ピッカーの検索・ラベル・保存前の確かめの読み取りで共通）。時間の上限の値は NFR 設計で決める。
- 検索 API の誤りの分け方（契約の未解決の点）: 本文の形の誤り（`conditions` と `value` の両方・どちらも無い、条件の値がすべて空、値が 1,000 文字を超える、ページが範囲外）は 400 `VALIDATION_FAILED`。名前に関わる誤り（`lookupSearch` に無い列・DSL に無い列・主権限 NONE の列、参照でないカラム、DSL に無い表）は 403 の同じ応答（AC2.1.8・AC2.1.9・AC2.1.11）。値の 1,000 文字は既存の一覧の検索と同じ（FR2.6 で確かめた）。
- ページ（AC2.1.3）は既存の一覧に合わせて 1 から数え、1〜1,000,000 の外は 400 `VALIDATION_FAILED`、最後のページより後は 200 の 0 件（`hasNext` は偽）。契約 C2 の `page`（`minimum: 0`）は、既存の一覧の数え方に合わせて 1 からに読み替え、差を機能設計に書く。深いページでも内部で読む行はページの先頭＋21 件まで（次の有無の判定に 1 件多く読む）。

## Q1. [設計] 参照先の形が「1 行に決まらない」ときの扱い（AC1.4.4）

DSL は、参照先の `valueColumn` が一意であることを求めていない。参照先がビュー・主キーの無いテーブル・`valueColumn` が一意でないテーブルのとき、同じ値の行が 2 行以上ありうる。複合の主キーのテーブルでも `valueColumn` は 1 つのカラムなので、同じ扱いになる。自己参照（参照元と参照先が同じテーブル）は、同じ作業ロールの写しで読むだけで、特別な扱いは要らない。

A. 形では拒否せず、そのまま読む（推奨）。REFERENCE の選択肢は、読んだ行を並びの順に見て、同じ値の 2 行目以降を落とす（最初のラベルを使う）。201 件目の判定は、落とす前の読んだ行の数で行う。ラベルの 1 件読みは、同じ値の行が 2 行以上でも、並びの順の最初の行のラベルを返す。保存前の確かめは、同じ値の行が 1 行以上あれば「ある」とする。ビューや主キーの無いテーブルを選択肢の元にする使い方（有効なコードだけを出すビューなど）を許せる
B. `valueColumn` が参照先の唯一の主キーのカラムである場合だけ参照を提供し、それ以外は定義の `reference.status` に新しい状態（例: `UNSUPPORTED`）を付けて入力不可にする。1 行に決まる参照だけになるが、ビューを選択肢の元にできず、契約の状態の値が 1 つ増える

## Q2. [設計] 型が合わないとき・ラベルに読めない型のとき（AC1.4.5）

参照元の値は文字列で受け取り、参照先の `valueColumn` の型で束ねる（ストーリーで決めた）。PostgreSQL は型の合わない比較を拒み、MySQL は暗黙の変換で通るため、DB ごとに結果が割れないようにする必要がある。

A. 値は参照先の `valueColumn` の DSL の型に、サーバー側で先に変換してから束ねる（推奨）。変換できない値（数の型に数でない文字列など）は、対象DB に問い合わせずに「無い」とする（ラベルの 1 件読みは 403 の同じ応答、保存前の確かめは `REFERENCE_NOT_FOUND`）。3 種類の DB で同じ結果になる。ラベルのカラムがバイナリの型のときはラベルを null にして値を出し、大きな文字列は既存の行の値の型の対応（上限）のまま渡す
B. 値を文字列のまま束ね、型の扱いは各 DB に任せる。実装は少ないが、PostgreSQL では 503（問い合わせの失敗）になりうるなど、DB ごとに結果が割れる

## Q3. [設計] 1 つの定義の取得で読む REFERENCE の数と、全体の時間（AC1.1.5）

定義の取得では、REFERENCE のカラムを 1 本の読み取りの接続で順に読む。数が多いと、最悪で「項目の数 × 問い合わせ 1 回の時間の上限」かかる。

A. 数の上限は置かず、定義の取得全体に時間の上限（値は NFR 設計で決める）を置く（推奨）。全体の上限を超えたら、残りを読まずに 503 `BUSINESS_TARGET_DB_TIMEOUT` で定義の取得ごと失敗にする（契約の Q5: A と同じ扱い）。DSL のカラムの数の上限（既存）が、実際の数の上限になる
B. 1 つの定義で読む REFERENCE の数に上限（例: 10）を置き、超えたら定義の取得を 409 などの新しい誤りにする。上限ははっきりするが、新しい code が要り、DSL の作り方に制約が増える
C. どちらも置かず、問い合わせ 1 回の時間の上限だけに任せる。最悪の時間が項目の数に比例して伸びる

## Q4. [設計] LOOKUP のラベルに使うカラム（契約の未解決の点、AC2.1.5）

DSL の LOOKUP は `labelColumn` を任意で持てる（REFERENCE では必須）。ラベルは、ピッカーの結果の行と、更新の画面の保存済みの値の隣に出す。

A. DSL に `labelColumn` があればそれを使い、無ければ `lookupList` の並びの最初のカラムを使う（推奨）。ラベルに使うカラムも「読めること」の判定に入れ、主権限が NONE なら、REFERENCE と同じくピッカーを提供しない（`NO_PERMISSION`）
B. 常に `lookupList` の並びの最初のカラムを使う。判定が単純だが、DSL の `labelColumn` の指定が LOOKUP では使われない
