# NFR Design の質問 — U1 u1-reference-read（Intent 261029-reference-lookup-cleanup）

U1（参照の読み取り）の NFR 設計（非機能の要件をどう作るか）で、判断が分かれる点だけを尋ねる。各質問の最初の選択肢を推奨とし、理由を添える。

## 決まっていること（質問しません）

- 問い合わせ 1 回の上限は `REFERENCE` の目的の 5 秒（環境変数で変えられる、既存の形）。定義の取得全体の上限は 10 秒で、残りの時間を秒に切り上げて文ごとに絞り、1 秒未満なら流さず 503（機能設計の BR8.4、NFR 要件）。
- 値のカラムは 10,001 文字に切って読み、10,000 文字を超えた値の行は選択肢・ピッカーから外し、確かめでは「無い」とする（NFR 要件の F1: A）。ラベルと一覧の列は既存の 100 文字で切る。
- 性能の試験の読み取りのプールの上限は 5（前の Intent と同じ）。k6 の場面は Build and Test で書く。
- 監視の目盛り（`http.server.requests` のバケット）に 3 秒を足すかは、Observability Setup で決める。

## Q1. [設計] 10,000 文字を超えた値の行を外すときの数え方（NFR 要件の承認で直すよう記録した点）

読む行を 201 に絞ってから長い値の行を外すと、実際は 201 行あっても 200 件として返り、「候補が多い」（201 件以上）やピッカーの次のページの有無の判定がずれる。

A. 長い値の行を SQL の条件で先に除く（値のカラムの長さが 10,000 文字以下の行だけを読む）（推奨）。読んだ行の数がそのまま使える行の数になり、201 件目の判定と次のページの有無が正しくなる。長さの関数は DB の種類ごとの方言のクラスに閉じる。代わりに、長さの条件は索引を使えないため、大きな参照先では読む量が増えうる（試しで測る）
B. 外した行も 201 件目と次のページの判定に数える（読んだ 201 行で判定し、返す件数だけが減る）。SQL は変えないが、選択肢が 200 件未満なのに「候補が多い」になる場合がある
C. 外した行の分だけ読む行を延ばして読み直す。数は正しくなるが、問い合わせが繰り返しになり、時間と接続の見積もりが崩れる

## Q3. [品質] 設計の前提を、文書を書く前に捨ての試しで確かめるか

前の Intent では、試しを文書より先に流して前提の崩れを見つけてから書いた単位のほうが、書き直しが少なかった（`project.md` の学び）。この単位の前提は、SQL の側での 10,001 文字の切り取りと長さの条件（3 種類の DB）、201 行の読み取りの時間（既存の大きな業務データの表）、文ごとの時間の上限の絞り方（`TargetReadSession` の作り直し）、長い値の読み取りのヒープの増え方。

A. リポジトリの外の捨ての試しのコードで、3 種類の DB を起動して先に確かめ、結果の要点を文書に写してから書く（推奨）。前提が崩れていたら、追加の質問で確かめてから書く。代わりに、この段の時間が延びる
B. コードの読み取りだけで書き、確かめはコード生成に任せる。早いが、前提が崩れていたときにコード生成で設計を直すことになる

## 追加の質問（捨ての試しの結果から）

試しの結果は `trial-results.md` に置いた。前提が1つ崩れた。MySQL 26.10.0（既定の並べ替えの領域 256 KB）で、約 10,000 字の値の行を何十行も持つ文字のカラムを `ORDER BY` に置くと、`HY001`・1038（Out of sort memory）で失敗する。長さの条件・型（VARCHAR〜LONGTEXT）・`id` だけを選ぶ形のどれでも起き、約 8,000 字までなら行の数によらず成功した。先頭の 100 字・255 字で並べる形は、3種類の DB のすべてで成功した。PostgreSQL と MariaDB では起きない。今の分け方では 1038 が `UNEXPECTED`（500）になり、NFR1.10・NFR1.11 に反する。

## F1. [設計] MySQL の並べ替えの誤り（1038）をどう避けるか

A. 文字の型のラベルと値の並びの項を、先頭の 100 字（既存の `LIST_TEXT_LIMIT` と `SUBSTRING` の形）で作る。式は DB の種類ごとの方言のクラスに閉じ、3種類で同じ形にする（推奨）。試しで3種類のすべてで成功した唯一の形で、画面に出す 100 字で並ぶ。代わりに、承認済みの BR4.2・BR5.8 の並びとの差を記録し、「先頭 100 字が同じ行は主キーの順」の動作と、MySQL で 1038 にならないことを確かめる結合テストを足す
B. 並びはそのままにし、1038 を既存の 409 か 503 に写す。承認済みの並びは保てるが、MySQL だけデータしだいで画面が開けなくなり、NFR1.11 に反する
C. DSL の検証で長い文字の型を断る。VARCHAR でも起きるため防げず、前提 A7（DSL の書式を変えない）にも触れる

## F2. [範囲] 既存の業務データの一覧で同じ誤りが起きうる点をどう扱うか

既存の業務データの一覧でも、DSL で `sortable` にした長い文字のカラムで並べると、MySQL で同じ 1038 になり 500 を返しうる（試しからの見立てで、一覧そのものでは確かめていない）。

A. この Intent では直さず、後の Intent の論点として振り返り（Feedback & Optimization）に記録する（推奨）。この Intent の範囲（参照）を広げず、一覧の並べ替えの仕様を変えるかは改めて要件で決められる
B. この Intent の範囲に入れ、一覧の並べ替えも同じ先頭 100 字の形にそろえる。今すぐ直るが、承認済みの要件・ストーリーの外の変更になり、U1 の作業と既存のテストへの影響が増える
