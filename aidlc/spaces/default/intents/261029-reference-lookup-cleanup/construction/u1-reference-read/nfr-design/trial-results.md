この段の質問の答え（Q3: A）に従い、設計の文書を書く前に、リポジトリの外の捨ての試しのコードで設計の前提を確かめた。前提が1つ崩れたため（4節）、設計の文書（`performance-design.md` など）はまだ書いていない。依頼者の決定を得てから書く。

## 2. 確かめた項目と結果

### 2.1 T1: 長さの条件（文字数）と 10,001 字の切り取り

条件 `v IS NOT NULL AND CHAR_LENGTH(v) <= 10000`、選ぶ式 `SUBSTRING(v, 1, 10001)`（既存の `selectExpression` と同じ形。上限の数は SQL の中の定数で、バインドしない既存の書き方と同じ）。

| 確かめ | PostgreSQL | MySQL | MariaDB |
|---|---|---|---|
| 残った行（10,000 字以下だけ） | ascii-9999・ascii-10000・ja-10000・emoji-10000・pad-10000 | 同じ | 同じ |
| 外れた行 | ascii-10001・ja-10001（日本語）・emoji-10001（補助面の文字。UTF-16 で2つ）・2,000,000 字・pad-10001・NULL | 同じ | 同じ |
| 読んだ長さ（Java のコードポイント）と DB の長さ | 一致。`SUBSTRING` は文字の単位で切る（2,000,000 字の行も 10,001 で返る） | 同じ | 同じ |
| `CAST(v AS TEXT)`／`CAST(v AS CHAR)`（OTHER の型の形）に当てた長さの条件 | 5 行（同じ） | 5 行 | 5 行 |
| `v = 'x'` の一致（PAD SPACE） | 一致なし | 一致なし（NO PAD） | `x`＋空白 9,999 個・10,000 個の2行が一致 |
| `v = 'x' AND CHAR_LENGTH(v) <= 10000` | 一致なし | 一致なし | `x`＋空白 9,999 個の行だけ |

読み: `CHAR_LENGTH` は3種類とも文字（コードポイント）で数え、バイトで数えない。Java の `codePointCount` と既存の `ColumnValueCodec` の数え方にそろう。MariaDB の PAD SPACE で 10,001 字の行が `=` に当たっても、長さの条件で外れる（`check` は BR9.4 の厳密な一致でも外す）。

### 2.2 T2: 100,000 行の参照先から 201 行を読む時間と EXPLAIN

並び `name`（NULL は最後）→ `code` → `id`。値のカラムは `code`、ラベルは `SUBSTRING(name, 1, 101)`。

| 問い合わせ | PostgreSQL 中央値・最大 | MySQL | MariaDB |
|---|---|---|---|
| 選択肢 201 行・長さの条件なし | 59.7・60.9 ms | 19.2・20.2 ms | 45.9・46.3 ms |
| 選択肢 201 行・長さの条件あり | 63.4・63.9 ms | 21.2・22.0 ms | 48.2・48.5 ms |
| 同じ・主キーで結ぶ形（既存の `page` の形） | 58.8・60.0 ms | 20.7・21.0 ms | 48.8・50.4 ms |
| 値のカラムが長い文字の型（`note`）・長さの条件あり | 173.8・176.4 ms | **失敗 1038**（4節） | 187.9・212.1 ms |
| ピッカー `EQUALS`（ラベルの一致）1ページ目 | 5.5・6.0 ms | 13.4・13.7 ms | 15.6・15.9 ms |
| ピッカー `CONTAINS` 1ページ目（長さの条件あり／なし） | 7.1／7.0 ms | 15.2／12.9 ms | 18.0／16.3 ms |
| ピッカー 条件なし 1,000 ページ目（`OFFSET 19980`） | 535.6・561.7 ms | 39.5・58.4 ms | 98.8・106.0 ms |
| `check`（`code = ?`、索引あり） | 0.5 ms | 0.5 ms | 0.5 ms |
| ラベルの1件読み（`code = ?`、1 行） | 0.4 ms | 0.5 ms | 0.5 ms |

EXPLAIN の要点:

- 選択肢（ラベルで並べる）: 3種類とも表の全部を読んで並べる（PostgreSQL は `Parallel Seq Scan`→`Sort`→`Limit`、MySQL は `Table scan`→`Sort ... limit input to 201 row(s)`、MariaDB は `type=ALL ... Using filesort`）。長さの条件は `Filter` に1つ足されるだけで、プランは変わらない。並びがラベルから始まるため、もともと索引で並びを作れず、長さの条件が索引を無にするのではない。足された時間は 1.3〜3.7 ms。
- `check`・ラベルの1件読み（値の一致）: 長さの条件があっても `code` の索引を使う（PostgreSQL `Index Scan using idx_ref_code`＋`Filter`、MySQL `Covering index lookup`、MariaDB `type=ref key=idx_ref_code`）。

読み: 1 本の接続での時間は、NFR2.1 の線（p95 1,000 ms・部分一致 3,000 ms）に十分な余裕がある。条件なしで深いページを読むピッカー（PostgreSQL 536 ms）は線の半分を超える。k6 の場面（`EQUALS`・`CONTAINS` の1ページ目）には入らない形だが、Performance Validation で注意する。

### 2.3 T3: 秒の単位の時間の上限

`Statement.setQueryTimeout(秒)` を 1・2・3 秒で、`SLEEP(8)`／`pg_sleep(8)` と重い結合に当てた。

| 確かめ | PostgreSQL | MySQL | MariaDB |
|---|---|---|---|
| 1・2・3 秒の上限で切れるまで | 1,020〜1,027 ms／2,014〜2,021 ms／3,018〜3,021 ms | 1,021〜1,023／2,022〜2,023／3,026〜3,027 ms | 1,005〜1,008／2,006〜2,007／3,005〜3,009 ms |
| 投げられる例外 | `PSQLException`、SQLState `57014`（`SQLTimeoutException` ではない） | `MySQLTimeoutException`（`SQLTimeoutException` の子、SQLState なし） | `SQLTimeoutException`、SQLState `70100`、業者の番号 1969 |
| 既存の `RowSqlFailureClassifier` の分け方 | `57014` で `TIMEOUT` | `SQLTimeoutException` で `TIMEOUT` | `SQLTimeoutException`／`70100` で `TIMEOUT` |
| 同じ接続で文ごとに上限を変える（5 秒→1 秒） | 効く（2 秒の待ちが 5 秒では返り、1 秒では切れる） | 効く | 効く |
| 時間切れの後の接続 | 使える | 使える | 使える |
| `TargetReadSession` と同じ形の record を作り直す費用 | 21.5 ns | 16.3 ns | 7.0 ns |

読み: 秒に切り上げた残りで文ごとに上限を絞る形（BR8.4）は、3種類のドライバーで正しく効き、誤差は 30 ms 未満。どのドライバーも上限を無視しない。作り直しの費用は無視できる。時間切れの後も接続は使えるが、設計どおり壊れた印を立てて捨てる（NFR3.6。既存の決まりを変えない）。

### 2.4 T4: 長い値を読むヒープ

`long_ref` から 201 行を読み、値とラベルの文字列を持ったまま測った（`ThreadMXBean` の割り当ての量と、GC の後の使用量の差）。

| 読み方 | 3種類の結果（行・10,000 字超・最長） | 割り当て | GC の後に残る量 | 応答の JSON（UTF-8）の見込み |
|---|---|---|---|---|
| 長さの条件＋10,001 字の切り取り（Q1: A の形） | 201 行・0・10,000 字（PostgreSQL・MariaDB。MySQL は 1038 で失敗、4節） | 38.8 MB | 3.9 MB | 5.8 MB |
| 切り取りだけ（条件なし。`id` の降順で長い行を含める） | 201 行・20・10,001 字 | 38.8〜39.3 MB | 3.9 MB | 5.8 MB |
| 切らずに読む（比べるための参考） | 201 行・20・2,000,000 字 | 418.3〜423.5 MB | 43.7〜43.8 MB | 62.7 MB |

読み: Q1: A の形で、1要求の値の文字列は GC の後で約 3.9 MB、応答の JSON は約 5.8 MB で、ドライバーの行の写しと JSON に書く写しを足しても NFR2.8 の見積もり（1要求で最大約 10〜15 MB）の内に収まる。割り当ての量（約 39 MB）は文字の組の変換の一時の量で、すぐ回収される。10 VU では一時の割り当てが約 390 MB／巡になるが、残る量は約 40 MB で、見積もり（100〜150 MB）の内。切らずに読むと1要求で約 420 MB を割り当てるため、SQL の側で切ることは欠かせない。

## 3. 前提ごとの判定

| 前提（出典） | 判定 |
|---|---|
| 長さの条件は文字数で数え、日本語・補助面の文字を含めて 10,000 字を超える行を外す（Q1: A、NFR2.8） | 成り立つ（3種類） |
| 10,001 字の切り取りは既存の方言の書き方（`SUBSTRING`、定数）で書ける（NFR2.8） | 成り立つ |
| 201 行の読み取りの時間は p95 1 秒に収まり、長さの条件は索引を無にしない（Q1: A の懸念、NFR2.1） | 成り立つ（並びの都合で索引はもともと使えない。値の一致の索引は使える） |
| 秒の単位の上限の絞り込みと時間切れの分け方（BR8.4、NFR3.4・NFR3.5） | 成り立つ |
| ヒープの見積もり（NFR2.8） | 成り立つ |
| 固定の並び「ラベル → 値 → 主キー」をカラムそのもので並べられ、DB によって 500 にならない（BR4.2・BR5.8、NFR1.10・NFR1.11） | **崩れた（MySQL）** |

## 4. 崩れた前提: MySQL で長い文字の値を並べると 1038 で失敗する

### 4.1 何が起きたか

MySQL 26.10.0 で、`ORDER BY` に長い文字の値を持つカラムを置くと、`SQLException`（SQLState `HY001`、業者の番号 1038、Out of sort memory）で失敗した。長さの条件で 10,000 字を超える行を外しても、選ぶのを `id` だけにしても、主キーで結ぶ形にしても同じ。PostgreSQL と MariaDB では起きない。

| 並べたカラムとデータ（T5・T6、2,000 行） | MySQL |
|---|---|
| 値が短い（〜8,000 字。20 行に1行でも全行でも） | 成功 |
| 約 10,000 字の値が 10 行に1行（200 行） | 失敗 1038（VARCHAR(16000)・TEXT・MEDIUMTEXT・LONGTEXT のどれも） |
| 約 10,000 字の値が 200 行に1行（10 行） | 成功 |
| 2,000,000 字の値が 500 行に1行で、長さの条件で外した後 | 成功（外した行は並べない） |
| 2,000,000 字の値が並べるカラムにあり、長さの条件が無い（ピッカーのラベルの並びの形） | 失敗 1038 |
| 同じデータで `SUBSTRING(列, 1, 100)` や `SUBSTRING(列, 1, 255)` で並べる | どれも成功 |
| JSON の型 | 値の並びは成功、ラベルの並びの形（長さの条件なし）は失敗 |

原因の見立て（未検証）: MySQL の既定の照合 `utf8mb4_0900_ai_ci` は NO PAD で、NO PAD の照合では `max_sort_length`（1,024 バイト）が効かず、文字列の全体が並べ替えのキーになる。1 行のキーが 30 KB 前後に達し、既定の `sort_buffer_size`（256 KB）に収まらない。MariaDB は PAD SPACE の照合で `max_sort_length` が効き、並べ替えの領域も 2 MB のため起きない。

### 4.2 この単位への影響

固定の並び（BR4.2・BR5.8。ラベル → 値 → 主キー）は、MySQL で次のときに失敗する。

- REFERENCE の選択肢・`countState`: ラベルのカラムか値のカラムに長い文字の値（目安は 1 行で約 10,000 字。数十行以上）がある。値のカラムは 10,000 字までに絞るが、10,000 字近い値が多いと失敗する。ラベルのカラムは長さで絞らない（表示は 100 字で切るが、並びはカラムの全体）。
- ピッカーの検索・ラベルの1件読み・`check`: ラベルのカラムに長い文字の値がある。

既存の `RowSqlFailureClassifier` は 1038（`HY001`）を `UNEXPECTED` に分けるため、定義の取得・ピッカーの検索が 500 になる。NFR1.10（500 にしない）と NFR1.11（DB ごとに結果が割れない）に反する。参照先がアプリの外で入れた長い文の説明のカラム（備考など）をラベルにした DSL で起きうる。

あわせて分かったこと（この単位の外）: 既存の業務データの一覧も、DSL で `sortable` にした長い文字のカラムで並べると、同じ 1038 で 500 になりうる（試しの「ラベルの並びの形」と同じ問い合わせの形）。この単位では直さず、後の Intent の論点として依頼者に伝える。

### 4.3 選択肢

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| A（推奨） | 文字の型（STRING と、文字にして読む OTHER）のラベルと値は、並びの項を先頭の 100 字（`LIST_TEXT_LIMIT`、既存の `selectExpression` と同じ `SUBSTRING`）で作る。式は方言のクラスに閉じ（`orderTerm` に渡す式を作る口を足す）、3種類の DB で同じ形にする。主キーと数・日時の型は今のまま | 試しで 3種類とも成功し、1行のキーは数百バイトに収まる。ラベルは画面に出す 100 字で並ぶため、見た目の並びと合う。SQL の新しいメソッドや境界の変更は要らない | BR4.2・BR5.8 の「ラベルの昇順・値の昇順」が「ラベルの先頭 100 字の昇順・値の先頭 100 字の昇順」に変わる（承認済みの機能設計との差として記録する）。先頭 100 字が同じ行どうしは主キーの順になる。BR4.2 は3種類で同じ並びを求めていないため、決まりの趣旨は保てる |
| B | 並びはカラムの全体のままとし、1038 を既存の失敗の code（たとえば 409 `BUSINESS_TARGET_DB_MISMATCH` か 503 `BUSINESS_TARGET_DB_UNAVAILABLE`）に分けて、定義の取得ごと失敗にする | 承認済みの並びを変えない | MySQL だけ、データしだいで作成・更新の画面が開けなくなる（NFR1.11 に反する）。分け方の変更は既存の一覧の失敗にも効く |
| C | DSL の検証で、長い文字の型（TEXT 系）をラベル・値に選べないようにする | 起きる形を前もって断てる | VARCHAR(16000) でも起きるため型では防げない。DSL の検証の変更は前提 A7（DSL の書式を変えない）に触れる |

推奨は A。試しで唯一3種類とも成功した形で、画面に出す 100 字で並べることになり、機能設計の決まり（3種類で同じ並びは求めない）とも合うため。A を選んだときは、設計の文書に次を書く: 並びの項の作り方（方言のクラスの口）、承認済みの BR4.2・BR5.8 との差、「先頭 100 字が同じ行は主キーの順」の決めた動作を確かめる結合テスト、MySQL で約 10,000 字の値・ラベルを 200 行以上持つ参照先で 1038 にならないことを確かめる結合テスト。

## 5. ほかに設計に写す点（前提は崩れていない）

- 時間の上限の例外は3種類で形が違う（2.3 の表）が、既存の分け方で3つとも `TIMEOUT` になる。参照の読み取りで分け方を変える必要は無い。
- 条件なしで深いページを読むピッカーは、PostgreSQL で 1 本の接続でも約 0.5 秒かかる（2.2）。k6 の場面に入らないため合否には関わらないが、性能の設計の注意として書く。
- MariaDB の PAD SPACE で、末尾の空白だけが違う行が DB の比べ方で一致する（2.1）。BR9.4 の厳密な一致と長さの条件で外れることを、結合テストの境界に入れる。

## 6. 後片付け

- `u1trial-` の3つのコンテナは、各実行の終わりに消した（実行の後に一覧で 0 件を確かめた）。配備したアプリ・見本の PostgreSQL（`mastersmith-targetdb-postgres-1`）・Mailpit は動いたまま。
- 試しのコードと記録はリポジトリの外の置き場に残してある（資格情報は置き場に書いていない。実行ごとに作って環境変数で渡しただけ）。
