## 2. 伏せ字の決まり（置換）

### 2.1 JWT の形と置換の関数（NFR8.62・BR1.1〜BR1.4）

- 形の定義を道具の中の 1 か所（1 つの正規表現の定数）に置き、置換の関数・残存の検査の関数・evidence の検査が共有する。

```text
// 形の定義（考え方。実装はコード生成。型の検査・リンタの対象にしない断片）
const JWT_SHAPE = /(?<![A-Za-z0-9])eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+/g
export const JWT_MARK = '[REDACTED-JWT]'
export const SETUP_MARK = '[REDACTED-SETUP]'
export function redactJwt(s) { /* s.replace(JWT_SHAPE, JWT_MARK) と置き換えた件数 */ }
```

- 区間は貪欲に最も長く取る（BR1.1）。3 区間目の後ろの `=` は区間に入らないため残る。4 つ以上の `.` は先頭の 3 区間だけが 1 件になり、残りの `.xxx` はそのまま残る。
- `Bearer ` の後ろの JWT は、直前の文字が空白のため形に当たり、`Bearer [REDACTED-JWT]` になる（BR1.4）。
- 冪等の根拠: 置き換えの印 `[REDACTED-JWT]`・`[REDACTED-SETUP]` は `eyJ` を含まず形に当たらない。また、形の直前の英数字で形から外れた `eyJ…` は、その英数字がほかの件の 3 区間目に続いていれば同じ件に呑まれて置き換わり、そうでなければ置き換えの後も直前の英数字が残るため、2 回目に新しい件が生まれない。これを性質のテスト (2)(t2) で確かめる（7節）。
- 処理の時間: 形の始まりは「直前が英数字でない `eyJ`」に限られるが、`-eyJ-eyJ…` のように始まりの候補が続き `.` が無い長い文字列では、試しが入力の長さの 2 乗に近づく。コード生成で、この形の 1 MiB 程度の入力を例のテストで当て、Vitest の既定の時間の上限の中で終わることを確かめる。収まらないときは、上限を延ばさず、形の定義を保ったまま 1 回のなめ（文字を左から 1 度だけ読む関数）に替える（置換と検査の両方が同じ関数を使う）。

### 2.2 JSON の口（NFR8.62・BR1.3・BR1.5〜BR1.7）

- 入力の木を、再帰ではなく明示の積み上げ（スタック）でたどる（深い入れ子で呼び出しの深さが尽きない。BR1.3）。
- 文字列の値・配列の要素の文字列・キー名に `redactJwt` を当てる。数・真偽・null は触らない。
- 上の階層がオブジェクトで、自分自身のキー `setup_data` を持つときは、その値の下のすべての文字列（`setup_data` の値そのものが文字列ならそれも）を `[REDACTED-SETUP]` に替える。キー名には `redactJwt` だけを当てる。深い所の `setup_data` という名前は特別に扱わない（BR1.7）。
- キー名を替えた後、同じオブジェクトの中で名前が重なれば中止し、終わりのコード 3。表示は置換の後の名前でたどった道だけ（BR1.5）。
- キーの並び: 新しいオブジェクトを、元のオブジェクトの並び（`JSON.parse` が作った並び）のとおりに組み直し、替えたキーも同じ位置に置く。JavaScript のオブジェクトは整数の形のキー（`"0"`・`"10"` など）を先に小さい順に並べるため、その種のキーの並びは入力の文字の並びではなく `JSON.parse` の並びになる（5節「上流との差」）。性質 (4) の比べは、入力を `JSON.parse` した木の並びと比べる。
- 数は `JSON.parse` で倍精度の数になる。k6 の summary json の数は倍精度の範囲で、値は変わらない（`1.0` が `1` になるなどの書き方の違いは BR1.6 のとおり許す）。2^53 を超える整数は値が丸まりうるが、k6 の出力に無いため対象外とし、5節に書く。
- 書き出しは UTF-8・改行 LF・末尾に改行 1 つの、字下げのある JSON（幅はコード生成で決める）。
- `JSON.parse`・`JSON.stringify` が深さで投げる `RangeError` は、入力の誤り（コード 2）として扱い、実行環境の文言を表示しない。

### 2.3 テキストの口（NFR8.62・BR1.8・BR3.4）

- 入力のバイト列を `TextDecoder('utf-8', { fatal: true, ignoreBOM: true })` で読む。`fatal` で不正な UTF-8 をコード 2 にし、`ignoreBOM` で先頭の BOM を文字として残す（既定のままだと BOM が落ち、BR1.8「BOM を変えない」に反する）。
- 読む前に、バイト列に NUL（0x00）が 1 つでもあればコード 2。空・空白だけもコード 2。
- 中身が JSON として読めて、上の階層がオブジェクトで `setup_data` を持てばコード 1（summary json は JSON の口で置く）。読めないのは普通のログで、そのまま進む。
- 出力のパスの拡張子が `.json`（大文字と小文字を区別しない）ならコード 1。
- 中身全体に `redactJwt` を 1 回当て、ほかの文字は変えない。出力は同じ形でバイト列に戻す（BOM・改行 LF・CRLF・末尾の改行は入力のまま）。

### 2.4 JSON の口の入力の読み方

- JSON の口は `TextDecoder('utf-8', { fatal: true })`（BOM は既定どおり読み飛ばす）で読み、`JSON.parse` に渡す。出力に BOM は付けない（k6 は BOM を出さない。5節）。

## 3. 残存の検査（NFR8.63・BR2.1・BR2.2・BR2.4）

- 置換の関数を呼ばない別の関数 `findResidual(text)` が、書き出す直前の文字列（JSON の口は `JSON.stringify` の結果、テキストの口は出力の文字列）を `JWT_SHAPE` で端から調べ、件数と位置（行と桁）だけを返す。値・前後の文字は返さない。
- 行は LF で数え、桁は行の始まりからの文字の位置（JavaScript の文字列の位置、1 始まり）とする。
- JSON の口では、あわせて書き出す直前の文字列を `JSON.parse` し直し、上の階層の `setup_data` の下を明示の積み上げでたどって、`[REDACTED-SETUP]` でない文字列の件数と道（置換の後のキー名）だけを返す関数 `findUnredactedSetup(tree)` を当てる。
- どちらかで 1 件でも見つかれば、一時ファイルを作る前に止め、出力のパスに何も書かずにコード 4。
- 検査を書き出しの「前」に置くことで、一時ファイルにも検査を通らない中身が書かれない（一時ファイルが残る場合でも中身は伏せ済み。6節）。

## 4. 値を表示しない形（NFR8.64・BR2.3）

- 表示はすべて 1 つの報告の部品を通す。報告の部品が受けるのは、決めた文言の番号・件数・位置（行と桁、またはバイトの位置）・パス・道だけで、任意の文字列を受ける口を持たない。
- パスと道は、表示の前に必ず `redactJwt` を通す（ファイルの名前やキー名に JWT の形があっても、表示に出さない）。
- 実行環境の誤りの文言（`JSON.parse` の `SyntaxError` の文、ファイルの誤りの文）をそのまま出さない。`JSON.parse` の誤りは、文言の中の `position <数>` の数字だけを抜き出して位置として出し、抜けなければ位置を出さない。ファイルの誤りは `code`（`ENOENT`・`EACCES` など）だけを出す。
- 成功の表示は、置き換えた JWT の件数・`[REDACTED-SETUP]` にした件数・出力のパスだけ。
- 性質のテストの失敗の表示は、乱数の種と道（`counterexamplePath`）と回数だけにし、反例の値を出さない（7.3節）。

## 5. 入力と出力の守り（NFR8.65〜NFR8.67・NFR6.61・NFR7.61）

### 5.1 呼び方と引数（NFR8.67・NFR7.61）

| 口 | 呼び方 | 引数の誤り（コード 1） |
|---|---|---|
| JSON の口（契約 C7、変えない） | `node perf/<道具>.mjs <入力> <evidence/ の中の出力>` | 引数が 2 つでない |
| テキストの口 | `node perf/<道具>.mjs --text <入力> <evidence/ の中の出力>` | `--text` の後が 2 つでない、出力の拡張子が `.json` |
| evidence の検査の口 | `node perf/<道具>.mjs --scan <根のディレクトリ>`（旗の名前はコード生成で決める） | 根が無い・ディレクトリでない、引数の数が違う |

- 出力のパス（JSON の口・テキストの口）: 親のディレクトリが在ることを確かめ、親を `realpath` で解いた絶対パスのどこかに、名前がちょうど `evidence` のディレクトリがあることを求める（記号のリンクで別の場所へ書かせない）。無ければコード 1。
- 入力と出力が同じ: 入力の `realpath` と、出力の親の `realpath` に出力の名前をつないだものが同じならコード 1。

### 5.2 入力の大きさの上限（NFR8.66）

- 道具の中の定数 `MAX_INPUT_BYTES = 64 * 1024 * 1024`（64 MiB）を、テストが読めるように公開する。
- 中身を読む前に `stat` の大きさで判定する。上限ちょうどは受け、上限＋1 バイトからコード 2。読んだ後に大きさが変わっていても、読んだバイト数が上限を超えればコード 2。
- evidence の検査でも同じ定数で判定し、超えるファイルはパスと大きさだけを表示して検査を失敗にする（8節）。

### 5.3 書き出し（NFR8.65・BR3.3）

- 残存の検査が通った後に、出力と同じディレクトリに一時ファイル `.<出力の名前>.<プロセス番号>.<乱数>.tmp` を排他の作成（`wx`）で作って書き、書き終えたら出力のパスへ名前を替える（同じファイルシステムの中の名前の替えで、途中の状態が出力のパスに見えない）。
- 書き込み・名前の替えのどこかで失敗すれば、一時ファイルを消してコード 5。出力のパスは前のまま（無ければ無いまま）。
- `SIGINT`・`SIGTERM` を受けたら一時ファイルを消してから終える。`kill -9` などで一時ファイルが残った場合も、中身は残存の検査を通った伏せ済みのもので、evidence の検査（8節）がその一時ファイルも調べる。

### 5.4 終わりのコード（NFR6.61）

| コード | 意味 | JSON の口 | テキストの口 | evidence の検査の口 |
|---|---|---|---|---|
| 0 | 成功 | ○ | ○ | 検出 0 件・誤り 0 件 |
| 1 | 呼び出しの誤り | ○ | ○（summary json を渡したときを含む） | 根が無い・引数の誤り |
| 2 | 入力の誤り | ○ | ○ | 飛ばしてはいけない NUL 混じりのファイル・上限を超えるファイル・読めないファイルがあった |
| 3 | キーの衝突 | ○ | 起きない | 使わない |
| 4 | 残存の検出 | ○ | ○ | JWT の形を中身かパスに見つけた |
| 5 | 書き出しの失敗 | ○ | ○ | 使わない（書かない） |

- 1 つのコードに 1 つの意味を固定し、3 つの口で同じ意味に使う（新しいコードは足さない）。evidence の検査は、すべてのファイルを調べ終えてから、検出があれば 4、無くて入力の誤りがあれば 2 で終える（検出を先に知らせる）。

## 7. 仕組みのテストの設計（NFR5.61〜NFR5.63・NFR8.71・team.md Testing Posture）

### 7.1 テストの作り方の決まり

- 道具は、純粋な関数（`redactJwt`・`findResidual`・`redactTree`・`findUnredactedSetup`・引数の判定）と、表示と読み書きを差し替えられる入口 `main(argv, io)` に分ける。テストは主に `main` を一時のディレクトリで直接呼び、表示（標準出力・標準エラー）を捕まえる。終わりのコードが本物のプロセスでも同じことは、子のプロセスで道具を起動する例のテストを 3 つの口で 1 件ずつ置いて確かめる。
- 書き出しの失敗（コード 5）は、`io` の名前の替えを失敗させる差し替えで確かめる（実行する利用者の権限に左右されない）。
- JWT の形の値は、テストの中で `'eyJ'` と base64url の区間を実行の時につないで作る手伝いの関数（例: `makeJwtLike()`）だけから作り、テストのソースと見本のファイルに完成した JWT の形を書かない（NFR8.71）。招待のトークンに似た値も架空の値だけにする。
- テストの説明文は英語、Vitest の時間の上限（既定）を延ばさない。大きな入力の例は、作るのが速い中身（空白で埋めた JSON、`a` の続くテキスト）で作る。

### 7.3 性質のテストの種と道（NFR5.61）

- `fc.assert` の既定の失敗の文は反例の値を含むため、`fc.check` の結果を受け、失敗のときは `seed`・`counterexamplePath`・回数だけを載せた誤りを投げる手伝いの関数を置く。再現は、その種と道を `fc.assert` の引数に渡して流す（手順をテストのファイルの先頭のコメントに書く）。

```text
// 考え方（実装はコード生成。fast-check の fc を読み込んだテストのファイルの中の手伝いの関数）
function assertProperty(prop: fc.IProperty<unknown>, params?: fc.Parameters<unknown>) {
  const r = fc.check(prop, params)
  if (r.failed) throw new Error(`property failed: seed=${r.seed} path=${r.counterexamplePath} runs=${r.numRuns}`)
}
```

### 7.4 verify と CI に入ること（NFR5.62・NFR5.63）

- テストは `frontend/` の Vitest の単体テスト（`verifyUnitTest` の `frontendTest`）で毎回流れ、条件で飛ばす仕組み（`skip`・`todo`・環境による分岐）を持たない。置き場と `vitest.config.ts` の変更、カバレッジの扱いはコード生成の計画の義務とする（`logical-components.md` 4節）。

## 8. verify の evidence の検査（NFR8.68・NFR8.66・Q1: A）

### 8.1 対象

- 根（verify では `aidlc`）の下を、記号のリンクをたどらずに歩く。根からのパスのどこかに名前がちょうど `evidence` のディレクトリがある通常のファイルをすべて対象にする（拡張子で絞らない。git の対象か否かを問わない）。
- 記号のリンク（ファイル・ディレクトリとも）はたどらず、パスを表示して「リンク」として数える。失敗にはしない（git はリンクの先の中身を記録しないため、中身は記録に入らない）。
- 対象のファイルの相対のパスそのものにも `findResidual` を当て、JWT の形があれば検出として数える（ファイルの名前は記録に入るため）。

### 8.2 1 つのファイルの判定の順

1. 大きさが `MAX_INPUT_BYTES` を超える → 「上限超え」。パスと大きさを表示し、入力の誤りとして数える。中身は読まない。
2. 読めない → 「読めない」。パスと誤りの `code` を表示し、入力の誤りとして数える。
3. バイト列のどこかに NUL（0x00）がある →
   - 拡張子が下のバイナリの一覧にある → 「バイナリとして飛ばした」。パスを表示して数え、検査は通る。
   - 一覧に無い（拡張子なし・ドットだけの名前を含む）→ 「飛ばしてはいけない NUL 混じり」。パスを表示し、入力の誤りとして数える。
4. それ以外 → UTF-8 として読み（不正なバイトは置き換えの文字にして読み進める。JWT の形は ASCII のため拾える）、`findResidual` を当てる。見つかればパス・件数・位置（行と桁、1 ファイルにつき先頭の 10 件まで。残りは件数だけ）を表示し、検出として数える。

- NUL は先頭の一部ではなくファイル全体で調べる（上限 64 MiB の中で全体を読むため。NUL を後ろに混ぜたテキストも「NUL 混じり」として扱う。9節）。

### 8.3 バイナリの拡張子の一覧（Q1: A で設計した一覧）

| 種類 | 拡張子（大文字と小文字を区別しない。名前の最後の `.` の後ろで判定） | 入れる理由 |
|---|---|---|
| 画像 | `.png`・`.jpg`・`.jpeg`・`.gif`・`.webp`・`.svgz` | 画面の確かめ（E2E・スモークテスト）の画面の写しを記録に置きうる。`.svgz` は gzip で圧縮した SVG |
| 圧縮 | `.gz`・`.zip` | Playwright の trace（`.zip`）や大きな記録の圧縮を置きうる。`.tar.gz` は最後の `.gz` で当たる |
| 文書 | `.pdf` | 報告を PDF で置きうる |

- 今の `evidence/`（`aidlc/` の下の 2 つ、97 ファイル）の名前を読み取りで確かめた（中身は開いていない）。拡張子は `.json` 22・`.log` 2・`.md` 1・`.tsv` 21・`.txt` 51 で、バイナリの拡張子のファイルは無い。そのため、Q1: A の例に挙がった 9 つのほかに足す拡張子は無い。
- `.svg`・`.html`・`.csv`・`.yaml` などテキストの形式は一覧に入れない（NUL があれば失敗、無ければテキストとして調べる）。
- 一覧は道具の中の 1 つの定数に置き、テストが参照する。一覧に足す（例: Playwright の動画 `.webm`）ときは、理由をこの一覧と同じ形で記録し、依頼者の承認を得てから定数とテストを変える（一覧を広げるほど中身を調べないファイルが増えるため）。
- 残る穴: 一覧の拡張子のファイルは、NUL を含めば中身を調べない。圧縮の中や画像の中に置いた値は、この検査では拾えない（9節・10節）。

### 8.4 表示と終わり

- 終わりに、調べたファイルの数・バイナリとして飛ばした数・リンクの数・検出の数・入力の誤りの数を表示する。飛ばしたファイル・リンク・誤りのファイルは、それぞれパスを 1 行ずつ表示する（パスは `redactJwt` を通す）。中身・断片は出さない。
- 終わりのコードは 5.4節（検出があれば 4、無くて入力の誤りがあれば 2、どちらも無ければ 0）。
- Gradle のタスクは非 0 で失敗し、`verifySecurity` が止まる。CI も同じ `verify` を呼ぶ。

### 8.6 導入の前の一度の実行

## 13. 未決の点（承認の場で確かめたいこと）

- バイナリの一覧の拡張子のファイルについて、先頭のバイト（PNG の `89 50 4E 47`、gzip の `1F 8B`、zip の `PK`、PDF の `%PDF-` など）が拡張子と合うかも確かめ、合わなければ失敗にするか。拡張子だけを替えて置いた UTF-16 のテキストを拾える代わりに、壊れたファイルで落ちうる。Q1: A の範囲（拡張子の一覧）を超えるため、この設計には入れていない。
- `gitleaks dir` を verify にも入れるか（9節）。入れればコミットの前の守りが手順に頼らなくなる代わりに、過去の記録の誤検知で verify が止まりうる。
