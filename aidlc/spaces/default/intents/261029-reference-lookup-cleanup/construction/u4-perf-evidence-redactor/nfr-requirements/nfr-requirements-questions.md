# NFR Requirements の質問 — U4 u4-perf-evidence-redactor（Intent 261029-reference-lookup-cleanup）

この単位には、依頼者に尋ねる質問はありません。U4 は種類が `library`（単独で動かない道具の部品）のため、この段の成果物は security-requirements.md・tech-stack-decisions.md・traceability.json だけで、性能・規模・可用性・観測の要件は対象外です。判断が分かれる点は、機能設計と要件で決まっています。

## 決まっていること（質問しません）

- 要件の枝番は、単位の間で重ならないよう、U4 は `NFRx.61` から振る（U1 は `.1`、U2 は `.21`、U3 は `.41` から）。
- セキュリティは要件 NFR8・NFR9 と `project.md` の Forbidden（認証の値を伏せずに perf の記録へ置かない）、機能設計の決まり（JWT の形の置換・`setup_data` の伏せ字・残存の検査・evidence の検査・テキストの置換の口・失敗のときに何も残さない）のとおり。
- 技術の選び方は機能設計と ADR-004 のとおり: Node の 1 ファイル（依存なし。Node はフロントエンドのビルドが使う版）、テストは `frontend/` の Vitest と fast-check（どちらも既存の依存で、新しい依存は足さない）。
- 入力の大きさの上限は 64 MiB とし、超えたら入力の誤り（終わりのコード 2）で何も書かない。k6 の summary json は数 MB で、この上限に余裕がある。上限は道具の中の定数にし、コード生成で決めた値をテストで確かめる。
- 道具は、入力と出力の値（JWT の形の文字列・伏せた値）を標準出力・標準エラーに出さない。見つかったことは件数と場所（キーの道筋）だけで知らせる。
- 機能設計の段の承認で「直してほしい」と記録した U4 の指摘（標準出力・ログに出る JWT の形でない秘密の穴の記録）は、この段で機能設計の文書に書き足す。
