# NFR Design の質問 — U2 u2-reference-write-check（Intent 261029-reference-lookup-cleanup）

U2（保存前の参照の確かめ）の NFR 設計で、判断が分かれる点だけを尋ねる。各質問の最初の選択肢を推奨とし、理由を添える。

## 決まっていること（質問しません）

- 1回の問い合わせの上限は `REFERENCE` の目的の 5 秒、保存前の段の全体の上限は 10 秒（NFR3.24・NFR3.25）。残りを秒に切り上げて文ごとに絞り、1 秒未満なら流さず 503。
- 長い値の行は U1 の決定どおり SQL の条件で先に除き、確かめでは「無い」とする（U1 の Q1: A、F1: A）。
- 失敗の写し方・監査・ログを出す所（対象DB の例外を結果の型に変える境界の1か所）は NFR 要件のとおり。
- 外部キーの無い参照先での確かめと保存の間のすき間は、既知の制約として受け入れる（NFR1.29）。

## Q1. [性能] 1回の保存で値の違う参照が複数あるときの `check` の呼び方（NFR2.28）

A. 捨ての試しで、参照 1・3・5 個の保存について「参照ごとに順に呼ぶ」形と「1つの問い合わせに束ねる」形の文の数と時間を3種類の DB で測り、順に呼ぶ形で目標（保存の p95 1 秒未満）に収まるなら順に呼ぶ形にする（推奨）。順に呼ぶ形は U1 の `check` をそのまま使え、SQL の部品と SpotBugs の除外を増やさずに済む。収まらないときだけ束ねる形にし、その場で依頼者に諮る
B. 試さずに、初めから束ねる形にする。文の数は減るが、IN の条件の新しい SQL を方言ごとに足すことになり、SQL の部品の変更と境界のテストの見直しが要る

## Q2. [設計] 保存前の段の全体の上限（10 秒）の設定の持ち方

U1 は定義の取得の全体の上限を設定 `MASTERSMITH_TARGET_DB_REFERENCE_READ_TOTAL`（既定 10 秒）にした（U1 の Q2: A）。

A. U1 と同じ設定の値と、締め切りを数える同じ部品を使う（推奨）。どちらも「参照を読む段の全体の上限」で既定が同じ 10 秒のため、設定が1つで済み、運用で直す所も1か所になる。代わりに、定義の取得と保存前の確かめの上限を別々に変えることはできない
B. 保存前の確かめ用に別の設定を置く（既定 10 秒）。別々に変えられるが、設定と確かめのテストが増える

## Q3. [品質] 確かめと保存の間のすき間を再現するテストの、待ち合わせの差し込み先（NFR 要件の承認で直すよう記録した点）

NFR1.29 のテストは、確かめの後・書き込みの前に止めて、ほかの接続で参照先の行を消してから保存を進める。差し込み口は、本番のクラスと境界テストの許可の一覧を変えず、テストの設定での部品の差し替えだけで作る条件。ただし、更新の「変わらないと判定した参照」は、確かめを呼ばずに更新前の行の読み取りと書き込みの間にすき間があるため、確かめの部品を包む形では止められない可能性がある。

A. NFR 設計の中で既存のコード（書き込みの流れと、テストで差し替えられる部品）を読み、作成と更新のそれぞれで止められる差し替え先を具体に決めて書く。作れない場合（本番のクラスに手を入れないと止められない場合）は、文書を書く前に止めて、選択肢を添えて依頼者に諮る（推奨）。条件を守ったまま、作れないことが後で分かる危険を設計の段で潰せる
B. 作成の側だけを確かめるテストにし、更新の「変わらないと判定した参照」のすき間は、外部キーの無い参照先の既知の制約に含めて、テストを置かない。手間は減るが、外部キーのある参照先で 409 になることを更新の側では確かめない

## Q4. [品質] 設計の前提を、文書を書く前に捨ての試しで確かめるか

U1 では、試しを先に流して MySQL の並べ替えの誤り（1038）を見つけ、文書を書く前に直し方を決められた。U2 の前提は、確かめを足した保存の時間（参照 1・3・5 個）と、待ち合わせの差し込み先で止められるか。

A. リポジトリの外の捨ての試しで先に確かめ、結果の要点を文書に写してから書く（推奨）。U1 と同じ進め方で、前提が崩れていたら追加の質問で確かめてから書く。代わりに、この段の時間が延びる
B. コードの読み取りだけで書き、確かめはコード生成に任せる。早いが、前提が崩れていたときにコード生成で設計を直すことになる
