# 捨ての試しの結果 — U2 u2-reference-write-check（NFR 設計）

この段の答え（Q1: A・Q3: A・Q4: A）に従い、設計の文書を書く前に、リポジトリの外の捨ての試しのコードと既存のコードの読み取りで、設計の前提を確かめた。前提は崩れなかった（5節）。ただし、更新のすき間の確かめ方（NFR1.29）は、外部キーの振る舞いに合わせて手順を直す（4.2）。

### 2.4 読み

- 順に呼ぶ形で参照が 1 個から 5 個に増えると、1本ずつでは保存1回あたり約 1〜2 ms（`check` 1文 約 0.5 ms × 4 と往復）、10 本の同時でも p95 で最大 約 13 ms（PostgreSQL 12.93 → 25.70 ms）増える。どの DB・どの数でも、目標（保存の p95 1,000 ms 未満、NFR2.21）の 3% 未満。
- 束ねる形は参照 5 個で 1〜12 ms 速いが、差は目標に比べて小さい。束ねるには、`IN` か `UNION ALL` の新しい SQL を方言ごとに足し、SQL の部品・SpotBugs の `SQL_` の除外・境界テストを見直すことになる（Q1 の B の悪い点）。1文で読む行も最大 201 × n 行になり、確かめのメモリの見積もり（NFR2.27 の「参照の数によらず約 4 MB」）が n 倍に変わる。
- 時間の大半は `countState`（200 行を並べる）と INSERT・確定で、`check` は索引の一致のため軽い。
- 試しは HTTP・認証・内部DB の権限の写しの読み取り・監査を通さない。それらは既存の `bizCreate` の場面（p95 < 1,000 ms）にすでに含まれ、この単位が足すのは読み取りの段の数 ms〜数十 ms だけと見込む。合否は Build and Test・Performance Validation の k6（NFR2.21・NFR2.22）で決める。

## 3. 確かめた項目: すき間の待ち合わせの差し込み先（Q3: A、NFR1.29）

既存のコードを読み取りだけで確かめた。

| 確かめ | 結果 |
|---|---|
| 書き込みの口 | `BusinessDataWriteService` は、⑨ の後に `TargetWriteAccess.withWrite(...)` を1回だけ呼ぶ。`TargetWriteAccess` は `targetdb.service` の公開の interface で、実装は `JdbcTargetWriteAccess`（`@Service`、Bean の名前 `jdbcTargetWriteAccess`）。注入はどこも interface の型（`BusinessDataWriteService`・`TableAccessResolver`）で、`TableAccessResolver` は `product()` だけを呼ぶ |
| ⑩ と書き込みの順 | 機能設計 BR4.1 で、⑩ の読み取り（更新前の行・`countState`・`check`）は読み取りの接続で行い、返してから書き込みの接続を借りる。U2 は ⑩ を `withWrite` の呼び出しの前に置くため、`withWrite` の入口は、作成では「確かめの後」、更新では「更新前の行を読み、変わらないと判定した後」で、どちらも「書き込みの前」に当たる |
| テストで部品を差し替える前例 | `businessdata/testsupport/CountingDataSourceConfig`（`@TestConfiguration` の static な `BeanPostProcessor` が、名前で選んだ Bean を包む）。`BusinessDataTestApp.start(..., sources, ...)` で足す |
| 境界テスト | `ArchitectureTest`・`BusinessDataBoundaryArchitectureTest` は `ImportOption.Predefined.DO_NOT_INCLUDE_TESTS` で読むため、`src/test` の部品は対象の外 |
| TraceAspect | 対象は `..web..`・`..service..`・`..domain..`・`..repository..` の中だけで、`testsupport` の部品は入らない |

判定: 作成と更新の両方で、本番のクラス・公開の口・境界テストの許可の一覧を変えずに、テストの設定で `TargetWriteAccess` の Bean を包むだけで止められる（`reliability-design.md` 4節）。

## 4. 確かめた項目: すき間の外部キーの振る舞い（NFR1.29・NFR3.27）

### 4.1 結果

| 手順 | PostgreSQL | MySQL | MariaDB |
|---|---|---|---|
| 作成: 確かめ（1行）の後に別の接続で参照先 `GAPX` を消し、`r1 = GAPX` で INSERT | 拒否 `23503` | 拒否 `23000`／1452 | 拒否 `23000`／1452 |
| 更新の準備: 行 8002 が `GAPX` を指す。更新前の行を読む（変わらないと判定） | `r1 = GAPX` | 同じ | 同じ |
| 更新 (1): 別の接続で参照先 `GAPX` だけを消す | 外部キーで消せない `23503` | 消せない `23000`／1451 | 消せない `23000`／1451 |
| 更新 (2): 別の利用者が行 8002 の参照を `GAPY` に変え、その後に `GAPX` を消す | どちらも成功 | 同じ | 同じ |
| 更新の書き込み: 確かめなかった値 `GAPX` で行 8002 を更新 | 拒否 `23503` | 拒否 `23000`／1452 | 拒否 `23000`／1452 |
| 書き込みの後の行 | 変わらない（`note=before`、`r1=GAPY`） | 同じ | 同じ |
| 参考: 参照先がある値で同じ行を更新 | 保存 | 保存 | 保存 |

### 4.2 読み

- 作成のすき間は、外部キーの違反で拒否される。既存の変換（セーブポイントへ戻して違反のカラムを確かめ、409 `BUSINESS_REFERENCE_NOT_FOUND`）が最後の守りになる（BR6.1）。
- 更新の「変わらないと判定した参照」では、外部キーのある参照先の行は、その行自身が指している間は消せない。そのため、NFR1.29 の確かめ方の文言（判定の後に別の接続から参照先の行を消す）のままでは、消す操作が外部キーで失敗し、すき間を作れない。すき間は「別の利用者が行の参照を別の値に変え、その後に元の参照先の行を消す」ときにだけ現れ、その場合は書き込みが外部キーの違反で拒否され、行は変わらない。結合テストの手順をこの形にする（`reliability-design.md` 4節、上流との差）。
- 違反の SQLState と業者の番号は、既存の `RowSqlFailureClassifier` が外部キーの違反として分ける形（類 `23`）と同じ。

## 5. 前提ごとの判定

| 前提（出典） | 判定 |
|---|---|
| 参照ごとに順に `check` を呼ぶ形で、保存の p95 1 秒未満に収まる（Q1: A、NFR2.21・NFR2.28） | 成り立つ（3種類。最悪の 10 本の同時でも p95 25.70 ms） |
| 作成と更新の両方で、テストだけの部品の差し替えで確かめと書き込みの間に止められる（Q3: A、NFR1.29） | 成り立つ（`TargetWriteAccess` の Bean を包む） |
| 外部キーのある参照先では、すき間で消えた参照先の値の保存が外部キーの違反で拒否される（BR6.1・NFR3.27） | 成り立つ（作成・更新とも3種類） |
| 更新の「変わらないと判定した参照」のすき間は、参照先の行を消すだけで作れる（NFR1.29 の確かめ方の文言） | 当たらない（外部キーが消す操作を止める）。確かめ方を「参照を変えてから消す」に直す。前提の崩れではなく、手順の直し |

## 6. 後片付け

- `u2trial-` の3つのコンテナは各実行の終わりに消した（実行の後に一覧で 0 件を確かめた）。配備したアプリ・見本の PostgreSQL（`mastersmith-targetdb-postgres-1`）・Mailpit は動いたまま。
- 試しのコードと記録はリポジトリの外の置き場に残した（資格情報は置き場に書いていない。実行ごとに作って環境変数で渡しただけ）。
