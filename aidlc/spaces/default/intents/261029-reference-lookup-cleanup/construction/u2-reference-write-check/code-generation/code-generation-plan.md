### 1.1 U1 への依存（NFR 設計 U2 R-05 の直し）

U2 は U1 の次の型と口に依存する。どれも **U1 の B1（549d38b）と B2（b048ec1）で `develop` に統合済み**で、B3 はその後の `develop`（U4 の B5 13883f6 を含む）から始める（Step 1 で確かめる）。名前は U1 の実装のとおりに使う。

| U1 の型・口 | 置き場 | U2 での使い方 |
|---|---|---|
| `ReferenceLookup.check(Resolved source, String column, ReferenceValue value, TargetReadSession session)` → `ReferenceCheckResult`（`Found`・`NotFoundOrDenied`・`Failed(ReferenceReadFailure)`） | `businessdata.service`・`businessdata.domain` | 確かめる参照ごとに順に呼ぶ（BR4.3・BR4.4、performance-design.md 1節） |

## 9. 計画の承認で確かめたいこと（推奨と理由）

- **Q1. U2 が参照のカラムと参照先・読めるかを知る口。** 推奨: A（`ReferenceLookup` に `writeTargets`・`accessOf` の2つの公開の口を足す）。⑨ の前の保留（BR3.6）と同じ参照先の鍵（BR4.7）に、対象DB を読まずに参照先と `accessOf` が要るが、U1 の DSL の引き方（`dslTable`）は `ReferenceLookup` の中に閉じているため。新しいクラスを足さず、引き方を1か所に保てる。B は `BusinessDataWriteService` の中に同じ引き方を複製する（口は増えないが、DSL の引き方が2か所になる）。
- **Q2. 書き込みの結合テストの表の置き場。** 推奨: A（U1 の `ReferenceTables` に書き込みの組を足す）。U1 が同じクラスに小さな組を足した形と同じで、テストの部品のクラスが増えないため。B は新しい `ReferenceWriteTables` を作る（読み取りの表と分かれて読みやすいが、クラスが1つ増える）。
- **Q3. 参照元の表が空であることの確かめ（基盤の設計 R-03）。** 推奨: A（種の台本の行の数の出力 `COUNTS` に `biz_refcreate` を足す）。種を入れるたびに必ず出て、手順の読み落としが無いため。B は `perf/README.md` に確かめのコマンドを書く。
- **Q4. 結合テストの置き方。** 推奨: A（`ReferenceWrite*IT` の新しいクラスに置き、既存の `*BusinessDataWrite*IT` は変えずに通す）。T-C1（既存のテストを変えずに通す）を、差分で見て分かる形で守れるため。B は既存のクラスに場合を足す（クラスは減るが、既存のテストの変更と見分けにくい）。
- **Q5. `README.md` の書き込みの API の失敗の code の行を直すか。** 推奨: A（直す）。保存前の確かめで `BUSINESS_REFERENCE_NOT_FOUND`・`NOT_EDITABLE_NOT_NULL`（`field` がカラムの名前）・503 が増え、今の行（「参照先に無い値は 409」）では外部キーの無い参照先の拒否と項目の名前の違いが読み取れないため。B は直さない（基盤の設計は環境変数の表を変えないとしているだけで、API の節には触れていない）。
- 3.1節の新しいクラス（domain 5・テストだけの部品 2・テストのクラス）と、3.2節の既存のクラスの形の変更（`ReferenceLookup` の公開の口2つ、`WriteValidation.Valid.held`、`WriteRequestValidator` の多重定義、`BusinessDataWriteService` の構成子）を承認するか。境界テストと SpotBugs の除外は変えない（3.3節）。
