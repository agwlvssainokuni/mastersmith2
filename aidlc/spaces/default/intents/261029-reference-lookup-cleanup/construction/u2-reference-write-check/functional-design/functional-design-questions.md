# Functional Design の質問 — U2 u2-reference-write-check（Intent 261029-reference-lookup-cleanup）

U2（作成・更新の保存前の参照先の確かめ）の機能設計で、上流が「機能設計で決める」とした点と、U1 の設計・レビューで U2 に回った点のうち、判断が分かれるものだけを尋ねる。各質問の最初の選択肢を推奨とし、理由を添える。

## 決まっていること（質問しません）

- 確かめは U1 の口 `check` を使う。U2 は `REFERENCE` の目的で読み取りの接続を 1 本借り、確かめる参照ごとに順に呼ぶ。`NOT_FOUND_OR_DENIED` は 409 `BUSINESS_REFERENCE_NOT_FOUND`（項目の誤り `REFERENCE_NOT_FOUND`）、`FAILED` は理由ごとに既存の code（503 の TIMEOUT・UNAVAILABLE、409 の MISMATCH）に写す（U1 の functional-spec.md の 4.5・D3）。
- 更新では、更新前の行を同じ読み取りの接続で主キーで読み、型に直した値（`TypedValue`）で比べて、値が変わった参照だけを確かめる。行が無いときは参照の拒否より先に既存の「行が無い」の応答にする（AC3.2.4・AC3.2.6・AC3.2.7）。書き込みの接続は、確かめが済んでから借りる（ADR-003）。
- 確かめで拒否された参照が複数あるときは、すべてを確かめ、項目ごとに 1 件ずつ誤りを並べる（契約 C3）。
- 拒否は既存の監査の出来事に、既存の理由 `BUSINESS_REFERENCE_NOT_FOUND` で残す。確かめの読み取りそのものは残さない（契約 C4）。
- 書き込み側の検証の材料は `lookup` を `text` のまま扱う（契約 C3、U1 の D2）。

## Q1. [設計] 作成で、必須（NOT NULL）の参照項目に値を入れられないときの応答（AC1.5.2）

参照先を読めない、または REFERENCE の候補が 201 件以上の項目は、画面で入力不可になる。その項目が必須のとき、作成は行き止まりになる（M1: A で受け入れた）。本文に値が来たときは、権限の無い値と同じく 409 `REFERENCE_NOT_FOUND` にする（AC1.5.2・AC3.1.3）。本文の値が空・無いときの応答を決める。

A. 409 `BUSINESS_REFERENCE_NOT_FOUND` で、項目の誤りの理由を既存の `NOT_EDITABLE_NOT_NULL`（入力できないカラムの NOT NULL で保存できない、利用者には直せない）にする（推奨）。契約 C3 の決めと同じで、画面は US1.5 の文言（「必須の参照項目に値を入れられません」）を出し分けられる。利用者は定義の状態で「読めない・多すぎる」とすでに分かっているため、参照先の存在は漏れない
B. 既存の必須の誤り（400 `VALIDATION_FAILED`、理由 `REQUIRED`）にする。既存の流れのままだが、利用者には直せない誤りが「入力してください」と読め、契約 C3 と食い違う

## Q2. [設計] 大文字と小文字だけが違う値の確かめ（U1 のレビューの指摘）

MySQL・MariaDB の既定の照合順序は大文字と小文字を区別しないため、参照先に `ABC` しか無くても `abc` で引くと行が当たる。PostgreSQL は区別する。このままだと、同じ値の確かめの結果が DB によって割れる。

A. `check` で当たった行の値を読み、本文の値と文字どおり（型に直した値で）一致するときだけ「ある」とする（推奨）。3 種類の DB で同じ結果になり、画面で選んだ値（参照先の値そのもの）はいつも通る。代わりに、利用者が大文字と小文字を変えて手で入れた値は、MySQL でも「無い」として拒否される
B. 各 DB の照合順序に任せる（MySQL・MariaDB では `abc` が通り、PostgreSQL では拒否される）。外部キーも同じ照合順序で働くため保存とは食い違わないが、DB ごとに結果が割れ、AC1.4.5 の「DB ごとに結果が割れない」と合わない
