- 対象DB へ書き込むテスト（業務データの作成・更新・削除を範囲に入れる場合）は、アプリの対象DB への接続とテストの接続が別のため、アプリのトランザクションの巻き戻しに頼らない。3種類の対象DB のすべてで、テストのクラスごとに名前の重ならないスキーマ（MySQL・MariaDB ではデータベース）と表を作って行を用意し、終わったら消す。書いた後の値は、アプリとは別の接続で読み直して確かめる。

<!-- 元: team.md の ## Testing Posture -->
- 業務データを表示する E2E は、見本の対象DB（PostgreSQL の1種類）がコンテナで動いていることを前提にする。`./gradlew e2eTest` は始める前に対象DB に届くかを確かめ、届かなければ起動の手順を示して失敗する（Mailpit と同じ扱い。起動・停止はしない）。流れが使う行は、その流れで自分で作るか、流れの専用のスキーマに置き、見本の行は架空の値だけにする。対象DB の資格情報は Playwright の `webServer.env` に置かずプロセスの環境変数で渡し、報告の json を文字列で検索して資格情報・接続先の値が入っていないことを確かめる。

<!-- 元: team.md の ## Testing Posture -->
- 業務データの一覧・詳細（と、範囲に入れるなら作成・更新・削除）の機能では、次のテストを必ず書く（役割・権限の機能と同じ扱い）。★印の項目は要件が未確定のため、要件定義で決めてからテストを書く。具体的な上限の値は設計の段で決め、決めた値の境界で確かめる。
  - 権限ごとの操作の可否: テーブルの主権限と補助権限の組ごとに、業務データの API を上の「共通の形」で確かめる。作業ロールを切り替えた直後・割り当てを変えた直後の次の要求で切り替わること。
  - 主キーとビュー: 主キーの無いテーブルとビューでは、行を1件に決められない操作（更新・削除など）を、画面で隠すだけでなくサーバー側で拒否する。主キーが複数のカラムのテーブルも確かめる。★主キーの無いテーブルで詳細を見せるか
  - カラムの出し分け: カラムの主権限が NONE（読めない）のカラムは、画面で隠すだけでなく API の応答に含めないことを確かめる。DSL の表示の設定（`list.visible`・`detail.visible`）で隠すだけのカラムの扱いは設計の段で決め、決めた側の動作を明示したテストにする。
  - IDOR と一括代入: スキーマ名・テーブル名・主キーの値・並べ替えの列・検索の列を差し替えた要求（適用中の DSL に無い名前、権限の無いテーブル、存在しない行）は拒否され、状態が変わらないこと。作成・更新の本文に許していないカラムを足しても反映されないこと。
  - 403 と 404 の使い分け: 権限の無いテーブル・DSL に無いテーブル・存在しない行の応答の状態コードと code をそろえるか。★使い分け（決めた側の動作を明示したテストにする）
  - SQL の組み立て: 識別子は適用中の DSL にある名前と照らし、値はバインド変数で渡すこと。識別子・検索の値・並べ替えに `'`・`"`・`;`・`--`・バッククォート・改行を含めても、SQL として解釈されないこと（Code Style の SQL の組み立ての決まりを確かめる）。
  - 3種類の対象DB の境界の値: 一覧・詳細（と書き込み）を、MySQL・MariaDB・PostgreSQL のすべてで結合テストで確かめる。型の違い・識別子の大文字と小文字・NULL の並びと、境界の値（最大の整数・桁の多い小数・NULL）を含める。
  - 行の数の上限と時間切れ: 一覧のページの大きさの上限の境界（上限ちょうどは受け付け、超えると拒否）。JDBC の取り出しの上限（`setMaxRows` か問い合わせの上限）を置き、上限を超える行を内部で読まないこと。応答しない対象DB での時間切れの応答（既存の ServerSocket の方式）。
  - 部分一致の検索: 部分一致の検索を設けるなら、検索の値の `%`・`_`・エスケープの文字が一致の条件として働かない（エスケープして渡す）こと。
  - 画面に出す値: 業務データの値とカラムの表示名を信頼できない入力として扱い、`<script>`・`<img onerror>`・`"`・`'`・`javascript:` を含めても、一覧・詳細で文字として出る（HTML として描かない、リンクの先にしない）こと。
  - 道に乗る主キーの値: 画面の道に乗る主キーの値（複合の主キー、`/`・`%`・`?`・`#`・空白・引用符を含む値）をエンコードし、サーバー側でデコードの後に照らすこと。
  - 接続の数: 業務データの API が1要求で使う対象DB の接続と内部DB の接続の数を、既存の `*ConnectionUsageIT`（`NavigationConnectionUsageIT` など）と同じ形の結合テストで決定的に確かめる。
  - 性質ベースのテスト: テーブルの主キーの有無・ビューか・主権限・補助権限から許す操作の集合を求める関数と、識別子の照合の部品は純粋な関数にし、jqwik・fast-check で性質（権限を足しても許す操作は減らない、主キーの無いテーブルに行を1件に決める操作が出ない、DSL に無い名前は拒否される、引用符・`;`・改行を含む任意の文字列でも SQL の構文として解釈されない など）を確かめる。
  - 漏えい: 業務データの行の値（主キーの値を含む）と対象DB の接続情報が、アプリのログ（TRACE を有効にした `XxxSecretLeakIT`）・トレースの属性（外部へ送る設定を有効にした結合テスト）・エラー応答に含まれないこと。JDBC の例外のメッセージが応答にもログにも出ないこと。
  - 監査: ★業務データの操作（読み取りを含めるか）を監査に残すか、残す中身、対象DB の確定と監査の行の一方だけが残ったときの扱い。決まった側の動作を明示したテストにする。
  - 画面: 一覧・詳細の画面ごとのアクセシビリティ検査、権限の無いテーブルへ直接移ったときの 403 の表示、操作の可否に合わせてボタンが押せない（または出ない）こと。

- 業務データの読み書きは、新しい機能のパッケージ（名前は設計の段で決める）に置き、自分の `<機能>BoundaryArchitectureTest` を足す。既存の `TargetDbBoundaryArchitectureTest`（書き込み・`JdbcTemplate`・`@Transactional` の禁止）と `RoleBoundaryArchitectureTest`（`role` に依存してよい相手）は、緩めずに足す形を先に検討し、緩める・依存してよい相手を足す必要があるときは、上の決まりどおりコード生成の計画に明記して依頼者の承認を得る。

- 業務データの SQL の DB の種類ごとの差（ページ送り・識別子の引用符・NULL の並びなど）は、repository の層の DB の種類ごとのクラス（既存の `SchemaQueries`・`MysqlSchemaQueries`・`PostgresSchemaQueries` の形）に閉じ、service の層は DB の種類で分岐しない。

<!-- 元: team.md の ### バックエンド（Java） -->
- 業務データの行の値は、DB の型ごとの対応を repository の層の1か所で決めて受け渡す。整数の長い型（`BIGINT` など）と小数（`DECIMAL`・`NUMERIC`）は文字列で渡す。日時のタイムゾーンの変換の形（どの型を、どこで、どの時差に直すか）は要件定義で決め、変換はサーバー側の1か所（今の `ColumnValueCodec`）と画面の側の1か所（`src/shared/format/`）に閉じる。JVM・ブラウザの既定のタイムゾーンを暗に使わず、時差を明示に渡す。バイナリと大きな文字列には上限を置く（値は設計の段で決める）。

<!-- 元: team.md の ### バックエンド（Java） -->
- 業務データの行の値（主キーの値を含む）を持つ型は、個人に関する値を持つ record と同じく `toString` を上書きして値を伏せる（`TraceAspect` が web・service・domain・repository の引数と戻り値を TRACE に出すため）。行を `Map` などの汎用の型のまま層をまたいで渡さない。JDBC の例外のメッセージは、行の値が入りうるため、エラー応答だけでなくアプリのログにも出さない（SQLState・業者のエラーの番号・例外のクラスの名前だけを出す）。主キーの値を道（URL）に置かないか、トレースの属性の道を道の雛形に置き換えるかは設計の段で決め、外部へ送る設定を有効にした結合テストと TRACE を有効にした `XxxSecretLeakIT` で確かめる（固い制約は `project.md` の Forbidden）。

<!-- 元: team.md の ### バックエンド（Java） -->
- 対象DB への問い合わせには、目的ごとの時間の上限を必ず付ける（今の `ReadPurpose` と `TargetDbProperties.QueryTimeout` の形に、一覧・詳細（と書き込み）の目的を足す。値は設計の段で決める）。

<!-- 元: team.md の ### バックエンド（Java） -->
- 対象DB へ書き込む場合（業務データの作成・更新・削除を範囲に入れる場合）は、書き込みの接続と資格情報を読み取りの接続（読み取りだけのアカウント）と分け、どちらも環境変数（`.env`）だけから受け取る（固い制約は `project.md` の Mandated）。対象DB のトランザクションは対象DB 用の別のトランザクションの管理者で業務処理の層に置き、内部DB の接続を持ったまま対象DB を待たない。監査など内部DB への書き込みは、対象DB の確定の後に別の短いトランザクションで行う。見本の対象DB に足す書き込みのアカウントとその権限は、README と見本の初期化に書く。

- 業務データの一覧・詳細の画面は、今の置き場の `features/tables` を置き換える1つの機能にする。テーブルを指す道を作る関数は1か所のままにし、一覧の表などほかの機能でも使う部品は `src/shared/` に置く。業務データの値は `any` で受けず、`unknown` か union で受ける。

<!-- 元: team.md の ### 静的解析とセキュリティ検査 -->
- 業務データの SQL を組み立てて実行する部品は1つ（DB の種類ごとに分けるなら種類ごとに1つ）に閉じる。識別子（スキーマ名・テーブル名・カラム名・並べ替えの列）は適用中の DSL にある名前と照らしてから引用し、値はバインド変数で渡す（固い制約は `project.md` の Forbidden）。SpotBugs の `SQL_` の指摘の除外は、その部品のクラスの名前・メソッドの名前・パターン名の3つで絞り（パッケージや `SQL_` の全体では外さない）、理由と識別子が DSL の名前の照合を通ったものだけである根拠を書く。除外を足す・広げるときは、コード生成の計画に明記して依頼者の承認を得る。業務データの機能の境界テスト（ArchUnit）で、`java.sql.Connection` の `prepareStatement`・`createStatement` を呼んでよい場所をその部品だけに絞る。
