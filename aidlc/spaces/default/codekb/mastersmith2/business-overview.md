# 業務の概要（mastersmith2）

## 目的

mastersmith2 は、MasterSmith（マスタ管理アプリ）のリポジトリである。現時点では、管理画面の土台（骨格・認証・管理者向け API の認可・監査ログ）までが実装されている。業務データ（マスタ）を扱う機能は、まだ1つも無い。

配備先は当面、開発者の PC 上のコンテナ（colima）だけである。

## 利用者と、今ある機能

| 利用者 | 機能 | 主な実装（部品は `component-inventory.md`） |
|---|---|---|
| 管理画面の利用者 | メールアドレスとパスワードでログインし、アクセストークン（JWT）とリフレッシュトークン（Cookie）を受け取る。連続で失敗するとアカウントがロックされる | `auth` |
| 管理画面の利用者 | リフレッシュトークンでアクセストークンを更新する（使ったリフレッシュトークンは無効にし、新しいものを発行する） | `auth` |
| 管理画面の利用者 | ログアウトする（画面側でトークンを破棄し、サーバー側でリフレッシュトークンを無効にする。アクセストークンは有効期限まで使える） | `auth`・`frontend-feature-auth` |
| 管理者 | 管理者向け領域（画面 `/admin`、API `/api/admin/**`）に入る。中身は今は置き場（プレースホルダ）だけ | `access`・`frontend-feature-admin` |
| 運用者・監査者 | 認証の出来事（ログインの成功・失敗、ログアウト）と、管理者向け API へのアクセス拒否を、追記だけの監査ログとして内部DBに残す | `audit` |
| 運用者 | 起動時に初期管理者を1回だけ作る（設定は環境変数で渡す） | `user` |
| 開発者（運用者を兼ねる） | 1コマンドの検査（`./gradlew verify`）で統合前の関門を通し、コンテナで起動・停止し、必要なときだけ手元の監視を起動する | `build-and-verify`・`container-runtime`・`perf-and-monitoring` |

## 業務上の決まり（コードで確かめたもの）

- ログインの失敗は、理由（利用者がいない・パスワード誤り・ロック中）によらず同じ応答（401 / `AUTHENTICATION_FAILED`）にし、応答から利用者の存在を推測できないようにしている。
- 監査ログは内部DBの `audit_events` 表に追記するだけで、変更・削除の処理を持たない。記録は元の操作の確定の後に行い、元の操作が取り消されたら記録しない。書き込みに失敗しても元の操作は失敗させない（ERROR のログ1件で知らせ、再試行しない）。
- 管理者かどうかは、要求ごとに内部DBから読んだ利用者の値で判断する（トークンの中身や画面から送られた値は使わない）。画面の管理メニューを隠すことは、サーバー側の確認の代わりにしていない。
- 秘密情報（署名鍵・初期管理者のパスワード・DB のパスワード）は `backend/src/main/resources/application.yaml` に書かず、環境変数の参照だけを置いている。

## この Intent（`260923-dsl-schema-loader`）との関係

この Intent は、ロードマップの Intent A（DSL のスキーマ定義）・D（対象DBのメタデータからの既定 DSL の生成）・E（DSL の読み込み・検証とプレビュー→適用）をまとめたものである。これが、業務データに触れる最初の機能になる。

コードを調べた結果、次のことが分かった。

- 対象DB（MySQL・MariaDB・PostgreSQL、`mastersmith.target-db.*`）への接続、DSL（YAML＋JSON Schema）、メタデータの読み取り、プレビュー・適用に当たるコード・設定・画面・テストは、どこにも無い。すべて新しく作ることになる。
- 置き場は用意されている。管理者のみの API は `/api/admin/` の下に置けば守られ、管理画面は機能ごとの登録ファイルで差し込める（`api-documentation.md` の「内部の差し込み口」）。

足りないものと、既存の仕組みとの間の懸念は `code-quality-assessment.md` の「この Intent に向けた懸念」にまとめた。
