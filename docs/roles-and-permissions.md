# ロールと権限

管理の画面の「権限が無い」の扱い、グループ・ロールと権限・業務のメニューの API、ロール・グループ・権限の受け渡しの画面、骨組みの画面、API のアクセス制御をまとめた文書です。

## 管理の画面の「権限が無い」の扱い

管理の画面（DSL の管理・招待の管理・利用者の管理・ロール・グループ・権限の受け渡し）が管理の API から「権限が無い」（`/api/admin/` の下・403・`code` が `ACCESS_DENIED`）を受けたときの表示とログインの状態の読み直しを、画面の骨組み（`frontend/src/app/admin-forbidden/`）の1か所で扱います。

- **表示（S6）**: サイドバーと上の帯はそのままで、コンテンツの領域が「この画面を使う権限がありません」と「ホームへ戻る」のリンクに置き換わります（見出しはその画面のサイドバーの項目の名前）。開いていた確かめや入力の表示は閉じます。サーバーの `detail` などの値は出しません。管理者でない利用者が管理の画面の URL を直接開いたときも同じ表示です（「ページが見つかりません」は、登録に無い URL だけに出ます。管理の画面の一覧の道 `/admin` そのものは画面が無く、管理者にも管理者でない利用者にも「ページが見つかりません」になります）。
- **読み直し**: S6 になったとき、ログインの状態を1回読み直します（トークンの更新と同じ API）。管理者でなくなっていれば、サイドバーの管理の項目とホームの管理のカードが消えます。決まった間隔の読み直しはしません。読み直しが失敗したときは、今までの 401 と同じくログアウトになります。
- **判定の置き場**: 「権限が無い」の判定は `frontend/src/shared/api-client/adminForbidden.ts` の `isAdminForbidden` だけで行い、各画面は失敗を骨組みの `useAdminForbidden` に渡します。`code` の無い・違う 403 は、各画面の今までの誤りの扱いのままです。401 の扱い（更新と送り直し、ログイン画面への移動）は変わりません。
- **サーバー側が正**: 表示とメニューを隠すことは画面の切り替えにすぎず、使えるかどうかはサーバー側（401・403）で決まります。
- **自分の氏名と言語の反映**: 管理者が自分自身の氏名・言語を変えたときに、上の帯の氏名と画面の言語を直後から変える口（`frontend/src/app/display-settings/useApplyOwnProfile.ts`）を用意しました（利用者の管理の画面が使います）。テーマと文字の大きさ、管理者の印は変えません。

## グループの管理の API

管理者が利用者のグループを作り、名前を変え、メンバーを足し外し、消す API です。どれも `/api/admin/groups` の下にあり、API の分類は `ADMIN`（管理者だけ）です。`/api/admin/**` の決まり（未認証・停止中の利用者は 401 `AUTHENTICATION_REQUIRED`、管理者でない利用者は 403 `ACCESS_DENIED`）に乗ります。グループへのロールの割り当ては「ロールと権限の API」、画面は「ロール・グループ・権限の受け渡しの画面」にあります。

| API | 成功 | 主な失敗 |
|---|---|---|
| `GET /api/admin/groups?page=` | 200 と1ページ（`items`・`page`・`size` 20・`total`）。行は `groupId`・`name`・`memberCount`・`assignedRoleCount` | 400 `VALIDATION_FAILED`（page が 1 以上の整数でない） |
| `POST /api/admin/groups`（`name`） | 201 と `groupId`・`name`・`createdAt`・`updatedAt` | 400 `VALIDATION_FAILED`（`fieldErrors` の `name`）・409 `GROUP_NAME_DUPLICATE`・409 `GROUP_BUSY` |
| `GET /api/admin/groups/{groupId}` | 200 と `groupId`・`name`・`members`（足した順に全件。各人の `userId`・`displayName`・`email`・`suspended`） | 404 `GROUP_NOT_FOUND` |
| `PUT /api/admin/groups/{groupId}`（`name`） | 204（本文なし） | 400・404 `GROUP_NOT_FOUND`・409 `GROUP_NAME_DUPLICATE`・409 `GROUP_NO_CHANGE`（今と同じ名前）・409 `GROUP_BUSY` |
| `DELETE /api/admin/groups/{groupId}` | 204 | 404 `GROUP_NOT_FOUND`・409 `GROUP_IN_USE`（本文に残りの `members`・`assignedRoles` の数）・409 `GROUP_BUSY` |
| `POST /api/admin/groups/{groupId}/members`（`userId`） | 204 | 400（`userId` が無い・正の整数でない）・404 `GROUP_NOT_FOUND`・404 `USER_NOT_FOUND`・409 `GROUP_NO_CHANGE`（すでにメンバー）・409 `GROUP_BUSY` |
| `DELETE /api/admin/groups/{groupId}/members/{userId}` | 204 | 404 `GROUP_NOT_FOUND`・404 `USER_NOT_FOUND`・409 `GROUP_NO_CHANGE`（メンバーでない）・409 `GROUP_BUSY` |

- **名前**: 前後の空白を除いてから判定して保存します。除いた後が 1〜64 文字（コードポイント）で、制御文字を含めません。重なりは大文字と小文字を区別せずに判定し、全角と半角は別の文字です。
- **メンバー**: 足せるのは登録の終わった利用者だけです（招待中の人は利用者 ID を持ちません）。利用停止中の利用者も足せます。判定はグループの有無、利用者の有無、メンバーかの順です。
- **削除**: メンバーかロールの割り当てが残るグループは消せません（409 `GROUP_IN_USE`）。メンバーも割り当ても無いグループは行ごと消えます。
- **本文**: 決めた項目（`name`・`userId`）だけを読み、ほかの項目（ID・日時・作成者など）は読み捨てます。壊れた JSON は 400 `MALFORMED_REQUEST` です。
- **同時の操作**: グループを変える操作は、最初にそのグループの行を排他します。行の排他の待ちの上限は 3 秒、名前の一意の鍵とメンバーの主キーの待ちは H2 の既定の約 2 秒で、超えると巻き戻して 409 `GROUP_BUSY` で断ります（状態は変わりません。少し待ってやり直してください）。同じ名前の作成・変更が重なったときは、後の側が先の側の確定を見たかどうかで code が分かれます。確定を見れば 409 `GROUP_NAME_DUPLICATE`、先の側が確定しないまま鍵の待ちの上限を過ぎれば 409 `GROUP_BUSY` です。一意の制約の違反の文（鍵の値を含む）は、応答・ログ・監査に出しません。
- **監査**: 成功した変える操作と、業務の理由で断った変える操作（404・409 の `GROUP_NAME_DUPLICATE`・`GROUP_NO_CHANGE`・`GROUP_IN_USE`）を残します（`docs/operations.md` の「監査ログ」）。入力の誤り（400）・`GROUP_BUSY`・一覧と詳細の読み取りは残しません。
- **指標**: 既存の `http.server.requests` で道ごとに数えます（新しい指標は足していません）。

## ロールと権限の API

管理者がロールを作り、名前を変え、消し、ロールごとに権限を設定する API です。どれも `/api/admin/roles` の下にあり、API の分類は `ADMIN`（管理者だけ）です。`/api/admin/**` の決まり（未認証・停止中の利用者は 401 `AUTHENTICATION_REQUIRED`、管理者でない利用者は 403 `ACCESS_DENIED`）に乗ります。利用者・グループへのロールの割り当て、作業ロール、自分の権限の木の API と、実効の権限の解決の口は下の「割り当てと作業ロール」、ロールと権限の設定を YAML で書き出し・読み込む API は下の「権限の受け渡し」にあります。画面は「ロール・グループ・権限の受け渡しの画面」にあります。

| API | 成功 | 主な失敗 |
|---|---|---|
| `GET /api/admin/roles?page=` | 200 と1ページ（`items`・`page`・`size` 20・`total`）。行は `roleId`・`name`・`userCount`・`groupCount`（直接の割り当ての利用者の数と、割り当てたグループの数） | 400 `VALIDATION_FAILED`（page が 1 以上の整数でない） |
| `POST /api/admin/roles`（`name`） | 201 と `roleId`・`name`・`createdAt`・`updatedAt` | 400 `VALIDATION_FAILED`（`fieldErrors` の `name`）・409 `ROLE_NAME_DUPLICATE`・409 `ROLE_BUSY` |
| `GET /api/admin/roles/{roleId}` | 200 と `roleId`・`name`・`createdAt`・`updatedAt` | 404 `ROLE_NOT_FOUND` |
| `PUT /api/admin/roles/{roleId}`（`name`） | 204 | 400・404 `ROLE_NOT_FOUND`・409 `ROLE_NAME_DUPLICATE`・409 `ROLE_NO_CHANGE`（今と同じ名前）・409 `ROLE_BUSY` |
| `DELETE /api/admin/roles/{roleId}` | 204（権限の設定も一緒に消える） | 404 `ROLE_NOT_FOUND`・409 `ROLE_IN_USE`（割り当てが残る。`detail` ではなく応答の `assignedUsers`・`assignedGroups` に数）・409 `ROLE_BUSY` |
| `GET /api/admin/roles/{roleId}/permissions/schemas` | 200 と `items`（スキーマの節） | 404 `ROLE_NOT_FOUND`・409 `DSL_NOT_APPLIED` |
| `GET …/permissions/tables?schema=` | 200 と `items`（そのスキーマの下のテーブルの節） | 400（`schema` が無い・空・128 文字を超える）・404・409 `DSL_NOT_APPLIED` |
| `GET …/permissions/columns?schema=&table=` | 200 と `items`（そのテーブルの下のカラムの節） | 400・404・409 `DSL_NOT_APPLIED` |
| `PUT /api/admin/roles/{roleId}/permissions`（`scope`・`entries`） | 204（差分だけを保存する） | 400（`fieldErrors`）・404・409 `PERMISSION_TARGET_NOT_IN_DSL`・409 `DSL_NOT_APPLIED`・409 `ROLE_NO_CHANGE`（変わる点が無い）・409 `ROLE_BUSY` |
| `POST /api/admin/roles/{roleId}/permissions/clear`（`targets`） | 204（指定した対象の明示の設定を消す。今の DSL に無い対象も消せる） | 400・404・409 `ROLE_NO_CHANGE`（消すものが無い）・409 `ROLE_BUSY` |

- **名前**: 前後の空白を除いてから判定して保存します。除いた後が 1〜64 文字（コードポイント）で、制御文字を含めません。重なりは大文字と小文字を区別せずに判定します（グループと同じ決まり）。
- **木の節**: 各節は `schemaName`・`tableName`・`columnName`（その階層より下は空）、`displayName`（`Accept-Language` で日本語か英語の表示名。今の DSL に無い対象は物理名）、`explicit`（明示の `main`・`create`・`delete`。設定なしは空）、`effective`（上の階層から受け継いだ後の実効の値）、`inheritedFrom`（主権限の出どころの階層）、`inMenu`・`inCurrentDsl`・`hasChildren` を持ちます。今の DSL に無いが設定の残る対象も、`inCurrentDsl: false` で並びます。
- **主権限**: `NONE`・`READ`・`FULL` の3つです。`create`・`delete` は補助の権限で、スキーマとテーブルの階層で持ちます（カラムの行に入れると 400）。空は上から受け継ぎます。下の階層の明示の値は上の階層の値より優先します。
- **保存の範囲**: `scope` がスキーマならそのスキーマの行だけ、テーブルならそのテーブルとその下のカラムの行だけを受け付けます。範囲の外の行・重なる行・空の `entries` は 400 です。今の DSL に無い対象を保存しようとすると、全体を断ります（409 `PERMISSION_TARGET_NOT_IN_DSL`、何も保存しない）。
- **DSL が無いとき**: 適用済みの DSL が無いと、木の読み取りと保存は 409 `DSL_NOT_APPLIED` です。ロールの作成・名前の変更・削除と、設定を消す操作は DSL が無くても行えます。
- **本文**: 決めた項目だけを読み、ほかの項目（ID・日時・作成者など）は読み捨てます。壊れた JSON は 400 `MALFORMED_REQUEST` です。
- **同時の操作**: ロールを変える操作は、最初にそのロールの行を排他します。行の排他の待ちの上限は 3 秒、名前の一意の鍵の待ちは H2 の既定の約 2 秒で、超えると巻き戻して 409 `ROLE_BUSY` で断ります（状態は変わりません。少し待ってやり直してください）。同じ名前の作成・変更が重なったときは、後の側が先の側の確定を見たかどうかで code が分かれます。確定を見れば 409 `ROLE_NAME_DUPLICATE`、先の側が確定しないまま鍵の待ちの上限を過ぎれば 409 `ROLE_BUSY` です。一意の制約の違反の文（鍵の値を含む）は、応答・ログ・監査に出しません。
- **監査**: 成功した変える操作と、業務の理由で断った変える操作（404・409 の `ROLE_NAME_DUPLICATE`・`ROLE_NO_CHANGE`・`ROLE_IN_USE`・`PERMISSION_TARGET_NOT_IN_DSL`・`DSL_NOT_APPLIED`）を残します（`docs/operations.md` の「監査ログ」）。入力の誤り（400）・`ROLE_BUSY`・読み取りは残しません。
- **指標**: 既存の `http.server.requests` で道ごとに数えます（専用の指標はありません。割り当てと作業ロールの口も同じ）。

### 割り当てと作業ロール

ロールは、利用者へ直接割り当てるか、グループへ割り当てて（そのメンバー全員が持つ）使います。管理の口は `ADMIN`、自分の作業ロールと自分の権限の木の口は `AUTHENTICATED`（ログインした利用者なら誰でも。主体は要求の文脈から読み、利用者を指す値を受け取りません）です。

| API | 分類 | 成功 | 主な失敗 |
|---|---|---|---|
| `GET /api/admin/roles/{roleId}/assignments` | ADMIN | 200 と `users`（`userId`・`displayName`・`email`・`suspended`・`sources`）と `groups`（`groupId`・`name`） | 404 `ROLE_NOT_FOUND` |
| `POST /api/admin/roles/{roleId}/assignments`（`userId` か `groupId` のちょうど一方） | ADMIN | 204 | 400（両方が無い → `userId`、両方ある → `groupId`）・404 `ROLE_NOT_FOUND`・`USER_NOT_FOUND`（招待中の人を含む）・`GROUP_NOT_FOUND`・409 `ROLE_NO_CHANGE`（割り当て済み）・409 `ROLE_BUSY`・409 `GROUP_BUSY` |
| `DELETE /api/admin/roles/{roleId}/assignments/users/{userId}` | ADMIN | 204 | 404 `ROLE_NOT_FOUND`・409 `ROLE_NO_CHANGE`（割り当てが無い。いない利用者も同じ）・409 `ROLE_BUSY` |
| `DELETE /api/admin/roles/{roleId}/assignments/groups/{groupId}` | ADMIN | 204 | 404 `ROLE_NOT_FOUND`・409 `ROLE_NO_CHANGE`（割り当てが無い。いないグループも同じ）・409 `ROLE_BUSY`・409 `GROUP_BUSY` |
| `GET /api/admin/groups/{groupId}/roles` | ADMIN | 200 とロールの参照（`roleId`・`name`、ID の順） | 404 `GROUP_NOT_FOUND` |
| `GET /api/admin/users/{userId}/roles` | ADMIN | 200 とロールと出どころ（`roleId`・`name`・`sources`、ID の順） | 404 `USER_NOT_FOUND` |
| `GET /api/me/work-role` | AUTHENTICATED | 200 と自分のロール（`roles`、ID の順）と今の作業ロール（`current`。ロールが無ければ null） | 401 |
| `PUT /api/me/work-role`（`roleId`） | AUTHENTICATED | 204（今の保存と同じなら何もしない成功） | 400（`roleId` が無い）・409 `ROLE_NOT_ASSIGNED`（自分のロールでない。存在しないロールも同じ）・409 `ROLE_BUSY` |
| `GET /api/me/permissions/schemas` | AUTHENTICATED | 200 と `workRole` と `items`（スキーマの節） | 401 |
| `GET /api/me/permissions/tables?schema=` | AUTHENTICATED | 200 と `items`（そのスキーマの下のテーブルの節） | 400（`schema` が無い・空） |
| `GET /api/me/permissions/columns?schema=&table=` | AUTHENTICATED | 200 と `items`（そのテーブルの下のカラムの節） | 400（`schema`・`table` が無い・空） |

- **出どころ**: `sources` の各要素は `type`（`USER` は直接の割り当て、`GROUP` はグループ経由）と、グループ経由のときの `groupId`・`name` です。同じロールを直接とグループの両方で持つときは両方が並びます。
- **作業ロールの決め方**: 利用者のロールは「直接の割り当て」と「メンバーであるグループの割り当て」を合わせたものです。保存した作業ロールが今のロールに含まれればそれ、含まれなければ ID の最も小さいロール（最初のロール）、ロールが無ければ無しです。割り当てが外れて読み替えても保存は書き換えず、後でまた割り当てられれば保存した作業ロールに戻ります。保存を書くのは `PUT /api/me/work-role` だけです。ロールを消すと、そのロールを指す保存も同じトランザクションで消えます。
- **実効の権限**: 有効な作業ロールの設定だけで決めます（ほかのロールの設定を合算せず、管理者の印も使いません）。作業ロールが無い・適用済みの DSL が無い・対象が今の DSL に無いときは `NONE`・不可です。自分の権限の木では、DSL が無いと `items` が空、作業ロールが無いと `workRole` が null ですべて `NONE` です。木の節は `schemaName`・`tableName`・`columnName`・`displayName`（`Accept-Language` の言語）・`effective`・`inMenu`・`hasChildren` を持ちます。
- **管理の可否**: ロールを持っても管理の API は使えません。管理の可否は管理者の印（`users.admin_flag`）だけで決めます（すべての `ADMIN` の口で、全権限のロールを持つ印の無い利用者が 403 になることを `RoleGrantsNoAdminAccessIT` で確かめています）。
- **反映**: 割り当て・切り替えの結果は次の要求からサーバー側で効きます。実効の権限はトークンや画面から送られた値を使わず、要求ごとに内部DB から求めます。
- **実効の権限の解決の口（業務のメニュー・業務データなど、ほかの機能向け）**: `role.service.EffectivePermissionResolver` を使います。対象が1つのときは `resolve(userId, target)`（有効な作業ロールを決める読み取り4回と祖先の行の読み取り1回）、2つ以上の対象を判定するときは `snapshotFor(userId)` を1回呼び、返った写しで判定してください（読み取り4回と設定の読み取り1回で、1回の要求の中で同じ作業ロールで答えます）。写しは要求をまたいで持たないでください。有効な作業ロールだけが要るときは `effectiveWorkRole(userId)` です。
- **同時の操作**: 割り当ての操作はロールの行を、グループへの割り当てはグループの行も排他します（待ちの上限を過ぎるとロールは 409 `ROLE_BUSY`、グループは 409 `GROUP_BUSY`）。作業ロールの切り替えはロール・グループの行を排他せず、保存の1行を書くだけです。ロールの割り当てを外す操作と重なっても、外したロールを保存したまま残しません（外れたロールは読みで最初のロールに読み替えます）。同じ利用者の初めての切り替えが重なったときは、後の側が 409 `ROLE_BUSY` になりえます（少し待ってやり直してください）。グループの削除は、ロールの割り当てが残ると 409 `GROUP_IN_USE` で断ります（グループの一覧の `assignedRoleCount`）。
- **監査**: 割り当て・外し・作業ロールの切り替えの成功と業務の拒否を残します（`docs/operations.md` の「監査ログ」）。今の保存と同じ作業ロールへの切り替え・入力の誤り（400）・`ROLE_BUSY`・`GROUP_BUSY`・読み取りは残しません。

### 権限の受け渡し

ロールと権限の設定を YAML で書き出し、別の環境や同じ環境へ読み込みます。3つの口はどれも `ADMIN` です。読み込みは「確かめ」と「適用」の2段で、確かめは何も変えず、変わる点の一覧と指紋を返します。適用は同じ YAML と確かめの指紋を送り、確かめの後に状態が変わっていなければまとめて確定します。

| API | 成功 | 主な失敗 |
|---|---|---|
| `GET /api/admin/role-transfer/export` | 200 と `application/yaml` の添付（`role-permissions.yaml`）。本文が読み込みの上限を超えたら応答のヘッダー `X-Role-Transfer-Exceeds-Import-Limit: true` | 401・403 |
| `POST /api/admin/role-transfer/check`（本文は `application/yaml`） | 200 と `fingerprint`・`roles`（ロールごとの `name`・`roleId`（置き換えのとき）・`action`（`CREATE`・`REPLACE`）・`added`・`changed`・`cleared`・`notInDsl`・`changes`（対象ごとの `target`・`before`・`after`・`reason`・`inCurrentDsl`））・`untouchedRoles` | 400 `ROLE_TRANSFER_INVALID`（`errors` に `reason`・`line`・`column`・`path`、最大 100 件）・409 `DSL_NOT_APPLIED`・409 `ROLE_BUSY`・413 `PAYLOAD_TOO_LARGE`・415 `UNSUPPORTED_MEDIA_TYPE` |
| `POST /api/admin/role-transfer/apply`（本文は `application/yaml`、ヘッダー `X-Role-Transfer-Fingerprint` に確かめの指紋） | 200 と `created`・`replaced` | 400 `VALIDATION_FAILED`（指紋のヘッダーが無い・16 進数の小文字 64 文字でない。`fieldErrors` の `X-Role-Transfer-Fingerprint`）・400 `ROLE_TRANSFER_INVALID`・409 `ROLE_TRANSFER_STALE`・409 `DSL_NOT_APPLIED`・409 `ROLE_NO_CHANGE`（変わる点が無い）・409 `ROLE_NAME_DUPLICATE`・409 `ROLE_BUSY`・413・415 |

- **YAML の形**: `version: 1` と `roles`（ロールの名前をキーにした対応表）。ロールは `schemas`、スキーマとテーブルは `main`（`NONE`・`READ`・`FULL`）・`create`・`delete`（真偽）と下位の `tables`・`columns`、カラムは主権限の値だけを書きます。書かない項目は設定なしです。書き出しは、ロールを ID の順、対象を名前のコードポイントの順に並べ、設定のある対象だけを書き、YAML で型や特別な意味を持ちうる名前（`true`・`null`・数・日付・記号を含む名前・前後に空白のある名前など）は二重引用符で囲みます。別名とタグは作りません。
- **照らし方**: ファイルのロールは名前（大文字と小文字・前後の空白を除いた鍵）で今のロールと照らし、当たれば設定をファイルの状態に置き換え（名前は今のまま。ファイルに無い対象の設定は消える）、当たらなければ作ります。ファイルに無いロールは残します（`untouchedRoles`）。グループ・メンバー・割り当ては書き出さず、読み込みでも変えません。今の DSL に無い対象の設定も名前で持つ設定として読み込みます（`inCurrentDsl: false`、`notInDsl` に数える）。
- **指紋**: 作り直した変わる点の一覧（ロールの鍵の順・対象の順）と適用中の DSL の識別から作る SHA-256 の 16 進数の小文字です。サーバーは保存しません。確かめの後に別の操作でロール・設定が変わる、同じ名前のロールが作られる、DSL が適用し直されると、適用は 409 `ROLE_TRANSFER_STALE` になります（DSL が外れたときは 409 `DSL_NOT_APPLIED`）。確かめからやり直してください。
- **一括の確定**: 適用は、置き換えるロールの行を ID の昇順に排他してから、1つのトランザクションで作成・置き換えを書きます。途中で失敗すると何も変わらず、監査の成功の行も残りません。適用の間、同じロールへのほかの管理の操作は待ちの上限（3 秒）で 409 `ROLE_BUSY` になります。
- **信頼できない入力の守り**: 読み込みは上限つきの安全な読み込みだけで行います。上限は大きさ 5 MiB（5,242,880 バイト。確かめと適用の道ごとの本文の上限と同じ値）・入れ子の深さ 10・コレクションを指す別名 0（値を指す別名は受け付ける）・別名を展開した後の節 500,000・1行の長さ 65,536 文字（DSL と同じ。コードポイントで数え、改行は数えない。超えると本文が 5 MiB の内でも大きさの拒否と同じ 413 `PAYLOAD_TOO_LARGE` になり、画面では「大きすぎる」の文言で出ます）です（大きさと節の上限は、配備と同じ最大ヒープ 1 GiB での測りから決めた値です。1万カラムを明示したロールで、1ファイルに約 12〜19 ロール分です）。タグ・任意の型・重複キーを断り、知らない項目・版の誤り・値の誤り・カラムの `create`・`delete`・名前の規則の違反・ロールの重なりを `errors` に返します。応答に読み込みの部品の例外の文は載りません。`errors` の `path` はキーを点でつないだ形です（例 `roles.営業.schemas.SALES.main`）。
- **同時に1つずつ**: 確かめと適用は、アプリの中で同時に1つずつしか通しません。2つ目は待たずに 409 `ROLE_BUSY` で断り（監査に残さない）、WARN（`権限の受け渡しの入口を取れませんでした`、キーは `lockKind=ROLE_TRANSFER_SLOT` だけ）を1回出します。少し待ってからやり直してください。
- **大きい書き出し**: 書き出しは上限を超えても止めません。`X-Role-Transfer-Exceeds-Import-Limit: true` が付いたファイルはそのままでは読み込めない（413）ため、ロールの一部ずつに分けて、それぞれ確かめと適用を行ってください（ロールのキーごとに分ければ、各ファイルが独立して読み込めます）。
- **受け入れた制約**:
  - 分割送信（`Content-Length` の無い本文）は、既存の本文の大きさのフィルターが上限（5 MiB）まで先に読みます。入口（同時に1つずつ）はその後の読み込み・木・適用を守ります。
  - 本文をゆっくり送る管理者は、その間入口を持ち続けます（本文の読み込みの時間切れは Tomcat の既定に頼ります）。
  - 書き出しと、DSL の管理の 10 MiB の投入と適用は、入口に入りません（同時に動くとヒープを大きく使いえます。管理者の操作の頻度が低いことを前提にしています）。
  - 本文を読まずに断った要求（`ROLE_BUSY`・413・DSL の重い操作の 503 `DSL_BUSY` など）でも、送り手に応答を届けるため、Tomcat は最大 11MB（`server.tomcat.max-swallow-size`）の本文を読み捨ててから応答を返します。この読み捨ては**未認証の要求にも**働き、その間 Tomcat のスレッドを持ち続けます（ヒープには貯めません）。配備先が決まったときに、前段の大きさの上限と合わせて見直してください。
- **監査**: 適用の成功と業務の拒否（`ROLE_TRANSFER_STALE`・`DSL_NOT_APPLIED`・`NO_CHANGE`・`ROLE_NAME_DUPLICATE`）を1回1行残します（`docs/operations.md` の「監査ログ」）。確かめ・書き出し・入力の誤り（400・413・415）・`ROLE_BUSY` は残しません。
- **ログ**: YAML の中身（ロールの名前・対象の名前・値）はアプリのログに出しません（TRACE を有効にしても、受け渡しの値は大きさと件数だけで出ます。JDBC の部品の引数の TRACE（`org.springframework.jdbc.core.StatementCreatorUtils`）は `OFF` です）。

## 業務のメニューの API

ログインした利用者の業務のメニュー（適用中の DSL の `menus` を、作業ロールの実効の主権限で絞った N 階層の木）の API です。API の分類は `AUTHENTICATED`（ログインした利用者なら誰でも）で、読み取りだけです。テーブルの画面の置き場の問い合わせ（`GET /api/me/table-access`）はありません（呼ぶと 404。業務データの API の定義が置き場の権限を返します）。主体は要求の文脈から読み、利用者を指す値（`userId` などの引数）は読みません。画面は「骨組みの画面」にあります。

| API | 成功 | 主な失敗 |
|---|---|---|
| `GET /api/me/navigation` | 200 と `items`（項目の木）と `emptyReason` | 401 `AUTHENTICATION_REQUIRED`（未認証・停止中） |

- **項目**: 各項目は `id`（絞る前の DSL の木での位置の道。各段の 0 から数えた番号を `.` でつなぐ。例 `2.0`。落とした項目があっても番号を詰めない）・`label`（`{ja, en}`。DSL の値をそのまま。エスケープも空白の除去もしない）・`icon`（下の一覧で照らした名前）・`table`（移れる項目だけ `{schemaName, tableName}`、ほかは null）・`tableKind`（移れる項目が指すものがテーブルなら `TABLE`、ビューなら `VIEW`。まとまりと、DSL にテーブルが見つからない項目は null）・`navigable`・`items`（子）を持ちます。DSL の識別・ロールの ID・権限の値は載せません。
- **絞り方**: テーブルを指す項目は、そのテーブルの階層の実効の主権限が `READ`・`FULL` なら移れる項目として出ます（カラムの値は見ません）。テーブルが見えない項目は、子が残れば移れないまとまり（`navigable: false`・`table: null`）として残り、子も残らなければ落ちます。子が残らないまとまりはさかのぼって落ちます。残った項目の親子と並びは DSL のままです。管理のメニューは含めません。
- **空の理由**: `items` が空のときだけ値を持ちます。`NOT_CONFIGURED` は適用済みの DSL が無い・DSL の `menus` が空、`NOTHING_VISIBLE` は作業ロールが無い・すべて見えないなど絞った結果が空です（どちらも 200）。
- **反映**: 作業ロールの切り替え・権限の設定・割り当ての変更・DSL の適用は、次の要求の木に効きます（要求をまたいで写しを持ちません）。
- **アイコンの一覧**: 許したアイコンの名前は `backend/src/main/resources/navigation/allowed-icons.txt`（1行に1つ。`#` で始まる行と空行は読まない）にあります。DSL の `icon` が無い・空・一覧に無い（大文字と小文字・前後の空白も区別）ときは `list` になります。画面（サイドバーとホームのカード。`frontend/src/app/navigation/navIcon.ts` の1か所）は、`icon` が一覧にあり `list` でなければその名前を使い、`list` のときは `tableKind` で `TABLE` → `table`・`VIEW` → `view`、まとまり（移れない項目）は `folder`、種類の分からない移れる項目は `list` を出します（`icon` に `list` を書いた項目も、指定なしと同じ扱いになります）。ファイルが無い・読めない・名前が無い・`list` が無い・名前が重なるときは起動を止めます。make-you-chic-ui の固定先を上げてアイコンが変わったら、このファイルと `frontend/src/app/registry/allowedIcons.ts` の両方を直してください（一致は `frontend/src/app/registry/allowedNavIcons.test.ts` が、make-you-chic-ui の `Icon` の登録の名前に対する画面の欠けは型の検査の `ALL_ICONS_COVERED` が確かめます）。
- **監査とログ**: 監査に残しません。指標は既存の `http.server.requests` だけです。
- **受け入れた制約**:
  - p95 の警報はありません（応答時間の目標の確かめは Performance Validation で行います）。

## ロール・グループ・権限の受け渡しの画面

管理者は、サイドバーの管理の区画（またはホームの管理のカード）の「ロール」（`/admin/roles`）・「グループ」（`/admin/groups`）・「権限の受け渡し」（`/admin/role-transfer`）から開きます。利用者の管理の画面の行の「操作」に「ロールを見る」（その人のロールと出どころの読み取り）を足しました。画面は上の「グループの管理の API」「ロールと権限の API」だけを使い、サイドバーの項目を隠すのは表示の切り替えで、使えるかどうかはサーバー側（401・403）で決まります。管理者でない利用者が URL を直接開くと「この画面を使う権限がありません」の表示が出ます。

- **ロール**: 一覧（20 件ずつ）・作る・名前を変える・削除（割り当てがあると数と割り当てのタブへのリンクを出して削除しない）。ロールを開くと「権限の設定」と「割り当て」のタブ（道 `/admin/roles/{id}` と `/admin/roles/{id}/assignments`）。
- **権限の設定**: 左の木（スキーマ → テーブル）で選び、右の表で主権限（設定なし・NONE・READ・FULL）と CREATE・DELETE（スキーマとテーブル）を選んで「保存」。実効の値は文字（明示・継承の元・既定）で示します。今の DSL に無い設定には「⚠ 今の DSL に無い」の印と「設定を消す」。DSL が適用されていないときは DSL の管理への案内だけを出します。
- **未保存の確かめ**: 保存していない変更があるまま、木の別の節・タブ・サイドバー・ブラウザの戻るで移ろうとすると確かめ（「留まる」「移る」）が出ます。読み込み直し・タブを閉じるときはブラウザの確かめが出ます。上の帯の「ログアウト」でも確かめが出ます（ログアウトは道 `/logout` への移動のため）。
- **割り当て**: 利用者（出どころ「直接」「グループ 〇〇」）とグループを足す・外す。利用者の直接の割り当てを外して、その人のロールが無くなるときは、作業ロールが変わることを確かめます。
- **グループ**: 一覧・作る・名前を変える・削除、詳細でメンバーを足す・外す（外した後に、グループ経由で無くなったロールを知らせます）、割り当てたロールの読み取り。
- **権限の受け渡し**: 「書き出す」で全ロールの権限を YAML に保存（読み込みの上限 5 MiB を超えるときは案内）。ファイルを選んで「確かめる」と、ロールごとの変わる点（作る・置き換える、足す・変わる・消える）を示し、「適用する」で確かめた内容をそのまま送ります。確かめた後にロールの設定が変わっていると適用せず、確かめのやり直しを案内します。ファイルは 5 MiB まで（上限の確かめは案内で、正はサーバー側の 413）。
- **表示言語**: ブラウザの言語が英語なら英語、それ以外は日本語です。ロール・グループ・スキーマ・テーブル・カラムの名前と氏名は訳しません。
- **入れ替えの後**: 新しい版に入れ替えた後は、開いているタブを読み込み直してください（古い版の画面の部品の読み込みに失敗することがあります）。

## 骨組みの画面（作業ロール・業務のメニュー・業務データの画面・自分の権限）

ログインした後の画面の骨組み（make-you-chic-ui の AppShell）を、作業ロールと権限で絞った N 階層の業務のメニューに替えました。画面は上の「ロールと権限の API」「業務のメニューの API」だけを使います。メニューを隠すのは表示の切り替えで、見てよいかどうかはサーバー側（403）で決まります。

- **作業ロール**: トップバーの右に「作業ロール: 〇〇 ▼」を出し、割り当てられたロールが2つ以上なら一覧から切り替えます（結果は Toast で知らせます）。ロールが1つ・無いときは、一覧に理由を出します。画面の幅が 768px 未満では、トップバーではなく内容の領域の先頭に出します（幅 220px のサイドバーの横のトップバーに収まらないため）。
- **サイドバー**: 「ホーム」・「業務」（作業ロールで見てよいテーブルを指す項目だけ、5 段まで）・「管理」（管理者だけ。DSL・利用者の招待・利用者の管理・ロール・グループ・権限の受け渡しの順）の区画です。項目にはアイコンが付きます（業務の項目は上の「業務のメニューの API」の「アイコンの一覧」の決まり、管理の項目は画面ごとに決めたアイコン）。業務の区画のまとまりは開閉のボタンで開き、開閉の状態はタブを閉じるまで覚えます（ログアウトで消します）。画面の移動・作業ロールの切り替え・ログインのたびに業務のメニューを読み直します。
- **業務データの画面**: 業務のメニューの項目を選ぶと、`/tables?schema=…&table=…` の業務データの一覧（見出しはテーブルの表示名）を開きます。検索・並べ替え・ページ送り・1ページの件数（20・50・100）を選べ、行のリンクか行の「操作」の「詳細」で `/tables/row?…` の詳細を開きます。主キーの値と検索の値は道に載せません（詳細を開いたまま読み込み直すと一覧へ戻ります）。一覧の状態（検索の条件・ページ・件数・並べ替え）は、詳細から戻る・ブラウザの戻る操作では保ち、読み込み直すと既定に戻ります。見てよくないテーブルの道を直接開くと「このテーブルを見る権限がありません。作業ロールを確かめてください。」の表示で、テーブルの表示名は出しません。作成・更新・削除の画面もこの機能の中にあります。日時の表示と入力は下の「業務データの画面の日時」です。
- **自分の権限**: ユーザーメニュー・作業ロールの一覧・ホームの案内の「自分の権限を見る」（`/me/permissions`）で、今の作業ロールでのスキーマ・テーブル・カラムの権限を読み取りで見られます。表示の言語や作業ロールを替えると読み直します。
- **上のバーのロゴ**: トップバーにアプリのアイコン（`docs/app-icon.md` の `app-icon.svg` と同じ図）をロゴとして出します。押せない飾りで、画面の幅が 480px 未満では出しません。
- **ホーム**: 見出しと説明の下に、作業ロールの1行（「作業ロール: 〇〇」、無ければ「作業ロール: なし」。作業ロールを読み込んだ後だけ）、「業務」の入口のカード、案内、「管理」の入口のカードの順に並べます。新しい API は呼ばず、骨組みがすでに読んだ業務のメニューとログインの状態だけを使います。カードが 0 枚の見出しは出しません。
  - **業務のカード**: 業務のメニューの最上位の項目ごとに1枚（応答の順）。名前とアイコンはサイドバーと同じ決め方です（カードのアイコンは飾りで、読み上げには出しません）。押すと、テーブルを指す項目はそのテーブルの業務データの一覧へ、まとまりは子を応答の順に深くたどって最初に見つかる移れる項目の一覧へ移ります。移れる項目が無い最上位の項目のカードは出しません。
  - **管理のカード**: 管理者だけに、サイドバーの管理の区画と同じ項目を同じ順で出します（カードを隠すのは表示の切り替えで、使えるかどうかはサーバー側の 401・403 で決まります）。
  - **案内**: 業務のメニューが設定されていない・作業ロールが無い・表示できる業務のメニューが無い・読み込めなかった（［もう一度］）ときに案内を出します。
- **ログアウト**: ユーザーメニューの「ログアウト」は道 `/logout` への移動です（保存していない変更がある画面では確かめが出ます）。メニューを通らずに `/logout` を直接開いたときは、ログアウトせずにホームへ戻ります。
- **入れ替えの後**: 新しい版に入れ替えた後・前の版へ戻した後は、開いているタブを読み込み直してください（画面の部品の読み込みに失敗することがあります）。

### 業務データの画面の日時

業務データの画面（一覧・詳細・作成・更新・検索・他テーブル参照の選択肢とピッカー）は、時点を表す型（MySQL・MariaDB の `timestamp`、PostgreSQL の `timestamptz`。API の受け渡しの型 `DATETIME_TZ`）の値を、利用者の表示のタイムゾーン（`docs/users.md` の「プリファレンスとパスワードの変更の画面」の「表示のタイムゾーン」）で出し・受けます。サーバーとの受け渡しはいつも UTC です（`docs/target-db.md` の「日時・時刻の値」）。変換は `frontend/src/shared/format/timeZone/` の関数だけで行い、ブラウザの既定のタイムゾーンを暗に使いません。

- **表示**: 時点を表す型は `YYYY-MM-DD HH:mm:ss[.端数] ±HH:mm` で出します。端数はサーバーが返した桁のまま（丸めない・0 を足さない）です。時差は行ごとの時点で決まるため、夏時間のある地域では同じ一覧に `-04:00` と `-05:00`（`America/New_York` の例）が混じります。分の端数の時差（`+05:45`・`+09:30`・`-03:30` など）はそのまま、秒を含む歴史的な時差は `±HH:mm:ss` で出します。表・詳細・行のリンクと画面の題・削除の確かめの文・参照の選択肢の文（「ラベル (値)」）・ピッカーの結果は同じ書式です。参照のラベルは、定義の `labelValueType` でラベルのカラムの型が分かるときにその型で書式にし、分からなければ文字のまま出します。
- **時差を持たない型**: `datetime`（PostgreSQL の `timestamp`）・`date`・`time` は DB の値のまま出し（日付と時刻の区切りの `T` を空白にするだけ）、時差を添えません。表示のタイムゾーンを変えても変わりません。PostgreSQL の `timetz` は DB の値と時差のまま出します（`Z` は `+00:00` に書き換えます）。
- **読めない値**: サーバーが DB の文字のまま返した値（MySQL のゼロの日時など）は、その文字のまま出します（誤りの表示にしません）。
- **案内の1行**: 一覧・詳細の見出しの下に、その画面に時点を表す型のカラムがあるときだけ、「表示のタイムゾーン: 〇〇」（保存した名前）・「表示のタイムゾーン: ブラウザのタイムゾーン（〇〇）」（「ブラウザに合わせる」のとき）・「保存したタイムゾーンを使えないため、ブラウザのタイムゾーン（〇〇）で表示しています」（保存した名前をそのブラウザが解釈できないとき）のどれかと、プリファレンスの画面へのリンク「プリファレンスで変更」を出します。
- **表示のタイムゾーンの読み込み**: 時点を表す型のカラムを持つ画面は、ログイン直後の表示のタイムゾーンの読み込みが済むまで時刻を出しません（ブラウザのタイムゾーンの時刻を一瞬出すことはしません）。読み込みに失敗したときは、画面の上に「表示のタイムゾーンを読み込めませんでした。時刻を表示できません。」と「もう一度読み込む」を出し、時点を表す型のセルは「時刻を表示できません」、検索とピッカーの時点を表す型の欄は使えなくします。作成・更新の画面は、時点を表す型のカラムがあればフォームを開かず、読み込み直しが成功してから開きます。プリファレンスで表示のタイムゾーンを変えると、開いている一覧・詳細の時刻は読み込み直さずに切り替わります。作成・更新のフォームは、開いたときの表示のタイムゾーンを開いている間使い続けます（入れた文字の意味を途中で変えません）。
- **入力の形**: 時点を表す型と `datetime`（時差を持たない日時）の欄は、ブラウザの日時の入力ではなく文字の入力で、形は `YYYY-MM-DD HH:mm:ss`（秒の端数 1〜6 桁は任意。例 `2026-11-02 09:30:15.123`）だけです。全角の数字・`T` の区切り・秒の省略・暦に無い日付は「日時を YYYY-MM-DD HH:mm:ss の形で入れてください」の誤りです。時点を表す型の欄の下には「〇〇 (+09:00) で入力。例: …」の案内を出します（時差は今の時刻の時差のため、夏時間の地域では入れる日時の時差と違うことがあります）。`datetime` の欄は変換せず、案内にタイムゾーンを出しません。`date` は日付の入力、`time`・`timetz` は文字の入力のままです。フォーム部品が `select`・`radio`・`lookup` のカラムは、選択肢の値を変換しません。確かめは欄を離れたときと保存を押したときで、入力の途中には誤りを出しません。
- **存在しない時刻と2回ある時刻**: 夏時間の切り替えで飛ばされる時刻は「〇〇 では、この時刻はありません（夏時間の切り替えで飛ばされる時刻です）」の誤りで、保存しません（この判定は画面の側だけです）。2回ある時刻は、欄の下に「〇〇 では、この時刻は2回あります。どちらですか」と「先（-04:00）」「後（-05:00）」のような時差つきの2択を出し、選ぶまで保存できません（「どちらの時刻かを選んでください」）。欄の文字を書き換えると選択は未選択に戻ります。2択は作成の欄と、更新で値を変えた欄にだけ出ます。
- **送る値と更新**: 送るのは UTC の時点（`…+00:00`。端数は入れた桁のまま）だけです。更新の画面の初めの値は、表示のタイムゾーンの時刻から時差を除いた文字（端数は桁のまま）で、初めの値のままの欄は送りません（別の欄だけ直しても日時は変わりません。2回ある時刻の値もそのまま保たれます）。主キーと参照の値は、表示用の文字ではなくサーバーが返した文字のまま送り返します。
- **検索**: 時点を表す型の条件も表示のタイムゾーンで入れ、UTC の時点で送ります。範囲は始まりも終わりも含み、終わりに端数が無ければその秒ちょうどまでです（端数を含めるときは `23:59:59.999999` のように入れます）。始まりが終わりより後なら誤りで、存在しない時刻も誤りです。2回ある時刻は、範囲の検索では始まりを先・終わりを後の時点にして2択を出さず、一致の検索（検索の画面とピッカー）では2択を出します。一致は入れた桁で比べるため、秒の端数を持つ値は端数まで入れます（案内に出します）。DSL の検索の既定の値（`search.default`）は時点として読み（時差が無ければ UTC）、表示のタイムゾーンが読み込めた時点で1回だけ欄に入れます。ブラウザに残った一覧の状態に前の形（`T` の区切り）の日時の条件があるときは、欄に残して誤りを出し、その条件は送りません。

## API のアクセス制御

`/api/` の下は**既定でログインが必要**です。ログインなしで呼べるのは、次の明示した一覧だけです。

| パス | 置く単位 | 理由 |
|---|---|---|
| `/actuator/health` | アプリの骨格 | 起動確認 |
| `/api/problems/**` | アプリの骨格 | 誰でも読める説明文書 |
| `/api/auth/login` | 認証 | ログインする前に呼ぶ |
| `/api/auth/session/**` | 認証 | 更新は Cookie で認証し、ログアウトは期限切れでも呼べる必要がある |
| `GET /api/appearance`（GET だけ） | インスタンスの見た目の設定 | ログインの前の画面も見た目の設定を読む |
| `POST /api/registration/verify`・`POST /api/registration/complete`（POST だけ） | 招待と登録の完了 | 招待された人がログインの前にリンクを確かめ、登録を完了する |

- **管理者のみの範囲**: `/api/admin` そのものと `/api/admin/**` は管理者だけが使えます。未ログインは 401 / `AUTHENTICATION_REQUIRED`、管理者でない利用者は 403 / `ACCESS_DENIED` になります。存在しない管理 API も、管理者でない利用者には 403 になります（有無を明かさないため）。管理者かどうかは、要求ごとに内部DBから読んだ値で判断します。
- 管理者のみの API を足すときは、**`/api/admin/` の下に置いてください**（個々の API での宣言には頼りません）。それ以外の `/api/` の下は、置くだけでログインが必要になります。
- **確認用 API**: `GET /api/admin/check` は、管理者なら 204（内容なし）を返します（管理者でなければ 403）。今の画面はこれを呼びません。
- **正規化されていないパスの拒否**: エンコードされた区切り・`;`・`..`・連続した `//` などを含む要求は、判定の前に 400 / `REQUEST_REJECTED` で拒否します。応答はほかのエラーと同じ形（`type`・`code`・`traceId`）で、安全のためのヘッダーも付きます。拒否したパスはログに出しません。
- **画面**: サイドバーの「管理」の区画とホームの管理のカードは管理者にだけ表示されますが、これは表示の切り替えにすぎません。判定は必ずサーバー側で行われます。
- 環境変数は増えません。
- **登録の完了の公開の API**: 差し込み口（order 310）で上の2つの POST だけを公開します。`/api/registration/` のほかの道・ほかのメソッドはログインが必要です。公開の道でも、壊れた・期限切れのアクセストークンを付けると 401 になります（画面はトークンを付けずに呼ぶ）。**回数の制限は置いていません**（受け入れた危険 R1）。誤ったトークンで完了を呼ぶたびに監査に `REGISTRATION_FAILED` が1行増えます。急な増えに自動で気づく仕組みは無いため、`docs/operations.md` の「監査ログの確かめ方」の数える問い合わせで見つけます。
